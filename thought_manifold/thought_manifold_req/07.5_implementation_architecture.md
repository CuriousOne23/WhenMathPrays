# 07.5 Implementation Architecture

## 1. Purpose

This document serves as the operational translation layer between the conceptual requirements defined in `03_core_conceptual_requirements.md`, the high-level system architecture in `04_system_architecture.md`, and the detailed subsystem specifications. It defines the software architecture and implementation boundaries required for faithful realization of the Thought Manifold Simulator.

## 2. High-Level Module Breakdown

The simulator shall be organized into the following core modules with strict separation of responsibilities:

- **Manifold**: Manages geometric space, coordinate transformations, metric computations, and local coordinate charts.
- **PotentialFunction**: Encapsulates the differentiable potential landscape $V(\mathbf{x})$.
- **BasinSystem**: Handles Object Basins, Relational Basins, and Inquiry Basins.
- **ThoughtPoint**: Core entity representing the active thought state.
- **RegulatorSystem**: Implements anti-collapse stabilizers, flow modulators, volitional steering, and stability monitors.
- **SimulationEngine**: Orchestrates the main simulation loop and state evolution.
- **Logger**: Provides time- and event-indexed observability.

## 3. Module Interaction Rules

- The Manifold never calls the SimulationEngine or modifies ThoughtPoint state.
- Regulators never modify state directly; they return proposed modification deltas.
- The BasinSystem evaluates membership and recommends transitions but does not compute gradients, apply damping, or modify energy.
- The PotentialFunction never logs or updates state.
- The Logger is write-only and shall not influence simulation logic.

## 4. Core Data Structures & Interfaces

### 4.1 ThoughtPoint

- The central state carrier must include:
  - Position $\mathbf{x}$
  - Fuzzy embedding vector $\mathbf{e}$
  - Total energy $E = K + V(\mathbf{x})$
  - Normalized entropy percentage $H_\\%$
  - Remaining time budget
  - Current basin context

**Dimensionality Rule**: The ThoughtPoint is **strictly 0-dimensional**. It has no shape, size, radius, volume, mass, or physical extent. All dynamics, interactions, basin detection, and computations apply only to its coordinate and metadata.

**State Handling Rule**: ThoughtPoint shall be treated as immutable. Updates create new instances. Mid-tick mutation is prohibited.

## 5. Simulation Update Loop & Tick Semantics

The SimulationEngine shall execute the following strict ordered steps per tick:

1. Compute gradient $\nabla V(\mathbf{x})$
2. Apply perturbation terms
3. Apply damping and energy updates
4. Evaluate and activate regulators (by priority)
5. Perform numerical integration
6. Check basin transitions via BasinSystem
7. Update entropy $H_\\%$
8. Log major state changes and regulatory interventions

**Splitting/Merging Rules**:
- Governed by activation energy threshold and local curvature.
- Energy and entropy distributed proportionally.

**Transition Timing Rule**:
The consecutive-tick stability conditions apply **only while the ThoughtPoint remains inside the current Object Basin** for the purpose of setting the `canonicalization_achieved` flag.  
Once canonicalization is achieved and the Thought Simulator (TS) selects a target basin, the transition to the new basin shall occur on the **next simulation tick**. There is no mandatory dwell time after completion.

## 6. OB Exit and Energy Reinitialization (New)

**OB exit is a TS-driven routing event**, not a physical escape from the potential well.

- At the moment of canonicalization inside an Object Basin, the ThoughtPoint’s kinetic energy is effectively zero and its total energy approximates the OB floor potential: $E_{tot} \approx V(x_{OB})$.
- Upon TS routing to a new basin (typically a Relational Basin), the ThoughtPoint’s energy is **reinitialized** according to the new basin’s potential landscape and damping regime.
- This is a discrete context switch performed by the TS on top of the continuous manifold dynamics. It does not create discontinuities in the underlying manifold.

This hybrid approach (continuous diffeq dynamics inside basins + discrete TS routing between basins) preserves manifold smoothness while enabling clean cognitive state transitions.

## 7. Configuration Schema

Configuration shall be defined via structured YAML/JSON with sections for:
- manifold, basins, dynamics, regulators, entropy, simulation, thoughtpoint, observability.
- Must include validation rules against core invariants.

## 8. Numerical & Stability Considerations

- Curvature bounded ($|K| < K_{\max}$).
- Integration methods must preserve energy and entropy conservation within basins.
- Timestep adaptive in high-curvature zones.
- All operations must be deterministic and reproducible.

## 9. Error Handling & Fallbacks

- Curvature or NaN failures trigger stability monitor and full state logging.
- Conflicting regulators resolved by priority with logging.
- Ambiguous basin transitions default to current basin with diagnostic log.
- All errors must be logged with sufficient context for reproducibility.

## 10. Non-Functional Constraints

- **Determinism**: Same seed and configuration must produce identical results.
- **Reproducibility**: All random elements properly seeded and logged.
- **Observability**: Full visibility into state transitions and regulator actions.
- **Modularity**: Strict adherence to defined interfaces.
- **Traceability**: Every major decision links back to requirements.
- **Debuggability**: Detailed logging and state inspection required.

## 11. Implementation Notes for Coding Agents

- The 0-dimensional nature of the ThoughtPoint is a non-negotiable invariant.
- OB exit is a TS routing event, not a gradient-driven physical escape.
- Strictly respect all rules in Sections 3, 5, and 6.
- Any ambiguity must be resolved by referring first to `03_core_conceptual_requirements.md`, then this document.

## 12. Traceability to Conceptual Requirements

This implementation architecture directly realizes concepts from `03_core_conceptual_requirements.md`, `04_system_architecture.md`, and `07_manifold_structure.md`.
