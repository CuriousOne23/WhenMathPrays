# 07.5 Implementation Architecture

## 1. Purpose

This document serves as the operational translation layer between the conceptual requirements defined in `03_core_conceptual_requirements.md`, the high-level system architecture in `04_system_architecture.md`, and the detailed subsystem specifications. It defines the software architecture and implementation boundaries required for faithful realization of the Thought Manifold Simulator.

## 2. High-Level Module Breakdown

The simulator shall be organized into the following core modules with strict separation of responsibilities.

## 3. Module Interaction Rules (Strengthened)

- The Manifold never calls the SimulationEngine or modifies ThoughtPoint state.
- Regulators never modify state directly; they return proposed modification deltas only.
- The BasinSystem evaluates membership and recommends transitions but does not compute gradients, apply damping, modify energy, or execute state changes.
- The PotentialFunction never logs, updates state, or makes decisions.
- The Logger is write-only and shall not influence simulation logic.
- All interactions between modules occur exclusively through well-defined interfaces.

## 4. Core Data Structures & Interfaces (Tightened)

### 4.1 ThoughtPoint
- Position $\mathbf{x}$
- Fuzzy embedding vector $\mathbf{e}$ (dimensionality consistent with local manifold structure, may be adaptive)
- Total energy $E = K + V(\mathbf{x})$
- Normalized entropy percentage $H_\\%$
- Remaining time budget
- Current basin context

**State Rule**: ThoughtPoint shall be treated as immutable. Updates create new instances. Mid-tick mutation is forbidden.

### 4.2 BasinSystem Interface (Strengthened)
- Basin detection must use both potential gradient direction and local curvature signature.
- Transition occurs only when a ThoughtPoint remains within a basin's attraction zone for a configurable number of consecutive ticks **and** meets minimum energy/entropy criteria.
- The BasinSystem recommends transitions; the SimulationEngine executes them.

### 4.3 Regulator Interface (Strengthened)
- Each regulator returns a delta vector and strength value.
- When multiple regulators activate, the RegulatorSystem applies them in a fixed priority order (Anti-collapse → Flow modulation → Volitional steering → Stability monitors).
- Conflicting regulator actions must be resolved deterministically according to priority.

### 4.4 PotentialFunction API (Strengthened)
- Must support three explicit modes: `learned`, `hand_designed`, `hybrid`.
- Mode switching rules and behavioral differences must be clearly defined in configuration.
- In `hybrid` mode, learned components may only influence regions outside defined Object Basins unless explicitly allowed.

### 4.5 Entropy Calculation (Strengthened)
- $H_\\%$ shall be computed from the statistical spread and coherence of the embedding vector $\mathbf{e}$ relative to local manifold geometry.
- Use a combination of variance and KL-divergence from local basin prototypes.
- Normalization baseline must be global and consistent across all runs.
- Entropy is conserved during splits/merges and reduced primarily through settling in Object Basins.

## 5. Simulation Update Loop & Tick Semantics (Tightened)

The SimulationEngine shall execute the following **strict ordered** steps per tick:

1. Compute gradient $\nabla V(\mathbf{x})$ from PotentialFunction
2. Apply perturbation terms
3. Apply damping and energy updates
4. Evaluate and collect regulator deltas (by priority)
5. Perform numerical integration step (RK4 or symplectic)
6. Request basin transition recommendation from BasinSystem
7. Execute approved basin transition (if any)
8. Update entropy $H_\\%$
9. Log all major state changes and regulatory interventions

**Splitting/Merging Rules** (Explicit):
- Splitting allowed only when activation energy exceeds threshold and local curvature is below maximum.
- Energy and entropy distributed proportionally to activation weights based on embedding similarity.
- Merging occurs when two ThoughtPoints are in the same basin and their embedding similarity exceeds threshold.

## 6. Configuration Schema

Must explicitly define:
- Regulator priority order
- Splitting/merging thresholds
- Potential function mode and switching rules
- Entropy computation parameters
- Basin transition persistence requirements
