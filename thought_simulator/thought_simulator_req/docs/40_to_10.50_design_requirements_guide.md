## 1. Purpose

This guide describes how evidence from the 40-series thought simulator playground (Phase B prototypes, harnesses, artifacts, capsules, and requirements deltas) is translated into the **10.50 design requirements layer**.

The 10.50 layer (`10_thought_simulator_req/50_design/10.50.xx_*.md`) is the **realization-ready design requirements anchor**. It sits between:
- Exploratory 40 Phase B evidence (and 20 HLRs).
- 30 verification records.
- 50-series design specifications (which **must not** be started until relevant 10.50 + approved 30 peers exist — see 50.05 Pre-Construction Verification Requirement).

While [30.00_verification_user_guide.md](../../30_verification/30.00_verification_user_guide.md) is the standard process that **mandates** creating or updating the matching 10.50 peer whenever a 30.xx module is promoted, this document provides the **content and translation guidance** for turning raw 40 evidence into high-quality 10.50 artifacts.

It also covers batch promotion patterns used in waves (see W3 example below), where 40 evidence may flow into 10.50 via wave coverage notes even when not every 40 module has a dedicated full 30 peer yet.

## 2. When to Use This Guide (vs. 30.00)

- **Primary path (recommended for most modules):** Follow 30.00. It drives 10.50 creation/update in the same change set as the 30 peer. This ensures paired verification + requirements.
- **Direct or batch 40 → 10.50 (this guide):** Use when:
  - Performing wave-level 30 normalize (40.510 §4.2.2), where the wave coverage note aggregates many 40 capsules and drives targeted 10.50 updates.
  - A 40 module's evidence is mature enough for 10.50 but a full dedicated 30 peer is partial, deferred, or covered by a wave note.
  - 50 insight or construction (via the companion 50_to_10.50 flow down) identifies that 40 evidence needs to be more directly reflected in 10.50.
  - Early scaffolding of 10.50 before full 30 verification is complete (allowed per 30.00, with "pending 10.50" notes avoided where possible).

In all cases, 10.50 updates must be traceable back to 40 evidence and forward to 50 design.

## 3. Sources to Mine from 40

For a given 40 module (or group of modules in a wave), extract from these artifacts:

- `verification_capsule.md`: Run records, positive/negative ledgers, determinism evidence, flows alignment statements, contract/invariant checks, open gaps.
- `requirements_delta.md`: HLR mappings, structural/process requirements, rationale, impacted documents, W3 (or wave) promotion sections.
- `artifacts/*.json` (and any determinism runs): Concrete examples of inputs/outputs, state transitions, digests, error cases.
- `software_description.md`: Lifecycle phases, contracts (from_contract/apply_contract), role metadata, on-TP or integration behaviors.
- `prototype.py` + `harness.py` (read-only): For precise contract shapes, validator logic, and scenario coverage (do not copy code; extract the normative behavior).
- Three-flow statements and any joint/cross-module notes.

Prioritize **normative, realization-ready** content: invariants, exact field semantics, boundary conditions (e.g., `tr_needs_update` gate rules, no-write rules for DCB, role decomposition), determinism guarantees, overflow/degradation handling, and forbidden behaviors.

## 4. Recommended Structure for 10.50 Files

Base new or updated 10.50 files on the patterns in existing files (e.g., 10.50.180_tr_requirements.md, 10.50.150_tp_requirements.md, 10.50.160_basin_requirements.md).

Typical top-level sections:

1. **Purpose / Document ID** (with HLR/LLR contains list).
2. **Canonical HLR Set** (promoted / integration / architectural).
3. **Scope** (what is proven vs. target vs. deferred).
4. **Verification / Evidence Alignment** (cite 40 capsules + artifacts + dates; note 30 peers where present; wave note for batch).
5. **Detailed Requirements** (numbered, with traceability back to 20 HLRs and 40 sources).
6. **Cross-cutting Concerns** (determinism, observability, stability, forbidden reads/writes, lineage/provenance).
7. **Update History** (include entries for 40 Phase B dates and any wave 30 normalize or 50 flow-down updates).
8. **Downward Flow Notes** (if this 10.50 was refined from 50 work — see 50_to_10.50_flow_down_protocol.md).
9. **Open Items / Gaps** (with owners, e.g., "full TP.TR population — see 50 insight" or "live joint runs with 40.200/40.210").

Always include a **Flows Alignment** or source attribution note:
- Forward (from 20 HLRs).
- Backward (from 40 evidence / 30 verification).
- Iterative (from 50 design if applicable via flow down).

## 5. Wave / Batch Promotion Pattern (W3 Example)

For waves (per 40.510 §4.2):

- The **wave coverage note** (e.g., W3_pipeline_a_wave_coverage_note.md) is the primary aggregation artifact. It contains:
  - Promoted modules table mapping 40 sources → 30 modules (or "(wave note)") → HLR/contract coverage.
  - Contract check table (A-chain, gating, no-collapse, strip-replay, etc.).
  - Glossary alignment.
  - Open gaps (including "Full 30.XXX for all 12" and 10.50 peer notes).
  - Explicit 10.50 peers section ("Cross: 10.50.180 and 10.50.190 to receive W3 evidence").

- After (or as part of) creating the wave note:
  - Update [30.01_verification_inventory_index.md](../../30_verification/30.01_verification_inventory_index.md) with a W3 summary table and status notes.
  - Update relevant individual 10.50 peers (and their 30 counterparts where they exist) with W3 evidence sections.
  - Sync [50.00_design_traceability_index.md](../50_thought_simulator_design/50.00_design_traceability_index.md).
  - Record in 40.510 wave log.

Example (from W3):
- 40.240 (TR on-TP 10/10) + 40.200/40.210 joints → updated 10.50.180 (moved FLOW sections from "Not Proxy-Proven" to evidenced) + 30.180 W3 promotion section.
- 40.260 basin decomposition + role split → 10.50.160 + 30.160.
- New role primitives (40.190 RB, 40.200 OB, 40.230 TB) carried primarily via the wave note + noted for future dedicated 10.50/30 bands.

This allows the wave to close 30 normalize without forcing 12 brand-new 30 directories on day one (40 numbering is independent of 10.50/30 numbering per 30.00).

## 6. Relation to 30 Verification

- 30.00 is the **verification** promotion. It produces human-readable evidence (capsules, deltas, artifacts) and **requires** the 10.50 peer in the same change set for "promoted" status.
- This 40→10.50 guide is the **requirements authoring** companion. The content you put into 10.50 comes from 40 (and 20), while 30 provides the independent verification that the 40 implementation matches the intent.
- In practice they are done together for individual modules. For waves they can be staggered: wave note + selective 10.50 updates first, followed by fuller 30 peer refreshes.

If a 10.50 is updated via this guide without a simultaneous 30 peer refresh, note it in 30.01 (e.g., "10.50 updated from 40 W3 evidence; 30 peer refresh pending per wave open gap").

## 7. Traceability and Tooling Requirements

- Every normative statement in 10.50 **MUST** cite sources (20 HLRs + 40 capsule/artifact paths + dates).
- Update 50.00_design_traceability_index.md in the same change set when 10.50 content or mappings change.
- Run or note the results of pairing validators (e.g., validate_30_10_50_pairing.py) and any design sync checks.
- For wave-driven updates, also update the relevant wave coverage note and 40.510 log.

## 8. Three-Flow in 10.50 Updates

All 10.50 files (new or updated) **SHALL** document the three flows for their content:
- **Forward Flow**: Driven by 20-series HLRs and architecture.
- **Backward Flow**: Driven by 40 Phase B evidence (cite specific capsules, runs, and scenarios).
- **Iterative Flow**: Driven by 50 design work or prior 10.50 authoring (especially via 50→10.50 flow down).

Include a short Agreement Statement.

## 9. Examples of Good 40 → 10.50 Translation

- From 40.240 W3 harness (gating + atomic TP.TR + DCB consumption negatives) → 10.50.180 added precise "TR routine runs iff tr_needs_update=true", "atomic TP.TR write + clear on success only", "reject DCB-direct" requirements with citations to W3-TC00x and the 2026-06-09 artifact.
- From 40.260 positive_w3_basin_decomposition (role metadata, distinct basin_ids, per-role replay) → 10.50.160 (and 30.160) strengthened "roles not collapsed" and "strip-replay without legacy generic IDs".
- Batch via W3 wave note contract check table → cross-cutting rules in multiple 10.50 files (e.g., "no truth_hypotheses in OB/DCB/TB early").
