## Purpose

This document defines the standard process, naming convention, and file structure for verification work in the 30-series.

## Role in the Development Flow

The 30-series is the **evidence and verification layer**. It consumes prototypes from the 40-series and design decisions from the 50-series, then produces verifiable results that help mature the 10-series.

## Core Principles

- Verification must be **evidence-based**.
- Every verification document must clearly record the contribution of the **three flows** (Forward, Backward, Iterative).
- Failures and partial results are highly valuable and must be documented honestly.

## Three-Flow Documentation Requirement

All verification documents **SHALL** include a **Flows Alignment Statement** that explicitly records:

- **Forward Flow**: Which parts were driven by 20-series guidance
- **Backward Flow**: Which parts were driven by previous 40-series evidence
- **Iterative Design Flow**: Which parts were driven by 50-series design decisions

**Agreement Statement**: A short paragraph explaining why the three flows are in agreement (or noting any remaining tension / justification).

---

## Standard Subdirectory Naming

When a 40.xx module reaches sufficient maturity, create a matching verification subdirectory using this exact naming pattern:

**`30.xx_[component]_prototypes`**

**Example:**  
`40.36_gb_prototypes` → `30.36_gb_prototypes`

---

## Required Files in Each 30.xx Subdirectory

Every 30.xx verification folder **SHALL** contain at minimum the following files:

| File                                      | Purpose | Why It Exists |
|-------------------------------------------|--------|---------------|
| `30.xx_xxx_verification_capsule.md`       | Main test results, scenarios executed, PASS/PARTIAL/FAIL summary, and observations | Provides the primary evidence record and executive summary |
| `30.xx_xxx_requirements_delta.md`         | Mapping of 20-series HLRs to what was implemented/tested, including three-flow breakdown | Ensures traceability and gap analysis between intent and reality |
| Optional: `xxx_verification_run_YYYY-MM-DD.json` | Raw output data from verification runs | Preserves reproducible raw data for future analysis |

---

## Associated 10.50 File Requirement

For every 30.xx verification subdirectory, a corresponding **10.50** design requirements file **MUST** also be created or updated in the `10_thought_simulator_req/50_design/` directory.

**Naming Convention:**  
`10.50.xx_[component]_design_requirements.md`

**Example:**  
`30.36_gb_prototypes` → `10.50.36_gb_design_requirements.md`

**Purpose of the 10.50 file:**  
To translate the exploratory evidence from the 40-series and verification results from the 30-series into **normative design requirements** that will eventually feed the canonical 10-series specification.

This file should be created **after** the 30.xx verification is approved, ensuring design decisions are grounded in real evidence.

---

## Standard Process

1. Create the matching `30.xx_[component]_prototypes` subdirectory.
2. Create or update the corresponding `10.50.xx_[component]_design_requirements.md` file.
3. Run verification using the 40-series prototype.
4. Populate the verification capsule and requirements delta with the three-flow breakdown.
5. Obtain explicit human approval before promoting evidence to further 50-series or 10-series work.

**Please refer to 40.20_master_program_guide.md** for the overall development flow and iteration rules.
