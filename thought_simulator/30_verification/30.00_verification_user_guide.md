## Purpose

This document defines how verification evidence should be created, structured, and maintained in the 30-series. It ensures consistency and traceability across all verification capsules and summaries.

## Role in the Development Flow

The 30-series is the **evidence and verification layer**. It consumes prototypes from the 40-series and design decisions from the 50-series, then produces verifiable results that help mature the 10-series.

## Core Principles

- Verification must be **evidence-based**, not assumption-based.
- Every verification capsule must clearly show which flows (Forward, Backward, Iterative) contributed to the current state.
- Verification should be **reproducible** (clear commands, inputs, and expected outputs).
- Failures and partial passes are **highly valuable** and must be documented honestly.

## Standard Structure for Verification Documents

Every major verification document in the 30-series should include:

1. **Flows Alignment Statement** (Forward / Backward / Iterative)
2. **Verification Summary** (PASS / PARTIAL / FAIL + metrics)
3. **Key Evidence / Test Results** (tables preferred)
4. **Alignment with 20-series** (with HLR references)
5. **Discoveries & Open Questions** for 10-series
6. **Verdict** and recommendations

## Recommended Files per Module (e.g., 30.36)

- `30.36_gb_prototypes_verification_capsule.md` — Detailed test results
- `30.36_gb_requirements_delta.md` — Mapping to 20-series HLRs
- JSON run artifacts (optional, for raw data)

## Best Practices

- Always run verification after changes in 40-series or 50-series.
- Keep verification lightweight during early exploration.
- Increase rigor as components move toward promotion to 50/10-series.
- Use tables for clarity when showing test scenarios and outcomes.
