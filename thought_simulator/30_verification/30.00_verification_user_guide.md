## Purpose

This document defines the standard process, naming convention, and file structure for verification work in the 30-series.

## Role in the Development Flow

The 30-series is the **evidence and verification layer**. It consumes prototypes from the 40-series and design decisions from the 50-series, then produces verifiable results that help mature the 10-series.

**Executing 30.00 means executing the full forward-flow promotion slice**, not only creating `30.xx` folders. An approved `40.xx` module does **not** promote directly to `50.*`; it first establishes **`10.50.*` + `30.*`** ([USER_GUIDE.md](../USER_GUIDE.md), [50.05](../50_thought_simulator_design/50.05_software_spec_construction_guide.md) § Pre-Construction Verification Requirement).

| Layer | Path | Role in promotion |
|-------|------|-------------------|
| 40 | `40_thought_simulator_playground/40.xx_*/` | Exploratory evidence source (Phase B PASS) |
| **10.50** | `10_thought_simulator_req/50_design/10.50.xx_*.md` | **Realization-ready design requirements anchor** — required peer for every promoted `30.xx` module |
| 30 | `30_verification/30.xx_*/` | Canonical verification record (this guide) |
| 50 | `50_thought_simulator_design/50.xx_*.md` | Subsystem design spec — only after **10.50 + approved 30** exist |

## Core Principles

- Verification must be **evidence-based**.
- Every verification document must clearly record the contribution of the **three flows** (Forward, Backward, Iterative).
- Failures and partial results are highly valuable and must be documented honestly.

## Three-Flow Documentation Requirement

All verification documents **SHALL** include a **Flows Alignment Statement** that explicitly records:

- **Forward Flow**: Which parts were driven by 20-series guidance
- **Backward Flow**: Which parts were driven by previous 40-series evidence
- **Iterative Design Flow**: Which parts were driven by 50-series design decisions

**Agreement Statement**: A short paragraph explaining why the three flows are in agreement (or noting any remaining tension / justification).

## Standard Subdirectory Naming (30 driven by 10.50)

**40 naming is standalone/independent.** A 40.xx module may use any numeric band chosen inside the 40-series playground. There is no requirement that the 40 number match the eventual 30 or 10.50 number.

**30 numbering is dictated by 10.50** (10.50 comes first as the canonical requirements anchor).

When promoting evidence (from any 40 source, or other origins), create the 30 verification subdirectory using the **same numeric band as its 10.50 peer**:

**`30.xx_[component]_prototypes`**  (where xx matches the chosen 10.50.xx)

**Examples (post-independence):**
- Evidence may come from `40.392_core_data_structs_prototypes` (or any other 40 number) → you may create `10.50.392_...` (or a different band) + `30.392_..._prototypes` using the 10.50 band.
- A new 40.777 module could promote via a newly created `10.50.205` + `30.205_*` (different number).

The originating 40 number and the 30/10.50 band no longer need to be the same.

---

## Required Files in Each 30.xx Subdirectory

Every 30.xx verification folder **SHALL** contain at minimum the following files:

| File                                      | Purpose | Why It Exists |
|-------------------------------------------|--------|---------------|
| `30.xx_xxx_verification_capsule.md`       | Main test results, scenarios executed, PASS/PARTIAL/FAIL summary, and observations | Primary human-readable evidence record |
| `30.xx_xxx_requirements_delta.md`         | Mapping of 20-series HLRs to what was implemented/tested, including three-flow breakdown | Traceability and gap analysis |
| `codename_verification_run_YYYY-MM-DD.json` | Raw output data from verification runs (e.g. `gb_verification_run_2026-06-04.json`) | Preserves reproducible raw data for future analysis and debugging |

## Associated 10.50 File Requirement (non-optional)

For every `30.xx` verification subdirectory, a corresponding **10.50** design requirements file **MUST** be created or updated **in the same change set**. Creating `30.xx` artifacts without the matching `10.50.xx` file is a **partial promotion** — not a complete execution of this guide.

**The 30 numeric band is chosen to match the 10.50** (10.50 is the authoritative anchor; 30 follows it). 40 sources may use completely different numbers.

**Naming Convention:**  
`10.50.xx_[component]_design_requirements.md`

**Location:**  
`10_thought_simulator_req/50_design/`

**Examples (illustrative; bands chosen to match 10.50 peers):**

| 30 module | Required 10.50 peer |
|-----------|---------------------|
| `30.392_core_data_structs_prototypes` | `10.50.392_core_data_structs_design_requirements.md` |
| `30.205_...` | `10.50.205_...` (could come from any 40 module or direct 10.50 authoring) |

**Purpose:** Translate exploratory evidence and verification results into normative, realization-ready design requirements. **50-series design specs MUST NOT be started** for a component until its 10.50 peer and approved 30 evidence exist.

Each `30.xx_*_requirements_delta.md` **SHALL** include an **Associated 10.50** line naming the peer file path (or `pending` with owner/date if explicitly deferred — deferral must be recorded in the wave/program log, not silently omitted).

## Standard Process

Use this order. Do **not** skip step 1 because step 3 is labeled “30.”

1. **Create or update** the `10.50.xx_[component]_design_requirements.md` in `10_thought_simulator_req/50_design/` (the 10.50 band may be newly chosen or may differ from any originating 40 module's number; translate verified evidence + 20 anchors into realization-ready requirements). 40 naming is independent.
2. Create the `30.xx_[component]_prototypes` subdirectory under `30_verification/` using the **same xx band** as the 10.50 peer.
3. Run verification using the 40-series prototype (or promote an existing Phase B PASS artifact) — the 40 source may have used a different number than the 30/10.50 band.
   (Future high-fidelity test benches will also feed 30-series verification evidence via the `30.tb/` structure. Only normalized text records (capsules/deltas) are stored in the repo; raw outputs, logs, artifacts, etc. from test benches are excluded via .gitignore rules in testbenches/ and 30.tb/.)
4. Populate the verification capsule, requirements delta, and JSON run artifact with the three-flow breakdown. Cross-link the **10.50 peer** in the delta and capsule.
5. Update [30.01_verification_inventory_index.md](30.01_verification_inventory_index.md) when the module folder or promotion status changes.
6. Obtain explicit human approval before treating evidence as ready for **50-series** design work.

### Promotion completeness checklist

Before marking a module **promoted** (or **approved**) in `30.01`, confirm:

| # | Item | Required for `promoted` | Required for `approved` |
|---|------|-------------------------|-------------------------|
| 1 | `10.50.xx_*` peer exists on disk | **Yes** | **Yes** |
| 2 | `30.xx` capsule + delta + JSON artifact | **Yes** | **Yes** |
| 3 | Delta/capsule cite 10.50 peer path | **Yes** | **Yes** |
| 4 | `30.01` row updated | **Yes** | **Yes** |
| 5 | Explicit human sign-off recorded | No | **Yes** |

**Partial promotion** (30-only, no 10.50): record status note `30-only pending 10.50` in `30.01` Notes — do **not** treat wave “30 normalize” or forward-flow promotion as complete.

**Wave / program context:** Playground wave step “30 normalize” (e.g. [40.510](../40_thought_simulator_playground/40.510_refactor.md) §4.2.2) means **this full checklist**, not 30-folder creation alone.

### CI enforcement (30 ↔ 10.50 pairing)

| Check | Mode | Rule |
|-------|------|------|
| `scripts/validate_30_10_50_pairing.py` | **Warning** (exit 0) | Every `30.01` row with status **`promoted` or `approved`** must have a matching `10.50.{band}_*.md` in `10_thought_simulator_req/50_design/` |

- **One-way only:** 30 → 10.50. Orphan `10.50` files (no 30 module yet) do **not** warn — 10.50 may be authored before verification.
- **`seeded` rows** are excluded (legacy inventory).
- **`30-only pending 10.50`** in Notes documents known debt; the warning remains until the peer file exists.
- **Renames:** if a `10.50` band changes, update `30.01` (and module folder name if needed) in the same change set; the check uses the numeric band from the module dir or an explicit `10.50.NNN` reference in Notes.

## Controlled identity rename (30 ↔ 10.50)

30 and 10.50 renames are **address maintenance only** — no verification re-review when conclusions are unchanged.

**Rules:**

- Always rename **both peers atomically** in one PR (10.50 file + `30.xx_*` folder)
- Use `scripts/rename_identity.py` with `tier: "30-1050"` in the request JSON
- Update `30_name_table.json`, `10.50_name_table.json`, and `30.01` in the same change set
- Run `validate_name_tables.py` and the full pre-PR validation suite

**Rename classes:**

| Class | Band changes? | ID prefix changes? |
|-------|---------------|-------------------|
| A — slug/path | No | No |
| B — band | Yes | Yes (`HLR-10.50.xx-*`, `LLR-30.xx-*`, `Document ID`) |

Policy: [00.00.43_controlled_identity_rename_policy.md](../00_program_governance/00_foundations/00.00.43_controlled_identity_rename_policy.md).
