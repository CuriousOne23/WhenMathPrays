# 30.160_Verification Glossary

This glossary defines the canonical vocabulary used across `40_thought_simulator_playground/` and its verification structure.

## Terms

### scenario
A named verification path executed by `harness.py` to validate one or more requirements, invariants, or failure conditions.

### scheduler
The deterministic selection mechanism that chooses active ThoughtPoints for each tick based on an explicit policy and tie-break rules.

### fairness
The scheduler property that ensures active ThoughtPoints continue to receive bounded execution opportunities over time.

### tie-break
A deterministic ordering rule applied when multiple ThoughtPoints have equal scheduling priority.

### starvation prevention
Scheduler constraints and policy behavior that prevent any eligible ThoughtPoint from being indefinitely skipped.

### artifact
Any persisted evidence produced by a verification run, including JSON snapshots, logs, capsule reports, or failure payloads.

### deterministic_mode
A boolean execution mode indicating that identical inputs must produce identical outputs, identity values, and state transitions.

### provenance
The lineage record for a ThoughtPoint or related object, including creation source, parent IDs, split children, and merge sources.

### merge event
A lifecycle operation that combines multiple source ThoughtPoints into a single resulting ThoughtPoint with traceable lineage.

### split event
A lifecycle operation that deterministically branches one ThoughtPoint into multiple child ThoughtPoints with traceable lineage.

### IO fields exercised
The specific inbound and outbound variables that a scenario used, validated, or observed during a run.

### negative-path coverage
Verification of expected failures or invariant enforcement when invalid inputs, invalid states, or unsupported operations are exercised.

### tp.tr
The TP semantic routing block produced by the TR routine and consumed by RB/downstream modules for routing-consistent behavior.

### tr_needs_update
Boolean TP dirty flag indicating whether TP.TR is stale and must be recomputed by the TR routine.

### tr dirty-flag lifecycle
The normative lifecycle for `tr_needs_update`: initialize true on TP creation, set true on routing-relevant semantic writes, clear only after successful TR execution, and preserve true on TR failure.

### rb-tr gate
The deterministic routing rule that RB invokes the TR routine if and only if `tr_needs_update=true`.

### parallel execution suitability
A measure of whether a module can be safely run or reasoned about alongside others without shared mutable state or hidden coupling.

### requirement emission
The act of printing or recording HLR/LLR identifiers during execution so a run can be traced back to the requirements it verifies.

### harness entrypoint
The single execution file for a module, responsible for orchestrating verification scenarios and producing evidence.

### verification capsule
The canonical module-level verification report that merges run history, evidence, failures, traceability, and architectural evaluation.

### requirements delta
The module-level record of requirement changes, proposed updates, and implementer feedback that emerged from verification or refactoring.

## Usage Rules

- The glossary is authoritative for terms used in `verification_capsule.md`, `requirements_delta.md`, and `40.05_master_program_guide.md`.
- New modules should reuse these definitions rather than inventing near-duplicates.
- If a term changes meaning, update this file first and then propagate the revision through the verification structure.
- Requirements-driven glossary terms are tracked in `glossary_term_registry.json` under `required_by_module`.
- CI warning check ([../scripts/validate_glossary_alignment.py](../scripts/validate_glossary_alignment.py)) is bidirectional and warns on any mismatch: required terms missing from glossary or glossary terms not required by the registry.
- If a term is intentionally deprecated, update both this glossary and `glossary_term_registry.json` in the same change set.
