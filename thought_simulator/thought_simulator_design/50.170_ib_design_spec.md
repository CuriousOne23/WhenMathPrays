# 50.170_IB Design Specification

## 1. Purpose and scope

The Inquiry Basin (IB) subsystem is the canonical container for inquiry‑state evolution, TP‑tagged evidence, and GB‑mediated lifecycle control. As stated in the canonical requirement anchor, “This document is the canonical Inquiry Basin (IB) requirement anchor for promotion-governed asynchronous creation, bounded inquiry evolution, supervised lifecycle transitions, and deterministic TP-tagged observability behavior.”   

This design specification defines the architectural contracts, lifecycle behavior, IO semantics, observability obligations, and verification coupling for IB in the design layer. It is scoped to:

- asynchronous GB‑approved IB creation from inquiry requests  
- deterministic, bounded inquiry evolution and TP tagging  
- split/merge lifecycle behavior and retirement  
- GB‑mediated promotion to OuB‑ready outputs  
- deterministic reject‑with‑audit behavior for routing, sequence, and safe‑boundary violations  
- TCU‑bounded execution expectations for IB tick participation   

IB does not define TR behavior, TP core dynamics, or OuB rendering; it consumes TP‑related inputs and produces OuB‑ready outputs under GB supervision.

## 3. Contracts and invariants

### 3.1 Creation and authority contracts

- **GB‑approved creation only:**  
  IB instances MUST be created only via an IB‑Creation‑Request flow that has received explicit GB approval. “IB must be instantiated only after GB approval from an IB-Creation-Request flow.”   
- **Asynchronous creation:**  
  Creation is asynchronous with respect to upstream inquiry requests; IB creation requests are queued, evaluated by GB, and only then materialize as `active_ibs`.  
- **No direct OuB routing:**  
  IB MUST NOT accept direct OuB routing from external channels; all OuB‑ready outputs are produced via GB‑mediated promotion paths. “IB must receive inquiry evidence through OB<->IB interaction and must reject direct OuB routing.”   

### 3.2 Bounded evolution and state invariants

- **Deterministic bounded evolution:**  
  For fixed inputs and sequence, IB inquiry state (hypotheses, evidence requests, depth, TP tags) MUST evolve deterministically and remain bounded. “IB must preserve deterministic inquiry-state fields and bounded evolution state.”   
- **Append‑only TP tagging:**  
  TP‑tagged logs (`tp_log`) are append‑only; existing entries are never mutated or removed, preserving replayability and auditability.  
- **Lifecycle monotonicity:**  
  IB lifecycle transitions (created → active → split/merged → promoted/retired) MUST be monotonic; once retired, an IB MUST NOT re‑enter active service.

### 3.3 Routing, safe‑boundary, and sequence invariants

- **Sequence‑driven lifecycle:**  
  All lifecycle‑affecting events MUST carry a monotonically increasing `sequence` token; out‑of‑order sequence MUST be rejected with deterministic reason codes, as evidenced by `negative_sequence_violation`.   
- **Safe‑boundary gating:**  
  Supervisory lifecycle transitions (merge, promotion, retirement, supervisory overrides) MUST be gated by `safe_boundary = true`. “IB supervisory actions must be applied only at deterministic safe boundaries.”   
- **Direct OuB bypass rejection:**  
  Any attempt to route outputs directly to OuB without GB‑mediated promotion MUST be rejected with a fixed reason code, as captured in `negative_direct_oub_bypass`.   

### 3.4 Merge, promotion, and retirement invariants

- **Deterministic merge:**  
  Merge operations MUST deterministically construct a merged IB state (`merged_ib_id`) from a set of `source_ib_ids`, and MUST retire the sources under GB reference. “IB merge operations must instantiate deterministic merged state and retire sources under GB-approved control.”   
- **GB‑mediated promotion:**  
  Promotion to OuB‑ready output MUST be GB‑mediated and MUST NOT mutate OB registry state directly. “IB promotion to OuB must occur only after GB approval and must not mutate OB registry state.”   
- **Append‑only lifecycle audit:**  
  All lifecycle transitions MUST be explicitly logged and observable via an append‑only `audit_log`, as required by HLR‑20.090‑019 and evidenced in the 30.170 capsule.   

### 3.5 TCU and execution invariants

- **Bounded per‑tick cost:**  
  For any tick with fixed input cardinality \(N\) and fixed configuration, IB MUST complete its work within a bounded number of CPU cycles \(C_{\max}(\text{ib})\) per tick phase, as constrained by 20.150. “No unbounded or data-dependent worst-case growth is permitted.”   
- **Deterministic cycle behavior:**  
  For fixed seed, \(N\), configuration, and hardware/runtime profile, IB MUST exhibit deterministic CPU cycle consumption within \([C_{\min}(\text{ib}), C_{\max}(\text{ib})]\) for the same scenario ID.   
- **Provisional vs measured budgets:**  
  IB MUST maintain distinct `provisional-budget(ib)` and `measured-budget(ib)` values; these MUST NOT be conflated in normative documents, and measured budgets MAY ONLY be updated via promotion‑controlled 30‑layer evidence.   

## 4. Operation flow and state transitions

### 4.1 High‑level lifecycle phases

1. **Creation request and GB approval**  
   - IB‑Creation‑Request is logged as a pending request.  
   - GB evaluates and issues a decision (`approve`/`reject`).  
   - On approval, a new IB is instantiated and added to `active_ibs`.  
   - Evidence: `async_creation_approval` scenario in 30.170 capsule.   

2. **Active inquiry evolution**  
   - IB maintains hypotheses, pending evidence requests, depth, and TP tags.  
   - Evolution is driven by deterministic deltas (`hypothesis_delta`, `evidence_request_delta`, `depth_increment`).  
   - Evidence: `deterministic_evolution_tp_tagging`.   

3. **Split and merge lifecycle**  
   - Split: an active IB may spawn child IBs with `child_suffixes` and updated branch state.  
   - Merge: a set of `source_ib_ids` is merged into `merged_ib_id`, with sources retired and lineage recorded.  
   - Evidence: `split_merge_lifecycle`.   

4. **Promotion and retirement**  
   - When IB reaches OuB‑ready state, GB may promote it by assigning an `oub_output_id` and retiring the IB.  
   - Promotion does not mutate OB registry directly; it produces a promotion record consumed by OuB.  
   - Evidence: `promote_and_retire`.   

5. **Negative‑path handling**  
   - Direct OuB bypass attempts → `negative_direct_oub_bypass`.  
   - Safe‑boundary violations → `negative_safe_boundary_violation`.  
   - Sequence violations → `negative_sequence_violation`.  
   - All negative paths produce deterministic reject reason codes and append‑only audit entries.   

### 4.2 Event model and sequencing

IB behavior is driven by a sequence‑controlled event stream. Each event includes:

- `event_type` (e.g., `create_request`, `gb_decision`, `evolve`, `split`, `merge`, `promote`, `retire`)  
- `sequence` (monotonic integer)  
- `safe_boundary` (bool, required for supervisory actions)  
- payload fields (IB IDs, deltas, GB references, OuB output IDs, etc.)

Rules:

- `sequence` MUST strictly increase by 1 for each accepted event; out‑of‑order events are rejected.  
- `safe_boundary = true` is required for supervisory lifecycle events (merge, promote, retire, GB overrides).  
- Event application is pure and deterministic for fixed inputs; replaying the same event stream yields the same IB state and determinism digests (as evidenced by `creation_digest` and related fields).   

### 4.3 Tick participation and TCU behavior

Within a TS tick:

- IB processes at most a bounded number of events per tick, consistent with `C_max(ib)` and the global tick budget share defined by 10.50.170.TCU.40.   
- IB MUST NOT introduce unbounded per‑tick work due to unbounded queue growth; lifecycle and evolution queues are bounded by design.  
- TCU measurement harnesses (in 40‑layer and 30‑layer) will eventually record `scenario_id`, `seed`, `N`, `config_hash`, and `cycles_measured` for IB scenarios, but this design spec treats those as verification obligations rather than implementation details.   

## 5. Data and IO contract

### 5.1 Inbound contract

IB inbound contract (conceptual, JSON‑compatible):

- **Creation and GB approval**  
  - `event_type`: `create_request|gb_decision`  
  - `snapshot_id`: inquiry snapshot reference (for creation)  
  - `request_id`: unique creation request identifier  
  - `decision`: `approve|reject` (GB decision)  
  - `gb_reference`: GB decision provenance  

- **Evolution**  
  - `event_type`: `evolve`  
  - `ib_id`: target IB identifier  
  - `hypothesis_delta`: structured change to hypotheses  
  - `evidence_request_delta`: structured change to pending evidence requests  
  - `depth_increment`: integer depth change  
  - `tp_tag`: TP‑tagging metadata for this evolution step  

- **Split / merge**  
  - `event_type`: `split|merge`  
  - `ib_id`: source IB (for split)  
  - `child_suffixes`: list of suffixes for child IB IDs (split)  
  - `source_ib_ids`: list of IB IDs to merge  
  - `merged_ib_id`: resulting IB ID  

- **Promotion / retirement**  
  - `event_type`: `promote|retire`  
  - `ib_id`: IB to promote/retire  
  - `oub_output_id`: OuB‑visible output identifier (promotion)  
  - `gb_reference`: GB approval reference  

- **Control / supervisory**  
  - `event_type`: `suspend|reshape|override` (future extensions)  
  - `safe_boundary`: MUST be true for supervisory actions  
  - `sequence`: lifecycle ordering token  

### 5.2 Outbound contract

IB outbound contract (conceptual, JSON‑compatible):

- `active_ibs`: list of active IB descriptors (IDs, depth, hypothesis summary, pending evidence counts, lineage).  
- `pending_requests`: list of pending creation requests.  
- `retired_ibs`: list of retired IB IDs with retirement reason and lineage.  
- `promoted_outputs`: list of OuB‑ready outputs with `oub_output_id` and GB reference.  
- `tp_log`: append‑only TP‑tagged log of evolution steps.  
- `audit_log`: append‑only lifecycle and rejection log.  
- `determinism_digest`: hash summarizing IB state for determinism verification (e.g., `creation_digest` in 30.170 capsule).   

### 5.3 Compatibility and evolution

- Schema evolution MUST be additive and backward‑compatible for existing fields; removal or semantic repurposing of fields requires coordinated updates across 10/30/40/50 layers and explicit change control.  
- Any new IB‑visible fields that affect lifecycle or routing MUST be reflected in 10.50.170, 30.170 verification artifacts, and this design spec in a synchronized change set.

## 6. Observability and logging

- **Lifecycle logging:**  
  All lifecycle transitions (creation, evolution, split, merge, promotion, retirement) MUST emit structured entries into `audit_log`, including `event_type`, `sequence`, IB IDs, and GB references where applicable.   
- **Negative‑path logging:**  
  All rejections (direct OuB bypass, sequence violation, safe‑boundary violation, unsupported enums) MUST log fixed reason codes and minimal diagnostic context, consistent with the negative‑path scenarios in the 30.170 capsule.   
- **TP tagging observability:**  
  `tp_log` MUST be sufficient to reconstruct inquiry evolution for supervisory review and determinism checks; entries are append‑only and ordered by `sequence`.  
- **Determinism digests:**  
  Determinism evidence fields such as `creation_digest` and `active_ids_after_creation` MUST be reproducible for equivalent inputs, as shown in the 30.170 determinism snapshot.   
- **TCU observability:**  
  When TCU measurement is enabled, IB harnesses MUST emit `scenario_id`, `seed`, `N`, `config_hash`, and `cycles_measured` fields into verification artifacts, consistent with 20.150 and 10.50.170.TCU.* expectations.   

## 7. Verification obligations

Per 50.05, design specs must couple to verification artifacts without duplicating them as sources of truth. For IB:

- **Scenario coverage:**  
  The following scenario families MUST remain covered by executable harnesses and 30‑layer capsules:  
  - `async_creation_approval` (HLR‑20.090‑006)  
  - `deterministic_evolution_tp_tagging` (HLR‑20.090‑008)  
  - `split_merge_lifecycle` (HLR‑20.090‑021)  
  - `promote_and_retire` (HLR‑20.090‑023)  
  - `negative_direct_oub_bypass` (HLR‑20.090‑007)  
  - `negative_safe_boundary_violation` (HLR‑20.090‑020)  
  - `negative_sequence_violation` (HLR‑20.090‑019)   

- **Determinism evidence:**  
  Verification artifacts MUST include determinism snapshots (e.g., `creation_digest`, `active_ids_after_creation`, `pending_requests_after_creation`) and demonstrate stability across reruns for fixed inputs.   

- **Artifact governance:**  
  `30_verification/30.170_ib_prototypes/30.170_ib_prototypes_verification_capsule.md` and `30.170_ib_prototypes_requirements_delta.md` are the canonical verification records for IB; any material change to IB design that affects lifecycle or contracts MUST be accompanied by updated verification artifacts.   

- **TCU verification:**  
  When IB enters the TCU budgeting pipeline, 30‑layer capsules MUST include cycle‑budget evidence for IB scenarios, demonstrating bounded and deterministic cycle consumption within \([C_{\min}(\text{ib}), C_{\max}(\text{ib})]\).

## 9. Change control

Consistent with 50.05:

- **Trigger conditions:**  
  This design spec MUST be updated when:  
  - canonical IB requirements in 10.50.170 change;  
  - IB lifecycle behavior in 30.170 verification artifacts changes materially;  
  - IB IO contracts or observability obligations change;  
  - TCU budgeting expectations for IB change in 20.150 or 10.50.170.TCU.*.   

- **Forward flow:**  
  When new exploratory IB behavior is validated in 40.250 and promoted to 30.170, this spec MUST be updated to reflect the new canonical behavior, with traceability to updated capsules and deltas.

- **Backward flow:**  
  When canonical anchors in 10.50.170 are updated, backward flow MUST propagate into 30.170, 40.250, and this 50.170 spec as a governed transaction, with cross‑layer impact logs and integrity checks, as required by 50.05 section 5.3.   

- **Release coupling:**  
  When this spec cites specific 30.170 verification artifacts (e.g., `ib_verification_run_2026-06-03.json`), those artifacts are treated as release evidence for this design version. Material changes to those artifacts require a corresponding design‑spec revision and updated traceability.   

- **History and migration:**  
  Changes to this spec MUST preserve additive, lossless history via version control. If IB design is structurally migrated (e.g., split into multiple specs), a migration note MUST be recorded here and in `50.00_design_traceability_index.md` per 50.05.
