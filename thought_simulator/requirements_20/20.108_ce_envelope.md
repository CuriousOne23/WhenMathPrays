# **20.108 — CE Envelope (Rewritten)**  
**Document ID:** 20.108  
**Version:** 2.0 (Structural Optimization Rewrite)  
**Date:** 2026‑07‑20  
**Upstream:** CEx (20.107)  
**Downstream:** ISc (20.44)

---

# **1. Purpose** *(Informative)*

The Context Envelope (CE) is the **structured, deterministic, pre‑semantic context object** produced by CEx.  
CE is the **only** context object that ISc may read, and it serves as the **handoff boundary** between Path‑A extraction and the first semantic module.
CE also emits the candidate_set defined in 20.108.010 at TP.ce.candidate_set[], which is consumed by ISc for deterministic scoring.

CE has two purposes:

### **1. Provide a safe, bounded, pre‑semantic representation of context**  
CE contains only **explicit, normalized, bounded fields** extracted from CIL by CEx.  
It carries no inferred meaning, no semantic repair, no embeddings, and no latent vectors.  
CE ensures that all downstream semantic modules receive a **clean, deterministic, replay‑equivalent** context object.

### **2. Communicate CEx’s deterministic identity‑layer selection**  
CE encodes the identity‑layer chosen by CEx for the present turn, including:

- continuity decisions  
- ambiguity resolution  
- fallback selection  
- collapse fallback  
- ordering‑metric usage  
- continuity status  

Downstream primitives (ISc → TPU → TP(N+1)) rely on CE to understand **which conversation context is active** and **why** it was selected.

CE is a **versioned, canonical, deterministic data primitive**, similar in status to TP, MTP, and semantic_core, but strictly pre‑semantic.

---

# **2. Position in the Inference Path** *(Informative)*

```
InB → IIInB → IE → CEx → CE → ISc → TPU → TP(N+1)
```

CE is the **handoff boundary** between Pipeline‑A extraction and the first semantic module (ISc).

---

# **3. Nature of CE** *(Informative)*

CE is:

- a **bounded** context object  
- a **canonical** structure  
- a **deterministic** representation of extracted fields  
- a **non‑semantic** envelope  
- a **versioned** data primitive  

CE is **not**:

- a meaning layer  
- a semantic repair layer  
- a classifier  
- a routing object  
- a ΔH% carrier  
- a TB/IB/Truth Done structure  
- a Pipeline‑B envelope  

# **3.1 CE Placement in TP (Normative — 20.105 Alignment)**

CE is not an external object. CE is written directly into `TP.metadata.context_metadata` as defined in 20.105 and 20.105.010. CEx SHALL populate the following TP fields:

- `TP.metadata.context.relevance_flags`
- `TP.metadata.context.copy_forward_flags`
- `TP.metadata.context.reset_flags`
- `TP.metadata.context.context_fields`
- `TP.metadata.context.context_provenance`

CE is a TP-stream envelope. It is produced by CEx, stored in TP, and committed by TPU. CE SHALL be treated as read-only by all downstream primitives except TPU and OuBA.

Downstream primitives (RB, IdOB, ISc, MCB, OuBA, SSRGn) SHALL consume CE from `TP.metadata.context_metadata` and SHALL NOT re-derive context fields from CIL or upstream structures.

CE SHALL be included in the TP committed state and SHALL be preserved across freeze/thaw cycles.

---

# **4. Inputs and Outputs** *(Informative)*

**Input:**  
- CEx output (context_fields + extraction_audit)

**Output:**  
```
ce_record {
    context_fields{},     // structured, normalized, bounded
    extraction_audit[],   // deterministic audit entries
    ce_version_tag
}
```

ISc consumes `context_fields{}` and may inspect `extraction_audit[]`.

---

# **5. Structural Properties** *(Informative)*

CE is a **fixed‑schema** object with:

- canonical field names  
- canonical ordering  
- canonical encoding  
- bounded field sizes  
- deterministic normalization rules  

Fields not present in CIL do not appear in CE.  
Fields outside the allowlist do not appear in CE.

---

# **6. Allowed Content** *(Informative)*

CE may contain:

- explicit user‑provided context strings  
- explicit system‑provided context strings  
- timestamps  
- structural metadata  
- conversation window slices  
- explicit parameters  
- explicit flags  
- extraction audit entries  

All content must be **explicit**, **non‑semantic**, and **non‑inferred**.

---

# **7. Forbidden Content** *(Informative)*

CE may **not** contain:

- inferred semantics  
- embeddings  
- latent vectors  
- meaning‑layer fields  
- routing metadata  
- ΔH%  
- TB/IB fields  
- semantic_core fields  
- Pipeline‑B envelopes  
- any field not explicitly extracted by CEx  

---

# **8. Determinism and Replay** *(Informative)*

CE is fully deterministic:

- identical CIL + identical policy_signature → identical CE  
- ordering is canonical  
- normalization is canonical  
- extraction_audit is canonical  

Replay must yield byte‑identical CE.

---

# **9. Error Behavior** *(Informative)*

If CIL is malformed:

- CE still emits  
- only valid extracted fields appear  
- invalid fields are dropped  
- audit entries record all drops  
- CE remains deterministic  

CE never halts the pipeline.

---

# **10. CE Schema (Canonical)** *(Informative)*

```json
CE {
  context_fields: {
    identity_layer: IdentityLayerBlock,
    continuity_status: string,
    ordering_metrics: OrderingMetricsBlock,
    clarifying_fields: ClarifyingFieldBlock,
    next_context: NextContextBlock,
    timestamps: { generated_turn: TurnID }
  },
  extraction_audit: [AuditEntry],
  ce_version_tag: string
}
```

# **11. Normative Requirements (HLRs)**  
*(Reorganized, merged/split for clarity; all original information preserved)*

## **11.1 Core CE Requirements**

### **HLR‑20.108‑001**  
CE SHALL contain only explicit, bounded, normalized fields extracted by CEx.

### **HLR‑20.108‑002**  
CE SHALL be the only context object that ISc is permitted to read.

### **HLR‑20.108‑003**  
CE SHALL NOT contain inferred, semantic, latent, or probabilistic content.

### **HLR‑20.108‑004**  
CE SHALL use canonical field names, canonical ordering, and canonical encoding.

### **HLR‑20.108‑005**  
CE SHALL be deterministic: identical CIL and policy_signature SHALL produce identical CE.

### **HLR‑20.108‑006**  
CE SHALL include extraction_audit entries for all drops, truncations, and normalizations.

### **HLR‑20.108‑007**  
CE SHALL NOT include routing metadata, ΔH%, TB/IB fields, semantic_core fields, or Pipeline‑B envelopes.

### **HLR‑20.108‑008**  
CE SHALL enforce bounded size limits for all fields.

### **HLR‑20.108‑009**  
CE SHALL NOT modify, reinterpret, or repair any extracted content.

### **HLR‑20.108‑010**  
CE SHALL emit successfully even when CIL is malformed, containing only valid extracted fields.

### **HLR‑20.108‑041 (New — TP Integration)**
CE SHALL be written into `TP.metadata.context_metadata` exactly as defined in 20.105 and 20.105.010.

### **HLR‑20.108‑042 (New — Provenance Integration)**
CE SHALL include `context_provenance` fields recording origin and last_update identifiers as defined in 20.105.020.

### **HLR‑20.108‑043 (New — Downstream Usage Integration)**
CE SHALL be consumable by RB, IdOB, ISc, MCB, OuBA, and SSRGn as defined in 20.105.030.

### **HLR‑20.108‑044 (New — Commit Boundary Integration)**
CE SHALL be written prior to TPU commit; TPU SHALL commit CE into the TP committed state.

### **HLR‑20.108‑045 (New — TP Read-Only Discipline)**
CE SHALL NOT modify any TP fields outside `TP.metadata.context_metadata`.

### 11.1.1 Path‑A COB/CIL Lineage & Metrics Support**

### **HLR‑20.108‑046**  
CE SHALL ingest `TP.metadata.cil_metadata.identity_lineage` from CEx‑Pck and reflect it verbatim into `CE.context_fields.identity_layer.identity_lineage`.

### **HLR‑20.108‑047**  
CE SHALL ingest `TP.metadata.cil_metadata.continuity_lineage` and reflect it verbatim into `CE.context_fields.continuity_status_lineage`.

### **HLR‑20.108‑048**  
CE SHALL ingest `TP.metadata.cil_metadata.topology` and expose it verbatim in `CE.context_fields.topology`.

### **HLR‑20.108‑049**  
CE SHALL ingest all scalar fields in `TP.metadata.cil_metadata.metrics` and expose them verbatim in `CE.context_fields.metrics`:
- `ambiguity_score`  
- `collapse_risk`  
- `drift_score`  
- `stability_score`  
- `lineage_confidence`

### **HLR‑20.108‑050**  
CE SHALL treat all lineage, topology, and metric fields as read‑only and SHALL NOT compute, modify, or reinterpret any such field.

### **HLR‑20.108‑051**  
CE SHALL ingest `TP.metadata.cil_metadata.register_continuity` and expose it verbatim in `CE.context_fields.register_continuity`.

### **HLR‑20.108‑052**  
CE SHALL ingest `TP.metadata.cil_metadata.importance_continuity` and expose it verbatim in `CE.context_fields.importance_continuity`.

### **HLR‑20.108‑053**  
CE SHALL guarantee deterministic replay of all lineage, topology, metric, and continuity fields preserved from CEx‑Pck.

## **11.2 Identity‑Layer Continuity Requirements**

### **HLR‑20.108‑011**  
CE SHALL include the identity‑layer selected by CEx for the present turn.

### **HLR‑20.108‑012**  
CE SHALL include CE.metadata.continuity_status, indicating how the identity‑layer was selected:

```
continuity_status ∈ {
    "continuous",
    "switched",
    "fallback",
    "undetermined"
}
```

### **HLR‑20.108‑013**  
CE SHALL set continuity_status = "undetermined" when CEx selects TP.process.identity_layer_prev due to ambiguity or indeterminate identity selection.

### **HLR‑20.108‑014**  
CE SHALL set continuity_status = "fallback" when CEx selects a stable identity‑layer due to collapse_risk exceeding threshold.

### **HLR‑20.108‑015**  
CE SHALL set continuity_status = "switched" when CEx overrides continuity due to high certainty and low ambiguity.

### **HLR‑20.108‑016**  
CE SHALL set continuity_status = "continuous" when CEx preserves TP.process.identity_layer_prev.

---

## **11.3 Ordering‑Metric Requirements**

### **HLR‑20.108‑017**  
CE SHALL include ordering metrics provided by CEx:

```json
ordering_metrics {
    last_referred: TurnID,
    total_referrals: int,
    recent_referrals: int,
    ordering_score: float
}
```

### **HLR‑20.108‑018**  
CE SHALL NOT compute ordering metrics; it SHALL only reflect values provided by CEx.

### **HLR‑20.108‑019**  
CE SHALL expose continuity_status and ordering_metrics to downstream modules without modification.

---

## **11.4 Clarifying‑Field Requirements**

### **HLR‑20.108‑020**  
CE SHALL include clarifying fields, subfields, and hierarchical sub‑subfields (up to four levels) extracted by CEx.

### **HLR‑20.108‑021**  
CE SHALL include clarifying‑field importance scores exactly as provided by CEx.

### **HLR‑20.108‑022**  
CE SHALL preserve clarifying‑field topology, including hierarchical relationships and bounded limits.

### **HLR‑20.108‑023**  
CE SHALL enforce bounded limits on clarifying fields (10), subfields (100), and depth (4), reflecting any drops or truncations recorded by CEx.

### **HLR‑20.108‑024**  
CE SHALL treat clarifying fields and subfields as read‑only and SHALL NOT modify their values, importance scores, or provenance.

### **HLR‑20.108‑025**  
CE SHALL include clarifying‑field metadata using the canonical structure:

```json
clarifying_fields {
    fields: [string],
    subfields: [{ field: string, subfield: string }],
    topology: ClarifyingTopologyBlock,
    importance: ClarifyingImportanceBlock
}
```

### **HLR‑20.108‑026**  
CE SHALL guarantee deterministic clarifying‑field representation.

### **HLR‑20.108‑027**  
CE SHALL expose clarifying‑field metadata to downstream modules without modification.

### **HLR‑20.108‑028**  
CE SHALL include clarifying‑field metadata even when identity selection is ambiguous, indeterminate, or fallback‑based.

### **HLR‑20.108‑029**  
CE SHALL mark clarifying‑field continuity using continuity_status.

### **HLR‑20.108‑030**  
CE SHALL include clarifying‑field metadata in fallback selections and set continuity_status = "undetermined" when applicable.

---

## **11.5 Next‑Turn Context Requirements (20.105 Alignment)**

### **HLR‑20.108‑031**  
CE SHALL include next‑turn context fields extracted by CEx from TP.next_context{}.

### **HLR‑20.108‑032**  
CE SHALL treat next‑turn context fields as explicit, structured, non‑semantic metadata.

### **HLR‑20.108‑033**  
CE SHALL include next‑turn context fields exactly as provided by CEx:

`topic`, `stance`, `intent`, `register`, `politeness`, `epistemic_shading`,  
`continuity`, `direction`, `coherence`, `shift_required`, `importance`.

### **HLR‑20.108‑034**  
CE SHALL NOT derive next‑turn context fields from clarifying fields, identity‑layer metadata, referent maps, or structural cues.

### **HLR‑20.108‑035**  
CE SHALL guarantee deterministic representation of next‑turn context fields.

### **HLR‑20.108‑036**  
CE SHALL expose next‑turn context fields to downstream modules without modification.

### **HLR‑20.108‑037**  
CE SHALL include next‑turn context fields even when identity selection is ambiguous, indeterminate, or fallback‑based.

### **HLR‑20.108‑038**  
CE SHALL mark next‑turn context continuity using continuity_status.

### **HLR‑20.108‑039**  
CE SHALL include next‑turn context fields in fallback selections and set continuity_status = "undetermined" when applicable.

### **HLR‑20.108‑040**  
CE SHALL record next‑turn context drops, truncations, or normalization adjustments in extraction_audit[].

---

# **12. Conformance** *(Informative)*

CE conforms when:

- all fields are explicit, bounded, and normalized  
- no semantic or inferred content is present  
- deterministic replay is preserved  
- extraction_audit is complete and canonical  
- malformed CIL still yields a valid CE  
- ISc can consume CE without ambiguity
