# ⭐ **20.51 — RBU Primitive (Register / Belief / Usage Commit)**  
**Document ID:** 20.51  
**Version:** 4.2 (20.705 §2 hop order; 2026-08-30)  
**Status:** Normative — Path‑A Primitive  
**Parent:** 20.40 OB‑Requirements  
**Upstream:** IdOB  
**Downstream (20.705 §2):** RBU → DCB → TR → CTP → RB → WrdNm → ISc → RTU → TR → CTP → RB → IdOB → MCB → RBU (cycles) → or OuBA after `TR → CTP → RB`  

---

# **1. Purpose** *(Informative)*

The Register / Belief / Usage Commit primitive (RBU‑prm) is the **meaning‑side commit stage** of Path‑A.  
Its role is to commit **identity‑conditioned meaning fields refined by IdOB** into the Thought Packet (TP), including:

- identity  
- stance  
- register  
- tone  
- semantic tags  
- lineage markers  

RBU does **not** commit truth‑to‑belief (TPTB) or truth/safety fields (TPSF).  
Those belong exclusively to **Path‑B / SSR**.

RBU prepares the TP for routing through 20.705 §2:

```
RBU → DCB → TR → CTP → RB → WrdNm → ISc → RTU → TR → CTP → RB → IdOB → MCB → RBU → …
```

or the OuBA exit after the same `TR → CTP → RB` neighborhood.

RBU performs **no structural modification**, **no semantic inference**, and **no identity resolution**.  
It commits only the meaning‑side fields produced by IdOB.

---

# **2. Position in Path‑A** *(Informative)*

RBU appears **after IdOB** in each identity‑conditioned refinement cycle, and also once after STPX on the first 20.705 §2 pass (before any IdOB).

Canonical Path‑A pipeline (20.705 §2):

```
InB → IIInB → IE
→ CEx → CE
→ TPU
→ SOB → SROB → CnOB → SmOB
→ WrdNm → ISc → SSG → STPX → RBU
→ DCB → TR → CTP → RB → WrdNm → ISc → RTU
→ TR → CTP → RB → IdOB → MCB → RBU
→ (repeat routing loop per §2)
→ or TR → CTP → RB → OuBA
```

RBU operates **only** on meaning fields refined by IdOB when `TP.idob` is present.  
RBU does **not** alter structural geometry or pre‑semantic fields.

---

# **3. Metadata Consumption** *(Informative)*

RBU may consume deterministic, bounded TP‑stream metadata when relevant to meaning‑side commit formation, identity refinement, stance/register/tone alignment, or semantic‑tag consolidation.

Applicable metadata includes:

- IdOB‑refined meaning metadata  
- cue_envelope metadata (STPX)  
- continuity_metadata (COB, CIL, CST)  
- expressive_metadata (IIInB, IE)  
- normalization_metadata (IE)  
- semantic_layer_metadata (IdOB, MCB)  
- provenance_metadata  
- lineage_metadata  
- entropy and signature histories  

RBU treats all TP‑stream metadata as **read‑only**.  
RBU ignores metadata not applicable to meaning‑side commit formation.  
RBU does not consume:

- Pipeline‑B envelopes  
- truth/done fields  
- semantic ΔH%  
- supervisory fields  

RBU interprets metadata strictly as **meaning‑adjacent features**.

# **4. Normative Requirements (HLRs)**

Obsolete HLRs are marked **NA**.  
New HLRs begin at **HLR‑20.051‑017**.

---

## **4.1 Meaning‑Side Commit Requirements**

### **HLR-20.051-001 — Identity Commit**
RBU SHALL commit identity cues (subculture, persona, role) as usage cues, not pack keys, into `TP.semantic.identity` based on IdOB output.

### **HLR‑20.051‑002 — Stance/Register/Tone Commit**  
RBU SHALL commit stance, register, and tone into:

- `TP.semantic.stance`  
- `TP.semantic.register`  
- `TP.semantic.tone`

RBU SHALL NOT modify structural geometry or non‑semantic TP fields.

### **HLR‑20.051‑003 — Semantic Tags & Lineage Markers**  
RBU SHALL attach semantic tags to `TP.semantic.tags` and lineage markers to `TP.metadata.lineage_markers`, preserving all other metadata fields.

### **HLR‑20.051‑004 — Deterministic Commit**  
RBU SHALL operate deterministically; identical inputs SHALL produce replay‑equivalent meaning commits.

### **HLR‑20.051‑005 — No TPTB/TPSF Commit**  
RBU SHALL NOT produce or commit TPTB or TPSF.  
These fields belong exclusively to Path‑B / SSR.

### **HLR‑20.051‑006 — Pre/Post‑Semantic Separation**  
RBU SHALL operate only on meaning fields refined by IdOB and SHALL NOT modify structural geometry or pre‑semantic fields.

---

## **4.2 TP Field Protection**

### **HLR‑20.051‑010 — TP Field Protection**  
RBU SHALL NOT modify:

- `TP.process`  
- `TP.context`  
- `TP.intake`  
- `TP.ssg_signature`  
- `TP.ssg_layer_bitmap`  
- `TP.ssg_reason_code`  
- `TP.ssg_status`  
- `TP.presemantic_cues`  
- `TP.tr_input_cues`

RBU SHALL modify only the meaning‑side fields listed in §5.

### **HLR‑20.051‑011 — Applicable Metadata Consumption**  
RBU SHALL consume applicable deterministic TP‑stream metadata when such metadata improves meaning‑side commit formation, identity refinement, stance/register/tone alignment, or semantic‑tag consolidation.

### **HLR‑20.051‑012 — Read‑Only Discipline**  
RBU SHALL treat all TP‑stream metadata as read-only and SHALL NOT modify any TP fields outside the meaning‑side commit fields defined in §5.

### **HLR‑20.051‑013 — Metadata Applicability Rule**  
RBU SHALL consume TP‑stream metadata only when relevant to meaning‑side commit formation and SHALL ignore metadata that is not applicable.

### **HLR‑20.051‑014 — Forbidden Metadata Consumption**  
RBU SHALL NOT consume Pipeline‑B metadata, semantic ΔH%, truth/done fields, supervisory fields, or any metadata owned by Path‑B realization.

### **HLR‑20.051‑015 — Meaning‑Adjacent Interpretation Only**  
RBU SHALL treat all consumed TP‑stream metadata strictly as meaning‑adjacent features and SHALL NOT perform semantic interpretation, stance inference, identity resolution, or meaning reconstruction beyond IdOB‑refined meaning.

### **HLR‑20.051‑016 — Meaning‑Layer Integration**  
RBU SHALL integrate consumed TP‑stream metadata into meaning‑side commit formation only when such metadata affects meaning completeness, meaning determinism, or replay safety.

---

## **4.3 Routing Preparation**

### **HLR‑20.051‑007 — Routing Readiness**  
RBU SHALL prepare the TP for routing via 20.705 §2:

```
RBU → DCB → TR → CTP → RB → WrdNm → ISc → RTU → TR → CTP → RB → IdOB → MCB → RBU
```

or `TR → CTP → RB → OuBA` when routing selects the OuBA exit.

RBU SHALL NOT specify `TR → RB → CTP` as a live hop order. CTP is 20.145 and sits immediately before RB.

### **HLR‑20.051‑008 — Boundary Compliance**  
RBU SHALL maintain envelope and boundary‑condition compliance as defined in Path‑A boundary specifications.

### **HLR‑20.051‑009 — Per‑Cycle Execution**  
RBU SHALL execute after **every IdOB cycle**, committing meaning‑side fields before the next routing loop.  
RBU SHALL NOT defer commits only to the final cycle before OuBA.  
The first 20.705 §2 `STPX → RBU` appearance before any IdOB remains authorized (HLR-20.051-023).

---

## **4.4 New HLRs (Version 4.0)**

### **HLR‑20.051‑017 — Provenance Write**  
RBU SHALL write provenance for all meaning‑side commit fields under `TP.metadata.provenance`, recording origin = RBU, last_update = RBU, TPU commit identifier, and full commit lineage.

### **HLR‑20.051‑018 — Canonical TP Paths**  
RBU SHALL emit all meaning‑side commit fields using canonical nested TP paths defined in 20.105.010.

### **HLR‑20.051‑019 — No Upstream Re‑Derivation**  
RBU SHALL NOT re-derive upstream observations already encoded in IdOB‑refined metadata.

### **HLR‑20.051‑020 — Replay‑Safe Commit**  
RBU SHALL ensure meaning‑side commit fields are replay-safe and stable under deterministic replay.

### **HLR‑20.051‑021 — Monotonic Meaning Accumulation**  
RBU SHALL commit meaning‑side fields monotonically, preserving IdOB‑refined meaning without destructive edits.

# **5. Inputs and Outputs (Normative)**

## **5.1 Inputs**

RBU accepts a TP snapshot containing:

- IdOB‑refined meaning fields  
- identity profiles  
- referential bindings  
- lineage metadata  
- semantic tags  
- usage cues  
- structural fields (immutable)  
- semantic_layer_metadata (read‑only)  

RBU does not modify structural or pre‑semantic fields.

---

## **5.2 Outputs**

RBU updates **only**:

- `TP.semantic.identity`  
- `TP.semantic.stance`  
- `TP.semantic.register`  
- `TP.semantic.tone`  
- `TP.semantic.tags`  
- `TP.metadata.lineage_markers`  
- `TP.metadata.provenance` (RBU provenance only)

All other TP fields remain unchanged.

---

# **6. Invariant Compliance (Normative)**

RBU maintains:

### **Structural/Meaning Separation**  
Structural geometry and structural metadata remain unchanged.

### **Monotonic Meaning Accumulation**  
IdOB‑refined meaning is preserved and committed without destructive edits.

### **Replay Equivalence**  
Identical TP snapshots produce identical RBU commits.

### **Bounded Determinism**  
RBU operates within bounded meaning‑side correction context.

---

# **7. Path‑B / SSR Boundary (Normative)**

RBU is a **meaning‑side commit primitive in Path‑A**. OuBA is the Path A freeze (20.40-017R).

RBU does **not** commit:

- TPTB (truth‑to‑belief metadata)  
- TPSF (truth/safety semantic fields)  

These fields are constructed exclusively in **Path‑B** from OuBA and SSR.

RBU’s responsibility ends at committing **Path‑A meaning‑side identity and usage fields**.

---

# **8. IdOB Packet Alignment (Normative)**

Informative. RBU is the meaning-side commit of an already-crossed packet. It is not the crossing.

### **HLR-20.051-022**
When committed `TP.idob` is present, RBU SHALL treat that envelope as the authoritative IdOB-refined source for the meaning-side commit in §5.2. RBU SHALL NOT write `TP.idob`.

### **HLR-20.051-023**
When `TP.idob` is absent (including the official first `STPX → RBU` appearance before any IdOB hop), RBU SHALL complete. RBU SHALL NOT invent identity, stance, register, tone, tags, or pack keys. Meaning-side fields listed in §5.2 SHALL remain unchanged or empty as already present.

### **HLR-20.051-024**
RBU SHALL NOT emit `pack_ids[]` and SHALL NOT derive pack keys from `TP.semantic.register`, tone, stance, or “subculture” usage cues. Pack keys remain Pck/MSL fields.

### **HLR-20.051-025**
RBU SHALL NOT write COB, CIL, or OuBA ingest fields.
