# **20.50 — Relational Basin (RB‑prm)**  
**Document ID:** 20.50  
**Version:** 2.0 (Structural Optimization + TP‑Field Update)  
**Status:** Normative — Path‑A Primitive  
**Purpose:** Deterministic routing, arbitration, and TR‑gating authority for Pipeline A  

---

# **1. Purpose & Scope** *(Informative)*

The Relational Basin (RB‑prm) is the **relational topology authority** for Pipeline A.  
RB determines how Thought Particles (TPs):

- traverse basins  
- form lanes  
- split  
- merge  
- escalate inquiries  
- trigger TR updates  

RB consumes **committed `TP.TR`** in a **read‑only** manner.  
RB does **not** derive TR, modify TR, interpret semantics, or perform any Pipeline‑B responsibilities.

RB enforces:

- deterministic routing  
- TR gating  
- multi‑core routing discipline  
- split/merge arbitration  
- routing bounds  
- messy‑input routing  
- replay determinism  
- canonical routing‑filter construction  

RB performs **no semantic interpretation**, **no OB extraction**, **no TB truth evaluation**, and **no SSR behavior**.

## **1.1 TP‑Stream Metadata Consumption (Informative)**

RB‑prm may consume deterministic, bounded TP‑stream metadata when such metadata is applicable to routing‑filter formation, relational‑topology evaluation, or TR‑gating. Applicable metadata includes:

- structural_metadata (SOB, SROB, CnOB, SmOB, SSG)
- cue_envelope metadata (STPX)
- continuity_metadata (COB, CIL, CST)
- expressive_metadata (IIInB, IE)
- normalization_metadata (IE)
- semantic_layer_metadata (IdOB, MCB)
- provenance_metadata (TP.metadata.*)
- lineage_metadata (TP.lineage_log[])
- entropy and signature histories

RB‑prm treats all TP‑stream metadata as read‑only.  
RB‑prm ignores metadata that is not applicable to routing‑filter formation or relational‑topology evaluation.  
RB‑prm does not consume Pipeline‑B envelopes, truth/done fields, semantic ΔH%, or any supervisory fields.  
RB‑prm interprets TP‑stream metadata only as routing‑adjacent features.

# **2. Pipeline‑A Boundary Discipline (Normative)**

### **HLR‑20.050‑031**  
RB SHALL operate exclusively in Pipeline A and SHALL NOT read `exec_plan` or `exec_trace`.

### **HLR‑20.050‑032**  
RB SHALL NOT read `truth_hypotheses` or `routing_epoch_id`.

### **HLR‑20.050‑048**  
Pipeline‑B modules SHALL NOT alter RB routing decisions or mutate routing metadata.

### **HLR‑20.012‑010**  
Seed SHALL NOT influence routing outcomes; RB SHALL exclude seed from routing state.

RB SHALL NOT write:

- `TP.TR`  
- `tr_needs_update`  
- semantic_core  
- TP.context  
- TP.metadata  
- TP.intake  
- TP.process fields other than routing‑filter export  

RB is strictly **read‑only** except for writing the routing filter.

---

# **3. TR‑Gating Contract (Normative)**

### **HLR‑20.050‑027**  
RB SHALL route a TP to TR **iff** `TP.tr_needs_update = true`.

### **HLR‑20.050‑028**  
RB SHALL NOT write `TP.TR` or modify `tr_needs_update`.

### **HLR‑20.050‑004**  
RB routing decisions SHALL be replayable from deterministic logs.

### **HLR‑20.050‑005**  
RB SHALL enforce deterministic firing‑order and transition‑order computation.

### **Routing Equation (SSG‑Aligned)**

RB SHALL implement:

$$
RB\_route(TP) =
f(TP.input\_fields,\ TP.TR,\ TP.tr\_needs\_update,\ TP.process.\Delta H,\ TP.semantic.lineage,\ TP.process.routing\_metadata,\ policy\_signature)
$$

All inputs are **read‑only**.

# **4. Multi‑Core Routing (Normative)**

### **HLR‑20.050‑049**  
RB SHALL route each TP only to OBs whose `orthogonality_signature` matches the TP’s assigned core domain.

### **HLR‑20.050‑050**  
RB SHALL enforce core‑local firing‑order computation.

### **HLR‑20.050‑059**  
RB SHALL maintain strict routing‑domain isolation across `core_id` boundaries; no cross‑core lane consolidation SHALL occur.

### **HLR‑20.050‑060**  
RB SHALL treat `core_id` and `orthogonality_signature` strictly as routing‑domain metadata and SHALL NOT interpret them semantically.

---

# **5. Deterministic Routing Filter (Normative)**

### **HLR‑20.050‑021**  
RB SHALL compute a deterministic routing filter each cycle.

### **HLR‑20.050‑022**  
The routing filter SHALL be representable, inspectable, logged, and replayable.

### **HLR‑20.050‑023**  
RB SHALL apply deterministic relational‑topology rules governing traversal, lane formation, and OB selection.

### **HLR‑20.050‑051**  
The routing filter SHALL be exportable in canonical form with stable ordering.

### **HLR‑20.050‑038**  
All nested maps and ID arrays SHALL use canonical ordering.

### **Canonical Routing Filter Structure**

```
routing_filter {
    selected_ob_ids[],        // canonical sort by ob_id
    lane_projections[],
    delta_h_routing_context,  // Q32.32
    firing_order[],           // deterministic sequence
    transition_rationale[],
    policy_justification{},
    inquiry_escalation?,
    merge_eligibility?,
    split_directive?
}
```

# **9. Messy‑Input Routing (Normative)**

RB SHALL treat messy‑input fields as read‑only contextual signals.

### **HLR‑20.050‑010**

# **12. RB Invariants (Normative)**

### **HLR‑20.050‑047**  
RB SHALL maintain:

1. **Deterministic Routing Invariant**  
   Identical inputs → identical routing filters.

2. **TR‑Gating Invariant**  
   TR updates occur only when `tr_needs_update = true`.

3. **Core‑Isolation Invariant**  
   No cross‑core merges, splits, or lane consolidations.

4. **Read‑Only TR Invariant**  
   RB SHALL NOT modify `TP.TR`.

5. **Canonical Ordering Invariant**  
   All routing‑filter arrays and maps SHALL be canonically ordered.

# **13. Conformance Requirements (Normative)**

### **HLR‑20.050‑061**  
A system is RB‑conformant only if all routing decisions, routing‑filter exports, TR‑gating behaviors, and multi‑core routing constraints satisfy all HLRs in this document.

### **HLR‑20.050‑062 — TP‑Stream Metadata Consumption**
RB‑prm SHALL consume applicable deterministic TP‑stream metadata when such metadata improves routing‑filter formation, relational‑topology evaluation, or TR‑gating.

### **HLR‑20.050‑063 — Read‑Only Discipline**
RB‑prm SHALL treat all TP‑stream metadata as read‑only and SHALL NOT modify any TP fields outside routing‑filter export.

### **HLR‑20.050‑064 — Metadata Applicability Rule**
RB‑prm SHALL consume TP‑stream metadata only when such metadata is relevant to routing‑filter formation, relational‑topology evaluation, or TR‑gating, and SHALL ignore metadata that is not applicable.

### **HLR‑20.050‑065 — Forbidden Metadata Consumption**
RB‑prm SHALL NOT consume Pipeline‑B metadata, semantic ΔH%, truth/done fields, supervisory fields, or any metadata owned by Path‑B realization.

### **HLR‑20.050‑066 — Routing‑Adjacent Interpretation Only**
RB‑prm SHALL treat all consumed TP‑stream metadata strictly as routing‑adjacent features and SHALL NOT perform semantic interpretation, stance inference, identity resolution, or meaning reconstruction.

### **HLR‑20.050‑067 — Routing‑Layer Integration**
RB‑prm SHALL integrate consumed TP‑stream metadata into routing‑filter formation only when such metadata affects routing completeness, routing determinism, or replay safety.

### **HLR‑20.050‑004**  
Routing decisions SHALL be replayable.

### **HLR‑20.050‑038**  
Canonical ordering SHALL be applied before export or diff.

### **HLR‑20.050‑048**  
Pipeline‑B SHALL NOT alter RB routing decisions.
