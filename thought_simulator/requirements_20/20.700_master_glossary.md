## Glossary Format Requirements

These rules apply to **every** document in the 20.700 family: this master (`20.700`) and all sub-glossaries (`20.700.xxx`). They capture the format already used on main; they do not invent a new house style. New or edited 20.700.xxx files SHALL conform. Existing entries MAY be brought into conformance incrementally; new entries MUST conform on first write.

### File identity

- Path: `thought_simulator/requirements_20/`.
- Filename: `20.700_master_glossary.md` for the hub; `20.700.xxx_<snake_topic>_glossary.md` for category files (e.g. `20.700.010_primitives_glossary.md`).
- Document ID equals the numeric stem (`20.700`, `20.700.010`, …). One ID per file. Do not reuse an ID for a different category.
- H1 is the filename itself: `# 20.700.xxx_<snake_topic>_glossary.md`.
- Sibling links only. Files in this directory MUST link as `[20.700_master_glossary.md](20.700_master_glossary.md)`, never `../20.700_master_glossary.md`.

### Required document header

Immediately after the H1, before the first `---`, every 20.700 / 20.700.xxx file SHALL declare these bold-label fields, one per line, two trailing spaces for hard line breaks:

```
**Title:** <human title>
**Document ID:** 20.700[.xxx]
**Version:** <n.n (short change note)>
**Date:** YYYY-MM-DD
**Status:** Active | Draft | Superseded | Archived
```

Optional header fields, in this order when present:

```
**Normative Reference:** <link or ID of the structure/spec this glossary binds>
**Format Authority:** 20.700 (§ Glossary Format Requirements)
```

Rules:

- `Title` is the human name (e.g. `Primitives Glossary`), not the filename.
- `Version` is `major.minor` plus a short parenthetical when a named alignment landed (e.g. `1.1 (T-001–T-009 glossary alignment)`).
- `Date` is the date of this version, ISO `YYYY-MM-DD`.
- `Status` uses the tokens above. The master MAY append a role clause (`Active – Navigation, Format & Invariants Hub`).
- Do not add YAML front-matter. The bold-label block is the front-matter.

### Required sections (document body)

After a `---` separator, every glossary file SHALL include, in order:

1. `## Purpose` — what this file owns. End Purpose with a `**Scope:**` sentence that states what is in and what is out (definitions live in which sibling).
2. `## Navigation` — bullet links to the master and to sibling 20.700.xxx files that this file is expected to be read with. Optional extra bullets for the bound normative spec (e.g. 20.709 / 20.710).
3. Content section:
   - Master only: invariants, family index, category navigation, flow-diagram pointer, then this format section, then changelog.
   - Sub-glossaries: `## Entries` containing the term blocks.
4. Closing line: `*End of <Document ID> <Title>*`.

The master does **not** host term definitions. Each term has exactly one authoritative home in a single 20.700.xxx file.

### Required term-entry schema (all 20.700.xxx)

Every glossary term is a contiguous block. Preferred heading form:

```
## **<ShortName> (<expansion>) — <normative home ID>**
```

Acceptable variants already on main: a leading checkmark on primitives (`# ✔️ **InB …**`), or a plain `###` heading for concept-scale entries in 20.700.050. Do not mix a second heading style inside a new file; pick one style per file and keep it.

Immediately under the heading, these field labels are **required**, in this order, each on its own line (or wrapped paragraph) starting with the bold label:

| Label | What it records |
| --- | --- |
| `**Purpose:**` | One-sentence job of the term. |
| `**Focus:**` | What it reads, writes, computes, or constrains. |
| `**When:**` | Pipeline locus / ordering. |
| `**Why:**` | Architectural reason it exists. |
| `**Is not:**` | Negative definition; adjacent terms it must not be collapsed into. |
| `**Example:**` | One concrete, deterministic illustration. Empty examples are non-conformant; use `n/a` only if a worked example would invent behavior. |
| `**Normative home:**` | Authoritative requirements ID(s) (e.g. `20.40.050`, `20.12.010`). |

Optional trailing fields, only when they already exist in the source or are required by the category:

| Label | When to use |
| --- | --- |
| `**Additional architectural role:**` | Extra pipeline duty that does not change Purpose. |
| `**Scope invariant:**` | A hard MUST/MUST NOT that belongs with the term (e.g. Path-B MUST NOT invoke TPU). |

Rules for entries:

- Do not invent terms. A 20.700.xxx entry restates an existing requirements-home definition; it does not become a second source of truth.
- One term, one home. If a name appears in two categories, the second file links to the home; it does not fork the definition.
- Keep the six required labels even when a field is short. Do not drop `Is not` or `Example`.
- Field text is prose, not a nested heading. Do not promote Purpose/Focus/… to `###`.
- Separate entries with a `---` line.
- Status words inside a term (`Updated`, `Corrected`, `Removed`) belong in the heading or in Purpose, not as a new header field.
- Removed/obsolete terms stay in place with Purpose stating the removal and Normative home pointing at the replacement. Do not delete history from the glossary silently.

### What 20.700.xxx files MUST NOT do

- Host requirements SHALL statements that do not already live in a numbered 20.xxx requirements file.
- Change primitive IDs, field names, or writer walls. Those walls live in 20.116 / 20.12 / the primitive file.
- Use `../` links for siblings in `requirements_20/`.
- Duplicate the master invariants list as if it were a term.
- Add a parallel glossary under `system_playground/` as a second authority. Playground copies are non-normative.

## TS-Level Invariants Summary
- **A/B Separation**: Path A constructs meaning deterministically; Path B performs realization only (read-only on committed meaning).
- **Envelope-Writer Rule**: TPU is the Path A content-mutation writer. Field-name authority 20.116.020 also authorizes bounded envelope writes: IdOB-prm (`TP.idob`, stand-in M / Φ), CTP-prm (`TP.metadata.cognitive_history[]`), MCB (`TP.next_context{}`). “TPU sole writer” does not erase those walls.
- **Determinism & Replay-Safety**: All Path A operations are fully deterministic and replayable. Nondeterminism is isolated to Path B expression via the Random Seed Boundary.
- **Monotonic Entropy Reduction**: Cue OB layers (SOB → SROB → CnOB → SmOB) reduce structural uncertainty; ΔH% tracks incremental changes (see 20.710).
- **Cue vs Birth (INV-M0)**: SmOB and prior OBs emit cues in E. Meaning-birth B and Φ writes (`selected_group_id`, `meaning_semantics`) are IdOB-prm only. Rich E is not birth. See the cut in 20.12.010 / 20.700.050.
- **Two freezes**: CTP-prm applies a policy freeze immediately before every RB (`TR→CTP→RB`). OuBA / SSRGn apply the Path A meaning-commit freeze. `ready_for_ouba` is not OuBA freeze. CTP is the 20.145 primitive only; OuBA commit is not called CTP.
- **Governance Gates**: TPTB, TPSF, and GBIB operate only on committed meaning from OuBA.
- **Provenance & Traceability**: All OB structures must carry complete provenance (see 20.710 normative structures).
- **Pluggability**: Rulesets and routing policies are swappable without violating structural invariants.
