# **20.106 — Directional Conversation Basin (DCB‑prm)**
### **Version 5.3 — Implementation‑Bound**

---

## **1. Overview**

The Directional Conversation Basin (DCB‑prm) is the Path‑A primitive responsible for producing the execution‑flow accounting envelope for a Thought Packet (TP).

DCB does not interpret semantic, structural, identity, or routing metadata.

DCB is a non‑semantic, non‑structural, non‑identity, non‑routing primitive.

DCB produces:

- a current‑cycle geometric_state snapshot (scalar fields),
- directional‑change events (delta signals),
- geometric_history entries (append‑only log).

These outputs provide deterministic execution‑flow visibility for Path‑A and support replay and diagnostics.

DCB is the sole writer of `TP.metadata.geometric_state.*`.

---

## **2. Purpose**

DCB exists to:

- observe TP movement through Path‑A,
- compute deterministic execution‑flow indices,
- detect deviation from expected routing trajectory,
- update the TP’s geometric_state snapshot,
- emit directional‑change events,
- append geometric_history entries,
- provide deterministic replay visibility.

DCB is the execution‑flow indexer for Path‑A.

---

## **3. Definitions**

### **3.1 Fixed Path‑A Routing‑Loop Ordinal Table (v1)**

For DCB v1 indexing, Path‑A’s **routing loop** is the fixed, ordered list:

```
PATH_A = [ STPX, RBU, DCB, TR, CTP, ISc, RTU, RB, IdOB, MCB ]
```

Let:

```
N = len(PATH_A)
ordinal(p) = index of primitive p in PATH_A   # 0 .. N-1
```

This table is normative for v1 DCB indexing. Intake, encoder, and pre‑STPX structure primitives are outside DCB’s v1 index domain.

---

### **3.2 Geometric State (Snapshot)**

DCB writes the following scalar fields under `TP.metadata.geometric_state.*`:

```
position   : int
direction  : int
curvature  : float
step_index : int
lane_id    : int
```

These fields:

- are scalar,
- are overwritten each DCB invocation,
- represent the current execution‑flow state,
- do not contain semantic, structural, identity, or routing metadata.

Type and range constraints:

- `position` ∈ [0, N−1]
- `direction` ∈ [0, N−1]
- `curvature` ∈ [0.0, 1.0] (v1)
- `step_index` ≥ 0
- `lane_id` = 0 (v1)

---

### **3.3 Geometric History (Replay Log)**

DCB appends history entries to:

```
TP.metadata.geometric_history[]
```

Each entry contains:

```
{
  position   : int,
  direction  : int,
  curvature  : float,
  step_index : int,
  lane_id    : int,
  cycle_id   : int,
  timestamp  : float
}
```

History is append‑only, strictly ordered by `cycle_id`, and used for replay and diagnostics.

---

### **3.4 Directional‑Change Events**

DCB appends events to:

```
TP.metadata.dcb_events[]
```

Each **delta** event contains:

```
{
  prev_position,
  new_position,
  prev_direction,
  new_direction,
  prev_curvature,
  new_curvature,
  prev_step_index,
  new_step_index,
  prev_lane_id,
  new_lane_id,
  cycle_id,
  timestamp
}
```

Each **cycle_start** event (first invocation only) contains the same keys, with all `prev_*` values set to `null` and all `new_*` values set to the newly written geometric_state fields, plus `cycle_id` and `timestamp`.

Events reflect the exact delta between previous and current geometric_state (or the first‑cycle baseline when no previous state exists).

---

## **4. Computation Contract (v1)**

DCB computes geometric_state using the following pure functions.

Let:

- `prev` = previous `TP.metadata.geometric_state` if present; else absent,
- `current_primitive_id` = runner‑supplied identity of the primitive whose completion this DCB invocation indexes (string name present in `PATH_A`),
- `curr_primitive = ordinal(current_primitive_id)`,
- `cycle_id` supplied by runner,
- `timestamp` supplied by runner.

### **4.1 position**

```
position := curr_primitive
```

### **4.2 direction**

```
direction := (curr_primitive + 1) mod N
```

### **4.3 step_index**

```
if prev does not exist:
    step_index := 0
else:
    step_index := prev.step_index + 1
```

### **4.4 lane_id (v1)**

```
lane_id := 0
```

### **4.5 curvature (v1)**

Let:

```
expected_direction := (prev.position + 1) mod N   # only if prev exists
```

Then:

```
if prev does not exist:
    curvature := 0.0
else if direction == expected_direction:
    curvature := 0.0
else:
    curvature := 1.0
```

### **4.6 First‑Cycle Event Policy**

If `prev` does not exist:

- geometric_state is written,
- geometric_history receives exactly one entry,
- DCB emits exactly one `cycle_start` event with `prev_* = null` and `new_* = geometric_state` fields,
- DCB does **not** also emit a separate field‑change delta event on that same invocation.

### **4.7 Subsequent‑Cycle Event Policy**

If `prev` exists and any of the five geometric_state fields differs from `prev`, DCB emits exactly one delta event with previous and new values for all five fields.

---

## **5. Read‑Set Contract (v1)**

DCB may read only:

- previous `TP.metadata.geometric_state` (if present),
- `cycle_id` (runner),
- `timestamp` (runner),
- `current_primitive_id` (runner).

**HLR‑20.106‑001:** DCB shall not read semantic, structural, identity, or routing metadata.

**HLR‑20.106‑013:** DCB shall obtain `current_primitive_id`, `cycle_id`, and `timestamp` exclusively from the runner‑supplied cycle context for the current invocation.

---

## **6. Provenance Contract (v1)**

**HLR‑20.106‑002:** DCB shall write:

```
TP.metadata.provenance.dcb_last_update := timestamp
```

DCB writes no additional provenance fields.

---

## **7. Functional Requirements (HLRs)**

**HLR‑20.106‑003:** DCB shall overwrite all five geometric_state fields on every invocation.

**HLR‑20.106‑004:** DCB shall append exactly one geometric_history entry per invocation.

**HLR‑20.106‑005:** When a previous geometric_state exists, DCB shall append exactly one directional‑change delta event if and only if any geometric_state field changed relative to that previous state.

**HLR‑20.106‑006:** DCB shall compute geometric_state using the v1 Computation Contract in §4.

**HLR‑20.106‑007:** DCB shall emit a first‑cycle `cycle_start` event when no previous geometric_state exists, and shall not emit an additional delta event on that same invocation.

**HLR‑20.106‑008:** DCB shall append history entries strictly ordered by cycle_id.

**HLR‑20.106‑009:** DCB shall maintain geometric_history as append‑only.

**HLR‑20.106‑010:** DCB shall maintain dcb_events as append‑only.

**HLR‑20.106‑011:** DCB shall not modify any TP field outside geometric_state, geometric_history, dcb_events, and provenance.dcb_last_update.

**HLR‑20.106‑012:** DCB shall maintain no hidden internal state.

**HLR‑20.106‑014:** DCB shall set `position` to `ordinal(current_primitive_id)` and `direction` to `(ordinal(current_primitive_id) + 1) mod N` per §4.1–4.2.

**HLR‑20.106‑015:** DCB shall set `lane_id` to 0 on every v1 invocation.

**HLR‑20.106‑016:** DCB shall compute `curvature` exclusively by the binary rule in §4.5 (`0.0` or `1.0`).

---

## **8. Non‑Functional Requirements**

Informative statements only; no SHALLs.

Given identical TP geometric inputs and identical runner cycle context (`current_primitive_id`, `cycle_id`, `timestamp`), DCB produces identical geometric_state, geometric_history entries, and events.

In testbench mode, the runner is expected to supply deterministic `timestamp` values so that history and event logs are byte‑stable under replay.

All geometric_state updates, history entries, and events are expected to be visible to the testbench.

History entries are expected to be sufficient for replay reconstruction of execution‑flow movement.

DCB does not interpret semantic, structural, identity, or routing metadata.

---

## **9. Lifecycle Rules**

Informative statements only; no SHALLs.

Lifecycle ordering:

1. Read allowed indexing inputs (previous geometric_state, runner cycle context)
2. Compute geometric_state
3. Emit events (`cycle_start` or delta)
4. Append history
5. Write provenance
6. Pass control to TR

---

## **10. Invariants**

Informative statements only; no SHALLs.

- geometric_state has exactly five fields.
- geometric_state fields are scalar.
- geometric_state is overwritten each cycle.
- geometric_history is append‑only.
- geometric_history has exactly one entry per DCB invocation.
- dcb_events is append‑only.
- curvature follows the v1 binary formula.
- lane_id = 0 in v1.
- direction follows the routing‑loop ordinal table.
- step_index increments deterministically after the first cycle.
- First cycle emits `cycle_start` only; later cycles emit a delta only on field change.
- DCB maintains no hidden internal state.

---

## **11. Testbench Visibility Requirements**

Informative statements only; no SHALLs.

The testbench can inspect geometric_state, geometric_history, dcb_events, ordering, overwrite behavior, append‑only behavior, event deltas (including `prev_* = null` on `cycle_start`), provenance writes, and stability under deterministic runner timestamps.

---

## **12. Summary**

DCB is the deterministic execution‑flow indexer for Path‑A.

It produces:

- current geometric_state snapshot,
- directional‑change events (`cycle_start` or delta),
- geometric_history entries.

This specification is implementation‑bound for v1: pure scalar formulas, explicit write paths, narrow read‑set, first‑cycle policy, and progressive‑testable boundaries.
