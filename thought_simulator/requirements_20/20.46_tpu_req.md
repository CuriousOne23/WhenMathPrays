# **20.46 — TPU Requirements (Option C Rewrite)**  
**TPU — TP‑UPDATE Subsystem Requirements**  
**Document ID:** 20.46  
**Version:** 2.1 (Option C Rewrite + TP‑Field Model Alignment)**  
**Status:** Normative — Path‑A Commit Subsystem  
**Scope:** Deterministic commit authority for TP semantic/process/metadata fields  

---

# **0. Informative Overview (No SHALLs)**

The TP‑UPDATE subsystem (TPU) is the **sole commit authority** in Path‑A.  
Every mutation to the Thought Packet (TP) — semantic, process, metadata, clarifying‑fields, next‑context fields, lineage markers, and meaning‑side updates — MUST pass through TPU.

TPU:

- receives structured `tp_update_request{}` objects from Merge  
- validates writer authority (20.105)  
- enforces deterministic safe‑boundary commit rules (20.30)  
- applies canonical ordering (20.95)  
- commits updates atomically  
- enforces 1‑TP‑primitive cycle lag semantics  
- produces append‑only audit records  
- guarantees replay equivalence (20.12)  

TPU performs **no semantic interpretation**, **no meaning generation**, **no routing**, and **no OB‑class behavior**.

TPU is the **only subsystem allowed to mutate TP**.

# **3. Normative Requirements (HLRs)**

---

## **3.1 Core Commit Authority**

### **HLR‑20.46‑001 — Structural Commit Authority**  
TPU is the **sole structural‑commit authority** for TP updates.  
Meaning‑layer primitives (CEx, TR, IdOB, RBU) may write to their authorized TP fields, but TPU is the only subsystem that:

- validates update requests  
- enforces writer‑authority boundaries  
- enforces canonical ordering  
- applies structural and metadata updates atomically  
- commits updates at deterministic safe boundaries  
- produces audit records for all updates

All other subsystems treat TP fields **outside their writer‑authority domain** as read‑only.

---

### **HLR‑20.46‑002 — Deterministic Commit**  
TPU SHALL apply updates deterministically such that:

```
identical TP(N) + identical tp_update_request → identical TP (N) + 1 primitive cycle
```

Replay equivalence SHALL be preserved across all cycles.

---

### **HLR‑20.46‑003 — Writer Authority Enforcement**  
TPU validates writer authority at the level of the tp_update_request{} object, not at the level of raw TP writes.

Merge constructs update blocks (isc{}, cil{}, cob{}, cop{}, idob_update{}, mcb_update{}, rbu_update{}), and TPU verifies that:
- each block appears only in its authorized namespace
- each block contains only fields permitted for that writer
- no block attempts to modify fields outside its authority domain
- structural and metadata updates originate only from TPU
- meaning‑layer blocks do not contain structural geometry or process‑layer fields

If any block violates its authority domain, TPU rejects the entire update request and records an audit entry.

---

### **HLR‑20.46‑004 — Canonical Ordering**  
TPU SHALL enforce canonical ordering for:

- arrays  
- maps  
- clarifying‑fields  
- next‑context fields  
- lineage markers  
- ΔH% histories  
- metadata blocks  

Canonical ordering SHALL follow 20.95.

---

### **HLR‑20.46‑005 — Safe‑Boundary Commit**  
TPU SHALL commit updates only at deterministic safe boundaries defined in 20.30.

TPU SHALL NOT commit during:

- OB execution  
- RB routing  
- TR update  
- IdOB refinement  
- MCB context generation  
- RBU commit  
- OuBA commit window  

---

### **HLR‑20.46‑006 — 1‑TP‑primitive cycle lag**  
All updates SHALL be committed with a 1‑TP primitive‑cycle lag:

```
tp_update_request(N) → TP (N) + 1 primitive cycle
```

No subsystem SHALL observe updates in the same cycle they were proposed.

---

### **HLR‑20.46‑007 — No Meaning Generation**  
TPU SHALL NOT generate meaning, interpret semantics, or modify semantic content beyond committing fields provided by IdOB, MCB, or RBU.

---

### **HLR‑20.46‑008 — Intake/Context Integrity**  
TPU SHALL NOT modify:

- `TP.intake.*`  
- `TP.context.*` (current‑turn context)  
- `TP.semantic_core`  
- structural geometry fields  

TPU SHALL commit only next‑turn context fields produced by MCB.

---

## **3.2 Clarifying‑Field Commit Requirements**

### **HLR‑20.46‑017 — Clarifying‑Field Validation**  
TPU SHALL validate clarifying‑field metadata including:

- field identity  
- hierarchical level  
- importance  
- provenance  
- topology  
- boundedness  

### **HLR‑20.46‑018 — Writer Authority**  
TPU SHALL enforce clarifying‑field writer authority exactly as defined in 20.105.

### **HLR‑20.46‑019 — Atomic Commit**  
Clarifying‑field updates SHALL be committed atomically as a single deterministic unit.

### **HLR‑20.46‑020 — Provenance Preservation**  
TPU SHALL preserve:

- producer identity  
- last‑update identity  
- commit lineage  
- clarifying‑field provenance  

### **HLR‑20.46‑021 — Canonical Ordering**  
TPU SHALL apply canonical ordering to:

- fields  
- subfields  
- hierarchical levels  
- importance scores  

### **HLR‑20.46‑022 — Continuity**  
TPU SHALL maintain clarifying‑field continuity across TP(N) → TP (N) + 1 primitive cycle.

### **HLR‑20.46‑023 — Audit Logging**  
TPU SHALL include clarifying‑field metadata in `tpu_audit_record{}` whenever:

- fields are updated  
- fields are pruned  
- fields are compressed  
- fields are dropped  

### **HLR‑20.46‑024 — 1‑primitive cycle lag**  
Clarifying‑field updates SHALL follow 1‑TP‑primitive cycle lag semantics.

### **HLR‑20.46‑025 — Bounded Limits**  
TPU SHALL reject clarifying‑field updates that violate bounded limits:

- max 10 fields  
- max 100 subfields  
- max 4 hierarchical levels  

Rejection SHALL produce deterministic fallback behavior and audit.

### **HLR‑20.46‑026 — Replay Equivalence**  
Clarifying‑field commits SHALL be replay‑equivalent.

---

## **3.3 Next‑Context Commit Requirements (MCB Output)**

### **HLR‑20.46‑030 — Next‑Context Validation**  
TPU SHALL validate next‑context fields produced by MCB:

- topic  
- stance  
- intent  
- register  
- politeness  
- epistemic_shading  
- continuity  
- direction  
- coherence  
- shift_required  
- importance  

### **HLR‑20.46‑031 — Write‑Only Commit**  
TPU SHALL commit next‑context fields into `TP.next_context{}` and SHALL NOT modify current‑turn context.

### **HLR‑20.46‑032 — Deterministic Ordering**  
TPU SHALL enforce canonical ordering for next‑context fields.

### **HLR‑20.46‑033 — Replay Equivalence**  
Next‑context commits SHALL be replay‑equivalent.

---

## **3.4 Atomicity & Audit Requirements**

### **HLR‑20.46‑009 — Atomicity**  
TPU SHALL apply updates atomically; partial commits are forbidden.

### **HLR‑20.46‑010 — Audit Logging**  
TPU SHALL produce append‑only audit records for every update attempt.

### **HLR‑20.46‑011 — Immutable Request**  
TPU SHALL treat `tp_update_request{}` as immutable.

### **HLR‑20.46‑012 — Deterministic Fallback**  
On validation failure, TPU SHALL:

- retain TP(N)  
- produce deterministic fallback  
- emit audit  

### **HLR‑20.46‑013 — TCU & GB Caps**  
TPU SHALL enforce TCU budgets and GB caps; violations SHALL trigger deterministic degradation and audit.

---

## **3.5 Merge & Proposal Requirements**

### **HLR‑20.46‑014 — COP Proposal Validation Only**  
TPU SHALL treat COP outputs as proposals only and SHALL perform structural validation only.

### **HLR‑20.46‑015 — Internal Merge**  
Merge SHALL be performed internally within TPU and SHALL NOT appear as a pipeline stage.

### **HLR‑20.46‑016 — No Interpretation**  
TPU SHALL NOT interpret content originating from:

- CIL  
- COB  
- COP  
- MCB  
- IdOB  

TPU commits fields exactly as provided.

- **TP (N) + 1 primitive cycle** — updated Thought Packet  
- **tpu_audit_record{}** — append‑only audit entry  
- **tpu_error{}** — deterministic fallback object  

TPU writes only to:

- `TP.semantic.*`  
- `TP.process.*`  
- `TP.metadata.*`  
- `TP.clarifying_fields.*`  
- `TP.next_context.*`
- `TP.idob` (from authorized `idob_update{}` only; see HLR‑20.46‑034)`TP.idob` (from authorized `idob_update{}` only; see HLR‑20.46‑034)

# **6. Forbidden Actions (Informative)**

TPU does **not**:

- generate meaning  
- interpret semantics  
- modify structural geometry  
- bypass writer authority  
- bypass safe boundaries  
- reorder candidate sets  
- call coprocessors  
- introduce nondeterminism  
- create/delete TP fields  
- perform partial commits

# **10. Path‑A IdOB Commit Path (Normative)**

Informative. `20.105` authorizes `TP.idob` as an IdOB write that TPU commits. This section names that path in 20.46 so TPU cannot drop the packet as an unknown namespace.

### **HLR‑20.46‑034**
TPU SHALL accept `idob_update{}` inside `tp_update_request{}` as the authorized writer block for the `TP.idob` envelope.

### **HLR‑20.46‑035**
TPU SHALL commit `idob_update{}` into `TP.idob` at a deterministic safe boundary and SHALL apply the 1-TP-primitive-cycle lag of HLR‑20.46‑006.

### **HLR‑20.46‑036**
TPU SHALL validate that `idob_update{}` contains only fields permitted for IdOB under `20.40.050` and `20.105`. TPU SHALL reject the entire request if the block includes structural geometry, intake text mutation, or fields outside that domain.

### **HLR‑20.46‑037**
TPU SHALL NOT generate, reinterpret, or recompute six-axis meaning, CIE stance, `meaning_delta_h`, pack keys, or residue. TPU commits `idob_update{}` fields exactly as provided.

### **HLR‑20.46‑038**
TPU SHALL include `TP.idob` commits in `tpu_audit_record{}`.

### **HLR‑20.46‑039**
TPU SHALL preserve replay equivalence for `TP.idob` commits.
