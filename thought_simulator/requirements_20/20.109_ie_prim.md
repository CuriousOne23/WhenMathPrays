# **1. Purpose** *(Informative)*

The Intake Envelope (IE) is the **final pre‑semantic and first mild‑semantic primitive** in Path‑A.  
IE is the **boundary between human input and machine‑efficient representation**.

IE consumes IIInB output and produces the **first committed TP envelope**, including:

- committed token sequence  
- committed normalized surface  
- committed structural interpretation  
- committed anomaly and repair provenance  
- committed replay metadata  
- committed token‑level normative flags  

IE is the first primitive that applies **meaning‑adjacent corrections** (spelling, shorthand, repetition, whitespace, punctuation, Unicode), but **only** when IIInB proposes them.  
IE does not infer meaning, expand meaning, or perform semantic interpretation.

IE’s output is the canonical substrate consumed by all downstream primitives.

---

# **2. IE Role in Path‑A** *(Informative)*

IE performs:

1. **Deterministic repair application**  
   Applies all IIInB repair proposals exactly as specified.

2. **Token‑level normative classification**  
   Produces `TP.intake.token_flags` indicating whether each token is normative, repaired, anomalous, or unrecognizable.

3. **Normalization**  
   Applies rule‑driven normalization (whitespace, punctuation, repetition, Unicode) only when IIInB proposes corrections.

4. **Structural construction**  
   Constructs TP.structure from committed tokens and committed surface.

5. **Replay determinism**  
   Encodes all provenance required for deterministic reconstruction.

6. **Machine‑efficiency enforcement**  
   Produces tokens + token_flags as the primary machine substrate.

IE does not modify upstream fields and does not introduce semantic content.

---

# **3. IE Output Schema (Canonical TP Mapping)** *(Informative)*

IE emits a committed TP instance:

```json
{
  "intake": {
    "tokens": ["string"],
```

# **3.1 TP Fields Used and Produced by IE (Normative)**

### **HLR‑20.109‑017 — TP Fields Read by IE**  
IE SHALL read only the following IIInB‑produced fields:
- TP.intake.surface  
- TP.intake.tokens  
- TP.repair_proposals  
- TP.anomaly_flags  
- TP.intake.metadata.iiinb  

### **HLR‑20.109‑018 — TP Fields Written by IE**  
IE SHALL write only:
- TP.intake.normalized_text  
- TP.intake.tokens  
- TP.intake.token_flags  
- TP.structure  
- TP.metadata.repair_annotations  
- TP.metadata.replay  
- TP.metadata.ruleset_id  
- TP.error  

### **HLR‑20.109‑019 — Prohibition on Upstream Mutation**  
IE SHALL NOT modify:
- TP.intake.surface  
- TP.repair_proposals  
- TP.anomaly_flags  
- TP.intake.metadata.iiinb

# **4. Normative Requirements (HLRs)**

## **4.1 Determinism Requirements**

**HLR‑20.109‑001**  
IE SHALL be deterministically reproducible from the same IIInB output.

**HLR‑20.109‑002**  
IE SHALL NOT include nondeterministic fields (timestamps, random IDs, environment‑dependent values).

---

## **4.2 Boundedness Requirements**

**HLR‑20.109‑003**  
IE SHALL enforce bounded size limits on TP.intake.

**HLR‑20.109‑004**  
IE SHALL record deterministic truncation in TP.metadata.replay.

---

## **4.3 Replayability Requirements**

**HLR‑20.109‑005**  
IE SHALL encode all provenance required for deterministic replay.

**HLR‑20.109‑006**  
IE SHALL preserve ordering of tokens, structures, and metadata.

---

## **4.4 Structural Normalization Requirements**

**HLR‑20.109‑007**  
IE SHALL represent input using the normalized structural schema.

**HLR‑20.109‑008**  
IE SHALL include structural tags when present or derivable.

---

## **4.5 Repair Integration Requirements**

**HLR‑20.109‑009**  
IE SHALL incorporate all IIInB repair proposals without semantic modification.

**HLR‑20.109‑010**  
IE SHALL mark repaired regions in TP.metadata.repair_annotations.

**HLR‑20.109‑016**  
IE SHALL surface all anomaly_flags as anomaly‑provenance entries.

**HLR‑20.109‑027**  
IE SHALL apply repair proposals deterministically and without reordering.

**HLR‑20.109‑028**  
IE SHALL apply each repair proposal exactly to its specified span.

**HLR‑20.109‑029**  
IE SHALL preserve rule identifiers and spans for all applied repairs.

---

## **4.6 Token Normalization Requirements**

**HLR‑20.109‑011**  
IE SHALL produce a normalized token sequence including repair integration.

**HLR‑20.109‑012**  
IE SHALL preserve token boundaries except where repairs modify them.

**HLR‑20.109‑030**  
IE SHALL preserve token boundaries unless explicitly modified by repair.

**HLR‑20.109‑031**  
IE SHALL emit tokens suitable for deterministic replay.

---

## **4.7 Structural Integrity Requirements**

**HLR‑20.109‑013**  
IE SHALL validate TP against the TP schema.

**HLR‑20.109‑014**  
IE SHALL reject malformed structures and emit TP.error.

**HLR‑20.109‑032**  
IE SHALL construct TP.structure deterministically.

**HLR‑20.109‑033**  
IE SHALL record structural provenance in TP.metadata.replay.

---

## **4.8 Prohibited Content Requirements**

**HLR‑20.109‑015**  
IE SHALL NOT include semantic interpretations or inferred meanings.

**HLR‑20.109‑034**  
IE SHALL NOT modify upstream fields.

**HLR‑20.109‑035**  
IE SHALL NOT introduce semantic content.

**HLR‑20.109‑036**  
IE SHALL emit TP.error when deterministic construction fails.

---

# **5. New Requirements Introduced in Version 3.1**

## **4.9 Token‑Level Normative Classification**

**HLR‑20.109‑037**  
IE SHALL emit TP.intake.token_flags with one entry per token.

**HLR‑20.109‑038**  
IE SHALL classify each token as normative, repaired, anomalous, unrecognized, or null according to rule‑driven behavior defined in ie_rules.yaml.

**HLR‑20.109‑039**  
IE SHALL NOT drop or replace tokens unless explicitly directed by rule.

---

## **4.10 Rule‑Driven Anomaly Handling**

**HLR‑20.109‑040**  
IE SHALL resolve anomaly_flags using rule‑driven behavior defined in ie_rules.yaml.

**HLR‑20.109‑041**  
IE SHALL NOT perform spelling correction, shorthand expansion, repetition collapse, punctuation normalization, or Unicode normalization unless IIInB proposes the correction.

**HLR‑20.109‑042**  
IE SHALL record all anomaly resolutions in TP.metadata.repair_annotations.

---

## **4.11 Rule‑Driven Normalization and Spacing**

**HLR‑20.109‑043**  
IE SHALL construct TP.intake.normalized_text using rule‑driven whitespace behavior defined in ie_rules.yaml.

**HLR‑20.109‑044**  
IE SHALL insert or omit spaces between tokens according to rule‑driven behavior and SHALL NOT assume downstream primitives require spaces.

---

## **4.12 Downstream Consumption Model**

**HLR‑20.109‑045**  
IE SHALL produce TP.intake.tokens and TP.intake.token_flags as the primary machine‑efficient substrate for downstream primitives.

**HLR‑20.109‑046**  
IE SHALL ensure normalized_text is suitable for structural primitives, replay, provenance, and debugging, but SHALL NOT require downstream semantic primitives to consume normalized_text.

---

## **4.13 Machine‑Efficiency Enforcement**

**HLR‑20.109‑047**  
IE SHALL encode normative classification so downstream primitives can ignore or down‑weight unrecognizable tokens without re‑deriving anomaly information.

---

# **6. Mathematical Form** *(Informative)*

$$
TP = \\{ TP.intake,\ TP.structure,\ TP.metadata,\ TP.error \\}
$$

IE produces the committed TP envelope by applying deterministic repair proposals, constructing committed tokens, classifying token normativity, generating structural interpretation, and encoding replay metadata.

# **7. Example** *(Informative)*

An IE‑emitted TP instance includes:

- committed token sequence  
- token‑level normative flags  
- committed normalized surface  
- repair‑provenance annotations  
- anomaly‑provenance entries  
- structural tags  
- deterministic replay metadata  

TP.semantic remains empty.
