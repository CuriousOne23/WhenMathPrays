# **1. Purpose** *(Informative)*

The Intake Envelope (IE) is the **final pre‑semantic representation** of the user’s input in Path‑A.

IE is the primitive that **first constructs the TP envelope** for Path‑A:

- IE consumes IIInB output  
- IE produces a **TP instance** containing:
  - `TP.intake`
  - `TP.structure`
  - `TP.metadata`
  - `TP.error`

IE consumes IIInB output and applies all deterministic repair proposals to produce the committed surface form and committed token sequence for Path‑A. IE constructs the first complete TP envelope, including committed intake fields, structural interpretation, and deterministic metadata required for replay. IE does not interpret meaning and does not modify any upstream fields produced by IIInB.

1. Deterministic repair application  
   IE applies all repair proposals from IIInB in deterministic order to produce the committed surface and committed token sequence.

2. Structural construction  
   IE constructs TP.structure deterministically from the committed surface and token sequence.

3. Replay determinism  
   IE emits deterministic metadata describing applied repairs, anomaly propagation, and structural derivation.

4. Pre‑semantic safety  
   IE emits no semantic content and performs no semantic interpretation.

5. Foundation for semantic processing  
   IE produces the committed TP envelope consumed by CEx, CE, ISc, TPU, and TP.semantic.

---

IE operates after IIInB and before any semantic processing. IE is the first primitive that emits a committed TP envelope, including normalized intake, committed tokens, structural interpretation, and deterministic metadata. IE applies repairs proposed by IIInB and does not modify any upstream fields.

---

# **3. IE Output Schema (Canonical TP Mapping)** *(Informative)*

IE emits a committed TP instance containing the normalized surface form, committed token sequence, deterministic structural interpretation, and metadata required for replay and provenance. All fields conform to the TP specification and reflect deterministic application of IIInB repair proposals.

```json
{
  "intake": {
    "tokens": ["string"],
    "normalized_text": "string"
  },
  "structure": {
    "tags": ["StructuralTag"],
    "spans": ["Span"],
    "markup": ["MarkupIndicator"]
  },
  "metadata": {
    "repair_annotations": ["RepairAnnotation"],
    "replay": "ReplayMetadata",
    "ruleset_id": "string"
  },
  "error": "TPError | null"
}
```

All field names SHALL conform to:

- **20.105_tp_requirements.md**  
- **20.105.010_tp_meta_fields.md**  
- **20.105.020_tp_meta_provenance.md**  
- **20.105.030_tp_meta_usage.md**

## 3.1 TP Fields Used and Produced by IE (Normative)

### HLR‑20.109‑017 — TP Fields Read by IE
IE SHALL read only the following TP fields produced by IIInB:
- TP.intake.surface
- TP.intake.tokens
- TP.repair_proposals
- TP.anomaly_flags
- TP.intake.metadata.iiinb

### HLR‑20.109‑018 — TP Fields Written by IE
IE SHALL write only the following TP fields:
- TP.intake.normalized_text
- TP.intake.tokens
- TP.structure
- TP.metadata.repair_annotations
- TP.metadata.replay
- TP.metadata.ruleset_id
- TP.error

### HLR‑20.109‑019 — Prohibition on Writing Upstream Fields
IE SHALL NOT write, modify, or mutate the following TP fields:
- TP.intake.surface
- TP.repair_proposals
- TP.anomaly_flags
- TP.intake.metadata.iiinb

### HLR‑20.109‑020 — Committed Surface Construction
IE SHALL construct TP.intake.normalized_text by deterministically applying all repair proposals from TP.repair_proposals in the order emitted by IIInB.

### HLR‑20.109‑021 — Committed Token Construction
IE SHALL construct TP.intake.tokens as the committed token sequence after deterministic application of repair proposals, preserving token boundaries except where a repair proposal explicitly modifies them.

#### HLR‑20.109‑022 — Committed Structural Construction
IE SHALL construct TP.structure deterministically from the committed surface and token sequence, including:
- TP.structure.tags
- TP.structure.spans
- TP.structure.markup

### HLR‑20.109‑023 — Anomaly Propagation
IE SHALL propagate all entries in TP.anomaly_flags into TP.metadata.repair_annotations as deterministic anomaly‑provenance entries.

### HLR‑20.109‑024 — Repair Provenance Recording
IE SHALL record the provenance of each applied repair in TP.metadata.repair_annotations, including:
- the deterministic rule identifier,
- the token span affected,
- the applied replacement or normalization.

### HLR‑20.109‑025 — Deterministic Repair Ordering
IE SHALL apply repair proposals strictly in the deterministic order provided by IIInB and SHALL NOT reorder, merge, or suppress repair proposals.

### HLR‑20.109‑026 — Deterministic Error Envelope
IE SHALL emit TP.error when repair application or structural construction cannot be completed deterministically, and SHALL NOT emit a partially valid TP instance.

# **4. Normative Requirements (HLRs)**

## **4.1 Determinism Requirements**

**HLR‑20.109‑001**  
IE SHALL be deterministically reproducible from the same IIInB output.

**HLR‑20.109‑002**  
IE SHALL NOT include nondeterministic fields (timestamps, random IDs, environment‑dependent values) in `TP.metadata`.

---

## **4.2 Boundedness Requirements**

**HLR‑20.109‑003**  
IE SHALL enforce bounded size limits on `TP.intake` as defined by system intake constraints.

**HLR‑20.109‑004**  
IE SHALL truncate or summarize oversized `TP.intake` fields using a deterministic, documented procedure, and SHALL record such truncation in `TP.metadata.replay`.

---

## **4.3 Replayability Requirements**

**HLR‑20.109‑005**  
IE SHALL encode all information required for downstream components to replay the user’s input without accessing external state, stored in `TP.metadata.replay`.

**HLR‑20.109‑006**  
IE SHALL preserve ordering of user‑provided tokens, structures, and metadata in `TP.intake.tokens` and `TP.structure.tags`.

---

## **4.4 Structural Normalization Requirements**

**HLR‑20.109‑007**  
IE SHALL represent the user’s input using the normalized structural schema defined by the TP specification.

**HLR‑20.109‑008**  
IE SHALL include structural tags (token spans, block boundaries, markup indicators) in `TP.structure.tags` when present in IIInB output.

---

## **4.5 Repair Integration Requirements**

**HLR‑20.109‑009**  
IE SHALL incorporate all repair proposals from IIInB into `TP.intake.normalized_text` without semantic modification.

**HLR‑20.109‑010**  
IE SHALL mark repaired regions using `TP.metadata.repair_annotations`.

**HLR‑20.109‑016**  
IE SHALL read `IIInB_Output.anomaly_flags` and SHALL surface each unresolved anomaly as an anomaly‑provenance entry in `TP.metadata.repair_annotations`, enabling deterministic propagation downstream.

### HLR‑20.109‑027 — Deterministic Repair Application
IE SHALL apply all repair proposals from TP.repair_proposals deterministically and SHALL NOT reorder, merge, or suppress repair proposals.

### HLR‑20.109‑028 — Repair Span Fidelity
IE SHALL apply each repair proposal exactly to the token span specified by IIInB and SHALL NOT extend, contract, or reinterpret the span.

### HLR‑20.109‑029 — Repair Provenance Preservation
IE SHALL preserve the rule identifier and span information for each applied repair in TP.metadata.repair_annotations.

---

## **4.6 Token Normalization Requirements**

**HLR‑20.109‑011**  
IE SHALL contain a normalized token sequence in `TP.intake.tokens`, including whitespace normalization, canonicalization, and repair integration.

**HLR‑20.109‑012**  
IE SHALL preserve token boundaries exactly as defined by the IIInB tokenizer.

### HLR‑20.109‑030 — Token Boundary Determinism
IE SHALL preserve token boundaries except where a repair proposal explicitly modifies them.

### HLR‑20.109‑031 — Token Sequence Replayability
IE SHALL emit TP.intake.tokens in a form that allows deterministic replay of all applied repairs without reference to external state.

---

## **4.7 Structural Integrity Requirements**

**HLR‑20.109‑013**  
IE SHALL validate its emitted TP instance against the TP schema before being passed to CEx.

**HLR‑20.109‑014**  
IE SHALL reject malformed or incomplete structures and return a deterministic error envelope in `TP.error`, without emitting a partially valid TP instance.

### HLR‑20.109‑032 — Structural Construction Determinism
IE SHALL construct TP.structure deterministically from the committed surface and token sequence, without semantic interpretation.

### HLR‑20.109‑033 — Structural Provenance Recording
IE SHALL record structural derivation metadata in TP.metadata.replay sufficient for deterministic reconstruction of TP.structure.

---

## **4.8 Prohibited Content Requirements**

**HLR‑20.109‑015**  
IE SHALL NOT contain semantic interpretations, inferred meanings, candidate expansions, or truth‑evaluation artifacts.  
`TP.semantic` SHALL remain empty until CE → ISc → TPU.

### HLR‑20.109‑034 — Prohibition on Upstream Mutation
IE SHALL NOT modify TP.intake.surface, TP.repair_proposals, TP.anomaly_flags, or TP.intake.metadata.iiinb.

### HLR‑20.109‑035 — Prohibition on Semantic Mutation
IE SHALL NOT introduce semantic content, inferred meaning, or contextual interpretation into any TP field.

### HLR‑20.109‑036 — Deterministic Error Envelope
IE SHALL emit TP.error when repair application or structural construction cannot be completed deterministically, and SHALL NOT emit a partially valid TP instance.

---

# **5. Mathematical Form** *(Informative)*

$$
TP = \\{ TP.intake,\ TP.structure,\ TP.metadata,\ TP.error \\}
$$

Where:

- **TP.intake** = normalized token sequence + applied repairs  
- **TP.structure** = structural tags and spans  
- **TP.metadata** = replay metadata, ruleset identifiers, repair annotations  
- **TP.error** = deterministic error envelope (or null)

---

# **6. Example** *(Informative)*

An example TP emitted by IE may include:

- normalized tokens in `TP.intake.tokens`  
- repair annotations in `TP.metadata.repair_annotations`  
- structural tags in `TP.structure.tags`  
- deterministic replay metadata in `TP.metadata.replay`  

No semantic interpretation is included; `TP.semantic` remains empty.
