# **20.120 — MTP Schema Requirements (v0.4, Fully Rewritten)**  
**Status:** Normative — TS‑Side Schema Specification  
**Scope:** Master Thought Packet (MTP) wire schema, commit metadata, supervisory markers, audit fields  
**Excludes:** Meaning construction, semantic_core, Path A/B internals, merge/truth/done semantics

---

# **0. Purpose**

20.120 defines the **canonical wire schema** for the **Master Thought Packet (MTP)** — the TS‑side, immutable snapshot produced by **MTPU‑prm** from the finalized **OuBB** artifact.

The schema ensures:

- deterministic replay  
- stable supervisory integration  
- auditability  
- bounded retention  
- platform‑independent serialization  

MTP contains **only TS‑side fields**.  
It does **not** contain meaning‑side structures.

---

# **1. MTP Schema Overview**

An MTP snapshot consists of:

1. **Identity fields**  
2. **Commit metadata**  
3. **Supervisory markers**  
4. **Stability metrics**  
5. **Lineage and provenance**  
6. **Audit records**  
7. **Deterministic serialization envelope**

No meaning‑side fields (semantic_core, stance, affect, TPTB, TPSF, truth hypotheses, ΔH%, etc.) appear in the schema.

---

# **2. Identity Fields**

### **HLR‑20.120‑001 — Identity Block**  
Each MTP SHALL contain:

- `mtp_id` — stable identifier for the MTP instance  
- `commit_id` — unique identifier for the snapshot  
- `cycle_id` — TS cycle associated with the snapshot  
- `snapshot_hash` — deterministic hash of the snapshot contents  
- `schema_version` — versioned schema identifier  

### **HLR‑20.120‑002 — Immutability**  
Identity fields SHALL be immutable once written.

---

# **3. Commit Metadata**

### **HLR‑20.120‑003 — Commit Block**  
Each snapshot SHALL include:

- `commit_id`  
- `commit_timestamp` (evidence only; ordering is deterministic via sequence tokens)  
- `policy_signature`  
- `execution_signature`  
- `commit_reason_codes[]`  

### **HLR‑20.120‑004 — Deterministic commit_id**  
`commit_id` SHALL be derived deterministically from:

- `mtp_id`  
- `cycle_id`  
- `snapshot_hash`  
- `policy_signature`  
- `execution_signature`  

### **HLR‑20.120‑005 — One commit per update**  
Each invocation of MTPU‑prm SHALL produce exactly one new `commit_id`.

---

# **4. Supervisory Markers**

### **HLR‑20.120‑006 — Supervisory Block**  
MTP SHALL include TS‑side supervisory markers:

- GB flow‑control markers  
- CIL/COB snapshot references  
- supervisory reason codes  
- safe‑boundary integration markers  

### **HLR‑20.120‑007 — Deterministic Pathways**  
Supervisory markers SHALL be written only through deterministic TS→GB→TS pathways.

---

# **5. Stability Metrics**

### **HLR‑20.120‑008 — Stability Block**  
MTP SHALL include TS‑side stability metrics:

- bounded retention counters  
- deterministic compaction markers  
- overflow/degradation markers  
- sequence tokens (`mtp_seq`, `integration_seq`, `fifo_index`)  

### **HLR‑20.120‑009 — No meaning‑side metrics**  
Stability metrics SHALL NOT include meaning‑side fields such as ΔH%, stance, affect, or truth hypotheses.

---

# **6. Lineage and Provenance**

### **HLR‑20.120‑010 — Lineage Block**  
MTP SHALL include:

- parent snapshot references  
- deterministic lineage markers  
- provenance signatures  
- policy‑bound inheritance markers  

### **HLR‑20.120‑011 — Append‑Only**  
Lineage SHALL be append‑only and SHALL NOT overwrite prior entries.

---

# **7. Audit Records**

### **HLR‑20.120‑012 — Audit Block**  
Each snapshot SHALL include an audit record containing:

- `commit_id`  
- `cycle_id`  
- `policy_signature`  
- `execution_signature`  
- `commit_reason_codes[]`  
- deterministic event markers  

### **HLR‑20.120‑013 — Deterministic Rejects**  
Invalid schema states SHALL produce deterministic reject‑with‑audit behavior.

---

# **8. Serialization Requirements**

### **HLR‑20.120‑014 — Canonical Serialization**  
MTP serialization SHALL use:

- deterministic key ordering  
- canonical encoding  
- platform‑independent representation  

### **HLR‑20.120‑015 — Zero‑Event Windows**  
Empty snapshots SHALL use canonical empty‑artifact semantics.

---

# **9. Excluded Fields (Normative)**

The following SHALL NOT appear in the MTP schema:

- semantic_core  
- stance, affect, tone, register  
- TPTB, TPSF  
- ΔH%  
- truth hypotheses  
- completion state  
- TP contents  
- OB/RB/TB intermediate structures  
- XP, exec_plan, exec_trace  
- Path A or Path B artifacts  

These belong to meaning‑side or execution‑side systems, not MTP.

---

# **10. Summary**

20.120 defines the **TS‑side schema** for the Master Thought Packet:

- updated only by MTPU‑prm  
- derived only from OuBB  
- consumed only by supervisory modules  
- containing only TS‑side fields  
- deterministic, immutable, auditable  

This schema removes all legacy meaning‑side fields and aligns MTP with the corrected TS architecture.
