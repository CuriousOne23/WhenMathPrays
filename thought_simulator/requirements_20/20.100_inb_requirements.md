# **1. Purpose** *(Informative)*

The Input Basin (InB) is the **first deterministic boundary** of Path‑A and a **data‑integrity primitive with bounded semantic operations** in the **structural, encoding, and schema domains**.

Its role is to ingest raw external signals and convert them into **bounded, canonical, schema‑validated intake fields** by applying **non‑inferential structural and encoding semantics** needed to construct a single deterministic intake surface, while **avoiding meaning‑adjacent interpretation**.

InB ensures that every external input—regardless of noise, encoding, formatting, or transport artifacts—is transformed into a **stable, replay‑equivalent intake representation** that downstream modules can trust for further semantic and meaning‑adjacent processing.

InB responsibilities include:
- deterministic ingestion of external signals into TP.intake.surface and intake metadata
- canonicalization under versioned parser/profile rules
- schema validation and bounded reject/degrade behavior
- FIFO‑preserving intake ordering
- deterministic provenance recording
- non‑inferential normalization of noisy or malformed input
- strict separation between intake‑level structural semantics and downstream meaning‑adjacent repair
- deterministic construction of a single canonical surface string

InB is a **data‑integrity primitive whose semantic domain is limited to structural, encoding, and schema semantics**.  
Meaning‑adjacent semantics and user‑intent interpretation are performed by downstream Path‑A primitives.

---

# **2. Non‑Goals** *(Informative)*

InB does **not**:

- infer user intent  
- perform semantic error correction that requires choosing between plausible meanings  
- choose between plausible meanings  
- apply user‑specific shorthand interpretation  
- construct meaning, routing, truth, or inquiry  
- produce normalized_text  
- produce token_flags  
- produce structural metadata  

Meaning‑adjacent semantic repair and interpretation of user intent begin only after:

```
IIInB → IE → CEx → CE → ISc → TPU → TP.semantic
```

---

# **3. Input Correction Scope** *(Informative)*

| Term | InB Role |
|------|----------|
| **Structural / non‑inferential correction** | In scope — encoding normalization, schema validation, deterministic lexical canonicalization, bounded reject/degrade, MI_NOISE‑class surface handling, and other non‑inferential structural semantics required to construct TP.intake.surface. |
| **Meaning‑adjacent input error correction** | Out of scope — corrections that require semantic interpretation, user intent modeling, or choice among plausible meanings; these begin only after IIInB and IE. |

---

# **4. Architectural Position** *(Informative)*

```
External Input → InB → IIInB → IE → CEx → CE → ISc → TPU → TP(N+1)
```

InB is the **entry point** of the entire inference pipeline and establishes the **pre‑meaning intake boundary** for Path‑A.

---

# **5. Inputs and Outputs** *(Informative)*

### **Inputs (read‑only)**  
- raw external signals  
- transport/session metadata  
- parser/profile configuration  
- execution signature  

### **Outputs**  
- TP.intake.surface
- TP.metadata.intake_provenance
- TP.metadata.intake_audit
- TP.metadata.transport
- TP.metadata.sequence
- TP.metadata.profile_signature

InB does **not** output:

- normalized_text  
- token_flags  
- structural tags  
- structural spans  
- structural markup  

These are produced later by IIInB and IE.

---

# **6. Functional Boundaries** *(Informative)*

InB owns:
- external‑signal normalization
- deterministic canonicalization
- schema validation
- bounded intake acceptance/rejection behavior
- non‑inferential structural and encoding semantics required to construct TP.intake.surface

InB does **not** own:
- meaning‑adjacent semantic repair  
- user‑intent interpretation  
- repair proposal generation  
- committed intake construction beyond TP.intake.surface  
- structural construction (tags, spans, markup)  
- token_flags classification  

---

# **7. Determinism and Replay** *(Informative)*

InB guarantees:
- identical input → identical TP.intake.surface
- identical input → identical TP.metadata
- deterministic canonicalization
- deterministic provenance
- deterministic reject/degrade behavior
- deterministic FIFO ordering

Replay systems must reconstruct identical intake state suitable for deterministic downstream semantic processing.

---

# **8. Error Behavior** *(Informative)*

Malformed input results in:

- deterministic reject or canonicalize  
- fixed audit reason codes  
- append‑only audit entries  
- deterministic provenance  
- bounded degrade behavior  

InB never halts the pipeline.

# ⭐ **9.20 Bounded Structural‑Semantic Domain Requirements (HLR‑20.100‑041 through HLR‑20.100‑043)**

### **HLR‑20.100‑041 — Structural/Encoding Semantic Domain**  
InB SHALL restrict its semantic operations to structural, encoding, and schema semantics required to construct TP.intake.surface and TP.metadata, and SHALL NOT perform user‑intent or meaning‑adjacent interpretation.

### **HLR‑20.100‑042 — Non‑Inferential Structural Semantics**  
InB SHALL perform only non‑inferential structural and encoding semantics, such that all intake transformations remain replay‑deterministic and do not require choosing between plausible meanings.

### **HLR‑20.100‑043 — Path‑A Pre‑Meaning Intake Boundary**  
InB SHALL establish the pre‑meaning intake boundary for Path‑A by producing TP.intake.surface and TP.metadata that are sufficient for downstream primitives to perform meaning‑adjacent and user‑intent semantics without requiring additional intake‑level semantic mutation.

# **10. Conformance** *(Informative)*

InB conforms when:

- intake is deterministic  
- provenance is deterministic  
- audit behavior is deterministic  
- FIFO ordering is preserved  
- malformed input is handled deterministically  
- semantic isolation of **TP.semantic** is preserved  
- bounded structural/encoding/schema semantics are applied without meaning‑adjacent interpretation  
- replay produces identical **TP.intake** and **TP.metadata**
