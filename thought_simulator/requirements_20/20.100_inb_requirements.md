# **1. Purpose** *(Informative)*

The Input Basin (InB) is the **first deterministic boundary** of Path‑A.  
Its role is to ingest raw external signals and convert them into **bounded, canonical, schema‑validated intake fields** without performing semantic interpretation.

InB ensures that every external input—regardless of noise, encoding, formatting, or transport artifacts—is transformed into a **stable, replay‑equivalent, pre‑semantic representation** that downstream modules can trust.

InB responsibilities include:

- deterministic ingestion of external signals into **TP.intake**  
- canonicalization under versioned parser/profile rules  
- schema validation and bounded reject/degrade behavior  
- FIFO‑preserving intake ordering  
- deterministic provenance recording  
- non‑inferential normalization of noisy or malformed input  
- strict separation between raw input handling and semantic repair  
- **deterministic surface → token alignment**  
- **deterministic token‑sequence construction**  

InB is a **data‑integrity primitive**, not a semantic module.  
It ensures Path‑A begins from a **stable, deterministic, auditable foundation**.

---

# **2. Non‑Goals** *(Informative)*

InB does **not**:

- infer user intent  
- perform semantic error correction  
- choose between plausible meanings  
- apply user‑specific shorthand interpretation  
- construct meaning, routing, truth, or inquiry  
- produce normalized_text  
- produce token_flags  
- produce structural metadata  

Semantic repair begins only after:

```
IIInB → IE → CEx → CE → ISc → TPU → TP.semantic
```

---

# **3. Input Correction Scope** *(Informative)*

| Term | InB Role |
|------|----------|
| **Structural / non‑inferential correction** | In scope — encoding normalization, schema validation, deterministic lexical canonicalization, bounded reject/degrade, MI_NOISE‑class surface handling. |
| **Semantic input error correction** | Out of scope — semantic repair begins only after IE; TP.semantic remains empty. |

---

# **4. Architectural Position** *(Informative)*

```
External Input → InB → IIInB → IE → CEx → CE → ISc → TPU → TP(N+1)
```

InB is the **entry point** of the entire inference pipeline.

---

# **5. Inputs and Outputs** *(Informative)*

### **Inputs (read‑only)**  
- raw external signals  
- transport/session metadata  
- parser/profile configuration  
- execution signature  

### **Outputs**  
- **TP.intake.surface**  
- **TP.intake.tokens**  
- **TP.metadata.intake_provenance**  
- **TP.metadata.intake_audit**  
- **TP.metadata.transport**  
- **TP.metadata.sequence**  
- **TP.metadata.profile_signature**

InB does **not** output:

- normalized_text  
- token_flags  
- structural tags  
- structural spans  
- structural markup  

These are produced later by IE.

---

# **6. Functional Boundaries** *(Informative)*

InB owns:

- external‑signal normalization  
- deterministic canonicalization  
- schema validation  
- bounded intake acceptance/rejection behavior  
- deterministic surface → token alignment  
- deterministic tokenization  

InB does **not** own:

- semantic repair  
- meaning‑adjacent normalization  
- repair proposal generation  
- committed intake construction  
- structural construction  
- token_flags classification  

---

# **7. Determinism and Replay** *(Informative)*

InB guarantees:

- identical input → identical **TP.intake.surface**  
- identical input → identical **TP.intake.tokens**  
- identical input → identical **TP.metadata**  
- deterministic canonicalization  
- deterministic provenance  
- deterministic reject/degrade behavior  
- deterministic FIFO ordering  
- deterministic surface → token alignment  

Replay systems must reconstruct identical intake state.

---

# **8. Error Behavior** *(Informative)*

Malformed input results in:

- deterministic reject or canonicalize  
- fixed audit reason codes  
- append‑only audit entries  
- deterministic provenance  
- bounded degrade behavior  

InB never halts the pipeline.

## **9.1 Deterministic Intake Requirements**

### **HLR‑20.100‑001**  
InB SHALL ingest external signals into bounded **TP.intake** fields.

### **HLR‑20.100‑002**  
InB SHALL NOT perform inference or truth arbitration; **TP.semantic** SHALL NOT be constructed or modified by InB.

### **HLR‑20.100‑003**  
InB transformations SHALL be deterministic and replayable.

---

## **9.2 Schema Validation Requirements**

### **HLR‑20.100‑004**  
InB input mappings into **TP.intake** SHALL be schema‑validated.

### **HLR‑20.100‑005**

# ⭐ **9.19 New Model‑A Requirements (HLR‑20.100‑027 through HLR‑20.100‑040)**

These updates synchronize InB with:

- IIInB v3.1  
- IE v3.1  
- token_flags architecture  
- rule‑driven normalization  
- replay determinism  
- pipeline determinism  

---

### **HLR‑20.100‑027 — Deterministic Token Boundary Construction**  
InB SHALL construct token boundaries deterministically and SHALL NOT infer token boundaries from semantic cues.

### **HLR‑20.100‑028 — Deterministic Surface → Token Alignment**  
InB SHALL preserve deterministic alignment between TP.intake.surface and TP.intake.tokens.

### **HLR‑20.100‑029 — No Meaning‑Adjacent Normalization**  
InB SHALL NOT perform normalization that requires semantic interpretation, including spelling correction, shorthand expansion, repetition collapse, or semantic punctuation normalization.

### **HLR‑20.100‑030 — No Normalized Text Production**  
InB SHALL NOT produce TP.intake.normalized_text.

### **HLR‑20.100‑031 — No Token Flags Production**  
InB SHALL NOT produce TP.intake.token_flags.

### **HLR‑20.100‑032 — No Structural Metadata Production**  
InB SHALL NOT produce TP.structure.tags, TP.structure.spans, or TP.structure.markup.

### **HLR‑20.100‑033 — No Repair Proposal Production**  
InB SHALL NOT produce TP.repair_proposals; repair proposals are produced exclusively by IIInB.

### **HLR‑20.100‑034 — No Anomaly Flag Production**  
InB SHALL NOT produce TP.anomaly_flags; anomaly flags are produced exclusively by IIInB.

### **HLR‑20.100‑035 — Replay Determinism Contract**  
InB SHALL guarantee that TP.intake.surface, TP.intake.tokens, and TP.metadata are sufficient for deterministic replay by IIInB and IE.

### **HLR‑20.100‑036 — Pipeline Determinism Contract**  
InB SHALL guarantee deterministic intake for all downstream primitives (IIInB → IE → CEx → CE → ISc → TPU).

### **HLR‑20.100‑037 — No Semantic Mutation of Surface**  
InB SHALL NOT modify surface in ways that alter meaning or semantic boundaries.

### **HLR‑20.100‑038 — No Token Re‑Segmentation After Canonicalization**  
InB SHALL NOT re‑tokenize or reinterpret token boundaries after canonicalization.

### **HLR‑20.100‑039 — Deterministic Token Classification**  
InB SHALL classify tokens deterministically using pre‑semantic rules only.

### **HLR‑20.100‑040 — Pre‑Semantic Boundary Enforcement**  
InB SHALL enforce that all meaning‑adjacent corrections remain out of scope and SHALL NOT be performed until IIInB and IE.

# **10. Conformance** *(Informative)*

InB conforms when:

- intake is deterministic  
- provenance is deterministic  
- audit behavior is deterministic  
- FIFO ordering is preserved  
- malformed input is handled deterministically  
- semantic isolation is preserved  
- replay produces identical **TP.intake** and **TP.metadata**  
- surface → token alignment is deterministic  
- token boundaries are deterministic
