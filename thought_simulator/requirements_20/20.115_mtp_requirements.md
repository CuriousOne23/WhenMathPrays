# **20.115 — MTP Requirements (v0.4, Fully Rewritten)**  
**Status:** Normative — TS‑Side Snapshot Specification  
**Scope:** Master Thought Packet (MTP) structure, commit semantics, audit invariants  
**Excludes:** Path A meaning construction, merge semantics, truth/completion semantics, semantic_core, TPTB/TPSF, stance/affect, identity metadata

---

# **0. Purpose**

The **Master Thought Packet (MTP)** is the **TS‑side global snapshot** of the system’s committed reasoning state at a given cycle boundary.  
It is produced exclusively by the **MTP Update Primitive (MTPU‑prm)** using the finalized **OuBB** artifact from Pipeline B.

MTP serves three roles:

1. **Stable snapshot** for supervisory modules (GB, CIL, COB)  
2. **Deterministic reference point** for cross‑turn reasoning  
3. **Audit‑ready record** of TS‑side state transitions

MTP does **not** participate in meaning construction and is **not** written by Path A.

---

# **1. Architectural Placement**

- **Input:** OuBB (final output of Pipeline B)  
- **Writer:** MTPU‑prm (TS‑side commit primitive)  
- **Readers:** CIL, COB, GB, supervisory modules  
- **Not a reader:** Path A  
- **Not a writer:** Path A, Path B, XP, OB, TB, merge, truth/done  

MTP is a **pure TS‑side artifact**.

---

# **2. MTP Contents (TS‑Side Only)**

MTP contains only **TS‑side snapshot fields**, including:

- snapshot identity (`mtp_id`, `commit_id`, `cycle_id`)  
- deterministic snapshot hash  
- supervisory markers  
- stability metrics  
- lineage and provenance  
- bounded retention metadata  
- deterministic audit records  
- policy signatures  
- execution signatures  
- TS‑side state summaries derived from OuBB  

MTP **does not** contain:

- semantic_core  
- stance, affect, tone, register  
- TPTB, TPSF  
- ΔH%  
- truth hypotheses  
- completion state  
- TP contents  
- OB/RB/TB intermediate structures  
- XP or execution‑plan fields  

These belong to Path A, Path B, or TP/OuBB — not MTP.

---

# **3. MTPU‑prm and commit_id**

MTP is updated only by **MTPU‑prm**, which:

- consumes OuBB  
- produces a new MTP snapshot  
- emits a new `commit_id`  
- appends an audit record  
- freezes the snapshot for supervisory use  

### **HLR‑20.115‑001 — Single Writer**  
MTPU‑prm SHALL be the only primitive permitted to write or update MTP.

### **HLR‑20.115‑002 — Deterministic commit_id**  
Each MTP update SHALL emit exactly one deterministic `commit_id`.

### **HLR‑20.115‑003 — Immutable Snapshots**  
Snapshots referenced by a `commit_id` SHALL be immutable.

### **HLR‑20.115‑004 — Deterministic Snapshot Hash**  
MTPU‑prm SHALL compute a deterministic content hash for each snapshot.

---

# **4. Snapshot Lifecycle**

### **HLR‑20.115‑005 — Creation**  
MTP creation SHALL initialize identity, lineage, supervisory, and audit fields deterministically.

### **HLR‑20.115‑006 — Update**  
Each update SHALL produce a new snapshot derived solely from OuBB and TS‑side policy.

### **HLR‑20.115‑007 — Retention**  
MTP SHALL maintain bounded retention and deterministic compaction semantics.

### **HLR‑20.115‑008 — Retirement**  
Retired snapshots SHALL preserve lineage and summary‑proof evidence.

---

# **5. Supervisory Integration**

### **HLR‑20.115‑009 — Supervisory Markers**  
MTP SHALL include GB/CIL/COB supervisory markers as TS‑side evidence only.

### **HLR‑20.115‑010 — Deterministic Pathways**  
Supervisory updates SHALL occur only through deterministic TS→GB→TS pathways.

### **HLR‑20.115‑011 — Append‑Only Audit**  
All supervisory and commit events SHALL be recorded append‑only.

### **HLR‑20.115‑012 — Reason Codes**  
Audit entries SHALL include deterministic reason codes and policy signatures.

---

# **6. Audit and Serialization**

### **HLR‑20.115‑013 — Canonical Serialization**  
MTP serialization SHALL use deterministic key ordering and canonical encoding.

### **HLR‑20.115‑014 — Platform Independence**  
MTP behavior SHALL remain deterministic across supported platforms.

### **HLR‑20.115‑015 — Zero‑Event Windows**  
Empty snapshots SHALL use canonical empty‑artifact semantics.

### **HLR‑20.115‑016 — Deterministic Rejects**  
Invalid schema or profile states SHALL be rejected with deterministic audit entries.

---

# **7. Functional Boundaries**

| Component | Responsibility |
|----------|----------------|
| **MTP** | TS‑side snapshot; commit_id; supervisory markers; audit |
| **MTPU‑prm** | Sole writer; snapshot creation; commit_id emission |
| **OuBB** | Sole input to MTPU‑prm |
| **CIL/COB** | Slow readers of MTP; global culture and long‑range analysis |
| **GB** | Supervisory flow‑control markers |
| **TP / Path A** | Meaning construction (not stored in MTP) |
| **Pipeline B** | Realization (not stored in MTP) |

---

# **8. Verification Focus**

- Deterministic MTPU‑prm behavior  
- One commit_id per update  
- Immutable snapshots  
- Deterministic audit trail  
- Deterministic serialization  
- Bounded retention  
- Supervisory markers preserved  
- No meaning‑side fields present  

---

# **9. Summary**

MTP is a **pure TS‑side snapshot**, updated only by **MTPU‑prm**, consumed only by supervisory modules, and containing only TS‑side fields.  
It does **not** participate in meaning construction and does **not** store semantic_core or any Path‑A/Path‑B artifacts.
