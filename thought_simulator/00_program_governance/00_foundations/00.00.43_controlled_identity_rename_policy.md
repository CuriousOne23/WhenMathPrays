# 00.00.43 Controlled Identity Rename Policy

## 1. Purpose

This document defines the **controlled identity rename** process for tiers **40**, **30**, **10.50**, and **50**.

A rename is **address maintenance** — not a semantic change. When executed through this policy:

- No content re-review is required
- No verification or design conclusions are reopened
- Only identity fields and live references change
- Active canon behaves as if the file always had the new name
- Historical material in `archive/` remains exempt

This policy complements [00.00.42_document_addressing_and_insertion_policy.md](00.00.42_document_addressing_and_insertion_policy.md) (insertion without renumbering) and [00.00.41_documentation_tier_map_and_ci_policy.md](00.00.41_documentation_tier_map_and_ci_policy.md) (inventory vs process).

## 2. Core principle — identity migration

| Allowed | Not allowed |
|---------|-------------|
| Filename / folder rename | Changing requirements or design substance |
| Slug or band address change | Re-running promotion or GATE approval |
| Frontmatter `Document ID` update | Editing scenario conclusions |
| HLR/LLR prefix update (Class B only) | Leaving stale paths in active canon |
| Inventory row path update | Rewriting governance prose on every rename |

## 3. Name tables — canonical identity layer

Identity is centralized in tier-scoped JSON name tables under `00_program_governance/00_identity/`:

| Table | Scope |
|-------|-------|
| [40_name_table.json](../00_identity/40_name_table.json) | Playground module folders |
| [10.50_name_table.json](../00_identity/10.50_name_table.json) | Design-requirements files; `paired_entry_id` links to 30 |
| [30_name_table.json](../00_identity/30_name_table.json) | Verification module folders; `paired_entry_id` links to 10.50 |
| [50_name_table.json](../00_identity/50_name_table.json) | Design spec files (level-1 and level-2) |

**Relationship to markdown inventories:**

- Name tables are the **machine-readable SSOT** for canonical paths and pairing.
- `30.01`, `50.00`, and `40.510` remain the **human-readable inventories** and must be updated in the same change set.
- After bootstrap or rename, tables and inventories must agree.

No script, validator, or new governance text should hardcode canonical paths outside these tables (except `archive/` and historical refactor logs).

### Entry fields

Each entry defines:

- `entry_id` — unique identity key (canonical name stem)
- `band` — numeric address band (e.g. `392`, `36.10`)
- `slug` — descriptive suffix
- `canonical_name` — filename or folder name on disk
- `canonical_path` — path relative to `thought_simulator/`
- `paired_entry_id` — for 30 ↔ 10.50 coupling only
- `aliases` — retired names kept for audit (not used in active canon)
- `children` — level-2 50 files under a level-1 parent (optional)
- `shorthand_eligible` — `false` when band is duplicated within the tier (full canonical name required)

## 4. Rename classes

### Class A — slug / path rename (band unchanged)

Example: `50.50_regulator_design_support.md` → a new slug such as `50.50_regulator_design_spec.md`

- Updates paths, links, inventory rows
- Does **not** change HLR/LLR numeric prefixes
- Approval: rename plan + green validation suite

### Class B — band renumber (band changes)

Example: `50.09_geometry_engine_design.md` → a new band such as `50.10_geometry_engine_design.md`

- Everything in Class A, plus:
- `HLR-{old}-*` → `HLR-{new}-*`
- `LLR-{old}-*` → `LLR-{new}-*`
- `Document ID` fields embedding the old band
- Approval: Class A approval **plus** explicit ID-migration sign-off
- **Governed shorthand** band prefixes in allowlisted locations only (see §11)

## 5. Tier-scoped processes

### 5.1 Process 40 (standalone)

**Scope:** `40_thought_simulator_playground/40.xx_*` module folders.

**Mandatory updates (same change set):**

- `40_name_table.json` entry
- `40.510_refactor.md` program row (if module is listed)
- `40_thought_simulator_playground/README.md` child links
- Module-internal relative links and Python import paths (if folder renamed)
- Cross-tier citations in 30, 50, 10.50, 20 (reference sweep only)

**Does not require:** 30 or 10.50 band changes.

### 5.2 Process 30 ↔ 10.50 (coupled, atomic)

**Scope:** verification band `xx` — always rename **both peers in one PR**.

**Mandatory updates (same change set):**

- `10.50_name_table.json` and `30_name_table.json` entries (paired)
- `10.50.xx_*` file rename
- `30.xx_*` folder rename and internal capsule/delta filenames if they embed the band
- `30.01_verification_inventory_index.md` row
- Cross-tier citations in 50.00, 50 specs, 40 sources

**Rule:** 10.50 is the anchor; 30 follows the same numeric band.

### 5.3 Process 50 (standalone)

**Scope:** `50.xx_*` design files (level-1 or level-2).

**Mandatory updates (same change set):**

- `50_name_table.json` entry
- `50.00_design_traceability_index.md` row
- `50.01_50_series_glossary.md` / registry (if term source paths cited)
- Cross-tier citations in 30 capsules, 10.50, 40 handoff docs, 20 (explicit cites only)

**Does not require:** 30 or 10.50 band changes.

## 6. Rename pipeline

Use [rename_identity.py](../../scripts/rename_identity.py) with an approved request JSON ([rename_request.template.json](../00_identity/rename_request.template.json)).

### Steps

1. Author and approve rename request JSON (`rename_class`, `tier`, `entry_id`, new band/slug fields)
2. Run `--dry-run` or `--plan` — review identity changes and affected files
3. Run `--apply --yes` — executes:
   - Physical file/folder renames
   - Name table updates (old name recorded in `aliases`)
   - Deterministic content replacements across `.md`, `.py`, `.json`
   - Mandatory inventory path updates via reference sweep
4. Run full pre-PR validation suite
5. Run `validate_name_tables.py`
6. Commit with refactor log reference from `archive/refactors/`

### Propagation model

| Trigger | Peer rename? | Reference sweep |
|---------|--------------|-----------------|
| 40 rename | No | 30, 50, 10.50, 20 (explicit paths) |
| 50 rename | No | 30, 10.50, 40, 20 (explicit paths) |
| 30 ↔ 10.50 rename | **Yes — atomic** | 50, 40, 20 (explicit paths) |

**Governance and CI scripts** are updated only when they contain the renamed path as a normative example or hardcoded fixture — not on every rename.

### Bootstrap

Initial tables are generated from disk:

```powershell
python thought_simulator/scripts/bootstrap_name_tables.py
```

(from repository root)

Re-run bootstrap after large structural imports to reconcile tables with filesystem.

## 8. Exemptions

- `archive/` — historical names may remain
- Dated refactor logs in `archive/refactors/`
- Closed wave reports and non-normative audit trails
- `aliases` in name tables (audit only; `--scan-aliases` warns if found in active canon)

## 9. Supersession

[align_design_numbering.py](../../scripts/align_design_numbering.py) is superseded by [rename_identity.py](../../scripts/rename_identity.py) for new rename work. The legacy script remains for reference until removed in a future cleanup.

## 10. Governed band-prefix shorthand

Band-only tokens (e.g. `40.100`, `30.140`, `10.50.140`, `50.50`) are **shorthand** — not canonical identity. They are legal **only** in contexts declared in [shorthand_registry.json](../00_identity/shorthand_registry.json).

### Why shorthand is governed

Global replace of a substring like `50.50` is unsafe: the same digits can appear in requirement IDs, unrelated prose, TCU references (`10.50.220.TCU.10`), or coincidental text. The rename pipeline therefore updates shorthand **only** via allowlisted patterns per file class — never via raw substring replace across all documents.

### Two-tier identity model

| Tier | Example | Updated on |
|------|---------|------------|
| **Canonical** | `50.50_regulator_design_support.md` | Class A and B |
| **Shorthand** | `50.50` in a `50.00` table or `LLR-50.50-001` | Class B only, allowlisted spots |

### Shorthand usage matrix (summary)

| File class | Allowed shorthand patterns |
|------------|---------------------------|
| `30.01` inventory | `10.50.{band}` peer refs; `30.{band}_` module paths |
| `50.00` traceability | `10.50.{band}_`, `30.{band}_`, `50.{band}_` in table cells |
| `40.510` program ledger | `40.{band}`, `30.{band}`, `10.50.{band}`, `50.{band}` in module rows |
| Wave coverage notes | `40.{band}` source column; `30.{band}` prose |
| Design specs (`50.*.md`) | Cross-layer tuples; `HLR-10.50.{band}-`; `LLR-50.{band}-`; `[30.{band}]` link labels |
| Verification capsules | `40.{band}` source; `HLR-10.50.{band}-` |
| `10.50.*.md` requirements | `HLR-10.50.{band}-`; `Document ID:** 10.50.{band}` |
| Markdown (governed) | `[30.{band}]`, `[40.{band}]`, `[50.{band}]`, `[10.50.{band}]` display labels |
| Frontmatter (governed) | `LLR-50.{band}-`, `LLR-30.{band}-`, `HLR-10.50.{band}-` |

Full machine-readable rules: [shorthand_registry.json](../00_identity/shorthand_registry.json). Validator: [validate_shorthand_usage.py](../../scripts/validate_shorthand_usage.py).

### Forbidden zones (no bare band shorthand)

- `40_thought_simulator_playground/**/*.py` — use full `MODULE_NAME` / `"module"` field only
- `archive/**` — historical exempt
- `**/artifacts/**` — dated artifact names

### Duplicate bands

Name-table entries with duplicate bands in the same tier have `shorthand_eligible: false`. Those modules must use **full canonical names** in all references; shorthand replace is skipped for them.

### Class A vs B shorthand behavior

- **Class A** (slug only): canonical strings update; shorthand unchanged (band unchanged).
- **Class B** (band change): canonical strings update **plus** governed shorthand patterns in [shorthand_registry.json](../00_identity/shorthand_registry.json) for the affected tier(s).

## 11. Phased bulk migration (multi-module renumber)

When many module bands move in one approved pass (e.g. Phase-1 40 stride-10 cleanup), use a **manifest + orchestrator** instead of ad hoc bulk substring replace.

### 11.1 Manifest requirements

- Store the approved plan as JSON under `00_program_governance/00_identity/` (example: [40_renumber_manifest.json](../00_identity/40_renumber_manifest.json); future: `30_1050_renumber_manifest.json`).
- Each row records `entry_id`, target band/slug, and expected `result` canonical name.
- For **30 ↔ 10.50** passes: one manifest row per **coupled pair** with `tier: "30-1050"`; 10.50 is the anchor band.

### 11.2 Execution rules

1. **Canonical paths only** — replace full `entry_id`, `canonical_path`, and `canonical_name` strings; never bare band digits (`40.160` vs `40.160_tp_lifecycle`, `10.50.270` vs `10.50.220`).
2. **Longest-first** replacement order to avoid substring collisions.
3. **Two-phase staging** on disk when rename targets collide (temp suffix pass, then final pass).
4. Prefer an orchestrator that wraps [rename_identity.py](../../scripts/rename_identity.py) for phase-2 reference sweep and name-table updates rather than divergent one-off logic.
5. Run a **corruption fixer** after the sweep when governance tokens were accidentally rewritten (example: [fix_40_post_renumber_refs.py](../../scripts/fix_40_post_renumber_refs.py)).
6. Protect governance tokens explicitly (e.g. `40.05` master guide must not become `40.160` when `40.20` module bands are rewritten).

### 11.3 Mandatory same-change-set updates

| Tier / scope | Updates |
|--------------|---------|
| 40-only | `40_name_table.json`, `40.510_refactor.md` rows, playground `README.md`, refactor log in `archive/refactors/` |
| 30 ↔ 10.50 | Both name tables, `30.01`, `10.50.xx_*` file, `30.xx_*` folder, HLR/LLR on Class B |
| 50-only | `50_name_table.json`, `50.00`, cross-tier reference sweep |

### 11.4 Validation before merge

- [validate_name_tables.py](../../scripts/validate_name_tables.py)
- [validate_doc_reference_targets.py](../../scripts/validate_doc_reference_targets.py) (blocking)
- Tier inventory validators (`30.01`, `50.00`) as applicable
- [validate_30_10_50_pairing.py](../../scripts/validate_30_10_50_pairing.py) after coupled passes

Non-normative layout targets: [naming_strategy_target.md](../00_identity/naming_strategy_target.md).
