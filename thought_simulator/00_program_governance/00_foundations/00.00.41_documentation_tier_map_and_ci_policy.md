# 00.00.41 Documentation Tier Map and CI Policy

## Purpose

Defines where canonical documentation lives across the 10/20/30/40/50 tiers, which documents are **living inventories** versus **timeless process guides**, when indexes must be updated, and how local or CI checks enforce structural alignment without blocking routine content work.

## Tier map (canonical layers)

| Tier | Path | Role | Formal trace edges |
|------|------|------|-------------------|
| 00 | `00_program_governance/` | Program intent, architecture framing, policy | Influence only — not in the canonical trace graph |
| 10 | `10_thought_simulator_req/` | Realization-ready requirement anchors | Canonical ↔ canonical |
| 20 | `20_requirements/` | Primary collaborative requirement authoring | Canonical ↔ canonical |
| 30 | `30_verification/` | Verification capsules, deltas, run artifacts | Canonical ↔ canonical |
| 40 | `40_thought_simulator_playground/` | Exploratory prototypes and experiments | Optional source for 30 — not a trace parent |
| 50 | `50_thought_simulator_design/` | Formal design specifications | Canonical ↔ canonical |

Exploratory layers (20 collaborative drafts, 40 playground) may inform canonical work through human review. They do **not** become formal trace parents. See [00.00.40_normative_evidence_and_conformance_rules.md](00.00.40_normative_evidence_and_conformance_rules.md).

**Rule:** Process guides describe *how* to work. Inventory indexes record *what exists on disk* and cross-layer paths. Do not duplicate full process prose in inventory files.

## When to update inventories

Update `30.01` or `50.00` in the **same change set** when:

- A module folder or level-1 design file is **added, renamed, or removed**
- Capsule, delta, or design **paths** in the index table change
- Promotion **status** changes (e.g. seeded → promoted → approved)
- Cross-layer anchor or verification capsule **paths** in `50.00` change

Do **not** update inventories for:

- Capsule, delta, or design spec **content-only** edits
- New harness scenarios or JSON artifact content within an existing module
- Playground-only edits under `40_thought_simulator_playground/` that do not promote structure to 30 or 50

Contributor workflow detail: [CONTRIBUTING_CHANGE_WORKFLOW.md](../../CONTRIBUTING_CHANGE_WORKFLOW.md) § Required Sequence step 4; § Document tier inventories; § CI check matrix.

## CI policy

The structural validation scripts and workflows must support the generalized addressing rules defined in [00.00.42_document_addressing_and_insertion_policy.md](00.00.42_document_addressing_and_insertion_policy.md), including recognition of 3-digit subfields (e.g., `20.xxx.yyy` or `50.xx.yyy`) in paths and inventory tables. See 00.00.42 §6 for required script extensions.

Scripts live under `thought_simulator/scripts/`. Modes:

| Mode | Behavior | Use |
|------|----------|-----|
| **Blocking** | Non-zero exit fails the GitHub Actions job | Merge gate for broken refs, missing level-1 rows, dependency graph violations |
| **Warning** | Prints drift; exit 0 | Local pre-PR parity; visibility without blocking content-only work |

Structural inventory checks:

| Script | Mode (typical) | Compares |
|--------|----------------|----------|
| [validate_design_traceability.yml](../../../.github/workflows/validate_design_traceability.yml) | Blocking (CI) | Level-1 `50.*.md` ↔ `50.00` table |
| [validate_50_traceability_index.py](../../scripts/validate_50_traceability_index.py) | Warning (local) | Same rules as blocking workflow |
| [validate_30_inventory_index.py](../../scripts/validate_30_inventory_index.py) | Warning | `30.*` module dirs ↔ `30.01` table |
| [validate_30_10_50_pairing.py](../../scripts/validate_30_10_50_pairing.py) | Warning | `30.01` `promoted`/`approved` rows → matching `10.50.{band}_*.md` (one-way only). This is the *only* enforced cross-tier name coupling. 40/20/50 names are independent. |
| [validate_name_tables.py](../../scripts/validate_name_tables.py) | Warning | Identity name tables ↔ filesystem; 30 ↔ 10.50 band pairing in tables |
| [validate_shorthand_usage.py](../../scripts/validate_shorthand_usage.py) | Warning | Band-prefix shorthand only in [shorthand_registry.json](../00_identity/shorthand_registry.json) contexts |

These checks are **filesystem ↔ table** diffs. They do not use git heuristics, capsule text diffing, or scenario coverage analysis.

**30 ↔ 10.50 pairing** enforces forward-flow completeness from [30.00](../../30_verification/30.00_verification_user_guide.md): a promoted or approved 30 module must have a realization anchor in `10_thought_simulator_req/50_design/`. Orphan `10.50` files without a 30 module are intentionally not reported (`10.50` may precede `30`). `seeded` inventory rows are excluded.

Allowlisted exceptions (e.g. `30.tb/`, `50.00–50.09` governance band) are encoded in the scripts — not ad hoc CI exceptions. Known partial promotions are documented in `30.01` Notes (`30-only pending 10.50`); warnings remain until the peer file exists.

## Playground promotion path (40 → 30) and naming independence

**Component numbering independence (post-renumber policy):**
- Names / .xx component numbers in `40_thought_simulator_playground/` (40) are **standalone and independent**.
- Names in `20_requirements/` (20) are standalone.
- Names in `50_thought_simulator_design/` (50) are standalone.
- **Only 30 and 10.50 are coupled**: a 30 module's numeric band **must** match a 10.50 peer (10.50 comes first as the canonical requirements anchor in `10_thought_simulator_req/50_design/`). See `validate_30_10_50_pairing.py`.

Mature `40.xx` modules (using any 40-chosen number) can supply evidence that leads to creation or update of a `10.50.yy` anchor + matching `30.yy_*` verification module (where yy may differ from the originating 40.xx). The 30 number is dictated by the 10.50, not by the 40 source module number.

Playground program logs (e.g. wave closure in `40.510_refactor.md`) are **audit trails** — not normative dependencies for `30.00` or `50.05`.

After promotion, update `30.01` and any affected `50.00` rows in the same change set.
