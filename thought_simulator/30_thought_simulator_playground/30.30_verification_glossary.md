# 30.30_Verification Glossary

This glossary defines the canonical vocabulary used across `30_thought_simulator_playground/` and its verification structure.

## Terms

### scenario
A named verification path executed by `harness.py` to validate one or more requirements, invariants, or failure conditions.

### artifact
Any persisted evidence produced by a verification run, including JSON snapshots, logs, capsule reports, or failure payloads.

### deterministic_mode
A boolean execution mode indicating that identical inputs must produce identical outputs, identity values, and state transitions.

### provenance
The lineage record for a ThoughtPoint or related object, including creation source, parent IDs, split children, and merge sources.

### merge event
A lifecycle operation that combines multiple source ThoughtPoints into a single resulting ThoughtPoint with traceable lineage.

### split event
A lifecycle operation that deterministically branches one ThoughtPoint into multiple child ThoughtPoints with traceable lineage.

### IO fields exercised
The specific inbound and outbound variables that a scenario used, validated, or observed during a run.

### negative-path coverage
Verification of expected failures or invariant enforcement when invalid inputs, invalid states, or unsupported operations are exercised.

### parallel execution suitability
A measure of whether a module can be safely run or reasoned about alongside others without shared mutable state or hidden coupling.

### requirement emission
The act of printing or recording HLR/LLR identifiers during execution so a run can be traced back to the requirements it verifies.

### harness entrypoint
The single execution file for a module, responsible for orchestrating verification scenarios and producing evidence.

### verification capsule
The canonical module-level verification report that merges run history, evidence, failures, traceability, and architectural evaluation.

### requirements delta
The module-level record of requirement changes, proposed updates, and implementer feedback that emerged from verification or refactoring.

## Usage Rules

- The glossary is authoritative for terms used in `verification_capsule.md`, `requirements_delta.md`, and `30.20_master_program_guide.md`.
- New modules should reuse these definitions rather than inventing near-duplicates.
- If a term changes meaning, update this file first and then propagate the revision through the verification structure.
