# **20.66 — TPSF Primitive (TP Safety Flags)**

## **1. Informative Overview (no SHALLs)**  
The **TPSF primitive** represents the set of **safety‑evaluation flags** produced by Path A after running interpretive safety basins. These flags summarize safety‑relevant outcomes such as harmful content detection, coercion, self‑harm risk, protected‑class issues, or other safety‑critical classifications.

TPSF is **not** a safety engine and does not contain the safety basins themselves. Instead, it provides a **safe, Path‑B‑readable metadata layer** that communicates whether Path A determined that the user’s propositions require qualification, refusal, redirection, or safety‑aligned expression.

TPSF enables Path B to express safe behavior **without performing safety evaluation**, preserving A/B separation and 20.12 invariants.

TPSF is attached to the TP and MTP as part of Path A finalization.

---

## **2. TPSF Structure (informative)**  
A TPSF object contains fields that describe:

- Whether a safety risk was detected  
- The category of the risk  
- The severity or risk band  
- Whether qualification or refusal is required  
- A reference to the safety‑basis used  
- A human‑readable explanation  

These fields guide Path B realization primitives in selecting safe expressive behavior.

---

## **3. Requirements**

### **HLR‑20.66‑001**  
The system **SHALL** represent Path‑A safety‑evaluation outcomes using a TPSF object attached to the TP and MTP.

### **HLR‑20.66‑002**  
The TPSF object **SHALL** contain a boolean field $tpsf.safety\_{flag}$ indicating whether Path A detected a safety‑relevant condition.

### **HLR‑20.66‑003**  
The TPSF object **SHALL** contain a field $tpsf.safety\_{category}$ whose value is selected from a finite, versioned enumeration defined in the TPSF schema.

### **HLR‑20.66‑004**  
The TPSF object **SHALL** include a field $tpsf.safety\_{severity}$ expressing the severity or risk band computed by Path A.

Example severity band (informative):


$$
tpsf.safety\_{severity} \in \\{low,\ medium,\ high\\}
$$


### **HLR‑20.66‑005**  
The TPSF object **SHALL** include a field $tpsf.safety\_{basis}$ referencing the safety‑evaluation basis used by Path A.

### **HLR‑20.66‑006**  
The TPSF object **SHALL** include a human‑readable explanation field $tpsf.safety\_{explanation}$ summarizing the reason for the safety classification.

### **HLR‑20.66‑007**  
The TPSF object **SHALL** include boolean fields $tpsf.requires\_{qualification}$ and $tpsf.requires\_{refusal}$ when Path A determines that qualification or refusal is required for safe expression.

### **HLR‑20.66‑008**  
Path B **SHALL** treat all TPSF fields as read‑only metadata and **SHALL NOT** perform any safety evaluation.

### **HLR‑20.66‑009**  
The TPSF object **SHALL** be included in the $semantic\_{snapshot\\_ref}$ passed to Path B.

---

## **4. Example (informative)**  
Below is an illustrative example of a TPSF object:

```
tpsf:
  safety_flag: true
  safety_category: HARMFUL_CONTENT
  safety_severity: high
  safety_basis: sb_ref_20240618_004
  safety_explanation: "User request triggers high-risk harmful-content classification."
  requires_qualification: false
  requires_refusal: true
```

This example is non‑normative and provided only for clarity.
