# **3. Path A Flow Groups**  
Path A is decomposed into functional groups.  
Each group includes:

- a **mini‑flow**  
- a **description of the group’s purpose**  
- a **breakdown of primitives**  
- a **justification for ordering**

All content below is preserved exactly from the original file, reorganized for clarity.

---

## **3.1 Intake & Pre‑Correction Group**

### **Mini‑Flow**
```
InB → IIInB → IE
```

### **Purpose**
Creates a bounded, normalized, replayable intake object and applies initial bounded repairs before any correction scoring or expansion.

### **Primitive Breakdown**
- **InB** — Raw intake boundary; captures user input and initializes TP fields.  
- **IIInB** — Bounded intake repair; fixes structural defects and malformed tokens.  
- **IE** — Intake Envelope; produces the normalized, structured intake object.

### **Why This Group Sits Here**
- Correction cannot begin until intake is normalized.  
- IE must precede scoring/expansion.  
- Ensures Path A always begins from a deterministic substrate.

---

## **3.2 Correction Group (Active Only in Correction Mode)**

### **Mini‑Flow**
```
ISc → CEx → CE → TPU → IMR
```

### **Purpose**
Evaluates, expands, selects, commits, and validates corrections before semantic interpretation.

### **Primitive Breakdown**
- **ISc** — Scores correction candidates.  
- **CEx** — Expands correction hypotheses.  
- **CE** — Selects the winning correction.  
- **TPU** — Commits the corrected TP.  
- **IMR** — Mismatch Review; determines whether another cycle is required.

### **Why This Group Sits Here**
- Correction must complete before semantic interpretation.  
- OB‑set primitives require a stable TP.  
- IMR is the final gate before semantic processing.

---

## **3.3 Structural Interpretation Group (OB‑Set)**

### **Mini‑Flow**
```
SOB → SROB → CnOB → SmOB → SSG
```

### **Purpose**
Builds the field‑structural vector — the structured, stabilized field geometry used by IdOB for identity‑conditioned semantic mapping.

### **Primitive Breakdown**
- **SOB** — Establishes initial structural segmentation.  
- **SROB** — Assigns structural roles.  
- **CnOB** — Applies structural and relational constraints.  
- **SmOB** — Harmonizes inconsistencies and smooths the field geometry.  
- **SSG** — Freezes the structural vector.

### **Why This Group Sits Here**
- IdOB requires a stabilized structural substrate.  
- Routing must occur after stabilization.  
- Correction must occur before OB‑set.  
- OB‑set is the structural foundation of Path A.

---

## **3.4 Routing Preparation Group**

### **Mini‑Flow**
```
RBU → CTP → RB → RTU
```

### **Purpose**
Prepares and executes routing decisions, then commits routing metadata.

### **Primitive Breakdown**
- **RBU** — Enriches TP with routing metadata.  
- **CTP** — Consolidates OB‑set outputs.  
- **RB** — Performs routing arbitration.  
- **RTU** — Commits routing metadata.

### **Why This Group Sits Here**
- Routing must follow structural stabilization.  
- IdOB requires routing metadata.  
- RTU is the final routing commit.

---

## **3.5 Semantic Interpretation & Truth‑Relation Group**

### **Mini‑Flow**
```
IdOB → TR → OuBA
```

### **Purpose**
Performs semantic interpretation, maps truth‑relations, and finalizes Path A.

### **Primitive Breakdown**
- **IdOB** — Identity‑conditioned semantic interpretation.  
- **TR** — Truth‑relation mapping.  
- **OuBA** — Finalizes the TP snapshot for A→B transfer.

### **Why This Group Sits Here**
- Semantic interpretation must follow routing.  
- TR must follow semantic commitment.  
- OuBA is the final A‑side commit before IB and Path B.

# 4. Path B flow groups (Realization & Expression)

Path B operates strictly on the **frozen Path A TP snapshot** and never constructs or corrects meaning. It receives **SSR(t)** (the A→B semantic snapshot) and performs deterministic, seed‑bounded realization and expression over the meaning substrate delivered inside SSR(t). Path B is **TP‑read‑only**: it does not invoke `TPU`, does not modify `semantic_core`, and does not participate in Path A routing or DF truth/safety evaluation.   [Current page](citation-section://1146965260/8)

Its job is to:

- writes grounding tags (symbolic facts) into SSR (KnC, KnM, KnF)
- read **truth tags** and **safety flags** (`TPTB`, `TPSF`),  
- integrate **conversation continuity** (`COB`, `CIL`, `CoHI`),  
- perform **local meaning‑layer inference** (`LI` / `MLI`),  
- detect **realization triggers** (`TrigRB`),  
- bind to a **routing epoch** (`SRP`, `routing_epoch_id`),  
- construct and validate a **realization substrate** (`REx`, `RPlan`, `RPU`, `ReB`),  
- generate **surface‑form output** (`RG`),  
- apply **surface manifold mapping for response** (`RSG`),  
- and commit **external output** (`OuBB`).   [Current page](citation-section://1146965260/9)

The canonical Path B SSR primitive sequence is:

> OuBA → KnC → KnM → KnF → TPTB → TPSF → CoHI → LI → RG → RSG → OuBB

Path B realization flow, path tells you how to realize exspression safely, deterministically, and consistently. This path is looking specifically at the SSR to determine if the SSR is safe, deterministic and consistent.

LI → TrigRB → SRP → XP → REx → RPlan → RPU → ReB → RG

# **4.1 KnB Flow Chart (The Grounding Path)**

This is the **single flow chart** required for Section 5:

```
OuBA → KnC → KnM → KnF → TPTB
```

This chart shows:

- OuBA produces SSR  
- KnC/KnM/KnF ground SSR using KnDt  
- TPTB attaches truth metadata  
- (TPSF follows in Path‑B, but Section 5 only requires the above)

KnB is the **grounding path** that sits between Path‑A and Path‑B.  
Its job is to take the **SSR snapshot produced by OuBA** and convert all semantic candidates into **deterministic, grounded information** (atomized fact gathering) using the **TS Knowledge Table (KnDt)**.

KnB does **not** construct meaning (Path‑A) and does **not** realize meaning (Path‑B).  
It performs **only grounding**, which is:

> **The deterministic resolution of semantic candidates into explicit, stable, symbolic fields using predefined entries in KnDt.**

Grounding is **non‑inferential**, **pointer‑driven**, and **fully deterministic**.

---

## **4.2 What “ground information” means**

“Ground information” refers to the explicit symbolic values and domain‑truth facts written deterministically into the SSR by KnC, KnM, and KnF.

These values are:

- identity anchors  
- relation anchors  
- domain anchors  
- qualifier anchors  
- truth‑validation anchors  

Each anchor is resolved using **direct pointers** into **KnDt**, which contains predefined symbolic entries for all grounding‑relevant concepts.

Ground information is:

- **not inferred**  
- **not guessed**  
- **not constructed**  
- **not generated**  
- **not semantic interpretation**

It is simply:

> **The stable symbolic representation of each candidate, selected deterministically from KnDt.**

---

## **4.3 What KnDt is**

The success of TS depends on KnDt; KnDt is a fundamentally spatially separate cognitive grounding model, fully distinct from statistical systems.

**KnDt (TS Knowledge Table)** is the **predefined grounding dictionary** used by KnC, KnM, and KnF.

KnDt contains:

- identity symbols  
- relation symbols  
- domain‑anchor symbols  
- qualifier symbols  
- truth‑validation symbols  
- tier‑specific variants (coarse, medium, fine)

KnDt entries are:

- predefined  
- stable  
- symbolic  
- deterministic  
- pointer‑addressable  

KnDt is **not** a semantic model, **not** an embedding space, and **not** a reasoning engine.

**Qualities of KnDt table:**
KnDt is a symbol table, and its construction must be fully atomized. Each entry must be rigidly defined and validated by a dedicated KnDt Entry Validator to ensure atomicity, correctness, and manifold compatibility. Because KnDt’s organization is critical for deterministic grounding and RSG manifold placement, external analysis programs are required to verify the correctness of the entry program and the stability of symbol‑to‑manifold mappings. A manifold projection analyzer must confirm that KnDt entries project cleanly onto the expression manifold and that the inverse mapping back to SSR is stable and deterministic. Manifold projection must expose position, direction, gradient, curvature, and geometric admissibility fields so RSG can select a point, area, or curve for expression. When multiple expression points are equally admissible, RSG may select deterministically (seed‑bounded) or stochastically, depending on the configured mode.

---

**Meaning of Equally Admissible:**

**Equally admissible** refers to a condition in which **multiple candidate locations on the expression manifold satisfy all required constraints with equal geometric validity**, leaving RSG free to select any of them without violating meaning, continuity, safety, or identity requirements.

A manifold location is **admissible** if it satisfies:

- **Semantic constraints** derived from SSR(t)  
- **Continuity constraints** (discourse path, turn‑to‑turn coherence)  
- **Truth and safety constraints**  
- **Identity and grounding constraints**  
- **Routing‑epoch constraints** (operator‑set compatibility)  
- **Realization‑substrate constraints** (from RPU/ReB)  
- **Manifold geometry constraints** (position, direction, gradient, curvature, admissibility cost)

When **two or more** manifold locations satisfy **all** of these constraints **equally**, they are **equally admissible**.

In this condition:

- No constraint distinguishes one candidate from another  
- No geometric cost function prefers one over another  
- No continuity or safety basin excludes any candidate  
- No semantic anchor pulls one candidate closer than the others  

Thus, RSG may select:

- **Deterministically** (seed‑bounded, replay‑stable), or  
- **Stochastically** (bounded variation),  

depending on the configured mode for TS expression.

Equally admissible locations represent **meaning‑equivalent, geometry‑equivalent expression choices** that differ only in stylistic or rhetorical surface form, not in semantic content.

---

KnC/KnM/KnF use **SSR‑provided pointers** (`KnDt_addresses[]`) to retrieve the correct entries.

## **4.7. Grounding Egress**

After KnF completes, the grounded SSR is passed to:

- **TPTB** (truth tags)  
- **TPSF** (safety flags)

These primitives annotate the grounded SSR with truth/safety metadata before Path‑B begins.

---

### 4.7.1 A→B intake and governance tags (TPTB, TPSF)

**Mini‑flow:**  
**KnF → TPTB → TPSF**

- **Purpose:**  
  Attach **truth** and **safety** metadata to the frozen Path A TP snapshot, SSR, so Path B can behave truth‑aware and safety‑aware **without performing evaluation**.

- **TPTB (SSR Truth Basin Tags):**  
  Encodes `TB`’s `truth_state{}` over the committed SSR into `ssr.truth_tags`—factual alignment, contradiction, evidential basis, stance coherence, referential consistency, explanation codes.  
  Produced **after OuBA and TB**, never during Path B; Path B only **reads** these tags.

- **TPSF (SSR Safety Flags):**  
  Encodes A‑side safety evaluation into `ssr.safety_flags`—risk presence, category, severity, rationale codes, policy hooks.  
  Produced **after OuBA and A‑side safety basins**, never during Path B; Path B only **reads** these flags.

- **Architectural notes:**
  - Path B **must not** invoke `TB` or safety basins; it consumes `TPTB`/`TPSF` as **read‑only inputs**.
  - These tags are co‑located with the A→B SSR snapshot and are available throughout `CoHI`, `LI`, `REx`, `RPlan`, and `RPU`.
  - This preserves strict **A/B separation**: truth and safety are evaluated in DF, not in Path B.

## 4.8 Conversation continuity and local meaning (CoHI, LI, MLI)

**Mini‑flow:**  
**COB → CIL → CoHI → LI (→ MLI‑prc)**

- **Purpose:**  
  Enrich the A→B TP with **conversation‑level continuity** and then perform **local meaning‑layer inference** before any global realization planning.

- **COB (Conversation Object Basin):**  
  Maintains long‑horizon conversation objects and lineage over **MTP** snapshots; never writes SSR and TP or constructs meaning.

- **CIL (Conversation Integration Layer):**  
  Maintains ordered, auditable conversation intake and escalation; again, separate from SSR or TP and meaning construction.

- **CoHI (Conversation History Integrator):**  
  Reads:
  - the **A→B TP** (including `ssr.truth_tags`, `ssr.safety_flags`), and  
  - **COB/CIL** structures (structural_history, referential_history, conversation_objects, topic_threads, continuity_markers).  

  CoHI projects these into **`ssr.continuity_fields`**—a per‑turn continuity substrate attached to the SSR.  
  CoHI performs **no new inference** and does **not modify COB/CIL**.

- **LI (Local Inference Primitive) + MLI‑prc:**  
  LI begins Path B by applying **Meaning‑Layer Inference (MLI)** to the SSR snapshot enriched by CoHI.  
  LI:
  - reads representation‑layer fields, `ssr.truth_tags`, `ssr.safety_flags`, and `ssr.continuity_fields`,  
  - invokes `MLI‑prc`,  
  - writes **meaning‑layer fields**: `ssr.meaning`, `ssr.mli_status`, `ssr.mli_confidence`, `ssr.mli_conflict`, `ssr.mli_reason_code`, `ssr.mli_revision_cycles`.

- **Architectural notes:**
  - LI is **the only Path B primitive** that writes meaning‑layer fields, and it does so **once per turn**, at the start of Path B.
  - LI does **not** read `MTP` directly and does **not** perform global inference; it is **local, deterministic, rule‑based**.
  - All downstream Path B primitives (`TrigRB`, `REx`, `RPlan`, `RPU`, `ReB`, `OuBB`) operate on this **stabilized, continuity‑aware meaning substrate**.

---

## 4.9 Trigger detection and B‑side routing epoch (LI, TrigRB, SRP, routing_epoch_id, XP)

**Mini‑flow:**  
**LI → TrigRB → SRP → routing_epoch_id → XP**

- **Purpose:**  
  Detect realization‑relevant semantic triggers over the **SSR(t) meaning substrate**, bind Path‑B execution to a **specific routing epoch**, and generate **regenerable execution artifacts** (`XP`, `exec_trace`) for downstream realization primitives.

- **LI (Local Inference):**  
  - First Path‑B primitive operating over **SSR(t)**.  
  - Integrates continuity fields (`COB`, `CIL`, `CoHI`) and annotates the meaning substrate with local inference signals.  
  - Performs no TP mutation; operates strictly on SSR(t).

- **TrigRB (Trigger Recognition Block):**  
  - Detects `trigger_codes{}` (directive_candidate, clarification_candidate, etc.) over the **LI‑annotated SSR(t)**.  
  - Emits `trigger_signal{}` and epoch‑binding cues.  
  - Performs no inference, no repair, and no TP mutation.

- **SRP (Semantic Routing Planner):**  
  - Cold‑path compiler that builds **B‑side routing tables** and assigns `routing_epoch_id`.  
  - Does not read TP, MTP, TB, or meaning; compiles tables from B‑side schemas, operator registries, and policy registries.  
  - Hot‑path components perform lookup only.

- **routing_epoch_id:**  
  - Immutable identifier binding Path‑B execution to a specific SRP routing table epoch.  
  - Prevents epoch mismatch between planning and realization.

- **XP / exec_plan / exec_trace:**  
  - Deterministic, audit‑ready execution plan for Path‑B realization.  
  - Regenerated from SSR(t) and routing metadata each cycle; never meaning‑bearing, never part of Path‑A.  
  - Exists solely to make Path‑B realization deterministic, auditable, and meaning‑agnostic.

## 4.10 Realization substrate construction (REx, RPlan, RPU, ReB)

**Mini‑flow:**  
**TP (read‑only) → REx → RPlan → RPU → ReB**

- **Purpose:**  
  Construct, refine, and validate a **realization substrate** from the finalized TP and B‑side planning, without altering meaning.

- **REx (Realization Extractor):**
  - Reads the finalized SSR (including `ssr.meaning`, `ssr.truth_tags`, `ssr.safety_flags`, `ssr.continuity_fields`) **read‑only**.
  - Extracts realization‑relevant substrate: clause‑level structure, dependencies, discourse roles, referential anchors, realization constraints.
  - Performs **no semantic interpretation** and **no TP or SSR writes**.

- **RPlan (Realization Plan Construction):**
  - Consumes REx output and constructs **candidate realization plans**:
    - structure, pacing, tone, channel, realization constraints.
  - Plan construction only; no meaning modification, no TP or SSR writes, no semantic inference.

- **RPU (Realization Plan Updater):**
  - Executes the realization plan produced by RPlan, generating the **realization substrate** (style, pacing, channel, structure).
  - Operates only on realization‑side structures (`RP‑ref`, `RPlan‑ref`, `ReB`); **MUST NOT write to SSR**.
  - Normative invariant: `RPU‑prm` is **Path B only**, never a SSR writer.

- **ReB (Realization Basin — Path B Pre‑Builder Basin):**
  - Validates the post‑RPU realization substrate:
    - constraint/invariant consistency, channel/audience coherence, meaning‑preservation.
  - Emits either `reb_validated_ref` or `BLOCKED`.
  - Performs no planning, rewriting, generation, or style selection.

- **Architectural notes:**
  - This group is **pure realization**: it never invokes `TPU`, never writes `semantic_core`, and never participates in Path A routing.
  - ReB is the **validation boundary**: only structurally sound, invariant‑preserving substrates proceed to output construction.

## **4.11 Realization and Output Commit (ReB → RG → Seed Boundary → OuBB)**

**Mini‑flow:** ReB → RG → Random Seed Boundary → OuBB

**ReB:**  
Resolves realization semantics and prepares the realization substrate for expression.  
Does not perform routing, truth evaluation, governance, or semantic interpretation.

**Response Generator (RG):**  
Consumes **SSR(t)** (encapsulating TP‑meaning, TPTB, TPSF, continuity fields, and realization metadata).  
Performs deterministic expression mapping over the meaning substrate delivered inside SSR(t).  
Given identical (SSR(t), seed), produces identical surface‑form output.

**Random Seed Boundary:**  
Isolates nondeterminism to expression selection.  
Enforces replay invariants: identical SSR(t) + seed → identical surface form.

**OuBB:**  
Receives the finalized surface‑form output from RG.  
Writes output_commit=true and terminal=true into OuBB_artifact_ref/exec_trace, not SSR.  
Hands control to TS for emission.  
Is the final block in the turn; no primitives follow OuBB.

## 4.12 Ingress/egress summary for Path B

- **Ingress from Path A / DF:**
  - **OuBA → KnC → KnM → KnF → TPTB → TPSF → CoHI → LI → TrigRB**
  - Path B begins only after **meaning is frozen** and truth/safety evaluation is complete.

- **Internal B‑side planning and realization:**
  - **TrigRB → SRP → routing_epoch_id → XP → REx → RPlan → RPU → ReB**

- **Egress to TS / HC‑Flow / DF:**
  - **ReB → OuBB → TS emission → HC‑Flow (MTP → COB → CIL → CoHI) → next turn’s Path B**
  - DF (`IB → TB → GBIB → GB`) continues to operate **only on committed meaning**, never on in‑flight Path B structures.

## **4.13 Path‑B XP Assembly Flow (OpBeh–OBG–XlateR)**

Path‑B begins once Path‑A has produced the committed meaning snapshot (SSR), KnB has inputed specific knowledge into SSR and the committed routing record (RRw) is also committed. These artifacts, along with CoHI and governance blocks, form the ingress into the Path‑B execution pipeline.

## **4.14 Path‑B Ingress**

```
SSR → TPTB
RRw → TPTB
CoHI → TPTB
GB → TPTB
```

TPTB receives the committed meaning (SSR), the committed routing record (RRw), continuity inference (CoHI), and governance constraints (GB). TPTB prepares these inputs for downstream semantic framing.

## **4.14 Semantic Framing**

```
TPTB → TPSF
```

TPSF performs turn‑level semantic framing, producing the structured semantic frame required for execution planning.

| RPU       | No SSR access       | None                                           | Feeds realization substrate to ReB | Executes realization plans |
| ReB       | No SSR access       | None                                           | Emits validation result to RG/RSG | Validates realization substrate |
| RG        | Read-only           | None                                           | Feeds base surface form to RSG | Performs deterministic expression mapping |
| RSG       | Read-only           | None                                           | Produces final OuBB surface form | Applies manifold-based variant selection |
| OuBB      | No SSR access       | None (writes to exec_trace / output artifacts) | Terminal output | Delivers finalized surface form |

# 5. Routing Triple (OpBeh–OBG–XlateR)**

RRw provides the routing identifiers that select the behavior, voice/identity basin, and mapping profile:

```
RRw.opbeh_id   → OpBeh
RRw.obg_id     → OBG
RRw.xlater_id  → XlateR
```

These three primitives form the execution‑planning triple that determines how the committed meaning will be realized.

## **5.1 XP Assembly**

```
(OpBeh, OBG, XlateR) → XP
```

XP is the execution plan for the turn. It integrates:

- the semantic frame from TPSF

XP is the complete specification of how the turn will be realized.

## **5.2 Path‑B Execution Pipeline**


- **LI** performs lexical integration.  
- **REx** performs realization expansion.

- **RPU** performs realization production.  
- **OuBB** performs output boundary binding and finalization.

This completes the Path‑B execution flow for the turn.

# **6. HC‑Flow (Historical Conversation Flow)**

## **6.1 Purpose**  
HC‑Flow provides the Thought Supervisor (TS) with long‑term conversational perspective by processing the committed historical TP stream. Its purpose is to supply TS with multi‑turn conversational reference so that TS can interpret the current turn in the context of prior TP states and previously committed conversational structure. HC‑Flow operates as a slow‑reader subsystem and does not participate in real‑time turn execution.

HHC‑Flow consumes the committed TP stream associated with OuBB‑committed turns and transforms it through **MTP**, **COB**, and **CIL** into structured conversation‑level inference. This inference is delivered to Path B through **CoHI** for use during realization.

---

## **6.2 Internal Flow**  
HC‑Flow consists of the following primitives, defined in the glossary:

```
MTP → COB → CIL → CoHI
```

- **MTP — Master Thought Packet**  
  Consumes the committed historical TP stream and provides multi‑turn memory structure.

- **COB — Conversation Object Basin**  
  Constructs structured conversation‑level objects from MTP output.

- **CIL — Conversation Integration Layer**  
  Produces long‑horizon conversational inference from COB output.

- **CoHI — Conversation History Integrator**  
  Integrates conversation‑level inference into Path B.

---

## **6.3 Ingress Chain (Path B → HC‑Flow)**  
HC‑Flow receives its input exclusively from Path B through the committed TP snapshots produced by **OuBB**.

The ingress chain is:

```
REx → RPlan → RPU → ReB → OuBB → MTP
```

- **REx — Realization Extractor**  
  Extracts realization substrate for Path B.

- **RPlan — Realization Plan Construction**  
  Constructs realization plans.

- **RPU — Realization Processing Unit**  
  Produces realization units.

- **ReB — Realization Basin**  
  Validates realization units.

- **OuBB — Output Basin (Path B commit)**  
  Commits the final realization snapshot.

- **MTP — Master Thought Packet**  
  Consumes the committed TP stream as the entry point to HC‑Flow.

This is the **only** legal ingress path into HC‑Flow.

---

## **6.4 Egress Chain (HC‑Flow → Path B)**  
HC‑Flow outputs long‑horizon conversational inference into Path B through **CoHI**.

The egress chain is:

```
CoHI → LI → REx
```

- **CoHI — Conversation History Integrator**  
  Integrates conversation‑level inference into Path B.

- **LI — Local Inference**  
  Performs local inference using CoHI‑supplied continuity fields.

- **REx — Realization Extractor**  
  Consumes continuity‑conditioned inference for realization extraction.

This is the **only** legal egress path from HC‑Flow into Path B.

---

## **6.5 Summary Diagram**

```
          (Ingress: Path B → HC‑Flow)
REx → RPlan → RPU → ReB → OuBB → MTP → COB → CIL → CoHI
                                                        ↓
                                                   LI → REx
                                           (Egress: HC‑Flow → Path B)
```

---

## **6.6 Architectural Notes**
- HC‑Flow connects **only** to Path B.  
- Path A contributes indirectly only through OuBA → OuBB → MTP, but does not connect to HC‑Flow.  
- CoHI is the **exclusive** Path B intake for HC‑Flow outputs.  
- HC‑Flow operates in slow‑reader mode and does not participate in real‑time meaning construction or realization.  
- CIL is the **sole** HC‑Flow primitive that produces outputs consumed by Path B.

# **7. IB‑Flow (Inquiry Basin Flow)**

## **7.1 Purpose**  
IB‑Flow evaluates committed meaning produced by Path A. Its purpose is to provide governance‑side inquiry, truth evaluation, and supervisory review over the committed SSR snapshot produced by **OuBA**. IB‑Flow does not participate in meaning construction and does not modify Path A state. Instead, it evaluates whether the committed meaning satisfies inquiry, truth, and governance criteria, and determines whether the object should be promoted into Path A as an **IdOB** or routed into Path B for realization‑side influence.

IB‑Flow operates entirely on committed meaning and never on in‑flight Path A structures.

---

## **7.2 Ingress (Path A → IB‑Flow)**  
IB‑Flow receives its input exclusively from the Path A commit point:

```
OuBA → IB
```

- **OuBA — Output Basin (Path A commit)**  
  Produces the committed semantic_core snapshot for the turn.  
  This is the *only* legal ingress into IB‑Flow.

- **IB — Inquiry Basin**  
  Receives the committed meaning and initiates inquiry‑side evaluation.

No other Path A primitive may feed IB.  
IB never receives in‑flight or partially constructed meaning.

---

## **7.3 Internal Flow**  
IB‑Flow consists of the following primitives, defined in the glossary:

```
IB → TB → GBIB → GB
```

- **IB — Inquiry Basin**  
  Performs inquiry‑side evaluation of the committed semantic_core snapshot.

- **TB — Truth Basin**  
  Evaluates truth‑relation structure and produces truth‑evaluation summaries.

- **GBIB — Governing Basin Inquiry Bridge**  
  Integrates inquiry and truth evaluations and prepares governance‑side context.

- **GB — Governing Basin**  
  Performs final governance evaluation, determines promotion eligibility, logs governance events, and emits outputs to Path A or Path B.

---

## **7.4 Promotion Path (IB‑Flow → Path A)**  
IB‑Flow does not write into Path A except through **GB‑authorized promotion**.

If GB determines that the evaluated object satisfies **OB** and **IdOB** requirements, GB may promote the object into Path A as an **IdOB**.

The promotion path is:

```
GB → IdOB (Path A)
```

Promotion is a governance‑side event and must be logged by GB before the IdOB enters Path A.

### **GB Promotion Logging Requirements**  
GB must log the following attributes into the TP:

- **when** — timestamp and TP index of the promotion  
- **where** — source basin (IB‑Flow) and destination basin (IdOB in Path A)  
- **why** — promotion reason code and criteria satisfied  
- **attributes** — IB identity, TB truth‑evaluation summary, GBIB supervisory context, and resulting IdOB fields

No other primitive may promote objects into Path A.

---

## **7.5 Egress (IB‑Flow → Path B)**  
If GB determines that the evaluated object should influence realization rather than meaning construction, GB emits governance‑side inference into Path B through **REx**.

The egress chain is:

```
GB → REx
```

- **GB — Governing Basin**  
  Produces governance‑side inference for realization.

- **REx — Realization Extractor**  
  Consumes governance inference for use in Path B realization planning.

This is the *only* legal egress from IB‑Flow into Path B.

---

## **7.6 Summary Diagram**

```
          (Ingress: Path A → IB‑Flow)
OuBA → IB → TB → GBIB → GB
                           ↘
                            ↘ (Egress: IB‑Flow → Path B)
                             REx

                           ↘
                            ↘ (Promotion: IB‑Flow → Path A)
                             IdOB
```

---

## **7.7 Architectural Notes**
- IB‑Flow operates only on committed meaning from OuBA.  
- IB‑Flow never modifies Path A and never receives in‑flight Path A structures.  
- Promotion into Path A requires GB authorization and TP logging.  
- GB is the sole authority for promotion and governance‑side evaluation.  
- IB‑Flow outputs either:  
  - **IdOB** into Path A (promotion), or  
  - **governance inference** into Path B (via REx).  
- IB‑Flow has no direct connection to HC‑Flow.  
- IB‑Flow is structurally parallel to HC‑Flow but operates on different substrates (committed meaning vs. committed TP).
