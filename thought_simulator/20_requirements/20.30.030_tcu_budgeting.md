# **20.30.030 — TCU Budgeting & Deterministic Degradation**  
**Status:** Normative  
**Scope:** TCU budgeting, compute envelopes, deterministic degradation  
**Excludes:** Cycle allocation (20.30.020), MCS rules (20.30.040), merge semantics (20.30.050)

---

# **0. Purpose**

This document defines the **TCU budgeting model** for the Thought Simulator (TS).  
It describes:

- how computational cost is normalized  
- how subsystem budgets are defined  
- how the TS maintains deterministic behavior under load  
- how deterministic degradation is applied when budgets are exceeded  

Metadata structures such as TPTB and TPSF are zero‑cost; only the upstream truth and safety evaluation steps that generate them contribute to TCU usage.

This file provides the compute‑level foundation for stability and replay equivalence.

---

# **1. TCU Model Overview**

A **Thought Compute Unit (TCU)** is a normalized unit of computational cost.  
It abstracts away hardware differences and provides a consistent measure of:

- routing update cost (RTU‑prm)  
- routing refinement cost (TR‑prm)  
- splitting cost  
- OB processing cost  
- TB interpretation cost  
- merge cost  
- truth/completion evaluation cost  
- MTP update cost  
- truth‑metadata generation cost (TPTB) — counted as part of truth/completion evaluation  
- safety‑metadata generation cost (TPSF) — counted as part of safety evaluation  

The TCU model enables deterministic budgeting and predictable degradation behavior.

---

# **2. Calibration Kernel**

The TS uses a fixed calibration kernel to determine the machine’s baseline TCU rate.  
The kernel is a deterministic arithmetic loop whose runtime is measured once at initialization.

The calibration establishes:

- the baseline TCU per millisecond  
- the per‑cycle compute envelope  
- the min/typ/max budgets for each subsystem  

The kernel is descriptive here; implementation details are defined in the 10‑series.

---

# **3. Subsystem TCU Budgets**

Each subsystem operates within a deterministic TCU envelope.  
Budgets are expressed as **min/typ/max** values to support:

- predictable performance  
- deterministic degradation  
- bounded compute usage  
- replay equivalence  

Subsystems include:

- RTU‑prm (routing update)  
- TR‑prm (routing refinement)  
- splitting  
- OB processing  
- TB interpretation  
- merge  
- truth/completion evaluation  
- MTP update  

These budgets define the compute‑level stability envelope for the TS.

---

# **4. Deterministic Degradation Model**

When a subsystem exceeds its TCU budget, the TS applies **deterministic degradation**.  
Degradation is designed to:

- preserve meaning construction  
- maintain replay equivalence  
- avoid nondeterministic behavior  
- prevent runaway compute usage  

Examples of deterministic degradation include:

- reducing semantic shading  
- skipping non‑critical TB channels  
- postponing lineage updates  
- reducing evidence detail  
- compressing ΔH% contributions  

Degradation never alters the meaning‑construction contract and never introduces nondeterminism.

---

# **5. Compute Reporting**

Each cycle produces a deterministic compute report containing:

- TCU usage per subsystem  
- total TCU usage  
- ΔH% cost attribution  
- MTP update cost  
- any degradation applied  

This report supports:

- auditability  
- replay verification  
- supervisory visibility  
- performance diagnostics  

---

# **6. Normative Requirements (HLR‑20.30.030‑xxx)**

These are the **only** SHALL‑bearing requirements in this file.

### **HLR‑20.30.030‑001 — TCU Definition**  
The TS SHALL define a normalized Thought Compute Unit (TCU) using a deterministic calibration kernel.

### **HLR‑20.30.030‑002 — Subsystem Budgets**  
The TS SHALL define deterministic min/typ/max TCU budgets for each subsystem in the TS cycle.

### **HLR‑20.30.030‑003 — Budget Enforcement**  
Each subsystem SHALL operate within its defined TCU envelope unless deterministic degradation is applied.

### **HLR‑20.30.030‑004 — Deterministic Degradation**  
When a subsystem exceeds its TCU budget, the TS SHALL apply deterministic, policy‑bounded degradation behavior.

### **HLR‑20.30.030‑005 — No Nondeterministic Recovery**  
Degradation SHALL NOT involve probabilistic reconstruction, latent‑state inference, or nondeterministic fallback behavior.

### **HLR‑20.30.030‑006 — Compute Reporting**  
The TS SHALL produce a deterministic per‑cycle compute report including subsystem TCU usage and any applied degradation.

### **HLR‑20.30.030‑007 — Replay‑Safe Degradation**  
Degradation outcomes SHALL be identical for identical $(\text{input}, \text{MTP state}, \text{execution signature})$ tuples.

### **HLR‑20.30.030‑008 — ΔH% Cost Attribution**  
The TS SHALL attribute ΔH%‑related compute cost deterministically in the per‑cycle compute report.

### **HLR‑20.30.030‑009 — MTP Update Cost Accounting**  
The TS SHALL include deterministic MTP update cost in the per‑cycle compute report.

### **HLR‑20.30.030‑010 — Zero‑Cost Metadata Structures**  
Truth‑metadata (TPTB) and safety‑metadata (TPSF) SHALL be treated as zero‑cost structures for TCU budgeting; only the evaluation steps that generate them SHALL contribute to TCU usage.

---

# **7. Summary**

20.30.030 defines the compute‑level foundation for TS stability:

- normalized TCU model  
- deterministic subsystem budgets  
- deterministic degradation  
- deterministic compute reporting  
- replay‑safe behavior under load  

Detailed MCS rules appear in 20.30.040.
