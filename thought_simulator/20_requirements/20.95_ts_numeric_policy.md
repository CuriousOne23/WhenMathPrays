# 20.95 TS Numeric Policy

**Document ID:** 20.95  
**Version:** 0.3  
**Date:** 2026-06-06  
**Status:** CP-approved — dual-pipeline numeric contract (v0.2 refinements applied)

## Purpose

Defines the canonical arithmetic contract for deterministic numeric behavior across TS runtime, coprocessor offload, and CPU fallback execution.

This document is normative for numeric representation, rounding, overflow handling, reduction rules, comparison behavior, envelope serialization, and replay-diff preimages. It SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

## Normative Determinism Statement

Hashing, serialization, compression, and replay strip-diff require **bit-level determinism**.  
Arithmetic operations require **numeric-equivalence determinism** under this policy.

## Parent Scope

- **Applies to:** all authoritative numeric state in `semantic_core`, `supervisory`, and numeric fields in governance records
- **Replay authority:** strip-diff and golden fixtures per [20.36_canonical_end_to_end_trace.md](20.36_canonical_end_to_end_trace.md) SHALL use this policy
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Scope and Compatibility Targets

Required for compatibility with:

- 10.10.10 System Architecture (state and replay model)
- 10.10.20 Interprocess Communication and Channels
- 10.10.60 Coprocessor Offload and Portability Rules
- [20.92_ts_parameter_table.md](20.92_ts_parameter_table.md) (numeric bounds)
- [20.39_ts_core_data_structures.md](20.39_ts_core_data_structures.md) (struct serialization)

## Arithmetic Model

TS uses a hybrid canonical model:

- **Authoritative numeric state:** signed fixed-point **Q32.32** stored in int64 containers.
- **Derived compute acceleration:** constrained binary64 permitted only as an intermediate form when canonicalized back to Q32.32 before comparison, commit, hash, or serialization.

Canonical Q32.32 scale factor:

- `scale = 2^32`
- `encoded_value = round_half_to_even(real_value * scale)`
- `decoded_value = encoded_value / scale`
- **Negative zero:** canonical Q32.32 SHALL normalize `encoded_value = 0` for −0 inputs (HLR-20.095-032)

## 1. Core Numeric Requirements

1. **HLR-20.095-001:** Authoritative state arithmetic SHALL use canonical Q32.32 representation.

2. **HLR-20.095-002:** Any non-canonical intermediate representation SHALL be canonicalized before commit, comparison, hashing, and serialization.

3. **HLR-20.095-003:** Rounding mode SHALL be round-half-to-even for all canonicalization and quantization steps.

4. **HLR-20.095-004:** Overflow behavior for bounded state fields SHALL be deterministic saturating arithmetic unless reject-with-audit is specified by field policy.

5. **HLR-20.095-005:** Underflow behavior for bounded magnitude fields SHALL clamp to zero when absolute value is below one least significant fixed-point unit.

6. **HLR-20.095-006:** Equality for authoritative arithmetic SHALL be exact integer equality of canonical Q32.32 values.

7. **HLR-20.095-007:** Ordering comparisons SHALL be performed on canonicalized integer form only.

8. **HLR-20.095-008:** Deterministic reductions SHALL use canonical ordering and deterministic pairwise reduction topology.

9. **HLR-20.095-009:** Canonical ordering for reductions SHALL be lexicographic by `(module_id, tp_seq, lineage_seq, field_name)`.

10. **HLR-20.095-010:** Floating-point NaN, Inf, or denormal values SHALL be rejected with fixed reason codes before canonicalization.

11. **HLR-20.095-011:** ΔH% normalization SHALL produce canonical Q32.32 outputs before enforcement checks; relative volatility ordering across parallel contradiction traces (20.17 HLR-20.017-039) SHALL use canonical integer rank comparison on post-normalization ΔH% values. ΔH% SHALL be interpreted according to the unified structural‑entropy delta definition in HLR‑20.030‑015 (20.30 §2.6).

12. **HLR-20.095-012:** Vectorized arithmetic SHALL be acceptable only when canonical equivalence with CPU fallback is preserved.

13. **HLR-20.095-013:** Deterministic hashing inputs SHALL be generated only from canonical serialized numeric form.

14. **HLR-20.095-014:** Deterministic compression SHALL operate on canonical byte streams and SHALL NOT alter numeric semantics.

15. **HLR-20.095-015:** CPU fallback and coprocessor outputs SHALL be equivalent after canonicalization.

16. **HLR-20.095-016:** Tolerance SHALL be zero for authoritative commit decisions.

17. **HLR-20.095-017:** Optional diagnostic-only tolerances MAY be used for non-authoritative display metrics and SHALL NOT influence control or commit paths.

18. **HLR-20.095-018:** Numeric serialization SHALL be canonical and endianness-stable for replay and hash reproducibility.

19. **HLR-20.095-019:** Arithmetic policy violations SHALL be treated as deterministic conformance failures.

20. **HLR-20.095-020:** Any change to representation, rounding, overflow rules, or serialization SHALL require replay compatibility review per [20.36](20.36_canonical_end_to_end_trace.md).

21. **HLR-20.095-021:** Mixed-path computation (CPU plus offload) SHALL preserve deterministic reduction order under this policy.

22. **HLR-20.095-022:** Numeric policy SHALL remain cross-consistent with 20.92 parameter bounds and 10.10.60 offload constraints.

## 2. Dual-Pipeline Envelope Numeric Rules

| Envelope | Numeric domain | Representation |
|----------|----------------|----------------|
| `semantic_core` | ΔH%, missing-mass, stance weights, policy metrics | Q32.32 |
| `semantic_core` | Proposition/goal IDs, sequence refs | uint64 or UTF-8 string (non-float) |
| `exec_plan` / `exec_trace` | Planning refs, cycle IDs | uint64 counters |
| `supervisory` | Cap counters, `defer_cycle_count`, `escalation_depth` | uint64 |
| `supervisory` | `branching_suppression_factor`, TCU share | Q32.32 |

23. **HLR-20.095-023:** `semantic_core` authoritative numeric fields SHALL use Q32.32; Pipeline B SHALL NOT introduce floating intermediates into `semantic_core` serialization or replay preimages.

24. **HLR-20.095-024:** GB cap counters, IMR depth/cooldown counters, cycle IDs, and sequence indices SHALL use uint64; they SHALL NOT be stored as binary64 floats.

25. **HLR-20.095-025:** `tcu_overrun_amount` and `branching_suppression_factor` (20.80) SHALL be Q32.32 when numeric; comparison for cap enforcement SHALL use exact canonical equality/ordering.

31. **HLR-20.095-031:** GB cap enforcement, rate-limit counting, and supervisory numeric comparisons (20.16, 20.80) SHALL occur only on **canonicalized** uint64 or Q32.32 values; raw binary64 intermediates SHALL NOT feed cap-exceed decisions.

32. **HLR-20.095-032:** Canonical Q32.32 SHALL normalize negative zero to positive zero (`encoded_value = 0`); serialization and equality checks SHALL treat −0 and +0 as identical.

## 3. Replay and Strip-Diff Serialization

26. **HLR-20.095-026:** Replay strip-diff preimages per HLR-20.012-011 SHALL serialize `semantic_core` and retained `supervisory` records using this policy; `exec_plan` and `exec_trace` SHALL be excluded from semantic replay equivalence preimages when `strip_scope` so specifies (20.36).

27. **HLR-20.095-027:** Golden fixture byte-compare (20.36 Class 1) SHALL use identical canonical serialization for both dual-pipeline stripped output and Pipeline A-only baseline.

28. **HLR-20.095-028:** `replay_verdict` emission SHALL NOT depend on decimal text rendering; verdict inputs SHALL be canonical binary preimages only.

## 4. Canonical Array and Record Ordering

Authoritative arrays SHALL be sorted before serialization when order is semantically insignificant:

| Array / field | Sort key |
|---------------|----------|
| Reduction inputs | `(module_id, tp_seq, lineage_seq, field_name)` per HLR-20.095-009 |
| `lineage[]` | `(module_id, tp_seq, lineage_seq)` |
| `propositions[]` | stable `proposition_id` lexicographic |
| `goals[]` | stable `goal_id` lexicographic |
| `messy_input_class[]` | class code lexicographic: `MI_AFFECT`, `MI_CONTRA`, `MI_INCOMP`, `MI_NOISE`, `MI_VAGUE` |
| `deferred_action_ids[]`, `gb_cap_record` lists | canonical ID lexicographic |
| Governance record fields | schema-defined canonical field order per source module |

29. **HLR-20.095-029:** Harnesses SHALL reject replay fixtures and exports with non-canonical array ordering when a canonical sort is specified above or in 20.17/20.36.

30. **HLR-20.095-030:** Object keys in canonical JSON/binary serialization SHALL sort ascending bytewise UTF-8; numeric object values SHALL be encoded in canonical Q32.32 or uint64 form only — never IEEE decimal strings in authoritative paths.

33. **HLR-20.095-033:** Numeric overflow, underflow, and reject events SHALL emit fixed `numeric_reason_code` values from the canonical schema below; governance-layer codes (`gb_cap_code`, etc.) SHALL remain separate and MAY reference numeric codes in audit payloads.

### Canonical numeric audit reason codes

| Code | Condition | Typical action |
|------|-----------|----------------|
| `NUM_REJECT_NAN` | NaN input before canonicalization | Reject with audit |
| `NUM_REJECT_INF` | ±Inf input | Reject with audit |
| `NUM_REJECT_DENORMAL` | Denormal binary64 input | Reject with audit |
| `NUM_OVERFLOW_SATURATE` | Bounded Q32.32 overflow | Saturate to min/max |
| `NUM_OVERFLOW_REJECT` | Strict-no-clamp field overflow | Reject with audit |
| `NUM_UNDERFLOW_ZERO` | Below one LSB magnitude | Clamp to zero |
| `NUM_NEGZERO_NORMALIZED` | −0 canonicalized to +0 | Log optional; value = 0 |

Governance cap codes (`GB_CAP_*`, `DEFER_*`, etc.) are defined in 20.16/20.80 and SHALL NOT replace numeric reason codes when the root cause is arithmetic policy violation.

## Canonical Numeric Rules (Reference)

### Representation Model

| Domain | Canonical Representation | Notes |
|--------|-------------------------|-------|
| Authoritative TS state (ΔH%, policy metrics, suppression factors) | signed Q32.32 in int64 | Commit, compare, hash, replay |
| Counters (caps, cycles, depths, sequences) | uint64 | No floating conversion |
| Intermediate acceleration | constrained binary64 | Canonicalize before commit |

### Rounding Mode

- Canonical: round-half-to-even
- Forbidden: stochastic, toward-infinity-only, implementation-default unknown modes

### Overflow and Underflow

- Saturating arithmetic default for bounded Q32.32 fields
- Reject-with-audit for strict-no-clamp fields
- Underflow-to-zero when `abs(encoded_value) < 1` LSB and policy allows

### Comparison and Equality

- Equality: exact canonical integer equality
- Ordering: canonical integer ordering only
- No epsilon comparison on authoritative paths

### Deterministic Reduction

- Inputs canonicalized before reduction
- Sorted by `(module_id, tp_seq, lineage_seq, field_name)`
- Fixed-tree pairwise reduction; no thread-schedule dependency

### Numeric Serialization Format

- int64 / uint64: two's-complement big-endian 8 bytes
- Q32.32: canonical int64 encoded value
- Decimal text: derived view only — not authoritative for hash or replay

---

## Offload and CPU Fallback Equivalence

Offloaded numeric kernels must satisfy before acceptance:

- same canonical input bytes
- same canonicalized Q32.32 output bytes
- same deterministic reduction order
- same reject/overflow outcomes
- same audit reason codes for numeric-policy failures

---

## Deterministic Services Coverage

This policy supports:

- deterministic hashing and compression
- ΔH% normalization and volatility rank checks
- replay strip-diff (20.36 Classes 1–5)
- vectorizable arithmetic with canonicalization
- CPU/offload equivalence

## Conformance

Implementation conforms when:

- authoritative math uses canonical representation and rules
- envelope-specific types (Q32.32 vs uint64) are respected
- offload and CPU paths produce canonical-equivalent outcomes
- canonical serialization is used for hash, replay, and compression
- non-authoritative tolerances never affect supervisory or commit behavior

## Verification Focus

- Class 1 golden fixture byte-compare stable across platforms
- Cap counter arithmetic exact (uint64, no float drift); GB compares post-canonicalization only (HLR-20.095-031)
- Negative zero normalizes to +0 in Q32.32 equality and serialization
- Numeric overflow emits fixed `numeric_reason_code` from §4 schema
- ΔH% volatility rank invariant under normalization (20.17)
- Non-canonical array ordering rejected by harness
- Decimal display path isolated from `replay_verdict`
