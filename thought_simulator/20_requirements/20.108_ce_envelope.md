# **20.108 — CE Envelope**  
**Document ID:** 20.108  
**Version:** 1.1 (TP‑Field Cleanup)  
**Date:** 2026‑07‑17  
**Upstream:** CEx (20.107)  
**Downstream:** ISc (20.44)

---

## **1. Purpose** *(Informative)*

CE (Context Envelope) is the **structured, deterministic context object** produced by CEx.  
It is the *only* context object that ISc may read, and it serves as the **handoff boundary** between Path‑A extraction and the first semantic module.

CE’s purpose is twofold:

### **1. Provide a safe, bounded, pre‑semantic representation of context**  
CE contains only **explicit, normalized, bounded fields** extracted from CIL.  
It carries no inferred meaning, no semantic repair, no embeddings, and no latent vectors.  
CE ensures that all downstream semantic modules receive a **clean, deterministic, replay‑equivalent** context object.

### **2. Communicate CEx’s deterministic identity‑layer selection**  
CE encodes the identity‑layer chosen by CEx for the present turn, including:

- continuity decisions  
- ambiguity resolution  
- fallback selection  
- collapse fallback  
- ordering‑metric usage  
- whether continuity was preserved, overridden, or undetermined  

Downstream primitives (ISc → TPU → TP(N+1)) rely on CE to understand **which conversation context is active** and **why** it was selected.

CE is a **data primitive**, similar in status to **TP (the full packet)**, MTP, and semantic_core, but strictly pre‑semantic.  
It ensures that all semantic processing begins from a **stable, deterministic, context‑aware foundation** chosen by CEx.

# **2. Role in the Inference Path** *(Informative)*

```
InB → IIInB → IE → CEx → CE → ISc → TPU → TP(N+1)
```

CE is the **handoff boundary** between Pipeline‑A extraction and the first semantic module (ISc).  
It ensures that ISc receives a **safe, deterministic, replay‑equivalent** context object.

---

# **3. Nature of CE** *(Informative)*

CE is:

- a **bounded** context object  
- a **canonical** structure  
- a **deterministic** representation of extracted fields  
- a **non‑semantic** envelope  
- a **versioned** data primitive  

CE is **not**:

- a meaning layer  
- a semantic repair layer  
- a classifier  
- a routing object  
- a ΔH% carrier  
- a TB/IB/Truth Done structure  
- a Pipeline‑B envelope  

---

# **4. Inputs and Outputs** *(Informative)*

**Input:**  
- CEx output (extracted fields + audit trail)

**Output:**  
```
ce_record {
    context_fields{},     // structured, normalized, bounded
    extraction_audit[],   // deterministic audit entries
    ce_version_tag
}
```

ISc consumes `context_fields{}` and may inspect `extraction_audit[]` for transparency.

---

# **5. Structural Properties** *(Informative)*

CE is a **fixed‑schema** object with:

- canonical field names  
- canonical ordering  
- canonical encoding  
- bounded field sizes  
- deterministic normalization rules  

Fields not present in CIL do not appear in CE.  
Fields outside the allowlist do not appear in CE.

---

# **6. Allowed Content** *(Informative)*

CE may contain:

- explicit user‑provided context strings  
- explicit system‑provided context strings  
- timestamps  
- structural metadata  
- conversation window slices  
- explicit parameters  
- explicit flags  
- extraction audit entries  

All content must be **explicit**, **non‑semantic**, and **non‑inferred**.

---

# **7. Forbidden Content** *(Informative)*

CE may **not** contain:

- inferred semantics  
- embeddings  
- latent vectors  
- meaning‑layer fields  
- routing metadata  
- ΔH%  
- TB/IB fields  
- semantic_core fields  
- Pipeline‑B envelopes  
- any field not explicitly extracted by CEx  

---

# **8. Determinism and Replay** *(Informative)*

CE is fully deterministic:

- identical CIL + identical policy_signature → identical CE  
- ordering is canonical  
- normalization is canonical  
- extraction_audit is canonical  

Replay must yield byte‑identical CE.

---

# **9. Error Behavior** *(Informative)*

If CIL is malformed:

- CE still emits  
- only valid extracted fields appear  
- invalid fields are dropped  
- audit entries record all drops  
- CE remains deterministic  

CE never halts the pipeline.

# **10. High‑Level Requirements (HLRs)**

### **HLR‑20.108‑001**  
CE SHALL contain only explicit, bounded, normalized fields extracted by CEx.

### **HLR‑20.108‑002**  
CE SHALL be the only context object that ISc is permitted to read.

### **HLR‑20.108‑003**  
CE SHALL NOT contain inferred, semantic, latent, or probabilistic content.

### **HLR‑20.108‑004**  
CE SHALL use canonical field names, canonical ordering, and canonical encoding.

### **HLR‑20.108‑005**  
CE SHALL be deterministic: identical CIL and policy_signature SHALL produce identical CE.

### **HLR‑20.108‑006**  
CE SHALL include extraction_audit entries for all drops, truncations, and normalizations.

### **HLR‑20.108‑007**  
CE SHALL NOT include routing metadata, ΔH%, TB/IB fields, semantic_core fields, or Pipeline‑B envelopes.

### **HLR‑20.108‑008**  
CE SHALL enforce bounded size limits for all fields.

### **HLR‑20.108‑009**  
CE SHALL NOT modify, reinterpret, or repair any extracted content.

### **HLR‑20.108‑010**  
CE SHALL emit successfully even when CIL is malformed, containing only valid extracted fields.

---

## **New CE Requirements (TP‑Field Cleanup)**

### **HLR‑20.108‑011**  
CE SHALL include the identity‑layer selected by CEx for the present turn.

### **HLR‑20.108‑012**  
CE SHALL include **CE.metadata.continuity_status**, indicating how the identity‑layer was selected:

```
continuity_status ∈ {
    "continuous",
    "switched",
    "fallback",
    "undetermined"
}
```

### **HLR‑20.108‑013**  
CE SHALL set continuity_status = "undetermined" when CEx selects  
**TP.process.identity_layer_prev** due to ambiguity or indeterminate identity selection.

### **HLR‑20.108‑014**  
CE SHALL set continuity_status = "fallback" when CEx selects a stable identity‑layer due to collapse_risk exceeding threshold.

### **HLR‑20.108‑015**  
CE SHALL set continuity_status = "switched" when CEx overrides continuity due to high certainty and low ambiguity.

### **HLR‑20.108‑016**  
CE SHALL set continuity_status = "continuous" when CEx preserves **TP.process.identity_layer_prev**.

### **HLR‑20.108‑017**  
CE SHALL include ordering metadata provided by CEx:

```json
ordering_metrics {
    last_referred: TurnID,
    total_referrals: int,
    recent_referrals: int,
    ordering_score: float
}
```

### **HLR‑20.108‑018**  
CE SHALL NOT compute ordering metrics; it SHALL only reflect values provided by CEx.

### **HLR‑20.108‑019**  
CE SHALL expose continuity_status and ordering_metrics to downstream modules without modification.

---

### **Clarifying‑Field Requirements (New)**

### **HLR‑20.108‑020**  
CE **shall** include clarifying fields, clarifying subfields, and hierarchical clarifying sub‑subfields (up to four levels) extracted by CEx.

### **HLR‑20.108‑021**  
CE **shall** include clarifying‑field importance scores exactly as provided by CEx, without modification or reinterpretation.

### **HLR‑20.108‑022**  
CE **shall** preserve clarifying‑field topology, including hierarchical relationships and bounded limits, in a deterministic CE structure.

### **HLR‑20.108‑023**  
CE **shall** enforce bounded limits on clarifying fields (maximum 10), clarifying subfields (maximum 100), and hierarchical depth (maximum 4 levels), reflecting any drops or truncations recorded by CEx.

### **HLR‑20.108‑024**  
CE **shall** treat clarifying fields and clarifying subfields as read‑only and shall not modify their values, importance scores, or provenance.

### **HLR‑20.108‑025**  
CE **shall** include clarifying‑field metadata in `context_fields{}` using the following canonical structure:

```json
clarifying_fields {
    fields: [string],
    subfields: [{ field: string, subfield: string }],
    topology: ClarifyingTopologyBlock,
    importance: ClarifyingImportanceBlock
}
```

### **HLR‑20.108‑026**  
CE **shall** guarantee deterministic clarifying‑field representation such that identical CEx output produces identical clarifying‑field content in CE.

### **HLR‑20.108‑027**  
CE **shall** expose clarifying‑field metadata to downstream modules (ISc → TPU → TP(N+1)) without modification.

### **HLR‑20.108‑028**  
CE **shall** include clarifying‑field metadata even when identity selection is ambiguous, indeterminate, or fallback‑based.

### **HLR‑20.108‑029**  
CE **shall** mark clarifying‑field continuity status using the same continuity_status field used for identity‑layer continuity.

### **HLR‑20.108‑030**  
CE **shall** include clarifying‑field metadata in fallback selections and set continuity_status = `"undetermined"` when applicable.

## **Next‑Turn Context Requirements (TP.next_context_fields Cross‑Reference)**

### **HLR‑20.108‑031**  
CE SHALL include next‑turn clarifying/context fields extracted by CEx from `TP.next_context{}` as defined in **20.105_tp_requirements.md`.

### **HLR‑20.108‑032**  
CE SHALL treat next‑turn context fields as explicit, structured, non‑semantic metadata and SHALL NOT modify, reinterpret, or repair their values.

### **HLR‑20.108‑033**  
CE SHALL include the following next‑turn context fields in `context_fields{}` exactly as provided by CEx:  
`topic`, `stance`, `intent`, `register`, `politeness`, `epistemic_shading`, `continuity`, `direction`, `coherence`, `shift_required`, `importance`.

### **HLR‑20.108‑034**  
CE SHALL NOT derive next‑turn context fields from clarifying fields, identity‑layer metadata, referent maps, or structural cues; next‑turn context SHALL originate exclusively from CEx extraction of `TP.next_context{}`.

### **HLR‑20.108‑035**  
CE SHALL guarantee deterministic representation of next‑turn context fields; identical CEx output SHALL produce identical next‑turn context content in CE.

### **HLR‑20.108‑036**  
CE SHALL expose next‑turn context fields to downstream modules (ISc → TPU → TP(N+1)) without modification.

### **HLR‑20.108‑037**  
CE SHALL include next‑turn context fields even when identity selection is ambiguous, indeterminate, or fallback‑based.

### **HLR‑20.108‑038**  
CE SHALL mark next‑turn context continuity using the same `continuity_status` field used for identity‑layer continuity.

### **HLR‑20.108‑039**  
CE SHALL include next‑turn context fields in fallback selections and SHALL set `continuity_status = "undetermined"` when applicable.

### **HLR‑20.108‑040**  
CE SHALL record any next‑turn context drops, truncations, or normalization adjustments in `extraction_audit[]`, following the same deterministic rules used for clarifying‑field extraction.

---

# **11. Conformance** *(Informative)*

CE conforms when:

- all fields are explicit, bounded, and normalized  
- no semantic or inferred content is present  
- deterministic replay is preserved  
- extraction_audit is complete and canonical  
- malformed CIL still yields a valid CE  
- ISc can consume CE without ambiguity
