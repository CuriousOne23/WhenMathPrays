# **Introduction**

## **Purpose**  
This glossary is the canonical reference for the refactored 20‑series and serves as the **Primitive Intent Catalog** for the Thought Simulator architecture. Its role is to define, with precision, what each component *owns*, when it executes, and what it is *not*, ensuring strict intent boundaries and preventing authority drift across modules. Normative high‑level requirements (HLRs) remain in the corresponding 20.xx modules; entries here are descriptive unless explicitly marked normative. Architectural context for runtime‑pipeline blocks (B0–B8) is provided in **20.01_architecture_map.md**.

---

## **How to Read This Catalog**  
Each entry follows a fixed seven‑field template to ensure clarity and architectural consistency:

| Field | Meaning |
|-------|---------|
| **Purpose** | Architectural role: what disappears or breaks if this component is removed |
| **Focus** | Operational ownership: the one‑sentence statement of what this component owns |
| **When** | Execution context: Path A, Path B, conversation layer, post‑TS, or pre‑A |
| **Why** | The specific architectural problem this component solves |
| **Is not** | Common confusions and explicit non‑ownership boundaries |
| **Example** | One concrete scenario illustrating correct behavior |
| **Normative home** | Authoritative 20.xx module defining requirements |

This structure ensures every entry is auditable, comparable, and aligned with the TS execution model.

---

## **Category Structure**  
All glossary entries fall into one of five architectural categories:

| Category | Suffix | Definition |
|----------|--------|------------|
| **1. Primitives** | ‑prm | TP‑holding, TP‑reading, TP‑modifying atomic operations in the TS pipeline |
| **2. Processes** | ‑prc | Pure logic executed *inside* primitives; do not hold or modify the TP |
| **3. Reference Objects** | ‑ref | Static data structures used by primitives and processes; never modify TP |
| **4. Governance** | ‑gov | Supervisory, safety, audit, and correction rules governing TS behavior |
| **5. TS‑Level Concepts** | ‑tsc | Conceptual logic layers (semantic, structural, routing, uncertainty) that do not appear as blocks in flows |

This categorization enforces architectural separation and prevents conceptual drift.

---

## **Diagramming Conventions**  
Primitive flows and process flows use compact horizontal notation.  
Primitive flows represent the actual TP‑carrying execution path; process flows represent conceptual logic executed inside primitives.  
Full rules for diagramming appear in **Section 0: Diagramming Conventions** immediately after this introduction.

---

# **0. Diagramming Conventions**

## **Primitive Flow (TP pipeline)**  
Only primitives appear; this is the actual TP‑carrying execution path:

```
PrimitiveA-prm → PrimitiveB-prm → PrimitiveC-prm
```

---

## **Process Flow (conceptual)**  
A process flow illustrates conceptual logic executed *inside* primitives.  
It is diagrammed separately from the TP pipeline and must be explicitly labeled:

```
Process Flow: PrimitiveA-prm → ProcessName-prc (tsc: ConceptX) → PrimitiveB-prm
```

### **Process Flow Rules**

1. **Process flows are never drawn as part of the primitive TP pipeline.**  
   Primitives carry TP; processes do not.

2. **Every process flow must be explicitly labeled “Process Flow.”**  
   This distinguishes conceptual logic from TP‑carrying execution.

3. **A process flow must begin and end with a primitive.**  
   Processes do not hold or modify TP; they execute inside primitives.

4. **If a process applies to multiple primitives, separate flows must be drawn for each case.**  
   Each flow must specify:  
   - the starting primitive  
   - the ending primitive  
   - the condition or governance rule that selects that flow  

### **Interpretation**  
A process flow shows *how conceptual logic is applied*, not how TP moves.  
Horizontal notation is used to conserve space and maintain consistency with Path A/B diagrams.

# 1. Primitives

## InB (Input Basin) — 20.100
**Purpose:** Provides the deterministic, non-inferential front door for all external signals entering the architecture.
**Focus:** Deterministic external-signal intake, schema validation, and **non-inferential** surface canonicalization.
**When:** Pipeline A entry; first deterministic stage after external input.
**Why:** Normalize wire form and preserve FIFO ordering without guessing user meaning.
**Is not:** Semantic repair (IIInB); inquiry (IB); truth interpretation (TB); routing authority.
**Example:** `"teh"` → canonical token; `"Yeah Baby!"` → tagged, not interpreted.
**Normative home:** 20.100; messy-input classes in 20.17.

---

## IIInB (Input Inference/Repair Basin) — 20.101
**Purpose:** Applies user-sanctioned shorthand expansions before context extraction, keeping repair rule-bound and auditable.
**Focus:** Bounded **semantic shorthand repair** via explicit User Semantic Profile (USP) rules.
**When:** Optional stage `input_semantic_repair`; ordering **InB → IIInB → RB**.
**Why:** Apply user-approved shorthand expansions deterministically without constructing meaning.
**Is not:** Interpretation; candidate generation; truth evaluation; meaning construction.
**Example:** USP rule expands "quicker-ish" → canonical form.
**Normative home:** 20.101.

---

## IE (Intake Envelope, Structured Intake Object)

**Purpose:** Provides a deterministic, bounded, replayable representation of the user's input that can be safely passed to downstream components.
**Focus:** The structured, normalized, repaired intake object produced by InB → IIInB.
**When:** Immediately after IIInB; before CEx.
**Why:** Deterministic, bounded, replayable representation of the user's input for downstream consumption.
**Is not:** A semantic interpretation; a candidate generator; a truth evaluator.
**Example:** Normalized tokens + USP-applied repairs + structural tags.
**Normative home:** 20.109

---

## CEx (ContextExtractor)
**Purpose:** Bridges global conversation state and the inference path by producing a bounded, replayable context slice for ISc.
**Focus:** Deterministic extraction of **bounded, relevant, replayable** context from CIL to form the Context Envelope (CE).
**When:** Inference path: **IIInB → IE → CEx → CE → ISc**.
**Why:** ISc needs context but cannot read global state directly.
**Is not:** A semantic interpreter; a meaning constructor; a Thought Packet (TP) writer.
**Example:** Reads CIL; extracts active referents + lineage + relevant USP entries.
**Normative home:** 20.33 (CIL), 20.44 (ISc), architecture discussion.

---

## CE (ContextEnvelope) — New

**Purpose:** Delivers safe, isolated context to ISc without exposing global conversation state.
**Focus:** Bounded, deterministic, replayable context object consumed by ISc.
**When:** Immediately before ISc in the inference path.
**Why:** Provide ISc with safe, isolated context without exposing global state.
**Is not:** A history; a semantic object; a TP writer; a CIL proxy.
**Example:** CE contains active referents, lineage IDs, relevant commitments.
**Normative home:** Architecture discussion; 20.44.

## **ISc (Inference Scorer) — 20.44**
**Purpose:** Performs deterministic scoring of interpretation candidates by executing the **truth_hypotheses‑prc** process over the candidate_set{}, producing stable, auditable scoring fields in the TP without accessing global state.
**Focus:** Reads CE‑produced candidate_set{}; applies truth_hypotheses‑prc; writes scoring‑layer fields (`tp.score_set`, `tp.score_conflict`, `tp.score_reason_code`) into the TP for downstream routing and TPU commit.
**When:** Path A inference sequence: **CE‑prm → ISc‑prm → TPU‑prm(Merge process)**. Runs after candidate extraction and before merge/commit.
**Why:** Ensures that candidate interpretation scoring is deterministic, local, and reproducible, preventing global‑state leakage and ensuring that routing and TPU commit operate on stable, non‑probabilistic scoring data.
**Is not:** A semantic generator; a meaning constructor; a truth evaluator; a global inference engine; a CIL reader; a semantic repair mechanism; a TS‑level concept.
**Example:** Given multiple referent candidates extracted by CEx‑prm, ISc‑prm applies truth_hypotheses‑prc to compute deterministic scores and writes the resulting score_set into the TP for TR‑prm to route.
**Normative home:** 20.44.

## TPU (Thought Packet Updater) — Path A Only
**Purpose:** The sole safe writer to TP and semantic_core **for Path A correction only**. TPU commits validated *correction/understanding* meaning into durable TP state.
**Focus:** Deterministic, boundary‑enforced TP updates based strictly on CE + CEx + ISc output. TPU performs no topology operations and no realization work.
**When:** Path A correction flow: **CE → ISc → TPU → TP(N+1)**.
**Why:** Enforce the single‑writer invariant for meaning construction; ensure all semantic commits are deterministic, auditable, and isolated from Path B.
**Is not:** A topology engine; a semantic interpreter; a candidate generator; a CIL reader; **a Path B realization primitive**; **a meaning constructor for expression**.
**Example:** ISc selects a corrected referent; TPU applies the update to TP(N), producing TP(N+1) and freezing semantic_core under a new `commit_id`.
**Scope Invariant:** **TPU‑prm MUST NOT be invoked by Path B.** Path B is meaning‑read‑only and cannot write to TP or semantic_core.
**Normative home:** 20.105, architecture discussion.

## **SOB (Structural OB) — 20.40.010**
**Purpose:** Extracts first‑pass structural cues from TP content, forming the base residue used by downstream OB layers and routing.
**Focus:** Clause boundaries, syntactic shape, negation markers, modality markers, structural anchors, and pattern‑family activation.
**When:** First stage of OB evaluation during Pipeline A whenever structural pattern detection is required.
**Why:** Provides deterministic, low‑level structural residue enabling refinement, constraint extraction, and TR‑input formation.
**Is not:** A semantic interpreter; a constraint resolver; a truth evaluator; a geometric meta‑basin.
**Example:** SOB identifies clause boundaries and structural markers, producing the initial residue fragment for refinement.
**Normative home:** 20.40.010.

## **SROB (Structural Refinement OB) — 20.40.020**
**Purpose:** Refines SOB structural residue into normalized, canonicalized forms suitable for constraint extraction and routing.
**Focus:** Structural normalization, refinement of anchors, canonical ordering, residue smoothing, and refinement‑level metadata.
**When:** Invoked after SOB when structural refinement or normalization is required for downstream OB layers.
**Why:** Ensures structural residue is stable, canonical, and refinement‑consistent across TP variants and noisy inputs.
**Is not:** A constraint extractor; a semantic interpreter; a truth evaluator; a routing arbiter.
**Example:** SROB refines SOB’s structural cues into canonicalized residue fragments with stable ordering.
**Normative home:** 20.40.020.

## **CnOB (Constraint OB) — 20.40.030**
**Purpose:** Extracts constraint‑level residue and metadata from refined structure, enabling routing, ΔH% attribution, and downstream interpretation.
**Focus:** Constraint cues, missing‑slot signals, underspecification markers, conflict indicators, and constraint‑level residue hashing.
**When:** Invoked after SROB when constraint extraction or constraint metadata is required for routing or ΔH% accounting.
**Why:** Provides deterministic constraint residue enabling routing correctness, conflict detection, and missing‑mass attribution.
**Is not:** A semantic interpreter; a structural normalizer; a truth evaluator; a generative mechanism.
**Example:** CnOB extracts constraint markers and missing‑slot cues, producing constraint‑level residue for routing.
**Normative home:** 20.40.030.

## **SmOB (Semantic OB) — 20.40.040**
**Purpose:** Performs two jobs: (1) extracts pre‑semantic residue and semantic‑adjacent cues from SOB→SROB→CnOB output, and (2) compresses all upstream residue plus SmOB cues into a deterministic pre‑semantic residue hash and TR‑input cue vector.
**Focus:** (Job 1) semantic‑adjacent pattern activation, modality cues, affect markers, conflict‑adjacent and underspecification‑adjacent signals; (Job 2) deterministic pre‑semantic residue hashing and TR‑input cue formation for routing.
**When:** Invoked after CnOB when semantic‑adjacent cues, pre‑semantic residue, or deterministic routing representation are required for SSG or downstream interpretation.
**Why:** Job 1 adds pre‑semantic cues into the TP to support identity OB selection, ΔH% attribution, and semantic‑layer preparation; Job 2 provides a canonical, replay‑safe compressed representation enabling deterministic TR routing and SSG signal generation.
**Is not:** A semantic interpreter; a truth evaluator; a stance assigner; a geometric meta‑basin; a semantic normalizer.
**Example:** SmOB extracts semantic‑adjacent cues (Job 1) and then compresses upstream residue plus its own cues into a deterministic hash and TR‑input cue vector (Job 2) consumed by SSG and the Thought Router to derive TP.TR.
**Normative home:** 20.40.040.

## **SSG (Structural Signature Generator) — 20.47**
**Purpose:** Converts SmOB structural output into a deterministic, fixed‑length structural signature vector for routing and similarity operations.
**Focus:** Extraction and normalization of **structural invariants** (arc patterns, residue entropy, curvature, binding depth, motif frequencies) into a coordinate‑stable vector representation.
**When:** Mandatory stage `structural_signature_generation`; ordering **SmOB → SSG → RB**.
**Why:** Provide RB with a **geometry‑ready**, token‑free, replay‑stable coordinate chart enabling structural proximity, lane selection, and routing decisions.
**Is not:** Semantic embedding; tokenization; meaning construction; interpretation; hashing; candidate generation.
**Example:** SmOB graph with high branching depth and low curvature yields a signature emphasizing depth‑dominant structural geometry.
**Normative home:** 20.47.

### **RBU‑prm (Routing Buffer Update Primitive)**  
**Purpose:** Enrich the TP with subculture, identity, register, and interpretive metadata required for RB‑prm to perform correct routing.  
**Focus:** Deterministically writes interpretive metadata (culture, subculture, register, stance‑relevant cues) into the TP snapshot before routing occurs.  
**When:** Invoked **before RB‑prm**, ensuring RB‑prm receives a fully enriched TP.  
**Why:** Maintain architectural purity by separating interpretive metadata enrichment (RBU‑prm) from routing computation (RB‑prm).  
**Is not:** A router, classifier, scorer, or semantic evaluator. RBU‑prm does **not** compute routing deltas; it only prepares the TP so RB‑prm can compute routing correctly.  
**Example:** RBU‑prm writes subculture and identity metadata into the TP. RB‑prm then uses this metadata to select the correct manifold chart and routing lane.  
**Normative home:** 20.51.

# **RTU‑prm (Routing TP Update Primitive) — 20.30.005 (Corrected Patch)**
**Purpose:** RTU‑prm commits the routing metadata produced by RB‑prm into the TP snapshot.  
This includes **culture lane**, **subculture lane**, **fallback lane**, **routing lineage**, **routing reasons**, **fan‑out decisions**, and all other routing‑relevant structural fields. Its role is to provide TS, TR, and downstream primitives with a **stable, authoritative, deterministic routing state** for the next cycle. RTU‑prm **does not choose** culture or subculture — those decisions are made by RB‑prm — but RTU‑prm **is responsible for writing** the chosen culture/subculture lanes into the TP.
**Focus:** Pure, deterministic write‑back of RB‑prm’s routing metadata, validation of the routing envelope, ensuring RB‑prm remains pure and side‑effect‑free, embedding routing state into the TP for TS/TR scheduling and staleness evaluation  
**When:** Invoked immediately after RB‑prm and before TS schedules the next OB‑chain.  
Runs once per routing cycle and is never re‑invoked for the same RB output.
**Why:** Maintain architectural purity by separating **routing computation** (RB‑prm) from **routing commit** (RTU‑prm), provide TS/TR with a deterministic, auditable routing state, ensure replay equivalence and stable multi‑cycle behavior  
**Is no:t**  A router, a classifier, an interpreter, a scorer, a semantic evaluator, a modifier of OB outputs, semantic fields, truth fields, merge results, or completion data 
**Example:**  RB‑prm selects a cultural lane and fallback lane.  
RTU‑prm validates the routing envelope and **writes the culture lane, subculture lane, routing lineage, and lane‑selection fields** into the TP snapshot.  
TS then uses this committed routing state to schedule the next OB‑chain and determine TR execution.
**Normative home:** 20.30.005

## RB (Relational Basin) — 20.50
**Purpose:** Performs deterministic routing arbitration in Path‑A, selecting the next OB based on structural residue, ΔH%, lineage, and TR‑input fields, without accessing any Path‑B structures.  
**Focus:** Deterministic evaluation of routing metadata and relational cues to choose the next OB in the meaning‑construction cycle; RB does not move the TP but selects the next basin for OBA‑prm execution.  
**When:** Invoked during Path‑A routing after OB and TR evaluation; runs until Truth/Done stabilizes the turn‑final TP.  
**Why:** Provides governed, replay‑safe routing decisions that maintain A‑side determinism and enforce the A/B separation required by 20.705.  
**Is not:** SRP; TrigRB; TR; a geometric projector; a transport mechanism; a Path‑B computation; a reader of B‑side routing tables or MTP.  
**Example:** RB evaluates residue and ΔH% changes, determines that structural cues require re‑entering CnOB, and selects CnOB as the next basin for OBA‑prm execution.  
**Normative home:** 20.50.

## TR (Thought Router) — 20.37
**Purpose:** Produces the deterministic routing vector for Path‑A by consuming OB and DCB signals; TR influences but does not select RB’s next basin.  
**Focus:** Deterministic computation of TP.TR routing metadata; TR does not interpret, merge, or modify meaning.  
**When:** Path‑A, after OB/DCB evaluation and before RB arbitration.  
**Why:** Provide a stable, auditable routing vector that guides RB using curvature (DCB), structural evidence (OB), and trajectory signals.  
**Is not:** Semantic interpreter; TP writer; candidate generator; CE/CEx participant; realization component.  
**Example:** TR receives DCB curvature events and OB residue, then outputs TP.TR for RB’s next routing decision.  
**Normative home:** 20.37.

## **IdOB (Identity Object Basin) — 20.40.050**
**Purpose:** Performs identity‑conditioned interpretation of the routed TP, applying identity‑specific meaning rules, transformations, and basin‑local semantics after RB and TR have selected the appropriate identity pathway.
**Focus:** Consumes the post‑routing TP view, interprets identity‑relevant structures, resolves identity‑conditioned meaning, and emits updates through TPU.idob_update without producing residue, ΔH%, or TR‑input.
**When:** Invoked in Path A after SSG, RB, and RTU have produced a stable routing decision; may run multiple times in the RB→RTU→IdOB cycle until identity‑conditioned meaning stabilizes.
**Why:** Provides deterministic, replay‑safe identity‑specific interpretation that cannot be performed by OB, RB, TB, or DCB; isolates identity semantics from structural, routing, and truth‑evaluation responsibilities.
**Is not:** An OB primitive; a structural classifier; a constraint extractor; a routing arbiter; a truth evaluator; a ΔH% contributor; a Path B computation; a writer of TP.TR or routing_metadata.
**Example:** After RB routes a TP to a domain‑specific identity basin (e.g., mathematical identity, narrative identity, operator identity), IdOB applies identity‑conditioned interpretation rules and updates the TP via TPU.idob_update to reflect identity‑specific meaning.
**Normative home:** 20.40.050 (Identity OB Primitive Requirements).

## CTP‑prm (Collect/Consolidate Thought Point) — 20.145_prm
**Purpose:** Collects all OB‑outputs from an OB‑set into a single stable OB‑output packet for RB arbitration.  
**Focus:** Deterministic consolidation of OB‑outputs between OB‑sets; does not write or modify TP (TPU is sole writer).  
**When:** After an OB‑set completes and before RB arbitration; in multi‑core systems runs after all parallel OBs finish.  
**Why:** Ensures all legitimate OB‑outputs are available as one replay‑safe packet for routing in both serial and parallel execution.  
**Is not:** Meaning constructor; merge engine; scorer; TP writer; governance step.  
**Example:** Single‑core: InB→OB0→RB→OB1…OBn→CTP→RB; Multi‑core: InB→OB0→RB→{OB1∥OB2…∥OBn}→CTP→RB.

# **OuBA (Output Basin — Path A Commit) — 20.40.060 (Corrected)**  
**Purpose:** Serves as the authoritative commit point for Path A, producing the finalized, immutable semantic snapshot (`semantic_core`, object‑semantic fields, lineage, ΔH%) that becomes the sole input to D‑Flow (IB → TB → GBIB → GB) and the basis for all governance‑side evaluation.  
**Focus:** Freezes the Path‑A‑constructed meaning state into a committed TP snapshot; writes commit‑time metadata, resolution flags, and readiness‑for‑DF indicators without performing semantic correction, truth evaluation, or governance decisions.  
**When:** Invoked once per Path‑A cycle after meaning construction is complete; runs immediately before D‑Flow intake and never during Path B realization or governance evaluation.  
**Why:** Provide a deterministic, auditable, replay‑stable termination point for Path A that isolates meaning construction from governance evaluation; ensure that DF operates only on committed, immutable meaning and never on in‑flight Path‑A structures.  
**Is not:** A governance primitive; a truth evaluator; a semantic repair engine; a routing arbiter; a generator of inquiry or truth states; a producer of governance directives; OuBA never modifies semantic_core after commit and never invokes IB, TB, GBIB, or GB.  
**Example:** After Path A completes meaning construction for a turn, OuBA freezes the semantic_core and associated metadata into a committed TP snapshot, which DF then consumes beginning with IB for inquiry‑side evaluation.  
**Normative home:** 20.40.060 (Path A Output Basin Requirements), 20.705 (DF ingress), 20.90 (IB), 20.60 (TB), 20.80 (GB).

# **TPTB (TP Truth Basin Tags) — 20.64 (Finalized)**
**Purpose:** Encodes the truth‑evaluation results produced by TB over the **frozen Path A TP snapshot** into a compact, auditable metadata structure (`tp.truth_tags`) that Path B reads at intake. This enables truth‑aware behavior in Path B without allowing Path B to perform truth evaluation, preserving strict A/B separation.
**Focus:** Deterministic, read‑only truth metadata: factual alignment, contradiction detection, evidential basis, stance coherence, referential consistency, and explanation codes.  
TPTB serializes TB’s `truth_hypotheses{}` into stable tags attached to the **A→B TP semantic snapshot**.
**When:** Produced **after OuBA freezes the TP snapshot** and **after TB interprets that snapshot**, during A‑cycle finalization.  
Delivered to Path B **before LI**, and available throughout REx, RPlan, and RPU.  
Never produced or modified during Path B.
**Why:** Allows Path B to express truth‑aware behavior (qualification, contradiction handling, corrective phrasing) without invoking TB, performing inference, or accessing global truth state. Ensures replay‑safe, non‑inferential truth behavior grounded in Path A’s authoritative interpretation.
**Is not:** A truth engine; a basin; a semantic interpreter; a scorer; a routing mechanism; a safety evaluator; a global truth model; or a Path B computation.  
TPTB never modifies TP and performs no evaluation itself.
**Example:** TB detects a factual contradiction in the TP snapshot.  
TPTB encodes `truth_conflict=true`, `conflict_type=contradiction`, and `basis=evidence_X`.  
Path B later reads these tags to generate a corrective or qualified response without performing truth evaluation.
**Normative home:** 20.64.

# **TPSF (TP Safety Flags) — 20.66 (Finalized)**
**Purpose:** Encodes the safety‑evaluation results produced by A‑side safety basins over the **frozen Path A TP snapshot** into a compact, auditable metadata structure (`tp.safety_flags`) that Path B reads at intake. This enables safety‑aware behavior in Path B without allowing Path B to perform safety evaluation. **Focus:** Deterministic, read‑only safety metadata: risk presence, risk category, severity, rationale codes, and policy hooks. TPSF serializes the safety basins’ `safety_assessment{}` into stable flags attached to the **A→B TP semantic snapshot**, co‑located with `tp.truth_tags`.
**When:** Produced **after OuBA freezes the TP snapshot** and **after A‑side safety evaluation**, during A‑cycle finalization. Delivered to Path B **before LI**, and available throughout REx, RPlan, and RPU.  
Never produced or modified during Path B.
**Why:** Allows Path B to express safety‑aware behavior (refusal, redirection, qualification, de‑escalation) without invoking safety basins, performing inference, or accessing global safety state. Ensures replay‑safe, non‑inferential safety behavior grounded in Path A’s authoritative safety evaluation.
**Is not:** A safety engine; a basin; a semantic interpreter; a scorer; a routing mechanism; a truth evaluator; a global safety model; or a Path B computation.  
TPSF never modifies TP and performs no evaluation itself.
**Example:** A‑side safety basins detect self‑harm risk in the TP snapshot.  
TPSF encodes `safety_risk=true`, `risk_type=self_harm`, `severity=high`, and a rationale code.  
Path B later reads these flags to refuse or redirect the request without performing safety evaluation.
**Normative home:** 20.66.

## **CoHI (Conversation History Integrator) — 20.113 (Revised, dual‑input)**  
**Purpose:** Imports **conversation‑level structural continuity and historical inference** from the COB/CIL loop into the **frozen Path A TP snapshot** so that Path B primitives operate on a TP enriched with both cross‑turn structure and turn‑local truth/safety metadata (TPTB, TPSF). CoHI merges conversation objects, referential chains, topic threads, continuity markers, and selected CIL outputs into stable `tp.continuity_fields` consumed by LI and downstream Path B primitives.  
**Focus:** Deterministic, read‑only integration over two inputs: (1) the A→B TP (including `tp.truth_tags` (TPTB) and `tp.safety_flags` (TPSF)) and (2) COB/CIL structures (structural_history, referential_history, conversation_objects, topic_threads, continuity_markers, and continuity‑relevant inference). CoHI performs no new inference; it only normalizes and projects these into a per‑turn continuity substrate attached to the TP.  
**When:** Runs at the **start of Path B**, after the A→B handoff TP (with TPTB/TPSF) is available and after the COB/CIL loop has been updated for the prior turn; executes once per turn, before LI, ensuring LI receives a continuity‑augmented TP. Never runs during Path A and never mutates COB or CIL state.  
**Why:** Enables LI, REx, RPlan, and RPU to operate on a TP that reflects both turn‑local truth/safety metadata and conversation‑level structure, ensuring referential stability, topic continuity, and coherent multi‑turn realization without forcing Path B primitives to read COB/CIL directly or perform memory operations.  
**Is not:** A memory system; a planner; an inference engine; a scorer; a router; a semantic interpreter; or a continuity reasoner. CoHI does not modify COB or CIL, does not perform global inference, and does not generate meaning.  
**Example:** COB/CIL maintain a conversation object for “the dataset we discussed earlier” plus continuity inference that it remains active; the A→B TP carries `truth_tags{ factual_conflict=false }` and `safety_flags{ safe=true }`. CoHI merges these into `tp.continuity_fields`, allowing LI to interpret “run it again” as referring to that dataset while respecting truth and safety metadata.  
**Normative home:** 20.113.

# **LI (Local Inference Primitive) — 20.112 (Revised Final)**  
**Purpose:** Begins **Path B** by applying the TS‑level concept **MLI** to the TP snapshot (including TPTB, TPSF, and CoHI‑produced continuity fields), committing the first layer of meaning before any global inference, scoring, routing, or B‑side planning occurs.  
**Focus:** Reads representation‑layer fields, A‑side metadata (`tp.truth_tags`, `tp.safety_flags`), and **continuity_fields** injected by CoHI (structural_history, referential_history, conversation_objects, topic_threads, continuity_markers). Invokes **MLI‑prc** to resolve local meaning. Writes meaning‑layer fields (`tp.meaning`, `tp.mli_status`, `tp.mli_confidence`, `tp.mli_conflict`, `tp.mli_reason_code`, `tp.mli_revision_cycles`) into the TP.  
**When:** Runs **after CoHI** has integrated conversation‑level continuity into the TP snapshot and **before** any Path B global inference (REx, RPlan, RPU). Executes once per turn at the start of Path B inference.  
**Why:** Ensures deterministic, auditable, continuity‑aware local meaning commitment so all downstream Path B primitives operate on a stable semantic substrate enriched with cross‑turn structure. Prevents semantic drift and unstable global inference by forcing meaning resolution before any higher‑order reasoning.  
**Is not:** A global inference engine; a scorer; a router; a semantic_core builder; a B‑side planner; or MLI itself. Does not read from MTP or generate XP, and does not access COB directly.  
**Example:** Given an ambiguous utterance (“Can you check that for me”), LI reads the TP’s representation fields, A‑side metadata, and CoHI‑imported continuity (e.g., a conversation object representing “the dataset we discussed earlier”), applies MLI‑prc to classify the utterance as a *request*, and writes the resolved meaning and confidence into the TP for downstream primitives.  
**Normative home:** 20.112.

## REx (Realization Extractor) — Path B
**Purpose:** Extracts the realization‑relevant substrate from the finalized TP (read‑only) for downstream planning; does not read or modify MTP.  
**Focus:** Deterministic extraction of clause‑level structure, dependencies, discourse roles, referential anchors, and realization‑relevant constraints; no semantic interpretation or TP writes.  
**When:** First primitive in Path‑B: TP → REx → RPlan.  
**Is not:** Semantic interpreter; TP writer; meaning constructor; truth/safety evaluator.

## RPlan (Realization Plan Construction) — Path B
**Purpose:** Constructs candidate realization plans from REx output, specifying structure, pacing, tone, channel, and realization constraints.  
**Focus:** Plan construction only; no meaning modification, no semantic inference, no TP writes.  
**When:** After REx, before RPU.  
**Is not:** Merge engine; TP writer; meaning constructor; truth/safety evaluator.

**Purpose:** Constructs meaning deterministically from raw input, producing the authoritative TP for the turn.

**Is not:** A realization pipeline; a truth evaluator; a safety engine; a generator of surface text; a writer of MTP.

**Is not:** A meaning writer; a semantic interpreter; a truth evaluator; a safety engine; a generator of new meaning; a contributor to MTP.

**Why:** Prevent automatic inquiry escalation; require supervisory gate before IB creation.
**Is not:** IB state; automatic inquiry; IMR trigger.
**Normative home:** 20.17, 20.30.

## mtp_update — Removed (Obsolete Mechanism)

**Focus:** None. No Path‑A or Path‑B primitive writes to MTP, and no semantic snapshot is committed mid‑turn.  
**When:** Never invoked. Replaced by HC‑Flow’s once‑per‑turn archival snapshot of the finalized TP(N).  
**Why:** The architecture now enforces a strict separation: Path A and Path B construct meaning and realization, while HC‑Flow alone produces the immutable historical MTP snapshot. This eliminates mid‑turn commits, semantic_core dependencies, and RBU‑based updates.  
**Is not:** A Path‑A commit; a Path‑B commit; a semantic snapshot writer; an RBU operation; a truth evaluator; a routing step; a partial update.  
**Example:** (Removed) Any prior examples involving RBU validating update_structure and writing semantic snapshots into MTP are obsolete.  
**Normative home:** 20.115 (MTP), 20.705 (HC‑Flow).

# **4. Governance Rules**

## **Clarification Rules — Governance Block**  
**Purpose:** Determines when the system may issue a clarification request instead of producing a direct answer, ensuring ambiguity is resolved only when permitted by governance policy.  
**Focus:** Clarification allowed only when ambiguity is material, user‑intent cannot be safely inferred, and governance permits inquiry; suppressed when meaning is sufficiently determinate or when clarification would violate USP or safety constraints.  
**When:** Evaluated during TB→IB→GBIB→GB after Path B realization and before any clarification is emitted.  
**Why:** Prevents unnecessary or unsafe clarifications and ensures all clarifications are governance‑authorized.  
**Is not:** A semantic primitive; a meaning writer; an IMR mechanism; an automatic IB trigger.  
**Example:** IB proposes `ask_for_antecedent`; GBIB validates under USP; GB authorizes or suppresses the clarification.  
**Normative home:** 20.80.

---

## **Suppression Rules — Governance Block**  
**Purpose:** Enforces conditions under which clarification, interrogation, or inference proposals must be suppressed to maintain safety, truth integrity, and user‑intent fidelity.  
**Focus:** Suppression triggered when proposals violate USP, conflict with truth/safety tags, exceed allowed inquiry depth, or would cause user‑intent distortion.  
**When:** Applied in GBIB and finalized in GB during governance evaluation.  
**Why:** Ensures the system does not escalate inquiry or inference beyond what governance permits.  
**Is not:** A routing rule; a Path A/B primitive; an IMR mismatch classification.  
**Example:** IB proposes a follow‑up question; GBIB suppresses it because USP forbids interrogative expansion in the current context.  
**Normative home:** 20.80.

---

## **Truth–Safety Precedence Rules — Governance Block**  
**Purpose:** Establishes deterministic precedence between truth‑evaluation outcomes and safety‑evaluation outcomes when they conflict.  
**Focus:** Safety overrides truth when user harm or policy violation is possible; truth overrides ambiguity when meaning is determinate and safe; both feed into GB for final governance outcome.  
**When:** Evaluated in GBIB and GB after TB and TPSF/TPTB signals are available.  
**Why:** Ensures safe, truthful, policy‑aligned behavior under conflict conditions.  
**Is not:** A semantic inference rule; a TP writer; a Path A/B primitive.  
**Example:** A truthful answer is available but unsafe; safety precedence suppresses direct expression and GB authorizes a safer alternative.  
**Normative home:** 20.80.

---

## **USP Precedence Rules — Governance Block**  
**Purpose:** Ensures that User‑Specified Preferences (USP) constrain governance decisions without overriding safety or truth requirements.  
**Focus:** USP applied after safety and truth evaluation but before final governance outcome; USP may suppress or permit clarifications, tone, or style choices.  
**When:** Applied in GBIB and finalized in GB.  
**Why:** Ensures user preferences shape expression while remaining subordinate to safety and truth.  
**Is not:** A safety override; a truth override; a meaning‑layer inference.  
**Example:** User prefers no clarifications; USP suppresses IB proposals unless safety requires them.  
**Normative home:** 20.80.

---

## **Governance Outcome Rules — Governance Block**  
**Purpose:** Defines how GB produces the final `governance_outcome{}` that controls whether the system answers, clarifies, suppresses, or redirects.  
**Focus:** GB integrates TB truth‑state, IB ambiguity proposals, GBIB governance filters, USP, TPTB, TPSF, and safety constraints to produce a single deterministic outcome.  
**When:** Final step of the Post‑TS governance chain before output is emitted.  
**Why:** Ensures all outputs are policy‑aligned, safe, truthful, and consistent with user intent.  
**Is not:** A meaning writer; a realization primitive; a neural inference.  
**Example:** GB authorizes `issue_clarification`, `answer_directly`, or `suppress_and_redirect` based on combined governance signals.  
**Normative home:** 20.80.

---

## **Replay‑Determinism Rules — Governance Block**  
**Purpose:** Ensures that all governance decisions are deterministic and replay‑safe given identical inputs, meaning states, and seeds.  
**Focus:** Governance outcomes must be identical across replays; nondeterminism confined to B‑side expression selection under Random Seed Boundary.  
**When:** Applied across TB→IB→GBIB→GB and enforced before output emission.  
**Why:** Guarantees auditability, reproducibility, and compliance with TS determinism requirements.  
**Is not:** A randomness generator; a meaning writer; a Path A/B primitive.  
**Example:** Replaying the same TP/MTP commit with the same seed yields identical governance outcomes and identical surface‑form output.  
**Normative home:** 20.80, 20.207.

# 5. TS-Level Concepts

---

## ΔH% (DeltaHPercent) — 20.30
**Purpose:** Represents the incremental structural‑uncertainty contribution produced by each Path A interpretive stage (OB, TB, merge, truth evaluation), ensuring uncertainty evolution is auditable and replay‑safe.
**Focus:** Encodes local uncertainty adjustments derived from structural gaps, unresolved branches, missing‑mass indicators, and interpretive signals; contributes to the deterministic computation of H%.
**When:** Generated during each Path A interpretive step and accumulated before truth/completion evaluation; included in the update structure committed by RBU.
**Why:** Provides a deterministic, non‑probabilistic mechanism for tracking uncertainty evolution across the reasoning cycle without latent‑space inference or stochastic estimation.
**Is not:** A probability; a confidence score; a truth commitment; an entropy functional; a Path B computation.
**Example:** Merge detects unresolved semantic branches and increases ΔH%; truth evaluation stabilizes a hypothesis and decreases ΔH%, contributing to a lower H% in the next cycle.
**Normative home:** 20.30.030, 20.30.060.

---

## H% (UncertaintyPercent) — 20.30
**Purpose:** Represents the accumulated structural‑uncertainty state of the TP/MTP after integrating ΔH% contributions across Path A interpretive stages.
**Focus:** Encodes the current uncertainty level derived from structural gaps, unresolved hypotheses, and interpretive signals; used by truth and completion evaluation to determine stability and readiness for commit.
**When:** Updated during Path A after merge and truth‑hypotheses evaluation; included in the update structure validated and committed by RBU.
**Why:** Provides a deterministic, replay‑safe uncertainty measure that separates structural uncertainty from truth evaluation, confidence, or probabilistic reasoning.
**Is not:** A probability; a confidence score; a truth band; a global uncertainty model; a Path B computation.
**Example:** If ΔH% accumulates due to unresolved semantic branches, H% increases; if truth evaluation stabilizes hypotheses, H% decreases, signaling readiness for completion.
**Normative home:** 20.30.060, 20.30.070.

---

## OB (Object Basin) — 20.40
**Purpose:** Defines the generic class of Path‑A object‑basin primitives (SOB, SROB, CnOB, SmOB, IdOB) that classify structure, extract constraints, and emit residue and TR‑input cues for routing.  
**Focus:** Encodes structural, constraint, and pattern signatures from lane‑local TP views; produces residue fragments, ΔH% contributions, and TR‑input fields without performing semantic interpretation or truth evaluation.  
**When:** Invoked during Path‑A meaning construction prior to routing; activated deterministically based on lane‑local TP structure, routing context, and orthogonality_signature; contributes evidence and residue before TR and RB execution.  
**Why:** Provides deterministic, replay‑safe structural interpretation that grounds routing, ΔH% evolution, and downstream meaning construction without semantic inference or identity‑conditioned processing.  
**Is not:** A semantic basin; a truth evaluator; a routing arbiter; a geometric meta‑basin; an identity‑conditioned primitive; a Path‑B computation; a generator of TP.TR or truth_hypotheses.  
**Example:** SOB/SROB/CnOB extract structural and constraint residue; SmOB emits pre‑semantic residue; OB sets `tr_needs_update` when structural cues change, enabling TR to recompute routing.  
**Normative home:** 20.40 (parent‑level OB requirements).

---

## TCU (Thought Compute Unit) — 20.30
**Purpose:** Normalizes compute cost reporting per primitive so that deterministic cost envelopes can be enforced and compared across the architecture.
**Focus:** Normalized compute-cost unit reported per tick / per primitive.
**When:** Reported per tick / per primitive.
**Why:** Deterministic cost envelopes; comparable cost reporting across primitives.
**Is not:** Wall-clock time; token count.
**Example:** OpBeh vs OuB cost recorded separately.
**Normative home:** 20.30.

---

## Messy-Input Taxonomy (MI_*) — 20.17
**Purpose:** Classifies all malformed or ambiguous input conditions so that routing, repair, and escalation decisions are made deterministically rather than ad hoc.
**Focus:** Structured classification of problematic input conditions with deterministic downstream routing implications.
**When:** Applied at InB / IIInB during input canonicalization.
**Why:** Prevent ad hoc handling of malformed input; ensure deterministic routing per class.
**Is not:** Semantic interpretation; truth evaluation; a repair mechanism.

| Class | Focus | Example |
|-------|-------|---------|
| `MI_CONTRA` | Mutually incompatible propositions | "It is safe" + "It is dangerous" |
| `MI_VAGUE` | Underspecified referents | "Make it better" |
| `MI_AFFECT` | Affect tagging | Tone marker only |
| `MI_INCOMP` | Commitment-blocked incompleteness | Missing slots → IB-Creation-Request |
| `MI_NOISE` | Surface noise | Typos / encoding glitches |
**Normative home:** 20.17.

## MCS (Meaningful Cognitive Step) — 20.30.040
**Purpose:** Defines the atomic, auditable unit of cognitive work in TS, enabling deterministic accounting of interpretive, structural, and evaluative operations across Path A.
**Focus:** Counts only meaningful, user‑relevant cognitive transformations (OB/TB interpretation, merge decisions, truth‑hypothesis evaluation, completion evaluation, routing decisions) while excluding zero‑cost metadata updates and mechanical bookkeeping.
**When:** Incremented during Path A whenever TS performs a qualifying interpretive or evaluative action; never incremented during Path B or for non‑cognitive operations.
**Why:** Ensures TS reasoning is measurable, bounded, replay‑safe, and free of hidden computation; provides a stable basis for invariants, performance guarantees, and correctness proofs.
**Is not:** A token count; a FLOP measure; a latency metric; a routing hop; a metadata write; a safety or truth tag; a Path B operation.
**Example:** OB interpretation that resolves a referent counts as an MCS; writing TPTB or TPSF does not; updating lane lineage does not; merge reconciliation of conflicting semantic cores does.
**Normative home:** 20.30.040.

---

## semantic_core — 20.30
**Purpose:** Represents the stable, lane‑local semantic content extracted during Path A interpretation and preserved across merge, truth evaluation, and commit.
**Focus:** Encodes meaning‑bearing structures (propositions, roles, referents, frames, relations) that form the substrate for merge, truth‑hypotheses evaluation, completion evaluation, and deterministic commit.
**When:** Produced during OB/TB interpretation, carried through merge and truth/completion evaluation, and committed to the MTP by RBU.
**Why:** Provides a deterministic, replay‑safe semantic substrate that isolates meaning construction from routing, safety, realization, and stylistic rendering.
**Is not:** A routing structure; a safety model; a truth‑metadata object; a latent embedding; a Path B construct; a stylistic or expressive representation.
**Example:** OB/TB extract propositions and referents into `semantic_core`; merge reconciles multiple lane‑local cores into a unified structure used for truth and completion evaluation.
**Normative home:** 20.30.010, 20.30.050.

---

## update_structure — 20.30
**Purpose:** Represents the deterministic, fully‑specified envelope of all Path A outputs (semantic_core, truth_hypotheses, TPTB, TPSF, ΔH%, H%, merge_result, routing metadata) that RBU validates and commits to the MTP.
**Focus:** Encodes the complete, replay‑safe state transition produced by a Path A cycle, including structural updates, metadata fields, and commit‑relevant deltas; ensures no implicit or hidden computation occurs during commit.
**When:** Constructed after merge, truth evaluation, completion evaluation, and uncertainty updates; passed to RBU as the authoritative input for commit.
**Why:** Provides a single, auditable, deterministic object that captures the entire semantic and structural evolution of the TP, enabling RBU to perform atomic commit without re‑running any computation.
**Is not:** A semantic object; a truth model; a routing decision; a latent representation; a Path B construct; a partial update; an incremental diff.
**Example:** After merge reconciles lane‑local semantic cores and truth evaluation produces TPTB, update_structure aggregates semantic_core, truth_hypotheses, TPTB, TPSF, ΔH%, H%, and merge_result into a single commit‑ready envelope.
**Normative home:** 20.30.070.

---

## merge_result — 20.30
**Purpose:** Represents the deterministic, lane‑reconciled semantic output produced by merge after integrating multiple lane‑local semantic_cores, truth hypotheses, and structural signals.
**Focus:** Encodes the unified semantic structure (propositions, roles, referents, frames, relations) plus merge‑level decisions (conflict resolution, branch selection, structural reconciliation) that feed truth and completion evaluation.
**When:** Produced after OB/TB interpretation and before truth/completion evaluation; included in update_structure and validated by RBU during commit.
**Why:** Provides a single, authoritative semantic representation for downstream evaluation, ensuring deterministic reasoning and preventing lane‑specific divergence from leaking into commit.
**Is not:** A truth‑metadata object; a routing decision; a latent embedding; a Path B construct; a stylistic or expressive representation.
**Example:** Multiple lane‑local semantic_cores propose different referent bindings; merge_result reconciles them into a single referent structure used by truth evaluation.
**Normative home:** 20.30.050.

---

## **TP.TR — semantic‑routing fields**  
**Purpose:** Structured semantic‑routing state used by TR‑prm, RB‑prm, and SSG for staleness evaluation, semantic‑transition eligibility, and routing‑vector construction.  
**Focus:** Tracks semantic‑adjacent routing metadata (stance, intent, affect, epistemic shading, tension, politeness, commitment, reservation, logical structure, semantic‑deltaH, lineage additions, routing semantics). Contains routing‑relevant semantics, not meaning.  
**When:** Updated only when `tr_needs_update = true` under the TR‑gating contract.  
**Why:** Maintain deterministic, auditable semantic‑routing behavior across cycles; ensure semantic transitions occur only under explicit architectural conditions.  
**Is not:** A meaning field, truth field, stance interpreter, classifier, or semantic evaluator; does not contain semantic content, only semantic‑routing metadata.  
**Example:** TR‑prm updates stance and commitment fields after a semantic‑routing change; RB‑prm reads the updated TP.TR to determine semantic‑transition eligibility.  
**Normative home:** 20.30 (TP Message Contract), 20.40.040 (SmOB), 20.47 (SSG), 20.50 (RB), 20.10 (TR‑gating).

---

## **DF — Inquiry‑side evaluation flow**  
**Purpose:** Governance‑side evaluation of committed meaning produced by OuBA, determining inquiry, truth, and governance outcomes for the turn.  
**Focus:** Processes committed semantic_core snapshots through IB, TB, and GBIB into GB for inquiry evaluation, truth assessment, supervisory integration, and promotion or governance‑side routing decisions.  
**When:** Invoked only after Path A commits meaning via OuBA; operates exclusively on committed, immutable meaning.  
**Why:** Maintain deterministic, auditable governance evaluation; ensure that inquiry, truth, and supervisory decisions occur only on committed meaning under explicit architectural conditions.  
**Is not:** A meaning‑construction flow, semantic‑writer, or Path A participant; does not modify semantic_core, truth‑relations, or any Path A structure.  
**Example:** OuBA commits meaning; IB evaluates inquiry structure; TB evaluates truth; GBIB integrates supervisory context; GB logs governance events and either promotes to IdOB or emits governance inference to REx.  
**Normative home:** 20.705 (TS Flow Diagrams), 20.90 (IB), 20.80 (GB), 20.40.060 (OuBA), 20.110 (OuBB).

# **HCF — Historical Conversation Flow (Corrected Final)**  
**Purpose:** Provide TS and Path B with long‑horizon conversational perspective by transforming turn‑final TP snapshots (committed by OuBB) into structured conversation‑level continuity and inference.  
**Focus:** Processes historical TP sequences through MTP, COB, and CIL to derive conversation objects, referential history, topic threads, and long‑range conversational inference. These outputs are consumed by CoHI and reinjected into Path B as continuity‑relevant structure.  
**When:** Invoked after Path B completes a turn and OuBB finalizes the turn‑final TP. Operates as a slow‑reader subsystem independent of real‑time turn execution, maintaining its own historical loop (MTP → COB → CIL) while exchanging information with Path B through CoHI.  
**Why:** Maintain deterministic, auditable long‑term conversational context; ensure continuity, referential stability, and multi‑turn inference are derived only from committed TP history; and provide Path B with structured, policy‑safe continuity without requiring Path B primitives to read or manipulate historical memory directly.  
**Is not:** A meaning‑construction flow, truth evaluator, or governance subsystem; does not modify TP, semantic_core, or Path A state; does not participate in real‑time realization.  
**Example:** OuBB commits a turn‑final TP; HCF ingests it and updates MTP; COB constructs or updates conversation objects; CIL derives long‑horizon inference; CoHI merges these historical structures with the next turn’s Path B TP to provide continuity‑aware realization.  
**Normative home:** 20.705 (TS Flow Diagrams), 20.190 (Glossary), 20.110 (OuBB), 20.113 (CoHI), 20.112 (COB), 20.114 (CIL).
