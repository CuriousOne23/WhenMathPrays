# 20.50_Observability Requirements

## 1. Purpose

This document defines the **observability, logging, tracing, snapshotting, and introspection requirements** for the **Thought Simulator (TS)**.

It ensures every aspect of a simulation run is transparent, traceable, and reproducible for the external Observer (human researcher or automated analysis tools), while maintaining full determinism, low performance overhead, and strict conceptual boundaries.

## 2. Core Observability Principles

* Observability is a **first-class structural pillar**, not an afterthought.
* The Observer remains **strictly external** â€” observability tools provide visibility without influencing simulation mechanics.
* All simulator state and events must be **externally observable** without modifying core behavior.
* Logging, tracing, and snapshots must be **fully configurable** and must never alter determinism.
* Geometry / Manifold projections are **pure observer tools** â€” never part of core TS state.
* All outputs must support **replay, post-analysis, and deterministic re-execution** from any point.

## 3. Logging Requirements

**O-LOG-01: Structured Logging**  
All events logged in structured, machine-readable format (JSON Lines preferred) with these mandatory fields:
- `tick`: Current simulation tick
- `tp_id`: ThoughtPoint identifier(s)
- `event_type`: (e.g., `basin_transition`, `regulator_activation`, `entropy_update`, `error`, `warning`)
- `state_counter`: Strictly monotonic global state counter
- `details`: Context-specific payload
- `timestamp`: Wall-clock time (observability only)

**O-LOG-02: Log Levels**
- `minimal`: Critical errors + final summary only
- `standard` (default): Errors, warnings, major transitions, regulator actions, periodic summaries
- `debug-max`: Every micro-event, full TP state deltas, memory stats

**O-LOG-03: Log Management**  
Support log rotation and optional compression for long-duration runs.

## 4. State Counter Requirements

**O-STATE-01: Strictly Monotonic State Counter**  
- A global state counter **must** be strictly monotonic.
- It **must** increment on every state-changing event (TP movement, entropy update, basin transition, regulator action, etc.).
- This counter is used for determinism verification, replay validation, and debugging.

## 5. Snapshotting Requirements

**O-SNAP-01: Full and Incremental Snapshots**  
- Support full state snapshots at configurable intervals or on demand.
- Support **incremental/differential** snapshots for performance (see 20.40_performance_requirements.md).

**O-SNAP-02: Snapshot Content**
- Schema version identifier
- Complete list of active ThoughtPoints with:
  - Current basin / position
  - Entropy components (\( H_{rep} \), \( H_{pred} \), \( H_{struct} \))
  - Provenance / lineage records sufficient to reconstruct creation, split, and merge history
  - History buffer (configurable depth)
  - Tagged state counter
- Global metrics (total entropy, regulator stats, active TP count)
- Random seed and full configuration used

**O-SNAP-03: Snapshot Usability**
- Snapshots must be loadable to resume simulation exactly (bitwise determinism).
- Human-readable summary export option (Markdown / HTML).

## 6. Real-Time Introspection & Metrics

**O-MET-01: Live Metrics**  
Expose key runtime metrics via API or console:
- Active TP count
- Current total / per-TP entropy
- Regulator activation frequency
- TPS and tick duration statistics
- Memory usage breakdown

**O-MET-02: Observer Probes**  
- Probes must be **strictly read-only**.
- They must **never** modify internal state, scheduling, entropy, or behavior.

**O-MET-03: Stability Reports**  
On-demand generation of stability/health reports (cross-reference 20.20_error_and_stability_requirements.md).

## 7. Time Discipline

**O-TIME-01: Observer Time vs Simulation Time**  
- Wall-clock timestamps are for observability and performance analysis only.
- Wall-clock time **must never** influence simulation time, scheduling, entropy calculations, or any behavior.

## 8. Visualization & Projection Support

**O-VIS-01: Decoupled Manifold Projection**  
The TS core must export raw trajectory, basin, and entropy data consumable by the relational manifold layer for:
- 2D/3D geometric visualization
- Entropy gradient fields
- Thought trajectory paths
- Basin attraction maps

**O-VIS-02: Export Formats**  
Support common formats (CSV, JSON, Parquet, GraphML) for external tools.

## 9. Determinism Verification

**O-DET-01: Self-Verification**  
- Built-in mechanism to verify that replay from any snapshot produces identical state counters and final results.
- Automatic checksum / hash validation on key internal structures.

**O-DET-02: Reproducibility Guarantee**  
Any simulation (same seed + config + starting snapshot) must be fully reproducible, including all log sequences.

## 10. Performance Impact Control

* Observability overhead must be **measurable and configurable** (see 20.40_performance_requirements.md).
* Standard mode overhead target: â‰¤ 8% of total runtime.
* Debug-max mode may consume more resources but must remain usable for short runs.

## 11. Invariants (Non-Negotiable)

* No observability feature may alter simulation outcomes.
* Observer probes and tools must remain strictly read-only.
* All logged or snapshotted data must support reconstruction of Observer-evaluable meaning (coherence, beauty, value).
* Geometry layer has zero influence on core TS state or behavior.
* State counter monotonicity and time discipline must be enforced.

## 12. Success Criteria

* A researcher can stop a long-running simulation, inspect its internal state via snapshot + logs, understand *why* specific ThoughtPoints behaved as they did, and resume or branch the experiment with full confidence and bitwise reproducibility.
* All stability events, entropy transitions, and regulator actions are traceable via monotonic state counters.
* Snapshots are versioned and compatible across TS releases.
* External tools can consume TS outputs for advanced analysis and visualization without custom parsing.
