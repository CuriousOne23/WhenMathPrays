# 📄 **20.206 Pipeline A↔B Synchronization Contract**  
**Document ID:** 20.206  
**Version:** 0.3 (Strengthened Rewrite)  
**Date:** 2026‑06‑17  
**Status:** Approved — Modernized, Strengthened, Reviewer‑Ready  
**Authority:** This module owns the normative A↔B boundary, freeze semantics, commit_id authority, B read/write sets, determinism boundary, equivalence classes, and B→A return‑path limits.

---

# **0. Purpose**

This module defines the **synchronization contract** between **Pipeline A (meaning construction)** and **Pipeline B (realization)**. It establishes:

- when meaning is frozen  
- how `commit_id` identifies the authoritative semantic snapshot  
- what Pipeline B may read  
- what Pipeline B may write  
- what Pipeline B is forbidden from accessing  
- determinism and replay boundaries  
- equivalence classes (E1/E2/E3)  
- IMR return‑path limits  

This module SHALL govern all A↔B interactions and SHALL NOT be weakened by any sibling module.

---

# **1. Cycle Topology and Phase Ordering**

Pipeline A constructs meaning.  
Pipeline B realizes meaning.  
The boundary between them is **`mtp_update` → commit_id → freeze**.

### **Requirements**

**HLR‑20.206‑001**  
Pipeline A SHALL complete meaning construction, including Merge, Truth/Done, and all semantic updates, before emitting `mtp_update`.

**HLR‑20.206‑002**  
Every `mtp_update` SHALL emit exactly one `commit_id` that uniquely identifies the frozen `semantic_core` snapshot for that cycle.

**HLR‑20.206‑003**  
Pipeline B SHALL NOT begin realization for a cycle until a valid `commit_id` and frozen `semantic_snapshot_ref` are available.

**HLR‑20.206‑004**  
Pipeline B SHALL execute at most one primary realization pass per (`commit_id`, `cycle_id`), except when an IMR Type A retry authorizes a same‑snapshot re‑run using the same XP record.

**HLR‑20.206‑005**  
Pipeline B SHALL NOT use lane parallelism, TP instances, or lane‑local provenance as structural inputs.

---

# **2. Freeze Contract**

After `mtp_update`, the `semantic_core` snapshot is **frozen** for the referenced `commit_id`.

### **Requirements**

**HLR‑20.206‑006**  
For a given `commit_id`, Pipeline B SHALL treat the referenced `semantic_core` snapshot as read‑only for the duration of the B pass.

**HLR‑20.206‑007**  
Pipeline B SHALL NOT modify, patch, smooth, reinterpret, or retroactively revise any field in the frozen snapshot.

**HLR‑20.206‑008**  
Pipeline A SHALL NOT emit a second `mtp_update` for the same cycle after Pipeline B has begun realization for that cycle’s `commit_id`.

**HLR‑20.206‑009**  
Any attempt to start Pipeline B without a resolvable post‑commit `semantic_snapshot_ref` SHALL fail deterministically with reason code `B_START_WITHOUT_COMMIT`.

# **3. Structural Integrity — Checksum Requirement**

To guarantee that the frozen meaning snapshot is received by Pipeline B exactly as emitted by Pipeline A, the A→B payload SHALL include a `checksum` field that attests to the structural integrity of the handoff.

### Requirements

**HLR‑20.206‑033**  
Pipeline A SHALL compute a deterministic checksum over the fully frozen A→B payload body, excluding the `checksum` field itself, at the moment freeze semantics take effect.

**HLR‑20.206‑0034**  
The checksum algorithm SHALL be stable, deterministic, and SHALL produce identical output for identical frozen payloads across all replays.

**HLR‑20.206‑035**  
Pipeline B SHALL recompute the checksum upon receipt of the payload and SHALL compare it to the transmitted value before performing any semantic, behavioral, or realization operation.

**HLR‑20.206‑036**  
If the checksum comparison fails, Pipeline B SHALL treat the payload as structurally invalid, SHALL NOT attempt semantic recovery or best‑effort interpretation, and SHALL surface a Structural Error in accordance with the A↔B error‑class taxonomy.

**HLR‑20.206‑037**  
No module outside this contract SHALL weaken, bypass, or override checksum validation. Any A→B payload lacking a checksum, or failing checksum verification, SHALL be considered invalid and SHALL NOT be acted upon by Pipeline B.

# **4. Schema Version Requirement**

To ensure forward‑compatible evolution of the A↔B interface, every A→B payload SHALL declare the schema version under which it was produced. Pipeline B SHALL validate this version before interpreting any field in the payload.

### Requirements

**HLR‑20.206‑038**  
Pipeline A SHALL include a `schema_version` field in every A→B payload. This field SHALL be a stable, semantic version identifier (e.g., `"2.0"`).

**HLR‑20.206‑039**  
Pipeline B SHALL read `schema_version` before consuming any other field and SHALL validate that the version is recognized and supported.

**HLR‑20.206‑040**  
If `schema_version` is missing, malformed, or unsupported, Pipeline B SHALL fail deterministically with error class **Structural Error** and SHALL NOT attempt semantic recovery or best‑effort interpretation.

**HLR‑20.206‑041**  
Schema versioning SHALL be monotonic: newer versions MAY add fields but SHALL NOT silently change the meaning of existing fields without incrementing the major version.

**HLR‑20.206‑042**  
No sibling module SHALL weaken or override schema‑version validation. Any A→B payload lacking a valid `schema_version` SHALL be considered non‑conformant with this contract.

# 5. Synthesis Mode Requirement

Pipeline B SHALL interpret the frozen meaning snapshot according to the synthesis mode declared by Pipeline A. The synthesis mode determines the realization strategy, permissible transformations, and the expected structure of B outputs.

### Requirements

**HLR‑20.206‑043**  
Pipeline A SHALL include a `synthesis_mode` field in every A→B payload. This field SHALL identify the realization strategy for the cycle (e.g., `"normal"`, `"continuation"`, `"repair"`, `"summary"`, `"rewrite"`).

**HLR‑20.206‑044**  
Pipeline B SHALL read `synthesis_mode` before performing any realization step and SHALL select the realization algorithm consistent with the declared mode.

**HLR‑20.206‑045**  
Pipeline B SHALL NOT infer, guess, or override `synthesis_mode`. If the field is missing or malformed, B SHALL fail deterministically with a Structural Error.

**HLR‑20.206‑046**  
`synthesis_mode` SHALL NOT alter the frozen meaning snapshot. It SHALL only determine how B realizes the meaning into `exec_plan` and `exec_trace`.

**HLR‑20.206‑047**  
IMR Type A retries SHALL preserve the original `synthesis_mode` for the associated `commit_id` and SHALL NOT introduce a new mode for the same snapshot.

**HLR‑20.206‑048**  
No sibling module SHALL weaken or override the synthesis‑mode contract. Any A→B payload lacking a valid `synthesis_mode` SHALL be considered non‑conformant with this contract.

# **6. Allowed and Forbidden Inputs to Pipeline B**

Pipeline B consumes only the frozen meaning envelope and approved metadata.

### **Allowed Inputs**

**HLR‑20.206‑010**  
Pipeline B MAY read the following fields from the frozen snapshot:  
- `propositions[]`, `stance`, `goals[]`, `delta_h`  
- `truth_hypotheses`, `done_state`  
- `messy_input_record` (read‑only)  
- `policy_signature`, `execution_signature`  
- `routing_epoch_id`  
- any field explicitly marked as part of the committed meaning envelope

### **Forbidden Inputs**

**HLR‑20.206‑011**  
Pipeline B SHALL NOT read:  
- TP instances or `tp_id`  
- `lane_id`  
- lane‑local provenance  
- routing metadata from RB  
- uncommitted merge drafts  
- DCB geometry  
- TR ephemeral state  
- any pre‑commit or pre‑merge structure

**HLR‑20.206‑012**  
Any B read referencing forbidden inputs SHALL fail with `FAIL_B_FORBIDDEN_TP_READ`.

# **7. Error‑Class Taxonomy**  
*(Fixes Issue 4)*

Pipeline B SHALL classify all A→B payload failures using a stable, contract‑level taxonomy.

### **Requirements**

**HLR‑20.206‑049**  
Pipeline B SHALL classify all A→B payload failures into one of the following error classes:  
- **Structural Error** — malformed, incomplete, corrupted, or fails structural validation.  
- **Version Error** — unsupported or invalid `schema_version`.  
- **Mode Error** — invalid or unrecognized `synthesis_mode`.  
- **Forbidden Input Error** — B attempted to read a forbidden field.  
- **Snapshot Error** — `semantic_snapshot_ref` cannot be resolved or mismatches `commit_id`.

**HLR‑20.206‑050**  
Structural Errors SHALL be fatal. Pipeline B SHALL NOT attempt semantic recovery or best‑effort interpretation.

**HLR‑20.206‑051**  
Version Errors SHALL be fatal. Pipeline B SHALL NOT attempt downgrade or fallback interpretation.

**HLR‑20.206‑052**  
Mode Errors SHALL be fatal. Pipeline B SHALL NOT infer or guess a `synthesis_mode`.

**HLR‑20.206‑053**  
Forbidden Input Errors SHALL be fatal and SHALL immediately terminate realization.

**HLR‑20.206‑054**  
No sibling module SHALL weaken or override this taxonomy.

# **9. Pipeline B Output Contract**

Pipeline B produces realization artifacts only.

### **Requirements**

**HLR‑20.206‑013**  
Pipeline B SHALL write only:  
- `exec_plan`  
- `exec_trace`  
- append‑only IMR supervisory triggers  

**HLR‑20.206‑014**  
Every `exec_plan` and `exec_trace` record SHALL carry `commit_id`, `cycle_id`, and `routing_epoch_id`.

**HLR‑20.206‑015**  
XP SHALL serve as a logical index over B artifacts and SHALL NOT introduce a new authoritative state envelope.

**HLR‑20.206‑016**  
Exactly one primary XP record SHALL exist per (`commit_id`, `cycle_id`). IMR Type A retries SHALL increment `xp_pass_seq` on the same record.

# **10. Determinism and Replay Boundary**

Pipeline B must be deterministic under fixed conditions.

### **Requirements**

**HLR‑20.206‑017**  
Given a fixed `semantic_snapshot_ref`, fixed `routing_epoch_id`, and fixed seed, Pipeline B SHALL produce deterministic `exec_plan` and `exec_trace` outputs.

**HLR‑20.206‑018**  
Pipeline B logs SHALL be sufficient to replay realization deterministically (E2).

**HLR‑20.206‑019**  
Seed variability SHALL affect realization selection only and SHALL NOT influence the frozen meaning snapshot.

# **11. Equivalence Classes (E1, E2, E3)**

### **Requirements**

**HLR‑20.206‑020**  
Meaning equivalence class **E1** SHALL hold: stripping B artifacts from a cycle SHALL yield a `semantic_core` identical to Pipeline A‑only replay.

**HLR‑20.206‑021**  
Full‑trace reproducibility class **E2** SHALL treat B artifacts as derivable evidence, not meaning authority.

**HLR‑20.206‑022**  
Post‑correction meaning class **E3** SHALL apply only in subsequent cycles; same‑cycle IMR SHALL NOT mutate `semantic_core`.

# **12. Contradiction Annotation**

### **Requirements**

**HLR‑20.206‑065**  
Pipeline B SHALL read contradiction annotations and SHALL preserve them in `exec_plan` and `exec_trace`.

**HLR‑20.206‑066**

**HLR‑20.206‑067**

**HLR‑20.206‑068**  
Any attempt by B to modify contradiction annotations SHALL fail with a Structural Error.

# **13. B→A Return Path (IMR)**

Pipeline B may request corrections, but may not modify meaning.

### **Requirements**

**HLR‑20.206‑023**  
IMR MAY enqueue `CorrectionTrigger` entries, but Pipeline A SHALL consume them only in subsequent cycles.

**HLR‑20.206‑024**  
Type B corrections SHALL reference the frozen snapshot consumed by B and SHALL NOT use TP or lane inputs.

**HLR‑20.206‑025**  
Supervisory commands SHALL NOT bypass the freeze contract without emitting append‑only audit evidence.

# **14. Retry Semantics (IMR Type A / Type B)**  
*(Fixes Issue 5)*

### **Requirements**

**HLR‑20.206‑069**  
IMR Type A retries SHALL re‑run Pipeline B using the same `commit_id`, same `semantic_snapshot_ref`, and same XP record, incrementing only `xp_pass_seq`.

**HLR‑20.206‑070**  
IMR Type B corrections SHALL enqueue a `CorrectionTrigger` for Pipeline A and SHALL NOT cause a same‑cycle re‑run.

**HLR‑20.206‑071**  
Pipeline B SHALL NOT request retries based on TP, lane‑local, or pre‑commit structures.

**HLR‑20.206‑072**  
Retry semantics SHALL NOT alter equivalence classes E1, E2, or E3.

**HLR‑20.206‑073**  
Any retry request that violates these rules SHALL be rejected with a Structural Error.

`mtp_update` → B start → trig_rb → srp_lookup → exec_plan_commit → oub_expression → imr_evaluation.

**HLR‑20.206‑028**
