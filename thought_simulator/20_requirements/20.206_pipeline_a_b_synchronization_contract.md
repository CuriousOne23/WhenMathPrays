# 20.206 Pipeline A↔B Synchronization Contract

**Document ID:** 20.206  
**Version:** 0.2  
**Date:** 2026-06-07  
**Status:** Draft v0.2 — CP polish applied (Stage 4 review in progress per [20.500](20.500_refactoring_for_dual_TS_pipeline.md))

## Purpose

Defines the **normative synchronization contract** at the Pipeline A / Pipeline B boundary: when meaning is frozen, how `commit_id` identifies an authoritative `semantic_core` snapshot, what Pipeline B may read and write, how **XP** binds realization artifacts to a single MTP commit per cycle, and how **equivalence classes** partition meaning replay from full-trace replay.

This module **satisfies and refines** HLR-20.012-005, HLR-20.012-011, HLR-20.012-012, and HLR-20.012-014 and SHALL NOT weaken [20.12_ts_invariants.md](20.12_ts_invariants.md).

**Naming authority:** [20.500](20.500_refactoring_for_dual_TS_pipeline.md) §5 (`commit_id`, XP, Pipeline A/B). Legacy `mtp_snapshot_id` in older modules is a deprecated alias — this document uses `commit_id` only.

**Document authority (this module owns):** `mtp_update`→B start ordering; `commit_id` / `semantic_snapshot_ref` freeze contract; approved B read set; forbidden B inputs; E1/E2/E3 equivalence classes; IMR return-path limits at the boundary.

**Deferred to sibling modules:** XP field schema → [20.205](20.205_execution_packet_xp_requirements.md); `commit_id` derivation wire → [20.115](20.115_mtp_requirements.md); E2 regeneration procedure → [20.207](20.207_execution_replay_specification.md); TrigRB/SRP algorithms → 20.55–20.57.

## 1. Cycle Topology

**Intent:** This section defines the mandatory ordering and concurrency model for A→B execution within a TS cycle.

Within a single TS **cycle** `cycle_id`, Pipeline A completes meaning construction and commits before Pipeline B begins realization for that commit.

Pipeline B executes exactly one realization pass per **`commit_id`** unless IMR Type A authorizes a same-snapshot retry on the existing `xp_record` ([20.205](20.205_execution_packet_xp_requirements.md) §6). B scope is **commit-scoped**, not lane-scoped — a cycle may carry one committed snapshot and one primary B episode bound to that `commit_id`.

```text
Pipeline A (lane-parallel):
  InB → RB → OB → DCB → [TR if tr_needs_update] → TB → Merge → ΔH% → Truth/Done
       → mtp_update  ── emits commit_id, freezes semantic_core
                              │
                              ▼
Pipeline B (singular, MTP-scoped):
  TrigRB → SRP lookup → exec_plan_commit (OpBeh/OBG/XlateR) → OuB → IMR
       → [bounded CorrectionTrigger → next-cycle Pipeline A only]
```

*Stage-order note:* Canonical B hot-path order is **`trig_rb → srp_lookup`** (detect triggers, then resolve routing rows). SRP **table compile** remains off the hot path per HLR-20.012-006. [20.36](20.36_canonical_end_to_end_trace.md) §2.2 stage list aligns in Stage 4 (**D17**).

1. **HLR-20.206-001:** Every cycle SHALL execute Pipeline A meaning construction to completion (including `mtp_update` when policy requires commit) before Pipeline B realization planning begins for that `commit_id`.
2. **HLR-20.206-002:** Pipeline B SHALL execute **at most one** primary realization pass per (`commit_id`, `cycle_id`) unless an approved IMR Type A retry schedules an additional B pass on the **same** `semantic_snapshot_ref` via `xp_pass_seq` on the existing `xp_record` ([20.205](20.205_execution_packet_xp_requirements.md) §6; 20.45 HLR-20.045-004).
3. **HLR-20.206-003:** Pipeline B SHALL NOT use lane parallelism, split/merge, `lane_id`, or TP instances as structural inputs.

## 2. `mtp_update` and `commit_id`

`mtp_update` is the Pipeline A commit event that publishes authoritative meaning for realization.

| Field / event | Authority |
|---------------|-----------|
| `mtp_update` | Pipeline A only; occurs after Merge and Truth/Done when commit policy is satisfied |
| `commit_id` | Stable identifier for the committed `semantic_core` snapshot at `mtp_update` |
| `semantic_core` | Authoritative meaning envelope; frozen at `mtp_update` for the referenced `commit_id` |

4. **HLR-20.206-004:** Every `mtp_update` SHALL emit exactly one `commit_id` that uniquely identifies the committed `semantic_core` snapshot for that cycle.
5. **HLR-20.206-005:** `commit_id` SHALL remain immutable for the life of the referenced snapshot; subsequent `mtp_update` events SHALL emit new `commit_id` values.
6. **HLR-20.206-006:** Pipeline B SHALL bind all `exec_plan` and `exec_trace` records for a cycle to exactly one `commit_id` and one `cycle_id`.
7. **HLR-20.206-007:** Pipeline B SHALL NOT consume or reference pre-commit draft `semantic_core` state except through an explicit `semantic_snapshot_ref` that resolves to a post-`mtp_update` frozen snapshot.

### 2.1 Minimum commit record (normative sketch)

```text
mtp_commit_record {
  commit_id,
  cycle_id,
  mtp_id,
  policy_signature,
  execution_signature,
  semantic_snapshot_ref,    // frozen semantic_core bytes or content hash
  commit_reason_codes[],    // e.g. TRUTH_DONE_COMPLETE, GB_BOUNDARY, FORCED_COMMIT
  lane_merge_summary_ref?   // audit pointer only; not a B input
}
```

8. **HLR-20.206-008:** `mtp_commit_record` SHALL be append-only audit evidence; Pipeline B SHALL read `semantic_snapshot_ref` and `commit_id` from this record or an equivalent deterministic commit index.

The representation of `semantic_snapshot_ref` (content hash vs. embedded snapshot copy) is defined in [20.39](20.39_ts_core_data_structures.md) (open item **D2** in §9.2).

## 3. Freeze Semantics

After `mtp_update` for `commit_id` **C**, the `semantic_snapshot_ref` bound to **C** is **frozen** for Pipeline B.

9. **HLR-20.206-009:** For `commit_id` **C**, Pipeline B SHALL treat the referenced `semantic_core` snapshot as **read-only** for the duration of the B pass bound to **C** (HLR-20.012-003, HLR-20.012-014).
10. **HLR-20.206-010:** Pipeline B SHALL NOT mutate, patch, smooth, or retroactively revise any field in the frozen snapshot for **C** during the same `cycle_id` (HLR-20.012-005).
11. **HLR-20.206-011:** Pipeline A SHALL NOT perform a second `mtp_update` for the same `cycle_id` after Pipeline B has started realization for that cycle's `commit_id`, unless GB aborts the cycle with a fixed supervisory reason code and audit record.

### 3.1 Approved B reads from frozen `semantic_core`

Pipeline B MAY read only explicit `semantic_core` fields required for realization planning and expression, including at minimum:

- `propositions[]`, `stance`, `goals[]`, `delta_h`
- `thought_router_fields` (read-only routing semantics at meaning layer)
- `messy_input_record` (read-only; expression must not clear flags — 20.17, 20.31-018)
- `truth_hypotheses`, `done_state` (read-only presentation gating)
- `policy_signature`, `execution_signature`

12. **HLR-20.206-012:** Pipeline B SHALL NOT read TP instances, `tp_id`, `lane_id`, `TP.TR`, lane-local `channel_interpretations{}`, DCB ephemeral geometry, or pre-merge hypothesis fragments.

**TP visibility rationale:** TP is lane-local provenance and is not part of the committed meaning envelope; therefore it is never visible to Pipeline B. B consumes only post-`mtp_update` `semantic_core` via `commit_id` / `semantic_snapshot_ref` ([20.105](20.105_tp_requirements.md), [20.31](20.31_semantic_specification.md)).

### 3.2 Forbidden B inputs (hard reject)

| Input | Posture |
|-------|---------|
| TP / `TpLaneView` | **Forbidden** — lane-local provenance; not in meaning envelope |
| `lane_id` | **Forbidden** on B envelopes and XP |
| `routing_metadata` from RB | **Forbidden** for B planning — use published SRP tables + `routing_epoch_id` |
| Uncommitted merge drafts | **Forbidden** |

13. **HLR-20.206-013:** Attempts to start Pipeline B without a resolvable post-`mtp_update` `semantic_snapshot_ref` SHALL fail deterministically with fixed reason code `B_START_WITHOUT_COMMIT`.

## 4. Pipeline B Output Contract

14. **HLR-20.206-014:** Pipeline B SHALL write only `exec_plan`, `exec_trace`, and append-only supervisory trigger queue entries derived from IMR (HLR-20.012-001).
15. **HLR-20.206-015:** Every `exec_plan` and `exec_trace` record SHALL carry `commit_id`, `cycle_id`, and `routing_epoch_id`.
16. **HLR-20.206-016:** `exec_plan` and `exec_trace` SHALL remain distinct envelopes; XP aggregates them logically but SHALL NOT collapse write authority (HLR-20.012-004; 20.500 OQ-002).

### 4.1 XP binding (logical aggregate)

**XP** (Execution Packet) is the per-commit, per-cycle logical index for B artifacts. Normative `xp_record` schema, lifecycle, and serialization rules are in [20.205](20.205_execution_packet_xp_requirements.md) §4–§7 — this section states boundary obligations only.

17. **HLR-20.206-017:** Exactly one primary `xp_record` SHALL exist per (`commit_id`, `cycle_id`) for a normal realization pass (Type A retries use `xp_pass_seq` on the same record per 20.205 §6).
18. **HLR-20.206-018:** XP SHALL NOT introduce a fourth authoritative state envelope; XP is a logical index over `exec_plan` + `exec_trace` + B audit refs (HLR-20.012-004; 20.500 OQ-002).
19. **HLR-20.206-019:** XP SHALL NOT alias TP; there is no TP-B.

## 5. Equivalence Classes

Three replay/equivalence classes govern verification:

| Class | Name | Definition |
|-------|------|------------|
| **E1** | Meaning equivalence | Strip `exec_plan` + `exec_trace` (+ XP index) → `semantic_core` byte-identical to Pipeline A-only replay (HLR-20.012-011) |
| **E2** | Full-trace reproducibility | Re-run from inputs + `commit_id` snapshot + `routing_epoch_id` + seed → regenerate B envelopes deterministically (HLR-20.012-012; detail in 20.207) |
| **E3** | Post-correction meaning | After approved IMR Type B `CorrectionTrigger`, subsequent-cycle `semantic_core` diffs are Pipeline A writes with `correction_trigger_id` provenance — not IMR direct writes |

20. **HLR-20.206-020:** Meaning equivalence class **E1** SHALL hold for all golden scenarios before any approved Type B correction takes effect in a subsequent cycle (20.36 Class 1; 20.45 §Replay equivalence preservation).
21. **HLR-20.206-021:** Full-trace class **E2** SHALL treat B artifacts as **derivable evidence** — not meaning authority. Stripping B SHALL never be required to recover authoritative meaning.
22. **HLR-20.206-022:** Class **E3** corrections SHALL execute only in a **subsequent** Pipeline A cycle; same-cycle IMR SHALL NOT mutate `semantic_core` (HLR-20.012-005, 20.45 HLR-20.045-008).

### 5.1 Seed scope at boundary

23. **HLR-20.206-023:** `seed` variability at the A/B boundary SHALL affect Pipeline B expression/realization selection only and SHALL NOT influence the frozen `semantic_core` snapshot for `commit_id` **C** (HLR-20.012-010).

## 6. B→A Return Path (IMR and Supervisory)

Pipeline B feedback into Pipeline A is **trigger-only**.

24. **HLR-20.206-024:** IMR MAY append `CorrectionTrigger` entries to the supervisory trigger queue; Pipeline A SHALL consume them only through explicit bounded pathways in the **next** cycle (or later), never in the same cycle as the originating B pass (20.45, 20.37 §3.4).
25. **HLR-20.206-025:** Type B `CorrectionTrigger` SHALL reference `prior_semantic_snapshot_ref` equal to the frozen `commit_id` snapshot that B consumed; A-side correction passes SHALL NOT use TP or lane inputs.
26. **HLR-20.206-026:** GB supervisory commands (Type C, caps, Safe-Mode) SHALL NOT bypass the freeze contract in §3 without emitting append-only audit evidence and fixed reason codes.

---

## 7. Ordering and Concurrency Guards

27. **HLR-20.206-027:** Within a cycle, stage ordering SHALL be: `mtp_update` → `trig_rb` → `srp_lookup` → `exec_plan_commit` → `oub_expression` → `imr_evaluation` → (optional) supervisory trigger enqueue — no interleaving of A basin passes after B start for the same `commit_id`.
28. **HLR-20.206-028:** Implementations SHALL enforce envelope write-guards: any write to `semantic_core` during an active B pass for `commit_id` **C** SHALL fail with `FAIL_ENVELOPE_A_WRITE_DURING_B`.
29. **HLR-20.206-029:** Implementations SHALL reject B reads that reference `tp_id` or `lane_id` with `FAIL_B_FORBIDDEN_TP_READ`.

---

## 8. Verification Focus

- Golden fixture: one `commit_id`, one XP, zero `lane_id` in B envelopes
- Negative fixture: B start without `mtp_update` → `B_START_WITHOUT_COMMIT`
- Negative fixture: `lane_id` on `exec_plan` → reject
- E1 strip test: remove `exec_plan`/`exec_trace` → `semantic_core` identical
- Freeze test: attempt `semantic_core` write during B → `FAIL_ENVELOPE_A_WRITE_DURING_B`
- IMR Type B: trigger enqueued same cycle; A correction only next cycle

Short definitions for modules referenced in the A↔B boundary contract. Canonical terms: [20.190](20.190_glossary.md); algorithms: 20.41–20.58.

| Term | Meaning in this document |
|------|--------------------------|
| **SRP** | Semantic Routing Planner — cold-path routing table compile; hot path performs epoch-coherent lookup only (HLR-20.012-006; [20.55](20.55_srp_requirements.md)) |
| **TrigRB** | Semantic trigger detector on Pipeline B hot path; ≠ Thought Router **TR** or Relational Basin **RB** ([20.57](20.57_trig_rb_semantic_trigger_requirements.md)) |
