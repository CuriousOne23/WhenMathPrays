# **20.30.040 — Meaningful Cognitive Step (MCS) Rules**  
**Status:** Normative (HLR‑20.30.040‑xxx only)  
**Scope:** Definition of MCS, counting rules, anti‑inflation rules  
**Excludes:** TCU budgeting (20.30.030), merge semantics (20.30.050), truth semantics (20.30.060)

---

# **0. Purpose**

This document defines the **Meaningful Cognitive Step (MCS)** model used by the Thought Simulator (TS).  
It establishes:

- what qualifies as an MCS  
- how MCS events are counted  
- how MCS events relate to TP/MTP state transitions  
- how the TS prevents artificial inflation of cognitive steps  

MCS rules ensure that cognitive progress is measurable, auditable, and resistant to manipulation.

---

# **1. MCS Overview**

A **Meaningful Cognitive Step (MCS)** is a **state‑changing transition** that advances the TS toward a declared success condition.  
An MCS reflects **actual semantic progress**, not surface‑level activity.

MCS events are:

- attributable  
- deterministic  
- auditable  
- tied to TP/MTP transitions  
- bounded by subsystem semantics  

MCS is a **semantic** measure, not a compute measure.  
TCU budgeting is defined separately in 20.30.030.

---

# **2. What Qualifies as an MCS**

An MCS represents a transition that:

- changes validated TP or MTP semantic state  
- advances a reasoning trajectory  
- resolves or updates a hypothesis  
- integrates new evidence  
- performs a corrective action  
- meaningfully alters stance, intent, or truth hypotheses  

An MCS is always tied to a **deterministic, reviewable state change**.

---

# **3. What Does *Not* Qualify as an MCS**

The following do **not** count as MCS events:

- formatting changes  
- whitespace or structural normalization  
- repeated artifact emissions  
- no‑op transitions  
- micro‑steps that subdivide a single semantic action  
- redundant or oscillatory updates  
- deterministic replay of identical state  
- internal housekeeping or diagnostics
- TPTB metadata:  
  Truth metadata attached to TP/MTP (TPTB) is treated as zero‑cost; only the upstream
  truth‑evaluation steps that produce it are counted as MCS.
- TPSF metadata:
  Safety metadata attached to TP/MTP (TPSF) is treated as zero‑cost; only the upstream
  safety‑evaluation steps that produce it are counted as MCS.

These actions do not advance semantic state and therefore do not qualify.

---

# **4. MCS Logging and Attribution**

Each MCS event is logged with:

- the TP/MTP state before the transition  
- the TP/MTP state after the transition  
- the subsystem responsible  
- the semantic field(s) affected  
- the reason for the transition  
- the cycle index  

This ensures that MCS events are:

- attributable  
- replayable  
- auditable  
- stable under deterministic replay  

---

# **5. Anti‑Inflation Rules**

The TS prevents artificial inflation of MCS counts by:

- prohibiting subdivision of a single semantic action into multiple logged steps  
- prohibiting repeated emissions of identical artifacts  
- prohibiting redundant or oscillatory updates  
- prohibiting micro‑step inflation  
- requiring that each MCS correspond to a **meaningful** semantic transition  

These rules ensure that MCS counts reflect **true cognitive progress**.

---

# **6. Normative Requirements (HLR‑20.30.040‑xxx)**

These are the **only** SHALL‑bearing requirements in this file.

### **HLR‑20.30.040‑001 — MCS Definition**  
An MCS SHALL represent a deterministic, state‑changing transition that advances the TS toward a declared success condition.

### **HLR‑20.30.040‑002 — State‑Change Requirement**  
An MCS SHALL correspond to a validated change in TP or MTP semantic state.

### **HLR‑20.30.040‑003 — Attribution Requirement**  
Each MCS SHALL be attributable to a specific subsystem and a specific TP/MTP transition.

### **HLR‑20.30.040‑004 — No Micro‑Step Inflation**  
The TS SHALL prohibit subdivision of a single semantic action into multiple logged steps.

### **HLR‑20.30.040‑005 — No Redundant Emissions**  
The TS SHALL prohibit repeated or redundant artifact emissions from being counted as MCS events.

### **HLR‑20.30.040‑006 — No No‑Op Counting**  
The TS SHALL prohibit no‑ops, formatting changes, and deterministic replays of identical state from being counted as MCS events.

### **HLR‑20.30.040‑007 — Deterministic Logging**  
The TS SHALL log each MCS deterministically with before/after state, subsystem attribution, and cycle index.

### **HLR‑20.30.040‑008 — Replay‑Safe MCS Behavior**  
MCS counts SHALL be identical for identical (input, MTP state, execution signature) tuples.

### **HLR‑20.30.040‑008**
TS SHALL treat TPTB and TPSF as zero‑cost metadata fields for MCS accounting; only the cognitive steps that compute truth and safety outcomes upstream of these structures SHALL contribute to MCS.

---

# **7. Summary**

20.30.040 defines the TS’s cognitive‑progress metric:

- MCS = meaningful, state‑changing transition  
- deterministic, attributable, auditable  
- no micro‑step inflation  
- no redundant emissions  
- no no‑ops  
- replay‑safe behavior  

This ensures that MCS counts reflect **true semantic progress**, not surface‑level activity.
