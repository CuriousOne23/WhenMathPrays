**Status:** Architectural Overview  
**Source of Truth:** This document  
**Normative Weight:** High‑level invariants only

# **0. Purpose**

20.30 defines the **high‑level functional model** of the Thought Simulator (TS).  
It establishes:

- the dual‑pipeline architecture  
- the deterministic meaning‑construction model  
- the separation of meaning vs. expression  
- the supervisory boundaries  
- the global stability envelope  
- the role of the Master Thought Packet (MTP)  
- the lifecycle of a TS cycle  

This document is intentionally **short**.  
All detailed semantics, algorithms, and normative requirements are defined in the **20.30.010–20.30.080** subfiles.

---

# **1. Architectural Overview**

The TS is a **deterministic, structured, auditable reasoning system**.  
It replaces latent‑space inference with explicit meaning construction, explicit truth evaluation, and explicit supervisory boundaries.

The architecture is built around three pillars:

1. **Deterministic meaning construction** (Pipeline A)  
2. **Deterministic realization and expression** (Pipeline B)  
3. **Deterministic supervisory control** (GB/IB boundary)

Meaning is represented explicitly in the **Master Thought Packet (MTP)**.  
All reasoning steps are visible, structured, and replayable.

---

# **2. Dual‑Pipeline Model**

The TS operates two pipelines per cycle:

## **2.1 Pipeline A — Meaning Construction (Input‑Side)**  
Pipeline A constructs meaning from:

- input  
- prior MTP state  
- OB/RB path semantics  
- ΔH% contributions  
- TB interpretations  
- truth and completion evaluation  

Pipeline A is **deterministic**, **lane‑parallel**, and the **sole writer** of `semantic_core`.

Detailed semantics: **20.30.010**, **20.30.050**, **20.30.060**, **20.30.070**

---

## **2.2 Pipeline B — Realization and Expression (Output‑Side)**  
Pipeline B executes:

- realization planning  
- expression mapping  
- surface‑form generation  

Pipeline B is **deterministic given (MTP, seed)** and **never writes meaning**.

Variability is isolated to the **response generator seed**.

Detailed semantics: **20.30.080**

---

# **3. Meaning Representation**

Meaning is represented explicitly in:

- **TP** (lane‑local Thought Packet)  
- **MTP** (global Master Thought Packet)  

The MTP contains:

- propositions  
- stance  
- affect  
- intent  
- ΔH%  
- truth hypotheses  
- completion state  
- lineage  
- semantic tags  

Meaning is **not** stored in vectors or embeddings.

Detailed semantics: **20.30.010**, **20.30.060**, **20.30.070**

---

# **4. Deterministic Invariants**

The TS guarantees:

### **4.1 Deterministic Replay**  
Same input + same MTP state + same seed → same output.

### **4.2 Deterministic Meaning Construction**  
OB/RB/TB/ΔH%/truth/merge semantics are deterministic.

### **4.3 Deterministic Supervisory Boundaries**  
GB supervises global behavior; TS core constructs meaning.

### **4.4 Deterministic Overflow Behavior**  
Overflow produces deterministic degradation, tagging, and logging.

### **4.5 Deterministic TCU/MCS Accounting**  
All compute and cognitive steps are bounded and auditable.

Detailed invariants: **20.30.020**, **20.30.030**, **20.30.040**, **20.30.060**

---

# **5. Supervisory Model (GB/IB Boundary)**

The TS core performs meaning construction.  
The **Global Basin (GB)** supervises:

- drift  
- oscillation  
- inquiry depth  
- branching  
- safety‑mode transitions  

The **Inquiry Basin (IB)** is created only with GB approval.

TS core and GB communicate through a **deterministic supervisory interface**.

Detailed semantics: **20.30.060**, **20.30.070**

---

# **6. Stability and Boundedness**

The TS enforces global deterministic bounds on:

- lanes  
- OB activations  
- routing fan‑out  
- evidence size  
- ΔH% flow  
- provenance depth  
- TCU consumption  

Overflow triggers deterministic degradation and tagging.

Detailed semantics: **20.30.020**, **20.30.030**

---

# **7. TS Cycle Overview**

A TS cycle proceeds through:

1. **Input intake**  
2. **Routing and splitting**  
3. **OB processing**  
4. **TB interpretation**  
5. **Merge**  
6. **Truth and completion evaluation**  
7. **MTP update (`commit_id`)**  
8. **Pipeline B realization**  
9. **Response generation**  

### **OB Evaluation Sequence (Normative)**  
OB evaluation in Pipeline A consists of the ordered sequence:
**SOB → SROB → CnOB → SmOB**

RB routes TPs into the appropriate OB‑prm layer, and TS executes the OB chain in this fixed order whenever OB processing is required. Each layer consumes the layer‑specific TP view defined in 20.40.010–040 and produces residue for the next layer.

Pipeline A writes meaning; Pipeline B expresses it.

Detailed semantics: **20.30.010**, **20.30.050**, **20.30.060**, **20.30.070**, **20.30.080**

# **9. Normative Requirements (High‑Level Only)**

These are the **only** HLRs that remain in 20.30.  
All others move to the subfiles.

### **HLR‑20.30‑A01 — Deterministic Meaning Construction**  
TS SHALL construct meaning deterministically from OB/RB/TB/ΔH%/truth semantics.

### **HLR‑20.30‑A02 — Deterministic Replay**  
TS SHALL produce identical outputs for identical (input, MTP state, seed) tuples.

### **HLR‑20.30‑A03 — Supervisory Separation**  
TS core SHALL construct meaning; GB SHALL supervise global behavior.

### **HLR‑20.30‑A04 — Stability Envelope**  
TS SHALL enforce global deterministic bounds on lanes, evidence, ΔH%, provenance, and TCU.

### **HLR‑20.30‑A05 — Overflow Determinism**  
Overflow SHALL produce deterministic degradation, tagging, and logging.

### **HLR‑20.30‑A06 — Meaning/Expression Separation**  
Pipeline A SHALL write meaning; Pipeline B SHALL express meaning without modifying it.

### **HLR‑20.30‑A07 — Explicit Meaning Representation**  
Meaning SHALL be represented explicitly in TP/MTP structures, not vectors.
