# **20.30 TS Functional Model (Revised)**  

---

# **Purpose**

This document defines the functional model of the Thought Simulator (TS) and specifies the deterministic meaning‑construction pipeline known as **Pipeline A**. It describes how structured meaning is extracted, routed, transformed, merged, evaluated, and committed into the Master Thought Packet (MTP). It also defines the relationship between Pipeline A and the realization‑side **Pipeline B**, which consumes the committed semantic state.

This specification establishes the architectural boundaries among OB, RB, TR, TB, TPU, and MTP, and defines how meaning construction proceeds deterministically across cycles. It also defines the global invariants, stability constraints, and replay guarantees that govern TS behavior.

This document is descriptive; all normative obligations appear in the HLR‑20.030‑xxx series.

---

# **0. Functional Overview**

The TS operates as a deterministic, structured meaning‑construction engine. Pipeline A transforms input into explicit semantic state through a sequence of basin‑level primitives. The pipeline is lane‑parallel, deterministic, and replay‑stable. All semantic commitments occur through TPU, and  RB.

The canonical structural flow is:

> **OB → TP → RB (route) → TR → TB → Merge → TPU → MTP Update**

HLR-20.030-352: Under multi-core Path A execution (20.115), Pipeline A MAY execute multiple independent Path A instances in parallel, each bound to a distinct `core_id` and OB orthogonality domain. These instances SHALL NOT interact during meaning construction; Merge and MTP Update SHALL assemble Path A artifacts deterministically using whole-path semantics only.


Pipeline B consumes the frozen `semantic_core` after `mtp_update` and performs realization, expression, and supervisory integration.

# **2. TS Primitives (Definitions — Pipeline A)**

These are the fundamental units of Pipeline A meaning construction.

## **2.1 TP — Thought Packet**  
A structured semantic object containing:

- propositions  
- stance  
- affect  
- intent  
- ΔH%  
- lineage  
- semantic tags  
- tr_needs_update (boolean TR stale/fresh indicator)  

## **2.2 MTP — Master Thought Packet**  
The global semantic state for the current thought.  
All lane TPs merge into the MTP.

## **2.3 OB — Observation Basin**  
A correlator operating closest to the geometric substrate.  
Extracts local meaning fragments and ΔH%.

## **2.4 RB — Relational Basin**  
Defines the topology of meaning extraction:

- which OBs fire  
- in what order  
- with what projections  

## **2.5 TB — Truth Basin**  
Modules that interpret meaning:

- TB‑logic  
- TB‑emotion  
- TB‑intent  
- TB‑stance  
- TB‑social  

## **2.6 ΔH% — Entropy Change**  
A normalized measure of how much evidence a lane TP contributes to a hypothesis.

---

### **HLR‑20.030‑015 — Unified ΔH% Structural‑Entropy Delta**

> **ΔH% SHALL be defined as the normalized structural‑entropy delta between a primitive’s incoming envelope and its outgoing envelope.  
> All TS‑20 primitives SHALL compute ΔH% using this unified architectural definition.  
> Each primitive SHALL define its local entropy model (H_before, H_after, uncertainty sources, and normalization) in its corresponding 10.50.xx specification.  
> ΔH% SHALL remain deterministic, monotonic, MI‑class‑normalized, and SHALL NOT encode probability, truth, or semantic inference.**

---

## **2.7 TCU — Thought Compute Unit**  
A normalized unit of computational cost.  
Calibrated via the TCU kernel (Section 7).

## **2.8 MCS - Meaningful Cognitive Step**
A Meaningful Cognitive Step (MCS) is a logged, attributable, state-changing transition that advances the task toward a declared success condition.
An MCS SHALL:

- be logged deterministically
- be attributable to a specific TP/MTP transition
- alter validated task state
- map to a success path or corrective action
- NOT include no-ops, formatting changes, or repeated artifact emissions
- NOT allow micro-step inflation

Sections 2–3 describe **Pipeline A only** (lane-parallel meaning construction). Pipeline B realization after `mtp_update` is summarized above and in [20.206](20.206_pipeline_a_b_synchronization_contract.md) (draft pending Stage 4).

## **3.1 Input**
A prompt or prior MTP enters the system.

## **3.2 Routing**  
RBs determine:

- which OBs fire  
- the order of activation  
- the lane projections  

HLR‑20.030‑340: RB SHALL route the TP to the TR routine if and only if tr_needs_update = true. 
Under multi-core Path A execution, RB SHALL enforce core-local routing:
- RB SHALL route each TP only to OBs whose `orthogonality_signature` matches the TP’s assigned core domain.
- RB SHALL NOT route a TP into an OB family belonging to a different orthogonality domain.
- RB SHALL NOT collapse or merge lanes across different `core_id` values.


## **3.3 OB Processing**  
Each OB:

- processes its lane TP  
- extracts local meaning fragments  
- computes ΔH%  
- returns structured evidence  

HLR‑20.030‑341: Any OB that modifies semantic‑relevant TP fields SHALL set tr_needs_update = true.

## **3.3.1 DCB Observation (Geometric Meta-Basin)**

After OB processing and before the TR routine:

- DCB observes the TP trajectory (position, direction, curvature) across steps.
- DCB emits ephemeral directional-change events when bounded geometric invariants are exceeded.
- DCB does not write TP fields and does not interpret meaning.
- RB does not consume DCB events.
- TR consumes DCB events only when `tr_needs_update = true` and RB routes to the TR routine.

HLR‑20.030‑342: DCB SHALL emit deterministic directional‑change events based on bounded geometric invariants.  
HLR‑20.030‑343: DCB SHALL NOT write TP fields and SHALL NOT interpret meaning.  
HLR‑20.030‑344: TR SHALL consume DCB events only when tr_needs_update = true and RB routes to TR.

Normative cycle ordering:

```text
RB → OB → DCB observes trajectory → (if tr_needs_update) TR routine → RB
```

## **3.3.2 TS–RB Coordination for OB‑Chain Lifecycle**

After RB selects an OB‑set for execution, TS becomes responsible for managing the lifecycle of the resulting OB‑chain. RB communicates the complete routed OB‑set to TS, including all OB identifiers selected for the current cycle. TS tracks each routed OB instance, monitors their completion, and determines when the OB‑chain has fully resolved.

Once all OB outputs are available, TS invokes CTP‑prm. CTP‑prm collects the TP outputs from each OB in the chain, preserves provenance for each contribution, and produces a combined TP snapshot. This combined TP is structurally complete but not semantically merged; any semantic conflict resolution occurs later in Pipeline B.

TS then delivers the combined TP snapshot to RB for the next arbitration cycle. RB treats this snapshot as a standard TP input and remains unaware of OB‑chain structure or CTP involvement. RB does not track OB lifecycle, does not interact with CTP‑prm, and does not manage OB‑chain completion. TS is the sole orchestrator of OB‑chain execution and CTP invocation.

This coordination ensures deterministic OB‑chain execution, correct multi‑core parallel OB handling, and a clean modular boundary between routing (RB), bookkeeping (CTP), and orchestration (TS).

## **4.2 Merge Rules (Revised)**

Merge rules define how individual TP fields are structurally combined during the merging stage. Each field in the TP schema is associated with a specific merge rule that determines how values from multiple lanes contribute to the final update. Merge rules are deterministic and field‑local: each rule applies only to its own field and does not influence the behavior of other rules.

Merge rules fall into several categories. Max‑selection rules choose the highest‑priority or highest‑confidence value among lanes. Summation rules accumulate numeric contributions, such as ΔH% or missing‑mass adjustments. Overwrite rules select a single authoritative value based on lane ordering or arbitration results. Weighted‑combination rules blend values according to predefined weights or structural factors. Rule‑based selection rules apply conditional logic to choose among candidate values.

These rules operate only on the finalized TP snapshots produced after OB‑chain completion, CTP‑prm combination, RB arbitration, TR updates when required, and TB interpretation. Merge rules do not interpret meaning, resolve semantic conflicts, or modify the MTP. They provide the structural mechanism by which lane‑local updates are transformed into a unified `tp_update_request` for TPU.
