# 20.38 TS Implementation Guidelines

**Document ID:** 20.38  
**Version:** 0.1  
**Date:** 2026-06-04  
**Status:** Draft - For CP Review

## Purpose
This document provides concrete implementation-level guidance to ensure the Thought Simulator is structured, efficient, maintainable, and faithful to the architectural principles in 20.10 and the functional model in 20.30.

## Scope
These guidelines apply to all code written for the TS core, 40_playground prototypes, and eventual production implementation.

## Non-Goals
- This document does not redefine semantics (see 20.31).
- It does not specify exact algorithms (see 20.35).
- It does not define data structure field layouts (see 20.39).

## Implementation Principles

**HLR-20.038-001:** All TS code SHALL be written in a modular, layered architecture that mirrors the 10/20/30/40/50 structure.

**HLR-20.038-002:** Core deterministic logic SHALL be separated from I/O, randomness, and user interface layers.

**HLR-20.038-003:** Every major component (IB, OB, RB, TB, GB, COB, etc.) SHALL be implemented as a distinct module with well-defined interfaces.

**HLR-20.038-004:** State mutation SHALL only occur through explicit, typed primitive operators.

**HLR-20.038-005:** All execution cycles SHALL follow a strict, fixed phase ordering with clear safe boundaries for GB intervention.

**HLR-20.038-006:** Code SHALL prioritize readability, auditability, and debuggability over micro-optimizations.

**HLR-20.038-007:** All non-deterministic behavior SHALL be isolated behind the randomness boundary.

**HLR-20.038-008:** Error handling SHALL be deterministic and produce explicit, logged reason codes.

## Coding Standards

**HLR-20.038-009:** Code SHALL use strong typing and explicit contracts for all major data structures.

**HLR-20.038-010:** Functions SHALL be small, single-responsibility, and pure where possible.

**HLR-20.038-011:** All public APIs SHALL include comprehensive input validation and precondition checks.

**HLR-20.038-012:** Logging SHALL be structured, deterministic at safe boundaries, and include HLR traceability where relevant.

**HLR-20.038-013:** Unit and integration tests SHALL be written against specific HLRs.

## Performance and Efficiency Guidelines

**HLR-20.038-014:** Critical paths (ΔH% calculation, routing, safety checks) SHALL be O(1) or O(log n) where possible.

**HLR-20.038-015:** Memory usage SHALL be bounded and monitored per execution cycle.

**HLR-20.038-016:** Object creation and garbage collection pressure SHALL be minimized through reuse and pooling where appropriate.

**HLR-20.038-017:** Parallel trace processing SHALL use bounded thread pools or async patterns with backpressure.

## Debugging and Observability

**HLR-20.038-018:** The system SHALL support full deterministic replay from seed + input.

**HLR-20.038-019:** Execution traces SHALL be exportable in a canonical, human-readable format.

**HLR-20.038-020:** All GB decisions and safety violations SHALL be prominently logged with context.
