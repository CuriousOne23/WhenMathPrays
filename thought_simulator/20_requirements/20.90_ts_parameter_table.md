# 20.90 TS Parameter Table

## Purpose
Defines canonical numeric bounds and tunable values used by TS runtime control, IPC, supervision, regulation, and offload behavior.

This document is normative for numeric values consumed by architecture, implementation, verification, and replay.

## Normative Authority Statement
The 10-series architecture is normative about which bounds must exist and how violations are handled.
This parameter table is normative about the numeric values of those bounds.

## Scope and Compatibility Targets
This document supplies numeric values referenced by:
- 10.10.20 Interprocess Communication and Channels
- 10.10.30 Interrupts and Preemption Model
- 10.10.40 Scheduler and Regulator Architecture
- 10.10.50 Module Contracts and Visibility Rules
- 10.10.60 Coprocessor Offload and Portability Rules

## Change-Control Classes
- tunable: value may change under normal controlled release with impact note and verification refresh.
- stability-critical: value requires architecture sign-off, replay compatibility review, and supervisory safety impact review.

## Normative Requirements
1. HLR-20.090-001: Every numeric bound listed in this document SHALL be treated as canonical runtime configuration for TS deterministic operation.
2. HLR-20.090-002: Runtime behavior that exceeds a hard bound SHALL trigger deterministic bounded handling and audit tagging.
3. HLR-20.090-003: Stability-critical parameters SHALL NOT be changed without explicit architecture and safety sign-off.
4. HLR-20.090-004: Tunable parameters SHALL include rationale and verification impact notes in release artifacts.
5. HLR-20.090-005: IPC width, size, and queue constraints SHALL be enforced before payload execution.
6. HLR-20.090-006: Scheduler and regulator timing bounds SHALL be enforced each cycle.
7. HLR-20.090-007: Delta-H hard and soft limits SHALL be enforced deterministically and logged on violation.
8. HLR-20.090-008: Memory and snapshot bounds SHALL be enforced without silent truncation.
9. HLR-20.090-009: Routing fan-out and active-lane bounds SHALL be enforced deterministically.
10. HLR-20.090-010: Operator-cost ceilings SHALL be enforced with deterministic degrade or deny outcomes.
11. HLR-20.090-011: Offload bounds SHALL be enforced symmetrically for coprocessor and CPU fallback paths.
12. HLR-20.090-012: Parameter changes SHALL preserve deterministic replay under the active execution signature.
13. HLR-20.090-013: Each parameter SHALL include name, description, value, units, rationale, and change-control class.
14. HLR-20.090-014: Qualitative IPC labels (narrow, medium, wide) SHALL map to explicit numeric values in this document.
15. HLR-20.090-015: Queue overflow handling SHALL be deterministic, bounded, and auditable.
16. HLR-20.090-016: Timing-bound breaches SHALL trigger deterministic L2 or higher handling according to policy severity.
17. HLR-20.090-017: Soft limits MAY trigger damping behavior; hard limits SHALL trigger deterministic deny, preempt, or safe-mode behavior.
18. HLR-20.090-018: Parameter units SHALL be machine-testable and unambiguous.
19. HLR-20.090-019: Stability-critical value changes SHALL require replay baseline renewal.
20. HLR-20.090-020: Offload request cost and latency bounds SHALL be validated before acceptance.
21. HLR-20.090-021: Snapshot limits SHALL apply to both serialization and replay artifacts.
22. HLR-20.090-022: Message and channel limits SHALL be enforced before signature/hash generation.
23. HLR-20.090-023: Routing and lane bounds SHALL remain compatible with supervisory non-blocking behavior.
24. HLR-20.090-024: This table SHALL remain internally consistent with 20.95 numeric policy.
25. HLR-20.090-025: Violations of this table SHALL be treated as conformance failures for TS runtime control.

## Deterministic Violation Handling Summary
- Width/size violation: reject message with fixed reason code and log.
- Queue-depth violation: deterministic deny, throttle, or drop-with-audit according to policy class.
- Cycle-time hard violation: deterministic escalation to L2/L1 path.
- Delta-H hard violation: deterministic safe-mode or emergency path per severity.
- Memory bound violation: deterministic bounded degrade path; no silent truncation.
- Offload bound violation: deterministic deny and CPU fallback eligibility check.

## Conformance
Implementations conform only when:
- all listed bounds are enforced,
- all violation paths are deterministic and logged,
- change-control handling matches classification rules,
- values remain synchronized with execution-signature policy state.
