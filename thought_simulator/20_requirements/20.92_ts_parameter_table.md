# 20.92 TS Parameter Table

**Document ID:** 20.92  
**Version:** 0.4  
**Date:** 2026-06-06  
**Status:** CP-approved — dual-pipeline canonical bounds (v0.3 CP refinements applied)

## Purpose

Defines **canonical numeric bounds and tunable default values** for TS runtime control, IPC, supervision, regulation, offload, governance caps, and dual-pipeline envelopes.

This document is normative for numeric values consumed by architecture, implementation, verification, and replay. It SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

## Normative Authority

- **10-series:** which bounds must exist and how violations are handled
- **20.92 (this document):** canonical numeric values of those bounds
- **Module authority:** behavioral semantics in 20.16, 20.80, 20.45, 20.17; this table supplies their **default numbers**
- **Replay authority:** 20.36 Classes 2–5 consume parameters from this table for fixture assertions and golden baseline renewal

## Parent Scope

- **Numeric encoding:** [20.95_ts_numeric_policy.md](20.95_ts_numeric_policy.md) (Q32.32, uint64, canonical ordering, negative-zero normalization)
- **Override mechanism:** `policy_signature` MAY override tunable defaults; SHALL NOT disable enforcement
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Change-Control Classes

| Class | Rule |
|-------|------|
| **tunable** | May change under controlled release with impact note and verification refresh |
| **stability-critical** | Requires architecture sign-off, replay compatibility review (20.36), and supervisory safety review |

## Normative Requirements

1. **HLR-20.092-001:** Every numeric bound listed in this document SHALL be treated as canonical runtime configuration for TS deterministic operation.

2. **HLR-20.092-002:** Runtime behavior that exceeds a hard bound SHALL trigger deterministic bounded handling and audit tagging.

3. **HLR-20.092-003:** Stability-critical parameters SHALL NOT be changed without explicit architecture and safety sign-off.

4. **HLR-20.092-004:** Tunable parameters SHALL include rationale and verification impact notes in release artifacts.

5. **HLR-20.092-005:** IPC width, size, and queue constraints SHALL be enforced before payload execution.

6. **HLR-20.092-006:** Scheduler and regulator timing bounds SHALL be enforced each cycle.

7. **HLR-20.092-007:** ΔH% hard and soft limits SHALL be enforced deterministically and logged on violation; stored values SHALL use Q32.32 per 20.95; limit comparisons SHALL use canonical Q32.32 only (HLR-20.092-034).

8. **HLR-20.092-008:** Memory and snapshot bounds SHALL be enforced without silent truncation.

9. **HLR-20.092-009:** Routing fan-out and active-lane bounds SHALL be enforced deterministically.

10. **HLR-20.092-010:** Operator-cost ceilings SHALL be enforced with deterministic degrade or deny outcomes.

11. **HLR-20.092-011:** Offload bounds SHALL be enforced symmetrically for coprocessor and CPU fallback paths.

12. **HLR-20.092-012:** Parameter changes SHALL preserve deterministic replay under the active `policy_signature` and execution signature.

13. **HLR-20.092-013:** Each parameter SHALL include name, description, value, units, rationale, and change-control class.

14. **HLR-20.092-014:** Qualitative IPC labels (narrow, medium, wide) SHALL map to explicit numeric values in this document.

15. **HLR-20.092-015:** Queue overflow handling SHALL be deterministic, bounded, and auditable.

16. **HLR-20.092-016:** Timing-bound breaches SHALL trigger deterministic L2 or higher handling according to policy severity.

17. **HLR-20.092-017:** Soft limits MAY trigger damping behavior; hard limits SHALL trigger deterministic deny, preempt, or safe-mode behavior.

18. **HLR-20.092-018:** Parameter units SHALL be machine-testable and unambiguous.

19. **HLR-20.092-019:** Stability-critical value changes SHALL require replay baseline renewal per [20.36](20.36_canonical_end_to_end_trace.md).

20. **HLR-20.092-020:** Offload request cost and latency bounds SHALL be validated before acceptance.

21. **HLR-20.092-021:** Snapshot limits SHALL apply to all four envelopes: `semantic_core`, `exec_plan`, `exec_trace`, `supervisory`.

22. **HLR-20.092-022:** Message and channel limits SHALL be enforced before signature/hash generation.

23. **HLR-20.092-023:** Routing and lane bounds SHALL remain compatible with supervisory non-blocking behavior.

24. **HLR-20.092-024:** This table SHALL remain internally consistent with [20.95](20.95_ts_numeric_policy.md).

25. **HLR-20.092-025:** Violations of this table SHALL be treated as conformance failures for TS runtime control.

26. **HLR-20.092-026:** Governance parameters (`gb.*`, `imr.*`) in this table SHALL be the canonical defaults referenced by [20.16](20.16_gb_responsibility_matrix.md), [20.80](20.80_gb_requirements.md), and [20.45](20.45_imr_requirements.md).

27. **HLR-20.092-027:** `policy_signature` overrides MAY change tunable values but SHALL NOT remove cap or rate enforcement.

28. **HLR-20.092-028:** Dual-pipeline envelope snapshot bounds SHALL be enforced independently from MTP/TP bounds.

29. **HLR-20.092-029:** Percent and ratio parameters stored in authoritative state SHALL be represented as Q32.32; counter parameters SHALL be uint64.

30. **HLR-20.092-030:** Changes to stability-critical governance or replay parameters SHALL require pass on affected 20.36 replay test classes before release.

31. **HLR-20.092-031:** Messy-input parameters in §H SHALL be the canonical defaults referenced by [20.17](20.17_messy_input_handling.md); Pipeline B SHALL NOT consume or override them.

32. **HLR-20.092-032:** `gb.policy.routing_epoch_advance_per_cycle` SHALL remain **0**; no `policy_signature` override MAY permit GB to advance `routing_epoch_id` (HLR-20.016-045, HLR-20.080-061).

33. **HLR-20.092-033:** Rate limits and caps SHALL be enforced in independent accounting layers; exceeding a rate limit SHALL NOT consume cap budget and vice versa (HLR-20.080-044).

34. **HLR-20.092-034:** ΔH% soft, hard, and per-cycle step limit checks SHALL compare canonical Q32.32 encoded values per [20.95](20.95_ts_numeric_policy.md) — never pre-canonical float intermediates; volatility rank checks (20.17) SHALL use the same canonical form.

35. **HLR-20.092-035:** Q32.32 percent and ratio parameters in this table SHALL normalize negative zero to positive zero (`encoded_value = 0`) before comparison, commit, serialization, and replay diff (HLR-20.095-032).

36. **HLR-20.092-036:** When `gb.tcu_share.max_percent` is exceeded simultaneously with other GB caps, degradation SHALL follow multi-cap precedence in [20.16](20.16_gb_responsibility_matrix.md) §5.4 — **TCU first** — before action-priority ordering P0→P6 within the actions budget.

## Worked Example — Rate Limit + Cap + Defer Drain

External controller sends **5** `EXT_DAMPEN` commands within 10s while IMR posts **6** Type B notifications in one cycle. Parameters below are from §E–F.

| Step | Event | Parameter | Outcome |
|------|-------|-----------|---------|
| 1 | 5× `EXT_DAMPEN` in 10s | `gb.rate.external_commands_burst` (=3) | First 3 accepted; 4th–5th → `RATE_LIMITED` (no side effects) |
| 2 | 3 accepted Dampen | `gb.cap.actions_per_cycle` (=8) | 3 of 8 action budget consumed |
| 3 | 6× IMR Type B notify | `gb.rate.imr_notifications_per_cycle` (=4) | First 4 logged; 5th–6th → `IMR_NOTIFY_RATE_EXCEEDED` |
| 4 | 4 notifications evaluated | `gb.cap.imr_decisions_per_cycle` (=2) | 2 decisions; 2 → `GB_DEGRADE_DENY_IMR` |
| 5 | 9th action attempted | `gb.cap.actions_per_cycle` | P0/P1 retained; P6 deferred to `gb.cap.deferred_queue` |
| 6 | Cycle N+1 headroom | `gb.cap.defer_cycles` (=8) | Deferred P6 drains FIFO if within action cap |
| 7 | Cycle N+8, P6 still queued | `gb.cap.defer_cycles` | `DEFER_STARVATION_DENY`; audit + removal |
| 8 | Replay strip | `supervisory` + `semantic_core` | Identical rate rejects, cap denials, defer ordering; `routing_epoch_id` unchanged |

## Deterministic Violation Handling Summary

| Domain | Violation behavior |
|--------|-------------------|
| IPC width/size | Reject with fixed reason code |
| Queue depth | Deny, throttle, or drop-with-audit per policy |
| Cycle-time hard | Escalate L2/L1 |
| ΔH% hard | Safe-mode or emergency path |
| Memory bound | Bounded degrade; no silent truncation |
| Offload bound | Deny + CPU fallback check |
| GB cap exceed | Degrade mode per 20.16 §5 |
| GB rate exceed | `RATE_LIMITED`; no side effects; cap budget unaffected |
| IMR cap exceed | `IMR_CAP_EXCEEDED` + GB notify |
| Messy-input bound | Truncate with `truncated_fields[]`; preserve primary flags |
| `routing_epoch_advance` | Forbidden; conformance failure if non-zero |

## Conformance

Implementation conforms when:

- all listed bounds are enforced at runtime
- governance defaults match 20.16/20.80/20.45/20.17 unless signed override applies
- violation paths are deterministic and logged
- values remain synchronized with `policy_signature` and execution signature
- numeric storage follows 20.95 (Q32.32 / uint64; −0 normalized to +0)
- ΔH% limit checks use canonical Q32.32 before comparison
- GB TCU overrun applies 20.16 §5.4 TCU-first precedence
