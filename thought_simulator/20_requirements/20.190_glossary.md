# **Introduction**

## **Purpose**  
Please see [20.700_master_glossary.md](20.700_master_glossary.md), the 20.190 will not be supported going forward and be replaced by 20.700.

This glossary is the canonical reference for the refactored 20‑series and serves as the **Primitive Intent Catalog** for the Thought Simulator architecture. Its role is to define, with precision, what each component *owns*, when it executes, and what it is *not*, ensuring strict intent boundaries and preventing authority drift across modules. Normative high‑level requirements (HLRs) remain in the corresponding 20.xx modules; entries here are descriptive unless explicitly marked normative. Architectural context for runtime‑pipeline blocks (B0–B8) is provided in **20.01_architecture_map.md**.

---

## **How to Read This Catalog**  
Each entry follows a fixed seven‑field template to ensure clarity and architectural consistency:

| Field | Meaning |
|-------|---------|
| **Purpose** | Architectural role: what disappears or breaks if this component is removed |
| **Focus** | Operational ownership: the one‑sentence statement of what this component owns |
| **When** | Execution context: Path A, Path B, conversation layer, post‑TS, or pre‑A |
| **Why** | The specific architectural problem this component solves |
| **Is not** | Common confusions and explicit non‑ownership boundaries |
| **Example** | One concrete scenario illustrating correct behavior |
| **Normative home** | Authoritative 20.xx module defining requirements |

This structure ensures every entry is auditable, comparable, and aligned with the TS execution model.

---

## **Category Structure**  
All glossary entries fall into one of five architectural categories:

| Category | Suffix | Definition |
|----------|--------|------------|
| **1. Primitives** | ‑prm | TP‑holding, TP‑reading, TP‑modifying atomic operations in the TS pipeline |
| **2. Processes** | ‑prc | Pure logic executed *inside* primitives; do not hold or modify the TP |
| **3. Reference Objects** | ‑ref | Static data structures used by primitives and processes; never modify TP |
| **4. Governance** | ‑gov | Supervisory, safety, audit, and correction rules governing TS behavior |
| **5. TS‑Level Concepts** | ‑tsc | Conceptual logic layers (semantic, structural, routing, uncertainty) that do not appear as blocks in flows |

This categorization enforces architectural separation and prevents conceptual drift.

## **InB (Input Basin) — 20.100**  
**Purpose:** Deterministic, non‑inferential front door for all external signals; initializes all four Path A fields (surface, base, expression, intent) to default values without assigning meaning.  
**Focus:** Schema validation, surface canonicalization, FIFO preservation; sets token_base, token_expression, and token_intent to neutral defaults; no semantic, expressive, or pragmatic inference.  
**When:** Pipeline‑A entry, first deterministic stage after external input.  
**Why:** Normalize wire form and establish a clean four‑field starting point without guessing lexical identity, expressive metadata, or user intent.  
**Is not:** Semantic repair (IIInB); inquiry (IB); truth interpretation (TB); routing authority; any form of meaning construction.  
**Example:** "teh" → canonical token_surface; token_base=default; token_expression=default; token_intent=empty. "Yeah Baby!" → tagged for surface geometry only, not interpreted.  
**Normative home:** 20.100; messy‑input classes in 20.17.  
**Additional architectural role:** InB evaluates structural admissibility using its POS‑category dictionary and determines whether Path A proceeds via Clean Flow or Corrected Flow (IIInB engaged); meaning-layer fields remain uncommitted.

## **IIInB (Input Inference/Repair Basin) — 20.101**  
**Purpose:** Detect and propose bounded, user‑sanctioned shorthand expansions; initializes expression‑related proposals without modifying committed meaning-layer fields.  
**Focus:** Deterministic semantic‑shorthand repair proposals via USP rules; may propose updates to token_expression but does not commit surface, base, expression, or intent.  
**When:** Optional stage input_semantic_repair; ordering InB→IIInB→RB.  
**Why:** Identify user‑approved shorthand expansions and record proposed repairs while keeping all four fields in pre‑commit state.  
**Is not:** Interpretation; candidate generation; truth evaluation; meaning construction; commit point for any meaning-layer field.  
**Example:** USP proposes expanding "quicker‑ish"→"quicker" and records the proposal in the repair trace; token_surface/base/expression/intent remain uncommitted.  
**Normative home:** 20.101.  
**Additional architectural role:** IIInB produces a coherent set of repair proposals and associated trace entries; proposals may influence later expression refinement but are not applied or committed here.

## **IE (Intake Envelope, Structured Intake Object) — 20.109**  
**Purpose:** Apply and freeze the deterministic, bounded, replayable representation of user input; commit token_surface, token_base, and token_expression while leaving token_intent unassigned.  
**Focus:** Structured, normalized intake object incorporating applied USP repairs proposed by IIInB; produces the first committed meaning-layer envelope for Path A.  
**When:** Immediately after IIInB; before CEx.  
**Why:** Downstream components require a stable, globally coherent, replayable intake representation with committed surface/base/expression fields and empty intent.  
**Is not:** Semantic interpretation; candidate generator; truth evaluator; repair proposer; intent assigner.  
**Example:** IE applies all IIInB repair proposals in a single deterministic pass, commits token_surface/base/expression, and freezes the repaired intake; token_intent remains empty.  
**Normative home:** 20.109.  
**Additional architectural role:** IE is the commit point for surface/base/expression: it applies all proposed repairs, resolves ordering, and produces the final intake envelope handed to CEx with intent uncommitted.

## **CEx (ContextExtractor) - 20.107**  
**Purpose:** Produce a bounded, replayable context slice (CE) for ISc without exposing global state; may read all four meaning-layer fields but does not modify or commit any.  
**Focus:** Deterministic extraction of only the context‑relevant information from CIL needed for candidate generation and ISc scoring; preserves token_surface, token_base, token_expression, and token_intent exactly as committed upstream.  
**When:** Inference Path: IIInB → IE → CEx → CE → candidate_set{} → ISc.  
**Why:** ISc requires contextual information but cannot read CIL or any global state directly; CEx provides a safe, bounded intermediary while maintaining meaning-layer immutability.  
**Is not:** Semantic interpreter; meaning constructor; TP writer; global‑state reader; lineage exporter; field modifier.  
**Example:** Extract active referents, local discourse entities, and bounded conversation‑context cues from CIL to form CE; meaning-layer fields remain unchanged.  
**Normative home:** 20.107.  
**Note:** Primitive presently is a passthru; will be expanded in future revisions.

**When:** Produced immediately before ISc in the Inference Path.  
**Why:** Provide ISc with the minimal, safe context required for deterministic candidate generation and scoring while maintaining meaning-layer immutability.  
**Is not:** History; semantic object; TP writer; CIL proxy; lineage exporter; global‑state container; field modifier.  
**Example:** CE contains active referents, local discourse entities, and bounded commitment cues needed for candidate_set{} and ISc scoring; meaning-layer fields remain unchanged.

## **ISc (Inference Scorer) — 20.44**  
**Purpose:** Deterministically score interpretation candidates by applying truth_hypotheses‑prc over candidate_set{}, producing scoring fields for TPU without accessing global state; may read all four meaning-layer fields but does not modify or commit any.  
**Focus:** Read CE and candidate_set{}; apply truth_hypotheses‑prc; produce tp.score_set, tp.score_conflict, and tp.score_reason_code for inclusion in update_structure; preserves token_surface, token_base, token_expression, and token_intent exactly as committed upstream.  
**When:** Path‑A inference sequence: CE → candidate_set{} → ISc → TPU (Merge).  
**Why:** Provide deterministic, local scoring for routing and TPU commit while preventing global‑state leakage or unbounded inference; maintain meaning-layer immutability.  
**Is not:** Semantic generator; meaning constructor; truth evaluator; global inference engine; CIL reader; semantic repair mechanism; field modifier.  
**Example:** ISc scores referent candidates and produces a score_set consumed by TR‑prm during routing; meaning-layer fields remain unchanged.  
**Normative home:** 20.44.

## **TPU (Thought Packet Updater) — Path A Only**  
**Purpose:** Sole safe writer to TP for Path‑A correction; inserts and corrects message‑items, referents, constraints, and meaning-layer fields based on CE+CEx+ISc output; may write committed meaning-layer fields but never modifies token_surface, token_base, token_expression, or token_intent once SSR(t) is produced.  
**Focus:** Deterministic, boundary‑enforced TP updates; applies meaning-layer corrections derived from ISc scoring; preserves upstream commitments to token_surface, token_base, token_expression, and token_intent.  
**When:** Path‑A correction flow: CE → ISc → TPU → TP(N+1).  
**Why:** Enforce the single‑writer invariant for meaning construction and ensure all semantic updates are deterministic, auditable, and isolated from Path‑B; maintain meaning-layer immutability after commit boundaries.  
**Is not:** Topology engine; semantic interpreter; candidate generator; CIL reader; Path‑B primitive; meaning constructor for expression; field modifier for committed meaning-layer fields.  
**Example:** ISc selects a corrected referent or message‑item; TPU applies the update to TP(N), producing TP(N+1) under a new commit_id; meaning-layer fields remain exactly as committed by IE and IdOB.  
**Scope invariant:** TPU‑prm MUST NOT be invoked by Path‑B; Path‑B is meaning‑read‑only.  
**Normative home:** 20.46.

## **SOB (Structural OB) — 20.40.010**  
**Purpose:** Extract first‑pass structural cues from TP content, producing the base structural residue consumed by downstream OB layers and routing; may read all four meaning-layer fields but does not modify or commit any.  
**Focus:** Clause boundaries, syntactic shape, punctuation/symbol masks, negation markers, modality markers, structural anchors, and structural tags; uses token_surface, token_base, and token_expression for structural detection while leaving token_intent unchanged.  
**When:** First OB stage in Path‑A whenever structural pattern detection is required.  
**Why:** Provide deterministic low‑level structural residue enabling refinement, constraint extraction, and TR‑input formation while maintaining meaning-layer immutability.  
**Is not:** Semantic interpreter; constraint resolver; truth evaluator; geometric/meta‑basin; field modifier.  
**Example:** SOB identifies clause boundaries and structural markers, emitting the initial residue fragment for refinement; meaning-layer fields remain unchanged.  
**Normative home:** 20.40.010.

## **SmOB (Semantic OB) — 20.40.040**  
**Purpose:** Perform two jobs: (1) extract pre‑semantic and semantic‑adjacent cues from SOB→SROB→CnOB residue, and (2) compress all upstream residue plus SmOB cues into a deterministic pre‑semantic hash and TR‑input cue vector; may read all four meaning-layer fields but does not modify or commit any.  
**Focus:** (Job 1) semantic‑adjacent pattern activation, modality/affect cues, conflict‑adjacent and underspecification‑adjacent signals; (Job 2) deterministic pre‑semantic residue hashing and TR‑input cue formation for routing; uses token_surface, token_base, and token_expression for cue extraction while leaving token_intent unchanged.  
**When:** Invoked after CnOB when semantic‑adjacent cues, pre‑semantic residue, or deterministic routing representation are required for SSG or downstream interpretation.  
**Why:** Job 1 adds pre‑semantic cues supporting IdOB selection, ΔH% attribution, and semantic‑layer preparation; Job 2 provides a canonical, replay‑safe compressed representation enabling deterministic TR routing and SSG signal generation while maintaining meaning-layer immutability.  
**Is not:** Semantic interpreter; truth evaluator; stance assigner; geometric meta‑basin; semantic normalizer; field modifier.  
**Example:** SmOB extracts semantic‑adjacent cues (Job 1) and compresses upstream residue plus its own cues into a deterministic hash and TR‑input cue vector consumed by SSG and the Thought Router to derive TP.TR; meaning-layer fields remain unchanged.  
**Normative home:** 20.40.040.

## **SSG (Structural Signature Generator) — 20.47**  
**Purpose:** Convert SmOB structural output into a deterministic, fixed‑length structural signature vector for routing and similarity operations; may read all four meaning-layer fields but does not modify or commit any.

**When:** Mandatory stage structural_signature_generation; ordering SmOB → SSG → RB.  
**Why:** Provide RB with a geometry‑ready, token‑free, replay‑stable coordinate chart enabling structural proximity, lane selection, and routing decisions while maintaining meaning-layer immutability.  
**Is not:** Semantic embedding; tokenization; meaning construction; interpretation; hashing of semantic content; candidate generator; field modifier.  
**Example:** A SmOB graph with high branching depth and low curvature yields a signature emphasizing depth‑dominant structural geometry; meaning-layer fields remain unchanged.  
**Normative home:** 20.47.

## **STPX (Structured Token & Pattern Extractor) — 20.49**

**Why:** Provide ISc, RB, and IdOB with a replay‑stable, non‑semantic signal layer that enhances entropy scoring, routing stability, and identity refinement while maintaining meaning-layer immutability.  
**Is not:** Semantic interpretation; identity resolution; routing; entropy scoring; meaning refinement; modification of TPU or semantic fields; Path‑B signalization; field modifier.  
**Example:** A cleaned token stream containing “but” and a clause boundary yields lexical and structural cues indicating contrastive shift and multi‑clause structure; meaning-layer fields remain unchanged.

### **RBU‑prm (Routing Buffer Update Primitive)**  
**Purpose:** Enrich the TP with subculture, identity, register, and interpretive metadata required for RB‑prm to perform correct routing; may read all four meaning-layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent.  
**Focus:** Deterministically writes interpretive metadata (culture, subculture, register, stance‑relevant cues) into the TP snapshot before routing occurs; preserves all meaning-layer fields exactly as committed upstream.  
**When:** Invoked **before RB‑prm**, ensuring RB‑prm receives a fully enriched TP.  
**Why:** Maintain architectural purity by separating interpretive metadata enrichment (RBU‑prm) from routing computation (RB‑prm) while maintaining meaning-layer immutability.  
**Is not:** A router, classifier, scorer, or semantic evaluator; does **not** compute routing deltas; does **not** modify any meaning-layer field.  
**Example:** RBU‑prm writes subculture and identity metadata into the TP; RB‑prm then uses this metadata to select the correct manifold chart and routing lane; meaning-layer fields remain unchanged.  
**Normative home:** 20.51.

## **RTU‑prm (Routing TP Update Primitive) — 20.30.005**  
**Purpose:** Commit RB‑prm’s routing metadata into the TP snapshot, including culture/subculture lanes, fallback lane, routing lineage, routing reasons, fan‑out decisions, and routing‑relevant structural fields; may read all four meaning-layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent.  
**Focus:** Pure deterministic write‑back of RB‑prm output; validate the routing envelope; ensure RB‑prm remains pure and side‑effect‑free; embed routing state for TS/TR scheduling and staleness evaluation; preserves all meaning-layer fields exactly as committed upstream.  
**When:** Invoked immediately after RB‑prm and before TS schedules the next IdOB‑chain; runs once per routing cycle and is never re‑invoked for the same RB output.  
**Why:** Separate routing computation (RB‑prm) from routing commit (RTU‑prm); provide TS/TR with a stable, auditable routing state; ensure replay equivalence and multi‑cycle determinism while maintaining meaning-layer immutability.  
**Is not:** Router; classifier; interpreter; scorer; semantic evaluator; modifier of OB outputs, semantic fields, truth fields, merge results, or completion data; field modifier for committed meaning-layer fields.  
**Example:** RB‑prm selects culture and fallback lanes; RTU‑prm validates the routing envelope and writes lane‑selection fields, routing lineage, and routing reasons into the TP snapshot for TS/TR; meaning-layer fields remain unchanged.  
**Normative home:** 20.30.005.

## **RB (Relational Basin) — 20.50**  
**Purpose:** Perform deterministic routing arbitration in Path‑A, selecting the next IdOB based on structural residue, ΔH%, lineage, and TR‑input fields, without accessing any Path‑B structures; may read all four meaning-layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent.  
**Focus:** Deterministic evaluation of routing metadata and relational cues to choose the next IdOB in the meaning‑construction cycle; RB selects the basin but does not move the TP; preserves all meaning-layer fields exactly as committed upstream.  
**When:** Invoked during Path‑A routing after OB and TR evaluation; runs in the RB→RTU→IdOB loop until Truth/Done stabilizes the turn‑final TP.  
**Why:** Provide governed, replay‑safe routing decisions that maintain A‑side determinism and enforce the A/B separation required by 20.705 while maintaining meaning-layer immutability.  
**Is not:** SRP; TrigRB; TR; geometric projector; transport mechanism; Path‑B computation; reader of B‑side routing tables or MTP; field modifier.  
**Example:** RB evaluates residue and ΔH% changes, determines that structural cues require re‑entering CnOB, and selects CnOB as the next basin for OBA‑prm execution; meaning-layer fields remain unchanged.  
**Normative home:** 20.50.

## **TrSch‑prm (Turn Scheduler Primitive) — 20.155_prm**  
**Purpose:** Coordinate and sequence all Path‑A primitives by interpreting the consolidated IdOB‑output packet produced by CTP‑prm and selecting the next architectural action; may read all four meaning‑layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent.  
**Focus:** Deterministic interpretation of IdOB‑prm’s control flags (`continue`, `needs_correction`, `done`, `unstable`, `halt`, `retry`, etc.) and selection of the next primitive in the Path‑A pipeline; preserves all meaning‑layer fields exactly as committed upstream.  
**When:** Invoked immediately after CTP‑prm consolidates the outputs of an IdOB‑set; runs once per IdOB‑set cycle; the sole primitive allowed to decide whether the next step is RB‑prm, CE‑prm, OuBA‑prm, or Truth/Done.  
**Why:** Maintain architectural purity by separating meaning refinement (IdOB‑prm), routing computation (RB‑prm), routing commit (RTU‑prm), correction (CE‑prm → TPU‑prm), and commit (OuBA‑prm); enforce deterministic, replay‑safe turn sequencing and A/B separation while maintaining meaning‑layer immutability.  
**Is not:** Router; classifier; scorer; semantic evaluator; meaning‑refinement primitive; routing‑refinement primitive; TP writer; semantic_core writer; correction engine; governance step; truth evaluator; ΔH% contributor; merge engine; field modifier.  
**Example:** CTP‑prm consolidates IdOB₁…IdOBₙ into a single packet; TrSch‑prm reads the control flags and schedules another RB‑prm → RTU‑prm → IdOB‑prm cycle if meaning is unstable; schedules CE‑prm → TPU‑prm when `needs_correction` is set; schedules OuBA‑prm when `done` is set; meaning‑layer fields remain unchanged.  
**Normative home:** 20.155_trsch_prm.md.

## **IdOB (Identity Object Basin) — 20.40.050**

**Why:** Provide deterministic, replay‑safe identity‑specific refinement isolated from structural, routing, and truth‑evaluation responsibilities while maintaining meaning‑layer immutability outside TPU commit boundaries.  
**Is not:** OB primitive; structural classifier; constraint extractor; routing arbiter; truth evaluator; ΔH% contributor; Path‑B computation; writer of TP.TR or routing_metadata; field modifier for committed meaning‑layer fields.  
**Example:** After RB routes a TP to a domain‑specific identity basin (e.g., mathematical, narrative, operator), IdOB applies identity‑conditioned rules and updates the TP via TPU.idob_update; meaning‑layer fields remain unchanged except through deterministic TPU commits.  
**Normative home:** 20.40.050.

## **CTP‑prm (Collect/Consolidate Thought Point) — 20.145_prm**  
**Purpose:** Collect all IdOB‑outputs from an IdOB‑set into a single stable IdOB‑output packet for RB arbitration; may read all four meaning‑layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent.

**When:** After an IdOB‑set completes and before RB arbitration; in multi‑core systems runs only after all parallel IdOB‑prm instances finish and their outputs are available for consolidation.  
**Why:** Ensure all legitimate IdOB‑outputs are available as one deterministic, replay‑safe packet for routing in both serial and parallel execution; maintain meaning‑layer immutability and uphold the single‑writer invariant.  
**Is not:** Meaning constructor; merge engine; scorer; TP writer; governance step; field modifier. 
**Example:** Single‑core: InB → OB0 → RB → OB1…OBn → CTP → RB. Multi‑core: InB → OB0 → RB → {OB1 ∥ OB2 … ∥ OBn} → CTP → RB; meaning‑layer fields remain unchanged.

## **OuBA (Output Basin — Path A Commit) — 20.40.060**  
**Purpose:** Commit the finalized Path‑A meaning state into an immutable semantic snapshot (semantic_core and meaning‑bearing fields) for DF intake (IB → TB → GBIB → GB); may read all four meaning‑layer fields but does not modify or commit token_surface, token_base, token_expression, or token_intent except at the commit boundary.  
**Focus:** Freeze the meaning‑layer state and write commit‑time metadata, resolution flags, and DF‑readiness indicators; performs no semantic correction, truth evaluation, routing, or governance decisions; preserves all meaning‑layer fields exactly as stabilized by Path‑A.  
**When:** Runs once per Path‑A cycle after meaning construction and completion evaluation stabilize; executes immediately before DF ingress and never during Path‑B realization.  
**Why:** Provide a deterministic, replay‑safe termination point for Path‑A, ensuring DF operates only on committed meaning and never on in‑flight structures; uphold the single‑writer invariant and meaning‑layer immutability outside the commit boundary.  
**Is not:** Governance primitive; truth evaluator; semantic repair engine; routing arbiter; generator of inquiry/truth states; producer of governance directives; OuBA never modifies semantic_core after commit or invokes IB/TB/GBIB/GB; not a field modifier outside the commit boundary.  
**Example:** After Path‑A meaning construction stabilizes, OuBA freezes semantic_core and commit‑time metadata into a committed TP snapshot consumed by DF beginning at IB; meaning‑layer fields remain unchanged after commit.  
**Normative home:** 20.40.060; 20.705 (DF ingress); 20.90 (IB); 20.60 (TB); 20.80 (GB).

## **XlateR — Translation Routine — 20.43**  
**Purpose:** Maps the frozen semantic snapshot produced by Path‑A into an OuBB‑ready expression plan, providing the final mapping step in the OpBeh → OBG → XlateR execution chain.  
**Focus:** Reads only frozen semantic_core fields listed in its mapping profile, applies deterministic template selection, and produces an `expression_plan_ref` that OuBB will later render into surface text.

# **4. Governance Rules**

## **Clarification Rules — Governance Block**  
**Purpose:** Determines when the system may issue a clarification request instead of producing a direct answer, ensuring ambiguity is resolved only when permitted by governance policy.  
**Focus:** Clarification allowed only when ambiguity is material, user‑intent cannot be safely inferred, and governance permits inquiry; suppressed when meaning is sufficiently determinate or when clarification would violate USP or safety constraints.  
**When:** Evaluated during TB→IB→GBIB→GB after Path B realization and before any clarification is emitted.  
**Why:** Prevents unnecessary or unsafe clarifications and ensures all clarifications are governance‑authorized.  
**Is not:** A semantic primitive; a meaning writer; an IMR mechanism; an automatic IB trigger.  
**Example:** IB proposes `ask_for_antecedent`; GBIB validates under USP; GB authorizes or suppresses the clarification.  
**Normative home:** 20.80.

---

## **Suppression Rules — Governance Block**  
**Purpose:** Enforces conditions under which clarification, interrogation, or inference proposals must be suppressed to maintain safety, truth integrity, and user‑intent fidelity.  
**Focus:** Suppression triggered when proposals violate USP, conflict with truth/safety tags, exceed allowed inquiry depth, or would cause user‑intent distortion.  
**When:** Applied in GBIB and finalized in GB during governance evaluation.  
**Why:** Ensures the system does not escalate inquiry or inference beyond what governance permits.  
**Is not:** A routing rule; a Path A/B primitive; an IMR mismatch classification.  
**Example:** IB proposes a follow‑up question; GBIB suppresses it because USP forbids interrogative expansion in the current context.  
**Normative home:** 20.80.

---

## **Truth–Safety Precedence Rules — Governance Block**  
**Purpose:** Establishes deterministic precedence between truth‑evaluation outcomes and safety‑evaluation outcomes when they conflict.  
**Focus:** Safety overrides truth when user harm or policy violation is possible; truth overrides ambiguity when meaning is determinate and safe; both feed into GB for final governance outcome.  
**When:** Evaluated in GBIB and GB after TB and TPSF/TPTB signals are available.  
**Why:** Ensures safe, truthful, policy‑aligned behavior under conflict conditions.  
**Is not:** A semantic inference rule; a TP writer; a Path A/B primitive.  
**Example:** A truthful answer is available but unsafe; safety precedence suppresses direct expression and GB authorizes a safer alternative.  
**Normative home:** 20.80.

---

## **USP Precedence Rules — Governance Block**  
**Purpose:** Ensures that User‑Specified Preferences (USP) constrain governance decisions without overriding safety or truth requirements.  
**Focus:** USP applied after safety and truth evaluation but before final governance outcome; USP may suppress or permit clarifications, tone, or style choices.  
**When:** Applied in GBIB and finalized in GB.  
**Why:** Ensures user preferences shape expression while remaining subordinate to safety and truth.  
**Is not:** A safety override; a truth override; a meaning‑layer inference.  
**Example:** User prefers no clarifications; USP suppresses IB proposals unless safety requires them.  
**Normative home:** 20.80.

---

## **Governance Outcome Rules — Governance Block**  
**Purpose:** Defines how GB produces the final `governance_outcome{}` that controls whether the system answers, clarifies, suppresses, or redirects.  
**Focus:** GB integrates TB truth‑state, IB ambiguity proposals, GBIB governance filters, USP, TPTB, TPSF, and safety constraints to produce a single deterministic outcome.  
**When:** Final step of the Post‑TS governance chain before output is emitted.  
**Why:** Ensures all outputs are policy‑aligned, safe, truthful, and consistent with user intent.  
**Is not:** A meaning writer; a realization primitive; a neural inference.  
**Example:** GB authorizes `issue_clarification`, `answer_directly`, or `suppress_and_redirect` based on combined governance signals.  
**Normative home:** 20.80.

---

## Replay‑Determinism Rules — Governance Block
**Purpose:** Ensure governance outcomes are fully deterministic and replay‑safe given identical TP/MTP commits and identical seeds.  
**Focus:** Deterministic governance evaluation across TB→IB→GBIB→GB; nondeterminism confined to Path‑B expression under the Random Seed Boundary.  
**When:** Applied throughout DF and enforced before output emission.  
**Why:** Guarantee auditability, reproducibility, and compliance with TS determinism requirements.  
**Is not:** Randomness generator; meaning writer; Path‑A/B primitive.  
**Example:** Replaying the same TP/MTP commit with the same seed yields identical governance outcomes and identical surface‑form output.  
**Normative home:** 20.80, 20.207.

# 5. TS-Level Concepts

---

## ΔH% (DeltaHPercent) — 20.30
**Purpose:** Represent the incremental structural‑uncertainty contribution produced by each Path‑A interpretive stage (OB, merge, truth‑hypotheses evaluation), ensuring uncertainty evolution is deterministic, auditable, and replay‑safe.  
**Focus:** Encode local uncertainty adjustments from structural gaps, unresolved branches, missing‑mass indicators, and interpretive signals; contribute to the deterministic computation of H%.  
**When:** Generated at each Path‑A interpretive step and accumulated before truth/completion evaluation; included in the update_structure validated and committed by RBU.  
**Why:** Provide a deterministic, non‑probabilistic mechanism for tracking uncertainty evolution without latent‑space inference or stochastic estimation.  
**Is not:** Probability; confidence score; truth commitment; entropy functional; Path‑B computation.  
**Example:** Merge detects unresolved semantic branches and increases ΔH%; truth‑hypotheses evaluation stabilizes a hypothesis and decreases ΔH%, lowering H% in the next cycle.  
**Normative home:** 20.30.030, 20.30.060.

---

## **FFTM (Four‑Field Token Model) — 20.31**
**Purpose:** Canonical Path‑A meaning representation; the minimal deterministic token‑level structure required for meaning construction before any basin, routing, behavior, or expression mapping occurs.  
**Focus:** Owns the four token meaning fields (token_surface, token_base, token_expression, token_intent) and guarantees lane‑local, non‑inferential meaning formation.  
**When:** Executes strictly in Path‑A during meaning construction, before semantic_core aggregation and before any basin or Path‑B primitive.  
**Why:** Provides a stable, sufficient, and deterministic foundation for meaning; prevents premature inference, cross‑token contamination, and meaning collapse; ensures Path‑A meaning is structurally complete prior to downstream processing.  
**Is not:** Not a basin; not a routing primitive; not a behavior selector; not an expression mapper; does not read or write SSR; does not perform inference; does not modify semantic_core; not part of Path‑B.  
**Example:** The token “run” is represented as FFTM: token_surface=“run”, token_base=lemma(run), token_expression=verb/action frame, token_intent=neutral‑directive; these four fields form the atomic unit later aggregated into semantic_core.  
**Normative home:** 20.31_patha_meaning_spec.md.

---

## H% (UncertaintyPercent) — 20.30
**Purpose:** Represent the accumulated structural‑uncertainty state of the TP/MTP after integrating ΔH% contributions across Path‑A interpretive stages.  
**Focus:** Encode the current structural‑uncertainty level derived from unresolved branches, structural gaps, and interpretive signals; used by truth‑hypotheses and completion evaluation to determine stability and readiness for commit.  
**When:** Updated during Path‑A after merge and truth‑hypotheses evaluation; included in the update_structure validated and committed by RBU.  
**Why:** Provide a deterministic, replay‑safe uncertainty measure that cleanly separates structural uncertainty from truth evaluation, confidence, or probabilistic reasoning.  
**Is not:** Probability; confidence score; truth band; global uncertainty model; Path‑B computation.  
**Example:** If ΔH% accumulates due to unresolved semantic branches, H% increases; if truth‑hypotheses evaluation stabilizes a hypothesis, H% decreases, signaling readiness for completion.  
**Normative home:** 20.30.060, 20.30.070.

---

## **Grounding Entropy (H\_{Kn_{coarse}}, H\_{Kn_{medium}}, H\_{Kn_{fine}})**  
**Purpose:** Quantify grounding certainty at each abstraction tier (coarse, medium, fine) during KnB processing; provide Path‑B with deterministic entropy signals for tier selection, expression safety, and surgical‑question triggers.  
**Focus:** Measure precision of grounded knowledge relative to maximum attainable precision; reflect ambiguity, contextual stability, and domain‑specific resolution; expose entropy values as explicit SSR fields for downstream routing and realization.  
**When:** Computed during each grounding stage: KnC computes $H\_{Kn_{coarse}}$ after coarse grounding; KnM computes $H\_{Kn_{medium}}$ after medium grounding; KnF computes $H\_{Kn_{fine}}$ after fine grounding; all values are written into SSR before Path‑B executes.  
**Why:** Enable TS to select the correct abstraction tier without inference or probabilistic reasoning; ensure deterministic behavior by making uncertainty explicit and measurable; prevent Path‑B from expressing overly precise meaning when grounding entropy is high.  
**Is not:** A truth metric; semantic confidence score; probabilistic estimate; grounding entropy never performs inference, semantic repair, or truth evaluation and never modifies grounded fields.  
**Example:** KnC attaches coarse identity (“dog”) and computes $H\_{Kn_{coarse}}$; KnM refines identity (“retriever”) and computes $H\_{Kn_{medium}}$; KnF resolves identity (“Golden Retriever”) and computes $H\_{Kn_{fine}}$, allowing Path‑B to select coarse/medium/fine expression based on total entropy $H_{total} = H_{SSR} + H\_{Kn_{tier}}$.  
**Normative home:** 20.48.010–030 (KnC/KnM/KnF); 20.52 (SSR); 20.705 (Path‑A → KnB → Path‑B flow); ts_numeric_policy.md (entropy definitions).

## OB (Object Basin) — 20.40
**Purpose:** Defines the generic class of Path‑A object‑basin primitives (SOB, SROB, CnOB, SmOB, IdOB) that classify structure, extract constraints, and emit residue and TR‑input cues for routing.  
**Focus:** Encodes structural, constraint, and pattern signatures from lane‑local TP views; produces residue fragments, ΔH% contributions, and TR‑input fields without performing semantic interpretation or truth evaluation.  
**When:** Invoked during Path‑A meaning construction prior to routing; activated deterministically based on lane‑local TP structure, routing context, and orthogonality_signature; contributes evidence and residue before TR and RB execution.  
**Why:** Provides deterministic, replay‑safe structural interpretation that grounds routing, ΔH% evolution, and downstream meaning construction without semantic inference or identity‑conditioned processing.  
**Is not:** A semantic basin; a truth evaluator; a routing arbiter; a geometric meta‑basin; an identity‑conditioned primitive; a Path‑B computation; a generator of TP.TR or truth_hypotheses.  
**Example:** SOB/SROB/CnOB extract structural and constraint residue; SmOB emits pre‑semantic residue; OB sets `tr_needs_update` when structural cues change, enabling TR to recompute routing.  
**Normative home:** 20.40 (parent‑level OB requirements).

## TCU (Thought Compute Unit) — 20.30
**Purpose:** Normalizes compute cost reporting per primitive so that deterministic cost envelopes can be enforced and compared across the architecture.
**Focus:** Normalized compute-cost unit reported per tick / per primitive.
**When:** Reported per tick / per primitive.
**Why:** Deterministic cost envelopes; comparable cost reporting across primitives.
**Is not:** Wall-clock time; token count.
**Example:** OpBeh vs OuB cost recorded separately.
**Normative home:** 20.30.

## Messy-Input Taxonomy (MI_*) — 20.17
**Purpose:** Classifies all malformed or ambiguous input conditions so that routing, repair, and escalation decisions are made deterministically rather than ad hoc.
**Focus:** Structured classification of problematic input conditions with deterministic downstream routing implications.
**When:** Applied at InB / IIInB during input canonicalization.
**Why:** Prevent ad hoc handling of malformed input; ensure deterministic routing per class.
**Is not:** Semantic interpretation; truth evaluation; a repair mechanism.

| `MI_VAGUE` | Underspecified referents | "Make it better" |

## MCS (Meaningful Cognitive Step) — 20.30.040
**Purpose:** Defines the atomic, auditable unit of cognitive work in TS, enabling deterministic accounting of interpretive, structural, and evaluative operations across Path A.
**Focus:** Counts only meaningful, user‑relevant cognitive transformations (OB/TB interpretation, merge decisions, truth‑hypothesis evaluation, completion evaluation, routing decisions) while excluding zero‑cost metadata updates and mechanical bookkeeping.
**When:** Incremented during Path A whenever TS performs a qualifying interpretive or evaluative action; never incremented during Path B or for non‑cognitive operations.
**Why:** Ensures TS reasoning is measurable, bounded, replay‑safe, and free of hidden computation; provides a stable basis for invariants, performance guarantees, and correctness proofs.
**Is not:** A token count; a FLOP measure; a latency metric; a routing hop; a metadata write; a safety or truth tag; a Path B operation.
**Example:** OB interpretation that resolves a referent counts as an MCS; writing TPTB or TPSF does not; updating lane lineage does not; merge reconciliation of conflicting semantic cores does.
**Normative home:** 20.30.040.

## semantic_core — 20.30
**Purpose:** Represent the immutable, governance‑ready semantic snapshot produced at commit, capturing the finalized meaning of the turn for archival, replay, and downstream governance evaluation.  
**Focus:** Encodes the committed meaning‑bearing structures (propositions, roles, referents, frames, relations) extracted from the finalized TP(N) at commit; serves as the stable substrate for DF‑side truth, governance, and historical replay.  
**When:** Created exactly once per turn by OuBA at commit; never exists during Path‑A construction or Path‑B realization.  
**Why:** Provide a deterministic, replay‑safe semantic substrate that isolates meaning construction (Path‑A) and realization (Path‑B) from governance, archival, and historical evaluation.  
**Is not:** Path‑A structure; routing structure; safety model; truth‑metadata object; latent embedding; Path‑B construct; stylistic or expressive representation.  
**Example:** OuBA freezes the finalized TP(N) into semantic_core, which DF then uses for truth evaluation (TB), governance integration (GBIB), and governance decision (GB).  
**Normative home:** 20.30.010, 20.30.050.

---

## update_structure — 20.30
**Purpose:** Represent the deterministic, fully‑specified envelope of all Path‑A outputs (truth_hypotheses, TPTB, TPSF, ΔH%, H%, merge_result, routing metadata) that RBU validates before commit.  
**Focus:** Encode the complete, replay‑safe Path‑A state transition, including structural updates, metadata fields, and commit‑relevant deltas; ensure no implicit or hidden computation occurs during RBU validation.  
**When:** Constructed after merge, truth‑hypotheses evaluation, completion evaluation, and uncertainty updates; passed to RBU as the authoritative input for validation.  
**Why:** Provide a single, auditable, deterministic object capturing the entire Path‑A evolution of the TP, enabling RBU to validate commit‑readiness without re‑running computation.  
**Is not:** semantic_core; semantic object; truth model; routing decision; latent representation; Path‑B construct; partial update; incremental diff.  
**Example:** After merge produces merge_result and truth‑hypotheses evaluation produces TPTB/TPSF, update_structure aggregates truth_hypotheses, TPTB, TPSF, ΔH%, H%, merge_result, and routing metadata into a single validation envelope for RBU.  
**Normative home:** 20.30.070.

## merge_result — 20.30
**Purpose:** Represents the deterministic, lane‑reconciled semantic output produced by merge after integrating multiple lane‑local semantic_cores, truth hypotheses, and structural signals.
**Focus:** Encodes the unified semantic structure (propositions, roles, referents, frames, relations) plus merge‑level decisions (conflict resolution, branch selection, structural reconciliation) that feed truth and completion evaluation.
**When:** Produced after OB/TB interpretation and before truth/completion evaluation; included in update_structure and validated by RBU during commit.
**Why:** Provides a single, authoritative semantic representation for downstream evaluation, ensuring deterministic reasoning and preventing lane‑specific divergence from leaking into commit.
**Is not:** A truth‑metadata object; a routing decision; a latent embedding; a Path B construct; a stylistic or expressive representation.
**Example:** Multiple lane‑local semantic_cores propose different referent bindings; merge_result reconciles them into a single referent structure used by truth evaluation.
**Normative home:** 20.30.050.

## **TP.TR — semantic‑routing fields**  
**Purpose:** Structured semantic‑routing state used by TR‑prm, RB‑prm, and SSG for staleness evaluation, semantic‑transition eligibility, and routing‑vector construction.  
**Focus:** Tracks semantic‑adjacent routing metadata (stance, intent, affect, epistemic shading, tension, politeness, commitment, reservation, logical structure, semantic‑deltaH, lineage additions, routing semantics). Contains routing‑relevant semantics, not meaning.  
**When:** Updated only when `tr_needs_update = true` under the TR‑gating contract.  
**Why:** Maintain deterministic, auditable semantic‑routing behavior across cycles; ensure semantic transitions occur only under explicit architectural conditions.  
**Is not:** A meaning field, truth field, stance interpreter, classifier, or semantic evaluator; does not contain semantic content, only semantic‑routing metadata.  
**Example:** TR‑prm updates stance and commitment fields after a semantic‑routing change; RB‑prm reads the updated TP.TR to determine semantic‑transition eligibility.  
**Normative home:** 20.30 (TP Message Contract), 20.40.040 (SmOB), 20.47 (SSG), 20.50 (RB), 20.10 (TR‑gating).

## DF — Inquiry‑side evaluation flow
**Purpose:** Perform governance‑side evaluation of committed meaning produced by OuBA, determining inquiry, truth, and governance outcomes for the turn.  
**Focus:** Process committed semantic_core snapshots through IB, TB, and GBIB into GB for inquiry evaluation, truth assessment, supervisory integration, and promotion or governance‑side routing decisions.  
**When:** Invoked only after Path‑A commits meaning via OuBA; operates exclusively on committed, immutable meaning.  
**Why:** Maintain deterministic, auditable governance evaluation; ensure inquiry, truth, and supervisory decisions occur only on committed meaning under explicit architectural conditions.  
**Is not:** Meaning‑construction flow; semantic writer; Path‑A participant; DF never modifies semantic_core, truth relations, or any Path‑A structure.  
**Example:** OuBA commits meaning; IB evaluates inquiry structure; TB evaluates truth; GBIB integrates supervisory context; GB logs governance events and either promotes to IdOB or emits governance inference to REx.  
**Normative home:** 20.705 (TS Flow Diagrams), 20.90 (IB), 20.80 (GB), 20.40.060 (OuBA), 20.110 (OuBB).

## HCF — Historical Conversation Flow
**Purpose:** Provide TS and Path‑B with long‑horizon conversational perspective by transforming turn‑final TP snapshots (committed by OuBB) into structured conversation‑level continuity and inference.  
**Focus:** Process historical TP sequences through MTP, COB, and CIL to derive conversation objects, referential history, topic threads, and long‑range conversational inference; outputs are consumed by CoHI and reinjected into Path‑B as continuity‑relevant structure.  
**When:** Invoked after Path‑B completes a turn and OuBB finalizes the turn‑final TP. Operates as a slow‑reader subsystem independent of real‑time execution, maintaining its own historical loop (MTP → COB → CIL) while exchanging information with Path‑B through CoHI.  
**Why:** Maintain deterministic, auditable long‑term conversational context; ensure continuity, referential stability, and multi‑turn inference derive only from committed TP history; provide Path‑B with structured, policy‑safe continuity without requiring Path‑B primitives to read or manipulate historical memory directly.  
**Is not:** Meaning‑construction flow; truth evaluator; governance subsystem; HCF does not modify TP, semantic_core, or Path‑A state; does not participate in real‑time realization.  
**Example:** OuBB commits a turn‑final TP; HCF ingests it and updates MTP; COB constructs or updates conversation objects; CIL derives long‑horizon inference; CoHI merges these historical structures with the next turn’s Path‑B TP to provide continuity‑aware realization.  
**Normative home:** 20.705 (TS Flow Diagrams), 20.190 (Glossary), 20.110 (OuBB), 20.113 (CoHI), 20.112 (COB), 20.114 (CIL).

## RSG Manifold — Expression Manifold Mapping Layer
**Purpose:** Provide TS with a geometric intermediate representation by projecting atomic SSR fields into an n‑dimensional expression manifold, enabling deterministic collapse and pattern selection for surface‑form realization.  
**Focus:** Convert SSR fields (identity, relation, domain, qualifier, time, truth/safety, tone, continuity) into manifold coordinates using projection operators; apply priority gradients (truth > safety > clarity > brevity > tone > continuity) to collapse the manifold to a single realizable point; output the selected manifold address for RSG pattern lookup.  
**When:** Invoked after Path‑A and Path‑B produce finalized SSR; operates during RSG’s forward‑projection and gradient‑collapse phases before table-driven realization; participates only in meaning-to-geometry mapping, not in TP extraction or grounding.  
**Why:** Ensure deterministic, bounded, non-generative translation from SSR to surface form; enforce truth/safety dominance through geometric constraint surfaces; provide a structured IR that supports reproducible realization and eliminates stochastic behavior; guarantee that RSG selects only pre-defined patterns from the offline table.  
**Is not:** A generative model; semantic inference engine; grammar constructor; RSG Manifold does not synthesize language, modify SSR, alter grounding metadata, or participate in TP formation; it is not a runtime memory system or historical continuity mechanism.  
**Example:** SSR contains identity=User, relation=Location, domain=Current, qualifier=Immediate; projection operators map fields to manifold coordinates; gradients collapse the manifold to a direct declarative region; RSG selects the corresponding table entry and realizes “You are here now.”  
**Normative home:** 20.30.085 (RSG Primitive), 20.30.090 (RSG Mapping Rules), 20.705 (TS Flow Diagrams), [why_ts_uses_manifold_model.md](system_playground/why_ts_uses_manifold_model.md)
