## Purpose

Canonical glossary and **Primitive Intent Catalog** for the refactored 20-series.  
This document is the **intent enforcement layer**: it defines what each component owns, when it runs, and what it is *not* — to prevent authority drift across modules.

Normative HLRs remain in linked 20.xx modules; entries here are descriptive unless explicitly marked otherwise.

**Directory layout:** Runtime-pipeline concept blocks (B0–B8) → 20.01_architecture_map.md.

---

## How to Read This Catalog

Each entry uses a fixed seven-field template:

| Field | Meaning |
|-------|---------|
| **Purpose** | Architectural role: what would be absent without this entry |
| **Focus** | Operational ownership: what this component owns in one sentence |
| **When** | Pipeline A / B / conversation layer / post-TS / pre-A |
| **Why** | The specific problem this entry solves |
| **Is not** | Common confusions (1–3) |
| **Example** | One concrete scenario |
| **Normative home** | Authoritative 20.xx module |

---

## Category Structure

| Category | Suffix | Definition |
|----------|----------|----------|
| **1. Primitives** | -prm | A primitive is a TP‑holding, TP‑reading, and TP‑capable‑of‑modifying atomic operation in the TS pipeline. |
| **2. Processes** | -prc | A process is a pure logic operation (TS‑Level Concept executor) that does not hold or modify the TP. It is executed inside a primitive. |
| **3. Reference Objects** | -ref | Reference objects are data structures used by primitives and processes. They do not hold or modify the TP |
| **4. Governance** | -gov | Audit, correction, safety, and supervisory mechanisms |
| **5. TS-Level Concepts** | -tsc | TS‑Level Concepts are semantic logic layers (meaning inference, scoring logic, routing logic, etc.). They are not blocks and do not appear in flows |

## **6. Flow Diagram Rules**

### **Primitive Flow (TP pipeline)**  
Only primitives appear:

```
PrimitiveA-prm → PrimitiveB-prm → PrimitiveC-prm
```

### **Process Flow (conceptual)**  
Must be labeled and must suffix categories:

```
Process Flow:
PrimitiveA-prm
   ↓ reads TP
ProcessName-prc (tsc: ConceptX)
   ↓ returns result
PrimitiveB-prm
   ↓ writes TP
```

### **Mixed Flow (allowed only with explicit labeling)**  
```
Process Flow:
PrimitiveA-prm → ProcessName-prc (tsc: ConceptX) → PrimitiveB-prm
```

# 1. Primitives

## InB (Input Basin) — 20.100
- **Purpose:** Provides the deterministic, non-inferential front door for all external signals entering the architecture.
- **Focus:** Deterministic external-signal intake, schema validation, and **non-inferential** surface canonicalization.
- **When:** Pipeline A entry; first deterministic stage after external input.
- **Why:** Normalize wire form and preserve FIFO ordering without guessing user meaning.
- **Is not:** Semantic repair (IIInB); inquiry (IB); truth interpretation (TB); routing authority.
- **Example:** `"teh"` → canonical token; `"Yeah Baby!"` → tagged, not interpreted.
- **Normative home:** 20.100; messy-input classes in 20.17.

---

## IIInB (Input Inference/Repair Basin) — 20.101
- **Purpose:** Applies user-sanctioned shorthand expansions before context extraction, keeping repair rule-bound and auditable.
- **Focus:** Bounded **semantic shorthand repair** via explicit User Semantic Profile (USP) rules.
- **When:** Optional stage `input_semantic_repair`; ordering **InB → IIInB → RB**.
- **Why:** Apply user-approved shorthand expansions deterministically without constructing meaning.
- **Is not:** Interpretation; candidate generation; truth evaluation; meaning construction.
- **Example:** USP rule expands "quicker-ish" → canonical form.
- **Normative home:** 20.101.

---

## IE (Intake Envelope, Structured Intake Object)

- **Purpose:** Provides a deterministic, bounded, replayable representation of the user's input that can be safely passed to downstream components.
- **Focus:** The structured, normalized, repaired intake object produced by InB → IIInB.
- **When:** Immediately after IIInB; before CEx.
- **Why:** Deterministic, bounded, replayable representation of the user's input for downstream consumption.
- **Is not:** A semantic interpretation; a candidate generator; a truth evaluator.
- **Example:** Normalized tokens + USP-applied repairs + structural tags.
- **Normative home:** 20.109

---

## CEx (ContextExtractor)
- **Purpose:** Bridges global conversation state and the inference path by producing a bounded, replayable context slice for ISc.
- **Focus:** Deterministic extraction of **bounded, relevant, replayable** context from CIL to form the Context Envelope (CE).
- **When:** Inference path: **IIInB → IE → CEx → CE → ISc**.
- **Why:** ISc needs context but cannot read global state directly.
- **Is not:** A semantic interpreter; a meaning constructor; a Thought Packet (TP) writer.
- **Example:** Reads CIL; extracts active referents + lineage + relevant USP entries.
- **Normative home:** 20.33 (CIL), 20.44 (ISc), architecture discussion.

---

## CE (ContextEnvelope) — New

- **Purpose:** Delivers safe, isolated context to ISc without exposing global conversation state.
- **Focus:** Bounded, deterministic, replayable context object consumed by ISc.
- **When:** Immediately before ISc in the inference path.
- **Why:** Provide ISc with safe, isolated context without exposing global state.
- **Is not:** A history; a semantic object; a TP writer; a CIL proxy.
- **Example:** CE contains active referents, lineage IDs, relevant commitments.
- **Normative home:** Architecture discussion; 20.44.

---

## **ISc (Inference Scorer) — 20.44**
- **Purpose:** Performs deterministic scoring of interpretation candidates by executing the **truth_hypotheses‑prc** process over the candidate_set{}, producing stable, auditable scoring fields in the TP without accessing global state.
- **Focus:** Reads CE‑produced candidate_set{}; applies truth_hypotheses‑prc; writes scoring‑layer fields (`tp.score_set`, `tp.score_conflict`, `tp.score_reason_code`) into the TP for downstream routing and TPU commit.
- **When:** Path A inference sequence: **CE‑prm → ISc‑prm → TPU‑prm(Merge process)**. Runs after candidate extraction and before merge/commit.
- **Why:** Ensures that candidate interpretation scoring is deterministic, local, and reproducible, preventing global‑state leakage and ensuring that routing and TPU commit operate on stable, non‑probabilistic scoring data.
- **Is not:** A semantic generator; a meaning constructor; a truth evaluator; a global inference engine; a CIL reader; a semantic repair mechanism; a TS‑level concept.
- **Example:** Given multiple referent candidates extracted by CEx‑prm, ISc‑prm applies truth_hypotheses‑prc to compute deterministic scores and writes the resulting score_set into the TP for TR‑prm to route.
- **Normative home:** 20.44.

---

## TPU (Thought Packet Updater) — Path A Only
- **Purpose:** The sole safe writer to TP and semantic_core **for Path A correction only**. TPU commits validated *correction/understanding* meaning into durable TP state.
- **Focus:** Deterministic, boundary‑enforced TP updates based strictly on CE + CEx + ISc output. TPU performs no topology operations and no realization work.
- **When:** Path A correction flow: **CE → ISc → TPU → TP(N+1)**.
- **Why:** Enforce the single‑writer invariant for meaning construction; ensure all semantic commits are deterministic, auditable, and isolated from Path B.
- **Is not:** A topology engine; a semantic interpreter; a candidate generator; a CIL reader; **a Path B realization primitive**; **a meaning constructor for expression**.
- **Example:** ISc selects a corrected referent; TPU applies the update to TP(N), producing TP(N+1) and freezing semantic_core under a new `commit_id`.
- **Scope Invariant:** **TPU‑prm MUST NOT be invoked by Path B.** Path B is meaning‑read‑only and cannot write to TP or semantic_core.
- **Normative home:** 20.105, architecture discussion.

## **SOB (Structural OB) — 20.40.010**
- **Purpose:** Extracts first‑pass structural cues from TP content, forming the base residue used by downstream OB layers and routing.
- **Focus:** Clause boundaries, syntactic shape, negation markers, modality markers, structural anchors, and pattern‑family activation.
- **When:** First stage of OB evaluation during Pipeline A whenever structural pattern detection is required.
- **Why:** Provides deterministic, low‑level structural residue enabling refinement, constraint extraction, and TR‑input formation.
- **Is not:** A semantic interpreter; a constraint resolver; a truth evaluator; a geometric meta‑basin.
- **Example:** SOB identifies clause boundaries and structural markers, producing the initial residue fragment for refinement.
- **Normative home:** 20.40.010.

---

## **SROB (Structural Refinement OB) — 20.40.020**
- **Purpose:** Refines SOB structural residue into normalized, canonicalized forms suitable for constraint extraction and routing.
- **Focus:** Structural normalization, refinement of anchors, canonical ordering, residue smoothing, and refinement‑level metadata.
- **When:** Invoked after SOB when structural refinement or normalization is required for downstream OB layers.
- **Why:** Ensures structural residue is stable, canonical, and refinement‑consistent across TP variants and noisy inputs.
- **Is not:** A constraint extractor; a semantic interpreter; a truth evaluator; a routing arbiter.
- **Example:** SROB refines SOB’s structural cues into canonicalized residue fragments with stable ordering.
- **Normative home:** 20.40.020.

---

## **CnOB (Constraint OB) — 20.40.030**
- **Purpose:** Extracts constraint‑level residue and metadata from refined structure, enabling routing, ΔH% attribution, and downstream interpretation.
- **Focus:** Constraint cues, missing‑slot signals, underspecification markers, conflict indicators, and constraint‑level residue hashing.
- **When:** Invoked after SROB when constraint extraction or constraint metadata is required for routing or ΔH% accounting.
- **Why:** Provides deterministic constraint residue enabling routing correctness, conflict detection, and missing‑mass attribution.
- **Is not:** A semantic interpreter; a structural normalizer; a truth evaluator; a generative mechanism.
- **Example:** CnOB extracts constraint markers and missing‑slot cues, producing constraint‑level residue for routing.
- **Normative home:** 20.40.030.

---

## **SmOB (Semantic OB) — 20.40.040**
- **Purpose:** Performs two jobs: (1) extracts pre‑semantic residue and semantic‑adjacent cues from SOB→SROB→CnOB output, and (2) compresses all upstream residue plus SmOB cues into a deterministic pre‑semantic residue hash and TR‑input cue vector.
- **Focus:** (Job 1) semantic‑adjacent pattern activation, modality cues, affect markers, conflict‑adjacent and underspecification‑adjacent signals; (Job 2) deterministic pre‑semantic residue hashing and TR‑input cue formation for routing.
- **When:** Invoked after CnOB when semantic‑adjacent cues, pre‑semantic residue, or deterministic routing representation are required for SSG or downstream interpretation.
- **Why:** Job 1 adds pre‑semantic cues into the TP to support identity OB selection, ΔH% attribution, and semantic‑layer preparation; Job 2 provides a canonical, replay‑safe compressed representation enabling deterministic TR routing and SSG signal generation.
- **Is not:** A semantic interpreter; a truth evaluator; a stance assigner; a geometric meta‑basin; a semantic normalizer.
- **Example:** SmOB extracts semantic‑adjacent cues (Job 1) and then compresses upstream residue plus its own cues into a deterministic hash and TR‑input cue vector (Job 2) consumed by SSG and the Thought Router to derive TP.TR.
- **Normative home:** 20.40.040.

## **SSG (Structural Signature Generator) — 20.47**
- **Purpose:** Converts SmOB structural output into a deterministic, fixed‑length structural signature vector for routing and similarity operations.
- **Focus:** Extraction and normalization of **structural invariants** (arc patterns, residue entropy, curvature, binding depth, motif frequencies) into a coordinate‑stable vector representation.
- **When:** Mandatory stage `structural_signature_generation`; ordering **SmOB → SSG → RB**.
- **Why:** Provide RB with a **geometry‑ready**, token‑free, replay‑stable coordinate chart enabling structural proximity, lane selection, and routing decisions.
- **Is not:** Semantic embedding; tokenization; meaning construction; interpretation; hashing; candidate generation.
- **Example:** SmOB graph with high branching depth and low curvature yields a signature emphasizing depth‑dominant structural geometry.
- **Normative home:** 20.47.

### **RBU‑prm (Routing Buffer Update Primitive)**  
- **Purpose:** Enrich the TP with subculture, identity, register, and interpretive metadata required for RB‑prm to perform correct routing.  
- **Focus:** Deterministically writes interpretive metadata (culture, subculture, register, stance‑relevant cues) into the TP snapshot before routing occurs.  
- **When:** Invoked **before RB‑prm**, ensuring RB‑prm receives a fully enriched TP.  
- **Why:** Maintain architectural purity by separating interpretive metadata enrichment (RBU‑prm) from routing computation (RB‑prm).  
- **Is not:** A router, classifier, scorer, or semantic evaluator. RBU‑prm does **not** compute routing deltas; it only prepares the TP so RB‑prm can compute routing correctly.  
- **Example:** RBU‑prm writes subculture and identity metadata into the TP. RB‑prm then uses this metadata to select the correct manifold chart and routing lane.  
- **Normative home:** 20.51.

# **RTU‑prm (Routing TP Update Primitive) — 20.30.005 (Corrected Patch)**
**Purpose:** RTU‑prm commits the routing metadata produced by RB‑prm into the TP snapshot.  
This includes **culture lane**, **subculture lane**, **fallback lane**, **routing lineage**, **routing reasons**, **fan‑out decisions**, and all other routing‑relevant structural fields. Its role is to provide TS, TR, and downstream primitives with a **stable, authoritative, deterministic routing state** for the next cycle. RTU‑prm **does not choose** culture or subculture — those decisions are made by RB‑prm — but RTU‑prm **is responsible for writing** the chosen culture/subculture lanes into the TP.
**Focus:** Pure, deterministic write‑back of RB‑prm’s routing metadata, validation of the routing envelope, ensuring RB‑prm remains pure and side‑effect‑free, embedding routing state into the TP for TS/TR scheduling and staleness evaluation  
**When:** Invoked immediately after RB‑prm and before TS schedules the next OB‑chain.  
Runs once per routing cycle and is never re‑invoked for the same RB output.
**Why:** Maintain architectural purity by separating **routing computation** (RB‑prm) from **routing commit** (RTU‑prm), provide TS/TR with a deterministic, auditable routing state, ensure replay equivalence and stable multi‑cycle behavior  
**Is no:t**  A router, a classifier, an interpreter, a scorer, a semantic evaluator, a modifier of OB outputs, semantic fields, truth fields, merge results, or completion data 
**Example:**  RB‑prm selects a cultural lane and fallback lane.  
RTU‑prm validates the routing envelope and **writes the culture lane, subculture lane, routing lineage, and lane‑selection fields** into the TP snapshot.  
TS then uses this committed routing state to schedule the next OB‑chain and determine TR execution.
**Normative home:** 20.30.005

## RB (Relational Basin) — 20.50
- **Purpose:** Routes the TP to downstream basins through governed relational transitions, without consulting B-side routing tables.
- **Focus:** Deterministic relational projection and routing to downstream basins.
- **When:** Pipeline A `routing`.
- **Why:** Governed movement between basins without B-side routing tables.
- **Is not:** SRP; TrigRB; TR.
- **Example:** `MI_INCOMP` routes toward IB-Creation-Request.
- **Normative home:** 20.50.

## TR (Thought Router) — 20.37
- **Purpose:** Selects the next relational transition in Path A by routing meaning-layer state forward after structural merge. TR consumes OB and DCB signals and produces a routing vector for RB.
- **Focus:** Deterministic routing within the meaning-layer topology. TR does not interpret, merge, or modify meaning; it only selects the next relational basin for RB to evaluate.
- **When:** Path A, after OB and before RB. TR operates in the post-merge, pre-routing phase of the corrected Path A flow.
- **Why:** Provide a stable, auditable routing decision that guides RB’s relational evaluation using curvature (DCB), structural evidence (OB), and trajectory signals.
- **Is not:** A semantic interpreter; a TP writer; a candidate generator; a CE/CEx participant; a realization or expression component.
- **Example:** TR receives DCB curvature events and OB evidence, then outputs a routing vector instructing RB which relational transition to evaluate next.
- **Normative home:** 20.37.

## **IdOB (Identity Object Basin) — 20.40.050**
- **Purpose:** Performs identity‑conditioned interpretation of the routed TP, applying identity‑specific meaning rules, transformations, and basin‑local semantics after RB and TR have selected the appropriate identity pathway.
- **Focus:** Consumes the post‑routing TP view, interprets identity‑relevant structures, resolves identity‑conditioned meaning, and emits updates through TPU.idob_update without producing residue, ΔH%, or TR‑input.
- **When:** Invoked in Path A after SSG, RB, and RTU have produced a stable routing decision; may run multiple times in the RB→RTU→IdOB cycle until identity‑conditioned meaning stabilizes.
- **Why:** Provides deterministic, replay‑safe identity‑specific interpretation that cannot be performed by OB, RB, TB, or DCB; isolates identity semantics from structural, routing, and truth‑evaluation responsibilities.
- **Is not:** An OB primitive; a structural classifier; a constraint extractor; a routing arbiter; a truth evaluator; a ΔH% contributor; a Path B computation; a writer of TP.TR or routing_metadata.
- **Example:** After RB routes a TP to a domain‑specific identity basin (e.g., mathematical identity, narrative identity, operator identity), IdOB applies identity‑conditioned interpretation rules and updates the TP via TPU.idob_update to reflect identity‑specific meaning.
- **Normative home:** 20.40.050 (Identity OB Primitive Requirements).

## **CTP‑prm (Collect Thought Point) — 20.145_prm**
- **Purpose:**  
 CTP collects all OB outputs from the OB‑chain and produces a single combined TP snapshot for the next RB arbitration.
- **Focus:**  
  Provide a stable, immutable TP snapshot between sequential OB‑chains in Path A, regardless of whether OB‑chains are executed sequentially (single‑core) or in parallel (multi‑core).
- **When:**  
  After each OB‑chain completes and before RB arbitration. In multi‑core systems, CTP executes after all OBs in the parallel OB‑Region complete.
- **Why:**  
CTP needed to be created since all legitimate routing OB's need to be processed and combined before routing to the next series of OB's for proper thought processing. For single core CPU's this will be a serial process and for multi-core CPU's this will be a parallel process.
- **Is not:**  
  - A meaning constructor  
  - A merge engine  
  - A scorer  
  - A TP writer (TPU is the only writer)  
  - A governance step  
- **Example:**  
  Single‑core:  
  `InB → OB0 → RB → OB1 → OB2 → … → OBn → CTP → RB → …`  
  Multi‑core:  
  `InB → OB0 → RB → {OB1 ∥ OB2 ∥ … ∥ OBn} → CTP → RB → …`
- **Normative home:**  
  **20.145_tp_collection.md**

## **OuBA (Output Basin — Path A Resolution Commit) — 20.40.060**
- **Purpose:** Finalizes Path A by assessing whether semantic correction and identity‑conditioned interpretation have produced a sufficiently resolved TP; writes resolution status, IB/GB consultation indicators, and readiness‑for‑Path‑B fields into the TP without emitting realization output.
- **Focus:** Consumes the post‑IdOB TP view, evaluates meaning_resolved, unresolved_semantics, and idob_complete flags, registers unresolved meaning patterns via TP.ib_candidate or TP.gb_consult_needed, links to existing IBs when indicated, and commits the corrected TP state for further routing by TS.
- **When:** Invoked after IdOB and TR have completed their Path A passes and the TP requires a resolution checkpoint; may run multiple times in the IdOB→TR→RB→OuBA cycle until semantic resolution stabilizes or an IB/GB pathway is declared.
- **Why:** Provides a deterministic, replay‑safe termination point for Path A that isolates semantic‑resolution assessment, IB/GB registration, and TP‑state commit responsibilities from structural OBs, routing primitives, and Path B realization; ensures TS can route the TP correctly based on explicit TP fields rather than implicit primitive‑to‑primitive signaling.
- **Is not:** A realization primitive; a producer of external output; a routing arbiter; a truth evaluator; a ΔH% contributor; a writer of TP.TR; a Path B computation; a direct invoker of GB or IB (writes only TP fields that TS uses to orchestrate those interactions).
- **Example:** After IdOB refines identity‑conditioned meaning but leaves unresolved semantics, OuBA writes meaning_resolved=false, ib_candidate=“X”, and gb_consult_needed=true into the TP; TS then routes the TP to the appropriate IB or GB pathway before determining whether the TP is eligible to enter Path B.
- **Normative home:** 20.40.060 (Path A Output Basin Requirements).

## IB (Inquiry Basin) — 20.90
- **Purpose:** Manages post-TS ambiguity lifecycle, generating clarification proposals only after meaning is fully committed.
- **Focus:** Post-TS ambiguity detection, inquiry-state evolution, and clarification proposal generation.
- **When:** **Post-TS only**: **TB → IB → GBIB → GB**.
- **Why:** Handle unresolved ambiguity after meaning is fully committed.
- **Is not:** Pipeline A; lane-parallel; semantic repair; TP writer; candidate generator.
- **Example:** IB detects unresolved referent ambiguity and proposes clarification.
- **Normative home:** 20.90 v0.4.

## **TPTB (TP Truth Basin Tags) — 20.64**
- **Purpose:** Provides Path‑A‑generated truth‑evaluation metadata attached to the TP/MTP, enabling Path B to express truth‑aware behavior (qualification, correction, clarification) without performing truth evaluation.
- **Focus:** Encodes truth‑related outcomes from Path A (alignment, conflict, basis, explanation) into a compact, auditable metadata structure (`tp.truth_tags`) that is stable, local, and free of global‑state access.
- **When:** Produced during Path A finalization after scoring, merge, and truth‑hypotheses evaluation; included in the semantic snapshot passed to Path B before response generation.
- **Why:** Ensures Path B can safely reference truth‑evaluation results without invoking TB or performing any truth computation, preserving A/B separation and preventing global‑state leakage.
- **Is not:** A truth engine; a basin; a semantic generator; a routing mechanism; a safety evaluator; a global truth model; a replacement for TB; a Path B computation.
- **Example:** After Path A determines that a user claim contradicts known facts, TPTB encodes `truth_conflict=true`, `conflict_type=contradiction`, and a brief explanation, allowing Path B to respond with a correction without performing truth evaluation.
- **Normative home:** 20.64.

## **TPSF (TP Safety Flags) — 20.66**
- **Purpose:** Provides Path‑A‑generated safety‑evaluation metadata attached to the TP/MTP, enabling Path B to express safety‑aware behavior (refusal, redirection, qualification) without performing safety evaluation.
- **Focus:** Encodes safety‑related outcomes from Path A (risk flags, category, severity, rationale) into a compact, auditable metadata structure (`tp.safety_flags`) that is stable, local, and free of global‑state access.
- **When:** Produced during Path A finalization after safety evaluation and merge; included in the semantic snapshot passed to Path B before response generation.
- **Why:** Ensures Path B can safely reference safety‑evaluation results without invoking safety basins or performing any safety computation, preserving A/B separation and preventing global‑state leakage.
- **Is not:** A safety engine; a basin; a routing mechanism; a semantic generator; a truth evaluator; a global safety model; a replacement for safety basins; a Path B computation.
- **Example:** If Path A detects that the user request involves self‑harm content, TPSF encodes `safety_risk=true`, `risk_type=self_harm`, and a rationale, enabling Path B to respond safely without performing safety evaluation.
- **Normative home:** 20.66.

## SRP (Semantic Routing Planner) — 20.55
- **Purpose:** Separates routing table maintenance (cold path) from per-cycle execution lookup (hot path) on the B side.
- **Focus:** Cold-path routing table compile; hot-path deterministic lookup.
- **When:** Pipeline B planning.
- **Why:** Separate table maintenance from A-cycle routing.
- **Is not:** RB; IMR writer.
- **Example:** B envelopes carry `routing_epoch_id`.
- **Normative home:** 20.55.

## **OuBB (Output Basin — Path B Realization Commit) — 20.110**
- **Purpose:** Converts the fully resolved Path B TP into external‑facing realization output by writing the final realization payload, realization metadata, and terminal‑state markers into the TP for TS to emit; serves as the deterministic end‑of‑pipeline commit point for all Path B realizations.
- **Focus:** Consumes the post‑TR/post‑RB₂ TP view, reads realization_semantics, response_plan, surface_form_spec, register, and subculture fields, generates realization_output and realization_metadata, writes output_commit and terminal markers, and finalizes the TP for emission by TS without performing routing, truth evaluation, or semantic interpretation.
- **When:** Invoked after all Path B OB passes, TR, RB₂, and any required realization‑side transformations have completed and the TP is marked realization_ready=true; always runs exactly once per realized TP and terminates the thought.
- **Why:** Provides a replay‑safe, deterministic, single‑point‑of‑truth for realization output generation, ensuring that external emission is driven solely by TP state and TS orchestration; isolates realization‑commit responsibilities from OB narrowing, routing, truth evaluation, and Path A resolution.
- **Is not:** A routing arbiter; a semantic interpreter; a truth evaluator; a ΔH% contributor; a writer of TP.TR or routing_metadata; a producer of internal meaning; a Path A primitive; a generator of IB/GB signals; a direct emitter of output (TS performs emission based on TP.output_commit).
- **Example:** After TR and RB₂ select the final realization pathway and IdOB completes identity‑conditioned interpretation for Path B, OuBB writes realization_output="…", output_commit=true, realization_metadata={…}, and terminal=true into the TP; TS detects output_commit and emits the realization_output to the environment.
- **Normative home:** 20.110 (Path B Output Basin Requirements).

## **LI (Local Inference Primitive) — 20.112**
- **Purpose:** Commits the first layer of meaning in Path B by applying the TS‑level concept **MLI** to the TP, producing a stable, locally‑resolved meaning state before any global inference, scoring, routing, or B‑side planning occurs.
- **Focus:** Reads representation‑layer fields from Path A; invokes **MLI‑prc**; writes meaning‑layer fields (`tp.meaning`, `tp.mli_status`, `tp.mli_confidence`, `tp.mli_conflict`, `tp.mli_reason_code`, `tp.mli_revision_cycles`) into the TP.
- **When:** First primitive of Path B, immediately after Path A representation freeze and before ISc, TR, TPU, or any B‑side planning. Runs every turn.
- **Why:** Ensures deterministic, auditable, local‑first meaning commitment so that all downstream primitives operate on a stable semantic substrate. Prevents semantic drift and unstable global inference by forcing meaning to be resolved before any higher‑order reasoning.
- **Is not:** A global inference engine; a scorer; a router; a semantic_core builder; a B‑side planner; a TP aggregator; or MLI itself. Does not read from MTP or generate XP.
- **Example:** Given an ambiguous utterance (“Can you check that for me”), LI reads the TP’s representation fields, applies MLI‑prc to classify the utterance as a *request*, and writes the resolved meaning and confidence into the TP for downstream primitives.
- **Normative home:** 20.112.

## REx (Realization Extractor) — Path B
- **Purpose:** Extracts the meaning-layer subset required for expression. Reads TP/MTP (read-only) and produces an expression-ready meaning slice.
- **Focus:** Meaning extraction for realization; no interpretation, no merge, no TP writes.
- **When:** First primitive in Path B: TP/MTP → REx → RPlan.
- **Is not:** A semantic interpreter; a TP writer; a meaning constructor.

---

## RPlan (Realization Plan Construction) — Path B
- **Purpose:** Builds candidate realization plans from REx output. Plans include structure, tone, pacing, channel, and constraints.
- **Focus:** Plan construction only; no meaning modification.
- **When:** After REx, before RPU.
- **Is not:** A merge engine; a TP writer; a meaning constructor.

---

## RPU (Realization Plan Updater) — Path B Only
- **Purpose:** The central realization primitive for Path B. RPU consumes meaning from TP/MTP (read‑only) and constructs realization plans, expression structures, and behavioral outputs. It is the Path B counterpart to TPU, but operates strictly on the expression side.
- **Focus:** Deterministic, boundary‑enforced *realization* updates based on Path B processes (e.g., style, timing, channel, structure). RPU performs no semantic merge and does not modify TP or semantic_core.
- **When:** Path B realization flow: **TP/MTP (read‑only) → REx → RPlan → RPU → ReB**.
- **Why:** Provide a single, auditable locus for expression planning, separate from meaning construction. Ensures Path B has a coherent, deterministic update point for realization without touching meaning.
- **Is not:** A semantic merge engine; a TP writer; a meaning constructor; a CE/CEx participant; a Path A primitive.
- **Example:** RPU receives a realization plan (e.g., tone=calm, channel=text, pacing=slow) and commits it to the realization buffer for downstream formatting and output.
- **Scope Invariant:** **RPU‑prm MUST NOT write to TP or semantic_core.** It operates only on realization‑side structures (e.g., RP‑ref, RPlan‑ref, ReB). Path B is meaning‑read‑only.
- **Normative home:** 20.168 (Path B specification).

## ReB (Realization Basin) — Path B
- **Purpose:** Holds the final realized expression after RPU commits the selected plan. Feeds into formatting and external output.
- **Focus:** Output buffering for expression; no meaning-layer operations.
- **When:** Final primitive in Path B: RPU → ReB → externalization.
