# **Introduction**

## **Purpose**  
Please see [20.700_master_glossary.md](20.700_master_glossary.md), the 20.190 will not be supported going forward and be replaced by 20.700.

This glossary is the canonical reference for the refactored 20‑series and serves as the **Primitive Intent Catalog** for the Thought Simulator architecture. Its role is to define, with precision, what each component *owns*, when it executes, and what it is *not*, ensuring strict intent boundaries and preventing authority drift across modules. Normative high‑level requirements (HLRs) remain in the corresponding 20.xx modules; entries here are descriptive unless explicitly marked normative. Architectural context for runtime‑pipeline blocks (B0–B8) is provided in **20.01_architecture_map.md**.

---

## **How to Read This Catalog**  
Each entry follows a fixed seven‑field template to ensure clarity and architectural consistency:

| Field | Meaning |
|-------|---------|
| **Purpose** | Architectural role: what disappears or breaks if this component is removed |
| **Focus** | Operational ownership: the one‑sentence statement of what this component owns |
| **When** | Execution context: Path A, Path B, conversation layer, post‑TS, or pre‑A |
| **Why** | The specific architectural problem this component solves |
| **Is not** | Common confusions and explicit non‑ownership boundaries |
| **Example** | One concrete scenario illustrating correct behavior |
| **Normative home** | Authoritative 20.xx module defining requirements |

This structure ensures every entry is auditable, comparable, and aligned with the TS execution model.

---

## **Category Structure**  
All glossary entries fall into one of five architectural categories:

| Category | Suffix | Definition |
|----------|--------|------------|
| **1. Primitives** | ‑prm | TP‑holding, TP‑reading, TP‑modifying atomic operations in the TS pipeline |
| **2. Processes** | ‑prc | Pure logic executed *inside* primitives; do not hold or modify the TP |
| **3. Reference Objects** | ‑ref | Static data structures used by primitives and processes; never modify TP |
| **4. Governance** | ‑gov | Supervisory, safety, audit, and correction rules governing TS behavior |
| **5. TS‑Level Concepts** | ‑tsc | Conceptual logic layers (semantic, structural, routing, uncertainty) that do not appear as blocks in flows |

This categorization enforces architectural separation and prevents conceptual drift.

## InB (Input Basin) — 20.100
**Purpose:** Deterministic, non‑inferential front door for all external signals.  
**Focus:** Schema validation, surface canonicalization, FIFO preservation; no meaning inference.  
**When:** Pipeline‑A entry, first deterministic stage after external input.  
**Why:** Normalize wire form without guessing user intent.  
**Is not:** Semantic repair (IIInB); inquiry (IB); truth interpretation (TB); routing authority.  
**Example:** "teh" → canonical token; "Yeah Baby!" → tagged, not interpreted.  
**Normative home:** 20.100; messy‑input classes in 20.17.

---

## IIInB (Input Inference/Repair Basin) — 20.101
**Purpose:** Apply bounded, user‑sanctioned shorthand expansions before context extraction.  
**Focus:** Deterministic semantic‑shorthand repair via USP rules; no meaning construction.  
**When:** Optional stage input_semantic_repair; ordering InB → IIInB → RB.  
**Why:** Apply user‑approved shorthand expansions without inference.  
**Is not:** Interpretation; candidate generation; truth evaluation; meaning construction.  
**Example:** USP expands "quicker‑ish" → canonical form.  
**Normative home:** 20.101.

---

## IE (Intake Envelope, Structured Intake Object)
**Purpose:** Provide a deterministic, bounded, replayable representation of user input.  
**Focus:** Structured, normalized, repaired intake object from InB → IIInB.  
**When:** Immediately after IIInB; before CEx.  
**Why:** Downstream components require deterministic, replayable intake.  
**Is not:** Semantic interpretation; candidate generator; truth evaluator.  
**Example:** Normalized tokens + USP repairs + structural tags.  
**Normative home:** 20.109.

---

## CEx (ContextExtractor)
**Purpose:** Produce a bounded, replayable context slice (CE) for ISc without exposing global state.  
**Focus:** Deterministic extraction of only the context‑relevant information from CIL needed for candidate generation and ISc scoring.  
**When:** Inference Path: IIInB → IE → CEx → CE → candidate_set{} → ISc.  
**Why:** ISc requires contextual information but cannot read CIL or any global state directly; CEx provides a safe, bounded intermediary.  
**Is not:** Semantic interpreter; meaning constructor; TP writer; global‑state reader; lineage exporter.  
**Example:** Extract active referents, local discourse entities, and bounded conversation‑context cues from CIL to form CE.  
**Normative home:** 20.190.

---

## CE (ContextEnvelope) — 20.108
**Purpose:** Deliver safe, isolated context to ISc without exposing global conversation state.  
**Focus:** Bounded, deterministic, replayable context object containing only the context‑relevant information extracted by CEx from CIL.  
**When:** Produced immediately before ISc in the Inference Path.  
**Why:** Provide ISc with the minimal, safe context required for deterministic candidate generation and scoring.  
**Is not:** History; semantic object; TP writer; CIL proxy; lineage exporter; global‑state container.  
**Example:** CE contains active referents, local discourse entities, and bounded commitment cues needed for candidate_set{} and ISc scoring.  
**Normative home:** 20.108.

## ISc (Inference Scorer) — 20.44
**Purpose:** Deterministically score interpretation candidates by applying truth_hypotheses‑prc over candidate_set{}, producing scoring fields for TPU without accessing global state.  
**Focus:** Read CE and candidate_set{}; apply truth_hypotheses‑prc; produce tp.score_set, tp.score_conflict, and tp.score_reason_code for inclusion in update_structure.  
**When:** Path‑A inference sequence: CE → candidate_set{} → ISc → TPU (Merge).  
**Why:** Provide deterministic, local scoring for routing and TPU commit while preventing global‑state leakage or unbounded inference.  
**Is not:** Semantic generator; meaning constructor; truth evaluator; global inference engine; CIL reader; semantic repair mechanism.  
**Example:** ISc scores referent candidates and produces a score_set consumed by TR‑prm during routing.  
**Normative home:** 20.44.

## TPU (Thought Packet Updater) — Path A Only
**Purpose:** Sole safe writer to TP for Path‑A correction; inserts and corrects message‑items, referents, constraints, and meaning fields based on CE+CEx+ISc output.  
**Focus:** Deterministic, boundary‑enforced TP updates; no topology, routing, governance, or realization work; does not write semantic_core.  
**When:** Path‑A correction flow: CE → ISc → TPU → TP(N+1).  
**Why:** Enforce the single‑writer invariant for meaning construction and ensure all semantic updates are deterministic, auditable, and isolated from Path‑B.  
**Is not:** Topology engine; semantic interpreter; candidate generator; CIL reader; Path‑B primitive; meaning constructor for expression.  
**Example:** ISc selects a corrected referent or message‑item; TPU applies the update to TP(N), producing TP(N+1) under a new commit_id.  
**Scope invariant:** TPU‑prm MUST NOT be invoked by Path‑B; Path‑B is meaning‑read‑only.  
**Normative home:** 20.105.

## SOB (Structural OB) — 20.40.010
**Purpose:** Extract first‑pass structural cues from TP content, producing the base structural residue consumed by downstream OB layers and routing.  
**Focus:** Clause boundaries, syntactic shape, punctuation/symbol masks, negation markers, modality markers, structural anchors, and structural tags; no semantic interpretation.  
**When:** First OB stage in Path‑A whenever structural pattern detection is required.  
**Why:** Provide deterministic low‑level structural residue enabling refinement, constraint extraction, and TR‑input formation.  
**Is not:** Semantic interpreter; constraint resolver; truth evaluator; geometric/meta‑basin.  
**Example:** SOB identifies clause boundaries and structural markers, emitting the initial residue fragment for refinement.  
**Normative home:** 20.40.010.

## SROB (Structural Refinement OB) — 20.40.020
**Purpose:** Refine and canonicalize SOB structural residue into normalized forms suitable for constraint extraction and routing.  
**Focus:** Structural normalization, anchor refinement, canonical ordering, residue smoothing, and refinement‑level metadata; no semantic interpretation.  
**When:** Invoked after SOB when structural refinement or normalization is required for downstream OB layers.  
**Why:** Ensure structural residue is stable, canonical, and refinement‑consistent across TP variants and noisy inputs.  
**Is not:** Constraint extractor; semantic interpreter; truth evaluator; routing arbiter.  
**Example:** SROB refines SOB’s structural cues into canonicalized residue fragments with stable ordering.  
**Normative home:** 20.40.020.

## CnOB (Constraint OB) — 20.40.030
**Purpose:** Extract constraint‑level residue and metadata from refined structure, enabling routing, ΔH% attribution, and downstream interpretation.  
**Focus:** Constraint cues, missing‑slot signals, underspecification markers, conflict indicators, and constraint‑residue hashing; no semantic inference.  
**When:** Invoked after SROB when constraint extraction or constraint metadata is required for routing or ΔH% accounting.  
**Why:** Provide deterministic constraint residue enabling routing correctness, conflict detection, and missing‑mass attribution.  
**Is not:** Semantic interpreter; structural normalizer; truth evaluator; generative mechanism.  
**Example:** CnOB extracts constraint markers and missing‑slot cues, producing constraint‑level residue for routing.  
**Normative home:** 20.40.030.

## SmOB (Semantic OB) — 20.40.040
**Purpose:** Perform two jobs: (1) extract pre‑semantic and semantic‑adjacent cues from SOB→SROB→CnOB residue, and (2) compress all upstream residue plus SmOB cues into a deterministic pre‑semantic hash and TR‑input cue vector.  
**Focus:** (Job 1) semantic‑adjacent pattern activation, modality/affect cues, conflict‑adjacent and underspecification‑adjacent signals; (Job 2) deterministic pre‑semantic residue hashing and TR‑input cue formation for routing.  
**When:** Invoked after CnOB when semantic‑adjacent cues, pre‑semantic residue, or deterministic routing representation are required for SSG or downstream interpretation.  
**Why:** Job 1 adds pre‑semantic cues supporting IdOB selection, ΔH% attribution, and semantic‑layer preparation; Job 2 provides a canonical, replay‑safe compressed representation enabling deterministic TR routing and SSG signal generation.  
**Is not:** Semantic interpreter; truth evaluator; stance assigner; geometric meta‑basin; semantic normalizer.  
**Example:** SmOB extracts semantic‑adjacent cues (Job 1) and compresses upstream residue plus its own cues into a deterministic hash and TR‑input cue vector consumed by SSG and the Thought Router to derive TP.TR.  
**Normative home:** 20.40.040.

## SSG (Structural Signature Generator) — 20.47
**Purpose:** Convert SmOB structural output into a deterministic, fixed‑length structural signature vector for routing and similarity operations.  
**Focus:** Extract and normalize structural invariants (arc patterns, residue entropy, curvature, binding depth, motif frequencies) into a coordinate‑stable vector representation.  
**When:** Mandatory stage structural_signature_generation; ordering SmOB → SSG → RB.  
**Why:** Provide RB with a geometry‑ready, token‑free, replay‑stable coordinate chart enabling structural proximity, lane selection, and routing decisions.  
**Is not:** Semantic embedding; tokenization; meaning construction; interpretation; hashing of semantic content; candidate generator.  
**Example:** A SmOB graph with high branching depth and low curvature yields a signature emphasizing depth‑dominant structural geometry.  
**Normative home:** 20.47.

### **RBU‑prm (Routing Buffer Update Primitive)**  
**Purpose:** Enrich the TP with subculture, identity, register, and interpretive metadata required for RB‑prm to perform correct routing.  
**Focus:** Deterministically writes interpretive metadata (culture, subculture, register, stance‑relevant cues) into the TP snapshot before routing occurs.  
**When:** Invoked **before RB‑prm**, ensuring RB‑prm receives a fully enriched TP.  
**Why:** Maintain architectural purity by separating interpretive metadata enrichment (RBU‑prm) from routing computation (RB‑prm).  
**Is not:** A router, classifier, scorer, or semantic evaluator. RBU‑prm does **not** compute routing deltas; it only prepares the TP so RB‑prm can compute routing correctly.  
**Example:** RBU‑prm writes subculture and identity metadata into the TP. RB‑prm then uses this metadata to select the correct manifold chart and routing lane.  
**Normative home:** 20.51.

## RTU‑prm (Routing TP Update Primitive) — 20.30.005
**Purpose:** Commit RB‑prm’s routing metadata into the TP snapshot, including culture/subculture lanes, fallback lane, routing lineage, routing reasons, fan‑out decisions, and all routing‑relevant structural fields.  
**Focus:** Pure deterministic write‑back of RB‑prm output; validate the routing envelope; ensure RB‑prm remains pure and side‑effect‑free; embed routing state for TS/TR scheduling and staleness evaluation.  
**When:** Invoked immediately after RB‑prm and before TS schedules the next IdOB‑chain; runs once per routing cycle and is never re‑invoked for the same RB output.  
**Why:** Separate routing computation (RB‑prm) from routing commit (RTU‑prm); provide TS/TR with a stable, auditable routing state; ensure replay equivalence and multi‑cycle determinism.  
**Is not:** Router; classifier; interpreter; scorer; semantic evaluator; modifier of OB outputs, semantic fields, truth fields, merge results, or completion data.  
**Example:** RB‑prm selects culture and fallback lanes; RTU‑prm validates the routing envelope and writes lane‑selection fields, routing lineage, and routing reasons into the TP snapshot for TS/TR.  
**Normative home:** 20.30.005.

## RB (Relational Basin) — 20.50
**Purpose:** Perform deterministic routing arbitration in Path‑A, selecting the next IdOB based on structural residue, ΔH%, lineage, and TR‑input fields, without accessing any Path‑B structures.  
**Focus:** Deterministic evaluation of routing metadata and relational cues to choose the next IdOB in the meaning‑construction cycle; RB selects the basin but does not move the TP.  
**When:** Invoked during Path‑A routing after OB and TR evaluation; runs in the RB→RTU→IdOB loop until Truth/Done stabilizes the turn‑final TP.  
**Why:** Provide governed, replay‑safe routing decisions that maintain A‑side determinism and enforce the A/B separation required by 20.705.  
**Is not:** SRP; TrigRB; TR; geometric projector; transport mechanism; Path‑B computation; reader of B‑side routing tables or MTP.  
**Example:** RB evaluates residue and ΔH% changes, determines that structural cues require re‑entering CnOB, and selects CnOB as the next basin for OBA‑prm execution.  
**Normative home:** 20.50.

# **TrSch‑prm (Turn Scheduler Primitive) — 20.155_prm**
**Purpose:** Coordinate and sequence all Path‑A primitives by interpreting the consolidated IdOB‑output packet produced by CTP‑prm and selecting the next architectural action. TrSch‑prm is the sole arbiter of turn‑level control flow. It determines whether to continue the RB‑prm → RTU‑prm → IdOB‑prm cycle, invoke CE‑prm for correction, advance to OuBA‑prm for commit, or finalize the turn via Truth/Done. TrSch‑prm ensures that no meaning‑refinement primitive routes itself and that all routing, correction, and commit transitions remain deterministic, replay‑safe, and compliant with the A/B separation rules.  
**Focus:** Deterministic interpretation of IdOB‑prm’s control flags (`continue`, `needs_correction`, `done`, `unstable`, `halt`, `retry`, etc.) and selection of the next primitive in the Path‑A pipeline. TrSch‑prm does not modify TP, semantic_core, routing_metadata, or meaning fields. It performs no semantic evaluation, no routing computation, no correction, and no commit. TrSch‑prm is strictly a scheduler and control‑flow governor, ensuring that all downstream primitives operate in the correct order and under the correct conditions.  
**When:** Invoked immediately after CTP‑prm consolidates the outputs of an IdOB‑set. TrSch‑prm runs once per IdOB‑set cycle and is the only primitive allowed to decide whether the next step is RB‑prm, CE‑prm, OuBA‑prm, or Truth/Done. TrSch‑prm is never invoked during RB‑prm, RTU‑prm, IdOB‑prm, or OuBA‑prm execution; it only runs at turn‑level boundaries between primitive families. In multi‑core systems, TrSch‑prm executes only after all parallel IdOB‑prm instances have completed and CTP‑prm has produced a unified packet.  
**Why:** Maintain architectural purity by separating meaning refinement (IdOB‑prm), routing computation (RB‑prm), routing commit (RTU‑prm), correction (CE‑prm → TPU‑prm), and commit (OuBA‑prm). TrSch‑prm ensures that IdOB‑prm never routes itself, that RB‑prm never interprets meaning flags, and that OuBA‑prm is invoked only when meaning is stable and correction‑complete. TrSch‑prm enforces deterministic, replay‑safe turn sequencing and prevents cross‑contamination between routing, meaning, correction, and commit surfaces. It is the central enforcement point for the A/B separation and the single‑writer invariants.  
**Is not:** Router; classifier; scorer; semantic evaluator; meaning‑refinement primitive; routing‑refinement primitive; TP writer; semantic_core writer; correction engine; governance step; truth evaluator; ΔH% contributor; merge engine. TrSch‑prm does not read raw TP or semantic_core; it consumes only the consolidated IdOB‑output packet from CTP‑prm.  
**Example:** CTP‑prm consolidates the outputs of IdOB₁…IdOBₙ into a single packet. TrSch‑prm reads the packet’s control flags and determines that meaning is not yet stable; TrSch‑prm schedules another RB‑prm → RTU‑prm → IdOB‑prm cycle. Later, after a subsequent IdOB‑set, TrSch‑prm interprets the `done` flag and schedules OuBA‑prm for commit. If IdOB‑prm emits a `needs_correction` flag, TrSch‑prm schedules CE‑prm → TPU‑prm before resuming Path‑A. If IdOB‑prm emits `unstable`, TrSch‑prm may schedule additional refinement cycles or escalate to correction depending on the stability envelope.  
**Normative home:**  20.155_trsch_prm.md.

## TR (Thought Router) — 20.37
**Purpose:** Compute the deterministic routing vector (TP.TR) for Path‑A by consuming OB and DCB signals; TR influences RB’s arbitration but does not select the next basin.  
**Focus:** Deterministic computation of routing metadata; TR does not interpret, merge, or modify meaning.  
**When:** Path‑A, after OB/DCB evaluation and before RB arbitration.  
**Why:** Provide a stable, auditable routing vector guiding RB using curvature (DCB), structural evidence (OB), and trajectory signals.  
**Is not:** Semantic interpreter; TP writer; candidate generator; CE/CEx participant; realization component.  
**Example:** TR receives DCB curvature events and OB residue, then outputs TP.TR for RB’s next routing decision.  
**Normative home:** 20.37.

## IdOB (Identity Object Basin) — 20.40.050
**Purpose:** Perform identity‑conditioned meaning refinement on the routed TP, applying identity‑specific rules and basin‑local semantics after RB/TR select the identity pathway.  
**Focus:** Consume the post‑routing TP view, resolve identity‑conditioned meaning, and emit updates via TPU.idob_update; produce no residue, ΔH%, or TR‑input.  
**When:** Invoked in Path‑A after SSG → RB → RTU produce a stable routing decision; may run multiple times in the RB→RTU→IdOB cycle until identity‑conditioned meaning stabilizes.  
**Why:** Provide deterministic, replay‑safe identity‑specific refinement isolated from structural, routing, and truth‑evaluation responsibilities.  
**Is not:** OB primitive; structural classifier; constraint extractor; routing arbiter; truth evaluator; ΔH% contributor; Path‑B computation; writer of TP.TR or routing_metadata.  
**Example:** After RB routes a TP to a domain‑specific identity basin (e.g., mathematical, narrative, operator), IdOB applies identity‑conditioned rules and updates the TP via TPU.idob_update.  
**Normative home:** 20.40.050.

## CTP‑prm (Collect/Consolidate Thought Point) — 20.145_prm
**Purpose:** Collects all IdOB‑outputs from an IdOB‑set into a single stable IdOB‑output packet for RB arbitration.  
**Focus:** Deterministic consolidation of IdOB‑outputs between IdOB‑sets; does not write or modify TP (TPU is sole writer).  
**When:** After an IdOB‑set completes and before RB arbitration; in multi‑core systems runs after all parallel OBs finish.  
**Why:** Ensures all legitimate IdOB‑outputs are available as one replay‑safe packet for routing in both serial and parallel execution.  
**Is not:** Meaning constructor; merge engine; scorer; TP writer; governance step.  
**Example:** Single‑core: InB→OB0→RB→OB1…OBn→CTP→RB; Multi‑core: InB→OB0→RB→{OB1∥OB2…∥OBn}→CTP→RB.  
**Normative home:** 20.145_ctp.md

## OuBA (Output Basin — Path A Commit) — 20.40.060
**Purpose:** Commit the finalized Path‑A meaning state into an immutable semantic snapshot (semantic_core and meaning‑bearing fields) for DF intake (IB → TB → GBIB → GB).  
**Focus:** Freeze the meaning‑layer state and write commit‑time metadata, resolution flags, and DF‑readiness indicators; perform no semantic correction, truth evaluation, routing, or governance decisions.  
**When:** Runs once per Path‑A cycle after meaning construction and completion evaluation stabilize; executes immediately before DF ingress and never during Path‑B realization.  
**Why:** Provide a deterministic, replay‑safe termination point for Path‑A, ensuring DF operates only on committed meaning and never on in‑flight structures.  
**Is not:** Governance primitive; truth evaluator; semantic repair engine; routing arbiter; generator of inquiry/truth states; producer of governance directives; OuBA never modifies semantic_core after commit or invokes IB/TB/GBIB/GB.  
**Example:** After Path‑A meaning construction stabilizes, OuBA freezes semantic_core and commit‑time metadata into a committed TP snapshot consumed by DF beginning at IB.  
**Normative home:** 20.40.060; 20.705 (DF ingress); 20.90 (IB); 20.60 (TB); 20.80 (GB).

## **KnC (Knowledge Coarse Grounding Primitive) — 20.48.010**  
**Purpose:** Attach coarse identity, relation, domain‑anchor, qualifier, and truth‑validation primitives to SSR‑K using grammar‑atomic entries from KnDt; provide TS with a stable, high‑entropy, low‑precision grounding tier for deterministic fallback and safe expression.  
**Focus:** Perform broad lexical grounding without contextual disambiguation; resolve only the most general identity and relation categories; compute $H\_{Kn_{coarse}}$ and write coarse abstraction fields without modifying medium or fine tiers.  
**When:** Runs immediately after OuBA commit and before KnM; executes once per grounding cycle after coarse lexical indicators are extracted from SSR.  
**Why:** Ensure TS always has a deterministic grounding baseline even when Path‑A projection is incomplete or ambiguous; provide a safe abstraction tier for Path‑B expression and entropy‑conditioned routing.  
**Is not:** Contextual resolver; fine identity engine; semantic inference module; truth evaluator; multi‑hop grounding system; KnC never performs medium/fine grounding, deep validation, or domain‑specific refinement.  
**Example:** After OuBA commits meaning, KnC attaches coarse identity (“dog”), coarse relation (“is‑a”), and coarse domain anchors (“animal”) to SSR‑K using grammar‑atomic KnDt entries.  
**Normative home:** 20.48.010; 20.705 (Path‑A → KnB → Path‑B flow); 20.52 (SSR); 20.40.060 (OuBA).

## **KnM (Knowledge Medium Grounding Primitive) — 20.48.020**  
**Purpose:** Attach medium‑depth identity, relation, domain‑anchor, qualifier, and truth‑validation primitives to SSR‑K using contextual and domain‑specific indicators; refine coarse grounding into a moderate‑precision, moderate‑entropy abstraction tier.  
**Focus:** Perform contextual disambiguation and domain‑aware refinement; resolve ambiguity that coarse grounding cannot address; compute $H\_{Kn_{medium}}$ and write medium abstraction fields without modifying coarse or fine tiers.  
**When:** Runs after KnC grounding stabilizes and before KnF; executes once per grounding cycle when contextual cues and domain hints are available in SSR.  
**Why:** Provide TS with a balanced grounding tier that is more precise than coarse grounding but not fully resolved; enable Path‑B to express contextual meaning or generate targeted clarification questions.  
**Is not:** Fine identity resolver; deep truth validator; semantic inference engine; KnM never performs fine‑resolution grounding, multi‑hop reasoning, or domain‑specific micro‑classification.  
**Example:** After KnC attaches “dog,” KnM refines identity to “retriever” and attaches medium relations and domain anchors using contextual indicators from SSR and grammar‑atomic entries from KnDt.  
**Normative home:** 20.48.020; 20.705 (KnB pipeline); 20.52 (SSR); 20.40.060 (OuBA).

## **KnF (Knowledge Fine Grounding Primitive) — 20.48.030**  
**Purpose:** Attach fine‑resolution identity, relation, domain‑anchor, qualifier, and truth‑validation primitives to SSR‑K using precise contextual and domain‑specific signals; produce the lowest‑entropy, highest‑precision grounding tier for deterministic expression.  
**Focus:** Perform deep contextual disambiguation and fine identity resolution; attach exact domain anchors and fine qualifiers; compute $H\_{Kn_{fine}}$ and write fine abstraction fields without modifying coarse or medium tiers.  
**When:** Runs after KnM grounding stabilizes and immediately before Path‑B realization; executes once per grounding cycle when SSR contains sufficient contextual and domain‑specific detail.  
**Why:** Provide TS with a fully resolved grounding tier enabling precise expression when entropy is low; ensure deterministic meaning realization without semantic guessing or probabilistic inference.  
**Is not:** Coarse or medium resolver; semantic guesser; inference engine; KnF never performs multi‑hop reasoning, semantic repair, or any probabilistic interpretation of meaning.  
**Example:** After KnM refines identity to “retriever,” KnF resolves identity to “Golden Retriever,” attaches fine relations and domain anchors, and finalizes grounded knowledge for Path‑B expression.  
**Normative home:** 20.48.030; 20.705 (KnB → Path‑B flow); 20.52 (SSR); 20.40.060 (OuBA).

# **TPTB (Truth‑Tag Basin — Path A Truth Tagging) — 20.64**

**Purpose:** Commit deterministic, governance‑ready truth‑tag metadata into the **SSR(t)** snapshot, reflecting Path‑A truth evaluation outcomes without modifying meaning or semantic_core.  
**Focus:** Freeze truth‑tag fields (`truth_tags{}`) derived from Path‑A truth‑evaluation primitives; encode factuality, contradiction status, uncertainty, and truth‑relevant indicators for downstream Path‑B primitives (LI, TrigRB, REx).  
**When:** Runs during late Path‑A finalization, immediately before OuBA commit; executes once per turn and never during Path‑B realization.  
**Why:** Provide a stable, replay‑safe truth‑tag substrate so Path‑B can react to truth metadata without re‑entering Path‑A or performing truth evaluation.  
**Is not:** A truth evaluator; a semantic interpreter; a meaning constructor; a governance primitive; TPTB performs no inference, no repair, and no semantic_core mutation.  
**Example:** Path‑A truth evaluation marks a claim as `truth_tags{ factual_conflict=false, uncertainty=low }`; TPTB freezes these tags into SSR(t) for LI and TrigRB.  
**Normative home:** 20.64_tptb_prim.md.

## **CoHI (Conversation History Integrator) — 20.113 (Corrected)**  
**Purpose:** Imports conversation‑level structural continuity and historical inference from the COB/CIL loop into the **SSR(t)** snapshot so Path‑B primitives operate on a meaning substrate enriched with cross‑turn structure and turn‑local truth/safety metadata.  
**Focus:** Deterministic, read‑only integration over two inputs: (1) **SSR(t)** (including `truth_tags` and `safety_flags`) and (2) COB/CIL structures (structural_history, referential_history, conversation_objects, topic_threads, continuity_markers). CoHI performs no new inference; it normalizes and projects these into `ssr.continuity_fields`.  
**When:** Runs at the **start of Path‑B**, after SSR(t) is produced and after COB/CIL have been updated for the prior turn; executes once per turn, before LI.  
**Why:** Enables LI, REx, RPlan, and RPU to operate on SSR(t) enriched with cross‑turn continuity, ensuring referential stability and coherent multi‑turn realization.  
**Is not:** A memory system; a planner; an inference engine; a scorer; a router; a semantic interpreter.  
**Example:** COB/CIL maintain a conversation object for “the dataset we discussed earlier”; CoHI merges this into `ssr.continuity_fields`, enabling LI to interpret “run it again” correctly.  
**Normative home:** 20.113.

**Focus:** Input‑side primitives (InB→IIInB→IE→CEx→CE→ISc→TPU→OB→TR→RB→OB) or the no‑correction path (InB→OB→TR→RB→OB), plus OB‑set routing cycles (OB₀→RB→{OB₁…OBₙ}→CTP→RB) until Truth/Done completion.  
**When:** Runs every input cycle until Truth/Done evaluation stabilizes and the turn‑final TP is produced; Path A ends at the meaning boundary (OuBA), after which Path B begins.  
**Why:** Ensures meaning is built deterministically, replayably, and independently of realization, with all corrections and routing resolved before any B‑side processing.  
**Is not:** A realization pipeline; a truth evaluator; a safety engine; a generator of surface text; a writer of MTP.  
**Example:** OB‑set routing produces multiple OBs in parallel; CTP merges them into a single TP snapshot for the next RB arbitration, continuing until Truth/Done signals completion.  
**Normative home:** 20.705


---

## Path B (Realization & Expression) — Process Block
**Purpose:** Realizes the finalized TP into surface‑form output without altering meaning, using deterministic planning and seed‑isolated expression mapping.  
**Focus:** LI‑prm→MLI→REx→RPlan→RPU→OuB→Response Generator; deterministic meaning‑layer inference (MLI) precedes realization planning; the Response Generator performs seed‑isolated expression mapping using TPTB/TPSF and Path‑B realization metadata.  
**When:** Runs after Path A completes and the meaning boundary (OuBA) is finalized; Path B begins at TrigRB and proceeds through SRP‑selected realization plans to final expression.  
**Why:** Ensure expression is deterministic, replay‑stable, truth/safety‑aware, and strictly consistent with Path‑A meaning, without re‑entering or modifying meaning construction.  
**Is not:** A meaning writer; a semantic interpreter; a truth evaluator; a safety engine; a generator of new meaning; a contributor to MTP.  
**Example:** Given identical (TP, seed), Path B produces identical surface text regardless of OB‑set routing or Path‑A correction structure.  
**Normative home:** 20.111, 20.705, 20.30.080

## **Supervisory Processes (Cross‑Pipeline Control) — Process Block**  
**Purpose:** Provides deterministic supervisory control for mismatch detection, correction gating, IB instantiation, and nondeterminism boundaries.  
**Focus:** IMR evaluation consumes evaluator_signal and TP/MTP deltas, classifies mismatches (A/B/C), emits CorrectionTrigger for Type B, and gates Type C through GB; IB‑Creation‑Request prevents automatic IB instantiation and requires GB evaluation; MB observes all supervisory signals; Random Seed Boundary confines nondeterminism to B‑side expression.  
**When:** Runs concurrently with or immediately after Path A/B events depending on trigger conditions.  
**Why:** Ensures bounded, auditable correction and prevents uncontrolled escalation or unsafe inquiry creation.  
**Is not:** A meaning writer; a realization primitive; a governance basin; a semantic interpreter.  
**Example:** MI_INCOMP triggers IB‑Creation‑Request, which forces GB evaluation before any IB is instantiated.  
**Normative home:** 20.17, 20.30, 20.45, 20.70, 20.207.

## **Post‑TS Processes (TB → IB → GBIB → GB) — Process Block**  
**Purpose:** Executes the Interpretive Basin Chain (IBC) after Path B to evaluate ambiguity, truth, safety, and governance outcomes over the finalized meaning state.  
**Focus:** TB performs truth‑state evaluation; IB performs ambiguity analysis and generates clarification proposals; GBIB applies governance rules, USP constraints, truth‑tags, safety‑flags, and MTP‑commit boundaries to filter or escalate proposals; GB performs final global governance evaluation and produces `governance_outcome{}` for TS.  
**When:** Runs only after Path B realization completes and a stable TP/MTP commit exists; never runs during Path A or Path B.  
**Why:** Ensures ambiguity handling, clarification decisions, and governance outcomes are deterministic, auditable, and policy‑aligned, preventing IB or Path B from making unsupervised decisions.  
**Is not:** A meaning writer; a realization primitive; a semantic interpreter; a TP or MTP modifier; a neural inference path.  
**Example:** IB proposes `ask_for_antecedent`; GBIB validates it under USP/TPTB/TPSF; GB authorizes `issue_clarification` as the final governance outcome.  
**Normative home:** 20.80.

## Four‑Path Model (TS Processing Paths) — Process Block
**Purpose:** Prevent architectural drift by enforcing four distinct, non‑overlapping TS processing trajectories selected at InB based on ambiguity state, governance outcomes, and meaning‑layer requirements.  
**Focus:** Four deterministic, mutually exclusive paths: Normal Path, Clarification Path, Inference Path, Post‑TS Interrogation Path — each with its own entry conditions and isolated execution flow.  
**When:** Path chosen at InB using TB/IB ambiguity state, governance signals, and Path‑A/B readiness.  
**Why:** Ensure deterministic routing, prevent stage confusion, and isolate clarification, inference, and interrogation behaviors.  
**Is not:** Merged pipeline; semantic generator; meaning writer.  
**Example:** Ambiguous input triggers Clarification Path; MLI‑required interrogation triggers Inference Path.  
**Normative home:** Architecture discussion.

# **4. Governance Rules**

## **Clarification Rules — Governance Block**  
**Purpose:** Determines when the system may issue a clarification request instead of producing a direct answer, ensuring ambiguity is resolved only when permitted by governance policy.  
**Focus:** Clarification allowed only when ambiguity is material, user‑intent cannot be safely inferred, and governance permits inquiry; suppressed when meaning is sufficiently determinate or when clarification would violate USP or safety constraints.  
**When:** Evaluated during TB→IB→GBIB→GB after Path B realization and before any clarification is emitted.  
**Why:** Prevents unnecessary or unsafe clarifications and ensures all clarifications are governance‑authorized.  
**Is not:** A semantic primitive; a meaning writer; an IMR mechanism; an automatic IB trigger.  
**Example:** IB proposes `ask_for_antecedent`; GBIB validates under USP; GB authorizes or suppresses the clarification.  
**Normative home:** 20.80.

---

## **Suppression Rules — Governance Block**  
**Purpose:** Enforces conditions under which clarification, interrogation, or inference proposals must be suppressed to maintain safety, truth integrity, and user‑intent fidelity.  
**Focus:** Suppression triggered when proposals violate USP, conflict with truth/safety tags, exceed allowed inquiry depth, or would cause user‑intent distortion.  
**When:** Applied in GBIB and finalized in GB during governance evaluation.  
**Why:** Ensures the system does not escalate inquiry or inference beyond what governance permits.  
**Is not:** A routing rule; a Path A/B primitive; an IMR mismatch classification.  
**Example:** IB proposes a follow‑up question; GBIB suppresses it because USP forbids interrogative expansion in the current context.  
**Normative home:** 20.80.

---

## **Truth–Safety Precedence Rules — Governance Block**  
**Purpose:** Establishes deterministic precedence between truth‑evaluation outcomes and safety‑evaluation outcomes when they conflict.  
**Focus:** Safety overrides truth when user harm or policy violation is possible; truth overrides ambiguity when meaning is determinate and safe; both feed into GB for final governance outcome.  
**When:** Evaluated in GBIB and GB after TB and TPSF/TPTB signals are available.  
**Why:** Ensures safe, truthful, policy‑aligned behavior under conflict conditions.  
**Is not:** A semantic inference rule; a TP writer; a Path A/B primitive.  
**Example:** A truthful answer is available but unsafe; safety precedence suppresses direct expression and GB authorizes a safer alternative.  
**Normative home:** 20.80.

---

## **USP Precedence Rules — Governance Block**  
**Purpose:** Ensures that User‑Specified Preferences (USP) constrain governance decisions without overriding safety or truth requirements.  
**Focus:** USP applied after safety and truth evaluation but before final governance outcome; USP may suppress or permit clarifications, tone, or style choices.  
**When:** Applied in GBIB and finalized in GB.  
**Why:** Ensures user preferences shape expression while remaining subordinate to safety and truth.  
**Is not:** A safety override; a truth override; a meaning‑layer inference.  
**Example:** User prefers no clarifications; USP suppresses IB proposals unless safety requires them.  
**Normative home:** 20.80.

---

## **Governance Outcome Rules — Governance Block**  
**Purpose:** Defines how GB produces the final `governance_outcome{}` that controls whether the system answers, clarifies, suppresses, or redirects.  
**Focus:** GB integrates TB truth‑state, IB ambiguity proposals, GBIB governance filters, USP, TPTB, TPSF, and safety constraints to produce a single deterministic outcome.  
**When:** Final step of the Post‑TS governance chain before output is emitted.  
**Why:** Ensures all outputs are policy‑aligned, safe, truthful, and consistent with user intent.  
**Is not:** A meaning writer; a realization primitive; a neural inference.  
**Example:** GB authorizes `issue_clarification`, `answer_directly`, or `suppress_and_redirect` based on combined governance signals.  
**Normative home:** 20.80.

---

## Replay‑Determinism Rules — Governance Block
**Purpose:** Ensure governance outcomes are fully deterministic and replay‑safe given identical TP/MTP commits and identical seeds.  
**Focus:** Deterministic governance evaluation across TB→IB→GBIB→GB; nondeterminism confined to Path‑B expression under the Random Seed Boundary.  
**When:** Applied throughout DF and enforced before output emission.  
**Why:** Guarantee auditability, reproducibility, and compliance with TS determinism requirements.  
**Is not:** Randomness generator; meaning writer; Path‑A/B primitive.  
**Example:** Replaying the same TP/MTP commit with the same seed yields identical governance outcomes and identical surface‑form output.  
**Normative home:** 20.80, 20.207.

# 5. TS-Level Concepts

## ΔH% (DeltaHPercent) — 20.30
**Purpose:** Represent the incremental structural‑uncertainty contribution produced by each Path‑A interpretive stage (OB, merge, truth‑hypotheses evaluation), ensuring uncertainty evolution is deterministic, auditable, and replay‑safe.  
**Focus:** Encode local uncertainty adjustments from structural gaps, unresolved branches, missing‑mass indicators, and interpretive signals; contribute to the deterministic computation of H%.  
**When:** Generated at each Path‑A interpretive step and accumulated before truth/completion evaluation; included in the update_structure validated and committed by RBU.  
**Why:** Provide a deterministic, non‑probabilistic mechanism for tracking uncertainty evolution without latent‑space inference or stochastic estimation.  
**Is not:** Probability; confidence score; truth commitment; entropy functional; Path‑B computation.  
**Example:** Merge detects unresolved semantic branches and increases ΔH%; truth‑hypotheses evaluation stabilizes a hypothesis and decreases ΔH%, lowering H% in the next cycle.  
**Normative home:** 20.30.030, 20.30.060.

---

## H% (UncertaintyPercent) — 20.30
**Purpose:** Represent the accumulated structural‑uncertainty state of the TP/MTP after integrating ΔH% contributions across Path‑A interpretive stages.  
**Focus:** Encode the current structural‑uncertainty level derived from unresolved branches, structural gaps, and interpretive signals; used by truth‑hypotheses and completion evaluation to determine stability and readiness for commit.  
**When:** Updated during Path‑A after merge and truth‑hypotheses evaluation; included in the update_structure validated and committed by RBU.  
**Why:** Provide a deterministic, replay‑safe uncertainty measure that cleanly separates structural uncertainty from truth evaluation, confidence, or probabilistic reasoning.  
**Is not:** Probability; confidence score; truth band; global uncertainty model; Path‑B computation.  
**Example:** If ΔH% accumulates due to unresolved semantic branches, H% increases; if truth‑hypotheses evaluation stabilizes a hypothesis, H% decreases, signaling readiness for completion.  
**Normative home:** 20.30.060, 20.30.070.

## **Grounding Entropy (H\_{Kn_{coarse}}, H\_{Kn_{medium}}, H\_{Kn_{fine}})**  
**Purpose:** Quantify grounding certainty at each abstraction tier (coarse, medium, fine) during KnB processing; provide Path‑B with deterministic entropy signals for tier selection, expression safety, and surgical‑question triggers.  
**Focus:** Measure precision of grounded knowledge relative to maximum attainable precision; reflect ambiguity, contextual stability, and domain‑specific resolution; expose entropy values as explicit SSR fields for downstream routing and realization.  
**When:** Computed during each grounding stage: KnC computes $H\_{Kn_{coarse}}$ after coarse grounding; KnM computes $H\_{Kn_{medium}}$ after medium grounding; KnF computes $H\_{Kn_{fine}}$ after fine grounding; all values are written into SSR before Path‑B executes.  
**Why:** Enable TS to select the correct abstraction tier without inference or probabilistic reasoning; ensure deterministic behavior by making uncertainty explicit and measurable; prevent Path‑B from expressing overly precise meaning when grounding entropy is high.  
**Is not:** A truth metric; semantic confidence score; probabilistic estimate; grounding entropy never performs inference, semantic repair, or truth evaluation and never modifies grounded fields.  
**Example:** KnC attaches coarse identity (“dog”) and computes $H\_{Kn_{coarse}}$; KnM refines identity (“retriever”) and computes $H\_{Kn_{medium}}$; KnF resolves identity (“Golden Retriever”) and computes $H\_{Kn_{fine}}$, allowing Path‑B to select coarse/medium/fine expression based on total entropy $H_{total} = H_{SSR} + H\_{Kn_{tier}}$.  
**Normative home:** 20.48.010–030 (KnC/KnM/KnF); 20.52 (SSR); 20.705 (Path‑A → KnB → Path‑B flow); ts_numeric_policy.md (entropy definitions).

**When:** Invoked during Path‑A meaning construction prior to routing; activated deterministically based on lane‑local TP structure, routing context, and orthogonality_signature; contributes evidence and residue before TR and RB execution.  
**Why:** Provides deterministic, replay‑safe structural interpretation that grounds routing, ΔH% evolution, and downstream meaning construction without semantic inference or identity‑conditioned processing.  
**Is not:** A semantic basin; a truth evaluator; a routing arbiter; a geometric meta‑basin; an identity‑conditioned primitive; a Path‑B computation; a generator of TP.TR or truth_hypotheses.  
**Example:** SOB/SROB/CnOB extract structural and constraint residue; SmOB emits pre‑semantic residue; OB sets `tr_needs_update` when structural cues change, enabling TR to recompute routing.

## MCS (Meaningful Cognitive Step) — 20.30.040
**Purpose:** Defines the atomic, auditable unit of cognitive work in TS, enabling deterministic accounting of interpretive, structural, and evaluative operations across Path A.
**Focus:** Counts only meaningful, user‑relevant cognitive transformations (OB/TB interpretation, merge decisions, truth‑hypothesis evaluation, completion evaluation, routing decisions) while excluding zero‑cost metadata updates and mechanical bookkeeping.
**When:** Incremented during Path A whenever TS performs a qualifying interpretive or evaluative action; never incremented during Path B or for non‑cognitive operations.
**Why:** Ensures TS reasoning is measurable, bounded, replay‑safe, and free of hidden computation; provides a stable basis for invariants, performance guarantees, and correctness proofs.
**Is not:** A token count; a FLOP measure; a latency metric; a routing hop; a metadata write; a safety or truth tag; a Path B operation.

## semantic_core — 20.30

**Why:** Provide a deterministic, replay‑safe semantic substrate that isolates meaning construction (Path‑A) and realization (Path‑B) from governance, archival, and historical evaluation.  
**Is not:** Path‑A structure; routing structure; safety model; truth‑metadata object; latent embedding; Path‑B construct; stylistic or expressive representation.

## update_structure — 20.30

**Why:** Provide a single, auditable, deterministic object capturing the entire Path‑A evolution of the TP, enabling RBU to validate commit‑readiness without re‑running computation.  
**Is not:** semantic_core; semantic object; truth model; routing decision; latent representation; Path‑B construct; partial update; incremental diff.  
**Example:** After merge produces merge_result and truth‑hypotheses evaluation produces TPTB/TPSF, update_structure aggregates truth_hypotheses, TPTB, TPSF, ΔH%, H%, merge_result, and routing metadata into a single validation envelope for RBU.

**Is not:** A truth‑metadata object; a routing decision; a latent embedding; a Path B construct; a stylistic or expressive representation.

## DF — Inquiry‑side evaluation flow

**When:** Invoked only after Path‑A commits meaning via OuBA; operates exclusively on committed, immutable meaning.

**Is not:** Meaning‑construction flow; semantic writer; Path‑A participant; DF never modifies semantic_core, truth relations, or any Path‑A structure.

## HCF — Historical Conversation Flow

**Why:** Maintain deterministic, auditable long‑term conversational context; ensure continuity, referential stability, and multi‑turn inference derive only from committed TP history; provide Path‑B with structured, policy‑safe continuity without requiring Path‑B primitives to read or manipulate historical memory directly.  
**Is not:** Meaning‑construction flow; truth evaluator; governance subsystem; HCF does not modify TP, semantic_core, or Path‑A state; does not participate in real‑time realization.  
**Example:** OuBB commits a turn‑final TP; HCF ingests it and updates MTP; COB constructs or updates conversation objects; CIL derives long‑horizon inference; CoHI merges these historical structures with the next turn’s Path‑B TP to provide continuity‑aware realization.
