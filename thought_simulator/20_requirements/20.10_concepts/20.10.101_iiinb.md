# **20.10.101 — IIInB (Intake Inference Normalization Block)**  
### *Conceptual Overview*

---

## **Purpose**

The IIInB ensures that the **input text (TP)** is structurally complete, normalized, and ready for semantic interpretation.  
It operates **before** semantic meaning exists and **before** Pipeline A begins.  
It is a **bounded, deterministic, pre‑semantic expansion primitive**.

> **IIInB fixes the *text* so meaning can be built.**

---

# **What IIInB *Is***  
Each item includes a concrete example.

---

## **1. A TP‑level repair module**  
IIInB operates **only** on the TP (text packet).  
It never touches semantic structures.

**Example:**  
User input:  
> “add milk eggs bread”  
IIInB normalizes TP to:  
> “add milk, eggs, and bread”

**Handled Upstream/Downstream:**  
→ Output goes to **Pipeline A**, which constructs semantic_core.

---

## **2. A bounded pattern→expansion engine**  
IIInB applies deterministic expansions based on patterns and USP rules.

**Example:**  
User input:  
> “again”  
IIInB expands to:  
> “repeat the last action”

**Handled Upstream/Downstream:**  
→ Expansion is bounded; no semantic inference is performed.  
→ Semantic interpretation happens later in **Pipeline A**.

---

## **3. A shorthand expander**  
IIInB expands user shorthand into explicit surface forms.

**Example:**  
User input:  
> “same as before”  
IIInB expands to:  
> “repeat the previous command”

**Handled Upstream/Downstream:**  
→ Semantic meaning of “previous command” is resolved later by **ISc** if needed.

---

## **4. A surface normalizer**  
IIInB inserts missing surface tokens when the pattern is deterministic.

**Example:**  
User input:  
> “turn on lights kitchen”  
IIInB expands to:  
> “turn on the lights in the kitchen”

**Handled Upstream/Downstream:**  
→ Semantic interpretation of “lights” and “kitchen” is handled by **Pipeline A** and **ISc**.

---

## **5. A USP‑governed intake corrector**  
IIInB uses user‑specific patterns (USP) to normalize habitual omissions.

**Example:**  
If USP says the user omits “the”:  
> “open door”  
becomes  
> “open the door”

**Handled Upstream/Downstream:**  
→ Semantic role assignment happens later in **Pipeline A**.

---

## **6. A pre‑Pipeline A primitive**  
IIInB runs **before** semantic_core construction.

**Example:**  
User input:  
> “again”  
IIInB expands TP → Pipeline A builds meaning from the expanded TP.

**Handled Upstream/Downstream:**  
→ **Pipeline A** consumes the normalized TP.

---

## **7. A deterministic, non‑creative module**  
IIInB never guesses or chooses between alternatives.

**Example:**  
User input:  
> “put it there”  
IIInB does **nothing**, because “it” and “there” are ambiguous.

**Handled Upstream/Downstream:**  
→ Ambiguity is resolved (or flagged) by **Detection + ISc**.

---

# **What IIInB *Is Not***  
Each item includes a concrete example **and the primitive that *does* handle it**, ensuring no architectural holes.

---

## **1. Not semantic**  
IIInB does not interpret meaning.

**Example:**  
User input:  
> “schedule meeting”  
IIInB does **not** infer the time.

**Handled By:**  
→ **ISc**, which fills missing semantic roles using the envelope.

---

## **2. Not referent‑resolving**  
IIInB does not resolve pronouns or entities.

**Example:**  
User input:  
> “turn it on”  
IIInB does **nothing**.

**Handled By:**  
→ **ISc**, which resolves “it” using the envelope and projection rules.

---

## **3. Not part of the Detection/Projection loop**  
IIInB does not detect semantic defects or compute repairs.

**Example:**  
User input:  
> “book a flight to Paris from Paris”  
IIInB does **not** detect contradiction.

**Handled By:**  
→ **Detection** (finds contradiction)  
→ **ISc** (computes nearest valid meaning)

---

## **4. Not envelope‑aware**  
IIInB does not use long‑duration meaning, CIL, COB, or global referents.

**Example:**  
User input:  
> “call her”  
IIInB cannot determine who “her” is.

**Handled By:**  
→ **ISc**, which uses envelope referents and long‑duration meaning.

---

## **5. Not inferential**  
IIInB does not choose between multiple possible expansions.

**Example:**  
User input:  
> “open it”  
IIInB does **nothing**.

**Handled By:**  
→ **ISc**, which computes the nearest valid meaning $M'$.

---

## **6. Not creative**  
IIInB cannot invent missing information.

**Example:**  
User input:  
> “send message”  
IIInB does **not** guess the recipient or content.

**Handled By:**  
→ **ISc**, which may propose a correction if the envelope provides a unique candidate.

---

## **7. Not allowed to modify semantic_core, TP.TR, or MTP**  
This is explicitly forbidden in 20.101.

**Example:**  
User input:  
> “again”  
IIInB expands TP only; it does **not** modify semantic_core.

**Handled By:**  
→ **Pipeline A**, which constructs semantic_core from the normalized TP.

---

# **Why IIInB Exists**

Without IIInB:

- semantic_core would receive malformed TP  
- ISc would be overloaded with surface‑level repair  
- projection would become unstable  
- ambiguity would leak into meaning construction  
- shorthand and elliptical input would break the pipeline  

IIInB ensures that **semantic_core receives clean, normalized, structurally complete text**.

---

# **Summary**

> **IIInB fixes the *text* so meaning can be built.  
> ISc fixes the *meaning* so it can be committed.**

This file must always reflect the capabilities defined in **20.101**.  
If 20.101 changes, **20.10.101 must be updated accordingly**.
