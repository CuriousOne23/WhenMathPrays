# **2. Architectural motivation**

TS only works if every part of the system is built from **simple, bounded, well‑defined primitives**.  
20.500 and 20.510 created two major foundations:

- **20.500** separated the system into two pipelines (A‑side semantic, B‑side execution) and established safe boundaries.  
- **20.510** taught the system how to handle messy input and incomplete meaning safely.

But after those two refactors, one essential piece was still missing:

> **The runtime had no minimal, bounded inference capability to enforce the boundaries created in 20.500 and the messy‑input rules created in 20.510.**

The architecture could describe the rules,  
but nothing in the runtime could apply them.

This is the real reason 20.520 was necessary.

---

## **2.1 WHY 20.500 was necessary**

Before 20.500, everything lived in one pipeline:

- semantic reasoning  
- execution planning  
- execution expression  
- routing  
- scoring  
- TP mutation  

This caused:

- nondeterministic behavior  
- replay failures  
- semantic_core corruption  
- routing instability  
- no safe boundaries  
- no writer authority  

**20.500 fixed this by creating the dual pipeline and envelope boundaries.**

It gave TS structure — a skeleton.

---

## **2.2 WHY 20.510 was necessary**

After 20.500, TS still had no way to handle:

- messy input  
- incomplete meaning  
- malformed structures  
- repair decisions  
- input‑layer state  

This caused:

- inconsistent intake behavior  
- routing influenced by malformed input  
- replay divergence  
- no way to compute ΔH% safely  

**20.510 fixed this by creating Track H and the messy‑input primitives.**

It gave TS ears — a way to hear messy input safely.

**Summary after 20.500 and 20.510:**  
TS now has:

- a dual pipeline  
- safe boundaries  
- messy‑input handling  
- incomplete‑meaning semantics  

But the runtime still lacks the **minimal inference layer** needed to enforce these rules. That gap is what 20.520 addresses.

---

## **2.3 WHY 20.520 was necessary**

**20.520 was required because TS needed a minimal, bounded inference layer to enforce boundaries, validate merges, score meaning, and update TP deterministically. Routing, XP, OuB, TR, RB, and the structural documents all had to be aligned with this new inference layer.**

After 20.500 and 20.510, the architecture had:

- a dual pipeline  
- safe boundaries  
- messy‑input handling  
- incomplete‑meaning semantics  

But the runtime still lacked one essential capability:

- TS could not yet tell whether meaning was complete,  
- could not score meaning,  
- could not validate merge,  
- and could not update TP deterministically.

The architecture had rules,  
but the runtime had no minimal inference layer to enforce them.

### **1. TPU and ISc were required to make the architecture enforceable**

TPU and ISc are not “extra modules.”  
They are the **minimum inference primitives** needed to:

- detect incomplete meaning  
- compute ΔH%  
- validate merge output  
- enforce safe‑boundary commits  
- produce deterministic TP(N+1)

Without TPU and ISc, the dual pipeline was structurally incomplete.

### **2. Routing needed to be aligned with this inference layer**

Routing modules (SRP, routing tables, TrigRB) were written before:

- ΔH%  
- incomplete meaning  
- canonical ordering  
- safe‑boundary commits  

They needed to be updated so routing decisions were:

- deterministic  
- aligned with the dual pipeline  
- aligned with the new inference primitives  

### **3. XP and OuB needed enforceable boundaries**

XP and OuB were defined before the inference layer existed.  
They needed ΔH% and incomplete‑meaning signals to behave safely.

### **4. TR and RB needed to be realigned after Track H**

Track H changed the meaning of:

- incomplete meaning  
- messy input  
- ΔH%  

TR and RB needed to be updated to match.

### **5. 20.38 and 20.39 needed to be modernized**

These documents still reflected the pre‑20.500 world and needed to be aligned with:

- envelope boundaries  
- deterministic replay  
- inference‑aware structures  

### **6. The entire 20‑series needed a consistency sweep**

After three major refactors, every document needed to be checked for:

- boundary violations  
- replay determinism  
- routing correctness  
- meaning‑generation violations  
- XP/OuB alignment  
- TR/RB consistency
