# **2. Architectural Motivation (The Missing WHY)**

## **2.1 WHY 20.500 Was Necessary**  
### **20.500 — Refactoring for Dual TS Pipeline**

Before 20.500, the system had **no formal separation** between:

- semantic reasoning  
- execution planning  
- execution expression  
- governance  
- routing  
- scoring  
- TP mutation  

Everything lived in one conceptual pipeline, which caused:

### **Architectural contradictions**
- semantic_core could be mutated by B‑side modules  
- exec_plan and exec_trace had no envelope boundaries  
- replay could not be guaranteed  
- meaning generation could occur in the wrong modules  
- routing_epoch_id could leak into semantic reasoning  
- TP updates were nondeterministic  
- governance records had no stable placement  

### **Missing primitives**
- envelope model  
- A/B pipeline separation  
- safe boundaries  
- deterministic replay harness  
- routing_epoch_package  
- writer‑authority model  

### **Failure modes**
- nondeterministic TP updates  
- semantic_core corruption  
- replay divergence  
- routing instability  
- governance inconsistency  
- impossible to implement 40‑series safely  

### **20.500 solved this by introducing:**
- A/B pipeline separation  
- envelope boundaries  
- deterministic replay  
- routing_epoch discipline  
- safe boundaries  
- governance placement  
- writer authority  

**20.500 created the modern TS architecture.**

---

## **2.2 WHY 20.510 Was Necessary**  
### **20.510 — Track H Coordination (Semantic Input Correction)**

After 20.500, the architecture still had a major gap:

### **The system had no formal model for messy input.**

This caused:

### **Architectural contradictions**
- IIInB had no defined output contract  
- RB/TB had no messy‑input posture  
- semantic_core could not represent incomplete meaning  
- ΔH% could not be computed reliably  
- UPI/USP had no stable semantics  
- Track H state was mixed with runtime state  

### **Missing primitives**
- messy_input_record  
- input_repair_tag  
- incomplete‑meaning detection  
- Track H conversation‑layer state  
- UPI commit evaluation  
- USP version pinning  

### **Failure modes**
- semantic_core could contain unrepairable fragments  
- routing could be influenced by malformed input  
- XP could be triggered incorrectly  
- replay could diverge due to input repair  
- governance could not evaluate input quality  

### **20.510 solved this by introducing:**
- Track H as a separate program  
- messy‑input primitives  
- input repair boundaries  
- IIInB → RB → TB alignment  
- UPI/USP semantics  
- Track H conversation‑layer state  

**20.510 completed the intake side of the architecture.**

---

## **2.3 WHY 20.520 Was Necessary**  
### **20.520 — TPU/ISc + Routing Alignment Refactor**

After 20.500 and 20.510, the architecture still had unresolved seams:

### **Architectural contradictions**
- TPU was not fully defined  
- ISc was not fully defined  
- routing modules (SRP, TrigRB, routing tables) were inconsistent  
- XP lifecycle was unclear  
- OuB boundaries were ambiguous  
- TR and RB semantics were drifting  
- 20.38 and 20.39 were outdated  
- cross‑document invariants were not aligned  

### **Missing primitives**
- writer‑authority enforcement  
- ΔH% scoring  
- incomplete‑meaning detection  
- canonical ordering for TP updates  
- deterministic trigger mapping  
- routing_epoch_package schema  
- safe‑boundary commit rules  

### **Failure modes**
- nondeterministic TP updates  
- inconsistent routing behavior  
- semantic_core corruption  
- meaning generation in the wrong modules  
- replay nondeterminism  
- XP misalignment  
- OuB overreach  
- TR/RB contradictions  

### **20.520 solved this by:**
- finalizing TPU  
- finalizing ISc  
- aligning routing (SRP, routing tables, TrigRB)  
- aligning XP lifecycle  
- enforcing OuB boundaries  
- validating TR and RB  
- updating 20.38 and 20.39  
- re‑checking all 20‑series documents  

**20.520 completes the runtime alignment.**
