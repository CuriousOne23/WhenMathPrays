# 20.50 RB Requirements

**Document ID:** 20.50  
**Version:** 0.3  
**Date:** 2026-06-06  
**Status:** Approved v0.3 — §8 second-pass GATE (2026-06-07; CuriousOne23, Copilot, Grok; boundary check only; no edits)

## Purpose

Defines deterministic **Relational Basin (RB)** behavior for routing, transition control, split/merge arbitration, and cross-lane semantic flow within **Pipeline A (meaning construction)**.

RB is the **relational topology authority** — it determines how TPs traverse basins, how lanes form and resolve, and when the TR routine must recompute. RB consumes committed `TP.TR` read-only; it SHALL NOT derive or write TR fields.

This module SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

**Integration contract:** TR gating and `RB_route(TP)` are normatively specified in [20.37](20.37_thought_router_tr_specification.md) §5; this document defines RB-specific routing and arbitration obligations.

**Namespace:** Relational Basin **RB** (Pipeline A) SHALL NOT alias Pipeline B **TrigRB** (semantic trigger detector per 20.12-015, 20.20).

## Parent Scope

- **Pipeline:** Pipeline A only — RB SHALL NOT read `exec_plan` or `exec_trace`
- **Routing bounds:** [20.90](20.90_ts_parameter_table.md) §B (`routing.fanout`, `routing.active_lanes`, `inquiry.depth`)
- **Messy-input:** parallel-trace routing per [20.17](20.17_messy_input_handling.md)
- **Numeric encoding:** routing-context ΔH% fields Q32.32 per [20.95](20.95_ts_numeric_policy.md)
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Non-Goals

- TR derivation (`TP.TR`) — TR routine only (20.37)
- OB pattern extraction — OB (20.40)
- TB truth interpretation — TB (20.60)
- GB supervisory policy scoring — 20.16/20.80
- Pipeline B SRP/TrigRB/IMR scheduling
- DCB geometric event consumption — TR routine only (20.37 §4.4)

## 1. Dual-Pipeline Boundary Discipline

| Concern | RB posture |
|---------|------------|
| `TP.TR`, `thought_router_fields` | **Read-only** for routing; **no write** |
| `tr_needs_update` | **Read-only** for TR gating; RB SHALL NOT clear or set the dirty flag |
| `exec_plan`, `exec_trace`, `supervisory` | **No read/write** |
| `routing_epoch_id` | **No read/write; no advance** |
| `truth_hypotheses` | **No read for routing derivation; no write** |
| `messy_input_record` | Read-only routing context; **no resolve/smooth/clear** |
| Seed | **SHALL NOT influence** routing outcomes (HLR-20.012-010) |

**Pipeline B forbidden:** OuB, OpBeh/OBG/XlateR, IMR, SRP SHALL NOT alter RB routing decisions retroactively or mutate routing metadata in `semantic_core` without Pipeline A safe-boundary writes (20.17).

---

## 2. TR Gating and Routing Equation

RB SHALL implement the deterministic routing contract from [20.37](20.37_thought_router_tr_specification.md) §5:

```
RB_route(TP) = f(TP.input_fields, TP.TR, TP.tr_needs_update, TP.deltaH, TP.lineage, TP.routing_metadata, policy_signature)
```

| Rule | Semantics |
|------|-----------|
| TR gate | RB SHALL route TP to the TR routine **iff** `TP.tr_needs_update = true` (HLR-20.050-027) |
| Stale TR | When `tr_needs_update = true`, RB SHALL NOT infer downstream routing from stale or missing `TP.TR` |
| Fresh TR | When `tr_needs_update = false`, RB SHALL route using committed `TP.TR` and `routing_semantics` |
| TR write | RB SHALL NOT write `TP.TR` or clear `tr_needs_update` (HLR-20.050-028) |

**Cycle ordering (normative):** RB → OB → [DCB observes] → RB checks `tr_needs_update` → (if true) TR routine → RB → next module (20.37 contract).

---

## 3. Routing Filter Object

RB SHALL compute a deterministic **routing filter** each cycle (HLR-20.050-021, -022):

```text
routing_filter {
  selected_ob_ids[],       // canonical sort by ob_id
  lane_projections[],
  delta_h_routing_context, // Q32.32
  firing_order[],          // deterministic sequence
  transition_rationale[],
  policy_justification{},
  inquiry_escalation?,
  merge_eligibility?,
  split_directive?
}
```

The routing filter SHALL be representable, inspectable, logged, and replayable. Nested maps and ID arrays SHALL use canonical ordering before export and replay diff (HLR-20.050-038).

**`transition_rationale[]` ordering (HLR-20.050-044):** Entries SHALL sort by stable `rationale_id` lexicographic; nested reason-code arrays SHALL sort lexicographically; numeric weight fields SHALL be canonical Q32.32 before export and replay diff.

## 4. Routing Bounds (20.90)

| Parameter | Default | Enforcement |
|-----------|--------:|-------------|
| `routing.fanout.max_per_tp` | 6 | Max OB targets per TP per cycle |
| `routing.active_lanes.max` | 24 | Max active lanes per cycle |
| `inquiry.depth.max` | 8 | Max inquiry depth per branch |

Exceeding bounds SHALL produce deterministic reject-with-audit or bounded degrade per 20.30 §8 — **never silent branch drop** (HLR-20.050-024, -026, HLR-20.050-029).

---

## 5. Split / Merge Arbitration

RB is the **sole** split/merge arbitration authority in Pipeline A (OB SHALL NOT arbitrate per 20.40).

- Split/merge SHALL follow explicit policy rules with logged decisions (HLR-20.050-006)
- Lineage/provenance continuity SHALL be preserved (HLR-20.050-007)
- ΔH% contribution and missing-mass compatibility SHALL be preserved across lane flows (HLR-20.050-008)
- Under `conflict_flag = true`, RB SHALL preserve parallel traces; SHALL NOT force single-winner collapse except when `contradiction_status = GB_ARBITRATED` at GB-approved safe boundaries (20.17)

---

## 6. Messy-Input Routing (20.17)

| Class | RB obligation |
|-------|----------------|
| `MI_CONTRA` | Maintain parallel lane routing per `parallel_trace_ids[]`; no premature merge |
| `MI_VAGUE` | Route toward inquiry/TB refinement paths; no slot-fill routing |
| `MI_AFFECT` | Route to affect/stance/social TB modules per fixed policy table (20.17-028) |
| `MI_INCOMP` | Route toward IB-Creation-Request pathways; no silent gap-fill |
| `MI_NOISE` | Route on stabilized conceptual signals, not surface noise (HLR-20.050-009) |

RB SHALL NOT smooth contradiction, clear messy-input tags, or invent unstated content (HLR-20.050-010, HLR-20.050-030).

---

## 7. Approved Inputs and Overflow

**Approved read set (HLR-20.050-039, HLR-20.050-045):** RB MAY read only:

- lane-local TP projections: `TP.input_fields`, `TP.TR`, `tr_needs_update`, `TP.deltaH`, `TP.lineage`, `TP.routing_metadata`
- read-only MTP / `semantic_core` fields: `thought_router_fields.routing_semantics` context, `messy_input_record`, `overflow_metadata`, `stability_metadata`, `policy_signature`, `mtp_snapshot_id`

RB routing derivation SHALL NOT consume any MTP or `semantic_core` field outside this approved set (HLR-20.050-045).

**Explicit forbidden reads (HLR-20.050-043):** RB SHALL NOT read `truth_hypotheses` for routing derivation or split/merge arbitration; truth evaluation is downstream via TB (20.140). RB SHALL NOT read `exec_plan`, `exec_trace`, `routing_epoch_id`, `done_state` commitment fields, or supervisory envelope state.

On global bound exceedance, RB SHALL emit canonical overflow telemetry per 20.30 §8.3 (HLR-20.050-025) including deterministic fan-out reduction and lane truncation with explicit tagging (HLR-20.050-026). Under overflow, messy-input primary flags SHALL be preserved (20.17-031).

---

## 8. Replay and Determinism

- Routing decisions SHALL reproduce from `(TP state, read-only MTP context, policy_signature)` — seed excluded (HLR-20.050-004, HLR-20.012-010)
- RB SHALL NOT depend on TP creation order or allocation identity (HLR-20.050-040)
- Strip replay removing Pipeline B envelopes SHALL preserve routing filter logs and committed routing outcomes in `semantic_core` for Pipeline A equivalence (20.36 Class 1, HLR-20.050-036)

## Worked Example — TR Gate + Fan-Out Bound

| Step | Actor | Outcome |
|------|-------|---------|
| 1 | RB | Routes TP to OB |
| 2 | OB | Updates TR-input; sets `tr_needs_update = true` |
| 3 | RB | Sees stale flag; routes to TR routine (not downstream TB) |
| 4 | TR | Commits fresh `TP.TR`; clears dirty flag |
| 5 | RB | Computes `routing_filter`; 5 OB targets selected |
| 6 | Bound | `routing.fanout.max_per_tp` = 6 → 5 allowed; if 7 requested → deterministic truncate + `overflow_flag` |
| 7 | `MI_CONTRA` | Parallel lanes retained; no merge |
| 8 | Replay | Identical TR gate ordering and routing_filter bytes |

## Normative Requirements

1. HLR-20.050-001: RB SHALL deterministically select next OB targets and lane projections.
2. HLR-20.050-002: RB SHALL operate over bounded, explicit TP/MTP fields only and SHALL NOT rely on hidden or latent state.
3. HLR-20.050-003: RB SHALL NOT mutate truth-evaluation authority fields that belong to TB or truth/done stages.
4. HLR-20.050-004: RB routing decisions SHALL be replayable from deterministic logs.
5. HLR-20.050-005: RB SHALL enforce deterministic firing order, transition order, and lane-selection outcomes for identical effective state.
6. HLR-20.050-006: RB SHALL govern split/merge arbitration under explicit policy rules and SHALL log each arbitration decision.
7. HLR-20.050-007: RB split/merge decisions SHALL preserve lineage/provenance continuity required for replay and audit.
8. HLR-20.050-008: RB SHALL preserve ΔH% contribution and missing-mass accounting compatibility across routed/split/merged lane flows.
9. HLR-20.050-009: RB SHALL support deterministic handling of noisy or ill-formed input effects by routing based on stabilized conceptual signals, not surface-form noise.
10. HLR-20.050-010: RB SHALL NOT perform probabilistic inference, hallucinated correction, or unstated-content invention while routing.
11. HLR-20.050-011: RB SHALL expose deterministic test interfaces with explicit inputs, outputs, invariants, and failure modes.
12. HLR-20.050-012: RB SHALL expose test hooks sufficient for unit, integration, system, and property-based verification of routing and arbitration behavior.
13. HLR-20.050-013: RB telemetry SHALL include routing rationale fields, lane identifiers, split/merge decisions, transition outcomes, and ΔH% attribution context.
14. HLR-20.050-014: RB observability SHALL be consumable by MB, GB, OuB, and IB diagnostics without mutating RB core semantics.
15. HLR-20.050-015: RB SHALL define measurable TCU budgets (min/typ/max) and per-tick cost reporting for routing/arbitration operations.
16. HLR-20.050-016: RB overload/degradation behavior SHALL be deterministic, policy-bounded, and auditable.
17. HLR-20.050-017: RB behavior SHALL be platform-independent and SHALL NOT depend on hardware-, OS-, or runtime-specific nondeterministic effects.
18. HLR-20.050-018: RB contracts SHALL prioritize top-down thought-processing structure and semantic flow over implementation-specific mechanics.
19. HLR-20.050-019: RB interfaces and internal routing state SHALL remain modifiable, debuggable, and architecturally transparent.
20. HLR-20.050-020: RB documentation artifacts (contracts, routing policies, arbitration invariants, and telemetry fields) SHALL remain complete and version-aligned with TS architecture updates.
21. HLR-20.050-021: RB SHALL compute a deterministic routing filter that selects the OB set for the next TS cycle based on `TP.input_fields`, `TP.TR`, lane-local TP semantics, ΔH% potential, and explicit routing policy.
22. HLR-20.050-022: The RB routing filter SHALL be representable, inspectable, and replayable as a structured object containing selected OB identifiers, lane projections, ΔH% routing context, firing order, transition rationale, and policy justification.
23. HLR-20.050-023: RB SHALL define and apply deterministic relational-topology rules that govern TP traversal, lane formation/resolution, and cross-cycle semantic progression without transferring interpretation authority to OB or TB.
24. HLR-20.050-024: RB SHALL enforce applicable global boundedness constraints defined in 20.30 section 8, including global lane bounds, routing fan-out bounds, and per-basin TCU envelopes.
25. HLR-20.050-025: When a global bound condition affects routing, RB SHALL emit deterministic overflow/degradation tags and stability telemetry conforming to the canonical overflow field schema in 20.30 section 8.3.
26. HLR-20.050-026: RB degradation behavior under global-bound exceedance SHALL follow deterministic, policy-bounded actions, including deterministic fan-out reduction and lane truncation, and SHALL NOT silently drop routed branches without explicit tagging and logging.
27. HLR-20.050-027: RB SHALL route TP to the TR routine if and only if `TP.tr_needs_update = true`; when true, RB SHALL NOT infer downstream routing from stale or missing `TP.TR` (20.37).
28. HLR-20.050-028: RB SHALL NOT write `TP.TR`, `thought_router_fields`, or `tr_needs_update`; RB consumption of `TP.TR` is read-only.
29. HLR-20.050-029: RB SHALL enforce `routing.fanout.max_per_tp`, `routing.active_lanes.max`, and `inquiry.depth.max` defaults from 20.90 §B.
30. HLR-20.050-030: RB SHALL NOT smooth contradiction, fill underspec slots, clear messy-input tags, or collapse parallel traces unless `contradiction_status = GB_ARBITRATED` at GB-approved safe boundaries (20.17).
31. HLR-20.050-031: RB SHALL operate exclusively in Pipeline A; SHALL NOT read `exec_plan` or `exec_trace` (HLR-20.038-021).
32. HLR-20.050-032: RB SHALL NOT read `truth_hypotheses` for routing derivation; SHALL NOT read, write, or advance `routing_epoch_id` (HLR-20.050-043).
33. HLR-20.050-033: RB SHALL NOT consume DCB directional-change events directly; DCB influence reaches RB only through refreshed `TP.TR` after TR recompute (20.37 §4.4).
34. HLR-20.050-034: RB routing-context ΔH% fields in logs and `routing_filter` SHALL use canonical Q32.32 per 20.95; −0→+0 before comparison and export.
35. HLR-20.050-035: GB MAY consume RB telemetry read-only for supervisory gating; GB SHALL NOT override RB routing equations or write routing metadata on RB's behalf.
36. HLR-20.050-036: Strip replay removing Pipeline B envelopes SHALL preserve RB routing filter records and routing outcomes in `semantic_core` for Pipeline A-only equivalence (20.36 Class 1).
37. HLR-20.050-037: RB Relational Basin (Pipeline A) SHALL remain namespace-distinct from Pipeline B TrigRB per HLR-20.012-015 and 20.20.
38. HLR-20.050-038: `routing_filter` and RB telemetry arrays SHALL use deterministic canonical ordering before export, hash, and replay diff per 20.95/20.39.
39. HLR-20.050-039: RB SHALL read only the approved TP/MTP field set in §7; reads outside that set SHALL be conformance failures.
40. HLR-20.050-040: RB routing outcomes SHALL NOT depend on TP creation order, allocation sequence, or container address identity; only explicit canonical state and stable IDs MAY influence routing.
41. HLR-20.050-041: On `MI_AFFECT` detection, RB SHALL route to affect/stance/social TB modules per fixed policy table before Merge commits (20.17-028).
42. HLR-20.050-042: RB split/merge arbitration SHALL remain the sole Pipeline A authority for lane branch/consolidation decisions; OB and TB SHALL NOT perform split/merge arbitration.
43. HLR-20.050-043: RB SHALL NOT read `truth_hypotheses` from MTP or `semantic_core` for any routing, split/merge, or inquiry-escalation decision; truth evaluation consumes routing outcomes downstream via TB (20.140).
44. HLR-20.050-044: `transition_rationale[]` in `routing_filter` and RB telemetry SHALL use deterministic canonical ordering before export, hash, and replay diff — `rationale_id` lexicographic primary sort; nested reason-code arrays lexicographic; numeric weights canonical Q32.32.
45. HLR-20.050-045: RB routing outcomes SHALL depend only on the approved TP/MTP field set in §7; any read or implicit dependency on fields outside that set SHALL be a conformance failure.

## RB Invariants

- **Determinism:** identical effective input state yields identical routing, split, merge, and transition outcomes.
- **Isolation:** RB SHALL not assume OB evidence-extraction authority or TB truth-interpretation authority.
- **TR boundary:** RB gates TR execution; TR alone writes `TP.TR`.
- **Auditability:** each routed/split/merged decision SHALL be attributable to explicit deterministic policy and state inputs.

## Conformance

Implementation conforms when:

- TR gating matches 20.37 iff semantics for `tr_needs_update`
- `routing_filter` logged with canonical ordering; 20.90 bounds enforced
- no writes to `TP.TR`, `tr_needs_update`, or execution envelopes
- parallel traces preserved under `MI_CONTRA`; no unauthorized merge
- seed change does not alter routing for fixed inputs
- RB namespace distinct from TrigRB
- strip replay preserves routing outcomes in `semantic_core`
- RB does not read `truth_hypotheses`
- `transition_rationale[]` uses canonical ordering in replay export
- routing depends only on §7 approved MTP field allowlist

## Verification Focus

- 20.36 Class 1: strip B → routing_filter / lane outcomes stable
- 20.36 Class 2: overflow preserves messy-input primary flags through RB degrade
- 20.36 Class 5: `conflict_flag` lanes remain parallel through RB under governance stress
- 20.37 integration: stale TR blocks downstream routing until TR completes
- Fan-out exceed → deterministic truncate + overflow tags (not silent drop)
- Golden fixture rejects non-canonical `routing_filter` ordering
- TP creation-order permutation produces identical routing bytes
- Fixture rejects non-canonical `transition_rationale` ordering
- Harness rejects RB reads outside approved MTP field allowlist
