# **1. Purpose & Scope**  
*(Informative — no SHALLs)*

The Relational Basin (RB) defines the **deterministic routing, arbitration, and transition‑gating behavior** for Pipeline A. RB is the **relational topology authority**, determining how Thought Particles (TPs) traverse basins, form lanes, split, merge, and escalate inquiries.  
This aligns with the original description of RB as the topology authority   [Current page](citation-section://1146963897/3).

RB operates strictly within **Pipeline A**, consuming committed `TP.TR` in a **read‑only** manner and never deriving or mutating TR fields, consistent with the original specification   [Current page](citation-section://1146963897/4).

RB’s responsibilities include:

- Deterministic routing  
- TR gating  
- Split/merge arbitration  
- Multi‑core routing discipline  
- Enforcement of routing bounds  
- Messy‑input routing  
- Replay determinism  
- Structural transition approval  
- Canonical routing filter construction  

RB does **not** perform TR derivation, OB pattern extraction, TB truth interpretation, or any Pipeline B responsibilities, consistent with the original non‑goals list   [Current page](citation-section://1146963897/9).

RB’s boundary posture is defined by the SSG and preserved here in modernized form.  
The original boundary table is cited from the source document   [Current page](citation-section://1146963897/10).

### **Normative Requirements**

- **HLR‑20.050‑032** — RB SHALL NOT read `truth_hypotheses` or `routing_epoch_id`.  
- **HLR‑20.050‑048** — Pipeline B modules (OuB, OBG, IMR, SRP) SHALL NOT retroactively alter RB routing decisions or mutate routing metadata.

These requirements preserve the original boundary discipline semantics.

## **2.2 TR Gating Contract**

RB implements the deterministic TR‑gating contract defined in 20.37 §5.  
The original text states the routing equation and TR gating semantics   [Current page](citation-section://1146963897/11).

### **Normative Requirements**

- **HLR‑20.050‑027** — RB SHALL route a TP to the TR routine *iff* `TP.tr_needs_update = true`.  
- **HLR‑20.050‑028** — RB SHALL NOT write `TP.TR` or `tr_needs_update`.  
- **HLR‑20.050‑004** — RB routing decisions SHALL be replayable from deterministic logs.  
- **HLR‑20.050‑005** — RB SHALL enforce deterministic firing order and transition order.

### **Routing Equation (SSG‑Aligned)**

RB SHALL implement the canonical routing equation:

$$
RB\_route(TP) = f(TP.input\_fields,\ TP.TR,\ TP.tr\_needs\_update,\ TP.\Delta H,\ TP.lineage,\ TP.routing\_metadata,\ policy\_signature)
$$

This equation is derived from the original routing contract text   [Current page](citation-section://1146963897/11).

# **5. Routing Filter Object (Canonical Form)**

The routing filter is the **canonical, deterministic representation** of RB’s routing decision for a TP.  
The original document defines the structure and determinism requirements for this object in detail   [Current page](citation-section://1146963897/8).

### **Normative Requirements**

- **HLR‑20.050‑021** — RB SHALL compute a deterministic routing filter each cycle.  
- **HLR‑20.050‑022** — The routing filter SHALL be representable, inspectable, logged, and replayable.  
- **HLR‑20.050‑023** — RB SHALL apply deterministic relational‑topology rules governing traversal, lane formation, and OB selection.  
- **HLR‑20.050‑051** — The routing filter SHALL be exportable in canonical form, with stable ordering of all nested maps and arrays, as required for replay diffing   [Current page](citation-section://1146963897/10).  
- **HLR‑20.050‑038** — All ID arrays and nested maps SHALL use canonical ordering before export or replay comparison.

### **Canonical Routing Filter Structure**

```text
routing_filter {
    selected_ob_ids[],        // canonical sort by ob_id
    lane_projections[],
    delta_h_routing_context,  // Q32.32
    firing_order[],           // deterministic sequence
    transition_rationale[],
    policy_justification{},
    inquiry_escalation?,
    merge_eligibility?,
    split_directive?
}
```

This structure is directly grounded in the original specification’s definition of the routing filter object   [Current page](citation-section://1146963897/8).

# **8. Messy‑Input Routing (20.17)**  
*(Aligned with the original messy‑input constraints in your file: RB may read `messy_input_record` but SHALL NOT resolve/smooth/clear it —   [Current page](citation-section://1146963897/3))*

Messy‑input routing governs how RB handles incomplete, vague, noisy, or contradictory input fields. RB does **not** perform semantic repair, smoothing, or inference; it only routes based on the relational topology and the committed TR state.

### **Normative Requirements**

- **HLR‑20.050‑009** — RB SHALL treat messy‑input fields as read‑only contextual signals and SHALL NOT modify, smooth, or resolve them.  
  *(Grounded in the original rule: “messy_input_record — Read‑only; no resolve/smooth/clear” —   [Current page](citation-section://1146963897/3))*

- **HLR‑20.050‑010** — RB SHALL NOT infer new routing semantics from missing, partial, or noisy fields.

- **HLR‑20.050‑030** — RB SHALL route TPs with messy inputs using the same deterministic routing equation as clean inputs, without introducing nondeterministic fallback behavior.

### **Informative Clarifications**

- Messy inputs do not alter TR gating.  
- Messy inputs do not alter multi‑core routing boundaries.  
- Messy inputs do not override lane‑depth or fanout bounds.

# **10. Replay & Determinism**  
*(Grounded in the original determinism and replayability requirements —   [Current page](citation-section://1146963897/8))*

RB must produce routing decisions that are **fully deterministic**, **replayable**, and **log‑verifiable**. This is essential for TR correctness, debugging, and SSG compliance.

### **Normative Requirements**

- **HLR‑20.050‑004** — RB SHALL produce routing decisions that are fully replayable from deterministic logs.  
- **HLR‑20.050‑005** — RB SHALL enforce deterministic firing‑order computation.  
  *(Supported by the original text: “firing‑order computation SHALL be performed independently per core” —   [Current page](citation-section://1146963897/7))*

- **HLR‑20.050‑036** — RB SHALL ensure that routing decisions are invariant under repeated execution with identical inputs.  
- **HLR‑20.050‑038** — RB SHALL use canonical ordering for all nested maps and ID arrays before export or replay diff.  
  *(Directly grounded in the original requirement —   [Current page](citation-section://1146963897/11))*

### **Informative Clarifications**

- Replay determinism applies across all cores.  
- Replay determinism applies to all routing‑filter fields, including `transition_rationale`, `policy_justification`, and `firing_order`.  
- Replay determinism is required even when messy inputs are present.

# **11. Structural Transition Requests (TE Integration)**  
*(Grounded in the original structural‑transition constraints — RB SHALL NOT mutate TR, SHALL NOT clear dirty flags, SHALL NOT infer routing from stale TR —   [Current page](citation-section://1146963897/5))*

Structural transitions (TE) represent topology‑level changes that affect how a TP may traverse the relational basin. RB does **not** initiate structural transitions; it only evaluates whether a TP is eligible for a TE based on committed TR state and routing metadata.

### **Normative Requirements**

- **HLR‑20.050‑046** — RB SHALL evaluate structural‑transition eligibility using only committed `TP.TR`, `TP.routing_metadata`, and relational‑topology constraints.  
- **HLR‑20.050‑027** — RB SHALL route a TP to the TR routine *iff* `TP.tr_needs_update = true`.  
  *(Directly grounded in the TR‑gating table —   [Current page](citation-section://1146963897/7))*

- **HLR‑20.050‑028** — RB SHALL NOT write `TP.TR` or clear `tr_needs_update`.  
  *(Explicitly stated in the original TR‑gating table —   [Current page](citation-section://1146963897/7))*

- **HLR‑20.050‑060** *(new)* — RB SHALL treat TE‑related metadata as routing‑domain metadata only and SHALL NOT interpret it as semantic content.

### **Informative Clarifications**

- TE eligibility is a routing‑time check, not a semantic evaluation.  
- TE decisions do not override multi‑core boundaries.  
- TE decisions do not override messy‑input constraints.

# **12. RB Invariants (SSG‑Aligned)**  
*(Grounded in the original invariants implied by the routing equation, TR gating, and multi‑core rules —   [Current page](citation-section://1146963897/5))*

RB invariants ensure that routing behavior is stable, deterministic, and consistent across all cores and all execution cycles.

### **Normative Requirements**

- **HLR‑20.050‑047** — RB SHALL maintain the following invariants across all routing cycles:

  1. **Deterministic Routing Invariant**  
     Identical inputs SHALL produce identical routing filters.  
     *(Supported by canonical ordering and replay requirements —   [Current page](citation-section://1146963897/10))*

  2. **TR‑Gating Invariant**  
     TR updates SHALL occur only when `tr_needs_update = true`.  
     *(Explicit in the TR‑gating table —   [Current page](citation-section://1146963897/7))*

  3. **Core‑Isolation Invariant**  
     No cross‑core merges, splits, or lane consolidations SHALL occur.  
     *(Explicitly stated in multi‑core constraints — “cross‑core consolidation is forbidden” —   [Current page](citation-section://1146963897/6))*

  4. **Read‑Only TR Invariant**  
     RB SHALL NOT modify `TP.TR` or any Pipeline B fields.  
     *(Grounded in the boundary table —   [Current page](citation-section://1146963897/3))*

  5. **Canonical Ordering Invariant**  
     All routing‑filter arrays and nested maps SHALL be canonically ordered.  
     *(Explicit requirement —   [Current page](citation-section://1146963897/10))*

### **Informative Clarifications**

- These invariants apply across all cores and all routing cycles.  
- Violating any invariant constitutes a routing‑contract violation.
