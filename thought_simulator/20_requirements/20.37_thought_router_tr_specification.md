# 20.37 Thought Router (TR) Specification

**Document ID:** 20.37  
**Version:** 0.3  
**Date:** 2026-06-06  
**Status:** CP-approved — dual-pipeline TR specification (v0.2 CP refinements applied)

## Purpose

Define the Thought Router (TR) semantic field set, lifecycle, producers and consumers, and deterministic routing role for Thought Packets (TPs) under the **dual-pipeline architecture**.

TR is the **Pipeline A semantic routing vector** for a TP. It is produced by the TR routine/generator and consumed by RB, IB, Merge, Truth/Done, and GB read-only supervisory paths to perform deterministic routing and supervision-compatible flow control. Committed TR fields project into `semantic_core.thought_router_fields` per [20.31](20.31_semantic_specification.md) and [20.39](20.39_ts_core_data_structures.md).

This document SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

The integrated OB → TR → TP.TR → RB flow is defined in **Semantic Interpretation Flow Contract** (below); detailed module rules follow in subsequent sections.

## Parent Scope

- **Pipeline:** Pipeline A (meaning construction) only — TR SHALL NOT read `exec_plan` or `exec_trace` (HLR-20.038-021)
- **Envelope authority:** TR writes TP-local `TP.TR`; `mtp_update` commits `thought_router_fields` into `semantic_core`
- **Numeric encoding:** Q32.32 for authoritative numeric TR subfields per [20.95](20.95_ts_numeric_policy.md)
- **Routing bounds:** fan-out and lane limits from [20.90](20.90_ts_parameter_table.md) §B
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Non-Goals

- Execution-layer routing (`routing_epoch_id`, SRP, OpBeh/OBG selection)
- GB cap/rate policy semantics (20.16, 20.80)
- Reference TR derivation algorithms (20.35 operationalizes field semantics)

## Semantic Interpretation Flow Contract

This section is the authoritative integration view for the deterministic OB → TR → TP.TR → RB semantic routing cycle. It consolidates obligations defined in this document; it does not introduce new semantics beyond referenced sections.

**Normative precedence for overlapping rules:**
- `tr_needs_update` lifecycle semantics: [20.31](20.31_semantic_specification.md) §13 (TR Dirty-Flag Semantics)
- TR field definitions and module boundaries: this document §§2–6, §8–10
- Messy-input tag semantics: [20.17](20.17_messy_input_handling.md) (TR read-only consumption)
- DCB geometric overlay: this document §4.4; [20.106_dcb_requirements.md](20.106_dcb_requirements.md)
- OB local extraction: [20.40_ob_requirements.md](20.40_ob_requirements.md)
- IMR Type B bounded recompute: [20.45](20.45_imr_requirements.md) (schedules TR via `CorrectionTrigger`)

### Contract summary

| Step | Actor | Action | TP / routing effect |
|------|--------|--------|---------------------|
| 1 | RB | Routes TP to OB for lane-local processing | — |
| 2 | OB | Writes pre-semantic **TR-input** fields into `TP.input_fields` | OB does **not** write `TP.TR` |
| 3 | OB | When semantic-relevant inputs change, sets `TP.tr_needs_update = true` | Stale TR; TR recompute required |
| 4 | DCB | (When enabled) Observes TP trajectory; emits ephemeral directional-change events | No TP writes; does **not** set `tr_needs_update` (§4.4) |
| 5 | RB | Evaluates `TP.tr_needs_update` | Routes to TR routine **iff** `true` |
| 6 | TR routine | Reads `TP.input_fields`, TP snapshot, MTP/`messy_input_record` (read-only), and permitted ephemeral DCB events | Derives semantic `TP.TR` without smoothing messy-input tags |
| 7 | TR routine | Atomically writes `TP.TR`; on success sets `tr_needs_update = false`; `mtp_update` projects to `thought_router_fields` | Fresh TR in `semantic_core` |
| 8 | TR routine | On reject/error/failure | Leaves `tr_needs_update = true` |
| 9 | RB | Routes using `TP.TR`, `TP.input_fields`, and explicit routing inputs (§5) | Deterministic next-module routing |

### Canonical cycle (normative ordering)

```text
RB → OB → [DCB observes trajectory] → RB checks tr_needs_update
  → (if true) TR routine → RB
```

- **Semantic interpretation path:** steps 2–3 (OB TR-input + stale flag) and 5–8 (TR derive/commit/clear).
- **Geometric overlay path:** step 4 only; consumed by TR on step 6 when step 5 permits TR execution.
- When `tr_needs_update = false`, TR does not execute and DCB events are not consumed (§4.4, §7).

### Authority boundaries (non-overlapping)

- **OB:** TR-input and evidence only; may set `tr_needs_update`; never writes `TP.TR`; never interprets TR semantics.
- **TR routine:** exclusive writer of `TP.TR`; sole clearer of `tr_needs_update` on successful commit; does not bypass OB pre-semantic inputs.
- **RB:** read-only for `TP.TR`; routes to TR iff `tr_needs_update`; routes downstream using committed `TP.TR`; does not consume DCB events directly.
- **Other semantic writers** (Merge, IB, ΔH% logic, messy-input classifiers, MTP-context mutators): may set `tr_needs_update = true` per §3.3; do not write `TP.TR`.
- **Pipeline B / IMR / OuB:** SHALL NOT write `TP.TR` or clear `tr_needs_update`; IMR Type B MAY schedule bounded TR recompute via `CorrectionTrigger` only (§3.4).
- **GB:** read-only TR consumption for supervisory gating; SHALL NOT mutate `TP.TR`, `tr_needs_update`, or `routing_epoch_id`.

### Integration invariants

1. No module except the TR routine writes `TP.TR`.
2. OB (and other semantic writers) signal TR staleness; TR alone signals TR freshness after successful commit.
3. RB never infers routing from unstale or missing TR when `tr_needs_update = true`.
4. DCB influence is geometric and ephemeral; it does not replace OB TR-input or TR semantic derivation.
5. Messy-input tags in `semantic_core` are inputs to TR derivation, not outputs TR may resolve or smooth.
6. Seed and `routing_epoch_id` SHALL NOT influence TR derivation (HLR-20.012-010).

## 1. Module Identity
- Module: TR (Thought Router fields)
- Pipeline: A (meaning construction)
- Envelope: `TP.TR` (lane-local) → `semantic_core.thought_router_fields` (committed)
- Type: Semantic field set, not a processor
- Producer: TR routine/generator
- Consumers: RB, IB, Merge, Truth/Done evaluator
- Optional Read: OB for multi-TP slot bookkeeping only
- Optional Read: GB for supervisory gating, read-only

Write permissions:
- Write: TR routine only
- Read: RB, IB, Merge, Truth/Done, GB
- Optional Read: OB for bookkeeping only; OB never interprets TR semantics

## 2. Canonical Locations

### 2.1 TP Snapshot (Primary Location)
Every TP contains a TR block.

TP.TR = {
    stance,
    intent,
    affect,
    epistemic_shading,
    tension,
    politeness,
    commitment,
    reservation,
    logical_structure,
    semantic_deltaH,
    lineage_additions,
    routing_semantics
}

This is the canonical TR representation for lane-local TP projection.

At `mtp_update`, TR fields SHALL commit into `semantic_core.thought_router_fields` with identical schema and canonical ordering (HLR-20.037-053). TP remains a lane-local projection; `semantic_core` is the authoritative meaning envelope per 20.31.

Every TP also contains:

TP.tr_needs_update = boolean

- true: TP.TR is stale for current TP/MTP semantic context
- false: TP.TR is current for current TP/MTP semantic context
- initialization: new TP SHALL initialize tr_needs_update = true

### 2.2 OB Multi-TP Memory Slots (Optional)
OB may maintain X concurrent TP slots for pre-semantic extraction bookkeeping.

OB.slot[i] = {
    tp_id,
    ob_fields,
    tr_input_fields,
    routing_metadata
}

OB never writes TR and never interprets TR semantics.

## 3. Producer Authority

### 3.1 TR routine is exclusive TR writer
The TR routine is the only module allowed to write TP.TR.

TR routine reads:
- OB-derived fields in TP.input_fields
- TP snapshot (lane-local projection)
- MTP / `semantic_core` snapshot (read-only), including `messy_input_record` when present
- `policy_signature` (read-only bounds context)

TR routine SHALL NOT read:
- `exec_plan`, `exec_trace`, OuB artifacts, or SRP tables
- `routing_epoch_id` (execution-layer only per 20.39)
- `truth_hypotheses` (truth evaluation is downstream of TR routing; coupling would break module boundaries per 20.140)

TR routine writes atomically into TP.TR:
- stance
- intent
- affect
- epistemic_shading
- tension
- politeness
- commitment
- reservation
- logical_structure
- semantic_deltaH
- lineage_additions
- routing_semantics

### 3.2 OB never sets TR
OB may set TR-input structural fields only and never TP.TR.

### 3.3 Dirty-flag writer authority
Any semantic-writer module that modifies semantic-relevant TP fields SHALL set TP.tr_needs_update = true.

This includes:
- OB (including TR-input field updates)
- Merge
- IB
- Delta-H% logic
- messy-input classifiers (InB, OB, TB, Merge per 20.17)
- any module that mutates TP semantics based on MTP context
- IMR Type B `CorrectionTrigger` scheduling TR recompute (sets stale; does not write TR)

TR routine dirty-flag authority:
- TR routine SHALL set TP.tr_needs_update = false only after successful TR recompute and commit
- TR reject/error/failure paths SHALL leave TP.tr_needs_update = true

### 3.4 Messy-input and IMR Type B dirty-flag triggers

Modules that create or modify messy-input tags in `semantic_core` or TP projections SHALL set `tr_needs_update = true` without writing `TP.TR` (20.17 Pipeline A classifiers at InB, OB, TB, Merge safe boundaries).

IMR Type B `CorrectionTrigger` listing `thought_router_fields` or TR subfields in `target_field_ids[]` SHALL schedule a **bounded** TR recompute pass in the subsequent Pipeline A cycle (20.45). The trigger SHALL set `tr_needs_update = true` before TR execution; IMR SHALL NOT write `TP.TR` directly.

Under `overflow_flag = true`, IMR SHALL NOT schedule Type B TR recompute (20.45 HLR-20.045-026); messy-input primary flags preserved per 20.17 SHALL still be visible to TR on read-only paths.

## 4. OB to TR Relationship

### 4.1 OB outputs TR-input fields
OB writes deterministic pre-semantic fields into TP.input_fields, including:
- pattern IDs
- clause boundaries
- negation markers
- modality markers
- syntactic shape
- raw deltaH
- provenance
- routing metadata
- structural cues consumed by the TR routine

### 4.2 TR routine consumes TR-input fields
The TR routine reads TP.input_fields, TP snapshot, and MTP snapshot (read-only), and deterministically derives TP.TR.

### 4.3 OB multi-TP slots
When OB maintains concurrent TP slots, the slot may include:
- tp_id
- ob_fields
- tr_input_fields

OB slots are storage/bookkeeping only, not semantic TR interpretation.

## 4.4 TR Geometric Inputs (DCB)

The TR routine MAY consume DCB directional-change events as geometric hints when deriving routing semantics and `routing_semantics` fields.

- TR fields remain semantic; DCB does not populate TP.TR directly.
- DCB events MAY influence OB family selection per OB registry and routing policy; named family examples are non-normative.
- DCB SHALL NOT set `tr_needs_update`; it provides an input signal only.
- DCB directional-change events SHALL be consumed only on cycles where `tr_needs_update = true` and RB routes the TP to the TR routine.
- DCB events are ephemeral and are not persisted as TP fields.

### 4.5 Messy-input read-only consumption

When `messy_input_record` is present, the TR routine SHALL treat it as **read-only routing context**:

- `conflict_flag` / `contradiction_status` MAY influence `routing_semantics` (e.g., parallel-lane retention, inquiry escalation hints at meaning layer) but SHALL NOT collapse parallel traces or clear contradiction tags.
- `underspec_flag` / `underspec_slots[]` MAY raise meaning-layer uncertainty markers in `routing_semantics` but SHALL NOT fill slots or exceed `messy_input.commitment_strength.cap_until_resolved` (20.90 §H).
- `incomplete_flag` / `missing_slots[]` MAY route toward IB-Creation-Request pathways without inventing missing content.
- `messy_input_class[]` SHALL be consumed in canonical export order (`MI_AFFECT`, `MI_CONTRA`, `MI_INCOMP`, `MI_NOISE`, `MI_VAGUE`) for deterministic derivation only.

TR SHALL NOT create, modify, or clear any messy-input tag in `semantic_core` (20.17 HLR-20.017-019).

## 5. TR to RB Relationship

### 5.1 RB routing inputs
RB reads:
- TP.input_fields
- TP.TR
- TP.tr_needs_update
- TP.deltaH
- TP.lineage
- TP.routing_metadata
- MTP routing-relevant fields

RB uses these to determine:
- whether TP must be routed to the TR routine
- next module
- inquiry escalation
- safety escalation
- merge eligibility
- refinement requirements
- TP splitting or consolidation

### 5.2 RB never writes TR
RB is strictly read-only with respect to TP.TR.

### 5.3 Deterministic routing equation
RB_route(TP) = f(TP.input_fields, TP.TR, TP.tr_needs_update, TP.deltaH, TP.lineage, TP.routing_metadata)

This is the deterministic routing contract replacing attention-like stochastic routing behavior.

RB SHALL route TP to the TR routine if and only if TP.tr_needs_update = true.

### 5.4 Routing bounds (20.90)

RB routing decisions that fan out from `TP.TR` and `routing_semantics` SHALL respect canonical bounds:

| Parameter | Default | Source |
|-----------|--------:|--------|
| `routing.fanout.max_per_tp` | 6 | 20.90 §B |
| `routing.active_lanes.max` | 24 | 20.90 §B |
| `inquiry.depth.max` | 8 | 20.90 §B |

Exceeding fan-out or active-lane bounds SHALL produce deterministic reject-with-audit or bounded degrade per 20.30 §8 — never silent truncation of routing metadata.

## 6. TR Field Definitions
The TR block SHALL contain all fields below.

- stance: declarative, interrogative, uncertain, assertive
- intent: inquire, assert, refine, contradict, confirm
- affect: positive, negative, neutral, tense, relaxed
- epistemic_shading: certain, uncertain, speculative, hedged
- tension: contradiction pressure or conflict level
- politeness: social-shading marker
- commitment: assertion strength
- reservation: hedging marker set
- logical_structure: conditional, biconditional, conjunction, disjunction, contradiction
- semantic_deltaH: TR-routine interpreted deltaH (**Q32.32**; canonical compare per 20.95)
- lineage_additions: semantic provenance additions (canonical sort per 20.95/20.39)
- routing_semantics: explicit **meaning-layer** routing hints consumed by RB

**Numeric subfields (Q32.32):** `semantic_deltaH`, `commitment`, `tension` (and any ratio/weight subfields). Negative zero SHALL normalize to +0 before commit and replay export (HLR-20.095-032).

**`routing_semantics` forbidden content (20.31 HLR-20.031-021):** SHALL NOT encode `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, register/voice selection, OuB presentation directives, or other execution-layer hints. Basin routing *intent* at the meaning layer is permitted.

**`routing_semantics` canonical ordering (HLR-20.037-064):** Before export, hash, and replay diff, `routing_semantics` sub-records and nested arrays SHALL use deterministic ordering:
- top-level hint records: lexicographic sort by stable `hint_id`
- nested ID arrays (`target_basin_ids[]`, `escalation_targets[]`, etc.): lexicographic sort by stable ID
- numeric hint weights: canonical Q32.32 before ordering tie-breaks

All TR fields SHALL be deterministic and replay-reproducible from `(TP inputs, read-only MTP/semantic_core, policy_signature)` — **excluding seed** (HLR-20.012-010).

TR derivation SHALL NOT depend on TP creation order, allocation sequence, or container address identity; only explicit canonical TP/MTP fields and stable IDs permitted by contract may influence outputs (HLR-20.037-065).

## 7. TR Lifecycle
1. RB routes TP to OB.
2. OB extracts pre-semantic fields and writes TP.input_fields.
3. DCB observes TP trajectory geometry and emits ephemeral directional-change events (no TP writes).
4. RB checks TP.tr_needs_update.
5. If TP.tr_needs_update = true, RB routes TP to TR routine.
6. TR routine reads TP.input_fields, TP snapshot, MTP snapshot (read-only), and ephemeral DCB events when present.
7. TR routine writes TP.TR atomically and sets TP.tr_needs_update = false after successful recompute and commit.
8. If TR reject/error/failure occurs, TP.tr_needs_update remains true.
9. RB reads TP.TR and TP.input_fields.
10. If TP.tr_needs_update = false, TR SHALL NOT execute (DCB events are not consumed).
11. RB routes TP to next module.
12. IB, Merge, Truth/Done, and GB may read TP.TR.
13. TR persists until TP merge or TP retirement.
14. On `mtp_update`, committed `TP.TR` projects into `semantic_core.thought_router_fields` with deterministic field ordering.
15. IMR Type B correction (when permitted) sets `tr_needs_update = true`; bounded TR recompute runs in next Pipeline A cycle before Pipeline B realization consumes updated `semantic_core`.

## 8. Module Boundaries
- OB may write TR-input fields only.
- TR routine writes TR.
- RB reads TR.
- IB reads TR.
- Merge reads TR.
- Truth/Done reads TR.
- GB may read TR for supervisory gating.
- OB may read TR for bookkeeping only.

No module except the TR routine may write TR.

**Pipeline B forbidden:** OuB, OpBeh/OBG/XlateR, IMR, and SRP SHALL NOT write `TP.TR`, mutate `thought_router_fields`, or clear `tr_needs_update` (20.12 envelope write authority).

## 9. Safety and Determinism Constraints
- TR must be deterministic for identical effective inputs.
- TR must be logged in TP snapshot artifacts.
- TR must contain no stochastic fields.
- TR must not depend on global mutable state.
- TR must not be influenced by other TPs except explicit canonical state fields.
- TR must not depend on TP creation order or runtime allocation identity (HLR-20.037-065).
- TR must not read `truth_hypotheses` for derivation (HLR-20.037-063).
- TR must not be modified after TR-routine commit in the same TP lifecycle stage.

### 9.1 Dual-pipeline replay

- Stripping `exec_plan` and `exec_trace` from a trace SHALL leave `thought_router_fields` and `tr_needs_update` history in `semantic_core` identical for Pipeline A-only replay (20.36 Class 1, HLR-20.012-011).
- TR derivation logs SHALL serialize with canonical field ordering before hash/replay diff (20.95).
- Class 2 fixtures SHALL assert messy-input primary flags survive TR recompute without smoothing.
- Class 5 fixtures SHALL assert `routing_semantics` contains no execution-layer identifiers after full governance stress.

55. HLR-20.037-055: TR SHALL consume `messy_input_record` read-only when deriving `routing_semantics`; TR SHALL NOT smooth contradiction, fill underspec slots, or clear messy-input tags (20.17).
56. HLR-20.037-056: Modules that create or modify messy-input tags SHALL set `tr_needs_update = true` without writing `TP.TR`.
57. HLR-20.037-057: IMR Type B `CorrectionTrigger` listing TR/`thought_router_fields` in `target_field_ids[]` SHALL set `tr_needs_update = true` and schedule bounded TR recompute per 20.45; IMR SHALL NOT write `TP.TR`.
58. HLR-20.037-058: Numeric TR subfields (`semantic_deltaH`, `commitment`, `tension`, and ratio weights) SHALL use canonical Q32.32 per 20.95; comparisons SHALL use canonical integer equality.
59. HLR-20.037-059: RB routing using `TP.TR` SHALL enforce `routing.fanout.max_per_tp`, `routing.active_lanes.max`, and `inquiry.depth.max` defaults from 20.90.
60. HLR-20.037-060: TR derivation SHALL be reproducible from `(TP inputs, read-only MTP/semantic_core, policy_signature)`; seed SHALL NOT influence TR outputs (HLR-20.012-010).
61. HLR-20.037-061: Strip replay removing Pipeline B envelopes SHALL preserve `thought_router_fields` in `semantic_core` for Pipeline A-only equivalence (20.36 Class 1).
62. HLR-20.037-062: GB SHALL NOT write `TP.TR`, `thought_router_fields`, or `tr_needs_update`; GB read access is supervisory gating only and SHALL NOT advance `routing_epoch_id`.
63. HLR-20.037-063: The TR routine SHALL NOT read `truth_hypotheses` from MTP or `semantic_core` for TR derivation; truth evaluation consumes TR as read-only input via Truth/Done, not vice versa (20.140).
64. HLR-20.037-064: `routing_semantics` nested records and arrays SHALL use deterministic canonical ordering before export, hash, and replay diff — stable `hint_id` lexicographic primary sort; nested ID arrays lexicographic; numeric weights canonical Q32.32.
65. HLR-20.037-065: TR derivation SHALL NOT depend on TP creation order, heap/container allocation order, or address identity; only explicit canonical fields and stable IDs in the effective input set MAY influence outputs.

## Worked Example — Messy Input + TR Recompute

Input carries `MI_VAGUE` + `MI_CONTRA` (canonical sort in export). Pipeline A classifiers set messy tags; OB updates TR-input; `tr_needs_update = true`.

| Step | Actor | Outcome |
|------|-------|---------|
| 1 | InB/OB | `messy_input_class: [MI_CONTRA, MI_VAGUE]`; `conflict_flag = true`; `underspec_flag = true` |
| 2 | OB | Writes TR-input; sets `tr_needs_update = true` |
| 3 | RB | Routes to TR routine (stale flag) |
| 4 | TR | Reads messy tags read-only; `routing_semantics` retains parallel-lane hint; `commitment` capped ≤ 0.4 (20.90) |
| 5 | TR | Commits `TP.TR`; clears `tr_needs_update = false` |
| 6 | `mtp_update` | Projects to `thought_router_fields`; messy tags unchanged |
| 7 | Pipeline B | OuB realizes from read-only `semantic_core`; no messy-tag mutation |
| 8 | Strip replay | Remove `exec_plan`/`exec_trace` → `thought_router_fields` + messy tags identical |

## 11. Conformance
Implementation conforms when all of the following hold:
- TP.TR exists and is complete for routed TPs requiring semantic routing.
- TP.tr_needs_update exists as a boolean field for each TP and initializes to true on TP creation.
- The TR routine is the only TR writer.
- Semantic-writer modules set tr_needs_update = true when semantic-relevant TP fields are modified.
- RB routes to TR routine if and only if tr_needs_update = true.
- TR successful recompute/commit clears tr_needs_update = false; reject/error/failure leaves tr_needs_update = true.
- RB, IB, Merge, Truth/Done, GB, and optional OB bookkeeping paths obey read-only constraints.
- Logs prove deterministic TR generation and consumption order.
- `thought_router_fields` commits to `semantic_core` at `mtp_update` with canonical ordering.
- TR does not read `exec_plan`/`exec_trace`; `routing_semantics` contains no execution-layer IDs.
- Messy-input tags survive TR recompute; TR does not smooth or resolve them.
- Numeric TR subfields use Q32.32; −0 normalizes to +0.
- RB respects 20.90 routing fan-out and active-lane bounds.
- IMR Type B schedules TR recompute via dirty flag only; does not write TR.
- GB is read-only for TR; does not advance `routing_epoch_id`.
- Strip replay preserves `thought_router_fields` (20.36 Class 1).
- TR does not read `truth_hypotheses`.
- `routing_semantics` subfields use canonical ordering in replay export.
- TR outputs invariant under permuted TP creation order for identical canonical inputs.
