# 20.37 Thought Router (TR) Specification

**Document ID:** 20.37  
**Version:** 0.3  
**Date:** 2026-06-06  
**Status:** Approved v0.3 — §8 second-pass GATE (2026-06-07; CuriousOne23, Copilot, Grok; boundary check only; no edits)

## Purpose

Define the Thought Router (TR) meaning-layer field set, lifecycle, producers and consumers, and deterministic routing role for Thought Packets (TPs) under the **dual-pipeline architecture**. RBU commits TR fields into SSR during mtp_update; TR itself is not a meaning-layer-core primitive.

TR is the **Pipeline A Path A routing vector** for a TP. It is produced by the TR is consumed by RB for routing and read-only by supervisory paths (GB, SRP). TR is not consumed by IB, Merge, or Truth/Done. GB may read TR in a supervisory capacity but does not consume TR for routing. Committed TR fields project into `SSR.thought_router_fields` per [20.31](20.31_patha_meaning_spec.md) and [20.39](20.39_ts_core_data_structures.md).

This document SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

The correct Path A routing flow is {SOB, SROB, CnOB, SmOB} → TR → RB → downstream evaluators (Truth/Done/Completion); detailed module rules follow in subsequent sections.

## Parent Scope

- **Pipeline:** Pipeline A (meaning construction) only — TR SHALL NOT read `exec_plan` or `exec_trace` (HLR-20.038-021). TR has no interaction with Pipeline B and is not visible to RG.
- **Envelope authority:**  TR writes TP.TR. RBU later commits TP.TR into SSR during mtp_update. TR does not read or write MTP.
- **Numeric encoding:** Q32.32 for authoritative numeric TR subfields per [20.95](20.95_ts_numeric_policy.md)
- **Routing bounds:** fan-out and lane limits from [20.90](20.90_ts_parameter_table.md) §B
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Non-Goals

- Execution-layer routing (`routing_epoch_id`, SRP, OpBeh/OBG selection)
- GB cap/rate policy meaning-layers (20.16, 20.80)
- Reference TR derivation algorithms (20.35 operationalizes field meaning-layers)

## meaning-layer Interpretation Flow Contract

This section is the authoritative integration view for the deterministic {SOB, SROB, CnOB, SmOB} → TR → TP.TR → RB Path A routing vector cycle. It consolidates obligations defined in this document; it does not introduce new meaning-layers beyond referenced sections. Note that {SOB, SROB, CnOB, SmOB} are Grammatical Structure primitives.

**Normative precedence for overlapping rules:**
- `tr_needs_update` lifecycle meaning-layers: [20.31](20.31_patha_meaning_spec.md) §13 (TR Dirty-Flag meaning-layers)
- TR field definitions and module boundaries: this document §§2–6, §8–10
- TR does not consume messy-input tags; TR is computed solely from TP.input_fields.
- DCB geometric overlay: this document §4.4; [20.106_dcb_requirements.md](20.106_dcb_requirements.md)
- Grammatical Structure primitives local extraction: [20.40_ob_requirements.md](20.40_ob_requirements.md)
- TR recompute is triggered exclusively by TP.tr_needs_update: [20.45](20.45_imr_requirements.md) (schedules TR via `CorrectionTrigger`)

### Contract summary

| Step | Actor | Action | TP / routing effect |
| --- | --- | --- | --- |
| 1 | RB | Routes TP to Grammatical Structure primitives for lane‑local processing | — |
| 2 | Grammatical Structure primitives | Writes pre‑meaning-layer **TR‑input** fields into ``TP.input_fields`` | Grammatical Structure primitives does **not** write ``TP.TR`` |
| 3 | Grammatical Structure primitives | When meaning-layer‑relevant inputs change, sets ``TP.tr_needs_update ``= ``true`` | Stale TR; TR recompute required |
| 4 | DCB | (When enabled) Observes TP trajectory; emits ephemeral directional‑change events | No TP writes; does **not** set ``tr_needs_update`` (§4.4) |
| 5 | RB | Evaluates ``TP.tr_needs_update`` | Routes to TR routine **iff** ``true`` |
| 6 | TR routine | Reads ``TP.input_fields`` and the TP snapshot; may read permitted ephemeral DCB events (read‑only) | Derives meaning-layer ``TP.TR`` using deterministic rules |
| 7 | TR routine | Atomically writes ``TP.TR``; on success sets ``tr_needs_update ``= ``false``; RBU later commits ``TP.TR`` into ``SSR`` during ``mtp_update`` | Fresh TR in ``SSR`` after commit |
| 8 | TR routine | On reject/error/failure | Leaves ``tr_needs_update ``= ``true`` |
| 9 | RB | Routes using ``TP.TR``, ``TP.input_fields``, and explicit routing inputs (§5) | Deterministic next‑module routing |

### Canonical cycle (normative ordering)

```text
RB → Grammatical Structure primitives → [DCB observes trajectory] → RB checks `tr_needs_update`
  → (if true) TR routine → RB
```

- **meaning-layer interpretation path:** steps 2–3 (Grammatical Structure primitives TR-input + stale flag) and 5–8 (TR derive/commit/clear).
- **Geometric overlay path:** step 4 only; consumed by TR on step 6 when step 5 permits TR execution.
- When `tr_needs_update = false`, TR does not execute and DCB events are not consumed (§4.4, §7).

### Authority boundaries (non-overlapping)

- **Grammatical Structure primitives:** TR-input and evidence only; may set `tr_needs_update`; never writes `TP.TR`; never interprets TR meaning-layers.
- **TR routine:** exclusive writer of `TP.TR`; sole clearer of `tr_needs_update` on successful commit; does not bypass Grammatical Structure primitives inputs.
- **RB:** read-only for `TP.TR`; routes to TR iff `tr_needs_update`; routes downstream using committed `TP.TR`; does not consume DCB events directly.
- **Other meaning-layer writers** (Merge, IB, ΔH% logic, messy-input classifiers, MTP-context mutators): may set `tr_needs_update = true` per §3.3; do not write `TP.TR`.
- **Pipeline B / IMR / OuB: HLR-20.037-066** SHALL NOT write `TP.TR` or clear `tr_needs_update`; IMR SHALL NOT schedule TR recompute.
- **GB:** read-only TR consumption for supervisory gating; SHALL NOT mutate `TP.TR`, `tr_needs_update`, or `routing_epoch_id`.

### Integration invariants

1. No module except the TR routine writes `TP.TR`.
2. Grammatical Structure primitives (and other meaning-layer writers) signal TR staleness; TR alone signals TR freshness after successful commit.
3. RB never infers routing from unstale or missing TR when `tr_needs_update = true`.
4. DCB influence is geometric and ephemeral; it does not replace Grammatical Structure primitives TR-input or TR meaning-layer derivation.
5. TR derivation uses `TP.input_fields` (and permitted DCB hints) only; it does not consume or smooth messy‑input tags.
6. Seed and `routing_epoch_id` SHALL NOT influence TR derivation (HLR-20.012-010).

## 1. Module Identity
- Module: TR (Thought Router fields)
- Pipeline: A (meaning construction)
- Envelope: `TP.TR` (lane-local) → `SSR.thought_router_fields` (committed)
- Type: meaning-layer field set, not a processor
- Producer: TR routine/generator
- Consumers: RB (routing), GB (supervisory read-only)
- Grammatical Structure primitives: writes TR‑input fields only; does not read or interpret `TP.TR`
- Prohibited Reads: Pipeline B, IMR, OuB SHALL NOT read TP.TR

Write permissions:
- Write: TR routine only
- Read: RB & GB
- Grammatical Structure primitives: read‑only for bookkeeping; never interprets TR meaning-layers

## 2. Canonical Locations

### 2.1 TP Snapshot (Primary Location)
Every TP contains a TR block.

TP.TR = {
    stance,
    intent,
    affect,
    epistemic_shading,
    tension,
    politeness,
    commitment,
    reservation,
    logical_structure,
    meaning-layer_deltaH,
    lineage_additions,
    routing_meaning-layers
}

This is the canonical TR representation for lane-local TP projection.

At `mtp_update`, TR fields SHALL commit into `SSR.thought_router_fields` with identical schema and canonical ordering (HLR-20.037-053). TP remains a lane-local projection; `SSR` is the authoritative meaning envelope per 20.31 TR is not visible to Pipeline B.

Every TP also contains:

TP.tr_needs_update = boolean

- true: TP.TR is stale for the current TP meaning-layer context
- false: TP.TR is current for the current TP meaning-layer context
- initialization: new TP SHALL initialize `tr_needs_update = true`

### 2.2 Grammatical Structure primitives Multi-TP Memory Slots (Optional)
Grammatical Structure primitives may maintain X concurrent TP slots for grammatical-structure extraction bookkeeping.

Grammatical Structure primitives.slot[i] = {
    tp_id,
    ob_fields,
    tr_input_fields,
    routing_metadata
}

Grammatical Structure primitives never writes TR and never interprets TR meaning-layers.

## 3. Producer Authority

### 3.1 TR routine is exclusive TR writer  
The TR routine is the only module allowed to write `TP.TR`.

**TR routine reads:**  
- `core_id` (read‑only; assigned at Grammatical Structure primitives stage during multi‑core Path A execution)  
- `orthogonality_signature` (read‑only; Grammatical Structure primitives information‑domain identity)  
- Grammatical Structure primitives‑derived fields in `TP.input_fields`  
- TP snapshot (lane‑local projection)  
- permitted ephemeral DCB events (read‑only)

**TR routine SHALL NOT read:**  
- `exec_plan`, `exec_trace`, OuB artifacts, or SRP tables  
- `routing_epoch_id` (execution‑layer only per 20.39)  
- `truth_hypotheses` (truth evaluation is downstream of TR routing; coupling would break module boundaries per 20.140)  
- `policy_signature`  
- MTP or `SSR`  
- `messy_input_record` or messy‑input tags  

**TR routine writes atomically into `TP.TR`:**  
- stance  
- intent  
- affect  
- epistemic_shading  
- tension  
- politeness  
- commitment  
- reservation  
- logical_structure  
- meaning-layer_deltaH  
- lineage_additions  
- routing_meaning-layers  

---

### 3.2 Grammatical Structure primitives never sets TR  
Grammatical Structure primitives may set TR‑input structural fields only and never `TP.TR`.

---

### 3.3 Dirty‑flag writer authority  
Any meaning-layer‑writer module that modifies meaning-layer‑relevant TP fields SHALL set `TP.tr_needs_update = true`.

This includes:  
- Grammatical Structure primitives (including TR‑input field updates)  
- Merge  
- IB  
- Delta‑H% logic  
- messy‑input classifiers (InB, Grammatical Structure primitives, TB, Merge per 20.17)  
- **any module that mutates TP meaning-layers**  

**Removed:** “modules that mutate TP meaning-layers based on MTP context” — TR no longer depends on MTP.  
**Removed:** IMR Type B scheduling — IMR no longer schedules TR recompute.

**TR routine dirty‑flag authority:**  
- TR routine SHALL set `TP.tr_needs_update = false` only after successful TR recompute and commit  
- TR reject/error/failure paths SHALL leave `TP.tr_needs_update = true`

---

### 3.4 Messy‑input dirty‑flag triggers  
Modules that create or modify messy‑input tags in TP projections SHALL set `tr_needs_update = true` without writing `TP.TR` (20.17 Pipeline A classifiers at InB, Grammatical Structure primitives, TB, Merge safe boundaries).

**Removed:** IMR Type B `CorrectionTrigger` scheduling — IMR SHALL NOT schedule TR recompute.

Under `overflow_flag = true`, IMR SHALL NOT schedule TR recompute (20.45 HLR‑20.045‑026); messy‑input primary flags preserved per 20.17 SHALL still be visible to TR on read‑only paths.

## 4. Grammatical Structure primitives to TR Relationship

### 4.1 Grammatical Structure primitives outputs TR‑input fields  
Grammatical Structure primitives writes deterministic grammatical-structure fields into `TP.input_fields`, including:  
- pattern IDs  
- clause boundaries  
- negation markers  
- modality markers  
- syntactic shape  
- raw deltaH  
- provenance  
- routing metadata  
- structural cues consumed by the TR routine  

TR SHALL treat `orthogonality_signature` as a routing constraint:  
- TR SHALL NOT combine TR‑input from different orthogonality domains.  
- TR SHALL NOT derive TR meaning-layers using TR‑input originating from a different `core_id`.

---

### 4.2 TR routine consumes TR‑input fields  
The TR routine reads:  
- `TP.input_fields`  
- the TP snapshot (lane‑local projection)  
- permitted ephemeral DCB events (read‑only)  

TR SHALL NOT read MTP, `SSR`, `messy_input_record`, or any messy‑input tags.  
TR deterministically derives `TP.TR` from TP‑local inputs only.

---

### 4.3 Grammatical Structure primitives multi‑TP slots  
When Grammatical Structure primitives maintains concurrent TP slots, the slot may include:  
- `tp_id`  
- `ob_fields`  
- `tr_input_fields`  

Grammatical Structure primitives slots are storage/bookkeeping only, not meaning-layer TR interpretation.

---

## 4.4 TR Geometric Inputs (DCB)

The TR routine MAY consume DCB directional‑change events as geometric hints when deriving `routing_meaning-layers`.

- TR fields remain meaning-layer; DCB does not populate `TP.TR` directly.  
- DCB events MAY influence Grammatical Structure primitives‑family selection per Grammatical Structure primitives registry and routing policy; named family examples are non‑normative.  
- DCB SHALL NOT set `tr_needs_update`; it provides an input signal only.  
- DCB directional‑change events SHALL be consumed only on cycles where `tr_needs_update = true` and RB routes the TP to the TR routine.  
- DCB events are ephemeral and are not persisted as TP fields.

---

### 4.5 Messy‑input dirty‑flag triggers (read‑only; not TR inputs)

Modules that create or modify messy‑input tags in TP projections SHALL set `tr_needs_update = true` without writing `TP.TR` (20.17 Pipeline A classifiers at InB, Grammatical Structure primitives, TB, Merge safe boundaries).

TR SHALL NOT:  
- read `messy_input_record`  
- consume messy‑input tags as TR inputs  
- derive TR meaning-layers from messy‑input tags  
- create, modify, or clear any messy‑input tag in `SSR` (20.17 HLR‑20.017‑019)

Messy‑input tags influence **dirty‑flag triggers only**, not TR derivation.

## 5. TR to RB Relationship

### 5.1 RB routing inputs  
RB reads:  
- `TP.input_fields`  
- `TP.TR`  
- `TP.tr_needs_update`  
- `TP.deltaH`  
- `TP.lineage`  
- `TP.routing_metadata`  

**RB SHALL NOT read MTP or `SSR` for routing decisions.**  
Routing is computed strictly from the TP snapshot and TR.

RB SHALL enforce core‑local routing:  
- RB SHALL NOT route a TP into a lane whose `core_id` differs from the TP’s `core_id`.  
- RB SHALL treat `core_id` as a hard routing boundary.

RB uses these to determine:  
- whether TP must be routed to the TR routine  
- next module  
- inquiry escalation  
- safety escalation  
- merge eligibility  
- refinement requirements  
- TP splitting or consolidation

### 5.2 RB never writes TR  
RB is strictly read‑only with respect to `TP.TR`.

## 6. TR Field Definitions  
The TR block SHALL contain all fields below.

- stance: declarative, interrogative, uncertain, assertive  
- intent: inquire, assert, refine, contradict, confirm  
- affect: positive, negative, neutral, tense, relaxed  
- epistemic_shading: certain, uncertain, speculative, hedged  
- tension: contradiction pressure or conflict level  
- politeness: social‑shading marker  
- commitment: assertion strength  
- reservation: hedging marker set  
- logical_structure: conditional, biconditional, conjunction, disjunction, contradiction  
- meaning-layer_deltaH: TR‑routine interpreted deltaH (**Q32.32**; canonical compare per 20.95)  
- lineage_additions: meaning-layer provenance additions (canonical sort per 20.95/20.39)  
- routing_meaning-layers: explicit **meaning‑layer** routing hints consumed by RB  

**Numeric subfields (Q32.32):** `meaning-layer_deltaH`, `commitment`, `tension` (and any ratio/weight subfields).  
Negative zero SHALL normalize to +0 before commit and replay export (HLR‑20.095‑032).

**`routing_meaning-layers` forbidden content (20.31 HLR‑20.031‑021):**  
SHALL NOT encode `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, register/voice selection, OuB presentation directives, or other execution‑layer hints.  
Basin routing *intent* at the meaning layer is permitted.

**`routing_meaning-layers` canonical ordering (HLR‑20.037‑064):**  
Before export, hash, and replay diff, `routing_meaning-layers` sub‑records and nested arrays SHALL use deterministic ordering:  
- top‑level hint records: lexicographic sort by stable `hint_id`  
- nested ID arrays (`target_basin_ids[]`, `escalation_targets[]`, etc.): lexicographic sort by stable ID  
- numeric hint weights: canonical Q32.32 before ordering tie‑breaks  

All TR fields SHALL be deterministic and replay‑reproducible from **TP‑local inputs only** —  
**excluding seed** (HLR‑20.012‑010).  
TR derivation SHALL NOT depend on MTP, `SSR`, `policy_signature`, or messy‑input tags.

TR derivation SHALL NOT depend on TP creation order, allocation sequence, or container address identity; only explicit canonical TP fields and stable IDs permitted by contract may influence outputs (HLR‑20.037‑065).

## 7. TR Lifecycle  
1. RB routes TP to Grammatical Structure primitives.  
2. Grammatical Structure primitives extracts pre‑meaning-layer fields and writes `TP.input_fields`.  
3. DCB observes TP trajectory geometry and emits ephemeral directional‑change events (no TP writes).  
4. RB checks `TP.tr_needs_update`.  
5. If `TP.tr_needs_update = true`, RB routes TP to the TR routine.  
6. TR routine reads `TP.input_fields`, the TP snapshot, and permitted ephemeral DCB events (read‑only).  
   **TR SHALL NOT read MTP, `SSR`, or messy‑input tags.**  
7. TR routine writes `TP.TR` atomically and sets `TP.tr_needs_update = false` after successful recompute and commit.  
8. TR routine SHALL tag TR recompute with `core_id` for deterministic replay and MTP assembly.  
9. If TR reject/error/failure occurs, `TP.tr_needs_update` remains true.  
10. RB reads `TP.TR` and `TP.input_fields`.  
11. If `TP.tr_needs_update = false`, TR SHALL NOT execute (DCB events are not consumed).  
12. RB routes TP to the next module.  
13. RB and GB may read `TP.TR`.  
    **IB, Merge, and Truth/Done SHALL NOT read `TP.TR`.**  
14. TR persists until TP merge or TP retirement.  
15. On `mtp_update`, committed `TP.TR` projects into `SSR.thought_router_fields` with deterministic field ordering.  
16. **IMR SHALL NOT schedule TR recompute.**  
    Dirty‑flag triggers come only from meaning-layer‑writer modules that mutate TP‑local meaning-layers.

---

## 8. Module Boundaries

- Grammatical Structure primitives may write TR‑input fields only.  
- TR routine writes TR.  
- **RB reads TR.**  
- **IB SHALL NOT read TR.**  
- **Merge SHALL NOT read TR.**  
- **Truth/Done SHALL NOT read TR.**  
- GB may read TR for supervisory gating (read‑only).  
- Grammatical Structure primitives may read TR for bookkeeping only (never meaning-layer interpretation).

No module except the TR routine may write TR.

**Pipeline B forbidden:** OuB, OpBeh/OBG/XlateR, IMR, and SRP SHALL NOT read or write `TP.TR`, SHALL NOT mutate `thought_router_fields`, and SHALL NOT clear `tr_needs_update` (20.12 envelope write authority).

## 9. Safety and Determinism Constraints

- TR must be deterministic for identical effective inputs.  
- TR must be logged in TP snapshot artifacts.  
- TR must contain no stochastic fields.  
- TR must not depend on global mutable state.  
- TR must not be influenced by other TPs except explicit canonical TP fields.  
- TR must not depend on TP creation order or runtime allocation identity (HLR‑20.037‑065).  
- TR must not read `truth_hypotheses` for derivation (HLR‑20.037‑063).  
- TR must not be modified after TR‑routine commit in the same TP lifecycle stage.

### 9.1 Dual‑pipeline replay

- Stripping `exec_plan` and `exec_trace` from a trace SHALL leave `thought_router_fields` and `tr_needs_update` history in `SSR` identical for Pipeline A‑only replay (20.36 Class 1, HLR‑20.012‑011).  
- TR derivation logs SHALL serialize with canonical field ordering before hash/replay diff (20.95).  
- Class 2 fixtures SHALL assert messy‑input primary flags survive TR recompute without smoothing.  
- Class 5 fixtures SHALL assert `routing_meaning-layers` contains no execution‑layer identifiers after full governance stress.

## 11. Conformance  
Implementation conforms when all of the following hold:

- `TP.TR` exists and is complete for routed TPs requiring Path A routing vector.  
- `TP.tr_needs_update` exists as a boolean field for each TP and initializes to `true` on TP creation.  
- The TR routine is the only TR writer.  
- meaning-layer‑writer modules set `tr_needs_update = true` when TP‑local meaning-layer fields are modified.  
- RB routes to the TR routine **if and only if** `tr_needs_update = true`.  
- TR successful recompute/commit clears `tr_needs_update = false`; reject/error/failure leaves `tr_needs_update = true`.  
- **RB and GB obey read‑only constraints; IB, Merge, and Truth/Done SHALL NOT read `TP.TR`.**  
- Logs prove deterministic TR generation and consumption order.  
- `thought_router_fields` commits to `SSR` at `mtp_update` with canonical ordering.  
- TR does not read `exec_plan`/`exec_trace`; `routing_meaning-layers` contains no execution‑layer IDs.  
- Messy‑input tags survive TR recompute; TR does **not** smooth or resolve them.  
- Numeric TR subfields use Q32.32; −0 normalizes to +0.  
- RB respects 20.90 routing fan‑out and active‑lane bounds.  
- **IMR SHALL NOT schedule TR recompute; IMR SHALL NOT write TR.**  
- GB is read‑only for TR; does not advance `routing_epoch_id`.  
- Strip replay preserves `thought_router_fields` (20.36 Class 1).  
- TR does not read `truth_hypotheses`.  
- `routing_meaning-layers` subfields use canonical ordering in replay export.  
- TR outputs are invariant under permuted TP creation order for identical canonical inputs.
