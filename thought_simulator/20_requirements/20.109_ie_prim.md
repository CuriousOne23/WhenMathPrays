## **1. Purpose** *(Informative)*

The Intake Envelope (IE) is the **final pre‑semantic representation** of the user’s input in Path‑A.  
IE is produced after IIInB identifies deterministic repair operations.  
IE provides a **fully normalized, repaired, bounded, deterministic, replay‑safe** representation of the user’s input that CEx can consume without performing any semantic interpretation.

IE ensures that:

### **1. All deterministic repairs are applied before semantic processing begins**  
IIInB proposes repairs; IE applies them to produce **IE.intake**, a normalized, repaired surface form.  
This guarantees that CEx, CE, and downstream semantic modules operate on **clean, normalized input** free of surface defects or shorthand artifacts.

### **2. The input is structurally stable and schema‑validated**  
IE enforces a canonical structural schema, including:

- normalized token sequence in **IE.intake.tokens**  
- deterministic whitespace and punctuation normalization  
- repair annotations in **IE.metadata.repair_annotations**  
- structural tags in **IE.structure**  
- deterministic replay metadata in **IE.metadata**

### **3. The input is fully deterministic and replay‑equivalent**  
IE encodes all information needed for deterministic replay:

- repair operations  
- structural tags  
- token boundaries  
- normalization metadata  
- ruleset identifiers  

This allows governance, audit, and replay systems to reconstruct the exact input state without accessing external context.

### **4. The input is safe for CEx and CE**  
IE is the **last pre‑semantic boundary** before CEx.  
It ensures that CEx receives:

- no semantic content (TP.semantic is still empty)  
- no inferred meaning  
- no ambiguity resolution  
- no candidate expansions  
- no truth evaluation  
- no nondeterministic fields  

CEx can therefore perform identity‑layer selection and context extraction **without semantic contamination**.

### **5. Path‑A begins semantic processing from a clean foundation**  
IE is the bridge between:

- **InB → IIInB** (canonicalization + repair proposals)  
- **CEx → CE → ISc → TPU → TP.semantic** (context extraction + semantic processing)

IE ensures that semantic modules begin from a **stable, deterministic, pre‑semantic foundation**.

IE is a **data‑integrity primitive**, not a semantic module.

---

## **2. Position in Pipeline (Informative)**

IE is produced:

- After InB → IIInB  
- Before CEx  
- Before any semantic interpretation  
- Before TP.semantic, TP.process, or TP.metadata are constructed

## **3. Normative Requirements (HLRs)**  
*(All TP references rewritten to explicit fields)*

### **3.1 Determinism**

**HLR‑20.109‑001**  
IE SHALL be deterministically reproducible from the same IIInB output.

**HLR‑20.109‑002**  
IE SHALL NOT include nondeterministic fields (timestamps, random IDs, environment‑dependent values) in **IE.metadata**.

---

### **3.2 Boundedness**

**HLR‑20.109‑003**  
IE SHALL enforce bounded size limits on **IE.intake** as defined by system intake constraints.

**HLR‑20.109‑004**  
IE SHALL truncate or summarize oversized **IE.intake** fields using a deterministic, documented procedure.

---

### **3.3 Replayability**

**HLR‑20.109‑005**  
IE SHALL encode all information required for downstream components to replay the user’s input without accessing external state, stored in **IE.metadata.replay**.

**HLR‑20.109‑006**  
IE SHALL preserve ordering of user‑provided tokens, structures, and metadata in **IE.intake.tokens** and **IE.structure**.

---

### **3.4 Structural Normalization**

**HLR‑20.109‑007**  
IE SHALL represent the user’s input using the normalized structural schema defined by the IE specification.

**HLR‑20.109‑008**  
IE SHALL include structural tags (token spans, block boundaries, markup indicators) in **IE.structure** when present in IIInB output.

---

### **3.5 IIInB‑Applied Repairs**

**HLR‑20.109‑009**  
IE SHALL incorporate all repair proposals from IIInB into **IE.intake** without modification.

**HLR‑20.109‑010**  
IE SHALL mark repaired regions using **IE.metadata.repair_annotations**.

---

### **3.6 Token Normalization**

**HLR‑20.109‑011**  
IE SHALL contain a normalized token sequence in **IE.intake.tokens**, including whitespace normalization, canonicalization, and repair integration.

**HLR‑20.109‑012**  
IE SHALL preserve token boundaries exactly as defined by the IIInB tokenizer.

---

### **3.7 Structural Integrity**

**HLR‑20.109‑013**  
IE SHALL validate its structure against the IE schema before being passed to CEx.

**HLR‑20.109‑014**  
IE SHALL reject malformed or incomplete structures and return a deterministic error envelope in **IE.error**.

---

### **3.8 Prohibited Content**

**HLR‑20.109‑015**  
IE SHALL NOT contain any semantic interpretations, inferred meanings, candidate expansions, or truth‑evaluation artifacts.  
**TP.semantic SHALL remain empty until CE → ISc → TPU.**

---

## **4. Mathematical Form (Informative)**

A simplified representation of the IE can be expressed as:

$$
IE = \\{ IE.intake, IE.structure, IE.metadata \\}
$$

Where:

- **IE.intake** = normalized token sequence + applied repairs  
- **IE.structure** = structural tags  
- **IE.metadata** = replay metadata, ruleset identifiers, repair annotations  

This is illustrative; the normative schema is defined elsewhere.

---

## **5. Example (Informative)**

An example IE may include:

- normalized tokens in **IE.intake.tokens**  
- repair annotations in **IE.metadata.repair_annotations**  
- structural tags in **IE.structure**  
- deterministic replay metadata in **IE.metadata.replay**  

No semantic interpretation is included; **TP.semantic is still empty**.
