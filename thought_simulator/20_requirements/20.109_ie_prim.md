# **20.109 — IE Primitive (Intake Envelope / Structured Intake Object)**

## **1. Purpose** *(Informative)*

The Intake Envelope (IE) is the **final pre‑semantic representation of the user’s input** in Path‑A. It is produced after IIInB has identified deterministic repair operations. IE provides a **fully normalized, repaired, bounded, deterministic, replay‑safe** representation of the user’s input that CEx can consume without performing any semantic interpretation.

IE exists to ensure that:

### **1. All deterministic repairs are applied before semantic processing begins**  
IIInB proposes repairs; IE applies them. This guarantees that CEx, CE, and all downstream semantic modules operate on **clean, normalized, repaired input** that no longer contains surface defects, shorthand forms, or noisy artifacts.

### **2. The input is structurally stable and schema‑validated**  
IE enforces a **canonical structural schema**, including:

- normalized token sequence  
- deterministic whitespace and punctuation normalization  
- repair annotations  
- structural tags  
- deterministic metadata for replay  

This ensures that downstream modules receive a **stable, predictable, schema‑validated** input object.

### **3. The input is fully deterministic and replay‑equivalent**  
IE encodes all information needed for deterministic replay:

- repair operations  
- structural tags  
- token boundaries  
- normalization metadata  
- ruleset identifiers  

This allows governance, audit, and replay systems to reconstruct the exact input state without accessing external context.

### **4. The input is safe for CEx and CE**  
IE is the **last pre‑semantic boundary** before CEx.  
It ensures that CEx receives:

- no semantic content  
- no inferred meaning  
- no ambiguity resolution  
- no candidate expansions  
- no truth evaluation  
- no nondeterministic fields  

CEx can therefore perform identity‑layer selection and context extraction **without risk of semantic contamination**.

### **5. Path‑A begins semantic processing from a clean foundation**  
IE is the bridge between:

- **InB → IIInB** (canonicalization + repair proposals)  
- **CEx → CE → ISc** (context extraction + semantic processing)

IE ensures that semantic modules begin from a **clean, deterministic, repaired, normalized, bounded** representation of the user’s input.

IE is a **data‑integrity primitive**, not a semantic module.  
It exists to guarantee that all semantic processing begins from a **stable, deterministic, pre‑semantic foundation** that is fully auditable and replay‑safe.

---

## **2. Position in Pipeline (Informative)**

IE is produced:

- After InB → IIInB  
- Before CEx  
- Before any semantic interpretation

---

## **3. Normative Requirements**

### **3.1 Determinism**

**HLR‑20.109-001**  
The IE **SHALL** be deterministically reproducible from the same IIInB output.

**HLR‑20.109-002**  
The IE **SHALL** not include any nondeterministic fields (timestamps, random IDs, environment‑dependent values).

---

### **3.2 Boundedness**

**HLR‑20.109-003**  
The IE **SHALL** enforce a bounded size limit defined by the system’s intake constraints.

**HLR‑20.109.004**  
The IE **SHALL** truncate or summarize oversized fields using a deterministic, documented procedure.

---

### **3.3 Replayability**

**HLR‑20.109-005**  
The IE **SHALL** encode all information required for downstream components to replay the user’s input without accessing external state.

**HLR‑20.109-006**  
The IE **SHALL** preserve ordering of user‑provided tokens, structures, and metadata.

---

### **3.4 Structural Normalization**

**HLR‑20.109-007**  
The IE **SHALL** represent the user’s input using a normalized structural schema defined by the IE specification.

**HLR‑20.109-008**  
The IE **SHALL** include structural tags (e.g., token spans, block boundaries, markup indicators) when present in the IIInB output.

---

### **3.5 IIInB‑Applied Repairs**

**HLR‑20.109-009**  
The IE **SHALL** incorporate all IIInB‑applied repairs from IIInB without modification.

**HLR‑20.109-010**  
The IE **SHALL** mark repaired regions using the IE repair‑annotation schema.

---

### **3.6 Token Normalization**

**HLR‑20.109-011**  
The IE **SHALL** contain a normalized token sequence derived from IIInB, including whitespace normalization, canonicalization, and repair integration.

**HLR‑20.109-012**  
The IE **SHALL** preserve token boundaries exactly as defined by the IIInB tokenizer.

---

### **3.7 Structural Integrity**

**HLR‑20.109-013**  
The IE **SHALL** validate its structure against the IE schema before being passed to CEx.

**HLR‑20.109-014**  
The IE **SHALL** reject malformed or incomplete structures and return a deterministic error envelope.

---

### **3.8 Prohibited Content**

**HLR‑20.109-015**  
The IE **SHALL** not contain any semantic interpretations, inferred meanings, candidate expansions, or truth‑evaluation artifacts.

---

## **4. Mathematical Form (Informative)**

A simplified representation of the IE can be expressed as:

$$
IE = \{ T, R, S, M \}
$$

Where:

- $T$ = normalized token sequence  
- $R$ = IIInB‑applied repairs  
- $S$ = structural tags  
- $M$ = metadata required for deterministic replay  

This is an illustrative form only; the normative schema is defined elsewhere.

---

## **5. Example (Informative)**

An example IE may include:

- Normalized tokens  
- Repair annotations  
- Structural tags such as `$<block\_start>$`, `$<block\_end>$`  
- Deterministic metadata fields  

No semantic interpretation is included.
