# 20.80_Security and Safety Requirements

## 1. Purpose

This document defines the **security and safety requirements** for the **Thought Simulator (TS)**.

It ensures the simulator is robust against misuse, resource exhaustion, data corruption, unintended behavior, and partial failures while preserving determinism, observability, architectural integrity, and long-term research reproducibility.

## 2. Core Security & Safety Principles

* Safety and determinism are inseparable â€” no safety mechanism may introduce nondeterminism when `deterministic_mode` is enabled.
* The core TS engine must be **defensively isolated** from all observer layers (manifold translator, UI, probes, plugins).
* All inputs, configurations, and extensions must be validated without side effects on simulation semantics.
* Resource consumption must be strictly bounded and controllable (see 20.40_performance_requirements.md).
* Safety features must themselves be observable, testable, and fully traceable (see 20.60_testing_and_validation.md).
* The external Observer must never be able to inject behavior into the mechanical core.

## 3. Input Validation and Configuration Safety

**S-INP-01: Strict Configuration Validation**  
- All configuration files and command-line parameters must be schema-validated on startup.
- Unknown or malformed settings must cause clear failure with diagnostic output (fail-fast).

**S-INP-02: Safe Default Configurations**  
- If no configuration is provided, the TS must use safe, bounded, and deterministic default values.

**S-INP-03: Configuration Immutability**  
- After initialization and before the first tick, all configuration parameters **must become immutable** for the entire duration of the run.
- Any attempt to modify configuration mid-run must be rejected.

**S-INP-04: Seed and Snapshot Integrity**  
- Random seeds and loaded snapshots must be cryptographically hashed and verified.
- Any mismatch must abort the run with clear error and final diagnostic log.

**S-INP-05: Safe Parameter Ranges**  
- All numeric parameters must be clamped to safe, documented ranges.
- Out-of-range values must be rejected or clamped with logged warning.

## 4. Runtime Safety and Resource Protection

**S-RUN-01: Resource Bounding**  
- Hard limits on active ThoughtPoints, memory, history depth, and tick rate.
- Exceeding hard limits must trigger graceful shutdown with full snapshot.

**S-RUN-02: Execution Timeouts**  
- Configurable maximum wall-clock time and maximum tick count.
- Automatic termination with final snapshot and summary.

**S-RUN-03: Regulator Safe Failure Modes**  
- Regulators must **fail safe**: if a regulator encounters an internal error, the TS must immediately halt with a final snapshot and diagnostic log rather than continue in an undefined state.

**S-RUN-04: Loop and Divergence Protection**  
- Regulators and watchdog mechanisms must prevent infinite loops, stagnation, or entropy explosion.
- Watchdog must detect stalled tick progress and force safe termination.

**S-RUN-05: Memory Safety**  
- No unbounded allocations. Long-run memory leak detection required in validation suite.

**S-RUN-06: Safe Shutdown Ordering**  
- On any safety-triggered shutdown, the TS must follow this exact sequence:
  1. Freeze simulation state
  2. Flush all pending logs
  3. Write final snapshot
  4. Close resources gracefully

## 5. Data Integrity and Reproducibility Safety

**S-DAT-01: State Corruption Prevention**  
- Internal state counters and checksums must be maintained and periodically validated.
- Any detected corruption must halt execution immediately.

**S-DAT-02: Atomic Snapshot Writes**  
- Snapshots must be written atomically (e.g., write to temporary file then rename) to prevent partial/corrupted snapshots if interrupted.

**S-DAT-03: Snapshot Integrity and Compatibility**  
- Snapshots must include integrity hashes and schema version.
- Loading a tampered snapshot must be rejected.
- Clear policy: Snapshots from version N must load correctly in version N+1 (unless explicitly deprecated).

## 6. Isolation and Extension Safety

**S-ISO-01: Layer Isolation**  
- Core TS engine must have zero direct dependencies on UI, manifold translator, or visualization code.
- Observer tools may only interact through well-defined, read-only interfaces.

**S-ISO-02: Safe Plugin / Extension API**  
- Any plugin or extension API (if provided) must be sandboxed, strictly read-only, and unable to modify core TS state, scheduling, entropy, or behavior.
- No user-provided code execution is allowed inside the core simulation loop.

**S-ISO-03: Architectural Conformance**  
- Static checks must enforce partitioning (see 20.60_testing_and_validation.md).

## 7. Logging and Failure Handling

**S-LOG-01: Safe Logging Under Failure**  
- Logging subsystem must remain functional even under partial system failure so that all safety events, regulator failures, and termination reasons are recorded.
- Critical safety events must be logged at `standard` level or higher.

## 8. Dependency and Supply-Chain Safety

**S-DEP-01: Minimal Dependencies**  
- Core TS engine should minimize third-party dependencies.
- All dependencies must be pinned with hashes.

**S-DEP-02: Reproducible Builds**  
- The project must support fully reproducible builds for verification across machines.

## 9. Invariants (Non-Negotiable)

* No safety feature may introduce nondeterminism in `deterministic_mode`.
* Configuration becomes immutable after startup.
* Core simulation mechanics must remain isolated from all observer and extension layers.
* Resource exhaustion or safety violations must always produce a usable final snapshot and complete diagnostic logs.
* Safety mechanisms must be fully testable and observable.

## 10. Success Criteria

* The TS can run multi-hour simulations with 10,000+ TPs without crashes, unbounded resource growth, or silent failures.
* All invalid inputs, corrupted snapshots, regulator failures, and limit violations result in safe termination with full observability.
* Architectural isolation, configuration immutability, and safe shutdown ordering are statically and dynamically enforced.
* Snapshots remain compatible across versions, preserving long-term research reproducibility.
* A researcher can run long or edge-case experiments with confidence that the system will either complete correctly or fail safely and traceably.
