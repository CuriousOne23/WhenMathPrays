# 20.102 USP Requirements

**Document ID:** 20.102  
**Version:** 0.1  
**Date:** 2026-06-07  
**Status:** Approved v0.1 — Track H (2026-06-07; CuriousOne23, Copilot, Grok)

## Purpose

Defines deterministic **User Semantic Profile (USP)** behavior: a versioned, auditable store of user/conversation **shorthand rules** committed after clarification. USP supplies read-only rule snapshots to IIInB at intake and is governed under COB versioning policy.

This module **does not** perform meaning construction, routing, expression planning, or per-cycle TP intent derivation.

## Non-Goals

- **Intent structuring or task typing** — owned by Pipeline A (OB, TR, TB), not USP.
- **Routing or execution contracts** — owned by RB, SRP, and `exec_plan`; UPI does not generate job specs.
- **Semantic input repair at intake** — owned by IIInB (`input_semantic_repair` stage); USP is read-only to IIInB.
- **Direct rule commits** — only [20.103](20.103_upi_requirements.md) UPI may write USP entries after GB-gated clarification outcomes.
- **IMR or Pipeline B coupling** — USP SHALL NOT be read or written by IMR, OuB, or B envelopes.

## Parent Scope

- **Program:** [20.510](20.510_refactoring_for_input_correction_track_h.md) Track H
- **Informs:** [20.103](20.103_upi_requirements.md) (writer), [20.101](20.101_iiinb_requirements.md) (reader), [20.32](20.32_cob_requirements.md) (version pins)
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents
- **Closure context:** [20.100](20.100_inb_requirements.md) v0.2 — semantic repair out of InB

## Functional Boundaries

| Component | Relationship to USP |
|-----------|-------------------|
| **UPI** | Sole writer of `usp_rule` entries via `upi_commit_record` |
| **IIInB** | Read-only consumer of pinned `usp_snapshot` at `input_semantic_repair` |
| **COB** | Governs USP snapshot versioning, export/redaction, conversation continuity |
| **GB** | Veto / approve unsafe rule classes on UPI commit ([20.80](20.80_gb_requirements.md)) |
| **CIL** | Upstream of clarification; does not write USP directly |
| **InB / IB / IMR** | No USP read/write authority |

## Normative Requirements

### Store semantics and authority

1. **HLR-20.102-001:** USP SHALL store only **explicit shorthand rules** derived from approved clarification outcomes — not inferred latent preferences.
2. **HLR-20.102-002:** USP SHALL be the **only** durable store for user/conversation shorthand rules used by IIInB.
3. **HLR-20.102-003:** USP writes SHALL occur **only** through UPI commit pathways authorized by [20.103](20.103_upi_requirements.md); no other subsystem SHALL append or mutate active rule entries.
4. **HLR-20.102-004:** USP SHALL NOT write TP, MTP, `semantic_core`, `exec_plan`, `exec_trace`, or OB/TR/TB fields.
5. **HLR-20.102-005:** USP SHALL NOT perform per-turn meaning construction or routing.

### Read model (IIInB)

6. **HLR-20.102-006:** IIInB SHALL consume USP via **read-only snapshot load** pinned by `usp_version_ref` at the start of each `input_semantic_repair` pass.
7. **HLR-20.102-007:** USP snapshots presented to IIInB SHALL be **immutable** for the duration of that repair pass.
8. **HLR-20.102-008:** USP read failures SHALL follow deterministic reject-or-degrade policy with fixed audit reason codes; IIInB SHALL escalate unknown segments per [20.101](20.101_iiinb_requirements.md), not guess.

### Versioning and COB integration

9. **HLR-20.102-009:** Every UPI commit SHALL produce a monotonic `usp_version_id` and content-addressed `usp_version_ref` (hash of canonical serialized snapshot per [20.95](20.95_ts_numeric_policy.md) when applicable).
10. **HLR-20.102-010:** COB SHALL pin active USP snapshot references for conversation scope per [20.32](20.32_cob_requirements.md) lifecycle policy (HLR-20.031-027–032).
11. **HLR-20.102-011:** USP version transitions (create, supersede, revoke) SHALL occur only at deterministic safe boundaries.
12. **HLR-20.102-012:** Superseded rules SHALL remain in immutable audit history; active rule resolution SHALL use deterministic precedence: **scope specificity > version > `rule_id` lexicographic sort**.

### Rule lifecycle

13. **HLR-20.102-013:** USP SHALL support rule states: `ACTIVE`, `SUPERSEDED`, `REVOKED` with deterministic transitions only via UPI commit or GB-mandated revocation.
14. **HLR-20.102-014:** GB veto of a proposed rule commit SHALL NOT create an `ACTIVE` entry; veto outcomes SHALL append audit evidence only.
15. **HLR-20.102-015:** Revoked rules SHALL NOT be applied by IIInB on subsequent passes.

### Bounds and determinism

16. **HLR-20.102-016:** USP SHALL enforce a maximum active rule count per conversation scope (default = 256, configurable via [20.90](20.90_ts_parameter_table.md)); overflow SHALL reject new commits deterministically with fixed reason code.
17. **HLR-20.102-017:** USP rule matching inputs SHALL use bounded segment patterns only — no open-ended fuzzy or latent matchers in v0.
18. **HLR-20.102-018:** USP behavior SHALL be deterministic and replayable: identical clarification commit sequence and profile state SHALL yield identical active rule sets and `usp_version_ref` values.
19. **HLR-20.102-019:** USP serialization for replay export SHALL use canonical field ordering and stable identifier ordering per [20.95](20.95_ts_numeric_policy.md).

### Audit and observability

20. **HLR-20.102-020:** Every USP version transition SHALL append a `usp_version_record` to conversation audit storage (COB-visible).
21. **HLR-20.102-021:** `usp_version_record` and `usp_rule` exports SHALL be consumable by MB without mutating USP state.
22. **HLR-20.102-022:** USP SHALL emit fixed reason codes for reject, cap-exceeded, veto, and unsupported-schema outcomes.

### Parent compliance

23. **HLR-20.102-023:** USP requirements in this module SHALL satisfy and SHALL NOT weaken parent invariants in 20.10 and 20.30.
24. **HLR-20.102-024:** USP behavior SHALL remain fully testable via deterministic fixtures: empty profile, single rule, supersede chain, revoke, cap overflow, GB veto.

## Wire Schemas (Normative Minimum — v0.1)

### `usp_rule`

```text
usp_rule {
  rule_id,                   // stable schema-versioned ID
  rule_version,              // monotonic per rule_id
  rule_state,                // ACTIVE | SUPERSEDED | REVOKED
  scope,                     // USER | CONVERSATION | CHANNEL (canonical enum)
  pattern,                   // bounded match pattern (segment/text class)
  expansion,                 // bounded replacement / expansion payload
  clarification_ref,         // provenance link to clarification_event
  upi_commit_ref,            // link to upi_commit_record
  gb_approval_ref?,          // when GB gate applied
  effective_from_version_id, // usp_version_id when rule became ACTIVE
  superseded_by_rule_id?,    // if SUPERSEDED
  rationale_codes[]          // canonical sort order
}
```

### `usp_version_record`

```text
usp_version_record {
  usp_version_id,            // monotonic per conversation scope
  usp_version_ref,           // content hash of canonical active-rule snapshot
  prior_version_ref?,        // lineage
  active_rule_count,
  commit_refs[],             // upi_commit_record IDs in this version (canonical order)
  cob_snapshot_pin?,         // COB linkage per 20.32
  policy_signature,
  reason_codes[]
}
```

### Active snapshot (IIInB read contract)

IIInB SHALL load the snapshot referenced by `usp_version_ref` containing only rules in `ACTIVE` state at commit time, with deterministic conflict resolution per HLR-20.102-012.

## Verification Focus

- Deterministic snapshot identity for identical commit sequences.
- Read-only IIInB contract: no USP mutation during repair pass.
- Supersede/revoke precedence and cap enforcement.
- GB veto path produces no active rule.
- COB pin linkage per [20.32](20.32_cob_requirements.md) HLR-20.031-027–032.
