# **20.107 — CEx Extract**  
**Document ID:** 20.107  
**Version:** 1.1 (TP‑Field Cleanup)  
**Date:** 2026‑07‑17  
**Upstream:** IE (20.109)  
**Downstream:** CE (20.108), ISc (20.44)

---

## **1. Purpose** *(Informative)*

CEx (Context Extractor) is the module that reads **CIL** and produces a **bounded, deterministic, structured context envelope (CE)**.  
CEx performs **no semantic repair, no inference, and no meaning generation**.

CEx has two primary responsibilities:

### **1. Extract explicit, structured context fields from CIL**  
CEx normalizes identity‑layer fields, certainty, ambiguity, stability, structural hints, referent mappings, register hints, and ordering metadata into **CE.context_fields**.

### **2. Select the correct identity‑layer context for the present turn**  
CEx applies deterministic continuity rules using:

- **TP.process.identity_layer_prev** (previous turn’s identity‑layer),  
- **CIL.identity_selection_block**,  
- **CIL.ordering_metrics** (recency, frequency, density, ordering_score),  
- **CIL.certainty / ambiguity scores**,  
- **CIL.collapse_risk**,  
- deterministic fallback rules.

CEx does **not** modify CIL, COB, TP.semantic, TP.process, TP.metadata, or any upstream structure.  
Its role is strictly mechanical: **extract explicit fields, resolve identity‑layer continuity deterministically, and normalize the result into CE**.

---

## **2. Position in the Inference Path** *(Informative)*

```
InB → IIInB → IE → CEx → CE → ISc → TPU → TP(N+1)
```

CEx sits between IE and ISc and is the first module that transforms CIL into a structured object.

---

## **3. Scope** *(Informative)*

CEx:

- reads **CIL**  
- extracts explicit, bounded context  
- normalizes surface‑form fields  
- emits **CE**  
- records extraction audit entries  

CEx does **not**:

- infer meaning  
- repair semantics  
- classify messy input  
- read or write **TP.semantic**, **TP.process**, **TP.metadata**, or MTP  
- read routing metadata or ΔH%  
- use embeddings or probabilistic reasoning   

---

## **4. Inputs** *(Informative)*

CEx consumes (all read‑only):

```
cex_input {
    cil_record,
    ie_projection,
    tp_snapshot_id,
    policy_signature
}
```

---

## **5. Outputs** *(Informative)*

CEx emits:

```
ce_output {
    ce_record,
    extraction_audit[],
    version_tag
}
```

---

## **6. Extraction Behavior** *(Informative)*

CEx extracts only explicit fields present in CIL, applies deterministic normalization, enforces bounded limits, and records all drops or truncations in the audit trail.

Malformed CIL still produces a CE containing only valid extracted fields.

---

## **7. Allowlist / Denylist Model** *(Informative)*

Allowlist examples (explicit CIL fields):

- context strings  
- timestamps  
- structural metadata  
- conversation window slices  
- explicit parameters  

Denylist examples:

- inferred semantics  
- embeddings  
- routing metadata  
- ΔH%  
- semantic_core fields  
- TB/IB fields  
- Pipeline‑B envelopes  

---

## **8. Determinism and Replay** *(Informative)*

CEx produces identical CE for identical CIL and policy_signature.  
Ordering, normalization, and field selection are canonical and deterministic.

---

## **9. Error Handling** *(Informative)*

CEx never halts the pipeline.  
Malformed or partial CIL results in:

- extraction of valid fields  
- dropping invalid fields  
- audit entries describing the drops  
- emission of CE regardless of input quality

---

# **10. High‑Level Requirements (HLRs)**  
*(All TP references rewritten to explicit TP fields)*

### **HLR‑20.107‑001**  
CEx SHALL be the only module permitted to read CIL.

### **HLR‑20.107‑002**  
CEx SHALL extract only explicit, structured, bounded context fields from CIL.

### **HLR‑20.107‑003**  
CEx SHALL NOT perform semantic repair, inference, or meaning generation.

### **HLR‑20.107‑004**  
CEx SHALL emit CE in deterministic, canonical form.

### **HLR‑20.107‑005**  
CEx SHALL NOT read or write **TP.semantic**, **TP.process**, **TP.metadata**, MTP, routing metadata, ΔH%, or semantic_core.

### **HLR‑20.107‑006**  
CEx SHALL enforce allowlist‑only extraction and SHALL drop denylisted fields with audit entries.

### **HLR‑20.107‑007**  
CEx SHALL NOT classify or modify messy_input tags.

### **HLR‑20.107‑008**  
CEx SHALL NOT use embeddings, probabilistic reasoning, or latent inference.

### **HLR‑20.107‑009**  
CEx SHALL produce identical CE for identical CIL and policy_signature.

### **HLR‑20.107‑010**  
CEx SHALL NOT trigger downstream modules or perform multi‑stage extraction.

### **HLR‑20.107‑011**  
CEx SHALL record all drops, truncations, and normalizations in **CE.metadata.extraction_audit**.

### **HLR‑20.107‑012**  
CEx SHALL NOT modify CIL or any upstream structure.

### **HLR‑20.107‑013**  
CEx SHALL enforce bounded size limits on extracted fields.

### **HLR‑20.107‑014**  
CEx SHALL NOT read Pipeline‑B envelopes or execution traces.

### **HLR‑20.107‑015**  
CEx SHALL emit CE even when CIL is malformed, extracting only valid fields.

### **HLR‑20.107‑016**  
CEx SHALL select the identity‑layer context for the present turn using **CIL.identity_selection_block** and **CIL.ordering_metrics**.

### **HLR‑20.107‑017**  
CEx SHALL apply continuity rules using **TP.process.identity_layer_prev**.

### **HLR‑20.107‑018**  
CEx SHALL use recency (`last_referred`), frequency (`total_referrals`), and density (`recent_referrals`) to resolve low‑certainty or high‑ambiguity identity selection.

### **HLR‑20.107‑019**  
CEx SHALL override continuity only when primary_certainty exceeds a deterministic threshold and ambiguity_score falls below a deterministic threshold.

### **HLR‑20.107‑020**  
CEx SHALL apply fallback selection when identity selection is indeterminate (`primary_layer_id = null`).

### **HLR‑20.107‑021**  
CEx SHALL mark fallback selections with **CE.metadata.continuity_status = "undetermined"**.

### **HLR‑20.107‑022**  
CEx SHALL apply collapse fallback when collapse_risk exceeds a deterministic threshold.

### **HLR‑20.107‑023**  
CEx SHALL include **CE.metadata.continuity_status** in CE.

### **HLR‑20.107‑024**  
CEx SHALL NOT modify ordering metrics; it SHALL only consume them.

### **HLR‑20.107‑025**  
CEx SHALL guarantee deterministic identity‑layer selection for identical CIL and identical **TP.process.identity_layer_prev**.

---

## **HLR‑20.107‑026: Clarifying‑Field Extraction**  
CEx **shall** extract clarifying fields, clarifying subfields, and hierarchical clarifying sub‑subfields (up to four levels) from CIL into CE.context_fields.

## **HLR‑20.107‑027: Clarifying‑Field Normalization**  
CEx **shall** normalize clarifying‑field topology into a deterministic CE structure, preserving hierarchical relationships and bounded limits.

## **HLR‑20.107‑028: Clarifying‑Field Boundedness**  
CEx **shall** enforce bounded limits on clarifying fields (maximum 10), clarifying subfields (maximum 100), and hierarchical depth (maximum 4 levels), dropping excess entries with extraction‑audit records.

## **HLR‑20.107‑029: Clarifying‑Field Continuity**  
CEx **shall** preserve clarifying‑field continuity across turns by applying identity‑layer selection rules using clarifying‑field importance, topology, and stability metadata.

## **HLR‑20.107‑030: Clarifying‑Field Determinism**  
CEx **shall** produce identical clarifying‑field extraction results for identical CIL and identical policy_signature.

## **HLR‑20.107‑031: Clarifying‑Field Drop Auditing**  
CEx **shall** record all clarifying‑field drops, truncations, and topology compressions in **CE.metadata.extraction_audit**.

## **HLR‑20.107‑032: Clarifying‑Field Read‑Only Rule**  
CEx **shall** treat clarifying fields and clarifying subfields as read‑only and shall not modify their values, importance scores, or provenance.

## **HLR‑20.107‑033: Clarifying‑Field Fallback Behavior**  
When identity selection is indeterminate, CEx **shall** include clarifying‑field metadata from the fallback identity layer and mark the continuity status as `"undetermined"`.

## **Next‑Turn Context Extraction (TP.next_context_fields Cross‑Reference)**

**HLR‑20.107‑034**  
CEx SHALL read next‑turn clarifying/context fields exclusively from `TP.next_context{}` as defined in **20.105_tp_requirements.md**; CEx SHALL NOT read next‑turn context from any other TP fields.

**HLR‑20.107‑035**  
CEx SHALL treat all fields in `TP.next_context{}` as read‑only; CEx SHALL NOT modify, reinterpret, or transform next‑turn context values.

**HLR‑20.107‑036**  
CEx SHALL include next‑turn context fields in the CE output exactly as defined in 20.105, without renaming, omission, or structural modification.

**HLR‑20.107‑037**  
CEx SHALL include the following next‑turn context fields in **CE.context_fields**:  
`topic`, `stance`, `intent`, `register`, `politeness`, `epistemic_shading`, `continuity`, `direction`, `coherence`, `shift_required`, `importance`.

**HLR‑20.107‑038**  
CEx SHALL NOT derive next‑turn context fields from clarifying fields, structural cues, identity‑layer metadata, or referent maps; next‑turn context SHALL originate exclusively from `TP.next_context{}`.

**HLR‑20.107‑039**  
CEx SHALL guarantee deterministic replay of next‑turn context extraction; identical `TP.next_context{}` values and identical CIL input SHALL produce identical CE output.

**HLR‑20.107‑040**  
CEx SHALL NOT perform semantic interpretation when handling next‑turn context fields; next‑turn context SHALL be treated as explicit structured metadata only.

**HLR‑20.107‑041**  
CEx SHALL include next‑turn context fields in CE even when identity selection is ambiguous, indeterminate, or fallback‑selected.

**HLR‑20.107‑042**  
CEx SHALL reflect next‑turn context continuity across turns by including `TP.next_context{}` values in CE without modification.

**HLR‑20.107‑043**  
CEx SHALL NOT compute context coherence or context shift; it SHALL only reflect `TP.next_context.coherence` and `TP.next_context.shift_required` as provided by MCB.

**HLR‑20.107‑044**  
CEx SHALL record all next‑turn context drops, truncations, or normalization adjustments in **CE.metadata.extraction_audit**, following the same deterministic rules used for clarifying‑field extraction.

**HLR‑20.107‑045**  
CEx SHALL NOT write next‑turn context fields into clarifying fields; next‑turn context SHALL appear only in CE.context_fields.

**HLR‑20.107‑046**  
CEx SHALL NOT interact with truth/done fields, routing fields, structural geometry, ΔH%, lineage, or any Path‑B semantics when processing next‑turn context.

**HLR‑20.107‑047**  
CEx SHALL treat missing or partially populated `TP.next_context{}` fields as deterministic empty‑context cases and SHALL populate CE.context_fields with canonical empty values.

# **11. Conformance** *(Informative)*

CEx conforms when:

- CE is deterministic  
- only allowlisted fields appear in CE  
- no semantic inference occurs  
- no TP.semantic / TP.process / TP.metadata / MTP / routing / ΔH% fields are accessed  
- extraction_audit is complete and deterministic  
- malformed CIL still yields a valid CE  
- replay produces identical CE
