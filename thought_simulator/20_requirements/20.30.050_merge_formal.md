# **20.30.050 — Merge Formal Overview**  
**Status:** Normative  
**Scope:** Formal merge semantics, lane recombination, structural rules  
**Excludes:** ΔH% definition (10.50.xx), truth semantics (20.30.060), MTP update semantics (20.30.070)

---

# **0. Purpose**

This document defines the **formal merge semantics** used by Pipeline A to recombine lane‑local Thought Packets (TPs) into the Master Thought Packet (MTP).  
It establishes:

- the structural model of merging  
- the deterministic recombination contract  
- the field‑wise merge rules  
- the relationship between lane TPs and the MTP  
- the invariants required for replay equivalence  

This file provides the mathematical backbone for meaning recombination.

---

# **1. Merge Overview**

Merge is the **deterministic recombination** of lane‑local TPs into the global MTP.  
It integrates:

- lane‑local semantic fields  
- ΔH% contributions  
- TB interpretations  
- lineage updates  
- truth‑related fields (pre‑commit)  
- completion‑related fields (pre‑commit)  
- metadata fields (TPTB/TPSF), carried forward unchanged  

Merge is **purely structural**: it does not interpret meaning, infer new semantics, or modify TP content beyond deterministic recombination.

All semantic interpretation occurs earlier (OB/TB), and all state commitment occurs later by the responsible subsystem.

---

# **2. Merge Inputs and Outputs**

## **2.1 Inputs**

Merge receives:

- a set of lane‑local TPs  
- the prior MTP state  
- deterministic merge rules for each field  
- ΔH% contributions and missing‑mass indicators  
- TB interpretation outputs  
- lane‑local TPTB/TPSF metadata  
- prior‑MTP TPTB/TPSF metadata  

## **2.2 Output**

Merge produces:

- a single merged TP (the “merge result”)  
- a deterministic update structure suitable for commit  
- a complete, field‑wise recombined semantic structure  

The commit is performed by the subsystem responsible for Path A.

---

# **3. Field‑Wise Merge Semantics**

Merge applies **field‑specific deterministic rules**.  
Examples include:

- **max‑select** (confidence‑like fields)  
- **sum‑accumulate** (ΔH% contributions)  
- **overwrite‑on‑visibility** (stance/affect/intent)  
- **union‑accumulate** (semantic tags)  
- **rule‑based selection** (TB interpretations)  

These rules ensure that merging is:

- deterministic  
- auditable  
- replay‑equivalent  
- bounded  
- non‑expansive  

Exact rules for each field are defined in the 10‑series specifications.

---

# **4. Merge Ordering and Determinism**

Merge follows a **fixed, non‑configurable ordering**:

1. Initialize merge accumulator from prior MTP  
2. Integrate lane TPs in deterministic lane order  
3. Apply field‑wise merge rules  
4. Compute ΔH% missing‑mass adjustments  
5. Integrate TB interpretations  
6. Produce the merged TP  
7. Emit the deterministic update structure  

Lane order is deterministic and derived from routing and splitting rules.

Merge never depends on:

- hardware timing  
- thread scheduling  
- nondeterministic iteration order  
- probabilistic selection  

---

# **5. Merge Invariants**

Merge maintains the following invariants:

- **Determinism:** identical inputs produce identical merge results  
- **Completeness:** all lane TPs contribute according to merge rules  
- **Non‑expansion:** merge does not create new semantics  
- **Auditability:** merge results are fully reconstructable  
- **Replay equivalence:** merge behavior is stable across hardware  

These invariants ensure that merge is a stable, predictable component of Pipeline A.

---

# **6. Merge and ΔH%**

Merge integrates ΔH% contributions from lane TPs and computes:

- combined ΔH%  
- missing‑mass adjustments  
- normalization factors (if required)  

ΔH% is treated as a **structural quantity**, not a probability.  
Its definition and local entropy models are specified in the 10.50.xx series.

---

# **7. Merge and TB Interpretation**

TB outputs are integrated during merge using:

- rule‑based selection  
- overwrite semantics  
- structured field integration  

Merge does not reinterpret TB outputs; it only recombines them deterministically.

Detailed TB semantics appear in 20.30.060.

---

# **8. Merge Output and Commit Path**

Merge produces:

- the merged TP  
- a deterministic update structure  
- lineage updates  
- ΔH% adjustments  
- truth/completion fields  
- semantic tags  
- structural metadata  

The responsible subsystem performs the authoritative MTP write for the cycle.

Commit semantics are defined in 20.30.070.

---

# **9. Normative Requirements (HLR‑20.30.050‑xxx)**

These are the **only** SHALL‑bearing requirements in this file.

### **HLR‑20.30.050‑001 — Deterministic Merge**  
Merge SHALL recombine lane‑local TPs into a single merged TP using deterministic, field‑wise rules.

### **HLR‑20.30.050‑002 — No Semantic Invention**  
Merge SHALL NOT invent new semantics and SHALL only recombine existing lane‑local and prior‑MTP fields.

### **HLR‑20.30.050‑003 — Deterministic Lane Ordering**  
Merge SHALL process lane TPs in a deterministic, non‑configurable order.

### **HLR‑20.30.050‑004 — Field‑Wise Rule Application**  
Merge SHALL apply field‑specific deterministic merge rules for all semantic fields.

### **HLR‑20.30.050‑005 — ΔH% Integration**  
Merge SHALL integrate ΔH% contributions and missing‑mass adjustments deterministically.

### **HLR‑20.30.050‑006 — TB Integration**  
Merge SHALL integrate TB interpretation outputs deterministically without reinterpretation.

### **HLR‑20.30.050‑007 — Deterministic Update Structure**  
Merge SHALL produce a deterministic update structure suitable for commit by the responsible subsystem.

### **HLR‑20.30.050‑008 — Replay Equivalence**  
Merge results SHALL be identical for identical sets of lane TPs, prior MTP state, and merge rules.

### **HLR‑20.30.050‑009 — TPTB Preservation**  
Merge SHALL NOT modify, reinterpret, or generate TPTB metadata. It SHALL carry forward lane‑local or prior‑MTP TPTB fields unchanged.

### **HLR‑20.30.050‑010 — TPSF Preservation**  
Merge SHALL NOT modify, reinterpret, or generate TPSF metadata. It SHALL carry forward lane‑local or prior‑MTP TPSF fields unchanged.

# **10. Summary**

20.30.050 defines the **formal merge semantics** of the TS:

- deterministic lane recombination  
- field‑wise merge rules  
- ΔH% and TB integration  
- deterministic lane ordering  
- deterministic update structure  
- no semantic invention  
- replay‑equivalent behavior  

This file provides the structural backbone for meaning recombination in Pipeline A.
