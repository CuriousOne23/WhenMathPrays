# 20.39 TS Core Data Structures

**Document ID:** 20.39  
**Version:** 0.5  
**Date:** 2026-06-07  
**Status:** Approved v0.5 — dual-pipeline envelopes + Track H wire structs (2026-06-07)

## Purpose

Provides **guidance** on core data structures for consistent 40-series prototyping under the dual-pipeline architecture. Aims to inform 10-series canonical definitions once prototyping insights are available.

Prototypes SHOULD align struct layout with [20.12_ts_invariants.md](20.12_ts_invariants.md) envelope partition and [20.36_canonical_end_to_end_trace.md](20.36_canonical_end_to_end_trace.md) fixture shape.

## Role in the Development Flow

**Guidance only** — directs 40-series exploration. Discoveries and trade-offs mature into 10-series specs. Normative behavior remains in 20.12 and module requirements (20.17, 20.45, 20.16, 20.80); this document does not override them.

## Parent Scope

- **Informs:** 40-series playground prototypes and replay harnesses
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents
- **Semantic authority:** field semantics in [20.31_semantic_specification.md](20.31_semantic_specification.md)

## Non-Goals

- Final data structure specification (10-series)
- Override of 20.31 semantic requirements
- Memory layouts, optimizations, or implementation details (50-series)

## 1. Envelope Partition (Dual-Pipeline)

TS runtime state SHOULD be modeled as four disjoint logical envelopes per 20.12:

| Envelope | Prototype container | Primary writers | Guidance |
|----------|---------------------|-----------------|----------|
| `semantic_core` | `SemanticCoreSnapshot` | Pipeline A | Meaning fields only; MTP-centered |
| `exec_plan` | `ExecPlanRecord` | Pipeline B planning | Triple + `routing_epoch_id` |
| `exec_trace` | `ExecTraceLog` (append-only) | Pipeline B expression/IMR | Artifacts + `imr_record` |
| `supervisory` | `SupervisoryState` | GB at safe boundaries | Caps, modes, deferred queue |

10. **HLR-20.039-010:** 40-series prototypes SHOULD implement the four envelopes as separate types with explicit write guards; cross-envelope mutation SHOULD fail fast in harness builds.

11. **HLR-20.039-011:** `semantic_core` SHOULD be a structured snapshot (not a flat MTP duplicate) containing propositions, stance, goals, ΔH%, Thought Router fields, and `messy_input_record` when present.

12. **HLR-20.039-012:** `exec_plan` and `exec_trace` SHOULD remain separate containers; prototypes SHOULD NOT combine planning decisions and expression artifacts in one mutable struct.

13. **HLR-20.039-013:** `supervisory` SHOULD stay minimal — cap counters, mode state, deferred queue, GB audit records — and SHOULD NOT embed meaning-construction fields.

## 2. Core Structure Guidance

1. **HLR-20.039-001:** Prototypes SHOULD implement MTP as the central meaning container, incorporating key fields from 20.31; Pipeline A commits into `semantic_core` views derived from MTP update stages.

2. **HLR-20.039-002:** TP SHOULD be a lightweight, lane-specific projection or view derived from MTP / `semantic_core` — not a second authoritative meaning store.

18. **HLR-20.039-018:** TP SHOULD NOT carry `routing_epoch_id`; epoch metadata belongs only to execution-layer structs (`ExecPlanRecord`, `imr_record`, SRP lookup refs).

3. **HLR-20.039-003:** IB SHOULD include rich metadata (priority, uncertainty, ΔH% trajectory, lineage, evidence accumulation) to support GB population control per 20.16/20.80.

4. **HLR-20.039-004:** OB, RB, and TB SHOULD satisfy semantic contracts in 20.31 and respective component documents (20.40, 20.50, 20.60).

5. **HLR-20.039-005:** GB state SHOULD remain minimal and supervisory-only; cap accounting (`gb_cap_record`), mode (`gb_supervisory_mode`), and rate-limit counters SHOULD live in `supervisory`, not in MTP meaning fields.

## 3. Governance Record Structures

40-series prototypes SHOULD treat hardened-module records as first-class, serializable blocks (minimum schemas in source modules):

| Record | Source | Attach to |
|--------|--------|-----------|
| `messy_input_record` | 20.17 | `semantic_core` |
| `imr_record` / `CorrectionTrigger` | 20.45 | `exec_trace` (append-only) |
| `gb_cap_record` | 20.16 | `supervisory` |
| `gb_supervisory_output` / `gb_mode_record` | 20.80 | `supervisory` |
| `gb_upi_commit_evaluation` | 20.80 §10 | `supervisory` (Track H) |

14. **HLR-20.039-014:** Prototypes SHOULD implement governance records as versioned structs with canonical field ordering for replay export per 20.95.

### 3.1 Track H conversation-layer records (outside envelopes)

Track H state is **conversation-scoped** — not part of the four runtime envelopes ([20.510](20.510_refactoring_for_input_correction_track_h.md) Stage 6).

| Record | Source | Attach to |
|--------|--------|-----------|
| `iiinb_repair_record` | 20.101 | Conversation audit + stage record |
| `input_repair_tag` / `input_segment` / `iiinb_escalation_ref` | 20.105 §3.4 | `TpLaneView` (IIInB-only writes) |
| `clarification_event` | 20.33 | Conversation-layer queue → UPI |
| `upi_commit_record` | 20.103 | Conversation audit |
| `usp_rule` / `usp_version_record` | 20.102 | USP store under COB |
| `cob_usp_snapshot_pin` | 20.32 | COB pin lineage |

21. **HLR-20.039-021:** Prototypes SHOULD model Track H conversation-layer state separately from the four runtime envelopes; USP snapshots, UPI commits, and CIL clarification events are conversation-scoped, not per-cycle `semantic_core` fields.

22. **HLR-20.039-022:** `UspSnapshot` SHOULD be immutable for the duration of an IIInB repair pass; prototypes SHOULD pin `usp_version_ref` on every `iiinb_repair_record`.

23. **HLR-20.039-023:** `TpLaneView` SHOULD include optional intake-bound fields per [20.105](20.105_tp_requirements.md) §3.4; only IIInB module logic SHOULD write these fields.

### 3.2 Intake-bound wire minimums (Track H — align 20.105 §3.4)

Prototypes SHOULD implement these as data-only structs on `TpLaneView`; field semantics are normative in [20.105](20.105_tp_requirements.md) §3.4 and [20.101](20.101_iiinb_requirements.md) wire schemas.

```text
InputSegment {
  segment_ref,
  segment_span_start,
  segment_span_end,
  segment_class,             // SHORTHAND_ELIGIBLE | LITERAL | UNKNOWN
  iiinb_event_id
}

InputRepairTag {
  segment_ref,
  repair_outcome,            // APPLIED | ESCALATED | SKIPPED | TRUNCATED
  rule_id?,
  resolved_segment_ref?,
  usp_version_ref,
  iiinb_event_id
}

IiinbEscalationRef {
  escalation_id,
  segment_ref,
  iiinb_event_id,
  escalation_reason_code
}
```

Intake arrays SHOULD sort by `(segment_ref, iiinb_event_id)` lexicographic before export/hash per HLR-20.039-019 and [20.105](20.105_tp_requirements.md) §3.4.

24. **HLR-20.039-024:** Track H audit structs (`ClarificationEvent`, `UpiCommitRecord`, `UspVersionRecord`, `CobUspSnapshotPin`, `IiinbRepairRecord`) SHOULD be data-only, versioned, and canonically ordered per 20.95 before export.

25. **HLR-20.039-025:** Prototypes SHOULD NOT store USP rules, clarification payloads, or repair tags inside `semantic_core`, `exec_plan`, or `exec_trace` envelopes.

15. **HLR-20.039-015:** Execution-layer structs (`ExecPlanRecord`, `imr_record`, SRP lookup refs) SHOULD carry `routing_epoch_id` as read-only metadata; prototypes SHOULD NOT store mutable epoch state on GB or `semantic_core` containers.

## 4. Design Guidance for 40-series

6. **HLR-20.039-006:** Prototypes SHOULD explore immutable structures for stability-critical components (`semantic_core` snapshots, committed `exec_plan`, append-only `exec_trace`).

7. **HLR-20.039-007:** Lineage and provenance tracking SHOULD support efficient deterministic replay and auditing per 20.36 stage records.

8. **HLR-20.039-008:** Safety policy structures (especially RB) SHOULD enable fast lookup and clear violation reporting.

9. **HLR-20.039-009:** All major structures SHOULD support deterministic serialization for debugging, traceability, and golden-fixture diffing.

16. **HLR-20.039-016:** Replay harnesses SHOULD implement `strip_scope` from 20.36 (`exec_plan`, `exec_trace` removal) and diff remaining `semantic_core` + `supervisory` deterministically.

17. **HLR-20.039-017:** Numeric fields in authoritative structs SHOULD use Q32.32 representation per [20.95_ts_numeric_policy.md](20.95_ts_numeric_policy.md) before hash or comparison.

19. **HLR-20.039-019:** Authoritative arrays in snapshots (`propositions[]`, `goals[]`, `lineage[]`, deferred queues, audit logs) SHOULD use deterministic canonical ordering before serialization — typically stable ID lexicographic sort, or `(module_id, tp_seq, lineage_seq)` per 20.95 where applicable.

20. **HLR-20.039-020:** Core structs SHOULD be **data-only**: they SHOULD NOT embed behavior, callbacks, implicit policy, or side-effecting methods; policy and transitions belong in module logic, not in container types.

## 5. Suggested Prototype Type Sketch (Non-Normative)

```text
SemanticCoreSnapshot {     // data-only; no embedded behavior
  mtp_snapshot_id,
  propositions[],           // canonical sort by stable proposition_id
  stance{}, goals[],        // goals[] canonical sort by goal_id
  delta_h{},
  thought_router_fields{},
  messy_input_record?,     // 20.17; messy_input_class[] canonically ordered
  policy_signature
}

TpLaneView {               // projection only; no routing_epoch_id
  tp_id, lane_id,
  semantic_core_ref,
  lane_local_fields{},
  // Track H intake-bound (IIInB-only writes — 20.105 §3.4)
  input_segments[]?: InputSegment,
  input_repair_tags[]?: InputRepairTag,
  iiinb_escalation_refs[]?: IiinbEscalationRef
}

UspSnapshot {              // immutable for one IIInB repair pass
  usp_version_ref,
  usp_version_id,
  active_rules[],            // ACTIVE only; canonical sort: rule_id
  policy_signature
}

ConversationLayerState {   // NOT a runtime envelope; conversation-scoped
  conversation_scope_id,
  active_usp_version_ref,
  clarification_queue[],   // FIFO by integration_seq
  pending_upi_commits[],   // cap per 20.103 HLR-016 (default 8)
  usp_version_records[],   // append-only audit
  cob_usp_snapshot_pins[]  // append-only pin lineage
}

IiinbRepairRecord {        // per repair pass audit (20.101 wire minimum)
  iiinb_event_id,
  cycle_id,
  input_packet_id,
  usp_version_ref,         // pinned read snapshot
  profile_enabled,
  segment_count,
  applied_rule_count,
  repair_outcomes[],         // APPLIED | ESCALATED | SKIPPED | TRUNCATED
  rule_ids[],                // canonical sort when APPLIED
  escalation_refs[],         // when ESCALATED
  cap_status,                // OK | SEGMENT_CAP | APPLY_CAP
  tcu_cost,
  reason_codes[],
  rationale_codes[]
}

ClarificationEvent {       // CIL → UPI wire (20.33 / 20.103)
  clarification_event_id,
  integration_seq,
  segment_ref,
  clarified_pattern,
  clarified_expansion,
  rule_scope,
  policy_signature
}

UpiCommitRecord {
  upi_commit_id,
  clarification_event_id,
  commit_status,
  usp_version_id?,
  usp_version_ref?,
  gb_approval_granted?,
  gb_reason_code?
}

ExecPlanRecord {
  routing_epoch_id,        // read-only
  opbeh_id, obg_id, xlater_id,
  exec_trigger_id?,
  planning_refs[]
}

ExecTraceLog {             // append-only
  entries[]: {
    oub_artifact_ref?,
    imr_record?,           // 20.45
    cycle_id, stage_seq
  }
}

SupervisoryState {
  gb_supervisory_mode,
  cap_counters{},          // 20.16 cap IDs
  deferred_queue[],
  gb_cap_records[],        // append-only
  gb_supervisory_outputs[] // append-only
}
```

## 6. Exploration Directives for 40-series

- Map each 20.36 replay class (1–5) to at least one golden fixture with concrete struct instances.
- Evaluate trade-offs between envelope separation, memory efficiency, and copy cost for snapshots.
- Test immutability and snapshot versioning for Pipeline A → Pipeline B handoff.
- Verify write-guard violations are detectable in replay diff (`FAIL_ENVELOPE`).
- Document challenges maintaining determinism under TCU pressure and overflow truncation.
- Identify 20.31 fields that are costly or ambiguous to represent; feed back to 10-series.
- Prototype deferred-queue drain and cap-counter reset at cycle boundaries per 20.16/20.80.
- Validate replay diffs are stable under canonical array ordering (HLR-20.039-019).
- Reject struct designs that couple TP to `routing_epoch_id` or embed policy in data containers (HLR-20.039-018/020).
- Prototype `ConversationLayerState` separate from `SemanticCoreSnapshot` and execution envelopes.
- Map 20.36 Class 7 fixtures to concrete `UspSnapshot` + `TpLaneView` intake field instances.
- Enforce IIInB write guard: only `input_*` / `iiinb_escalation_refs` on TP views.
- Canonical-sort intake arrays before golden-fixture export (segment_ref primary).
