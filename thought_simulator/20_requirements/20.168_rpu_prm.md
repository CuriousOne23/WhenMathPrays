# 20.168 RPU — Realization Production Unit Primitive

## Purpose

RPU is the execution primitive for Path B. It accepts the ordered realization plan  
`ssr.rplan` from RPlan, executes each step in index order using continuity‑weighted  
execution logic, and produces a typed partial realization `ssr.rpu_partial` and  
realization‑layer update fields for consumption by ReB.

RPU performs no planning, no meaning interpretation, and no scoring; it executes  
exactly what RPlan specified.

**[HLR‑20.168‑001]**  
RPU SHALL accept `ssr.rplan` as its activation input and SHALL produce  
`ssr.rpu_partial` and all realization‑layer update fields required by ReB before  
ReB begins execution for the same turn.

## Input Contract

| Field | Source | Required | Type | Validity |
|---|---|---|---|---|
| `ssr.rplan` | RPlan | Required | object | must be present; `rplan_status` ∈ {`VIABLE`, `BLOCKED`} |
| `ssr.rplan.rplan_status` | RPlan | Required | enum | `VIABLE` or `BLOCKED` |
| `ssr.rplan.ordered_steps` | RPlan | Required | array | non‑null; empty only when blocked |
| `ssr.rplan.ordered_steps[i].step_id` | RPlan | Required | string | non‑empty; unique |
| `ssr.rplan.ordered_steps[i].index` | RPlan | Required | integer | strictly increasing |
| `ssr.rplan.ordered_steps[i].constraint_set` | RPlan | Required | set | valid TP field refs |
| `ssr.rplan.ordered_steps[i].continuity_weight` | RPlan | Required | float | $\omega\_i \in [0,1]$ |
| `ssr.rplan.ordered_steps[i].step_status` | RPlan | Required | enum | `VIABLE` or `BLOCKED` |
| `ssr.continuity_fields` | CoHI | Required | object | must be present |
| `ssr.truth_tags` | A‑side | Required | array | may be empty |
| `ssr.safety_flags` | A‑side | Required | array | may be empty |

**[HLR‑20.168‑002]**  
RPU SHALL read only the fields enumerated in the Input Contract.

**[HLR‑20.168‑003]**  
If required fields are absent or malformed, RPU SHALL set  
`ssr.rpu_partial.rpu_status = ABORTED`, write `reason_code = PRE_CONDITION_FAULT`,  
and halt without executing any step.

## Transfer Function

### Abort Path

If `ssr.rplan.rplan_status = BLOCKED`, RPU performs no execution.

**[HLR‑20.168‑004]**  
RPU SHALL set `rpu_status = ABORTED`, propagate `ssr.rplan.reason_code`, mark all  
step records as `SKIPPED`, and execute no steps.

### Execution Path

Let $S = \langle s\_1, \dots, s\_k \rangle$ be the ordered steps.

Each step $s\_i$ has:

- constraint set $C\_i$  
- continuity weight $\omega\_i$

The resolved field set after executing $j$ steps is:

$$
\text{resolved}(j)
= \bigcup\_{i=1}^{j}
\text{fields}\bigl(\text{exec}(s\_i,\ \omega\_i)\bigr)
$$

A step is blocked when:

$$
\text{blocked}(s\_j)
= C\_j \not\subseteq \text{resolved}(j - 1)
$$

Execution halts at the first blocked step:

$$
j^\ast =
\begin{cases}
\min\{\, j \mid \text{blocked}(s\_j)\,\} & \text{if any blocked} \\
k + 1 & \text{otherwise}
\end{cases}
$$

The accumulated partial realization is:

$$
P =
\bigoplus\_{i=1}^{\min(j^\ast - 1,\ k)}
\text{exec}(s\_i,\ \omega\_i)
$$

where $\oplus$ is the realization accumulation operator (using $\ast$ as  
$\text{combine}\_\text{realization}$ internally, written as $\oplus$ here).

**[HLR‑20.168‑005]**  
RPU SHALL execute steps strictly in ascending index order.

**[HLR‑20.168‑006]**  
RPU SHALL apply continuity weights exactly as supplied by RPlan.

**[HLR‑20.168‑007]**  
Upon detecting a blocked step, RPU SHALL:

- mark that step `HALTED`  
- set `rpu_status = HALTED`  
- write a `reason_code`  
- mark all later steps `SKIPPED`  

The final `rpu_status` is:

$$
\text{rpu}\_\text{status} =
\begin{cases}
\text{ABORTED} & \text{if } \text{rplan}\_\text{status} = \text{BLOCKED or pre-condition fault} \\
\text{HALTED} & \text{if } j^\ast \leq k \\
\text{COMPLETE} & \text{if } j^\ast = k + 1
\end{cases}
$$


## Output Contract

| Field | Type | Values | Meaning |
|---|---|---|---|
| `ssr.rpu_partial.rpu_status` | enum | `COMPLETE`, `HALTED`, `ABORTED` | Execution outcome |
| `ssr.rpu_partial.reason_code` | string | non‑empty on failure | Cause of halt/abort |
| `ssr.rpu_partial.accumulated` | object | $P$ | Partial realization for ReB |
| `ssr.rpu_partial.step_records[i].step_id` | string | matches plan | Step identifier |
| `ssr.rpu_partial.step_records[i].step_status` | enum | `DONE`, `HALTED`, `SKIPPED` | Per‑step result |
| `ssr.rpu_partial.step_records[i].exec_result` | object | populated on `DONE` | Realization contribution |
| Realization‑layer update fields | object | per ReB contract | Inputs to ReB |

**[HLR‑20.168‑008]**  
RPU SHALL populate all output fields on all execution paths.

**[HLR‑20.168‑009]**  
RPU SHALL NOT write to any field owned by TPTB, TPSF, CoHI, LI, REx, or RPlan, and SHALL write only to ssr.rpu_partial.* fields.

## When

RPU runs once per turn, after RPlan and before ReB.

**[HLR‑20.168‑010]**  
RPU SHALL NOT begin until RPlan has written a completed `ssr.rplan`.

**[HLR‑20.168‑011]**  
RPU SHALL complete all writes before ReB begins execution.

## Why

RPlan constructs the plan; RPU executes it.  
ReB validates the execution; OuBB surfaces the final output.

This separation ensures determinism, auditability, and invariant preservation.

## Is Not

RPU is not a planner.  
RPU is not a semantic interpreter.  
RPU is not a scorer.  
RPU is not a router.  
RPU is not a memory system.  
RPU does not modify the plan.  
RPU does not generate final output.

## Example

RPlan commits three steps:

- $s\_1$: `confirm-referent`, $C\_1 = \emptyset$, $\omega\_1 = 0.88$  
- $s\_2$: `apply-register`, $C\_2 = \{\text{ssr.meaning}\}$, $\omega\_2 = 0.91$  
- $s\_3$: `emit-tokens`,  
  $C\_3 = \{\text{confirm-referent},\ \text{apply-register}\}$,  
  $\omega\_3 = 0.85$

All constraints satisfied → all steps `DONE` → $j^\ast = 4$.

RPU sets `rpu_status = COMPLETE` and ReB receives `ssr.rpu_partial.accumulated = P`.
