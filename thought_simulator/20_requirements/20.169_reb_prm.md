# 20.169 — Realization Basin Primitive (ReB‑prm)

## 1. Purpose

ReB‑prm defines the **Realization Basin** primitive in Path B.

ReB is a **non‑semantic, non‑generative, non‑planning** primitive that:

- **Receives:** a fully realized, channel‑ready artifact candidate from Pipeline B (e.g., OuBB/Output Builder or equivalent)
- **Applies:** final basin‑level checks and normalizations
- **Emits:** a single, basin‑approved realization artifact reference for downstream delivery/logging

ReB **does not**:

- read or modify `semantic_core`
- read or modify TP
- perform planning, generation, or style selection
- resolve incomplete meaning
- interact with Pipeline A

It is a **terminal basin** for Path B artifacts.

---

## 2. Position in the architecture

Path B (conceptual):

- REx → RPlan → RPU → OuBB (or equivalent builder) → **ReB** → Delivery / Logging

ReB sits **after** all realization and formatting work is complete and **before** any external emission or logging.

ReB is the **last internal gate** for Path B content.

---

## 3. Inputs and outputs

### 3.1 Inputs

ReB SHALL consume a single, fully realized candidate artifact:

- **`b_realization_candidate`**
  - reference to a channel‑ready artifact produced by OuBB (or equivalent)
  - includes:
    - content (text/markup/structured)
    - channel metadata
    - audience metadata
    - constraint/invariant status as reported by OuBB
    - provenance / exec_trace up to OuBB

ReB SHALL NOT read:

- TP
- `semantic_core`
- COB/CIL
- Pipeline A state

### 3.2 Outputs

ReB SHALL emit exactly one:

- **`reb_artifact_ref`**
  - reference to the basin‑approved artifact
  - includes:
    - final content reference (unchanged or normalized)
    - channel
    - audience
    - constraint/invariant status
    - extended provenance including ReB

If ReB detects a **hard violation** (see §5), it SHALL:

- emit a **ReB‑level event** to the supervisory/logging channel, and
- either:
  - mark `reb_artifact_ref` as **BLOCKED**, or
  - emit a **null/empty artifact ref** according to integration contract (20.58‑style), but
  - SHALL NOT invent or repair meaning.

---

## 4. High‑level requirements (HLRs)

### HLR‑20.169‑001 — Non‑semantic basin

ReB SHALL NOT:

- interpret or modify meaning
- change tone, style, or audience
- re‑plan or re‑order content
- generate new content

ReB operates only as a **basin‑level validator/normalizer** over a fully realized candidate.

---

### HLR‑20.169‑002 — Single‑artifact emission

ReB SHALL emit **exactly one** `reb_artifact_ref` per invocation.

No branching, no alternatives, no sampling.

---

### HLR‑20.169‑003 — Constraint/invariant consistency

ReB SHALL verify that:

- all constraints marked as satisfied by OuBB are **internally consistent** with the artifact
- all invariants marked as preserved are **not violated** by the artifact

If a violation is detected, ReB SHALL:

- log a ReB‑level violation event, and
- mark the artifact as BLOCKED or INVALID according to the integration contract.

ReB SHALL NOT attempt to repair the artifact.

---

### HLR‑20.169‑004 — Channel/audience consistency

ReB SHALL verify that:

- the artifact’s channel metadata is consistent with its structure (e.g., no raw HTML in a “plain_text” channel)
- the artifact’s audience metadata is present and well‑formed

ReB SHALL NOT re‑target or re‑style the artifact; it only checks consistency.

---

### HLR‑20.169‑005 — Provenance extension

ReB SHALL:

- append its own step to the artifact’s provenance/exec_trace
- include:
  - ReB version
  - timestamp
  - constraint/invariant check results
  - any violation flags

ReB SHALL NOT remove or rewrite prior provenance entries.

---

### HLR‑20.169‑006 — No Pipeline A interaction

ReB SHALL NOT:

- read from or write to TP
- read from or write to Pipeline A state
- trigger Pipeline A corrections

ReB is strictly a **Path B basin primitive**.

---

## 5. Violation handling

ReB may detect:

- **Constraint violations** (e.g., length, format)
- **Invariant violations** (e.g., forbidden content that should have been blocked earlier)
- **Channel/audience inconsistencies**

When such a violation is detected, ReB SHALL:

1. **Log a ReB‑level event**, including:
   - violation type
   - artifact reference
   - upstream provenance
2. **Mark the artifact as non‑emittable** according to the integration contract:
   - `reb_artifact_ref.status = BLOCKED` (or equivalent)
3. **Not attempt repair**:
   - no rewriting
   - no regeneration
   - no semantic changes

Any remediation is handled by higher‑level supervisory or correction systems, not by ReB.

## 5.1 Downstream Handling (TS Behavior)

### HLR‑20.169‑007 — TS SHALL suppress invalid realizations
If `reb_artifact_ref.status = BLOCKED`, the Thought Supervisor (TS) SHALL suppress the invalid realization and SHALL NOT emit the blocked artifact to the user. TS SHALL treat the BLOCKED state as terminal for the current thought.

### HLR‑20.169‑008 — TS SHALL record terminal BLOCKED state
When ReB emits a BLOCKED artifact, TS SHALL record the terminal BLOCKED state in the execution trace, including the ReB violation event, upstream provenance, and the final realization status. TS SHALL NOT invoke any additional Path B primitives, SHALL NOT invoke Path A, and SHALL NOT attempt retry, regeneration, or correction.

### HLR‑20.169‑009 — TS SHALL emit a deterministic fallback message
Upon receiving a BLOCKED artifact from ReB, TS SHALL emit a deterministic, non‑semantic fallback message to the user (e.g., “Your request resulted in an invalid response; please rephrase.”). This fallback message SHALL be static, SHALL NOT depend on the blocked realization content, and SHALL NOT be produced by any Path B primitive. TS SHALL then terminate the thought.

---

## 6. Is / Is not

### ReB IS

- a **terminal basin** for Path B artifacts
- a **validator/normalizer** of fully realized content
- a **single‑artifact gate** with deterministic behavior
- a **provenance extender**

### ReB IS NOT

- a planner (RPlan)
- a realizer (RPU)
- a builder (OuBB)
- a semantic interpreter
- a generator
- a memory system
- a Pipeline A component

---

## 7. Invariants

ReB SHALL maintain:

- **No semantic mutation:** meaning of the artifact must not change.
- **No style/tone mutation:** style/tone must not change.
- **No multi‑artifact branching:** exactly one artifact ref per invocation.
- **No TP/semantic_core access.**
- **Append‑only provenance.**

---

## 8. Example (informal)

Input:

- `b_realization_candidate`:
  - content: `"Sure, here are three steps to get started…"`
  - channel: `"chat"`
  - audience: `"general"`
  - constraints: `{ max_tokens: 300, satisfied: true }`
  - invariants: `{ no_hate: preserved, no_pii: preserved }`
  - provenance: `[REx, RPlan, RPU, OuBB]`

ReB:

- verifies constraints/invariants are consistent with content
- verifies channel/audience metadata is well‑formed
- appends ReB step to provenance
- emits `reb_artifact_ref` pointing to the same content, with updated provenance and status `OK`.

If a violation is found (e.g., invariant actually violated), ReB logs a violation event and marks the artifact as BLOCKED instead of repairing it.
