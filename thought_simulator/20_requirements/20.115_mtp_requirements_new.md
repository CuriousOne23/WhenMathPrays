# **4. Aggregation, Merge, and Split (Revised for Multi‑Core Orthogonal Path A)**

Below is the **only section modified**.

### **Updated HLRs 001–007**

1. **HLR‑20.115‑001 — UPDATED**  
   MTP SHALL represent the canonical aggregated state derived from deterministic TP contributions, including **multiple independent Path A results when multi‑core execution is active**.

2. **HLR‑20.115‑002 — UPDATED**  
   Every MTP SHALL include stable identity fields including `mtp_id`, lineage identifiers, and merge/split provenance markers.  
   When multi‑core execution is used, provenance SHALL record each core’s OB identity and orthogonality guarantee.

3. **HLR‑20.115‑003 — UPDATED**  
   MTP identity fields SHALL remain immutable after creation, except deterministic append‑only lineage extension markers.  
   Multi‑core Path A execution SHALL NOT create additional MTP identities; all cores feed a single MTP instance.

4. **HLR‑20.115‑004 — UPDATED**  
   MTP core fields SHALL include aggregated TP evidence, delta‑H‑percent trajectory fields, and bounded stability metrics.  
   When multiple cores are used, aggregation SHALL treat each core’s Path A as a **complete, independent artifact**.

5. **HLR‑20.115‑005 — UPDATED**  
   MTP aggregation behavior SHALL be deterministic for identical TP inputs, profile state, and signature‑bound policies.  
   Aggregation of multi‑core Path A results SHALL use a deterministic operator (e.g., voting, scoring, meta‑analysis) defined in system policy.

6. **HLR‑20.115‑006 — UPDATED**  
   MTP merge behavior SHALL preserve deterministic parent lineage and deterministic field‑wise aggregation semantics.  
   Merge SHALL NOT combine partial fragments of a single Path A; only whole Path A artifacts from each core may be merged.

7. **HLR‑20.115‑007 — NA**  
   *Original split behavior requirement no longer applies.*  
   **Reason:** MTP no longer supports split semantics except for multi‑core independent Path A execution, which is not a “split” of a single MTP.  
   **Status:** NA (superseded by multi‑core orthogonal Path A model).

### **New Sub‑Requirements (under HLR‑20.115‑006)**

These do not consume new HLR numbers.

**HLR‑20.115‑006.A**  
When multiple cores are available, the system MAY execute multiple Path A instances in parallel only if each core is bound to a distinct, orthogonal Observation Basis (OB).

**HLR‑20.115‑006.B**  
OBs assigned to different cores SHALL be information‑orthogonal, meaning their probes, features, or perspectives SHALL NOT overlap except where explicitly permitted by policy.

**HLR‑20.115‑006.C**  
Multi‑core execution SHALL NOT be treated as a “split” of a single Path A; each core produces a complete Path A artifact.

**HLR‑20.115‑006.D**  
MTP SHALL assemble multi‑core Path A results using a deterministic aggregation operator defined in system policy, and SHALL preserve traceability to each core’s OB and Path A artifact.
