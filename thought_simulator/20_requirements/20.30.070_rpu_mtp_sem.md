# **20.30.070 — RPU & MTP Update Semantics**  
**Status:** Normative (HLR‑20.30.070‑xxx only)  
**Scope:** RPU commit semantics, MTP update lifecycle, commit ordering  
**Excludes:** Merge semantics (20.30.050), truth/completion semantics (20.30.060), response generation (20.30.080)

---

# **0. Purpose**

This document defines the semantics of the **Realization Plan Updater (RPU)** and the **Master Thought Packet (MTP) update process**.  
It describes:

- how merge results are validated  
- how semantic updates are committed  
- how `commit_id` is generated  
- how the MTP becomes the frozen semantic snapshot for Pipeline B  
- how deterministic replay is preserved across commits  

RPU is the **sole writer** to the MTP.

---

# **1. RPU Overview**

The RPU is the authoritative commit engine of Pipeline A.  
It receives:

- the merged TP  
- truth/completion results  
- ΔH% adjustments  
- lineage updates  
- semantic tags  
- structural metadata
- TPTB metadata
- TPSF metadata  

RPU performs:

- structural validation  
- deterministic commit ordering  
- atomic update of the MTP  
- generation of a new `commit_id`  

RPU does **not** interpret meaning; it commits meaning.

---

# **2. MTP Overview**

The **Master Thought Packet (MTP)** is the global semantic state for the current thought.  
It contains:

- propositions  
- stance/affect/intent  
- ΔH%  
- truth hypotheses  
- completion state  
- lineage  
- semantic tags  
- supervisory metadata
- truth metadata (TPTB)
- safety metadata (TPSF)

The MTP is:

- explicit  
- structured  
- deterministic  
- replay‑equivalent  

Pipeline B reads the MTP but never modifies it.

---

# **3. RPU Input: Update Envelope**

Merge produces a **RPU update envelope** containing:

- the merged TP  
- truth/completion fields  
- ΔH% adjustments  
- lineage updates  
- semantic tags  
- structural metadata  
- overflow/stability metadata (if any)  

RPU validates the envelope structurally before committing it.

---

# **4. RPU Commit Semantics**

RPU commit semantics include:

- **structural validation** of the update envelope  
- **canonical ordering** of field updates  
- **atomic write** to the MTP  
- **deterministic conflict resolution** (if applicable)  
- **generation of a new `commit_id`**  

RPU commits occur **once per cycle** and are the final step of Pipeline A.

---

# **5. `mtp_update` — A/B Boundary**

`mtp_update` is the boundary between Pipeline A and Pipeline B.

At this boundary:

1. RPU finalizes the MTP  
2. A new `commit_id` is generated  
3. Pipeline B receives a **frozen** semantic snapshot  
4. Pipeline B performs realization and expression  
5. Pipeline A begins the next cycle using the updated MTP  

Pipeline B is strictly **read‑only** with respect to meaning.

---

# **6. Deterministic Replay and Commit Ordering**

RPU commit semantics ensure:

- identical inputs → identical MTP(N+1)  
- deterministic ordering of updates  
- deterministic lineage evolution  
- deterministic truth/completion state  
- deterministic ΔH% integration  
- deterministic supervisory metadata  

Commit ordering is fixed and non‑configurable.

---

# **7. Supervisory Visibility**

RPU exposes commit‑level metadata to supervisory layers, including:

- `commit_id`  
- overflow/stability metadata  
- truth/completion state  
- ΔH% adjustments  
- lineage updates  

GB and MB consume this metadata through deterministic interfaces.

---

# **8. Normative Requirements (HLR‑20.30.070‑xxx)**

These are the **only** SHALL‑bearing requirements in this file.

### **HLR‑20.30.070‑001 — RPU as Sole Writer**  
RPU SHALL be the sole writer to the MTP and SHALL perform all semantic commits.

### **HLR‑20.30.070‑002 — Deterministic Structural Validation**  
RPU SHALL validate the update envelope structurally before committing it.

### **HLR‑20.30.070‑003 — Canonical Commit Ordering**  
RPU SHALL apply updates in a deterministic, canonical order.

### **HLR‑20.30.070‑004 — Atomic MTP Update**  
RPU SHALL update the MTP atomically within a single deterministic commit step.

### **HLR‑20.30.070‑005 — Deterministic Commit ID**  
RPU SHALL generate a deterministic `commit_id` for each successful commit.

### **HLR‑20.30.070‑006 — Replay‑Safe Commit Behavior**  
RPU commits SHALL produce identical MTP(N+1) for identical (input, MTP state, execution signature) tuples.

### **HLR‑20.30.070‑007 — A/B Boundary Integrity**  
`mtp_update` SHALL freeze the MTP and SHALL be the sole handoff point to Pipeline B.

### **HLR‑20.30.070‑008 — Read‑Only Pipeline B**  
Pipeline B SHALL NOT modify the MTP and SHALL treat it as immutable.

### **HLR‑20.30.070‑009 — Supervisory Metadata Exposure**  
RPU SHALL expose deterministic commit metadata, including overflow/stability information, to supervisory layers.

### **HLR‑20.30.070‑010*
RPU SHALL commit the TPTB metadata structure atomically as part of the MTP update without reinterpretation or modification.

### **HLR‑20.30.070‑011*
RPU SHALL commit the TPSF metadata structure atomically as part of the MTP update without reinterpretation or modification.

---

# **9. Summary**

20.30.070 defines the authoritative commit semantics of Pipeline A:

- RPU as the sole writer  
- deterministic structural validation  
- deterministic commit ordering  
- atomic MTP updates  
- deterministic `commit_id` generation  
- immutable A/B boundary  
- replay‑safe behavior  
- supervisory visibility  

This file completes the definition of the MTP lifecycle.
