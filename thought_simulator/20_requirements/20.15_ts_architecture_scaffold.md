## **1. Purpose of This Document**
The **TS Architectural Scaffold** defines the *engine-level backbone* that all TS components must inherit.  
It establishes the cross-cutting rules that govern:

- primitive structure  
- YAML specification format  
- Python prototype behavior  
- C++ runtime behavior  
- envelope geometry  
- anomaly detection  
- routing transitions  
- dictionary interactions  
- modularity and determinism  
- testbench alignment  

This document sits between:

- **20.10_ts_architectural_principles.md** (high-level philosophy)  
- **20.12_ts_invariants.md** (system-wide invariants)  
- **20.20_ts_prim_proc_ref_gov.md** (primitive governance)

It provides the **unifying contract** that ensures TS remains modular, verifiable, and realizable in both Python and C++.

## **2. Architectural Positioning**
TS is a **modular cognitive engine** composed of:

- deterministic primitives  
- envelope-based geometry  
- invariant-driven routing  
- dictionary-backed semantics  
- dual execution layers (Python → C++)  
- YAML-defined behavior  

This scaffold defines the *rules that all primitives must follow*, regardless of domain (boundary, structural, semantic, routing, projection, etc.).

## **3. YAML as the Source of Truth**
### **3.1 Why YAML Exists**
All primitives load their behavior from YAML because:

- YAML is machine-readable  
- YAML is versionable  
- YAML is testable  
- YAML is diff-friendly  
- YAML separates *specification* from *implementation*  
- YAML enables hot-swappability  
- YAML enables C++ and Python to share the same contract  

### **3.2 YAML Defines Primitive Behavior**
Every primitive YAML must define:

primitive:
domain:
version:
description:

#### Lifecycle
start_conditions:  
done_conditions:

#### Behavioral Contract
invariants:
geometry:
fields:
refinement_rules:

#### Envelope Evaluation
envelope_status:
anomaly_flags:

#### Routing
routing:

#### External Dependencies (Dictionaries)
dependencies:
  meaning_dictionary: <dictionary_name_or_none>
  runtime_dictionary: <dictionary_name_or_none>
  dev_dictionary: <dictionary_name_or_none>

#### External Dependencies (Reference Artifacts)
reference_objects:
  - <object_name_or_none>

field_reference_tables:
  - <table_name_or_none>

flow_contracts:
  - <flow_spec_name_or_none>

## **3.2.1 Unified TP Meaning Stream Contract (Updated)**

All primitives must declare their interaction with the **three Path A TP‑stream fields**:

- **semantics/meaning** — dictionary‑anchored identity, lexical roles, semantic interpretation, FFTM structures  
- **processes** — OB/TB/IB updates, ΔH%, completion behavior, messy‑input handling, flow‑contract operations  
- **supervisor** — reference‑object dependencies, field‑reference‑table dependencies, replay scaffolding

Each primitive YAML must specify:

```
tp_stream:
  read:
    - <list of TP-stream fields the primitive may read>
  write:
    - <list of TP-stream fields the primitive may modify>
  commit:
    - <list of TP-stream fields the primitive may finalize>
  invariants:
    - <TP-stream invariants the primitive must enforce>
```

### **Field Ownership Rules (Updated)**

- **InB** may initialize `semantics/meaning` and `processes`, but may not commit any field.  
- **IIInB** may refine `semantics/meaning` but may not commit any field.  
- **IE** may commit `semantics/meaning` and `processes`.  
- **SOB/SROB/SmOB** may refine `processes` but may not commit any field.  
- **IdOB** may commit `supervisor`.  
- **TR** may read all TP-stream fields but may not modify any.  
- **SSR** must read all TP-stream fields and produce the immutable SSR(t) snapshot.  
- **Path B primitives** may read TP-stream fields but may never modify them.

### **Determinism Requirement**

TP-stream evolution must be:

- deterministic  
- replay-equivalent  
- stable under identical routing  
- compliant with single-writer invariants  

### **Commit Boundaries (Updated)**

- **IE** is the commit boundary for `semantics/meaning` and `processes`.  
- **IdOB** is the commit boundary for `supervisor`.  
- **SSR(t)** integrates all three fields into the immutable meaning-layer snapshot.

---

### **3.3 YAML Is Mandatory**
No primitive may hard-code:

- invariants  
- routing transitions  
- anomaly flags  
- envelope geometry  
- dictionary dependencies  

All must be defined in YAML.

## **4. Generic Primitive Code**
### **4.1 Python Layer**
Python primitives are **generic skeletons** that:

- load YAML  
- enforce invariants  
- evaluate envelope geometry  
- detect anomalies  
- compute envelope status  
- route according to YAML  

Python is the **design and validation layer**.

### **4.2 C++ Layer**
C++ primitives are **generic high-performance engines** that:

- load the same YAML  
- enforce the same invariants  
- follow the same routing rules  
- use the same envelope geometry  
- use the same anomaly flags  

C++ is the **execution layer**.

### **4.3 Why Both Layers Are Generic**
Because the YAML defines behavior.  
The code implements the engine.

This separation ensures:

- modularity  
- verifiability  
- determinism  
- future evolution  
- testbench consistency  
- cross-language correctness

## **5.4 TP‑Stream Envelope (Updated)**

The **TP‑stream envelope** is the structured container that holds the **three Path A TP‑stream fields**:

- **semantics/meaning** — dictionary‑anchored identity, lexical roles, semantic interpretation, FFTM structures  
- **processes** — OB/TB/IB updates, ΔH%, completion behavior, messy‑input handling, flow‑contract operations  
- **supervisor** — reference‑object dependencies, field‑reference‑table dependencies, replay scaffolding

## **5.4.1 TP‑Stream Commit Boundaries (Updated)**

Commit boundaries define when each TP‑stream field becomes immutable within a Pipeline A cycle.  
All stabilization occurs inside the unified TP meaning stream, which contains:

- **semantics/meaning**  
- **processes**  
- **supervisor**

### **IE Commit Boundary**

The IE primitive is the deterministic commit boundary for:

- **semantics/meaning**  
- **processes**

IE freezes:

- dictionary‑anchored semantic identity  
- FFTM structures  
- lexical roles  
- semantic interpretation  
- OB/TB/IB process‑layer updates  
- ΔH% accumulation  
- completion signals  
- messy‑input interpretations  

After IE commits these fields:

- they become immutable for the remainder of the cycle  
- no primitive may modify them  
- routing must treat them as stabilized  
- replay equivalence must be preserved

### **IdOB Commit Boundary**

The IdOB primitive is the deterministic commit boundary for:

- **supervisor**

IdOB finalizes:

- reference‑object dependencies  
- field‑reference‑table anchoring  
- replay scaffolding  
- identity‑conditioned coordination metadata  

After IdOB commits the supervisor field:

- it becomes immutable  
- routing may incorporate supervisor metadata  
- replay equivalence must be preserved

### **SSR(t) Commit Boundary**

SSR(t) is the final commit boundary for the TP‑stream envelope.  
SSR(t):

- integrates **semantics/meaning**, **processes**, and **supervisor**  
- produces the immutable meaning‑layer snapshot  
- provides the only legal handoff to Path B  
- guarantees A/B separation  
- ensures replay‑stable realization across Python and C++

No primitive may modify any TP‑stream field after SSR(t).

### **5.4.2 Envelope Separation (Updated)**

- TP‑stream envelopes may be refined only by Path A primitives.  
- Path B primitives may **read** TP‑stream envelopes but may **never modify** them.  
- No primitive may move any TP‑stream field outside the envelope before SSR(t).

### **5.4.3 Deterministic Geometry Requirement (Updated)**

The TP‑stream envelope must:

- remain closed and connected  
- preserve geometry under replay  
- maintain stable meaning‑layer adjacency  
- enforce deterministic evolution of all three TP‑stream fields  
- comply with single‑writer invariants (TPU commit only)

### **5.4.4 Routing Dependency (Updated)**

Routing decisions (RB → identity basin) must use stabilized TP‑stream geometry, including:

- semantic identity cues  
- process‑layer evidence and completion signals  
- supervisor‑layer reference‑object dependencies  

Intent is no longer a Path A field and must not be referenced.

## **7. Routing Contract**
Routing is deterministic and must follow YAML:

### **7.1 Envelope Status**
- `valid_clean`  
- `valid_degraded`  
- `invalid`  

### **7.2 Routing Transitions**
- `valid_clean → PathA.clean`  
- `valid_degraded → PathA.corrected`  
- `invalid → PathB`  

### **7.3 No Hard-Coded Routing**
Routing must be defined in YAML and enforced by both Python and C++.

---

## **7.4 TP‑Stream Routing Dependencies (Updated)**

Routing decisions in Path A must incorporate stabilized geometry and metadata derived from the **three TP‑stream fields**:

- **semantics/meaning** — dictionary‑anchored identity, lexical roles, semantic interpretation, FFTM structures  
- **processes** — OB/TB/IB updates, ΔH%, completion signals, messy‑input interpretations  
- **supervisor** — reference‑object dependencies, field‑reference‑table anchoring, replay scaffolding

These fields guide routing transitions into structural and identity‑conditioned basins.

### **7.4.1 Routing Before Supervisor Finalization**

Before IdOB finalizes the **supervisor** field:

- routing may use stabilized semantics/meaning  
- routing may use stabilized process‑layer signals  
- routing must **not** use supervisor metadata  
- routing must treat supervisor as **unfinalized**  
- routing must remain deterministic under replay  
- routing must not infer coordination metadata prematurely

### **7.4.2 Identity‑Basin Routing**

Routing into identity basins (RB → IdOB) must use:

- stabilized semantic identity  
- lexical roles  
- FFTM structures  
- process‑layer evidence  
- envelope status  

Identity basins may **read** all TP‑stream fields but may **not modify** any field until IdOB commit.

### **7.4.3 Post‑Supervisor Routing**

After IdOB finalizes the **supervisor** field:

- routing may incorporate supervisor metadata  
- routing must treat supervisor as immutable  
- routing must not modify any TP‑stream field  
- routing must preserve replay equivalence

### **7.4.4 Routing Determinism Requirements**

Routing must remain:

- deterministic  
- invariant‑driven  
- replay‑stable  
- identical across Python and C++  
- compliant with commit boundaries  
- compliant with single‑writer invariants  

### **7.4.5 Path B Routing**

Path B primitives:

- may read all TP‑stream fields  
- may not modify any TP‑stream field  
- must treat SSR(t) as immutable  
- must route based solely on envelope status and SSR(t)

## **8.1.1 Semantics/Meaning Dictionary Contract (Updated)**

The **semantics/meaning** field is the dictionary‑anchored representation of lexical identity, semantic roles, FFTM structures, and meaning interpretation.  
All primitives that read or write the **semantics/meaning** field must declare dictionary dependencies explicitly in YAML.

### **Dictionary Requirements for semantics/meaning**

- The **semantics/meaning** field **must** be derived from the meaning dictionary.  
- No primitive may infer lexical identity or semantic roles outside dictionary constraints.  
- All dictionary lookups must be:  
  - deterministic  
  - replay‑stable  
  - identical across Python and C++  
  - validated by testbenches  

### **Semantic Role Alignment**

The meaning dictionary must provide:

- lexical identity  
- dictionary meaning  
- semantic roles  
- FFTM‑compatible role structures  
- frame‑compatible semantic interpretations  

Primitives that refine or interpret the **semantics/meaning** field must use only dictionary‑declared roles and meaning structures.

### **Dictionary Access Rules**

- **IE** must commit the **semantics/meaning** field using dictionary‑backed identity and FFTM structures.  
- **SOB/SROB/SmOB** may read dictionary roles but may not modify the **semantics/meaning** field.  
- **IdOB** may read dictionary roles for identity‑conditioned refinement but may not modify the **semantics/meaning** field.  
- **TR** and **SSR** may read dictionary roles but may not modify any TP‑stream field.  
- **Path B** primitives may read dictionary roles but may never modify TP‑stream fields.

### **Determinism Requirement**

Dictionary interactions must remain:

- explicit  
- auditable  
- invariant‑driven  
- stable under replay  
- identical across Python and C++  

No primitive may implicitly consume dictionary content.

## **10.1 TP‑Stream Determinism Contract (Updated)**

Determinism in TS requires that the **three Path A TP‑stream fields** evolve in a strictly controlled, replay‑stable manner:

- **semantics/meaning** — dictionary‑anchored identity, lexical roles, semantic interpretation, FFTM structures  
- **processes** — OB/TB/IB updates, ΔH%, completion behavior, messy‑input handling, flow‑contract operations  
- **supervisor** — reference‑object dependencies, field‑reference‑table anchoring, replay scaffolding

These fields must follow deterministic rules across Python and C++ execution layers.

### **10.1.1 Deterministic Field Evolution**

All TP‑stream field evolution must be:

- invariant‑driven  
- envelope‑stable  
- replay‑equivalent  
- identical across Python and C++  
- independent of global inference  
- bounded by primitive ownership rules  

No primitive may modify a TP‑stream field it does not explicitly own in YAML.

### **10.1.2 Deterministic Commit Boundaries**

Commit boundaries must remain deterministic:

- **IE Commit Boundary**  
  - deterministically freezes `semantics/meaning` and `processes`  
  - ensures identical replay under identical input and routing  

- **IdOB Commit Boundary**  
  - deterministically finalizes `supervisor`  
  - ensures identity‑conditioned coordination metadata is stable under replay  

- **SSR(t) Commit Boundary**  
  - deterministically integrates all three TP‑stream fields into the immutable meaning‑layer snapshot  
  - ensures deterministic A/B separation  

### **10.1.3 Deterministic Dictionary Anchoring**

The **semantics/meaning** field must be:

- dictionary‑anchored  
- deterministically derived  
- stable under replay  
- identical across Python and C++  

No primitive may infer lexical identity or semantic roles outside dictionary constraints.

### **10.1.4 Deterministic Process‑Layer Evolution**

The **processes** field must evolve deterministically:

- OB/TB/IB updates must be stable  
- ΔH% accumulation must be replay‑equivalent  
- completion signals must be deterministic  
- messy‑input interpretations must not drift across replay  

### **10.1.5 Deterministic Supervisor Evolution**

The **supervisor** field must evolve deterministically:

- reference‑object dependencies must be stable  
- field‑reference‑table anchoring must be replay‑equivalent  
- coordination metadata must not drift across replay  

### **10.1.6 Deterministic Routing**

Routing must use stabilized TP‑stream geometry:

- deterministic semantic identity  
- deterministic process‑layer signals  
- deterministic supervisor metadata  

Routing must not use unfinalized supervisor data before IdOB commit.

### **10.1.7 Deterministic Replay Requirement**

Under identical input and routing:

- all three TP‑stream fields must evolve identically  
- commit boundaries must occur identically  
- SSR(t) must be identical  
- Path B must receive identical TP‑stream envelopes  

Replay equivalence is mandatory.

## **11.1 TP‑Stream Compliance Requirements (Updated)**

All primitives must comply with the **three‑field TP‑stream model**:

- **semantics/meaning** — dictionary‑anchored identity, lexical roles, semantic interpretation, FFTM structures  
- **processes** — OB/TB/IB updates, ΔH%, completion behavior, messy‑input handling, flow‑contract operations  
- **supervisor** — reference‑object dependencies, field‑reference‑table anchoring, replay scaffolding

These fields form the complete meaning representation for Path A and must be handled according to strict ownership and commit rules.

### **11.1.1 TP‑Stream Field Ownership Declaration**

Every primitive YAML must declare:

```
tp_stream:
  read:
  write:
  commit:
  invariants:
```

No primitive may read, write, or commit a TP‑stream field it does not explicitly declare.

### **11.1.2 Commit Boundary Compliance**

Primitives must respect the following commit boundaries:

- **IE** must commit `semantics/meaning` and `processes`.  
- **IdOB** is the *only* primitive allowed to commit `supervisor`.  
- **SSR** must integrate all three TP‑stream fields into SSR(t).  
- No other primitive may finalize any TP‑stream field.

### **11.1.3 TP‑Stream Immutability**

After SSR(t):

- all three TP‑stream fields become immutable  
- Path B primitives may **read** but may **never modify** TP‑stream fields  
- replay equivalence must be preserved

### **11.1.4 Dictionary Compliance for semantics/meaning**

Primitives that read or write the **semantics/meaning** field must:

- declare dictionary dependencies  
- use dictionary‑backed lexical identity  
- use dictionary‑backed semantic roles  
- use dictionary‑backed FFTM structures  
- avoid any inference outside dictionary constraints

### **11.1.5 Process‑Layer Compliance**

Primitives must treat the **processes** field as:

- the sole container for OB/TB/IB updates  
- the sole container for ΔH%  
- the sole container for completion signals  
- the sole container for messy‑input interpretations  
- deterministically updated  
- immutable after IE commit

### **11.1.6 Supervisor Compliance**

Primitives must treat the **supervisor** field as:

- empty before IdOB  
- immutable after IdOB  
- identity‑conditioned  
- deterministically anchored to reference objects and field tables  
- replay‑stable

No primitive except IdOB may assign or modify supervisor metadata.

### **11.1.7 Replay Compliance**

Under identical input and routing:

- TP‑stream field evolution must be identical  
- commit boundaries must occur identically  
- SSR(t) must be identical  
- routing must be identical  
- dictionary lookups must be identical  

Replay equivalence is mandatory.

### **11.1.8 Python/C++ Compliance**

Both Python and C++ implementations must:

- load the same YAML  
- enforce the same TP‑stream ownership rules  
- enforce the same commit boundaries  
- produce identical TP‑stream envelopes  
- produce identical SSR(t) snapshots  

No divergence is permitted.
