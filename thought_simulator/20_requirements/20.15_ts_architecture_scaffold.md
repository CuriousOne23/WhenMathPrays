## **1. Purpose of This Document**
The **TS Architectural Scaffold** defines the *engine-level backbone* that all TS components must inherit.  
It establishes the cross-cutting rules that govern:

- primitive structure  
- YAML specification format  
- Python prototype behavior  
- C++ runtime behavior  
- envelope geometry  
- anomaly detection  
- routing transitions  
- dictionary interactions  
- modularity and determinism  
- testbench alignment  

This document sits between:

- **20.10_ts_architectural_principles.md** (high-level philosophy)  
- **20.12_ts_invariants.md** (system-wide invariants)  
- **20.20_ts_prim_proc_ref_gov.md** (primitive governance)

It provides the **unifying contract** that ensures TS remains modular, verifiable, and realizable in both Python and C++.

## **2. Architectural Positioning**
TS is a **modular cognitive engine** composed of:

- deterministic primitives  
- envelope-based geometry  
- invariant-driven routing  
- dictionary-backed semantics  
- dual execution layers (Python → C++)  
- YAML-defined behavior  

This scaffold defines the *rules that all primitives must follow*, regardless of domain (boundary, structural, semantic, routing, projection, etc.).

## **3. YAML as the Source of Truth**
### **3.1 Why YAML Exists**
All primitives load their behavior from YAML because:

- YAML is machine-readable  
- YAML is versionable  
- YAML is testable  
- YAML is diff-friendly  
- YAML separates *specification* from *implementation*  
- YAML enables hot-swappability  
- YAML enables C++ and Python to share the same contract  

### **3.2 YAML Defines Primitive Behavior**
Every primitive YAML must define:

primitive:
domain:
version:
description:

#### Lifecycle
start_conditions:  
done_conditions:

#### Behavioral Contract
invariants:
geometry:
fields:
refinement_rules:

#### Envelope Evaluation
envelope_status:
anomaly_flags:

#### Routing
routing:

#### External Dependencies (Dictionaries)
dependencies:
  meaning_dictionary: <dictionary_name_or_none>
  runtime_dictionary: <dictionary_name_or_none>
  dev_dictionary: <dictionary_name_or_none>

#### External Dependencies (Reference Artifacts)
reference_objects:
  - <object_name_or_none>

field_reference_tables:
  - <table_name_or_none>

flow_contracts:
  - <flow_spec_name_or_none>

### **3.2.1 Meaning-Layer Field Contract (New)**

All primitives must declare their interaction with the **four Path A meaning-layer fields**:

- **token_surface** — expressive geometry, adjacency, punctuation force  
- **token_base** — lexical identity, dictionary meaning, semantic roles  
- **token_expression** — affective and expressive metadata  
- **token_intent** — pragmatic communicative force  

Each primitive YAML must specify:

```
fields:
  read:
    - <list of fields the primitive may read>
  write:
    - <list of fields the primitive may modify>
  commit:
    - <list of fields the primitive may finalize>
  invariants:
    - <field-specific invariants the primitive must enforce>
```

#### **Field Ownership Rules**
- **InB** may initialize all fields but may not commit intent.  
- **IIInB** may propose expression metadata but may not commit any field.  
- **IE** must commit `token_surface`, `token_base`, and `token_expression`.  
- **SOB/SROB/SmOB** may refine intent precursors but may not commit intent.  
- **IdOB** is the *only* primitive allowed to commit `token_intent`.  
- **TR** may read all fields but may not modify any.  
- **SSR** must read all fields and produce the immutable SSR(t) snapshot.  
- **Path B primitives** may read fields but may never modify them.

#### **Determinism Requirement**
Field evolution must be:

- deterministic  
- replay-equivalent  
- stable under identical routing  
- compliant with single-writer invariants  

#### **Commit Boundaries**
- **IE** is the commit boundary for surface/base/expression.  
- **IdOB** is the commit boundary for intent.  
- **SSR(t)** is the immutable meaning-layer handoff to Path B.

### **3.3 YAML Is Mandatory**
No primitive may hard-code:

- invariants  
- routing transitions  
- anomaly flags  
- envelope geometry  
- dictionary dependencies  

All must be defined in YAML.

## **4. Generic Primitive Code**
### **4.1 Python Layer**
Python primitives are **generic skeletons** that:

- load YAML  
- enforce invariants  
- evaluate envelope geometry  
- detect anomalies  
- compute envelope status  
- route according to YAML  

Python is the **design and validation layer**.

### **4.2 C++ Layer**
C++ primitives are **generic high-performance engines** that:

- load the same YAML  
- enforce the same invariants  
- follow the same routing rules  
- use the same envelope geometry  
- use the same anomaly flags  

C++ is the **execution layer**.

### **4.3 Why Both Layers Are Generic**
Because the YAML defines behavior.  
The code implements the engine.

This separation ensures:

- modularity  
- verifiability  
- determinism  
- future evolution  
- testbench consistency  
- cross-language correctness

## **5. Envelope Geometry Contract**
All primitives must respect the envelope geometry rules:

### **5.1 Envelope Types**
- minimal  
- convex  
- weakly concave  

### **5.2 Envelope Invariants**
- envelope must be closed  
- envelope must be connected  
- envelope must be stable under replay  
- segmentation rules must be respected  

### **5.3 Envelope Refinement**
Only allowed refiners may modify envelope geometry.  
Refinement must preserve closure and connectedness.

## **5.4 Meaning-Layer Envelope (New)**

The **meaning-layer envelope** is the structured container that holds the four Path A token fields:

- **token_surface**  
- **token_base**  
- **token_expression**  
- **token_intent**

These fields form the complete meaning representation for each token and must remain inside the meaning-layer envelope until SSR(t) construction.

### **5.4.1 Field Stabilization Boundaries**
Meaning-layer field stabilization occurs at strict commit boundaries:

- **IE Commit Boundary**  
  - Freezes: `token_surface`, `token_base`, `token_expression`  
  - Ensures deterministic geometry, lexical identity, and expressive metadata  
  - No semantic inference or intent assignment permitted

- **IdOB Commit Boundary**  
  - Finalizes: `token_intent`  
  - Identity-basin authority required  
  - Ensures pragmatic force is assigned deterministically and replay-equivalently

- **SSR(t) Commit Boundary**  
  - Integrates all four fields into the immutable meaning-layer snapshot  
  - Provides the only legal handoff to Path B  
  - Guarantees A/B separation and replay-stable realization

### **5.4.2 Envelope Separation**
- Meaning-layer envelopes may be refined only by Path A primitives.  
- Path B primitives may **read** meaning-layer envelopes but may **never modify** them.  
- No primitive may move a field outside the meaning-layer envelope before SSR(t).

### **5.4.3 Deterministic Geometry Requirement**
The meaning-layer envelope must:

- remain closed and connected  
- preserve geometry under replay  
- maintain stable adjacency and punctuation force  
- enforce deterministic evolution of all four fields  
- comply with single-writer invariants (TPU commit only)

### **5.4.4 Routing Dependency**
Routing decisions (RB → identity basin) must use stabilized meaning-layer envelope geometry, including:

- token_surface structural cues  
- token_base lexical roles  
- token_expression expressive metadata  

token_intent must remain empty until IdOB finalization.

## **7. Routing Contract**
Routing is deterministic and must follow YAML:

### **7.1 Envelope Status**
- `valid_clean`  
- `valid_degraded`  
- `invalid`  

### **7.2 Routing Transitions**
- `valid_clean → PathA.clean`  
- `valid_degraded → PathA.corrected`  
- `invalid → PathB`  

### **7.3 No Hard-Coded Routing**
Routing must be defined in YAML and enforced by both Python and C++.

---

## **7.4 Meaning-Layer Routing Dependencies (New)**

Routing decisions in Path A must incorporate stabilized meaning-layer geometry derived from the four token fields:

- **token_surface** — adjacency, punctuation force, expressive geometry  
- **token_base** — lexical identity, semantic roles  
- **token_expression** — intensity, elongation, expressive metadata  

These fields guide routing transitions into structural and identity-conditioned basins.

### **7.4.1 Routing Before Intent Finalization**
Before IdOB finalizes `token_intent`:

- routing may use surface, base, and expression  
- routing must **not** use intent  
- routing must treat intent as **empty**  
- routing must remain deterministic under replay  
- routing must not infer pragmatic force prematurely

### **7.4.2 Identity-Basin Routing**
Routing into identity basins (RB → IdOB) must use:

- stabilized surface geometry  
- lexical roles  
- expressive metadata  
- envelope status  

Identity basins may **read** all fields but may **not modify** any field until IdOB commit.

### **7.4.3 Post-Intent Routing**
After IdOB finalizes `token_intent`:

- routing may incorporate intent  
- routing must treat intent as immutable  
- routing must not modify any meaning-layer field  
- routing must preserve replay equivalence

### **7.4.4 Routing Determinism Requirements**
Routing must remain:

- deterministic  
- invariant-driven  
- replay-stable  
- identical across Python and C++  
- compliant with commit boundaries  
- compliant with single-writer invariants  

### **7.4.5 Path B Routing**
Path B primitives:

- may read all four fields  
- may not modify any field  
- must treat SSR(t) as immutable  
- must route based solely on envelope status and SSR(t)

## **8. Reference Artifact Dependency Contract**

Primitives may depend on four classes of external reference artifacts:

### **8.1 Dictionaries**
- meaning dictionary  
- runtime dictionary  
- dev dictionary  

All dictionary usage must be explicitly declared in YAML:

```
dependencies:
  meaning_dictionary: <dictionary_name_or_none>
  runtime_dictionary: <dictionary_name_or_none>
  dev_dictionary: <dictionary_name_or_none>
```

No primitive may implicitly read from any dictionary.

---

## **8.1.1 Token Base Dictionary Contract (New)**

The **token_base** field is the dictionary‑anchored representation of lexical identity and semantic roles.  
All primitives that read or write `token_base` must declare dictionary dependencies explicitly in YAML.

### **Dictionary Requirements for token_base**
- `token_base` **must** be derived from the meaning dictionary.  
- No primitive may infer lexical identity outside dictionary constraints.  
- All dictionary lookups must be:
  - deterministic  
  - replay‑stable  
  - identical across Python and C++  
  - validated by testbenches  

### **Semantic Role Alignment**
The meaning dictionary must provide:

- lexical identity  
- dictionary meaning  
- semantic roles  
- frame‑compatible role structures  

Primitives that refine or interpret `token_base` must use only these dictionary‑declared roles.

### **Dictionary Access Rules**
- **IE** must commit `token_base` using dictionary-backed identity.  
- **SOB/SROB/SmOB** may read dictionary roles but may not modify `token_base`.  
- **IdOB** may read dictionary roles for identity‑conditioned refinement but may not modify `token_base`.  
- **TR** and **SSR** may read dictionary roles but may not modify any meaning-layer field.  
- **Path B** primitives may read dictionary roles but may never modify meaning-layer fields.

### **Determinism Requirement**
Dictionary interactions must remain:

- explicit  
- auditable  
- invariant-driven  
- stable under replay  
- identical across Python and C++  

No primitive may implicitly consume dictionary content.

## **10.1 Meaning-Layer Determinism Contract (New)**

Determinism in TS requires that the **four Path A meaning-layer fields** evolve in a strictly controlled, replay-stable manner:

- **token_surface**  
- **token_base**  
- **token_expression**  
- **token_intent**

These fields must follow deterministic rules across Python and C++ execution layers.

### **10.1.1 Deterministic Field Evolution**
All field evolution must be:

- invariant-driven  
- envelope-stable  
- replay-equivalent  
- identical across Python and C++  
- independent of global inference  
- bounded by primitive ownership rules  

No primitive may modify a field it does not explicitly own in YAML.

### **10.1.2 Deterministic Commit Boundaries**
Commit boundaries must remain deterministic:

- **IE Commit Boundary**  
  - deterministically freezes `token_surface`, `token_base`, `token_expression`  
  - ensures identical replay under identical input and routing  

- **IdOB Commit Boundary**  
  - deterministically finalizes `token_intent`  
  - ensures identity-conditioned pragmatic force is stable under replay  

- **SSR(t) Commit Boundary**  
  - deterministically integrates all four fields into the immutable meaning-layer snapshot  
  - ensures deterministic A/B separation  

### **10.1.3 Deterministic Dictionary Anchoring**
`token_base` must be:

- dictionary-anchored  
- deterministically derived  
- stable under replay  
- identical across Python and C++  

No primitive may infer lexical identity outside dictionary constraints.

### **10.1.4 Deterministic Expressive Metadata**
`token_expression` must evolve deterministically:

- expressive cues (elongation, intensity, repetition) must be stable  
- punctuation patterns must be preserved  
- expressive metadata must not drift across replay  

### **10.1.5 Deterministic Routing**
Routing must use stabilized meaning-layer geometry:

- deterministic surface cues  
- deterministic lexical roles  
- deterministic expressive metadata  

Routing must not use intent until IdOB finalization.

### **10.1.6 Deterministic Replay Requirement**
Under identical input and routing:

- all four fields must evolve identically  
- commit boundaries must occur identically  
- SSR(t) must be identical  
- Path B must receive identical meaning-layer envelopes  

Replay equivalence is mandatory.
