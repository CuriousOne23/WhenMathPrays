# 20.115 MTP Requirements

**Document ID:** 20.115  
**Version:** 0.3  
**Date:** 2026-06-16  
**Status:** Updated — Multi‑core Path A revision (HLR‑001–007)

## Purpose

Defines deterministic **Master Thought Packet (MTP)** structure, lifecycle, aggregation, **`mtp_update` / `commit_id` commit semantics**, and audit invariants for **global Pipeline A meaning authority** — including MTP's role as the sole publisher of frozen `semantic_core` snapshots consumed by Pipeline B.

MTP is the **global integrator**: lane TPs merge into MTP; Truth/Done evaluates on merged meaning; **`mtp_update`** commits authoritative `semantic_core` and emits **`commit_id`** for XP / Pipeline B (20.206, 20.205).

## 1. Dual-Pipeline Boundary

| Store | Authority |
|-------|-----------|
| **MTP / `semantic_core`** | Global authoritative meaning after Merge + Truth/Done + `mtp_update` |
| **TP** | Lane-local projection only; merges into MTP |
| **XP / `exec_plan` / `exec_trace`** | Pipeline B only; **SHALL NOT be stored on MTP** as authoritative fields |

27. **HLR-20.115-027:** MTP SHALL host the authoritative `semantic_core` meaning envelope for the active conversation horizon; Pipeline A modules SHALL treat committed MTP / `semantic_core` as the global truth store after `mtp_update`.
28. **HLR-20.115-028:** MTP SHALL NOT carry authoritative `exec_plan`, `exec_trace`, `xp_id`, `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, or IMR records as MTP core fields (20.31-013, 20.105-032).
29. **HLR-20.115-029:** Pipeline B SHALL consume MTP meaning only through post-`mtp_update` `commit_id` / `semantic_snapshot_ref` (20.206); MTP SHALL NOT expose TP instances or `lane_id` as B routing inputs.
30. **HLR-20.115-030:** Pipeline B SHALL NOT write MTP or `semantic_core` fields; IMR Type B corrections SHALL update MTP only through a **subsequent** Pipeline A cycle (20.45, 20.206 E3).

**Pipeline B forbidden:** retroactive mutation of merged MTP fields, truth/done results, or messy-input meaning after `mtp_update` for a given `commit_id`.

## 2. Pipeline Placement

Within Pipeline A, per `cycle_id`:

```text
… → Merge (lane TPs → MTP draft) → ΔH% → Truth/Done → mtp_update
                                                      │
                                              commit_id + frozen semantic_core
                                                      │
                                              Pipeline B may start (20.206)
```

31. **HLR-20.115-031:** Merge SHALL integrate lane TP contributions into MTP before Truth/Done evaluation for the cycle (20.130, 20.140).
32. **HLR-20.115-032:** `mtp_update` SHALL occur only after Truth/Done completes (or deterministic skip policy records explicit reason code when Truth/Done is bypassed by GB policy).
33. **HLR-20.115-033:** `mtp_update` SHALL be the **only** normative commit point that publishes a new frozen `semantic_core` snapshot for Pipeline B realization in that cycle.

---

## 3. `mtp_update` and `commit_id`

`mtp_update` commits authoritative meaning and publishes the B-side input handle.

| Event | Effect |
|-------|--------|
| `mtp_update` | Commits `semantic_core`; emits `commit_id`; appends audit |
| `commit_id` | Stable ID for frozen snapshot; binds XP and exec envelopes |

34. **HLR-20.115-034:** Every successful `mtp_update` SHALL emit exactly one new `commit_id` identifying the committed `semantic_core` snapshot (20.206 HLR-20.206-004).
35. **HLR-20.115-035:** `commit_id` SHALL remain immutable for the referenced snapshot; later `mtp_update` events SHALL emit distinct `commit_id` values.
36. **HLR-20.115-036:** MTP SHALL publish an `mtp_commit_record` (minimum schema per 20.206 §2.1) at each `mtp_update`, including `commit_id`, `cycle_id`, `mtp_id`, `semantic_snapshot_ref`, `policy_signature`, and `execution_signature`.
37. **HLR-20.115-037:** `semantic_snapshot_ref` SHALL reference the committed `semantic_core` bytes or deterministic content hash at `mtp_update` time.
38. **HLR-20.115-038:** Legacy exports using `mtp_snapshot_id` SHALL treat it as a **deprecated alias** for `commit_id` until Stage 4 per-doc renames complete (20.500 §5).

### 3.1 `commit_id` derivation (draft)

39. **HLR-20.115-039:** `commit_id` SHALL be derived deterministically from `(mtp_id, cycle_id, semantic_core_content_hash, policy_signature, execution_signature)` using a fixed, documented hash function (detail in 20.39 / 20.95 — open for review).

# **4. Aggregation, Merge, and Split (Revised for Multi‑Core Orthogonal Path A)**

Below is the **only section modified**.

### **Updated HLRs 001–007**

1. **HLR‑20.115‑001 — UPDATED**  
   MTP SHALL represent the canonical aggregated state derived from deterministic TP contributions, including **multiple independent Path A results when multi‑core execution is active**.

2. **HLR‑20.115‑002 — UPDATED**  
   Every MTP SHALL include stable identity fields including `mtp_id`, lineage identifiers, and merge/split provenance markers.  
   When multi‑core execution is used, provenance SHALL record each core’s OB identity and orthogonality guarantee.

3. **HLR‑20.115‑003 — UPDATED**  
   MTP identity fields SHALL remain immutable after creation, except deterministic append‑only lineage extension markers.  
   Multi‑core Path A execution SHALL NOT create additional MTP identities; all cores feed a single MTP instance.

4. **HLR‑20.115‑004 — UPDATED**  
   MTP core fields SHALL include aggregated TP evidence, delta‑H‑percent trajectory fields, and bounded stability metrics.  
   When multiple cores are used, aggregation SHALL treat each core’s Path A as a **complete, independent artifact**.

5. **HLR‑20.115‑005 — UPDATED**  
   MTP aggregation behavior SHALL be deterministic for identical TP inputs, profile state, and signature‑bound policies.  
   Aggregation of multi‑core Path A results SHALL use a deterministic operator (e.g., voting, scoring, meta‑analysis) defined in system policy.

6. **HLR‑20.115‑006 — UPDATED**  
   MTP merge behavior SHALL preserve deterministic parent lineage and deterministic field‑wise aggregation semantics.  
   Merge SHALL NOT combine partial fragments of a single Path A; only whole Path A artifacts from each core may be merged.

7. **HLR‑20.115‑007 — NA**  
   *Original split behavior requirement no longer applies.*  
   **Reason:** MTP no longer supports split semantics except for multi‑core independent Path A execution, which is not a “split” of a single MTP.  
   **Status:** NA (superseded by multi‑core orthogonal Path A model).

---

### **New Sub‑Requirements (under HLR‑20.115‑006)**

These do not consume new HLR numbers.

**HLR‑20.115‑006.A**  
When multiple cores are available, the system MAY execute multiple Path A instances in parallel only if each core is bound to a distinct, orthogonal Observation Basis (OB).

**HLR‑20.115‑006.B**  
OBs assigned to different cores SHALL be information‑orthogonal, meaning their probes, features, or perspectives SHALL NOT overlap except where explicitly permitted by policy.

**HLR‑20.115‑006.C**  
Multi‑core execution SHALL NOT be treated as a “split” of a single Path A; each core produces a complete Path A artifact.

**HLR‑20.115‑006.D**  
MTP SHALL assemble multi‑core Path A results using a deterministic aggregation operator defined in system policy, and SHALL preserve traceability to each core’s OB and Path A artifact.

## 5. Supervisory Integration

8. **HLR-20.115-008:** MTP supervisory fields SHALL include GB interaction markers, safe-boundary integration markers, and supervisory reason-code evidence.
9. **HLR-20.115-009:** MTP supervisory updates SHALL occur only through approved deterministic TS→GB→TS supervisory pathways.
10. **HLR-20.115-010:** MTP audit behavior SHALL be append-only and SHALL record merge, split, update, approval, denial, and retirement events.
11. **HLR-20.115-011:** MTP audit records SHALL include deterministic reason codes and deterministic profile-signature references for supervisory actions.
12. **HLR-20.115-012:** MTP reason-code dictionaries SHALL use immutable identifiers with deterministic versioned mapping behavior.

**`mtp_update` audit extension:** every `mtp_update` audit entry SHALL include `commit_id`, `cycle_id`, `commit_reason_codes[]`, and `semantic_snapshot_ref`.

## 6. Lifecycle, Schema, and Bounds (Retained Core)

13. **HLR-20.115-013:** MTP creation SHALL initialize all required identity, core, supervisory, and audit fields with deterministic defaults.
14. **HLR-20.115-014:** MTP field updates (pre-commit) SHALL occur only at deterministic safe boundaries when update policy requires boundary-gated activation.
15. **HLR-20.115-015:** MTP SHALL reject unsupported schema, enum, profile, or wire-map states with deterministic reject-with-audit behavior.
16. **HLR-20.115-016:** MTP SHALL preserve deterministic behavior across compatible profile-version windows and deterministically reject out-of-window states.
17. **HLR-20.115-017:** MTP timestamps SHALL be treated as evidence metadata only; authoritative ordering SHALL derive from deterministic sequence tokens.
18. **HLR-20.115-018:** MTP SHALL maintain bounded retention, bounded replay-horizon behavior, and deterministic compaction policy semantics.
19. **HLR-20.115-019:** MTP update, merge, and split operations SHALL NOT require unbounded scanning, inference, or additional unscheduled TS cycles.
20. **HLR-20.115-020:** MTP retirement SHALL preserve deterministic replayability through retained lineage and summary-proof evidence according to active policy.
21. **HLR-20.115-021:** MTP export and manifest serialization SHALL use deterministic key ordering and canonical serialization.
22. **HLR-20.115-022:** MTP zero-event windows SHALL follow deterministic empty-artifact semantics with canonical empty evidence or fixed no-artifact reason code.
23. **HLR-20.115-023:** MTP lifecycle transitions (creation, update, merge, split, retirement, **`mtp_update`**) SHALL be logged with deterministic when/why/how context.
24. **HLR-20.115-024:** MTP processing SHALL remain platform-independent deterministic under equivalent input, profile, and signature state.
25. **HLR-20.115-025:** MTP requirements in this module SHALL satisfy and SHALL NOT weaken parent invariants defined by 20.10, 20.30, and 20.12.
26. **HLR-20.115-026:** MTP invariants SHALL preserve determinism, boundedness, reproducibility, and auditability for all supported runtime profiles.

## 7. Functional Boundaries

| Owner | Responsibility |
|-------|----------------|
| **MTP** | Aggregated TP-derived `semantic_core`; global stability trajectory; `mtp_update` / `commit_id` publication |
| **TP** | Lane-local identity and per-step evidence; not B input |
| **Truth/Done** | Evaluates merged meaning; writes into pre-commit MTP draft |
| **XP** | Indexes B artifacts for a `commit_id`; not stored on MTP |
| **GB** | Flow-control and supervisory markers at safe boundaries only |

GB supervisory influence on MTP SHALL be flow-control-only and SHALL NOT violate deterministic safe-boundary constraints.

---

## 8. Verification Focus

- Deterministic merge → Truth/Done → `mtp_update` → `commit_id` emission
- One `commit_id` per `mtp_update`; immutability of committed snapshot
- B start blocked without post-`mtp_update` `commit_id` (20.206)
- No `exec_plan` / `exec_trace` / `xp_id` on MTP core
- Strip replay: committed `semantic_core` unchanged by Pipeline B (E1)
- Deterministic aggregation, merge, split under equivalent TP input (retained)
- `mtp_commit_record` present in golden fixtures with `commit_id` (not legacy alias only)
