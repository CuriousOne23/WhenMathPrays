# 20.34 COP Requirements

**Document ID:** 20.34  
**Version:** 0.3  
**Date:** 2026-06-06  
**Status:** CP-approved — dual-pipeline COP specification (v0.2 CP refinements applied)

## Purpose

Defines deterministic constraints for the optional **Conversation Coprocessor (COP)** — an asynchronous, **propose-only** subsystem supporting CIL/COB supervisory workflows and IB lifecycle **control proposals** under GB governance.

COP prepares bounded, provenance-rich proposals; **GB alone** approves or denies effective transitions at deterministic safe boundaries. COP SHALL NOT perform meaning construction or mutate dual-pipeline authoritative envelopes.

This module SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

## Parent Scope

- **Role:** control/lifecycle proposal authority — semantic meaning defers to [20.31](20.31_semantic_specification.md)
- **Governance:** GB caps/rates in [20.16](20.16_gb_responsibility_matrix.md), [20.80](20.80_gb_requirements.md); numeric defaults in [20.90](20.90_ts_parameter_table.md)
- **Decomposition:** normatively decomposes COP obligations from 20.10 §1.12 and 20.30 §1.9 (HLR-20.030-295–303)
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Non-Goals

- IB field semantics (20.31)
- GB scoring, heuristic weighting, or internal evaluation algorithms (20.80 boundary-only)
- Pipeline B realization, IMR correction scheduling, OuB expression
- Operational algorithms (20.35)

## Authority and Precedence

| Layer | Authority |
|-------|-----------|

## 1. Dual-Pipeline Boundary Discipline

COP sits **outside** Pipeline A meaning construction and Pipeline B realization. It operates on approved **canonicalized snapshot views** and emits **proposal records** consumed by GB.

### 1.1 Forbidden envelope access

COP SHALL NOT read or mutate basin internal implementation state (OB, RB, TB, IB, InB, OuB, CIL, COB, MTP internals beyond approved interfaces) — HLR-20.033-017.

Additionally under dual-pipeline hardening:

| Envelope / field | COP posture |
|----------------|-------------|
| `semantic_core` | Read-only canonicalized export views only; **no write** |
| `exec_plan`, `exec_trace` | **No read for proposal derivation; no write** |
| `supervisory` | **No write**; proposals enter GB intake only |
| `messy_input_record` | Read-only context; **no resolve/smooth/clear** |
| `thought_router_fields`, `TP.TR` | **No read for routing derivation; no write** |
| `truth_hypotheses` | **No read** (truth evaluation is downstream; 20.140) |
| `routing_epoch_id` | **No read/write; no advance** |

### 1.2 Propose-only contract

```
COP ──(cop_proposal)──► GB pending buffer ──(approve/deny)──► safe-boundary commit
                              │
                              └── cap/rate bounded (20.16, 20.80, 20.90)
```

- COP-visible outcomes become system-visible **only** through GB-approved supervisory actions at safe boundaries (HLR-20.033-003, HLR-20.033-009, HLR-20.030-301).
- Denied or expired proposals SHALL leave all authoritative envelopes unchanged.

## 2. COP Proposal Schema (minimum)

```text
cop_proposal {
  proposal_id,              // stable UUID or deterministic hash id
  proposal_class,           // IB_CREATE | IB_PROMOTE | IB_RETIRE | IB_SPLIT | IB_MERGE | COB_STAGE | CIL_ADVISORY
  conversation_id,
  cycle_id,
  mtp_snapshot_id,          // basis snapshot pin
  input_hash,               // deterministic preimage per 20.95
  policy_signature,
  execution_signature,
  target_ib_id?,            // when applicable
  criteria_fields{},        // safe-boundary evaluable; no latent scores
  provenance{
    source,                 // COP worker id / coprocessor path
    basis_snapshot_ref,
    enqueue_seq             // deterministic ordering token
  },
  proposal_status,          // QUEUED | SCHEDULED | COMMIT_ELIGIBLE | VISIBLE | REJECTED | EXPIRED
  reason_code?              // on reject/expiry
}
```

**Canonical ordering:** proposal export, hash, and replay diff SHALL sort top-level fields lexicographically; nested maps and ID arrays per 20.95/20.39 rules (HLR-20.033-041).

**`criteria_fields{}` ordering (HLR-20.033-050):** Nested criteria keys SHALL sort lexicographically; array values (`evidence_refs[]`, `metric_ids[]`, etc.) SHALL sort by stable ID; numeric criterion values SHALL be canonical Q32.32 before tie-break comparison.

## 3. GB and IB Control Integration

### 3.1 Pending inquiry buffer

IB instantiation and inquiry-related COP proposals SHALL enter the GB **pending inquiry buffer**, bounded by:

| Parameter | Default | Source |
|-----------|--------:|--------|
| `gb.cap.pending_ib_requests` | 16 | 20.90 §E (`CAP_GB_PENDING_IB`) |

When the buffer is full, COP SHALL apply deterministic admission policy (HLR-20.033-026, HLR-20.033-048):

1. Reject new proposal with `COP_PENDING_IB_FULL` / `GB_CAP_PENDING_IB_FULL` audit pairing, **or**
2. Evict lowest-priority queued proposal per fixed FIFO + priority tie-break — never silent drop.

GB IB approve/deny decisions remain subject to `gb.cap.ib_decisions_per_cycle` and sub-caps (20.16).

### 3.2 GB boundary-only evaluation

This document specifies **required inputs, required outputs, and allowed transition classes** for GB evaluation of COP proposals (HLR-20.033-027). It SHALL NOT define GB scoring logic (HLR-20.033-028).

COP `criteria_fields` SHALL be explicit, deterministic, and safe-boundary evaluable (HLR-20.033-025, HLR-20.033-047) — e.g., stability flags, ΔH% band markers, usage counters, conflict rates — without embedding heuristic weights.

### 3.3 IB lifecycle transitions (control classes)

Under COP/GB governance, IB control transitions SHALL include (HLR-20.033-029):

`create`, `evolve`, `split`, `merge`, `promotion_request`, `promotion_approval`, `retirement_request`, `retirement_approval`

Split/merge SHALL be safe-boundary applied with deterministic provenance references (HLR-20.033-030). Promotion/retirement SHALL require explicit GB supervisory decision records and fixed reason codes (HLR-20.033-031). COP/IB boundaries SHALL prohibit direct mutation of IB **semantic** fields outside approved pathways (HLR-20.033-032).

## 4. Queue, Fairness, and Offload

| Concern | Rule | 20.90 default |
|---------|------|---------------|
| Async proposal queue | Bounded, deterministic admission | `offload.queue_depth.max` = 128 |
| Coprocessor path | Symmetric CPU/offload equivalence | `offload.request.*`, `offload.timeout.hard` |
| Ordering | `enqueue_seq` / deterministic token — not wall-clock | HLR-20.033-011 |
| Fairness / overload | execution-signature-bound policy | HLR-20.033-005, -007, -019 |

COP queue admission, scheduling, and fairness SHALL remain deterministic under equivalent input/signature state (HLR-20.033-018). Safety-critical proposals SHALL receive deterministic bounded-latency guarantees (HLR-20.033-006).

## 5. COP Suitability Profile

**Appropriate** (HLR-20.030-302):

- Bounded, queueable proposal preparation
- Deterministic metadata transformation and commit staging
- Provenance-rich advisory analysis with replayable outputs
- Safe to reject, defer, or preempt without corrupting authoritative state

**Not appropriate** (HLR-20.030-303):

- Authoritative meaning construction or Pipeline A basin logic
- Pipeline B realization, IMR scheduling, OuB expression
- Direct mutation of CIL, COB, TS-core, or envelope state
- Unbounded search, wall-clock precedence, hidden mutable state
- Messy-input resolution, contradiction collapse, or slot fill (20.17)

---

## 6. Replay and Determinism

- Proposal lifecycle events (create, queue, schedule, commit-eligible, visible, reject, expire) SHALL append deterministic audit records (HLR-20.033-020).
- COP behavior SHALL be replayable under `(policy_signature, execution_signature)` (HLR-20.033-010).
- Proposal content SHALL be reproducible from `(proposal_inputs, policy_signature, execution_signature)`; **seed SHALL NOT influence** proposal bytes (HLR-20.033-044).
- Proposal derivation SHALL NOT depend on TP creation order, heap allocation order, or container address identity — only `enqueue_seq` and explicit canonical snapshot fields (HLR-20.033-051).
- Strip replay: removing unstaged or **denied** `cop_proposal` artifacts SHALL leave `semantic_core` identical for Pipeline A-only equivalence (20.36 Class 1, HLR-20.033-045).
- Approved transitions already committed in Pipeline A SHALL retain `correction_trigger_id` / GB decision provenance per 20.45 where applicable.

## Worked Example — IB Promotion Proposal

| Step | Actor | Outcome |
|------|-------|---------|
| 1 | COP | Reads canonicalized `semantic_core` export (read-only); prepares `IB_PROMOTE` proposal with `criteria_fields` |
| 2 | COP | Enqueues `cop_proposal`; `proposal_status = QUEUED`; `enqueue_seq` assigned |
| 3 | GB | Admits to pending buffer if `< gb.cap.pending_ib_requests` (16) |
| 4 | GB | Evaluates at safe boundary; issues approve within `gb.cap.ib_approvals_per_cycle` (4) |
| 5 | Pipeline A | IB promotion transition applied; semantic update per 20.31 — **not** by COP directly |
| 6 | Deny path | If GB denies → `proposal_status = REJECTED`; `semantic_core` unchanged |
| 7 | Replay | Identical proposal bytes, queue ordering, and GB cap accounting |

## Normative Requirements

1. HLR-20.033-001: Coprocessor operation SHALL remain propose-only relative to TS core semantics.
2. HLR-20.033-002: Coprocessor proposals SHALL include deterministic provenance metadata (source, basis snapshot, deterministic input hash).
3. HLR-20.033-003: Coprocessor effects SHALL become visible only at deterministic safe-boundary commits.
4. HLR-20.033-004: Coprocessor queue behavior SHALL be bounded and deterministic.
5. HLR-20.033-005: Fairness policy and overload policy SHALL be execution-signature-bound.
6. HLR-20.033-006: Safety-critical proposals SHALL receive deterministic bounded-latency guarantees.
7. HLR-20.033-007: Overload handling SHALL follow deterministic policy (quota, preemption, or reject-with-audit).
8. HLR-20.033-008: Unsupported coprocessor policy states SHALL reject deterministically with fixed audit reason codes.
9. HLR-20.033-009: Coprocessor behavior SHALL NOT mutate authoritative decision state outside GB/TS policy-approved boundaries.
10. HLR-20.033-010: Coprocessor behavior SHALL be replayable and auditable under deterministic execution signature state.
11. HLR-20.033-011: COP ordering-critical behavior SHALL derive from deterministic sequence/token state and SHALL NOT depend on wall-clock precedence.
12. HLR-20.033-012: COP commit visibility SHALL occur only at deterministic safe boundaries and SHALL NOT interleave with active TS-core decision cycles.
13. HLR-20.033-013: COP profile/policy overlaps SHALL resolve by execution-signature-bound profile precedence over environment defaults.
14. HLR-20.033-014: On profile/policy activation validation failure, COP SHALL retain prior valid signature-bound behavior deterministically and emit fixed audit reason codes.
15. HLR-20.033-015: COP enum, wire-map, and schema versions SHALL remain frozen per release and SHALL reject unsupported states with deterministic audit reason codes.
16. HLR-20.033-016: COP reason-code dictionaries SHALL use immutable identifiers, deterministic deprecation rules, and versioned deterministic mapping behavior.
17. HLR-20.033-017: COP SHALL NOT read or mutate OB, RB, TB, IB, InB, OuB, CIL, COB, or MTP internal implementation state and SHALL operate only on approved proposal interfaces and canonicalized metadata views.
18. HLR-20.033-018: COP queue admission, scheduling, and fairness behavior SHALL remain deterministic under equivalent input/signature state.
19. HLR-20.033-019: COP overload behavior SHALL be bounded and deterministic, including deterministic quota/preemption/reject outcomes and deterministic audit logging.
20. HLR-20.033-020: COP proposal lifecycle events, including proposal creation, queueing, scheduling, commit-eligible status, commit visibility, reject, and expiry, SHALL be logged in deterministic append-only audit records.
21. HLR-20.033-021: COP concurrent non-ordering side effects SHALL remain isolated from authoritative decision state and SHALL NOT influence signature-visible artifacts.
22. HLR-20.033-022: COP external interfaces SHALL be explicit, versioned, deterministic, and auditable across supported compatibility windows.
23. HLR-20.033-023: COP requirements in this module SHALL satisfy and SHALL NOT weaken parent invariants defined by 20.10 and 20.30.
24. HLR-20.033-024: COP behavior SHALL remain fully testable via deterministic proposal fixtures, deterministic queue/scheduling fixtures, deterministic overload fixtures, and reproducible profile-bound test-oracle behavior.
25. HLR-20.033-025: IB proposal criteria visible to COP/GB control paths SHALL be explicit, deterministic, and safe-boundary evaluable.
26. HLR-20.033-026: Pending inquiry buffer admission and eviction rules SHALL be deterministic, bounded, and auditable.
27. HLR-20.033-027: GB evaluation obligations in this document SHALL be boundary-only, specifying required inputs, required outputs, and allowed transition classes.
28. HLR-20.033-028: This document SHALL NOT define GB scoring logic, heuristic weighting, or algorithmic decision procedures.
29. HLR-20.033-029: IB lifecycle transitions under COP/GB governance SHALL include create, evolve, split, merge, promotion request, promotion approval, retirement request, and retirement approval states.
30. HLR-20.033-030: IB split and merge control transitions SHALL be safe-boundary applied and SHALL preserve deterministic provenance references.
31. HLR-20.033-031: IB promotion and retirement transitions SHALL require explicit GB supervisory decision records and deterministic reason codes.
32. HLR-20.033-032: COP/IB control boundaries SHALL prohibit direct mutation of IB semantic fields outside approved deterministic transition pathways.
33. HLR-20.033-033: COP/IB control-layer documentation SHALL reference 20.31 for semantics and SHALL NOT redefine semantic meaning in this document.
34. HLR-20.033-034: COP/IB transition records SHALL be append-only, deterministic, and replay-consistent under identical execution signatures.
35. HLR-20.033-035: If any conflict is found between this document and 20.31 semantic definitions, 20.31 SHALL take precedence.
36. HLR-20.033-036: Operational realization detail for COP/IB transition execution SHALL be specified in 20.35 and verified in 30-series verification documents.
37. HLR-20.033-037: COP SHALL NOT write `semantic_core`, `exec_plan`, `exec_trace`, or `supervisory`; read access SHALL be limited to approved canonicalized snapshot views (HLR-20.012-001).
38. HLR-20.033-038: COP SHALL NOT advance `routing_epoch_id`, mutate messy-input tags, or write `thought_router_fields` / `TP.TR` (20.17, 20.37, 20.90 `gb.policy.routing_epoch_advance_per_cycle`).
39. HLR-20.033-039: COP proposals affecting IB instantiation or inquiry admission SHALL respect `gb.cap.pending_ib_requests` (default 16, 20.90) and GB IB decision caps (20.16).
40. HLR-20.033-040: COP SHALL derive proposals only from explicit canonicalized inputs (`mtp_snapshot_id`, permitted export fields, `policy_signature`, `execution_signature`) — never from basin internal mutable state.
41. HLR-20.033-041: `cop_proposal` serialization SHALL use deterministic canonical field ordering per 20.95 before hash, commit eligibility, and replay diff.
42. HLR-20.033-042: Materialized COP effects SHALL occur only as GB-approved supervisory outcomes at safe boundaries; rejected or expired proposals SHALL leave authoritative envelopes unchanged.
43. HLR-20.033-043: COP async queue depth on coprocessor offload paths SHALL respect `offload.queue_depth.max` (default 128, 20.90); CPU fallback SHALL produce ordering-equivalent proposal sequences.
44. HLR-20.033-044: COP proposal bytes SHALL be reproducible from `(proposal_inputs, policy_signature, execution_signature)`; seed SHALL NOT influence proposal content (HLR-20.012-010).
45. HLR-20.033-045: Strip replay removing unstaged or denied `cop_proposal` records SHALL preserve `semantic_core` for Pipeline A-only equivalence (20.36 Class 1).
46. HLR-20.033-046: COP SHALL NOT schedule Pipeline B realization, IMR `CorrectionTrigger` emission, or OuB expression changes.
47. HLR-20.033-047: COP `criteria_fields` for IB promotion/retirement SHALL be explicit deterministic markers evaluable at safe boundary without embedding GB heuristic scores.
48. HLR-20.033-048: When `gb.cap.pending_ib_requests` is exhausted, COP SHALL reject or deterministically evict with paired `COP_PENDING_IB_FULL` / `GB_CAP_PENDING_IB_FULL` audit codes — never silent drop.
49. HLR-20.033-049: COP SHALL NOT read `truth_hypotheses` from MTP or `semantic_core` for proposal derivation; truth evaluation consumes committed meaning downstream, not vice versa (20.140).
50. HLR-20.033-050: `criteria_fields{}` nested keys and ID arrays SHALL use deterministic canonical ordering before export, hash, and replay diff — lexicographic key sort; stable-ID array sort; numeric values canonical Q32.32.
51. HLR-20.033-051: COP proposal derivation SHALL NOT depend on TP creation order, allocation sequence, or address identity; only explicit canonical inputs and `enqueue_seq` ordering tokens MAY influence proposal bytes.

## Conformance

Implementation conforms when:

- COP remains propose-only; no direct envelope mutation
- proposals carry deterministic provenance and canonical serialization
- GB buffer and IB caps from 20.16/20.90 are enforced at admission
- safe-boundary commit visibility; no interleaved TS-core mutation
- denied/expired proposals leave `semantic_core` unchanged
- no `routing_epoch_id` advance or messy-input tag mutation by COP
- COP does not read `truth_hypotheses`
- `criteria_fields{}` uses canonical nested ordering in replay export
- proposal bytes invariant under permuted TP creation order for identical canonical inputs
- offload and CPU paths produce ordering-equivalent proposal sequences
- append-only lifecycle audit supports replay under execution signature

## Verification Focus

- Deterministic proposal fixtures with canonical ordering rejection on drift
- Pending-inquiry buffer full → deterministic reject/evict (HLR-048)
- GB deny path leaves `semantic_core` byte-stable (20.36 Class 1 strip)
- Class 4: COP proposals count toward GB IB caps without bypass
- Overload/quota fixtures reproduce identical `proposal_status` paths
- Seed change does not alter `cop_proposal` bytes for fixed inputs
- CPU/offload equivalence for proposal queue ordering
- Fixture rejects non-canonical `criteria_fields` key ordering
- TP creation-order permutation test produces identical `cop_proposal` bytes
