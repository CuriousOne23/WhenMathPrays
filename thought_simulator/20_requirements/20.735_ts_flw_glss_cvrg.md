## **0.3 Assumptions**

### **A. Requirement Namespace Rule**

When a requirement family is referenced (e.g., **20.30**, **20.40**, **20.110**), the reference is to the **entire requirement namespace**, including all sub‑documents.

For example:

- **"20.40"** refers to:
  - 20.40_ob_requirements.md
  - 20.40.010_sob_prim.md
  - 20.40.020_srob_prim.md
  - 20.40.030_cnob_prim.md
  - 20.40.040_smob_prim.md
  - 20.40.060_ssg_prim.md
  - …and all other 20.40.xxx files

This is the **intended interpretation** of the 20‑series requirement hierarchy.

### **B. Flow Boundary Rule**

Every non‑primitive flow must:

- **begin with a primitive**, and
- **end with a primitive**,

even when the internal step is a process, reference object, governance object, or TS‑concept.

This ensures:

- deterministic boundaries
- glossary alignment
- consistent visualization semantics

### **C. Glossary Authority Rule**

The **20.700.xxx glossary family** is the authoritative source for:

- primitive definitions
- process definitions
- reference‑object definitions
- governance‑object definitions
- TS‑level conceptual definitions

This document reflects those definitions but does not override them.

### **D. Visualization‑Only Scope**

This file is a **reference visualization layer**.
Normative behavior is defined in:

- 20.1xx (core requirements)
- 20.2xx (primitive requirements)
- 20.3xx (process requirements)
- 20.110 / 20.169 (basin requirements)
- 20.205 / 20.206 / 20.207 (XP, A/B sync, replay)

This document only **organizes** flows; it does not define their semantics.
