# **0. Introduction, Purpose, Assumptions, and How to Read This Document**

## **0.1 Introduction**

This document provides the **complete, cross‑referenced flow coverage** for all primitives, processes, reference objects, governance objects, and TS‑level concepts defined in the **20.700.xxx glossary family**.  
It consolidates:

- flows explicitly defined in **20.705**  
- flows implicitly required by the **20.700.xxx glossary**  
- flows defined normatively in the **20‑series design‑requirement documents**  
- flows that were missing from earlier visualization layers  
- flows formally catalogued in **20.710–20.725** (CSF, BCF, ROF, GVF series)

This document does **not** define new behavior.  
It organizes, validates, and cross‑checks the flows that are already normatively defined elsewhere.

## **0.3 Assumptions**

### **A. Requirement Namespace Rule**

When a requirement family is referenced (e.g., **20.30**, **20.40**, **20.110**), the reference is to the **entire requirement namespace**, including all sub‑documents.

For example:

- **"20.40"** refers to:  
  - 20.40_ob_requirements.md  
  - 20.40.010_sob_prim.md  
  - 20.40.020_srob_prim.md  
  - 20.40.030_cnob_prim.md  
  - 20.40.040_smob_prim.md  
  - 20.40.060_ssg_prim.md  
  - …and all other 20.40.xxx files  

This is the **intended interpretation** of the 20‑series requirement hierarchy.

### **B. Flow Boundary Rule**

Every non‑primitive flow must:

- **begin with a primitive**, and  
- **end with a primitive**,  

even when the internal step is a process, reference object, governance object, or TS‑concept.

This ensures:

- deterministic boundaries  
- glossary alignment  
- consistent visualization semantics  

### **C. Glossary Authority Rule**

The **20.700.xxx glossary family** is the authoritative source for:

- primitive definitions  
- process definitions  
- reference‑object definitions  
- governance‑object definitions  
- TS‑level conceptual definitions  

This document reflects those definitions but does not override them.

### **D. Visualization‑Only Scope**

This file is a **reference visualization layer**.  
Normative behavior is defined in:

- 20.1xx (core requirements)  
- 20.2xx (primitive requirements)  
- 20.3xx (process requirements)  
- 20.110 / 20.169 (basin requirements)  
- 20.205 / 20.206 / 20.207 (XP, A/B sync, replay)  

This document only **organizes** flows; it does not define their semantics.

### **E. Catalog Document Scope**

The flow catalogs (20.710–20.725) enumerate flows using short canonical IDs (CSF‑xx, BCF‑xx, ROF‑xx, GVF‑xx). These IDs are cross‑referenced in Section G and do not replace the flow names used in Sections A–F.

## **0.4 How to Read This Document**

### **A. Flow Classification**

Each flow is classified as one of:

- **Primitive Flow**  
- **Process Flow**  
- **Reference‑Object Flow**  
- **Governance Flow**  
- **TS‑Concept Flow**

This classification corresponds directly to the glossary categories in:

- 20.700.010 (Primitives)  
- 20.700.020 (Processes)  
- 20.700.030 (Reference Objects)  
- 20.700.040 (Governance Objects)  
- 20.700.050 (TS‑Level Concepts)

### **B. Flow Naming**

Flows are named canonically using:

```
<StartPrimitive> → {Optional Internal Object} → <EndPrimitive>
```

Examples:

- `OB → {Lane Arbitration} → RB`  
- `TB → {Truth‑Stability} → TB`  
- `GB → {Supervisory Enforcement} → OuBA`

### **C. Requirement Mapping**

Each flow is mapped to the **20‑series requirement family** that governs it.

For example:

- `OB → RB` maps to **20.50** (Routing Basin Requirements)  
- `TB → ΔH%` maps to **20.30** (Functional Model)  
- `GB → REx` maps to **20.80** (Governance Basin Requirements) and **20.206** (A/B Sync)

### **D. Completeness Indicators**

At the end of the document, a completeness verdict confirms:

- all glossary items are represented  
- all 20‑series design‑requirement documents are represented  
- all catalog flow IDs (CSF, BCF, ROF, GVF) are cross‑referenced  
- any exclusions are intentional and explained
