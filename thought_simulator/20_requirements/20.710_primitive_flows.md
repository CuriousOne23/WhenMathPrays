## Purpose

This catalog provides precise, executable visualizations of all Primitive Flows in the Thought Simulator (TS). Each flow:

- Uses **only canonical primitives**
- Shows clear **Path A / Governance / Path B** relationships
- Includes full context for development, simulation, and review
- Maintains strict architectural invariants (A/B separation, single-writer rule, determinism)

These flows are authoritative for implementation and verification.

## 1. Primitive Flows

### **1.1 PF-01 — TP → InB (Input Normalization Flow)**
**Type:** Primitive Flow  
**Primary Context:** Path A – Intake  
**When It Appears:** Start of every new turn.  
**Relation to Path A / Path B:** Feeds raw input into **Path A**; Path B later realizes the committed meaning produced downstream.  
**Why It Exists:** Enforces deterministic front-door normalization.  
**What It Accomplishes:** Produces canonical, replay-safe intake.  
**Related Glossary Blocks:** 20.100 (InB), 20.17, 20.105  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        TP[TP] --> InB[InB]
    end
``` 

---

# **Section 1.1 — Block Definitions (PathA Flowchart)**

- **TP:** Thought Packet; the structured per‑turn container holding semantic_core, object‑semantic fields, lineage, continuity, truth/safety tags, and all turn‑level processing state used across Path A, DF, Governance, and Path B.  
- **InB:** Inbound Basin; normalizes raw user input into the initial TP substrate, converting external text into structured primitive form without performing inference or meaning construction.

---

**How to Apply This Flowchart:** Use as the mandatory first step in any Path A simulation or implementation. Validate InB output before repair or interpretation.  
**Notes:** Single primitive boundary.

### **1.2 PF-02 — InB → SOB (Structural Interpretation Flow)**
**Type:** Primitive Flow  
**Primary Context:** Path A – Intake to Interpretation  
**When It Appears:** After InB (and optional IIInB).  
**Relation to Path A / Path B:** Begins the core **Path A** structural pipeline; final meaning is later realized in Path B.  
**Why It Exists:** Starts layered structural residue extraction.  
**What It Accomplishes:** Moves normalized data into the OB primitive chain.  
**Related Glossary Blocks:** 20.100, 20.40  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        InB[InB] --> SOB[SOB]
        SOB --> SROB[SROB]
        SROB --> CnOB[CnOB]
        CnOB --> SmOB[SmOB]
    end
```

# **Section 1.2 — Block Definitions (PathA Flowchart)**
- **InB:** Inbound Basin; normalizes raw user input into the initial TP substrate.  
- **SOB:** Semantic Object Basin; constructs the atomic semantic object for the turn.  
- **SROB:** Semantic Reference Object Basin; applies referential lineage and continuity to SOB.  
- **CnOB:** Conceptual Object Basin; transforms the referential object into conceptual abstraction.  
- **SmOB:** Semantic Meaning Object Basin; produces the meaning‑layer representation from conceptual structure.

---
**How to Apply This Flowchart:** Route InB output directly to SOB. Trace structural residue through the full chain.  
**Notes:** Canonical entry to OB primitives.

---

### **1.3 PF-03 — SmOB → RB (Routing Preparation Flow)**
**Type:** Primitive Flow  
**Primary Context:** Path A – Interpretation to Routing  
**When It Appears:** After SmOB stabilization.  
**Relation to Path A / Path B:** Completes routing metadata in **Path A**; enables consistent Path B realization.  
**Why It Exists:** Prepares geometry-ready signature for lane arbitration.  
**What It Accomplishes:** Produces routing decisions.  
**Related Glossary Blocks:** 20.40.040, 20.47, 20.51, 20.55  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        SmOB[SmOB] --> SSG[SSG]
        SSG --> RBU[RBU]
        RBU --> RB[RB]
    end
```

---

# **Section 1.3 — Block Definitions (PathA Flowchart)**

- **SmOB:** Semantic Meaning Object Basin; produces the meaning‑layer representation from conceptual structure and finalizes Path A meaning before SSG.  
- **SSG:** Structural Signature Generator; converts SmOB’s meaning representation into a geometric‑invariant signature vector used for routing and manifold‑agnostic comparison.  
- **RBU:** Routing Basin Upstream; receives the SSG signature and performs upstream routing preparation, including normalization, gating, and routing‑epoch alignment.  
- **RB:** Routing Basin; performs the final routing decision using the SSG signature and RBU‑prepared substrate, selecting the correct downstream basin or processing path.

---

**How to Apply This Flowchart:** Execute SSG and RBU before RB. Test lane selection.  
**Notes:** Expanded for supporting primitives.

### **1.4 PF-04 — RB → TB (Truth Handoff Flow)**
**Type:** Primitive Flow  
**Primary Context:** Path A → Governance  
**When It Appears:** After RB and OuBA commit.  
**Relation to Path A / Path B:** Completes **Path A** meaning construction; hands frozen snapshot to governance. Path B reads derived TPTB.  
**Why It Exists:** Maintains strict A/B separation.  
**What It Accomplishes:** Delivers semantic_core for truth evaluation.  
**Related Glossary Blocks:** 20.40.060, 20.60, 20.64  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        RB[RB] --> OuBA[OuBA]
        OuBA --> TB[TB]
    end
```

# **Section 1.4 — Block Definitions (PathA Flowchart)**
- **RB:** Routing Basin; performs the final deterministic routing decision using the SSG signature and RBU‑prepared substrate, selecting the correct downstream basin or processing path.  
- **OuBA:** Output Basin (Path A Commit); commits the finalized meaning‑layer representation into an immutable semantic snapshot, including semantic_core, object‑semantic fields, lineage, and ΔH%, marking the end of Path A.  
- **TB:** Truth Basin; evaluates the committed meaning snapshot from OuBA for factual alignment, contradiction, evidential basis, referential consistency, and explanation codes, producing the truth_state{} used by downstream governance.

---

**How to Apply This Flowchart:** Use after routing. Verify commit boundary.  
**Notes:** None.

### **1.5 PF-05 — TB → ΔH% (Entropy Attribution Flow)**
**Type:** Primitive Flow  
**Primary Context:** Path A – Uncertainty Tracking  
**When It Appears:** During/after TB evaluation.  
**Relation to Path A / Path B:** Updates **Path A** uncertainty state; influences continuation or handoff to Path B.  
**Why It Exists:** Supports monotonic entropy reduction.  
**What It Accomplishes:** Accumulates structural uncertainty.  
**Related Glossary Blocks:** 20.30, 20.140, 20.44  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        TB[TB] --> TPU[TPU]
        TPU --> DeltaH[ΔH%]
    end
```

---

# **Section 1.5 — Block Definitions (PathA Flowchart)**

- **TB:** Truth Basin; evaluates the committed meaning snapshot from OuBA for factual alignment, contradiction, evidential basis, referential consistency, and explanation codes, producing the truth_state{} used by downstream governance.  
- **TPU:** Thought Packet Updater; the sole safe writer to TP during Path A correction, applying truth updates, structural corrections, and ΔH% accumulation while preserving invariants and never modifying semantic_core outside correction rules.  
- **ΔH%:** Delta‑H Percent; the incremental structural‑uncertainty contribution produced by TPU during Path A correction, accumulated into H% and used for auditability, replay safety, and uncertainty evolution tracking.

---

**How to Apply This Flowchart:** Track ΔH% in simulations for monotonic checks.  
**Notes:** Updated via TPU.

### **1.6 PF-06 — IMR → IB (Inquiry Trigger Flow)**
**Type:** Primitive Flow  
**Primary Context:** Supervisory Trigger  
**When It Appears:** High uncertainty at Truth/Done.  
**Relation to Path A / Path B:** Triggers governance from **Path A** output; may affect Path B realization.  
**Why It Exists:** Prevents unsafe or incomplete commits.  
**What It Accomplishes:** Converts uncertainty into controlled inquiry.  
**Related Glossary Blocks:** 20.17, 20.30, 20.140, 20.90  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph PathA
        direction LR
        IMR[IMR] --> IB[IB]
    end
```

---

# **Section 1.6 — Block Definitions (PathA Flowchart)**

- **IMR:** Inconsistency/Mismatch Record evaluator; detects semantic, realization, or safety mismatches over the committed TP snapshot, classifies them into IMR‑A/B/C types, and emits supervisory signals without modifying meaning or TP.  
- **IB:** Inbound Basin (Governance); receives IMR supervisory output and determines whether a governance action (GBMn, GBIB, or escalation) is required, forwarding only governance‑relevant signals downstream while never altering TP or meaning.

---

**How to Apply This Flowchart:** Activate only on high-uncertainty conditions.  
**Notes:** IMR is the decision primitive.

**Primary Context:** Governance  
**When It Appears:** After IB evaluation.  
**Relation to Path A / Path B:** Bridges **Path A** inquiry into governance for final Path B influence.  
**Why It Exists:** Provides deterministic filtering.  
**What It Accomplishes:** Prepares context for GB.  
**Related Glossary Blocks:** 20.80, 20.90  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph Governance
        direction LR
        IB[IB] --> GBIB[GBIB]
    end
```

---

# **Section 1.7 — Block Definitions (Governance Flowchart)**

- **IB:** Inbound Basin (Governance); receives IMR supervisory output and determines whether governance processing is required, forwarding only governance‑relevant signals downstream while never altering TP or meaning.  
- **GBIB:** Governance Basin — Inquiry Bridge; integrates IB’s governance‑relevant signals with TB truth_state{} and safety flags, producing gbib_directives{} that encode inquiry‑truth coherence, governance‑policy applicability, semantic‑constraint checks, and safety‑relevant governance rules without modifying semantic_core or TP.

---

**How to Apply This Flowchart:** Implement before GB.  
**Notes:** None.

**Relation to Path A / Path B:** Feeds final governance decision affecting both paths.  
**Why It Exists:** Ensures single governance authority.

**Related Glossary Blocks:** 20.80  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph Governance
        direction LR
```

---

# **Section 1.8 — Block Definitions (Governance Flowchart)**

- **GBIB:** Governance Basin — Inquiry Bridge; integrates IB’s governance‑relevant signals with TB truth_state{} and safety flags, producing gbib_directives{} that encode inquiry‑truth coherence, governance‑policy applicability, semantic‑constraint checks, and safety‑relevant governance rules without modifying semantic_core or TP.  
- **GB:** Governing Basin; performs final governance‑side evaluation over gbib_directives{}, determining whether the committed meaning warrants promotion into Path A as an IdOB or emission of governance inference into Path B, applying deterministic governance policy and logging governance events without altering semantic_core, TP, or MTP.

---

**How to Apply This Flowchart:** Core escalation step in governance chain.  
**Notes:** None.

### **1.9 PF-09 — GB → OuBA / IdOB / REx (Governance Output Flow)**
**Type:** Primitive Flow  
**Primary Context:** Governance Output  
**When It Appears:** End of governance chain.  
**Relation to Path A / Path B:** Can promote into **Path A** or emit inference to **Path B**.  
**Why It Exists:** Closes supervisory loop with A/B separation.  
**What It Accomplishes:** Finalizes meaning or realization influence.  
**Related Glossary Blocks:** 20.80, 20.40.060, 20.110  
**Mini-Flow Diagram:**
```mermaid
flowchart LR
    subgraph Governance
        direction LR
        GB[GB] --> OuBA[OuBA]
        GB --> IdOB[IdOB]
        GB --> REx[REx]
    end
```

---

# **Section 1.9 — Block Definitions (Governance Flowchart)**

- **GB:** Governing Basin; performs final governance‑side evaluation over gbib_directives{}, determining whether the committed meaning warrants promotion into Path A as an IdOB, emission of governance inference into Path B, or routing back to OuBA, applying deterministic governance policy and logging governance events without altering semantic_core, TP, or MTP.  
- **OuBA:** Output Basin (Path A Commit); commits the finalized meaning‑layer representation into an immutable semantic snapshot, including semantic_core, object‑semantic fields, lineage, and ΔH%, marking the end of Path A and providing the committed meaning state consumed by DF and Path B.  
- **IdOB:** Identity Object Basin; constructs a stable identity object when governance determines that the committed meaning satisfies identity‑level criteria, producing an IdOB that can be promoted into Path A or used for long‑horizon identity continuity.  
- **REx:** Realization Extractor; extracts realization‑relevant substrate from the committed TP snapshot, including clause structure, dependencies, discourse roles, and realization constraints, operating read‑only over TP and performing no semantic interpretation or TP mutation.

---

**How to Apply This Flowchart:** Implement and test all three branches with full logging.  
**Notes:** Multi-output governance flow.
