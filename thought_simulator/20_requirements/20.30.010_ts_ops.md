# **20.30.010 — TS Operational Semantics**  
**Status:** Normative  
**Scope:** Pipeline A + A/B boundary  
**Excludes:** Merge formalism, truth semantics, TPU semantics, response generation (delegated to 20.30.050–080)

---

# **0. Purpose**

This document defines the **operational semantics** of the Thought Simulator (TS).  
It describes the deterministic execution model for:

- Pipeline A (meaning construction)  
- lane‑parallel execution  
- the TP/MTP lifecycle  
- the A/B boundary (`mtp_update`)  
- deterministic replay behavior  
- contract‑level operational metadata (checksum, schema_version, synthesis_mode)  
- validation, retry semantics, and error taxonomy  

All detailed semantics are delegated to the 20.30.050–20.30.080 subfiles.

---

# **1. TS Execution Model**

The TS operates in **deterministic cycles**.  
Each cycle processes:

1. input  
2. routing  
3. splitting  
4. OB processing  
5. TB interpretation  
6. merge  
7. truth/completion evaluation  
8. MTP update  
9. Pipeline B realization  

Pipeline A constructs meaning.  
Pipeline B performs realization and expression.

---

# **2. Pipeline A — Meaning Construction**

Pipeline A transforms:

```
(input, prior MTP) → semantic_core(N+1)
```

Pipeline A is:

- deterministic  
- lane‑parallel  
- bounded  
- auditable  
- replay‑equivalent  

Pipeline A includes:

- **InB** — input intake  
- **RB** — routing  
- **OB** — local meaning extraction  
- **TB** — interpretive semantics  
- **Merge** — deterministic recombination  
- **TR** — routing refinement  
- **TPU** — commit of semantic updates to the MTP  

Detailed semantics: 20.30.050, 20.30.060, 20.30.070.

---

# **3. Lane‑Parallel Execution**

Pipeline A uses a **lane‑parallel** execution model:

- RB determines OB activation and TP projection  
- Splitting produces lane‑local TPs  
- OBs process lane TPs independently  
- TB interprets lane‑local meaning  
- Merge recombines lane TPs deterministically  

Lane parallelism is bounded and non‑expansive.  
Overflow behavior is defined in 20.30.020 and 20.30.030.

---

# **4. TP and MTP Lifecycle**

## **4.1 TP (Thought Packet)**  
A TP is a lane‑local semantic object containing:

- propositions  
- stance/affect/intent  
- ΔH%  
- lineage  
- semantic tags  
- truth hypotheses  
- `tr_needs_update`  
- contract metadata:  
  - `checksum`  
  - `schema_version`  
  - `synthesis_mode`  

TPs exist only within a single cycle.

---

## **4.2 MTP (Master Thought Packet)**  
The MTP is the global semantic state for the current thought.  
It is updated only through the Merge → TPU → `mtp_update` sequence.  
The MTP provides the frozen semantic snapshot consumed by Pipeline B.

---

# **5. Deterministic Replay Semantics**

The TS produces identical outputs for identical:

```
(input, MTP state, seed)
```

Replay determinism depends on:

- OB/RB/TB semantics  
- ΔH% computation  
- merge behavior  
- truth/completion evaluation  
- TPU commit  
- contract metadata validation  
- response‑generator mapping for a fixed seed  

Replay determinism is a global architectural invariant.

---

# **6. A/B Boundary — `mtp_update`**

`mtp_update` is the commit point between Pipeline A and Pipeline B.

At this boundary:

- Pipeline A finalizes `semantic_core(N+1)`  
- TPU commits the update  
- a new `commit_id` is generated  
- contract metadata is validated  
- Pipeline B receives a frozen semantic snapshot  

Pipeline B does not modify meaning.

---

# **7. Deterministic Cycle Ordering**

A TS cycle follows this fixed ordering:

1. InB  
2. RB  
3. Split  
4. OB  
5. TB  
6. Merge  
7. Truth/Completion evaluation  
8. TPU  
9. `mtp_update`  
10. Pipeline B  
11. Response generation  

This ordering is fixed and non‑configurable.

---

# **8. Deterministic Error, Overflow, and Retry Behavior**

Pipeline A detects overflow conditions deterministically.  
Overflow results in deterministic degradation, tagging, and logging.  
No probabilistic reconstruction is used.

Retry semantics follow VR‑1 → VR‑9 ordering (20.206).  
Error‑class taxonomy is defined in 20.206 and enforced here.  
Contradiction annotations propagate without smoothing.

---

# **9. Normative Requirements (HLR‑20.30.010‑xxx)**

### **HLR‑20.30.010‑001 — Deterministic Cycle Execution**  
Pipeline A SHALL execute the TS cycle in the canonical deterministic order defined in §7.

### **HLR‑20.30.010‑002 — Deterministic Lane Semantics**  
Lane creation, execution, and merge SHALL be deterministic and SHALL NOT introduce nondeterministic expansion.

### **HLR‑20.30.010‑003 — Deterministic TP/MTP Lifecycle**  
TPs SHALL be ephemeral lane‑local objects; MTP SHALL be the sole global semantic state.

### **HLR‑20.30.010‑004 — Deterministic Replay**  
Pipeline A SHALL guarantee replay equivalence for identical $(\text{input}, \text{MTP state})$ tuples.

### **HLR‑20.30.010‑005 — A/B Boundary Integrity**  
`mtp_update` SHALL freeze `semantic_core` and SHALL be the sole handoff point to Pipeline B.

### **HLR‑20.30.010‑006 — Meaning/Expression Separation**  
Pipeline A SHALL write meaning; Pipeline B SHALL express meaning without modifying it.

### **HLR‑20.30.010‑007 — Deterministic Overflow Behavior**  
Pipeline A SHALL detect, tag, and degrade deterministically under overflow conditions.

---

### **HLR‑20.30.010‑008 — Contract Metadata Presence**  
Each TP and MTP SHALL carry `checksum`, `schema_version`, and `synthesis_mode` fields.

### **HLR‑20.30.010‑009 — Contract Metadata Validation**  
Pipeline A SHALL validate checksum, schema version, and synthesis_mode before `mtp_update`.

### **HLR‑20.30.010‑010 — Error‑Class Taxonomy Enforcement**  
Pipeline A SHALL classify errors using the 20.206 error taxonomy and SHALL NOT invent new classes.

### **HLR‑20.30.010‑011 — Retry Semantics**  
Pipeline A SHALL apply retry semantics in VR‑1 → VR‑9 order (20.206).

### **HLR‑20.30.010‑012 — Contradiction Annotation Propagation**  
Pipeline A SHALL preserve contradiction annotations from TP to MTP without smoothing or suppression.

### **HLR‑20.30.010‑013 — Deterministic Contract Enforcement**  
All contract violations SHALL be logged with deterministic reason codes and SHALL NOT modify meaning-layer fields except through approved Type B A‑cycle writes.

---

# **10. Summary**

20.30.010 defines the operational semantics of the TS:

- deterministic cycle execution  
- deterministic lane‑parallel meaning construction  
- explicit TP/MTP lifecycle  
- deterministic replay  
- deterministic A/B boundary  
- deterministic overflow behavior  
- contract metadata enforcement  
- retry semantics and error taxonomy  

All detailed semantics are delegated to the 20.30.020–20.30.080 subfiles.
