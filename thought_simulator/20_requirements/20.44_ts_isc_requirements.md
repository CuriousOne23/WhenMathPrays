# **20.44_ts_isc_requirements.md**  
**TS Inference Scorer (ISc) Requirements**  
**Status:** Draft v0.3 — Pending CP/Grok Review**  
**Owner:** TS Architecture**  
**Related:** 20.01, 20.10, 20.12, 20.20, 20.30, 20.32, 20.33, 20.34, 20.46, 20.95, 20.105

---

# **1. Purpose**

The TS Inference Scorer (ISc) is a **Pipeline A primitive** responsible for **bounded, deterministic scoring** of TS‑generated candidate interpretations or state transitions. ISc does **not** generate meaning. It evaluates a **finite candidate set**, produces a **normalized distribution**, exposes **entropy, confidence, and rationale**, and may trigger **policy‑bound escalation** to COP.

ISc strengthens ambiguity detection, uncertainty propagation, and meaning stability while preserving all TS invariants (20.10, 20.12) and safe‑boundary rules (20.30, 20.105).

---

# **2. Scope**

ISc operates **inside Pipeline A**, between:

- **TB (Truth Basin)** — candidate generation  
- **Merge** — formation of TP‑UPDATE requests  

ISc is a **TS‑internal primitive**, not a basin, not a coprocessor, not a realization component, and not a TP subsystem.

ISc outputs are committed to TP **only** via Merge → TPU → TP, with a **1‑TP‑cycle lag**.

---

# **3. Architectural Positioning**

ISc is a first‑class Pipeline A primitive. Updated Pipeline A flow:

```
Pipeline A:
    InB → IIInB → RB → TB → ISc → Merge → TPU → TP
                         ↑
                         └───(optional escalation)──→ COP
```

ISc:

- receives a **finite candidate set** from TB  
- computes a **deterministic score distribution**  
- emits **bounded metadata**  
- never mutates TP directly  
- never interacts with Pipeline B  
- never bypasses Merge or TPU  

ISc results become visible to downstream modules in **TP(N+1)**.

---

# **4. Definitions**

**Candidate Set**  
A finite, TB‑generated set of structured interpretations or state transitions.

**ISc Distribution**  
A normalized probability distribution over the candidate set.

**Entropy / Confidence**  
Scalar uncertainty metrics used by CIL, COB, and escalation policy.

**Rationale Codes**  
Feature‑level explanations for scoring decisions.

---

# **5. High‑Level Requirements (HLRs)**

### **HLR‑20.044‑001 — Finite Candidate Set Only**  
ISc SHALL operate exclusively on a finite candidate set produced by TB.  
ISc SHALL NOT generate new meanings or expand the candidate set.

### **HLR‑20.044‑002 — Deterministic Scoring**  
ISc SHALL produce identical outputs for identical inputs, state, and seed.  
No stochasticity or nondeterministic methods are permitted.

### **HLR‑20.044‑003 — Transparent, Auditable Features**  
ISc SHALL use only interpretable scoring features.  
All features SHALL be logged in rationale metadata.

### **HLR‑20.044‑004 — Normalized Distribution**  
ISc SHALL output a normalized probability distribution over the candidate set.

### **HLR‑20.044‑005 — Uncertainty Metrics**  
ISc SHALL compute entropy, confidence, and rationale codes.

### **HLR‑20.044‑006 — Escalation Triggering**  
ISc SHALL trigger COP escalation when policy thresholds are met (entropy, confidence, OOD, high‑impact domain, or GB‑defined rules).

### **HLR‑20.044‑007 — No Direct TP Mutation**  
ISc SHALL NOT write to TP.  
All outputs SHALL be routed through Merge → TPU → TP.

### **HLR‑20.044‑008 — Replay Safety**  
ISc SHALL satisfy replay invariants (20.12).  
All scoring must be fully replayable and seed‑isolated.

### **HLR‑20.044‑009 — TCU Bound**  
ISc SHALL operate within a fixed TCU budget defined in 20.90.  
Overflow SHALL degrade deterministically.

### **HLR‑20.044‑010 — Pipeline A Only**  
ISc SHALL NOT interact with Pipeline B or realization planning.

---

# **6. Inputs**

ISc receives:

- **candidate_set{}** — structured candidates from TB  
- **context_window{}** — relevant TP fields  
- **features{}** — symbolic scoring features  
- **policy{}** — deterministic policy lookup (20.90)  
- **seed** — deterministic seed for replay  
- **tcu_budget** — TCU allocation  

All inputs MUST be immutable during scoring.

---

# **7. Outputs**

ISc outputs a structured object:

```
isc_output {
    distribution[]        // normalized scores (Q32.32)
    chosen_candidate      // index
    entropy               // Q16.16
    confidence            // Q16.16
    rationale[]           // feature-level explanations
    escalation_flag       // boolean
    escalation_reason     // code
    metadata {
        isc_version
        seed
        tcu_used
        canonical_ordering_hash
    }
}
```

ISc outputs SHALL NOT be written directly to TP.  
They SHALL be passed to Merge → TP‑UPDATE → TPU → TP.

---

# **8. TP Interaction**

ISc results are committed to TP via TPU as:

```
tp_update_request {
    isc {
        distribution[]
        entropy
        confidence
        rationale[]
        escalation_flag
        escalation_reason
    }
}
```

### **8.1 1‑TP‑Cycle Lag**  
ISc outputs SHALL become visible in **TP(N+1)**.  
This preserves safe‑boundary semantics and replay invariants.

### **8.2 Writer Authority**  
ISc SHALL NOT write to:

- semantic_core  
- conversation_objects  
- realization_plan  
- basins  
- any forbidden TP fields (20.105 writer matrix)

ISc SHALL write only to the `isc{}` block.

---

# **9. Coprocessor Escalation & Access Boundaries**

### **9.1 Overview**

ISc MAY request escalation to the Coprocessor Interface Layer (COP) when ambiguity, uncertainty, or policy thresholds require higher‑fidelity scoring. ISc SHALL NOT access any coprocessor directly. All escalation MUST occur through COP using the propose‑only mechanism defined in **20.34 COP Requirements**.

Escalation SHALL occur only at a **GB‑approved deterministic safe boundary** (20.10 §1.9, 20.30 §8.4–8.6).

---

### **9.2 Preconditions for Escalation**

ISc SHALL trigger escalation only when all of the following are true:

- **Policy threshold met** (entropy, confidence, OOD, high‑impact domain)  
- **Deterministic policy lookup** per 20.90 parameter table  
- **GB caps permit escalation** (`gb.cap.coprocessor_escalations_per_cycle`)  
- **Candidate set is finite and unchanged**  
- **TCU budget not exceeded**  

ISc SHALL NOT escalate for performance reasons alone.

---

### **9.3 Escalation Proposal Schema**

```
isc_cop_proposal {
    candidate_set[]          // identical to TB output; canonical ordering
    distribution[]           // ISc preliminary scores (Q32.32)
    entropy                  // Q16.16
    confidence               // Q16.16
    rationale[]              // feature-level explanations
    escalation_reason        // code
    metadata {
        isc_version
        seed
        tcu_used
        canonical_ordering_hash
    }
}
```

Canonical ordering SHALL follow 20.95 and 20.105.

---

### **9.4 COP Responsibilities (20.34 Alignment)**

COP SHALL:

- validate the proposal  
- prepare a `cop_proposal` conforming to **20.34 §2**  
- obtain **GB approval at a deterministic safe boundary**  
- invoke the transformer coprocessor  
- receive the refined distribution  
- wrap the result in a bounded, deterministic proposal  
- return the proposal to Merge for TPU commit  

COP SHALL NOT mutate TP or TS state.

---

### **9.5 Returned Distribution Requirements**

The coprocessor MUST return:

- a **distribution over the same candidate set**  
- no new meanings  
- no candidate expansion  
- no semantic rewriting  

Returned distributions MUST be:

- deterministic under fixed seed  
- replay‑equivalent (20.12 HLR‑20.012‑010/011)  
- canonically ordered  
- Q32.32 numeric format  
- accompanied by rationale codes  

---

### **9.6 TS Sovereignty & Validation**

Merge SHALL treat coprocessor output as a **proposal only**.

Merge SHALL validate:

- normalization  
- candidate alignment  
- rationale completeness  
- replay compatibility  
- envelope compliance  
- safe‑boundary approval  

Validation SHALL be deterministic and auditable per 20.105 §9.

If validation fails, Merge SHALL:

- reject the proposal  
- fall back to the ISc distribution  
- append an audit entry  
- optionally trigger GB review  

---

### **9.7 Forbidden Actions (Coprocessor‑Specific)**

#### **ISc SHALL NOT:**
- call the coprocessor directly  
- bypass COP or GB  
- bypass Merge or TPU  
- accept coprocessor output directly  
- request meaning generation  
- request candidate expansion  
- request semantic rewriting  
- modify intake‑bound fields (Track H; 20.105 §3.4; 20.17 messy‑input rules)

#### **COP SHALL NOT:**
- perform semantic interpretation  
- generate new meanings  
- expand or reorder candidates  
- mutate TP or TS state  
- bypass Merge or TPU  

---

### **9.8 1‑TP‑Cycle Lag**

All coprocessor‑refined distributions SHALL be committed to TP via TPU and SHALL become visible in **TP(N+1)**.

---

### **9.9 Verification Focus**

Verification SHALL include:

- replay tests for escalated vs. non‑escalated paths  
- strip‑replay equivalence tests (20.12 HLR‑20.012‑011)  
- canonical ordering checks  
- GB cap enforcement  
- deterministic fallback behavior  
- safe‑boundary approval logs  
- TCU‑bounded degradation tests

# **10. Canonical Ordering & Serialization**

ISc SHALL follow canonical ordering rules defined in 20.95 and 20.105:

- lexicographic ordering of candidate IDs  
- stable ordering of rationale codes  
- Q32.32 numeric formats  
- deterministic hashing for replay  
- canonical serialization for audit logs  

Any deviation SHALL be treated as a TS architecture error.

---

# **11. Forbidden Actions (General)**

ISc SHALL NOT:

- generate meaning  
- expand candidate sets  
- mutate TP directly  
- interact with Pipeline B  
- access coprocessors directly  
- use nondeterministic or opaque methods  
- perform intake repair (Track H)  
- bypass TB or Merge  
- exceed TCU or GB limits  
- introduce new state  

---

# **12. Error Handling**

ISc SHALL emit:

```
isc_error {
    code
    rationale
    fallback_distribution
    escalation_flag
}
```

Fallback SHALL be a deterministic uniform distribution unless policy specifies otherwise.

ISc SHALL NOT halt TS execution.

---

# **13. Risks & Mitigations**

### **13.1 Nondeterminism Creep**  
Mitigation: strict feature transparency, seed isolation, replay tests.

### **13.2 Envelope Leakage**  
Mitigation: writer authority matrix, forbidden actions, TPU enforcement.

### **13.3 TCU Explosion**  
Mitigation: fixed TCU budget, deterministic degradation.

### **13.4 Over‑Escalation to COP**  
Mitigation: GB caps, deterministic policy lookup, safe‑boundary approval.

### **13.5 Coprocessor Latency/Availability**  
Mitigation: deterministic fallback to ISc distribution.
