# 20.31 Semantic Specification

**Document ID:** 20.31  
**Version:** 0.5  
**Date:** 2026-06-19  
**Status:** CP-approved — dual-pipeline meaning semantics (v0.4 refinements applied)

## Purpose

Defines **semantic structures and meaning representation** for the Thought Simulator under the dual-pipeline architecture. This document is the semantic authority for Pipeline A (`semantic_core`) fields and SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

**Goal:** Meaning is explicit, structured, auditable, and isolated from execution/realization metadata.

## Role in the Development Flow

Defines meaning structures for 40-series prototypes and downstream 10-series formalization. Insights from prototyping refine this document.  
Execution-layer semantics (OpBeh, OBG, XlateR, IMR records) are defined in 20.20 and module requirements (20.45).  
Numeric encoding is defined in [20.95_ts_numeric_policy.md](20.95_ts_numeric_policy.md).

## Parent Scope

- **Authority:** Pipeline A meaning fields in `semantic_core` / MTP / TP projections  
- **Does not modify:** 20.10, 20.12, 20.20, 20.30.000 bootstrap documents  
- **Does not define:** `exec_plan`, `exec_trace`, or GB supervisory field semantics  

## Non-Goals

- Final 10-series executable schema  
- Realization planning or expression artifact semantics  
- GB cap/rate-limit policy semantics (20.16, 20.80)  
- Reference algorithms (20.35 operationalize this document)

# 1. Core Meaning Semantics (`semantic_core` / MTP)

### 1.1 Canonical Meaning Schema

**HLR-20.031-001:** The canonical meaning schema for MTP and committed `semantic_core` snapshots SHALL include:

| Field group | Semantics |
|-------------|-----------|
| `propositions[]` | Explicit semantic claims |
| `stance` | Declared position relative to propositions |
| `affect` | Structured emotional valence and intensity |
| `intent` | Declared action or communicative objective |
| `delta_h` / ΔH% | Bounded entropy contribution and missing-mass accounting |
| `lineage[]` | Deterministic provenance and ancestry chain |
| `semantic_tags[]` | Explicit classification tags for routing and interpretation |
| `truth_hypotheses` | Structured truth-evaluation fields |
| `done_state` | Deterministic completion state for current cycle or objective |
| `stability_metadata` | Stability and degradation indicators |
| `overflow_metadata` | Overflow tags and boundedness events per 20.30.070 |
| `thought_router_fields` | TR-derived routing fields per 20.37 |
| `tr_needs_update` | Boolean: TP.TR stale for current semantic context |
| `messy_input_record` | When present: tags per 20.17 |

### 1.2 Multi-core Path A Lineage Fields

**HLR-20.031-024:** Under multi-core Path A execution (20.115), `semantic_core` SHALL preserve read-only lineage fields:

- `core_id` — Path A instance that produced the meaning  
- `orthogonality_signature` — OB-domain identity for that Path A instance  

These fields SHALL NOT be interpreted as semantic content and SHALL NOT be modified by Pipeline B.

### 1.3 Commit Boundary Semantics

**HLR-20.031-011:** `semantic_core` SHALL be the authoritative meaning envelope committed at Pipeline A `mtp_update`.  
Pipeline B SHALL treat it as read-only semantic truth.  
Commit semantics SHALL follow 20.206 (post-refactor) and 20.115.

### 1.4 Numeric Semantics

**HLR-20.031-016:** Authoritative numeric meaning fields (ΔH%, missing-mass, stance weights) SHALL use Q32.32 semantics per 20.95.

**HLR-20.031-022:** Canonical Q32.32 meaning fields SHALL normalize negative zero to positive zero before commit, comparison, and replay export.

### 1.5 Canonical Ordering

**HLR-20.031-017:** Meaning arrays (`propositions[]`, `goals[]`, `lineage[]`, `semantic_tags[]`) SHALL use deterministic canonical ordering before export/replay diff.

**HLR-20.031-025:** Under multi-core Path A, lineage entries SHALL include core-local provenance and SHALL NOT collapse contributions across cores.

### 1.6 Semantic Tags

**HLR-20.031-021:** `semantic_tags[]` SHALL encode meaning-layer classification only.  
They SHALL NOT encode execution hints (`opbeh_id`, `obg_id`, `xlater_id`, `routing_epoch_id`, register/voice selection, OuB directives).

### 1.7 Truth Hypotheses Schema

**HLR-20.031-023:** `truth_hypotheses` SHALL use a stable schema-versioned record with minimum fields:

- `hypothesis_id`  
- `proposition_ref`  
- `truth_status`  
- `confidence_q32`  
- `evidence_refs[]`  
- `last_updated_cycle`  

**HLR-20.031-026:** Truth hypotheses SHALL include:

- `truth_epoch_id` (20.206)  
- `truth_update_reason_code` (20.206)  

**HLR-20.031-027:** Truth status enumeration SHALL match 20.206 final:  
`TRUE`, `FALSE`, `PROVISIONAL`, `UNSUPPORTED`.

# 2. TP Projection Semantics

**HLR-20.031-012:** TP SHALL be a lane-local projection of MTP / `semantic_core`.  
TP SHALL carry lane-specific views of propositions, ΔH%, suppression markers, and routing context.

**HLR-20.031-013:** TP SHALL NOT carry execution-layer fields (`routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, IMR records, GB fields).

**HLR-20.031-028:** TP SHALL carry basin-local suppression markers per 20.30.070.

**HLR-20.031-029:** TP SHALL expose ΔH% only after canonical normalization per 20.95.

---

# 3. Messy-Input Semantic Fields

**HLR-20.031-014:** When messy input is detected, `semantic_core` SHALL carry `messy_input_record` semantics per 20.17.

**HLR-20.031-015:** `messy_input_class[]` SHALL use canonical lexicographic order:  
`MI_AFFECT`, `MI_CONTRA`, `MI_INCOMP`, `MI_NOISE`, `MI_VAGUE`, `MI_AMBIG`, `MI_SCOPE`.

**HLR-20.031-018:** Pipeline B and OuB SHALL NOT clear, smooth, or rewrite messy-input fields.

**HLR-20.031-030:** Contradiction semantics SHALL follow 20.17 final, including parallel-trace arbitration rules.

---

# 4. OB Semantics (Local Extraction)

**HLR-20.031-002:** OB modules SHALL extract local meaning fragments from TP using deterministic semantics.

**HLR-20.031-003:** OB semantics SHALL define:

- visible vs suppressed boundaries  
- ΔH% contribution rules  
- canonical evidence field structure  
- deterministic projection semantics  
- MI_NOISE handling without invented content  

---

# 5. TB Semantics (Interpretation)

**HLR-20.031-004:** TB modules SHALL produce deterministic interpretation fields without latent state mutation.

**HLR-20.031-005:** TB semantics SHALL include stance, affect, intent, logic, and social interpretation channels.

**HLR-20.031-006:** Interpretations SHALL be explicit, auditable, and attributable to deterministic evidence.

---

# 6. IB Semantics (Inquiry Evolution)

**HLR-20.031-007:** IB semantics SHALL define deterministic inquiry evolution across cycles.

**HLR-20.031-008:** IB semantics SHALL include:

- ΔH% evolution  
- inquiry lifecycle state  
- evidence accumulation  
- conflict tracking  
- split/merge semantics  
- promotion/retirement criteria  

---

# 7. COB Semantics (Conversation Identity)

**HLR-20.031-009:** COB semantics SHALL define deterministic conversation identity and lifecycle behavior.

**HLR-20.031-010:** COB semantics SHALL include identity, lineage, compaction, replay, and promotion/deprecation transitions.

---

# 8. MCS Semantics (Meaningful Cognitive Step)

A Meaningful Cognitive Step (MCS) is a logged, attributable, state-changing transition advancing the task toward a declared success condition.

**HLR-20.031-019:** Each counted MCS SHALL be logged, attributable, state-changing, and success-path aligned.

**HLR-20.031-020:** MCS semantics SHALL prohibit micro-step inflation, repeated artifacts, and formatting-only steps.

## 9. Dual-Pipeline Semantic Boundary

The following artifacts are **not part of meaning semantics** and are defined elsewhere:

| Artifact | Authority |
|----------|-----------|
| `exec_plan`, realization triples | 20.20, 20.12 |
| `exec_trace`, `imr_record` | 20.45 |
| `supervisory`, GB caps/modes | 20.16, 20.80 |
| Seed-driven expression selection | 20.12-010, 20.160 |

**HLR-20.031-031:** Seed variability SHALL affect expression/realization only; seed SHALL NOT alter propositions, stance, goals, basin routing, Thought Router derivation, or messy-input classification in `semantic_core`.

**HLR-20.031-032:** Pipeline B SHALL NOT modify any meaning-layer field except through approved Type B A-cycle writes (20.36 Class 2/5).

## 10. Deterministic Replay Semantics

**HLR-20.031-033:** Pipeline A meaning replay SHALL be 100% deterministic for identical tuples  
$(\text{input}, \text{prior\_MTP}, \text{policy\_signature})$  
across InB, RB, OB, TB, $\Delta H\%$, merging, truth/done, and MTP update stages.

**HLR-20.031-034:** Replay equivalence SHALL satisfy: stripping `exec_plan` and `exec_trace` from a full trace SHALL yield a `semantic_core` identical to Pipeline A–only replay for the same inputs before approved Type B IMR corrections (20.36).

**HLR-20.031-035:** Full-trace reproducibility SHALL hold for tuples  
$(\text{input}, \text{MTP state}, \text{seed}, \text{routing\_epoch\_id}, \text{policy\_signature})$  
with all material meaning decisions logged with deterministic ordering and rationale codes.

**HLR-20.031-036:** Replay tuples SHALL include `routing_basin_id` and `semantic_epoch_id` per 20.36 and 20.30.070.

## 11. Deterministic Policy Enforcement Semantics

**HLR-20.031-037:** All policy constraints SHALL be enforced deterministically at RB/TB safe boundaries with zero unlogged violations.

**HLR-20.031-038:** Policy enforcement outcomes SHALL be logged with deterministic reason codes and replayable evidence.

**HLR-20.031-039:** Policy enforcement SHALL NOT modify meaning-layer fields except through approved Type B A-cycle writes (20.36).

Cross-document precedence for IB lifecycle content:

1. **20.31** defines meaning of IB fields and states.  
2. **20.34** defines governance, control boundaries, and lifecycle transition authority.  
3. **20.35** defines operational realization.

**HLR-20.031-040:** If conflicts occur, semantic definitions in 20.31 SHALL override 20.34 and 20.35.

## 13. TR Dirty-Flag Semantics

The TP-local `tr_needs_update` field governs TR recomputation lifecycle. Module placement and TR field integration defer to 20.37; lifecycle rules below are authoritative for semantics.

| Rule | Semantics |
|------|-----------|
| Type | boolean only |
| Initialization | each new TP: `tr_needs_update = true` |
| Stale | `true` → TP.TR requires recompute |
| Fresh | `false` → TP.TR current for present semantic context |
| Writers | any semantic writer modifying semantic-relevant TP fields SHALL set `true` |
| MTP context | modules mutating TP from MTP context SHALL set `true` |
| Clear | TR sets `false` only after successful recompute and commit |
| Failure | TR reject/error leaves `true` |
| Execution | TR SHALL NOT run when `false` |
| Routing | RB routes to TR iff `tr_needs_update = true` |

**HLR-20.031-041:** TR recompute SHALL NOT occur during the MTP commit window (20.37).

**HLR-20.031-042:** TR recompute SHALL use the canonical TP snapshot frozen at routing time (20.37).

**HLR-20.031-043:** TR outputs SHALL be lineage-attributable and SHALL NOT depend on nondeterministic ordering.
