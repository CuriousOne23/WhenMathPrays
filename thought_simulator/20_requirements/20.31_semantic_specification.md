# 20.31 Semantic Specification

**Document ID:** 20.31  
**Version:** 0.4  
**Date:** 2026-06-06  
**Status:** CP-approved — dual-pipeline meaning semantics (v0.3 refinements applied)

## Purpose

Defines **semantic structures and meaning representation** for the Thought Simulator under the dual-pipeline architecture. This document is the semantic authority for Pipeline A (`semantic_core`) fields and SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

**Goal:** Meaning is explicit, structured, auditable, and isolated from execution/realization metadata.

## Role in the Development Flow

Defines meaning structures for 40-series prototypes and downstream 10-series formalization. Insights from prototyping refine this document. **Execution-layer semantics** (OpBeh, OBG, XlateR, IMR records) are defined in 20.20 and module requirements (20.45); **numeric encoding** in [20.95_ts_numeric_policy.md](20.95_ts_numeric_policy.md).

## Parent Scope

- **Authority:** Pipeline A meaning fields in `semantic_core` / MTP / TP projections
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents
- **Does not define:** `exec_plan`, `exec_trace`, or GB supervisory field semantics

## Non-Goals

- Final 10-series executable schema
- Realization planning or expression artifact semantics
- GB cap/rate-limit policy semantics (20.16, 20.80)
- Reference algorithms (20.35 operationalize this document)

## 1. Core Meaning Semantics (`semantic_core` / MTP)

1. **HLR-20.031-001:** The canonical meaning schema for MTP and committed `semantic_core` snapshots SHALL include:

| Field group | Semantics |
|-------------|-----------|
| `propositions[]` | Explicit semantic claims |
| `stance` | Declared position relative to propositions |
| `affect` | Structured emotional valence and intensity |
| `intent` | Declared action or communicative objective |
| `delta_h` / ΔH% | Bounded entropy contribution and missing-mass accounting |
| `lineage[]` | Deterministic provenance and ancestry chain |
| `semantic_tags[]` | Explicit classification tags for routing and interpretation |
| `truth_hypotheses` | Structured truth-evaluation fields |
| `done_state` | Deterministic completion state for current cycle or objective |
| `stability_metadata` | Stability and degradation indicators |
| `overflow_metadata` | Overflow tags and boundedness event fields per 20.30 §8.3 |
| `thought_router_fields` | TR-derived routing fields (per 20.37) |
| `tr_needs_update` | Boolean: TP.TR stale for current semantic context |
| `messy_input_record` | When present: tags per [20.17](20.17_messy_input_handling.md) |

2. **HLR-20.031-011:** `semantic_core` SHALL be the authoritative meaning envelope committed at Pipeline A `mtp_update`; Pipeline B SHALL treat it as read-only semantic truth for realization. Commit boundary and `commit_id` semantics: [20.115](20.115_mtp_requirements.md), [20.206](20.206_pipeline_a_b_synchronization_contract.md) (20.500 refactor — draft pending Stage 4).

3. **HLR-20.031-016:** Authoritative numeric meaning fields (ΔH%, missing-mass, stance weights where numeric) SHALL use Q32.32 semantics per 20.95; semantic comparisons SHALL use exact canonical integer equality.

4. **HLR-20.031-022:** Canonical Q32.32 in meaning fields SHALL normalize negative zero to positive zero per HLR-20.095-032 before commit, comparison, and replay export.

5. **HLR-20.031-017:** Meaning arrays (`propositions[]`, `goals[]`, `lineage[]`, `semantic_tags[]`) SHALL use deterministic canonical ordering before export/replay diff — stable ID lexicographic sort, or `(module_id, tp_seq, lineage_seq)` for lineage per 20.95/20.39.

6. **HLR-20.031-021:** `semantic_tags[]` SHALL encode **meaning-layer** classification only (topic, domain, discourse act class, basin routing *intent* at meaning level); they SHALL NOT encode execution hints such as `opbeh_id`, `obg_id`, `xlater_id`, `routing_epoch_id`, register/voice selection, or OuB presentation directives.

7. **HLR-20.031-023:** `truth_hypotheses` SHALL use a stable schema-versioned record per hypothesis with minimum fields: `hypothesis_id`, `proposition_ref`, `truth_status`, `confidence_q32` (Q32.32), `evidence_refs[]`, `last_updated_cycle`. Records SHALL sort canonically by `hypothesis_id` lexicographic before export/replay diff.

## 2. TP Projection Semantics

5. **HLR-20.031-012:** TP SHALL be a **lane-local projection** of MTP / `semantic_core` — not a second authoritative meaning store. TP SHALL carry lane-specific views of propositions, ΔH%, suppression markers, and routing context.

6. **HLR-20.031-013:** TP SHALL NOT carry `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, IMR records, or GB supervisory fields; those belong to execution or supervisory envelopes only.

---

## 3. Messy-Input Semantic Fields

7. **HLR-20.031-014:** When messy input is detected, `semantic_core` SHALL carry `messy_input_record` semantics per 20.17, including at minimum: `messy_input_class[]`, `conflict_flag`, `conflict_group_id`, `underspec_flag`, `underspec_slots[]`, `incomplete_flag`, `missing_slots[]`.

8. **HLR-20.031-015:** `messy_input_class[]` SHALL use canonical lexicographic order: `MI_AFFECT`, `MI_CONTRA`, `MI_INCOMP`, `MI_NOISE`, `MI_VAGUE`. Contradiction semantics SHALL allow parallel traces with `contradiction_status` without collapsing meaning at Pipeline A unless GB-arbitrated at safe boundaries.

9. **HLR-20.031-018:** Pipeline B and OuB presentation SHALL NOT clear, smooth, or rewrite messy-input meaning fields in `semantic_core`; expression choices SHALL NOT substitute for propositional resolution of vagueness or contradiction (20.17).

---

## 4. OB Semantics (Local Extraction)

2. **HLR-20.031-002:** OB modules SHALL extract local meaning fragments from projected TP views using deterministic semantics.

3. **HLR-20.031-003:** OB semantics SHALL define:

- **visible vs suppressed:** deterministic projection boundaries per OB
- **ΔH% contribution rules:** deterministic contribution and missing-mass per OB output
- **evidence field structure:** canonical, typed evidence fields per OB
- **projection semantics:** deterministic mapping from TP semantic fields to lane-local representations
- **noisy input:** spelling-independent concept mapping without invented content (20.17 MI_NOISE)

---

## 5. TB Semantics (Interpretation)

4. **HLR-20.031-004:** TB modules SHALL produce deterministic interpretation fields from OB and TP/MTP evidence without latent, opaque state mutation.

5. **HLR-20.031-005:** TB semantics SHALL include: stance, affect, intent, logic, and social interpretation channels.

6. **HLR-20.031-006:** Each interpretation SHALL be explicit, auditable, and attributable to deterministic input evidence. Affect tagging SHALL NOT auto-resolve vagueness or contradiction (20.17).

---

## 6. IB Semantics (Inquiry Evolution)

7. **HLR-20.031-007:** IB semantics SHALL define deterministic inquiry evolution across cycles.

8. **HLR-20.031-008:** IB semantics SHALL include:

- ΔH% evolution and uncertainty change tracking
- explicit inquiry lifecycle state
- evidence accumulation and conflict tracking
- split/merge semantics at supervisory-safe boundaries
- promotion/retirement criteria and transitions

---

## 7. COB Semantics (Conversation Identity)

9. **HLR-20.031-009:** COB semantics SHALL define conversation-level deterministic identity and lifecycle behavior.

10. **HLR-20.031-010:** COB semantics SHALL include: identity, lineage, compaction, replay, and promotion/deprecation transitions.

---

## 8. MCS Semantics (Meaningful Cognitive Step)

A Meaningful Cognitive Step (MCS) is a logged, attributable, state-changing transition advancing the task toward a declared success condition.

MCS semantics SHALL require each counted step to be: logged, attributable, state-changing, and success-path aligned.

MCS semantics SHALL prohibit: micro-step inflation, repeated artifacts, and formatting-only steps.

## 9. Dual-Pipeline Semantic Boundary

**Not part of meaning semantics** (defined elsewhere):

| Artifact | Authority |
|----------|-----------|
| `exec_plan`, realization triples | 20.20, 20.12 |
| `exec_trace`, `imr_record` | 20.45 |
| `supervisory`, GB caps/modes | 20.16, 20.80 |
| Seed-driven expression selection | 20.12-010, 20.160 |

11. **HLR-20.031-019:** Seed variability SHALL affect expression/realization only; seed SHALL NOT alter propositions, stance, goals, basin routing, Thought Router derivation, or messy-input classification in `semantic_core`.

---

## 10. Deterministic Replay Semantics

12. **HLR-20.031-020:** Pipeline A meaning replay SHALL be 100% deterministic for identical `(input, prior_MTP, policy_signature)` tuples across InB, RB, OB, TB, ΔH%, merging, truth/done, and MTP update stages.

13. **Replay equivalence (dual-pipeline):** Stripping `exec_plan` and `exec_trace` from a full trace SHALL yield `semantic_core` identical to Pipeline A-only replay for the same inputs before approved Type B IMR corrections (HLR-20.012-011, [20.36](20.36_canonical_end_to_end_trace.md)).

14. **Full-trace reproducibility:** Complete traces SHALL reproduce from `(input, MTP state, seed, routing_epoch_id, policy_signature)` with all material **meaning** decisions logged with deterministic ordering and rationale codes.

---

## 11. Deterministic Policy Enforcement Semantics

All policy constraints SHALL be enforced deterministically at RB/TB safe boundaries with zero unlogged violations.

Policy enforcement outcomes SHALL be logged with deterministic reason codes and replayable evidence.

## 12. IB Lifecycle Precedence

Cross-document precedence for IB lifecycle content:

1. **20.31** defines meaning of IB fields and states.
2. **20.34** defines governance, control boundaries, and lifecycle transition authority.
3. **20.35** defines operational realization.

If conflicts occur, semantic definitions in 20.31 override 20.34 and 20.35.

## 13. TR Dirty-Flag Semantics

The TP-local `tr_needs_update` field SHALL govern TR recomputation lifecycle. Module placement and TR field integration defer to [20.37_thought_router_tr_specification.md](20.37_thought_router_tr_specification.md) where overlapping; lifecycle rules below are authoritative for semantics.

| Rule | Semantics |
|------|-----------|
| Type | boolean only |
| Initialization | each new TP: `tr_needs_update = true` |
| Stale | `true` → TP.TR requires recompute |
| Fresh | `false` → TP.TR current for present semantic context |
| Writers | any semantic writer modifying semantic-relevant TP fields SHALL set `true` |
| MTP context | modules mutating TP from MTP context SHALL set `true` |
| Clear | TR sets `false` only after successful recompute and commit |
| Failure | TR reject/error leaves `true` |
| Execution | TR SHALL NOT run when `false` |
| Routing | RB routes to TR iff `tr_needs_update = true` |

## Semantic Core Snapshot (minimum reference)

```text
semantic_core {
  mtp_snapshot_id,
  propositions[],          // canonical sort by proposition_id
  stance{},
  affect{},
  intent{},
  delta_h{},               // Q32.32 per 20.95
  lineage[],               // canonical (module_id, tp_seq, lineage_seq)
  semantic_tags[],
  truth_hypotheses{          // map/list sorted by hypothesis_id
    hypothesis_id,
    proposition_ref,
    truth_status,            // e.g. OPEN | SUPPORTED | REFUTED | UNKNOWN
    confidence_q32,          // Q32.32
    evidence_refs[],         // canonical sort
    last_updated_cycle
  },
  done_state{},
  stability_metadata{},
  overflow_metadata{},
  thought_router_fields{},
  messy_input_record?,     // 20.17 when applicable
  policy_signature
}
```

## Verification Focus

- Strip replay: `semantic_core` unchanged by Pipeline B except via approved Type B A-cycle writes
- Messy-input tags survive overflow and realization (20.36 Class 2/5)
- TP carries no execution-layer fields
- ΔH% and lineage ordering stable under golden fixture diff
- Seed changes do not alter `semantic_core` in Class 1 fixtures
- `semantic_tags[]` contain no execution-layer identifiers
- `truth_hypotheses` canonical sort stable across replay
