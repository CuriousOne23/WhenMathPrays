# 20.105 TP Requirements (v0.6 — Architecture-Aligned)

**Document ID:** 20.105  
**Version:** 0.6  
**Date:** 2026-06-12  
**Status:** Updated v0.6 — Architecture-Aligned (Pipeline A Only)

## Purpose

Defines deterministic **Thought Packet (TP)** structure, lifecycle, field authority, trajectory geometry persistence, and audit invariants for **lane‑local meaning‑construction projections** within **Pipeline A**.

**Normative definition (HLR‑20.105‑046):** TP is the **minimal deterministic state‑carrying artifact** exchanged across Pipeline A module boundaries — the per‑step, per‑lane working unit that records basin inputs/outputs, routing context, trajectory geometry, and **append‑only historical evidence** (`lineage_log[]`, `tp_audit_log[]`) without becoming a second authoritative meaning store.

TP projects MTP / `semantic_core` meaning into lane‑local form for OB, RB, TR, DCB, and Merge.  
**TB, IB, Truth/Done, and all Path‑B semantics are out of scope for Pipeline A and SHALL NOT appear on TP.**

Authoritative meaning commits only at Merge / `mtp_update`.

This module SHALL NOT weaken invariants in 20.12.

## 2. TP as Lane‑Local Projection

TP SHALL represent the canonical per-step meaning-construction unit exchanged across deterministic Pipeline A boundaries (HLR-20.105-001).

| Store | Authority |
|-------|-----------|
| **MTP / `semantic_core`** | Authoritative cross-lane meaning, truth/done commitment, messy-input record |
| **TP** | Lane-local working projection: evidence, TR block, routing context, trajectory geometry, pre-merge interpretation fragments |

TP SHALL carry lane-specific views of propositions refs, ΔH%, suppression markers, routing context, and basin outputs (20.31-012). TP SHALL NOT duplicate authoritative `semantic_core` fields as a second source of truth.

Lane TPs merge into MTP per 20.30 §3.6; post-merge authoritative fields SHALL commit through Merge and `mtp_update`, not through stale TP copies.

### 2.1 Safe Boundary (Normative Dependency)

A **safe boundary** is a deterministic cycle point where supervisory annotations, finalization markers, split/merge commits, and GB-approved flow-control directives MAY be applied without interleaving active unsafeguarded basin mutations (20.30 HLR-20.030-304, 20.130-010).

For TP, safe boundaries include at minimum: post-Merge pre-`mtp_update`, RB blocked-relation enforcement points (20.30-304–310), and GB-approved TS→GB→TS annotation windows (HLR-20.105-009). Runtime invariants SHALL be enforced at every safe boundary per HLR-20.010-075.

TP `safe_boundary_marker` and `blocked_relation_log` entries SHALL be written only at safe boundaries — never mid-basin unsafeguarded mutation.

## 3. TP Field Model (Normative Minimum)

### 3.1 Identity block (immutable after creation)

```text
tp_identity {
  tp_id,
  tp_seq,                   // monotonic within sequence domain
  cycle_id,
  lane_id,
  parent_tp_id?,
  schema_version,           // TP wire/schema version
  profile_signature,        // bound runtime profile
  wire_map_version,         // serialization map version
  policy_signature,         // bound policy for replay
  timestamp_evidence?       // metadata only — NOT ordering authority
}
```

Identity block fields SHALL be immutable after TP creation (HLR‑20.105‑004, HLR‑20.105‑047).  
Versioning fields SHALL be present on every TP for deterministic replay validation.

---

### 3.2 Lineage log (append‑only, separate from identity)

```text
lineage_log[] {             // append-only; NOT part of identity block
  lineage_seq,
  module_id,
  event_type,               // CREATE | SPLIT | MERGE | UPDATE | RETIRE
  parent_ref?,
  child_refs[]?,            // canonical sort by stable ID
  partition_rationale_ref?,
  merge_contribution_ref?
}
```

Lineage extensions SHALL append only to `lineage_log[]` (HLR‑20.105‑048).  
Split/merge markers SHALL reference lineage entries and SHALL NOT mutate `tp_identity`.

---

### 3.3 Working projection fields

```text
tp_lane_projection {
  tp_identity,              // immutable block above
  lineage_log[],            // append-only

  // Thought Router (lane-local)
  TP.TR{},                  // TR routine exclusive writer
  tr_needs_update,          // init true; semantic writers set true; TR clears on success
  input_fields{},           // OB TR-input / evidence context
  routing_metadata{},       // RB routing context; not DCB derivation input

  // Trajectory geometry (DCB read set — §4)
  step_index,
  trajectory_position{},
  trajectory_direction{},
  trajectory_curvature{},

  // ΔH% lane fields (entropy trajectory — §5)
  delta_h{},                // Q32.32 contribution, missing-mass, step trajectory

  // Basin outputs (lane-local, pre-merge)
  evidence_fields[]?,       // OB; canonical sort by evidence_id
  basin_affiliation?,

  // Stability / overflow (lane-local markers)
  stability_markers{},
  overflow_metadata?,

  // Supervisory annotations (safe-boundary only)
  safe_boundary_marker?,
  blocked_relation_log[]?,  // append-only; §8.2 schema

  // Intake-bound repair (Track H — §3.4; IIInB-only writes)
  input_segments[]?,
  input_repair_tags[]?,
  iiinb_escalation_refs[]?,

  // Audit (append-only)
  tp_audit_log[]            // §8.1 ordering rules
}
```

### 3.4 Intake‑bound repair fields (Track H — Normative Minimum)

```text
input_segment {
  segment_ref,
  segment_span_start,
  segment_span_end,
  segment_class,             // SHORTHAND_ELIGIBLE | LITERAL | UNKNOWN
  iiinb_event_id
}

input_repair_tag {
  segment_ref,
  repair_outcome,            // APPLIED | ESCALATED | SKIPPED | TRUNCATED
  rule_id?,
  resolved_segment_ref?,
  usp_version_ref,
  iiinb_event_id
}

iiinb_escalation_ref {
  escalation_id,
  segment_ref,
  iiinb_event_id,
  escalation_reason_code
}
```

Intake‑bound fields SHALL sort by `segment_ref` then `iiinb_event_id` before export/hash/replay diff.  
They SHALL NOT appear in `TP.TR`, `semantic_core`, or Merge‑authoritative meaning.

**Initialization:** new TP SHALL set `tr_needs_update = true` (20.37).  
TP creation SHALL initialize mandatory identity, core, and audit fields deterministically (HLR‑20.105‑013).

**Forbidden TP fields (HLR‑20.105‑032, ‑053, ‑054):**  
`routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, `imr_record`, `gb_cap_record`,  
`gb_supervisory_mode`, `exec_plan`, `exec_trace`, DCB `directional_change_events`,  
**truth_hypotheses**, **done_state**, and **all truth/done fragments**.

No Path‑B fields SHALL appear on TP.

## 4. Trajectory Geometry (DCB Cross‑Reference)

TP SHALL persist **geometric** trajectory fields consumed by DCB (HLR‑20.105‑027, 20.106 §3) —  
distinct from ΔH% entropy trajectory fields in §5.

| Field | Semantics |
|-------|-----------|
| `trajectory_position` | TP coordinate in trajectory space at `step_index` |
| `trajectory_direction` | Geometric tangent at observation step |
| `trajectory_curvature` | Rate of change of direction vector along trajectory |
| `step_index` | Deterministic step ordinal within lane/cycle context |

Geometry fields SHALL be updated during deterministic Pipeline‑A cycle transitions.  
Numeric encoding SHALL follow 20.95 (Q32.32 canonical).

**Writers:** Pipeline‑A trajectory persistence (deterministic step advance).  
**Readers:** DCB (read‑only).  
OB, TR, DCB, and Pipeline B SHALL NOT write trajectory geometry fields.

Multi‑step DCB observation SHALL use consecutive persisted TP instances.  
MTP trajectory‑projection stitching fields are defined in 20.106.

TP SHALL NOT persist DCB directional‑change events; events are ephemeral TR inputs  
recomputed from geometry on replay (20.106‑014, HLR‑20.105‑053).

---

### 4.1 Geometric vs entropy trajectory (comparison)

| Aspect | Geometric trajectory (§4) | Entropy trajectory — ΔH% (§5) |
|--------|---------------------------|-------------------------------|
| **Purpose** | DCB curvature/direction observation | Missing‑mass and entropy accounting |
| **Primary consumer** | DCB (read‑only) | OB, Merge, regulators (via MTP) |
| **TP fields** | `trajectory_position`, `trajectory_direction`, `trajectory_curvature`, `step_index` | `delta_h.contribution_q32`, `missing_mass_q32`, `step_delta_q32`, `cumulative_q32?` |
| **Numeric type** | Q32.32 canonical | Q32.32 canonical |
| **Writers** | Pipeline‑A trajectory persistence | OB / basin modules / Merge |
| **Replay** | Recomputable from consecutive TP geometry | Recomputable from lane evidence + policy |
| **Cross‑ref** | 20.106 | 20.31, 20.40, 20.90 |

## 5. ΔH% Lane Fields

## 5. ΔH% Lane Fields (Entropy Trajectory)

TP `delta_h{}` SHALL carry lane-local **entropy trajectory** fields (HLR-20.105-051) — not DCB geometric trajectory (§4):

```text
delta_h {
  contribution_q32,       // lane ΔH% contribution this step (Q32.32)
  missing_mass_q32,         // unresolved missing mass (Q32.32)
  step_delta_q32,           // per-cycle step contribution
  cumulative_q32?           // optional bounded cumulative marker
}
```

Semantics defer to [20.31](20.31_semantic_specification.md) (ΔH% / missing-mass), OB contribution rules ([20.40](20.40_ob_requirements.md)), Merge reconciliation ([20.130](20.130_splitting_and_merging_requirements.md)), and limit enforcement ([20.90](20.90_ts_parameter_table.md) §B). Numeric fields SHALL use canonical Q32.32 per 20.95.
