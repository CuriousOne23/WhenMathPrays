# 20.105 TP Requirements

**Document ID:** 20.105  
**Version:** 0.5  
**Date:** 2026-06-07  
**Status:** Approved v0.5 — Track H Stage 3 intake-bound repair tags (2026-06-07; CuriousOne23, Copilot, Grok)

## Purpose

Defines deterministic **Thought Packet (TP)** structure, lifecycle, field authority, trajectory geometry persistence, and audit invariants for **lane-local meaning-construction projections** within **Pipeline A**.

**Normative definition (HLR-20.105-046):** TP is the **minimal deterministic state-carrying artifact** exchanged across Pipeline A module boundaries — the per-step, per-lane working unit that records basin inputs/outputs, routing context, trajectory geometry, and **append-only historical evidence** (`lineage_log[]`, `tp_audit_log[]`) without becoming a second authoritative meaning store.

TP projects MTP / `semantic_core` meaning into lane-local form for OB, RB, TR, TB, DCB, Merge, and Truth/Done processing (20.31-012). Authoritative meaning commits only at Merge / `mtp_update`. TP retains lane-local history for replay and provenance; MTP retains authoritative aggregated meaning.

This module SHALL NOT weaken invariants in [20.12_ts_invariants.md](20.12_ts_invariants.md).

**Integration contract:** TR field authority per [20.37](20.37_thought_router_tr_specification.md); trajectory geometry consumption per [20.106](20.106_dcb_requirements.md) §4; split/merge lineage per [20.130](20.130_splitting_and_merging_requirements.md); prototype alignment per [20.39](20.39_ts_core_data_structures.md) `TpLaneView`.

**Semantic authority:** lane-local field semantics defer to [20.31](20.31_semantic_specification.md) §2; numeric encoding per [20.95](20.95_ts_numeric_policy.md).

| Concern | TP posture |
|---------|------------|
| `semantic_core` / MTP | TP **projects** meaning; authoritative commit at `mtp_update` only |
| `TP.TR`, `tr_needs_update` | Lane-local; TR routine exclusive `TP.TR` writer (20.37) |
| `exec_plan`, `exec_trace` | **SHALL NOT appear on TP** (20.31-013, 20.39-018) |
| `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id` | **SHALL NOT appear on TP** |
| `imr_record`, GB cap/mode records | **SHALL NOT appear on TP** — supervisory envelope only |
| `truth_hypotheses`, `done_state` | **Not authoritative on TP**; only TB lane-local pre-merge `channel_interpretations{}` / hypothesis fragments — no partial or provisional authoritative truth records (HLR-20.105-054) |
| DCB `directional_change_events` | **SHALL NOT be stored on TP** — ephemeral TR inputs only (20.106-014, HLR-20.105-053) |
| Seed | **SHALL NOT influence** TP field derivation (HLR-20.012-010) |

**Pipeline B forbidden:** OuB, OpBeh/OBG/XlateR, IMR, SRP SHALL NOT write TP fields or retroactively mutate lane-local Pipeline A projections.

## 2. TP as Lane-Local Projection

TP SHALL represent the canonical per-step meaning-construction unit exchanged across deterministic Pipeline A boundaries (HLR-20.105-001).

| Store | Authority |
|-------|-----------|
| **MTP / `semantic_core`** | Authoritative cross-lane meaning, truth/done commitment, messy-input record |
| **TP** | Lane-local working projection: evidence, TR block, routing context, trajectory geometry, pre-merge interpretation fragments |

TP SHALL carry lane-specific views of propositions refs, ΔH%, suppression markers, routing context, and basin outputs (20.31-012). TP SHALL NOT duplicate authoritative `semantic_core` fields as a second source of truth.

Lane TPs merge into MTP per 20.30 §3.6; post-merge authoritative fields SHALL commit through Merge and `mtp_update`, not through stale TP copies.

### 2.1 Safe Boundary (Normative Dependency)

A **safe boundary** is a deterministic cycle point where supervisory annotations, finalization markers, split/merge commits, and GB-approved flow-control directives MAY be applied without interleaving active unsafeguarded basin mutations (20.30 HLR-20.030-304, 20.130-010).

For TP, safe boundaries include at minimum: post-Merge pre-`mtp_update`, RB blocked-relation enforcement points (20.30-304–310), and GB-approved TS→GB→TS annotation windows (HLR-20.105-009). Runtime invariants SHALL be enforced at every safe boundary per HLR-20.010-075.

TP `safe_boundary_marker` and `blocked_relation_log` entries SHALL be written only at safe boundaries — never mid-basin unsafeguarded mutation.

## 3. TP Field Model (Normative Minimum)

### 3.1 Identity block (immutable after creation)

```text
tp_identity {
  tp_id,
  tp_seq,                   // monotonic within sequence domain
  cycle_id,
  lane_id,
  parent_tp_id?,
  schema_version,           // TP wire/schema version
  profile_signature,        // bound runtime profile
  wire_map_version,         // serialization map version
  policy_signature,         // bound policy for replay
  timestamp_evidence?       // metadata only — NOT ordering authority
}
```

Identity block fields SHALL be immutable after TP creation (HLR-20.105-004, HLR-20.105-047). Versioning fields SHALL be present on every TP for deterministic replay validation.

### 3.2 Lineage log (append-only, separate from identity)

```text
lineage_log[] {             // append-only; NOT part of identity block
  lineage_seq,
  module_id,
  event_type,               // CREATE | SPLIT | MERGE | UPDATE | RETIRE
  parent_ref?,
  child_refs[]?,            // canonical sort by stable ID
  partition_rationale_ref?,
  merge_contribution_ref?
}
```

Lineage extensions SHALL append only to `lineage_log[]` (HLR-20.105-048). Split/merge markers (`split_child_markers[]`, `merge_source_markers[]`) SHALL reference `lineage_log` entries — they SHALL NOT mutate `tp_identity` fields.

### 3.3 Working projection fields

```text
tp_lane_projection {
  tp_identity,              // immutable block above
  lineage_log[],            // append-only

  // Thought Router (lane-local)
  TP.TR{},                  // TR routine exclusive writer
  tr_needs_update,          // init true; semantic writers set true; TR clears on success
  input_fields{},           // OB TR-input / evidence context
  routing_metadata{},       // RB routing context; not DCB/Truth-Done derivation input

  // Trajectory geometry (DCB read set — §4)
  step_index,
  trajectory_position{},
  trajectory_direction{},
  trajectory_curvature{},

  // ΔH% lane fields (entropy trajectory — §5)
  delta_h{},                // Q32.32 contribution, missing-mass, step trajectory

  // Basin outputs (lane-local, pre-merge)
  evidence_fields[]?,       // OB; canonical sort by evidence_id
  channel_interpretations{}?, // TB pre-merge lane output
  basin_affiliation?,

  // Stability / overflow (lane-local markers)
  stability_markers{},
  overflow_metadata?,

  // Supervisory annotations (safe-boundary only)
  safe_boundary_marker?,
  blocked_relation_log[]?,  // append-only; §8.2 schema

  // Intake-bound repair (Track H — §3.4; IIInB-only writes)
  input_segments[]?,
  input_repair_tags[]?,
  iiinb_escalation_refs[]?,

  // Audit (append-only)
  tp_audit_log[]            // §8.1 ordering rules
}
```

### 3.4 Intake-bound repair fields (Track H — Normative Minimum)

Pre-routing intake evidence written by IIInB only ([20.101](20.101_iiinb_requirements.md); [20.510](20.510_refactoring_for_input_correction_track_h.md) Stage 3).

```text
input_segment {
  segment_ref,
  segment_span_start,
  segment_span_end,
  segment_class,             // SHORTHAND_ELIGIBLE | LITERAL | UNKNOWN
  iiinb_event_id
}

input_repair_tag {
  segment_ref,
  repair_outcome,            // APPLIED | ESCALATED | SKIPPED | TRUNCATED
  rule_id?,
  resolved_segment_ref?,
  usp_version_ref,
  iiinb_event_id
}

iiinb_escalation_ref {
  escalation_id,
  segment_ref,
  iiinb_event_id,
  escalation_reason_code
}
```

Intake-bound fields SHALL sort by `segment_ref` lexicographic primary, then `iiinb_event_id`, before export/hash/replay diff. They SHALL NOT appear in `TP.TR`, `semantic_core`, or Merge-authoritative meaning.

**Initialization:** new TP SHALL set `tr_needs_update = true` (20.37). TP creation SHALL initialize mandatory identity, core, and audit fields with deterministic defaults (HLR-20.105-013).

**Forbidden TP fields (HLR-20.105-032, HLR-20.105-053, HLR-20.105-054):** `routing_epoch_id`, `opbeh_id`, `obg_id`, `xlater_id`, `imr_record`, `gb_cap_record`, `gb_supervisory_mode`, `exec_plan` refs, `exec_trace` refs, DCB `directional_change_events`, authoritative `truth_hypotheses`, authoritative `done_state`, and partial/provisional truth-hypothesis records except TB lane-local pre-merge outputs in `channel_interpretations{}`.

## 4. Trajectory Geometry (DCB Cross-Reference)

TP SHALL persist **geometric** trajectory fields consumed by DCB (HLR-20.105-027, 20.106 §3) — distinct from ΔH% entropy trajectory fields in §5.

| Field | Semantics |
|-------|-----------|
| `trajectory_position` | TP coordinate in trajectory space at `step_index` |
| `trajectory_direction` | Geometric tangent at observation step |
| `trajectory_curvature` | Rate of change of direction vector along trajectory |
| `step_index` | Deterministic step ordinal within lane/cycle context |

Geometry fields SHALL be updated during deterministic Pipeline A cycle step transitions. When numeric values are persisted, encoding SHALL follow [20.95](20.95_ts_numeric_policy.md) (HLR-20.105-034).

**Writers:** Pipeline A trajectory persistence (deterministic step advance). **Readers:** DCB (read-only). OB, TB, TR, DCB, and Pipeline B SHALL NOT write trajectory geometry fields (20.106).

Multi-step DCB observation SHALL use consecutive persisted TP instances; MTP trajectory-projection stitching fields are defined in 20.106, not authoritative meaning on TP.

TP SHALL NOT persist DCB directional-change events; events are ephemeral TR inputs recomputed from trajectory on replay (20.106-014, HLR-20.105-053).

### 4.1 Geometric vs entropy trajectory (comparison)

| Aspect | Geometric trajectory (§4) | Entropy trajectory — ΔH% (§5) |
|--------|---------------------------|-------------------------------|
| **Purpose** | DCB curvature/direction observation | Missing-mass and entropy accounting |
| **Primary consumer** | DCB (read-only) | OB, Merge, regulators, Truth/Done (via MTP) |
| **TP fields** | `trajectory_position`, `trajectory_direction`, `trajectory_curvature`, `step_index` | `delta_h.contribution_q32`, `missing_mass_q32`, `step_delta_q32`, `cumulative_q32?` |
| **Numeric type** | Q32.32 when persisted (20.95) | Q32.32 canonical (20.95) |
| **Writers** | Pipeline A trajectory persistence | OB / basin modules / Merge |
| **Replay** | Recomputable from consecutive TP geometry | Recomputable from lane evidence + policy |
| **Cross-ref** | [20.106](20.106_dcb_requirements.md) | [20.31](20.31_semantic_specification.md), [20.40](20.40_ob_requirements.md), [20.90](20.90_ts_parameter_table.md) §B |

## 5. ΔH% Lane Fields (Entropy Trajectory)

TP `delta_h{}` SHALL carry lane-local **entropy trajectory** fields (HLR-20.105-051) — not DCB geometric trajectory (§4):

```text
delta_h {
  contribution_q32,       // lane ΔH% contribution this step (Q32.32)
  missing_mass_q32,         // unresolved missing mass (Q32.32)
  step_delta_q32,           // per-cycle step contribution
  cumulative_q32?           // optional bounded cumulative marker
}
```

Semantics defer to [20.31](20.31_semantic_specification.md) (ΔH% / missing-mass), OB contribution rules ([20.40](20.40_ob_requirements.md)), Merge reconciliation ([20.130](20.130_splitting_and_merging_requirements.md)), and limit enforcement ([20.90](20.90_ts_parameter_table.md) §B). Numeric fields SHALL use canonical Q32.32 per 20.95.

## 7. Identity, Sequence, and Lifecycle

- Every TP SHALL include stable identity fields per §3.1, including `schema_version`, `profile_signature`, and `wire_map_version` (HLR-20.105-002, HLR-20.105-047)
- `tp_seq` SHALL be monotonic within the configured deterministic sequence domain and SHALL preserve FIFO interpretation order (HLR-20.105-003)
- `tp_identity` fields SHALL be immutable after creation; lineage continuity SHALL extend only via append-only `lineage_log[]` (HLR-20.105-004, HLR-20.105-048)
- Timestamps SHALL be evidence metadata only; ordering authority SHALL derive from `tp_seq`, `cycle_id`, and canonical sequence tokens — **not** wall-clock time (HLR-20.105-018)
- TP SHALL NOT permit nondeterministic mutation of finalized projection fields once `safe_boundary_marker.finalized = true` (HLR-20.105-014)
- Lifecycle transitions SHALL be logged in append-only `tp_audit_log` (HLR-20.105-024)

**COB promotion (HLR-20.105-015):** TP promotion to COB-visible conversation-object semantics SHALL occur only through approved deterministic lifecycle pathways per [20.31](20.31_semantic_specification.md) §7 (COB) and 20.30 HLR-20.030-293. Minimum preconditions: valid `tp_identity`, complete `lineage_log[]`, Merge-committed `semantic_core` snapshot ref, and `policy_signature` binding. Promotion is **not reversible** at TP layer — deprecation SHALL follow COB retirement semantics only.

**Creation-order independence (HLR-20.105-040):** TP field derivation and basin outputs SHALL NOT depend on TP allocation order, heap/container address identity, or creation sequence except through explicit canonical fields (`tp_id`, `tp_seq`, `lane_id`).

## 8. Split / Merge Lineage

TP merge/split lineage markers SHALL preserve deterministic parent/child provenance continuity (HLR-20.105-017).

Split-derived lane TPs SHALL retain `parent_tp_id` and append `lineage_log` entries with `event_type = SPLIT` and `partition_rationale_ref` (20.130). Merge-target TPs SHALL append `event_type = MERGE` entries with `merge_contribution_ref`.

Split and merge operations SHALL NOT introduce inference, hallucinated reconstruction, or meaning invention beyond explicit source fields (20.130-006). Detailed split/merge algorithms are normative in 20.130; TP obligations here are lineage and audit preservation only.

## 9. Audit, Supervisory Annotations, Retention, and Reject Records

### 9.1 Audit log ordering (HLR-20.105-049)

`tp_audit_log[]` entries SHALL sort before export/hash/replay diff by composite key, in precedence order:

1. `cycle_id` (ascending)
2. `tp_seq` (ascending)
3. `audit_seq` (ascending, monotonic per TP)
4. `reason_code` (lexicographic tie-break)

`timestamp_evidence`, when present, SHALL NOT override this ordering.

### 9.2 Blocked-relation log schema (HLR-20.105-008)

```text
blocked_relation_entry {
  block_id,                 // stable deterministic ID
  obx_class,
  oby_class,
  rbxy_id,
  reason_code,              // immutable dictionary ID
  policy_signature_ref,
  cycle_id,
  tp_seq,
  audit_seq,
  safe_boundary_marker_ref
}
```

`blocked_relation_log[]` SHALL sort by `(cycle_id, tp_seq, audit_seq, reason_code)` before export/hash (HLR-20.105-049). Reason codes SHALL map through immutable versioned dictionaries (HLR-20.105-012).

### 9.3 Reject-with-audit schema (HLR-20.105-050)

When TP rejects unsupported schema, enum, profile, or wire-map states (HLR-20.105-019):

```text
tp_reject_record {
  reject_id,
  reject_class,             // SCHEMA | ENUM | PROFILE | WIRE_MAP
  reason_code,              // deterministic dictionary ID
  observed_schema_version?,
  observed_profile_signature?,
  observed_wire_map_version?,
  policy_signature_ref,
  cycle_id,
  tp_seq,
  evidence_fields{}         // minimal observed-state snapshot
}
```

Reject records SHALL append to `tp_audit_log` with `event_type = REJECT` and SHALL NOT partially mutate `tp_identity` or finalized projection fields.

### 9.4 Zero-event windows (HLR-20.105-052)

When a cycle produces **no basin mutations** for a lane (zero-event window):

- TS MAY emit a **synthetic continuity TP** with `event_type = ZERO_EVENT` in `tp_audit_log`
- `tp_seq` SHALL still increment monotonically for the lane sequence domain
- No new `evidence_fields[]` or basin outputs are required
- `tp_audit_log` SHALL carry fixed reason code `TP_ZERO_EVENT_WINDOW` or canonical empty-evidence marker per policy
- Zero-event windows SHALL NOT skip `tp_seq` values or reorder FIFO interpretation order

### 9.5 Retention and replay horizon

Retention and compaction SHALL be bounded by deterministic policy and **replay-horizon** semantics per [20.115](20.115_mtp_requirements.md) HLR-20.115-018 and 20.30 functional retention rules (HLR-20.105-016). Replay horizon is **profile-bound** via `profile_signature` — not wall-clock derived.

- TP SHALL maintain append-only audit invariants; existing audit entries SHALL NOT be overwritten or deleted in-place (HLR-20.105-010)
- Supervisory annotations on TP SHALL occur only through approved deterministic TS→GB→TS pathways at safe boundaries (HLR-20.105-009)

## 10. Canonical Ordering and Serialization

**Canonical ordering (HLR-20.105-038):** `lineage_log[]`, `evidence_fields[]`, nested ID arrays, `tp_audit_log[]`, and `blocked_relation_log[]` SHALL sort per §9.1/§9.2 before export, hash, and replay diff.

`TP.TR` nested maps SHALL sort per [20.37](20.37_thought_router_tr_specification.md) HLR-20.037-064: stable `hint_id` lexicographic primary sort; nested ID arrays lexicographic; numeric weights canonical Q32.32. `routing_metadata` nested arrays SHALL use stable-ID lexicographic sort.

TP export manifests SHALL use deterministic key ordering and canonical serialization (HLR-20.105-023).

Numeric TP fields SHALL use canonical Q32.32; −0→+0 before comparison and export (HLR-20.105-034).

---

## 11. Determinism and Replay

- TP core-field updates SHALL be deterministic, schema-versioned, auditable, and reproducible for identical effective state (HLR-20.105-006)
- TP SHALL preserve platform-independent deterministic behavior under equivalent input, `profile_signature`, and `policy_signature` state (HLR-20.105-020)
- TP field outputs SHALL reproduce from `(lane input, MTP projection, policy_signature)` — **seed excluded** (HLR-20.105-035)
- Strip replay removing Pipeline B envelopes SHALL preserve TP-merged meaning in `semantic_core` (20.36 Class 1, HLR-20.105-036)
- TP processing SHALL remain bounded (HLR-20.105-021)
- Unsupported schema/profile/wire-map states SHALL emit `tp_reject_record` per §9.3 — never silent accept (HLR-20.105-019, HLR-20.105-050)

## Normative Requirements

1. HLR-20.105-001: TP SHALL represent the canonical per-step meaning-construction unit exchanged across deterministic Pipeline A boundaries.
2. HLR-20.105-002: Every TP SHALL include stable identity fields including `tp_id`, `tp_seq`, `cycle_id`, `lane_id`, `schema_version`, `profile_signature`, `wire_map_version`, `policy_signature`, lineage identifiers, and parent pointers.
3. HLR-20.105-003: TP `tp_seq` SHALL be monotonic within the configured deterministic sequence domain and SHALL preserve FIFO interpretation order.
4. HLR-20.105-004: TP `tp_identity` block fields SHALL be immutable after creation; lineage continuity SHALL extend only through append-only `lineage_log[]` entries.
5. HLR-20.105-005: TP core fields SHALL include lane-local OB outputs, RB routing context, TB interpretation fragments, ΔH% lane fields (`delta_h{}`), geometric trajectory fields (§4), and bounded stability markers.
6. HLR-20.105-006: TP core-field updates SHALL be deterministic, schema-versioned, auditable, and reproducible for identical effective state.
7. HLR-20.105-007: TP supervisory annotation fields SHALL include safe-boundary markers, policy-enforcement markers, and blocked-relation logs — not full GB supervisory envelope records.
8. HLR-20.105-008: TP `blocked_relation_log` entries SHALL conform to §9.2 minimum schema and SHALL record OBx class, OBy class, RBxy identifier, policy reason code, and `tp_seq`/`cycle_id` evidence.
9. HLR-20.105-009: TP supervisory annotations SHALL occur only through approved deterministic TS→GB→TS supervisory pathways at safe boundaries per §2.1.
10. HLR-20.105-010: TP SHALL maintain append-only audit invariants; existing audit entries SHALL NOT be overwritten or deleted in-place.
11. HLR-20.105-011: TP audit records SHALL be deterministic, bounded, replayable, and serialized with canonical field ordering per §9.1.
12. HLR-20.105-012: TP reason codes SHALL use immutable identifiers with deterministic versioned dictionary mapping behavior.
13. HLR-20.105-013: TP creation SHALL initialize all mandatory identity, core, and audit fields with deterministic defaults; new TP SHALL initialize `tr_needs_update = true`.
14. HLR-20.105-014: TP SHALL NOT permit nondeterministic mutation of previously finalized projection fields once `safe_boundary_marker.finalized = true`.
15. HLR-20.105-015: TP promotion to COB-visible conversation-object semantics SHALL occur only through approved deterministic lifecycle pathways per 20.31 §7 and 20.30-293; promotion requires Merge-committed `semantic_core` ref and is not reversible at TP layer.

## Functional Boundaries

- **TP:** minimal deterministic state carrier for lane-local identity (`tp_identity`), append-only `lineage_log`, basin I/O projections, TR block, geometric + ΔH% trajectory fields, intake-bound repair evidence (§3.4), and audit evidence. TP does not own authoritative meaning — only working projections until Merge/`mtp_update`.
- **IIInB:** sole writer of `input_segments[]`, `input_repair_tags[]`, and `iiinb_escalation_refs[]`; no `TP.TR` or `semantic_core` writes.
- **MTP / `semantic_core`:** authoritative aggregated meaning, truth/done commitment, messy-input record, and post-merge TR projection. MTP owns replay-horizon retention policy that governs how long TP audit artifacts remain addressable.
- **DCB:** reads TP geometric trajectory only; emits ephemeral events never stored on TP; never writes TP fields (HLR-053).
- **RB:** writes `routing_metadata`; enforces blocked-relation logs at safe boundaries; never writes `TP.TR`.
- **GB:** annotates TP only through safe-boundary pathways (`safe_boundary_marker`, `blocked_relation_log`); full supervisory state remains in `supervisory` envelope — never embedded as GB cap/mode records on TP.

## Conformance

Implementation conforms when:

- TP defined as minimal deterministic state carrier (HLR-046)
- `tp_identity` includes schema/profile/wire-map versions; immutable after creation
- lineage extends only via `lineage_log[]`; identity block never mutated
- audit/blocked-relation logs use §9.1/9.2 ordering
- reject events emit §9.3 schema
- `delta_h{}` distinct from geometric trajectory fields
- zero-event windows follow §9.4
- forbidden execution/supervisory fields absent from TP
- TR exclusive `TP.TR` writer; `tr_needs_update` lifecycle matches 20.37
- seed change does not alter TP meaning fields for fixed inputs
- no DCB events or partial truth_hypotheses on TP (HLR-053, HLR-054)
