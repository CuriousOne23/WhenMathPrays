## HLR/LLR Naming Normalization Policy

To keep requirement attachment consistent across modules, use the following naming policy.

### High-Level Requirements (HLR)

- Format: `HLR-{20.<DOCGROUP>-<NNN>}`
- `DOCGROUP` maps to the requirement document numeric band.
- `NNN` is a stable sequence number inside that requirement group.

Examples:

- `HLR-20.30-001` for TP identity and lifecycle requirements
- `HLR-20.30-002` for TP state and provenance requirements
- `HLR-20.30-003` for TP determinism and validation requirements

### Low-Level Requirements (LLR)

- Verification LLR format: `LLR-{30.<MODULE>-<NNN>}`
- Design LLR format: `LLR-{50.<MODULE>-<NNN>}`
- If mapping is provisional, use `LLR-?` and record remediation.

Examples:

- `LLR-30.20-001` for TP observability verification constraints
- `LLR-30.20-002` for TP lifecycle operation verification constraints
- `LLR-30.20-003` for TP determinism and negative-path verification constraints

### Run Record and Ledger Usage Rules

- Every test row must include at least one HLR and one LLR reference.
- Multiple IDs must be comma-separated.
- If mapping is unknown, use `HLR-?` / `LLR-?` and record remediation in module insights and updated requirements.
