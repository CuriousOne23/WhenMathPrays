# 20.36 Canonical End-to-End Trace

## Purpose
Defines a normative, deterministic trace fixture template for TS end-to-end conformance.

This document is normative and specifies the required shape of a valid trace.

This document is not run-derived evidence.

## Normative Boundary
1. HLR-20.036-001: This document SHALL define canonical trace shape requirements only.
2. HLR-20.036-002: Run-derived traces, logs, and implementation outputs SHALL be stored in 30-series verification documents.

## Canonical End-to-End Stage Order
3. HLR-20.036-003: A valid trace fixture SHALL preserve this deterministic stage order: input -> routing -> splitting -> OB processing -> TB interpretation -> Delta-H normalization -> merging -> truth/done evaluation -> MTP update -> output realization.

## Required Canonical Trace Fields
4. HLR-20.036-004: Every canonical fixture SHALL include execution_signature, input_packet_id, mtp_snapshot_id, and seed_scope marker fields.
5. HLR-20.036-005: Every stage record SHALL include stage_name, stage_seq, deterministic_reason_codes, and safe_boundary_marker fields.
6. HLR-20.036-006: Splitting and merging stage records SHALL include lineage_delta and Delta-H contribution/missing-mass fields.
7. HLR-20.036-007: OB/TB stage records SHALL include explicit evidence fields, interpretation fields, and suppression/visibility markers.
8. HLR-20.036-008: Truth/done stage records SHALL include truth_hypotheses update fields, done_state, and uncertainty accounting fields.
9. HLR-20.036-009: Overflow/degradation state, if present, SHALL include canonical overflow tags and deterministic degradation reason codes.
10. HLR-20.036-010: MCS markers, if counted in fixture context, SHALL be explicit, attributable, and non-inflated according to 20.31 semantics.
