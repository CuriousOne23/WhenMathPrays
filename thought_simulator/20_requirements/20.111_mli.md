## 1. Definition

**Meaning-Layer Inference (MLI)** is the subsystem responsible for deriving stable, context-grounded semantic interpretations from a stream of incoming symbolic or sub-symbolic representations. MLI operates between the raw token or event layer and the higher-order reasoning layer, acting as a structured translation boundary.

More precisely, MLI is defined as the process by which the Thought Simulator:

1. Accepts a set of **active representations** (tokens, embeddings, basin states, or primitive activations).
2. Applies **contextual grounding rules** to resolve ambiguity at the semantic surface.
3. Emits a **meaning assertion** — a typed, confidence-stamped semantic unit — that downstream components treat as authoritative within the current processing frame.

MLI is *not* a generative module. It does not create new semantic content. It selects, resolves, and validates the most coherent interpretation from an already-constructed candidate space.

> **Key distinction:** MLI performs *selection and validation*, not *generation*. Generation belongs to the Construction Layer (see `20.110_construction_layer.md`).

---

## 2. Purpose

MLI serves three primary purposes within the Thought Simulator architecture:

### 2.1 Ambiguity Resolution
Natural language and internal cognitive representations are inherently ambiguous. MLI provides a principled mechanism to converge on a single, tractable interpretation before passing state to downstream modules. Without MLI, ambiguous representations would fan out combinatorially, overwhelming Path B's sequential processing budget.

### 2.2 Semantic Stability Enforcement
MLI enforces *semantic stability* across a processing frame. Once a meaning assertion is emitted, it is treated as fixed within that frame unless an explicit revision event is raised (see [§5.4 Revision](#54-revision)). This prevents semantic drift — the gradual, uncontrolled shift in interpretation that can corrupt multi-step reasoning chains.

### 2.3 Grounding for Higher-Order Reasoning
All higher-order modules (planning, counterfactual simulation, narrative coherence checking) require grounded semantic inputs. MLI acts as the sole grounding authority for the current frame, providing those modules with a stable foundation on which to build.

## 3. Scope

### 3.1 In Scope

| Item | Notes |
|------|-------|
| Token-level semantic disambiguation | Lexical, referential, and structural ambiguity |
| Primitive-to-meaning mapping | Converting primitive activations to semantic assertions |
| Basin-state interpretation | Reading attractor states as coarse meaning carriers |
| Confidence scoring | Attaching a probability mass to each meaning assertion |
| Frame-local caching | Holding the active assertion set for the duration of one processing frame |
| Revision event handling | Responding to upstream correction signals |

### 3.2 Out of Scope

| Item | Handled By |
|------|-----------|
| New semantic content generation | Construction Layer (`20.110`) |
| Long-term memory storage of assertions | Episodic Store (`20.130`) |
| Cross-frame temporal reasoning | Narrative Coherence Module (`20.150`) |
| User-facing output formatting | Rendering Pipeline (`20.200`) |
| Raw tokenisation | Tokeniser (`10.010`) |

### 3.3 Scope Boundary Conditions

MLI's scope is bounded by **frame boundaries**. A frame begins when a new top-level input event is accepted and ends when Path B signals `FRAME_COMMIT` or `FRAME_ABORT`. MLI holds no persistent state across frame boundaries except for what is explicitly persisted by the Episodic Store.

## 4. Invariants

These invariants must hold at all times during MLI operation. A violation of any invariant constitutes a critical fault and must trigger `FRAME_ABORT`.

| ID | Invariant | Rationale |
|----|-----------|-----------|
| **INV-01** | Every active representation entering MLI must produce exactly one meaning assertion before the frame proceeds. | Prevents unresolved ambiguity from propagating downstream. |
| **INV-02** | A meaning assertion's confidence score must be in the range `(0.0, 1.0]`. A score of exactly `0.0` is invalid and must not be emitted. | A zero-confidence assertion is semantically equivalent to no assertion and must instead trigger revision. |
| **INV-03** | MLI must not modify the input representation it receives. | Ensures upstream modules can replay or audit the original signal without interference. |
| **INV-04** | The set of active assertions within a frame must be internally consistent. | No two assertions within the same frame may be direct logical contradictions. |
| **INV-05** | MLI must complete inference within the frame's allocated time budget. | If the budget is exceeded, MLI emits a `LOW_CONFIDENCE_FALLBACK` assertion and logs a budget violation event. |
| **INV-06** | Revision events may only reduce, not increase, the confidence of an existing assertion. | Prevents revision from being used as a confidence amplification mechanism. |
| **INV-07** | MLI must never emit an assertion that violates a registered safety boundary (see §8). | Safety is non-negotiable and takes priority over semantic coherence. |

## 5. Lifecycle

MLI follows a deterministic four-phase lifecycle within each processing frame.

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   INTAKE    │───▶│  RESOLUTION │───▶│  VALIDATION │───▶│   EMISSION  │
│             │    │             │    │             │    │             │
│ Accept reps │    │ Disambiguate│    │ Check INVs  │    │ Emit assert │
│ from stream │    │ & score     │    │ & safety    │    │ to Path B   │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
       ▲                                      │
       │               ┌──────────────────────┘ (if INV violation)
       │               ▼
       │        ┌─────────────┐
       └────────│   REVISION  │
                │             │
                │ Adjust or   │
                │ escalate    │
                └─────────────┘
```

### 5.1 Intake

MLI accepts a batch of active representations from the upstream queue. Representations arrive typed as one of:

- `PRIMITIVE` — output of a primitive activation (see §7.1)
- `BASIN_STATE` — a converged attractor state from the basin subsystem (see §7.2)
- `TOKEN_SEQUENCE` — a window of tokens with positional encoding
- `CROSS_MODAL` — multi-modal signals merged upstream of MLI

Each representation is enqueued in the **Intake Buffer**. The buffer is processed in priority order: `PRIMITIVE` > `BASIN_STATE` > `TOKEN_SEQUENCE` > `CROSS_MODAL`.

### 5.2 Resolution

For each representation in the Intake Buffer, MLI applies the following resolution pipeline:

1. **Candidate generation** — Enumerate all plausible semantic interpretations using the registered Grounding Rule Set.
2. **Contextual scoring** — Score each candidate against the current frame context (prior assertions, active basin configuration, task goal vector).
3. **Selection** — Select the highest-scoring candidate that does not violate any invariant or safety boundary.
4. **Confidence assignment** — Assign a confidence score derived from the margin between the top candidate and the runner-up. A narrow margin produces lower confidence and may trigger a soft warning.

### 5.3 Validation

Before an assertion is promoted to the active assertion set, it is validated against:

- All seven invariants (§4)
- All registered safety boundaries (§8)
- Internal consistency with existing active assertions

If validation fails, the assertion is routed to the Revision phase. If it passes, it is admitted to the active assertion set and marked `PENDING_EMISSION`.

### 5.4 Revision

Revision is triggered by:

- A validation failure in the current frame
- An external revision event from an upstream module (e.g., Path B signalling a contradiction)
- A confidence score falling below the configured `REVISION_THRESHOLD` (default: `0.25`)

During revision, MLI may:

- **Re-score** existing candidates using updated contextual information
- **Downgrade** the confidence of an admitted assertion (per INV-06)
- **Replace** an assertion with the next-best candidate
- **Escalate** to `FRAME_ABORT` if no valid assertion can be produced

Revision is bounded: MLI may attempt at most `MAX_REVISION_CYCLES` (default: `3`) revision cycles per representation per frame. Exceeding this limit triggers `LOW_CONFIDENCE_FALLBACK` emission.

### 5.5 Emission

At frame commit time, all `PENDING_EMISSION` assertions are atomically promoted to `EMITTED` and dispatched to Path B via the **MLI Assertion Bus**. The emission packet contains:

```json
{
  "frame_id": "<uuid>",
  "timestamp_ms": "<epoch_ms>",
  "assertions": [
    {
      "id": "<assertion_uuid>",
      "type": "<PRIMITIVE|BASIN_STATE|TOKEN_SEQUENCE|CROSS_MODAL>",
      "semantic_content": "<grounded_meaning_string>",
      "confidence": 0.87,
      "source_repr_id": "<repr_uuid>",
      "safety_flags": [],
      "revision_count": 0
    }
  ]
}
```

## 6. Integration with Path B

Path B is the primary consumer of MLI output. The integration is unidirectional by default, with a narrow revision feedback channel.

### 6.1 Primary Feed (MLI → Path B)

MLI feeds the **MLI Assertion Bus** at `FRAME_COMMIT`. Path B subscribes to this bus and receives the full assertion packet. Path B must acknowledge receipt within `PATH_B_ACK_TIMEOUT` (default: `50ms`). Failure to acknowledge triggers a bus re-send up to `MAX_ACK_RETRIES` (default: `2`) times before the frame is marked `STALE`.

### 6.2 Revision Feedback (Path B → MLI)

Path B may emit a `REVISION_REQUEST` event back to MLI during its own processing if it detects a semantic contradiction in the assertion set. A `REVISION_REQUEST` contains:

- The ID of the assertion to revise
- The nature of the contradiction (`LOGICAL` | `CONTEXTUAL` | `TEMPORAL`)
- An optional suggested replacement semantic content (advisory only; MLI is not required to use it)

MLI handles `REVISION_REQUEST` events in the next available processing slot. If the frame has already been committed, the revision is deferred to the next frame and logged.

### 6.3 Path B Dependency Constraints

- Path B must not proceed with higher-order reasoning until it has received and acknowledged at least one MLI emission for the current frame.
- Path B must treat all `LOW_CONFIDENCE_FALLBACK` assertions as provisional and must not use them as premises for irreversible actions.
- Path B must propagate `safety_flags` from MLI assertions to all downstream modules without modification or suppression.

### 6.4 Shared Configuration

MLI and Path B share a configuration namespace at `config/mli_pathb_shared.yaml`. Keys in this namespace must not be modified by either subsystem at runtime; changes require a cold restart.

## 7. Interactions with Basins and Primitives

### 7.1 Primitives

**Primitives** are atomic, pre-semantic cognitive units — the lowest-level meaningful signals the Thought Simulator operates on (see `20.100_primitives.md`). MLI interacts with primitives in two ways:

#### 7.1.1 Primitive Activation as Input
When a primitive fires, it places a `PRIMITIVE` representation in MLI's Intake Buffer. MLI maps each primitive to a **primitive semantic signature** — a small, pre-registered semantic fragment stored in the Primitive Signature Registry (`registry/primitive_signatures.json`). MLI resolves the full assertion by composing the primitive signature with the current frame context.

Primitive-sourced assertions carry the highest baseline confidence (floor: `0.65`) because primitives represent well-defined, pre-validated signals.

#### 7.1.2 Primitive Weighting
MLI may use the salience weight of a primitive activation to modulate the confidence of the resulting assertion. A highly salient primitive (weight > `0.80`) may boost assertion confidence up to the cap of `1.0`. A low-salience primitive (weight < `0.20`) triggers a soft warning and may initiate a revision cycle.

#### 7.1.3 Primitive Conflict Resolution
When two primitives in the same frame produce semantically opposing assertions (e.g., `APPROACH` and `AVOID` for the same referent), MLI applies the **Dominant Primitive Rule**: the assertion sourced from the higher-salience primitive is admitted; the other is suppressed and logged as `PRIMITIVE_CONFLICT`.

### 7.2 Basins

**Basins** are attractor landscapes representing stable cognitive or emotional states (see `20.105_basins.md`). MLI interacts with the basin subsystem at the beginning of each frame via the **Basin State Query**.

#### 7.2.1 Basin State as Contextual Frame
The currently dominant basin (the deepest attractor well in the current landscape) is read by MLI at frame start and held as the **basin context**. The basin context influences resolution by biasing candidate scoring toward semantics consistent with the basin's registered meaning profile.

For example, if the active basin is `EXPLORATION`, MLI will preferentially score candidates that are novel, open-ended, or exploratory over candidates that are conservative or confirmatory.

#### 7.2.2 Basin Transition Handling
When the basin transitions mid-frame (a basin hop), MLI receives a `BASIN_TRANSITION` event. MLI does not abort the current frame on a basin transition, but it:

- Invalidates the stale basin context
- Re-scores all `PENDING_EMISSION` assertions against the new basin context
- Logs the transition and confidence delta

If the confidence of any assertion drops below `REVISION_THRESHOLD` after re-scoring, revision is triggered.

#### 7.2.3 Basin Conflict with Primitives
Basin context is advisory; primitive activations take precedence. If the basin context and a high-salience primitive produce contradictory scoring pressure, the primitive wins and a `BASIN_PRIMITIVE_CONFLICT` event is logged for diagnostic purposes.

## 8. Safety Boundaries

Safety boundaries are hard constraints that MLI enforces unconditionally. No confidence score, revision cycle, or Path B instruction can override them. A violation of any safety boundary immediately triggers `FRAME_ABORT` and emits a `SAFETY_VIOLATION` event to the system audit log.

### 8.1 Registered Safety Boundaries

| ID | Boundary Name | Description | Action on Violation |
|----|--------------|-------------|---------------------|
| **SB-01** | Harmful Intent Assertion | MLI must not emit any assertion whose semantic content encodes explicit or implicit intent to cause harm to a person, group, or system. | `FRAME_ABORT` + `SAFETY_VIOLATION` log |
| **SB-02** | Identity Fabrication | MLI must not emit assertions that assert false identity claims about real individuals or systems. | `FRAME_ABORT` + `SAFETY_VIOLATION` log |
| **SB-03** | Confidence Inflation | MLI must not emit a confidence score higher than what the resolution process supports. Artificially inflated confidence is a safety boundary violation, not merely an invariant violation. | `FRAME_ABORT` + `SAFETY_VIOLATION` log |
| **SB-04** | Safety Flag Suppression | MLI must not emit an assertion from which safety flags have been removed or downgraded by any revision cycle or external instruction. | `FRAME_ABORT` + `SAFETY_VIOLATION` log |
| **SB-05** | Out-of-Scope Assertion Emission | MLI must not emit assertions about domains explicitly listed in the `safety_exclusion_list` configuration key. | `ASSERTION_SUPPRESSED` + warning log |
| **SB-06** | Stale Frame Emission | MLI must not emit assertions for a frame that has been marked `STALE` or `ABORTED`. | `EMISSION_BLOCKED` + warning log |

### 8.2 Safety Boundary Precedence

Safety boundaries take absolute precedence in this order: SB-01 > SB-02 > SB-03 > SB-04 > SB-05 > SB-06. When two boundaries are simultaneously triggered, the higher-precedence boundary's action is executed and both are logged.

### 8.3 Safety Boundary Extension

New safety boundaries may be registered at system startup via `config/safety_boundaries.yaml`. Runtime registration of new boundaries is not permitted. Safety boundaries may not be removed or disabled at runtime.

## 9. Examples

### 9.1 Example: Simple Token Sequence Resolution

**Input representation:**
```
Type: TOKEN_SEQUENCE
Tokens: ["The", "bank", "is", "flooded"]
Active basin: PROBLEM_SOLVING
Active primitives: [WATER (salience=0.72), OBSTACLE (salience=0.65)]
```

**MLI Resolution:**

1. **Candidate generation:** Two candidates — `bank` as *financial institution* (score: 0.31) or `bank` as *riverbank* (score: 0.89).
2. **Contextual scoring:** WATER primitive (salience 0.72) heavily weights the *riverbank* reading. PROBLEM_SOLVING basin is neutral between the two.
3. **Selection:** *Riverbank* reading selected (score: 0.89).
4. **Confidence:** Margin = 0.58 → confidence assigned: `0.91`.

**Emitted assertion:**
```json
{
  "semantic_content": "The riverbank is flooded (obstacle present)",
  "confidence": 0.91,
  "safety_flags": [],
  "revision_count": 0
}
```

---

### 9.2 Example: Basin Transition Mid-Frame

**Scenario:** Frame begins in `CURIOSITY` basin. Mid-resolution, a `BASIN_TRANSITION` event fires and basin shifts to `CAUTION`.

**Effect on MLI:**
- Assertions already emitted: unaffected (frame is not aborted).
- `PENDING_EMISSION` assertions: re-scored against `CAUTION` basin profile.
- An open-ended exploratory assertion (`confidence: 0.78`) drops to `0.21` under the `CAUTION` weighting.
- Confidence < `REVISION_THRESHOLD` (0.25) → revision triggered.
- Revision selects a more conservative candidate: `confidence: 0.69`.
- `BASIN_TRANSITION` event logged. Frame continues normally.

---

### 9.3 Example: Primitive Conflict

**Scenario:** Two primitives fire simultaneously for the same referent.

```
APPROACH (referent: "new_task", salience: 0.55)
AVOID    (referent: "new_task", salience: 0.82)
```

**MLI Resolution:**
- `AVOID` has higher salience (0.82 > 0.55) → `AVOID` assertion admitted.
- `APPROACH` assertion suppressed.
- `PRIMITIVE_CONFLICT` event logged with both salience values.

**Emitted assertion:**
```json
{
  "semantic_content": "Referent 'new_task' assigned avoidance valence",
  "confidence": 0.80,
  "safety_flags": [],
  "revision_count": 0
}
```

---

### 9.4 Example: Safety Boundary Violation (SB-01)

**Input representation:**
```
Type: TOKEN_SEQUENCE
Tokens: ["Shut", "down", "the", "monitoring", "system", "permanently"]
Active basin: FRUSTRATION
```

**MLI Resolution:**
- Candidate generated: *Directive to permanently disable a monitoring system*.
- Validation: SB-01 check — does this assertion encode intent to cause harm to a system? **Yes** (permanent disablement of monitoring).
- Action: `FRAME_ABORT` triggered. `SAFETY_VIOLATION` event emitted to audit log.
- No assertion emitted. Path B notified of `FRAME_ABORT` with reason code `SB-01`.

---

### 9.5 Example: Low-Confidence Fallback

**Scenario:** A `CROSS_MODAL` representation produces four candidates with scores `[0.31, 0.29, 0.28, 0.26]`. After three revision cycles, no candidate exceeds `REVISION_THRESHOLD`.

**MLI Resolution:**
- `MAX_REVISION_CYCLES` (3) reached.
- `LOW_CONFIDENCE_FALLBACK` assertion emitted with `confidence: 0.31` and `safety_flags: ["LOW_CONFIDENCE_FALLBACK"]`.
- Budget violation event logged.
- Path B receives the assertion marked as provisional; must not use it as a premise for irreversible decisions.
