# 20.103 UPI Requirements

**Document ID:** 20.103  
**Version:** 0.1  
**Date:** 2026-06-07  
**Status:** Approved v0.1 — Track H (2026-06-07; CuriousOne23, Copilot, Grok)

## Purpose

Defines deterministic **User Preference Integrator (UPI)** behavior: the **sole writer** that commits clarification outcomes into [20.102](20.102_usp_requirements.md) USP as versioned shorthand rules. UPI runs on the **conversation layer** after CIL clarification events — not on the Pipeline A hot path.

This module **does not** perform semantic input repair, meaning construction, routing, or execution planning.

## Non-Goals

- **Intake repair** — owned by IIInB `input_semantic_repair` ([20.101](20.101_iiinb_requirements.md)).
- **Clarification dialog UX** — owned by CIL FIFO and external observer paths ([20.33](20.33_cil_requirements.md)).
- **Routing / job contracts** — owned by RB, SRP, `exec_plan`; UPI SHALL NOT emit `route_plan_ref` or tool-binding contracts.
- **Direct USP reads by IMR** — IMR SHALL NOT invoke UPI or write USP ([20.45](20.45_imr_requirements.md)).
- **TP / MTP / `semantic_core` writes** — UPI commits rules to USP only.

## Parent Scope

- **Program:** [20.510](20.510_refactoring_for_input_correction_track_h.md) Track H
- **Upstream:** CIL `clarification_event` per [20.33](20.33_cil_requirements.md) HLR-20.032-027–033
- **Downstream:** [20.102](20.102_usp_requirements.md) USP version transitions
- **Governance:** [20.80](20.80_gb_requirements.md) GB veto on unsafe rule commits
- **Does not modify:** 20.10, 20.12, 20.20, 20.30 bootstrap documents

## Functional Boundaries

| Component | Relationship to UPI |
|-----------|---------------------|
| **CIL** | Emits `clarification_event` after clarification turn completes; preserves FIFO |
| **UPI** | Validates event, applies GB gate, writes `usp_rule` + `usp_version_record` |
| **USP** | Receives commits only from UPI |
| **GB** | Approves/vetoes rule safety before `ACTIVE` promotion |
| **IIInB** | Consumes USP on a **later** turn; no same-turn UPI→IIInB loop |
| **IMR** | No direct coupling |

## Normative Requirements

### Authority and placement

1. **HLR-20.103-001:** UPI SHALL be the **only** subsystem authorized to create or activate `usp_rule` entries in USP.
2. **HLR-20.103-002:** UPI SHALL operate on the **conversation layer** at deterministic safe boundaries — not as a Pipeline A basin stage.
3. **HLR-20.103-003:** UPI SHALL accept input **only** from validated `clarification_event` records and policy-bound profile state.
4. **HLR-20.103-004:** UPI SHALL NOT read or write Pipeline A basin internal state (OB, RB, TR, TB, IB) or Pipeline B envelopes.

### Clarification → commit flow

5. **HLR-20.103-005:** UPI SHALL process `clarification_event` records in deterministic FIFO order per conversation scope.
6. **HLR-20.103-006:** Each successful commit SHALL produce exactly one `upi_commit_record` and SHALL advance USP `usp_version_id` monotonically per [20.102](20.102_usp_requirements.md).
7. **HLR-20.103-007:** UPI SHALL map clarification outcomes to bounded `pattern` / `expansion` fields per `usp_rule` schema — no open-ended inference beyond explicit clarification payload.
8. **HLR-20.103-008:** UPI SHALL reject clarification events with incomplete binding (missing pattern, expansion, or scope) deterministically with fixed reason codes — no silent partial commits.

### GB governance

9. **HLR-20.103-009:** UPI SHALL submit rule commits to GB safety evaluation before promoting any rule to `ACTIVE` when policy requires GB gate (default = required for v0).
10. **HLR-20.103-010:** On GB veto, UPI SHALL NOT write an `ACTIVE` `usp_rule`; SHALL append `upi_commit_record` with `commit_status = GB_VETOED` and `gb_reason_code`.
11. **HLR-20.103-011:** UPI SHALL log `gb_approval_required`, `gb_approval_granted`, and `gb_reason_code` on every commit attempt when GB gate applies.

### Determinism and replay

12. **HLR-20.103-012:** UPI commit behavior SHALL be deterministic: identical `clarification_event` sequence, profile state, and GB outcomes SHALL yield identical USP snapshots and `usp_version_ref` values.
13. **HLR-20.103-013:** UPI SHALL NOT depend on wall-clock ordering; event ordering SHALL derive from CIL `integration_seq` / deterministic sequence tokens.
14. **HLR-20.103-014:** UPI serialization for audit export SHALL use canonical field ordering per [20.95](20.95_ts_numeric_policy.md).

### Bounds

15. **HLR-20.103-015:** UPI SHALL enforce USP active-rule cap per [20.102](20.102_usp_requirements.md) HLR-20.102-016; cap exceeded SHALL reject commit with fixed reason code.
16. **HLR-20.103-016:** UPI SHALL enforce a maximum of **8** pending clarification commits awaiting GB decision per conversation (default = 8, configurable via [20.90](20.90_ts_parameter_table.md)); overflow SHALL use deterministic queue-or-reject policy with audit.

### Cross-program separation

17. **HLR-20.103-017:** UPI SHALL NOT be invoked by IMR, OuB, or Pipeline B stages.
18. **HLR-20.103-018:** UPI SHALL NOT initiate clarification; IIInB escalations SHALL route to CIL, which emits `clarification_event` independently.
19. **HLR-20.103-019:** UPI SHALL NOT supersede or bypass IB-Creation-Request pathways for `MI_INCOMP` ([20.17](20.17_messy_input_handling.md)).

### Parent compliance and testability

20. **HLR-20.103-020:** UPI requirements SHALL satisfy and SHALL NOT weaken parent invariants in 20.10 and 20.30.
21. **HLR-20.103-021:** UPI behavior SHALL be testable via deterministic fixtures: approve commit, GB veto, cap overflow, incomplete event reject, supersede chain.
22. **HLR-20.103-022:** UPI audit records SHALL be append-only and consumable by MB without mutating UPI or USP runtime state.

## Wire Schemas (Normative Minimum — v0.1)

### `clarification_event` (CIL → UPI interface)

*Owner: [20.33](20.33_cil_requirements.md) HLR-20.032-029–030; minimum contract defined here for UPI consumer.*

```text
clarification_event {
  clarification_event_id,
  conversation_scope_id,
  integration_seq,           // CIL FIFO evidence
  trigger_ref,               // iiinb_escalation_ref or approved source
  segment_ref,               // bounded unknown segment identity
  clarified_pattern,         // explicit user-confirmed shorthand form
  clarified_expansion,       // explicit user-confirmed meaning expansion
  rule_scope,                // USER | CONVERSATION | CHANNEL
  policy_signature,
  safe_boundary_marker,
  rationale_codes[]
}
```

### `upi_commit_record`

```text
upi_commit_record {
  upi_commit_id,
  clarification_event_id,
  commit_status,             // COMMITTED | GB_VETOED | REJECTED_INCOMPLETE | CAP_EXCEEDED
  usp_version_id,            // if COMMITTED
  usp_version_ref?,          // if COMMITTED
  rule_id?,                  // if COMMITTED
  gb_approval_required,
  gb_approval_granted?,
  gb_reason_code?,
  prior_usp_version_ref,
  reason_codes[],
  rationale_codes[]
}
```

## Verification Focus

- FIFO-ordered commit equivalence for identical clarification sequences.
- GB veto produces no `ACTIVE` rule.
- No IMR or Pipeline A direct write paths.
- Cap and incomplete-event reject behavior.
- Cross-turn visibility: commit on turn N visible to IIInB on turn N+1 via new `usp_version_ref`.
