# **20.30.020 — TS Cycle Allocation & Stability Envelope**  
**Status:** Normative  
**Scope:** Global cycle allocation, boundedness envelope, overflow detection  
**Excludes:** TCU budgeting (20.30.030), MCS rules (20.30.040), merge semantics (20.30.050)

---

# **0. Purpose**

This document defines the **cycle‑level allocation model** and the **global stability envelope** for the Thought Simulator (TS).  
It describes:

- how a TS cycle is partitioned across subsystems  
- global deterministic bounds on lane count, evidence size, ΔH% flow, and provenance depth  
- how overflow is detected and surfaced  
- how stability metadata is exposed  

Detailed degradation rules, TCU budgeting, and MCS semantics are defined in 20.30.030 and 20.30.040.

---

# **1. Cycle Allocation Model**

A TS cycle is divided into a deterministic sequence of subsystems:

- RTU‑prm (routing update)  
- TR‑prm (routing refinement)  
- splitting  
- OB processing  
- TB interpretation  
- merge  
- truth/completion evaluation  
- RBU (authoritative MTP update)  

Each subsystem consumes a predictable portion of the cycle.  
The allocation model provides a **bounded, deterministic execution envelope** that supports replay equivalence and prevents runaway growth.

Cycle allocation does not prescribe hardware timing; it defines **logical budget proportions** used by the TS runtime.

---

# **2. Global Stability Envelope**

The TS operates within a set of global deterministic bounds that constrain:

- the number of active lanes  
- OB activation count  
- routing fan‑out (RTU‑prm)  
- evidence payload sizes  
- TB interpretation channel sizes  
- ΔH% contribution limits  
- provenance chain depth  
- per‑cycle compute envelope  

These bounds ensure that meaning construction remains stable, non‑explosive, and auditable across cycles.

Overflow behavior is deterministic and visible to supervisory layers.

---

# **3. Overflow Detection and Tagging**

Overflow occurs when any global bound is exceeded.  
The TS detects overflow **within the same cycle** and produces:

- a deterministic overflow flag  
- a structured overflow record  
- a stability metadata entry in the MTP snapshot  
- a user‑visible stability signal  

Overflow detection does not halt execution; it produces a **bounded, deterministic degradation path**.

Detailed degradation rules are defined in 20.30.030.

---

# **4. Stability Metadata Schema**

Overflow and degradation events produce a structured metadata record containing:

- `overflow_flag`  
- `overflow_type`  
- `overflow_source_basin`  
- `overflow_cycle`  
- `truncated_fields`  
- ΔH% normalization applied  
- compute overrun amount  

This schema provides a consistent interface for:

- MB (monitoring basin)  
- GB (global basin)  
- OuB (output basin)  
- IB (inquiry basin)  
- user‑facing layers  

The schema is descriptive here; detailed field semantics appear in 20.30.030.

---

# **5. Cycle‑Level Deterministic Behavior**

Cycle allocation and stability constraints support:

- deterministic replay  
- bounded lane growth  
- bounded evidence growth  
- bounded ΔH% flow  
- bounded provenance depth  
- deterministic overflow outcomes  

These properties ensure that the TS remains stable under load and predictable across hardware.

---

# **6. Normative Requirements (HLR‑20.30.020‑xxx)**

These are the **only** SHALL‑bearing requirements in this file.

### **HLR‑20.30.020‑001 — Global Lane Bound**  
The TS SHALL enforce a deterministic global maximum for active lanes per cycle.

### **HLR‑20.30.020‑002 — OB Activation Bound**  
The TS SHALL enforce a deterministic maximum number of OB activations per cycle.

### **HLR‑20.30.020‑003 — Routing Fan‑Out Bound**  
The TS SHALL enforce a deterministic maximum routing fan‑out per TP to prevent exponential lane growth.

### **HLR‑20.30.020‑004 — Evidence Size Bound**  
The TS SHALL enforce deterministic maximum evidence payload sizes for OB outputs.

### **HLR‑20.30.020‑005 — TB Interpretation Bound**  
The TS SHALL enforce deterministic maximum TB interpretation channel sizes and hypothesis counts.

### **HLR‑20.30.020‑006 — Provenance Depth Bound**  
The TS SHALL enforce a deterministic maximum provenance chain depth.

### **HLR‑20.30.020‑007 — ΔH% Contribution Bound**  
The TS SHALL enforce deterministic maximum ΔH% contribution per basin per cycle.

### **HLR‑20.30.020‑008 — Cycle Compute Envelope**  
The TS SHALL enforce deterministic per‑cycle compute envelopes for all basins.

### **HLR‑20.30.020‑009 — Deterministic Overflow Detection**  
The TS SHALL detect overflow deterministically within the same cycle in which it occurs.

### **HLR‑20.30.020‑010 — Overflow Tagging**  
The TS SHALL tag overflow events with deterministic stability metadata accessible to supervisory and user‑facing layers.

### **HLR‑20.30.020‑011 — Deterministic Degradation Path**  
Overflow SHALL result in deterministic, policy‑bounded degradation behavior.

### **HLR‑20.30.020‑012 — No Silent Drops**  
The TS SHALL NOT silently drop lanes, evidence, or interpretation fields without deterministic tagging and logging.

### **HLR‑20.30.020‑013 — No Probabilistic Recovery**  
Overflow SHALL NOT trigger probabilistic reconstruction or latent‑state inference.

### **HLR‑20.30.020‑014 — Stability Metadata Exposure**  
The TS SHALL expose deterministic stability metadata in the MTP snapshot.

### **HLR‑20.30.020‑015 — Canonical Overflow Schema**  
Overflow and degradation metadata SHALL conform to the canonical schema defined in this file.

---

# **7. Summary**

20.30.020 defines the **cycle allocation model** and the **global stability envelope** for the TS:

- deterministic cycle partitioning  
- bounded lane and evidence growth  
- bounded ΔH% and provenance depth  
- deterministic overflow detection  
- deterministic degradation  
- structured stability metadata  

Detailed compute budgeting and degradation rules appear in 20.30.030.
