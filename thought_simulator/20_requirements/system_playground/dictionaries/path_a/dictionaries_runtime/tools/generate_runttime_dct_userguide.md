# 📘 **generate_runttime_dct_userguide.md**  
### *Generate Runtime Dictionary User Guide*

This guide explains **exactly** how a user generates a new TS Path A dictionary, how dictionary **versioning** works, what files are **inputs**, what files are **outputs**, what the user is **expected to modify**, and what the user must **never modify**.

It complements the main `README.md` by providing a **step‑by‑step workflow** for engineers who need to regenerate or version dictionaries.

---

# 🔹 1. Overview

The TS Path A dictionary is produced in **two stages**:

1. **Developer Dictionary Generation**  
   - Full semantic entries  
   - Glosses, pointers, metadata  
   - Six chunked `.json.gz` files  
   - Written into a *versioned developer directory*

2. **Runtime Dictionary Stripping**  
   - Removes glosses and metadata  
   - Produces TS‑efficient runtime chunks  
   - Six chunked `.json.gz` files  
   - Written into the *pipeline base directory*  
   - User must **manually move** them into `dictionaries_runtime/`

All chunking is controlled by **manifest.json**, which is automatically generated.

---

# 🔹 2. Inputs and Outputs

## **Inputs (user does not modify)**

Located in:

```
dictionary_conversion_pipeline/wordnet_raw/
```

Required WordNet files:

- `index.noun`
- `index.verb`
- `index.adj`
- `index.adv`
- `data.noun`
- `data.verb`
- `data.adj`
- `data.adv`

These files are **never edited** by the user.

---

## **Outputs (user must understand)**

### Developer Dictionary (auto‑generated)

Written to:

```
<BASE_DIR>/dictionaries_dev/
```

Files:

```
meaning_dictionary_dev_01.json.gz
meaning_dictionary_dev_02.json.gz
...
meaning_dictionary_dev_06.json.gz
manifest.json
```

### Runtime Dictionary (auto‑generated)

Written to:

```
<BASE_DIR>/
```

Files:

```
ts_meaning_dictionary_01.json.gz
ts_meaning_dictionary_02.json.gz
...
ts_meaning_dictionary_06.json.gz
manifest.json
```

### User Action Required

The user must **manually move** runtime files into:

```
dictionaries_runtime/
```

This prevents accidental overwrites and keeps dictionary versions clean.

---

# 🔹 3. What the User *Must* Modify

Users modify **only** `config.py`.

Specifically:

## ✔ 1. Developer dictionary version directory

To create a new version:

```python
DEV_OUTPUT_DIR = BASE_DIR / "dictionaries_dev_v2"
```

This controls **where** developer chunks are written.

---

## ✔ 2. (Optional) Developer dictionary filename prefix

If you want custom naming:

```python
DEV_CHUNK_PREFIX = "my_dictionary_v2"
DEV_CHUNK_SUFFIX = ".json.gz"
```

This controls **what the developer chunk files are named**.

---

## ✔ 3. (Optional) Runtime dictionary filename prefix

```python
RUNTIME_CHUNK_PREFIX = "ts_meaning_dictionary"
RUNTIME_CHUNK_SUFFIX = ".json.gz"
```

This controls **what runtime chunk files are named**.

---

# 🔹 4. What the User Must *Not* Modify

## ❌ Do NOT edit `manifest.json`

It is always regenerated by:

- `batch_converter.py` (developer manifest)
- `ts_meaning_dct_path_a.py` (runtime manifest)

Editing it breaks chunk alignment.

---

## ❌ Do NOT edit filenames inside the pipeline code

These lines:

```python
filename = f"meaning_dictionary_dev_{chunk_id:02d}.json.gz"
filename = f"ts_meaning_dictionary_{chunk_id:02d}.json.gz"
```

should be replaced with config‑based naming, but users should **never** edit pipeline code directly.

---

## ❌ Do NOT edit WordNet raw files

They are canonical inputs.

---

## ❌ Do NOT place runtime files directly into `dictionaries_runtime/`

The pipeline intentionally writes runtime files into `<BASE_DIR>` to avoid overwriting previous versions.

---

# 🔹 5. Step‑by‑Step: How to Generate a New Dictionary Version

## **Step 1 — Choose a version name**

Edit `config.py`:

```python
DEV_OUTPUT_DIR = BASE_DIR / "dictionaries_dev_v3"
```

Optional:

```python
DEV_CHUNK_PREFIX = "meaning_dictionary_dev_v3"
```

---

## **Step 2 — Run the developer dictionary generator**

From the pipeline directory:

```
python batch_converter.py
```

This produces:

```
dictionaries_dev_v3/
    meaning_dictionary_dev_v3_01.json.gz
    ...
    manifest.json
```

---

## **Step 3 — Inspect developer chunks**

Check:

- chunk count (should be 6)
- lemma ranges
- compressed sizes
- manifest.json correctness

---

## **Step 4 — Generate runtime dictionary**

Run:

```
python ts_meaning_dct_path_a.py
```

This produces runtime files in:

```
<BASE_DIR>/
    ts_meaning_dictionary_01.json.gz
    ...
    manifest.json
```

---

## **Step 5 — Move runtime files manually**

Move them into:

```
dictionaries_runtime/
```

Example:

```
mv ts_meaning_dictionary_*.json.gz dictionaries_runtime/
mv manifest.json dictionaries_runtime/
```

---

## **Step 6 — Verify runtime manifest**

Ensure:

- chunk count matches developer manifest  
- filenames match runtime naming  
- lemma ranges match developer manifest  

---

# 🔹 6. FAQ

### **Q: Why do runtime files go into the base directory?**  
To prevent accidental overwriting of existing runtime dictionaries.

### **Q: Why must I move runtime files manually?**  
To ensure version control and avoid mixing dictionary versions.

### **Q: How do I create multiple dictionary versions?**  
Change `DEV_OUTPUT_DIR` in `config.py`.

### **Q: How do I change dictionary naming?**  
Change `DEV_CHUNK_PREFIX` and `RUNTIME_CHUNK_PREFIX` in `config.py`.

### **Q: How does the pipeline know how many chunks exist?**  
From `manifest.json` — never edit it manually.

---

# 🔹 7. Summary

- Developer dictionaries → written to `DEV_OUTPUT_DIR`  
- Runtime dictionaries → written to `<BASE_DIR>`  
- User must move runtime files manually  
- User controls versioning via directory names  
- User controls naming via config prefixes  
- Manifest.json controls chunk count  
- Manifest.json is never edited manually  
- Pipeline code is never edited by users  

This file gives users everything they need to safely generate and version TS Path A dictionaries.
