# 20.35_TP Design

## 1. Purpose and Scope

This document defines the TP subsystem design specification for the Thought Simulator design layer.

The purpose of the TP is to record the thought processing it undergoes.

This design spec translates TP lifecycle behavior and canonical TP requirements into implementation-facing design contracts while preserving determinism, traceability, and interoperability.

Scope includes TP identity, state lifecycle, entropy behavior, split/merge lineage, IO schema contracts, observability obligations, and verification obligations for TP behavior.

## 3. TP Contract and Invariants

### 3.1 Identity and determinism contract

- Every TP must have a unique, stable `tp_id`.
- TP identity behavior must be deterministic when `deterministic_mode=True`.
- TP identity must remain traceable across creation, movement, split, merge, and completion evaluation.

### 3.2 State and lifecycle contract

A TP must carry, at minimum:

- basin affiliation
- entropy state (`h_rep`, `h_pred`, `h_struct`, `total`)
- energy state
- lifecycle trajectory history/provenance

Required lifecycle operations:

- creation
- basin movement
- entropy updates
- tagging and untagging
- split
- merge
- completion evaluation

### 3.3 Invariants

- `state_counter` is strictly monotonic for each mutating TP operation.
- Entropy components remain non-negative.
- A TP is in exactly one basin at a time.
- TP history is append-only for audit/replay.
- Provenance lineage is lossless for split/merge semantics.

## 4. TP Operation Flow and State Transitions

### 4.1 Operational placement in TS flow

TP behavior participates in deterministic TS phases consistent with program flow requirements:

- creation/injection
- entry checks
- basin processing
- routing/transitions
- split/merge
- regulation effects
- completion detection
- logging/snapshot

### 4.2 Mutating operation rules

Each TP mutating operation must:

- increment `state_counter`
- append a history event with tick and event semantics
- preserve or update provenance channels as required
- maintain deterministic outcomes under equivalent deterministic inputs

### 4.3 Split and merge transition rules

Split:

- requires `child_count >= 2`
- preserves parent-child lineage
- partitions TP state deterministically

Merge:

- requires non-empty source set
- requires compatible embedding dimensionality
- preserves all source lineage in merged provenance

## 5. Data and IO Contract

### 5.1 Public macro API boundary

The TP design exposes lifecycle operations equivalent to the lifecycle module API shape:

- construction/new
- basin movement
- entropy update
- tag add/remove
- split and merge
- serialization via `to_dict`

### 5.2 Canonical serialized form

`to_dict` output is the canonical TP interchange payload and must be JSON-compatible.

Required fields:

- `tp_id`
- `current_basin_id`
- `entropy.h_rep`
- `entropy.h_pred`
- `entropy.h_struct`
- `entropy.total`
- `state_counter`
- `history`
- `provenance`

### 5.3 Schema compatibility policy

- Current compatibility baseline: `tp_lifecycle_io_schema_v1`.
- Backward-compatible expansion may add optional fields.
- Breaking field renames/removals require version increment and migration notes.
- External consumers must preserve required fields exactly and ignore unknown optional fields.

### 5.4 Artifact contract

Canonical verification artifacts are produced in:

- `../30_thought_simulator_playground/30.20_tp_lifecycle/artifacts/`

Expected deterministic evidence set includes canonical run state and deterministic rerun comparisons.

## 6. Observability and Logging Contract

- All TP state-changing operations must emit observable events.
- TP event records must preserve tick, TP identity, event type, and `state_counter` semantics.
- Observability must support replay and audit without mutating TP behavior.
- Snapshot/state output must preserve provenance and history required for lifecycle reconstruction.

## 7. Verification and Validation Obligations

### 7.1 Entrypoint discipline

- TP module verification runs through `harness.py` as canonical entrypoint.
- TP lifecycle logic must remain importable without top-level side effects.

### 7.2 Determinism and regression obligations

- Deterministic reruns must preserve TP identity and `state_counter` trajectories under equivalent deterministic input.
- Negative-path checks must include split/merge invalid inputs and structural mismatch cases.

### 7.3 Requirement evidence obligations

- Executed TP scenarios must emit HLR/LLR references.
- Canonical scenario evidence is maintained in `verification_capsule.md`.
- Requirement-change evolution and migration deltas are maintained in `requirements_delta.md`.

## 8. Traceability

- This TP design spec is derived from and subordinate to canonical requirements in `20.30_tp_requirements.md`.
- TP design obligations must remain represented in the requirements traceability matrix.
- Any new TP design rule without requirement anchor must be proposed as a requirement delta before becoming normative.

## 9. Change Control

- Update this document when TP lifecycle behavior or canonical TP requirements change materially.
- Preserve additive and lossless migration history for TP design decisions.
- Keep terminology aligned with `20.150_glossary.md` and verification vocabulary aligned with `30.30_verification_glossary.md`.
- Keep relative links valid across design, requirements, lifecycle, and verification sources.
