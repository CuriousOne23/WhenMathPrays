# 50.34_COP Design Support

## 1. Purpose and Scope

This design support specification defines deterministic Conversation Coprocessor (COP) behavior, invariants, and IO contracts promoted from canonical COP requirements and 30-layer verification evidence.

## 3. Contracts and Invariants

- COP proposal admission preserves deterministic provenance hashing and append-only audit capture.
- Ordering-critical behavior is sequence-driven and independent of wall-clock precedence.
- Approved COP work remains staged and invisible until deterministic safe-boundary commit.
- Profile-bound fairness and overload policy are controlled by active execution-signature profile rather than environment default.
- Unsupported profile states and invalid control paths are rejected with fixed reason codes and append-only audit evidence.
- COP remains propose-only and does not mutate authoritative state directly.

## 4. Operation Flow and State Transitions

- Accept deterministic proposal packets through explicit approved interfaces.
- Compute canonical provenance hash from proposal input and admit the proposal into a bounded queue under the active policy.
- Apply GB supervisory decision at safe boundary to either stage, reject, or expire pending proposals.
- Transition staged proposals to visible commits only through explicit safe-boundary commit events.
- Persist append-only audit records for queue admission, preemption, supervisory decision, commit visibility, and reject outcomes.

## 5. Data and IO Contract

Input fields:
- `event_type` (`submit_proposal|gb_decision|commit_ready|profile_change`)
- `sequence` (int, monotonic)
- `safe_boundary` (bool)
- `payload` (JSON object)
- `proposal_id` (string)
- `source` (string)
- `basis_snapshot` (string)
- `priority` (`normal|safety_critical`)
- `decision` (`approve|reject|expire`)
- `profile` (`P1|P2`)

Output fields:
- `sequence`
- `policy`
- `pending_queue`
- `staged_commits`
- `visible_commits`
- `audit_log`
- `active_profile`
- `verification_digest`

## 6. Observability and Logging

- Proposal submission, preemption, supervisory decisions, commit visibility, and reject paths must emit append-only audit records.
- Audit records must carry fixed deterministic reason codes for both accept and reject outcomes.
- Determinism evidence must remain replay-visible through canonical artifact outputs and digest-bearing state snapshots.

## 7. Verification Obligations

- Deterministic proposal provenance hashing and bounded queue admission scenarios are mandatory.
- Deterministic GB staging and safe-boundary commit visibility scenarios are mandatory.
- Deterministic overload handling and profile-precedence scenarios are mandatory.
- Negative-path scenarios must cover sequence violations, safe-boundary violations, and unsupported profile states.

## 9. Change Control

- Any new COP event type, GB decision enum, or profile mode requires synchronized updates to 10.50.34, 30.34 verification ledgers, and this design support specification.
- Any overload-policy expansion requires deterministic queueing, preemption, and reject-rule updates with compatibility notes.
- TCU measurement fields are not mandatory at this design stage; they become required only when COP enters the TCU budgeting promotion path.

## CPU Execution Cycle Design Obligations (per 10.50.34.TCU and 20.150)

### 50.36.TCU.10 Design for bounded per-tick cost
- Obligation ID: 50.36.TCU.10
- Satisfies: 10.50.34.TCU.10
- Design notes:
  - Identify cycle-consuming per-tick operations in the COP subsystem.
  - Define expected O() behavior for proposal admission, queue maintenance, staging, and commit transitions.
  - Ensure no unbounded loops or data-dependent worst-case growth.
  - Document dependence on input cardinality N and explicit queue bounds.

### 50.36.TCU.20 Design for deterministic behavior
- Obligation ID: 50.36.TCU.20
- Satisfies: 10.50.34.TCU.20
- Design notes:
  - Define which code paths are active for a given scenario ID.
  - Ensure fixed seed + fixed N + fixed configuration + fixed hardware/runtime profile
    produces the same execution path, queue ordering, and cycle band.

### 50.36.TCU.30 Provisional-budget vs measured-budget
- Obligation ID: 50.36.TCU.30
- Satisfies: 10.50.34.TCU.30
- Design notes:
  - Document provisional-budget assumptions (min/typ/max and percent tick budget).
  - Specify where measured-budget will be recorded (30 capsules and 40 harness artifacts).
  - Specify harness evidence fields for future TCU promotion: scenario_id, seed, N, config_hash, cycles_measured.

### 50.36.TCU.40 Integration with scheduler and global tick budget
- Obligation ID: 50.36.TCU.40
- Satisfies: 10.50.34.TCU.40
- Design notes:
  - Show how provisional-budget fits into the global tick budget.
  - Define backpressure, shedding, or deferral behavior when measured-budget exceeds target.
