## 1. Purpose and Scope

The **Input Basin (InB)** is the Track H external-signal intake stage. It is responsible for:

- bounded, non-inferential intake of external signals
- deterministic surface-form canonicalization (Unicode NFKC; no semantic expansion)
- schema/wire validation and profile activation at safe boundaries
- transport/session metadata isolation from semantic payload
- FIFO-ordered batch processing with fixed audit reason codes
- explicit versioned handoff to IIInB (`input_semantic_repair`) — not direct RB semantic routing
- tick-boundary first-stage execution without downstream basin invocation or MTP mutation
- deterministic diagnostic export for replay and audit

InB **does not**:

- perform semantic shorthand repair or USP apply (IIInB territory)
- mutate MTP, Pipeline B envelopes (`exec_plan`, `exec_trace`), or semantic core
- interpret shorthand, vague, or incomplete input semantics
- participate in the RB→OB→TR→TB basin chain

This design specification defines architectural contracts, operation flow, IO semantics, observability obligations, and verification coupling for InB. It is scoped to obligations established in 10.50.100 (tracing to 20.100). InB is the `.100` component in the uniform cross-layer numbering scheme (40.100 / 30.100 / 10.50.100 / 50.100).

**Out of scope (W1):** semantic repair, USP/UPI, full Pipeline A basin chain, execution-signature-bound profile precedence (HLR-013 partial), immutable registry export (HLR-017 partial).

## 3. Contracts and Invariants

**Core invariants (normative, from 10.50.100 + 30.100 evidence)**

- **Non-inferential:** InB SHALL NOT infer, expand, or repair semantic content. Surface normalization only (HLR-001–003, -026).
- **Deterministic canonicalization:** Identical raw inputs under identical profile/schema context SHALL yield identical canonical surface forms and accept/reject outcomes (HLR-004–006, -018–021).
- **Bounded intake:** Payload, token, and field limits enforced with fixed audit reason codes; oversize/malformed inputs rejected or degraded deterministically (HLR-007–012, -025).
- **Transport isolation:** Session/transport metadata SHALL NOT contaminate semantic payload fields (HLR-008).
- **FIFO order:** Batch intake order preserved in accept sequence and diagnostic export (HLR-009–010).
- **Provenance and replay:** Accepted records carry intake provenance suitable for platform-independent replay (HLR-011, -018, -022).
- **Tick-boundary first stage:** `run_first_stage` executes at tick boundary without invoking downstream basins or mutating MTP (HLR-019–020, -023).
- **Zero-event window:** Empty intake windows produce deterministic zero-event semantics (HLR-021).
- **Profile gating:** Profile activation at safe boundary; unsupported schema/profile/wire-map rejected deterministically (HLR-014–016).
- **IIInB handoff only:** On accept, emit versioned handoff with `next_stage: input_semantic_repair`; ordering `InB → IIInB → RB` (HLR-10.50.100-001, HLR-20.101-003).

**Wire and schema identifiers (HLR-10.50.100-002)**

- Intake schema: `inb_intake_v1` (or successor under explicit migration)
- Wire map: `inb_wire_v1`
- Handoff contract: `inb_to_iiinb_v1`

**Reason codes**

- All emitted reason codes MUST be members of the fixed `REASON_CODES` registry (runtime assert-on-emission in reference impl).
- Full immutable versioned dictionary export remains open (HLR-017 residual).

**Reject/degrade contract**

- Unsupported schema, profile mismatch, wire-map failure, and oversize payloads SHALL produce deterministic reject records with stable reason codes — never silent drop or nondeterministic ordering.

## 4. Operation Flow and State Transitions

**Track H intake ordering (normative)**

1. External signal arrives at InB intake boundary
2. Schema/wire validation and profile check
3. Non-semantic canonicalization (NFKC surface norm)
4. Bounded accept or deterministic reject/degrade
5. On accept: emit `inb_to_iiinb_v1` handoff with `next_stage: input_semantic_repair`
6. IIInB consumes handoff (not RB directly)

InB is **not** in the RB→OB→TR→TB chain.

**Per-tick first stage (`run_first_stage`)**

- Invoked at tick boundary only
- Processes pending intake batch in FIFO order
- Does NOT invoke IIInB, RB, or other downstream modules inline
- Does NOT mutate MTP or Pipeline B envelopes
- Evidence: `positive_tick_boundary_first_stage` (30.100)

**Profile activation**

- `request_profile_activation` at safe boundary
- Reject unsupported profiles with deterministic reason codes

**State transitions (reference impl shape)**

- Intake queue: append on receive, drain in FIFO on process
- Per-output: `accepted` | `rejected` with reason_codes list
- Handoff emitted only on accept path
- Diagnostic digest refreshed on export

## 5. Data and IO Contract

**Intake input (normative shape, per 40.100 evidence)**

- `schema_version`: MUST be `inb_intake_v1` (or migrated successor)
- `wire_version`: MUST be `inb_wire_v1`
- `payload`: bounded semantic surface (pre-repair)
- `transport_meta`: isolated from semantic fields
- `profile_id`: for profile equality / reject checks

**Accept output / IIInB handoff (`inb_to_iiinb_v1`)**

- `contract_version`: `inb_to_iiinb_v1`
- `next_stage`: `input_semantic_repair`
- `canonical_surface`: NFKC-normalized string
- `schema_version`, `wire_version`, `profile_id`
- `intake_provenance`: replay-pinning fields per 20.100
- `reason_codes`: `[]` on accept

**Reject output**

- No handoff emitted
- `reason_codes`: fixed registry member(s)
- Deterministic ordering in batch diagnostics

**Diagnostic export (`export_intake_diagnostics`)**

- Deterministic sorted-key JSON over output list
- Order-independent of input list ordering (evidence: `positive_diagnostic_export_ordering`)
- Suitable for replay digest comparison

All serialization SHALL use deterministic sorted-key JSON (`separators=(",", ":")`, `ensure_ascii=True`).

## 6. Observability and Logging

InB SHALL emit:

- per-intake accept/reject outcome with reason codes
- handoff contract fields on accept path
- `export_intake_diagnostics` with stable key ordering
- tick-boundary first-stage audit without downstream side effects

Logs and diagnostics MUST support deterministic replay: identical intake sequences produce identical diagnostic exports (30.100 determinism scenarios).

Integrated replay observability: downstream [30.207](../../30_verification/30.207_replay_prototypes/) composes live InB output in C7-B intake-path scenarios.
