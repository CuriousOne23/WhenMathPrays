# 50.120_Experiment Runner Testing Design

## 1. Purpose and Scope

This design support specification defines deterministic experiment-run orchestration and batch validation behavior promoted from canonical requirements and verification evidence.

## 2. Source Index

- `10_thought_simulator_req/50_design/10.50.90_experiment_runner_requirements.md`
- `30_verification/30.90_experiment_runner/30.90_experiment_runner_verification_capsule.md`
- `30_verification/30.90_experiment_runner/30.90_experiment_runner_requirements_delta.md`
- `30_verification/30.30_verification_glossary.md`

## 3. Contracts and Invariants

- Equivalent single-run requests produce deterministic run identities and result fields.
- Batch result ordering and summary digests are deterministic for equivalent input sets.
- Invalid request constraints are rejected before execution.

## 4. Operation Flow and State Transitions

- Validate experiment request contract.
- Compute deterministic run identity.
- Execute single-run or batch path.
- Emit replay-safe result payload and verification digest.

## 5. Data and IO Contract

Input fields:
- `experiment_id`
- `max_ticks`
- `seed`

Output fields:
- `run_id`
- `status`
- `verification_digest`
- batch summary (`result_count`, batch digest)

## 6. Observability and Logging

- Execution summaries must include deterministic digest outputs for replay comparability.
- Contract-validation failures must be deterministic and explicit.

## 7. Verification Obligations

- Deterministic replay for single-run and batch-run scenarios is mandatory.
- Negative-path validation for invalid limits and malformed request sets is mandatory.

## 8. Traceability

- HLR anchor: `HLR-20.490-001`, `HLR-20.490-002`, `HLR-20.490-003`
- Verification evidence: `experiment_runner_verification_run_2026-05-28.json`
- Canonical requirement anchor: `10.50.90_experiment_runner_requirements.md`

## 9. Change Control

- Changes to run identity semantics or batch ordering policy require synchronized updates in canonical requirements and verification artifacts.

## CPU Execution Cycle Design Obligations (per 10.50.90.TCU and 20.150)

### 50.83.TCU.10 Design for bounded per-tick cost
- Obligation ID: 50.83.TCU.10
- Satisfies: 10.50.90.TCU.10
- Design notes:
  - Identify cycle-consuming per-tick operations in the experiment-runner subsystem.
  - Define expected O() behavior for each operation.
  - Ensure no unbounded loops or data-dependent worst-case growth.
  - Document dependence on input cardinality N and explicit bounds.

### 50.83.TCU.20 Design for deterministic behavior
- Obligation ID: 50.83.TCU.20
- Satisfies: 10.50.90.TCU.20
- Design notes:
  - Define which code paths are active for a given scenario ID.
  - Ensure fixed seed + fixed N + fixed configuration + fixed hardware/runtime profile
    produces the same execution path and cycle band.

### 50.83.TCU.30 Provisional-budget vs measured-budget
- Obligation ID: 50.83.TCU.30
- Satisfies: 10.50.90.TCU.30
- Design notes:
  - Document provisional-budget assumptions (min/typ/max and percent tick budget).
  - Specify where measured-budget will be recorded (30 capsules and 40 harness artifacts).
  - Specify harness evidence fields: scenario_id, seed, N, config_hash, cycles_measured.

### 50.83.TCU.40 Integration with scheduler and global tick budget
- Obligation ID: 50.83.TCU.40
- Satisfies: 10.50.90.TCU.40
- Design notes:
  - Show how provisional-budget fits into the global tick budget.
  - Define backpressure, shedding, or deferral behavior when measured-budget exceeds target.
