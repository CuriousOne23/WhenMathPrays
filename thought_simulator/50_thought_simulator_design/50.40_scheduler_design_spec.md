## 1. Purpose and Scope

The Scheduler is the **deterministic execution controller** of the TS. It is responsible for:

- ordering module execution  
- enforcing cycle boundaries  
- enforcing timing budgets  
- managing interrupt windows  
- coordinating preemption  
- ensuring deterministic sequencing  
- validating module readiness  
- routing supervisory and regulatory events  

The scheduler **does not**:

- perform cognitive inference  
- modify semantic content  
- alter TP or MTP state  
- interpret OB/TB/IB/COB-OPS payloads  

This design specification defines the architectural contracts, data/IO semantics, operational behavior, observability obligations, and verification coupling for the Scheduler. It is scoped to the contracts and invariants established in 10.50.40 (which in turn trace to 10.10.40 and 20-series).

The Scheduler is the .40 component in the uniform numbering scheme.

Scheduler does **not**:

- Define numeric TCU budgets or policies (20.95 / 50-series numeric areas; see 10.50.40.TCU)
- Perform regulation (Regulator territory per 10.10.40 separation of concerns)
- Issue supervisory actions (GB territory)

## 3. Contracts and Invariants

**Core Invariants (normative, from 10.10.40 principles + 10.50.40 HLRs 001-008)**
- Non-cognitive: neither component performs semantic interpretation or inference. Numeric attributes (energy/coherence on ThoughtPoints) used only as opaque policy inputs in exploratory WRR; no mutation of caller dicts or core cognitive state (TP, MTP, OB, RB, TB).
- Deterministic control: execution order is fixed, reproducible, and cycle-bounded. Identical effective inputs + event sequence + bounded state SHALL always produce identical outputs + verification_digest (HLR-001).
- Boundedness: all timing, ΔH%, fan-out, resource usage (including history_max), and TCU are explicitly bounded. No unbounded or data-dependent worst-case growth (HLR-005, 10.50.40.TCU.*).
- Replayability: all control-plane decisions must be reconstructable. Full event history with lineage (state_counter, tick, selected_tp_ids, policy, payload), sorted-key JSON, verification_digest for tamper/replay detection.
- Safety-first: supervisory and regulatory constraints override cognitive processing. Scheduler enforces envelopes but does not mutate ΔH% or core state.
- Isolation: scheduler and regulator cannot mutate cognitive state directly. Scheduler controls *when* modules run; Regulator controls *whether*; GB controls *why*. Forbidden: regulator reordering modules, scheduler modifying ΔH%, etc.
- Transparency: all actions are logged with lineage and reason codes (interrupts, timing events, regulatory actions, supervisory escalations, cycle boundaries, preemption events, safety violations).
- Selection deterministic and replayable for identical inputs and event sequences (HLR-001).
- Fairness policy provides bounded progress for active ThoughtPoints and prevents starvation under configured limits (HLR-002).
- Contract validation rejects malformed inputs that could break deterministic execution (empty TP IDs, non-monotonic ticks, unsupported policy values) (HLR-003).
- Scheduler shall emit rich, replay-safe observability including tie_break_rationale, cohort_metadata, window/preempt context, budget_status, fairness counters (wait_ticks, total_selected, last_scheduled_tick), and full event history (HLR-004).
- Scheduler shall enforce bounded internal state (history_max) consistent with 10.10.40 safety envelopes and 20.150 TCU constraints (HLR-005).
- Scheduler shall support and deterministically log interrupt windows (pre-OB, post-TB, post-TR, pre-merge, etc.) and preemption in the scheduling contract and observability (HLR-006).
- Scheduler shall support deterministic cohort selection and merge semantics, emitting cohort_metadata (is_cohort, cohort_size, merge_semantics="deterministic_stable_order") when max_active > 1 (HLR-007).
- Scheduler shall apply deterministic tie-breaking with explicit tie_break_rationale and provenance (e.g., stable tp_id ordering) when priority signals are equal (HLR-008).

**Scheduler Contract (normative at design layer, from 10.50.40 section 6; reference impl in 40.270 prototype.py)**
- **from_contract payload** (initialization): tick (non-negative int), deterministic_mode (bool, default true), policy ("round_robin" | "weighted_round_robin"), max_active (positive int), history_max (positive int), thoughtpoints: list of objects with at minimum tp_id (non-empty string), energy (non-negative float), coherence (non-negative float); optional state fields total_selected, wait_ticks, last_scheduled_tick.
- **apply_contract event** (for schedule_tick): event_type: "schedule_tick", tick: strictly increasing from prior, optional: policy, max_active (updates), optional control-plane context (non-cognitive): window (e.g. "pre_ob", "post_tb", "post_tr", "pre_merge", "none"), budget_tcu (non-negative int), preempt (bool).
- **snapshot / output**: module, contract_version, tick, deterministic_mode, policy, max_active, round_robin_cursor, state_counter, history_max, last_selection_rationale (string), last_cohort_metadata (object with is_cohort, cohort_size, merge_semantics), last_budget_status (object), last_window, thoughtpoints: list with full state (tp_id, energy, coherence, total_selected, wait_ticks, last_scheduled_tick), history: list of events with event_type, tick, state_counter, selected_tp_ids, policy, payload (including tie_break_rationale, cohort_metadata, window, preempt, sim_tcu, budget_status), verification_digest for replay integrity.

All serialization SHALL use deterministic sorted-key JSON (separators=(",", ":"), ensure_ascii=True). The contract SHALL remain stable (additive fields only for backward compatibility). Reference implementation in 40.270 enforces these via _require_* helpers, _json_safe, _digest_from_payload.

## 4. Operation Flow and State Transitions

The scheduler enforces the canonical TS pipeline order (from 10.10.40 §3.2):
1. Routing
2. OB extraction
3. Semantic write phase (OB/TB/IB updates that may set TP.tr_needs_update = true)
4. RB TR-gate evaluation (route to TR routine iff TP.tr_needs_update = true)
5. TR routine execution and TP.TR refresh (clear TP.tr_needs_update only on success)
6. IB lifecycle transitions
7. COB-OPS operator execution
8. Merge
9. GB supervisory review
10. Regulation
11. Commit to MTP
12. Cycle boundary enforcement

No module may execute outside its assigned position.

A TS cycle consists of (from 10.10.40 §3.3):
- pre-cycle checks
- module execution sequence
- TR dirty-flag gate and conditional TR execution
- interrupt window
- supervisory review
- regulation
- commit
- cycle boundary enforcement

The scheduler guarantees:
- no cross-cycle state leakage
- deterministic cycle start and end
- monotonic timestamps
- strict ordering of events

**Timing Model (from 10.10.40 §3.4):** Each module has maximum/ minimum/ expected execution time, interruptible/non-interruptible regions. If a module exceeds its timing budget: regulator notified, scheduler may preempt, GB may escalate.

**Interrupt Windows (from 10.10.40 §3.5):** The scheduler defines explicit interrupt windows: pre-OB, post-TB, post-TR routine, post-IB, pre-merge, post-merge, pre-commit. Interrupts outside these windows are queued unless L0. These windows implement deterministic safe-boundary handling for interpretation, merge, and end-of-cycle supervisory actions.

**Scheduler Message Handling (from 10.10.40 §3.6):** The scheduler receives: interrupts, supervisory requests, regulatory events, module readiness signals, timing violation alerts, CIL supervisory escalation events, GB-approved COP proposal application events, TP.tr_needs_update gate signals and TR execution success/failure outcomes. The scheduler must: classify events, determine priority, enforce ordering, route events to GB or regulator, log all actions.

**Reference Implementation Flow (from 40.270 prototype, for illustration only; normative is the contracts + 10.10.40):**
- from_contract: normalize/validate input, create ThoughtPoint map, initialize state (tick, policy, max_active, history_max, cursors=0, empty history), record "created" event, refresh digest.
- apply_contract (per tick): validate event_type=="schedule_tick" and tick strictly increasing; update policy/max_active if provided; extract window/preempt/budget_tcu; call _select_for_tick (RR: rotation by cursor + stable id; WRR exploratory: sort by - (1.0*wait + 0.1*energy + 0.1*coherence) + stable id); update per-TP fairness counters (increment total_selected/wait_ticks=0/last or wait+=1); set tick; build rich payload (max_active, policy, thoughtpoint_count, tie_break_rationale, cohort_metadata, window, preempt, sim_tcu, budget_status); _record_event (append, trim to history_max, increment state_counter, refresh digest); return snapshot().
- State transitions: monotonic tick, history append+trim to bound, fairness state per ThoughtPoint, cursor advance (RR), digest recompute on every change. assert_invariants checks non-empty unique TPs, positive max_active, history <= max, digest matches.

Interrupt/preempt and window are passed through in payload and surfaced in last_* for observability (per HLR-006).

Cohort when max_active>1: selection of N, metadata emitted (per HLR-007).

## 5. Data and IO Contract

See section 3 above for the full normative contract elements (from 10.50.40). The reference implementation in 40.270_scheduler_prototypes/prototype.py demonstrates one realization (ThoughtPoint dataclass, SchedulerEvent, SchedulerPrototype with the methods, _json_safe, _digest, etc.).

Key data structures (normative shape, types per 10.50.40):
- ThoughtPoint view in snapshot: tp_id, energy, coherence, total_selected, wait_ticks, last_scheduled_tick.
- Event in history: event_type, tick, state_counter, selected_tp_ids (list), policy, payload (rich as specified).
- Payload in schedule_tick events: includes the control fields + tie_break_rationale, cohort_metadata, window, preempt, sim_tcu, budget_status.

All values must pass the _require_* validation in the reference (non-empty strings, non-neg/positive ints/floats finite, etc.). Malformed inputs rejected deterministically (HLR-003).

## 6. Observability and Logging

Scheduler SHALL emit rich replay-safe observability per HLR-004 in every schedule_tick event and top-level snapshot: tie_break_rationale (string describing cursor/score/tie logic), cohort_metadata (is_cohort, cohort_size, merge_semantics), window, preempt, sim_tcu, budget_status; per-TP fairness counters (wait_ticks, total_selected, last_scheduled_tick); full history of events with lineage.

From 10.10.40 §7: Both scheduler and regulator must log: all interrupts, all timing events, all regulatory actions, all supervisory escalations, all cycle boundaries, all preemption events, all safety envelope violations. Logs must support deterministic replay.

The verification_digest (sha256 of sorted-key canonical JSON of snapshot body) provides tamper detection and replay integrity. History is bounded (history_max) and trimmed.

last_* fields in snapshot provide quick audit view without full history traversal.

- Full invariants verified (see 30.40 capsule and 40.270 capsule): non-cognitive, no core mutation, deterministic+replayable, bounded history/state, cycle/tick model, interrupt/preempt support, timing budget modeling, cohort/merge, rich obs emission, negative/safe degradation, safety envelopes/logging, full deterministic mode.

Reference implementation (40.270) and any conforming impl MUST:
- Support deterministic_mode.
- Enforce monotonic tick, contract validation, history bound, rich obs emission.
- Produce identical outputs + digest for identical inputs+events+initial state.
- Pass the invariants in assert_invariants.
