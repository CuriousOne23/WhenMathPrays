# 50.36.10_gb_signal_packet_format.md

**Document ID:** 50.36.10  
**Version:** 0.2  
**Date:** 2026-06-04  
**Status:** Finalized Design Decision

## Role in Development Flow
This document defines the data contract between Tier 1 (Signal Monitors) and Tier 2 (Supervisory Integrator) of the Governing Basin.

## 1. Design Decision: Canonical Signal Packet Format

**Decision:**  
All Tier 1 Signal Monitors SHALL emit signals using a standardized, deterministic `SignalPacket` structure.

**Rationale:**
- Provides clear, typed, and deterministic communication between tiers.
- Enables better logging, debugging, and replayability.
- Supports future extensibility while maintaining architectural discipline.

## 2. Signal Packet Definition

```python
@dataclass
class SignalPacket:
    monitor_id: str           # e.g., "DriftMonitor", "OscillationMonitor"
    signal_type: str          # "drift", "oscillation", "contradiction", "population"
    value: float              # Normalized magnitude (0.0 - 1.0)
    severity: float           # Severity of the condition (usually = value)
    timestamp: int            # Cycle number
    metadata: Dict[str, Any]  # Optional, kept minimal and non-semantic
```

## 3. Signal Types

| Signal Type      | Meaning                                 | Value Meaning                     | Typical Severity |
|------------------|-----------------------------------------|-----------------------------------|------------------|
| drift            | Sustained upward trend in ΔH%           | Severity of drift                 | High = concerning |
| oscillation      | Rapid fluctuation in state              | Intensity of oscillation          | High = unstable |
| contradiction    | High conflicting interpretations        | Level of semantic conflict        | High = messy input |
| population       | IB / trace count pressure               | Load level                        | High = overload risk |

## 4. Non-Goals (Design Boundaries)

Signal packets **SHALL NOT**:
- Contain semantic content or propositions
- Include multi-step reasoning or predictions
- Encode supervisory actions
- Include monitor-internal state
- Carry write-capable fields
- Grow large or complex

## 5. Design Constraints

**HLR-50.36.10-001:** All SignalPackets SHALL be immutable once created.  
**HLR-50.36.10-002:** Value and severity SHALL be normalized to [0.0, 1.0].  
**HLR-50.36.10-003:** The Supervisory Integrator SHALL treat missing signals as zero value / zero severity.  
**HLR-50.36.10-004:** Metadata SHALL be used sparingly and only for non-semantic diagnostic data.

## 6. Impact on System Requirements

**Positive Impacts:**
- Improves clarity and verifiability of Governing Basin behavior.
- Reduces risk of overload by enabling focused, typed signals.
- Makes the architecture more maintainable and extensible.

**Trade-offs:**
- Minor increase in data movement between tiers (acceptable).
