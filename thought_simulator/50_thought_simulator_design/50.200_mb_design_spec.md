## 1. Purpose and Scope

The Monitoring Basin (MB) is the canonical subsystem for non-intrusive, deterministic diagnostics, drift observation, stability reporting, and bounded what-if supervision within the TS pipeline.

MB provides structured observability and advisory monitoring outputs **without mutating TS core meaning-construction state** (TP, MTP, OB, RB, or TB).

This design specification defines the architectural contracts, data/IO semantics, operational behavior, observability obligations, and verification coupling for MB. It is scoped to the contracts and invariants established in 10.50.1500 (which in turn trace to 20.70).

MB does **not**:
- Perform semantic interpretation or evidence extraction (OB/TB authority)
- Issue authoritative supervisory actions (GB territory)
- Define numeric TCU budgets or policies (20.95 / 50-series numeric areas)

MB is the .39 component in the uniform numbering scheme and lives in the 50.30–50.200 dynamics/observability band for supporting docs when needed.

## 3. Contracts and Invariants

**Core Invariants (normative, from 20.70 + 10.50.1500)**
- Non-intrusion: MB SHALL NOT directly mutate TP/MTP/OB/RB/TB core meaning-construction state (HLR-10.50.1500-001 / HLR-20.070-003).
- Determinism: Identical effective MBInput + MTP context + seed-bounded state SHALL always produce identical MBOutput (HLR-10.50.1500-003 / HLR-20.070-004,011).
- Advisory-only: All recommendations and what-if flags are explicitly non-authoritative (HLR-10.50.1500-005 / HLR-20.070-008,026).
- Reproducibility & audit: Outputs SHALL support deterministic replay/audit with lineage (HLR-10.50.1500-010,012 / HLR-20.070-009,016).

**MBInput Contract (see 10.50.1500 for full schema)**
- schema_version, cycle, visibility_mode (enum), basin_telemetry (object), lane_identifiers (array<string>), lineage (object with id), mtp_snapshot (with delta_h_trend, active_ib_count, oscillation_flag, contradiction_level), stability_metadata (optional).

**MBOutput Contract (see 10.50.1500 for full schema)**
- schema_version, diagnostics_summary, drift_indicators (array), advisory_recommendations (array), what_if_flags (array with flagged/non_authoritative/policy_gated/logged/rationale), execution_diagnostics (incl. lifecycle_state, flush_epoch), telemetry (incl. sampling_density, user_notification), overflow (full canonical schema always present per HLR-10.50.1500-014).

**Threshold & Policy Governance (HLR-10.50.1500-011,013)**
All decision boundaries (drift classification, overflow trigger, what-if activation, visibility cost notification) and what-if gating SHALL be externally configurable via a deterministic, auditable policy engine. The prototype uses exploratory values only; production values come from 20.95/50-series.

**Lifecycle Model (HLR-10.50.1500-015)**
MB SHALL expose lifecycle_state (e.g. "running") and flush_epoch per a canonical 10-series model (states, transitions, and epoch semantics to be detailed in supporting docs).

**Malformed Input Handling (HLR-10.50.1500-016)**
Deterministic fallbacks for missing/malformed/contradictory fields. No probabilistic reconstruction.

**Consumption Boundaries (HLR-10.50.1500-017)**
Outputs are read-only consumable by GB/IB/OuB without creating supervisory loops or core mutation.

## 4. Operation Flow and State Transitions

MB is invoked per-tick (or on demand) with an MBInput snapshot. It performs read-only analysis and emits MBOutput.

Typical flow (derived from 40.350 prototype and 20.70/10.50.1500):
1. Coerce/validate input (apply fallbacks per HLR-016 if malformed).
2. Extract signals (delta_h_trend, active_ib_count, oscillation_flag, contradiction_level, etc.).
3. Update bounded internal drift history (eviction per HLR-030).
4. Compute visibility-adjusted sampling and cost notification (if high/full).
5. Generate diagnostics_summary, drift_indicators (recent), advisories (if elevated), what_if_flags (explicitly gated/flagged if conditions met).
6. Compute overflow using full canonical schema (always emitted).
7. Populate execution_diagnostics and telemetry.
8. Return MBOutput (no side effects on caller state).

Internal state (drift_history, intervention_count) is bounded and reset-capable for reproducibility. No persistent cross-run state beyond what is supplied in lineage/MTP snapshot.

State transitions for the MB instance itself are minimal (running → degraded on overflow policy, etc.) and exposed via execution_diagnostics.lifecycle_state.

## 5. Data and IO Contract

See §3 (Contracts) and the full schemas in 10.50.1500 for normative field definitions, required/optional, and serialization rules (schema_version, deterministic sorted-key JSON roundtrips per HLR-012).

MBInput is the sole entry point. MBOutput is the sole exit point. All fields are JSON-serializable with finite numbers, no NaN/Inf.

Prototype reference implementation (40.350) now exactly matches these contracts (post-alignment).

## 6. Observability and Logging

MB is itself the primary observability subsystem for diagnostics and drift.

It SHALL:
- Emit the full telemetry and execution_diagnostics in every output (for GB/IB/OuB and audit).
- Support visibility modes that control only its own sampling density (core TP/MTP visibility remains explicit and safe).
- Log all what-if activations with full rationale (flagged, policy_gated, non-authoritative).
- Preserve lineage in drift_indicators and outputs.
- Report flush_epoch and lifecycle_state for replay correlation.

Cross-cutting: integrates with 50.80 logging/observability (MB outputs feed into broader event log and observability contracts; MB does not replace 50.80).

## 7. Verification Obligations

Verification SHALL cover:
- Determinism/reproducibility (identical inputs → identical outputs across independent instances and reruns).
- Non-intrusion (no mutation of any input data).
- Full coverage of the 8 exploration scenarios from 40.350 software_description (stable, high-drift/what-if, high-pop/overflow, oscillation, visibility high, noisy/contradiction, reproducibility, lifecycle).
- Schema compliance (roundtrip serialization, schema_version presence, full overflow even on flag=false).
- Fallback behavior on malformed inputs.
- Bounded history and eviction.
- Lineage and provenance preservation.

Evidence is captured in 30.200 (capsule + delta + artifact) and must be re-run on any material change to contracts or prototype.

Negative paths (malformed input, policy denial for what-if, overflow degradation) SHALL be exercised.
