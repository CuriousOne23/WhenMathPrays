# 50.05_Software Spec Construction Guide

## Role in the Development Flow

This document serves as the **primary construction methodology** for the 50-series design layer. It governs how exploratory results from the 40-series and canonical anchors from the 10-series are turned into concrete subsystem design specifications.

All design decisions made using this guide SHOULD be traceable back to 20-series guidance and 40-series evidence, and SHOULD feed mature, proven specifications into the 10-series. This document is **process guidance**, not a final specification itself.

## Pre-Construction Verification Requirement

**Before starting or updating any document in the 50-series**, the following **MUST** be completed and approved:

- Relevant 10.50 and 30-series files **MUST** be created for the component
- All 30-series verification documents (`verification_capsule.md`, `requirements_delta.md`, etc.) must be up-to-date and approved
- Explicit human approval of the verification evidence must be obtained

**Please refer to `30.00_verification_user_guide.md`** (in `30_verification/`) for detailed verification procedures, required files, three-flow documentation, and approval standards.

This ensures that 50-series design decisions are grounded in real evidence and aligned with the full development flow.

## Three-Flow Documentation Requirement

All documents in the 50-series **SHALL** explicitly distinguish and document the contribution of each flow:

- **Forward Flow**: Content driven by 20-series guidance and intent.
- **Backward Flow**: Content driven by evidence and discoveries from the 40-series.
- **Iterative Design Flow**: Content driven by design decisions made in the 50-series itself.

Each 50-series document must include a **Flows Alignment Statement** that clearly identifies which sections/decisions come from each flow, plus a short **Agreement Statement** explaining whether the three flows are in agreement, any remaining tension, and the justification for the final design position.

This ensures full traceability and architectural coherence across the entire project.

## 50-Series Numbering Convention (3-Level Support)

The 50-series supports up to **three levels** of documents for clarity and organization:

- **Level 1 (50.xx)**: Main subsystem design decision or specification file (e.g., `50.36_gb_design_decisions.md`)
- **Level 2 (50.xx.yy)**: Supporting detailed design documents for the same subsystem (e.g., `50.36.10_gb_signal_packet_format.md`)
- **Level 3 (50.xx.yy.zz)**: Very detailed or specialized sub-documents (used rarely)

**Rules:**
- Every Level 2 and Level 3 document **MUST** be referenced in its parent Level 1 document.
- The parent (Level 1) document **SHALL** include a section titled **"Supporting Documents"** that lists document number, full filename, short description, and current version.

## 1. Purpose

This document defines the generic methodology for constructing subsystem software specifications in `50_thought_simulator_design` from lifecycle descriptions, canonical requirements, and verification sources.

For user-facing forward/backward flow runbooks and prompt templates, see `../USER_GUIDE.md`.

It is the design-layer bridge between:
- canonical requirement sources in `10_thought_simulator_req/`
- exploratory requirement context in `20_requirements/`
- lifecycle and verification workspace sources in `30_verification/`
- exploratory implementation context in the playground layer
- subsystem design specifications in `50_thought_simulator_design/`

This guide is process-governing and naming-governing. It does not replace subsystem requirements or subsystem lifecycle documents.

## 2. Definitions and Scope

### 2.1 What is a lifecycle description (`software_description.md`)?

A lifecycle description is a behavioral narrative that describes how a subsystem evolves over time, including state transitions, invariants, and operational phases.

Lifecycle descriptions are authored in natural language and are typically located under `30_verification/`.

A lifecycle description is **not**:
- a design specification
- an API definition
- a requirements document
- an implementation document

### 2.2 What is a subsystem design specification?

A subsystem design specification is the authoritative architectural definition of a subsystem in the design layer.

It is derived from requirements and lifecycle behavior, and it defines contracts, invariants, IO semantics, observability obligations, verification obligations, traceability, and change control.

Subsystem design specifications are located under `50_thought_simulator_design/`.

A subsystem design specification is **not**:
- a requirements document
- a lifecycle document
- a test plan
- an implementation artifact

### 2.3 Scope

This methodology applies to all current design macros/subsystems in this directory:
- System Architecture
- Geometry Engine
- Dynamics Engine
- Interaction Layer
- Data Structures
- Error Handling
- Logging and Observability
- Testing Strategy
- API Contract
- Core Contract
- UI Contract

## 3. Construction Workflow (Generic)

### 3.0 Pre-Execution Gate (Required)

Before executing this guide for a subsystem, confirm the following:
- For any `40.*` playground module input, the module `software_description.md` has explicit human approval.
- A canonical requirement anchor exists in `10_thought_simulator_req/` for the target decision set.
- Required promotion artifacts exist (promotion summary and, when non-trivial, ADR record) under `10_thought_simulator_req/docs/`.
- The target verification capsule/delta exists in `30_verification/` for evidence binding.
- For TR/routing-affecting specs, canonical architecture anchors in `10_thought_simulator_req/10_system_architecture` are synchronized.

If any of these are missing, stop and issue a human prerequisite handoff.

### 3.0A Controlled Backward Canonical Flow Gate (10 → 30/40/50)

This guide allows backward-flow updates initiated by canonical-anchor changes in `10_thought_simulator_req/`, but only in a controlled and confirmed manner.

(No auto-propagation from 20-layer edits alone.)

### 3.0B Ambiguous Flow-Direction Confirmation Rule

If an instruction is ambiguous, the AI Agent must obtain explicit human confirmation of the intended direction (forward or backward) before proceeding.

### 3.1 Identify source authority

For each subsystem design spec, identify the authoritative source set first (canonical requirements, architecture references, lifecycle documents, verification evidence, etc.).

### 3.2 Extract behavior and contracts

Extract subsystem behavior into four categories:
- invariant contracts
- operational flow
- data and IO contracts
- verification obligations

### 3.3 Map behavior to requirements

Every normative design statement must map to a requirement source.

### 3.4 Integrate cross-cutting concerns

Explicitly integrate interfaces, observability, testing, performance, stability, safety, and traceability.

### 3.5 Define design-spec output structure

Each subsystem software specification should include at minimum:
- purpose and scope
- source index
- contract and invariants
- operation flow and state transitions
- IO/data contract
- observability and verification obligations
- traceability references
- change control rules

### 3.6 Deterministic vs nondeterministic behavior

If a subsystem supports deterministic and nondeterministic modes:

- deterministic behavior must be explicitly defined as normative behavior
- nondeterministic behavior must be isolated from deterministic contracts
- randomness, seed handling, and reproducibility expectations must be documented
- verification must include deterministic rerun coverage

### 3.7 Embedding and state-vector rules (when applicable)

If a subsystem uses embeddings or state vectors, the design specification must define:

- dimensionality constraints
- update rules
- split/merge behavior
- serialization rules
- compatibility and validation rules

The script scans the entire project for references in:
- All `.md` files (User Guides, all READMEs, cross-layer links, titles, LLR frontmatter).
- `.py` files (with extra warnings, as string matches in code/comments/tests require human review).
It also maintains a dated history log in `archive/refactors/` after each successful run.

## 5. Maintenance and Change Control

- Update a subsystem spec when its authoritative requirements or lifecycle behavior changes materially.
- Preserve additive, lossless history during migrations.
- Do not duplicate requirements text as a new source of truth in design specs.
- Keep links valid and relative from the document location.
- Record unresolved requirement/design mismatches in the corresponding delta log before finalizing the spec.
- Treat `30_verification/30.30_verification_glossary.md` as a process-controlled shared vocabulary: terminology changes in capsules/deltas/specs must be reflected there first, then propagated.
- The 50-series has its own `50_thought_simulator_design/50.01_50_series_glossary.md` (with accompanying `glossary_term_registry.json`). 
  - A non-blocking CI warning check (`validate_50_glossary_alignment.py`) runs on changes to 50 design documents. It notifies when the glossary may not be fresh (missing declared terms, extra terms, or new candidate terms observed in design files).
  - The helper script `update_50_glossary.py` (in `scripts/`) can be run locally or via terminal to scan design docs, report drift, and generate reviewable proposal files (`--write-proposals`). It performs the mechanical work of term extraction and diffing to save tokens/context, but produces only proposals — no files are modified without explicit human review and decision.
  - The team always reviews warnings/proposals and decides what (if anything) to update. There is no hard enforcement for the 50 glossary.

For changes initiated by updated `10.10.*` architecture anchors, design specs must include explicit conformance text for any applicable TP/TR dirty-flag behavior and must not retain legacy wording that implies unconditional TR execution.

### 5.2 Revision control and release-coupling rule

When a subsystem design specification in `50_thought_simulator_design/` cites evidence from `30_verification/`, the cited verification artifacts are treated as release evidence for that design version.

Rule set:

- requirements in `10_thought_simulator_req/` remain normative
- design specs in `50_thought_simulator_design/` remain architectural contracts
- cited verification artifacts in `30_verification/` remain auditable evidence tied to the released design version
  (Future high-fidelity test benches will also feed 30-series verification evidence via the 30.tb/ structure.)

If cited verification evidence changes materially:

- update the impacted design spec version
- refresh traceability/evidence references
- update the relevant verification capsule and requirement delta records

### 5.3 Backward-Flow Change Control Rule

When canonical anchors in `10_thought_simulator_req/` are updated and propagation into design is required:

- treat the canonical anchor update as the normative trigger event
- require synchronized updates across `30_verification`, `40_thought_simulator_playground`, and impacted 50-specs
- block release coupling for affected specs until cross-layer references are fully synchronized
- record a cross-layer impact log listing updated files and unresolved follow-ups (if any)
- record whether the initiating canonical anchor change was promoted from `20_requirements/` and cite the rationale lineage path(s)
- require integrity-check evidence in the execution log (reference consistency, glossary consistency, and HLR/LLR mapping completeness)
- require final backward-flow completion assertion in execution log: `Forward-Equivalence State: YES`
- treat backward flow as incomplete until all 50-series design files pass synchronization review for the updated canonical anchors

## 6. Macro-Specific Construction Sections

### 6.1 TP Macro (Dynamics/TP Lifecycle)

#### Source set

- Lifecycle design source:
  - `30_verification/30.20_tp_lifecycle/30.20_tp_lifecycle_verification_capsule.md`
- Canonical TP requirements source:
  - canonical TP requirement anchor in `10_thought_simulator_req/` (create via promotion protocol if missing)
- Supporting verification and traceability sources:
  - `30_verification/30.20_tp_lifecycle/30.20_tp_lifecycle_verification_capsule.md`
  - `30_verification/30.20_tp_lifecycle/30.20_tp_lifecycle_requirements_delta.md`
  - subsystem lifecycle `software_description.md` from the TP playground module (exploratory narrative source)
  - `20_requirements/20.40_ob_requirements.md`
  - `20_requirements/20.200_traceability_matrix.md`
  - `20_requirements/20.90_ib_requirements.md`
  - `20_requirements/20.30_ts_functional_model.md`
  - `30_verification/30.30_verification_glossary.md`
  - `20_requirements/20.200_traceability_matrix.md`

#### Method

- Extract lifecycle behavior from `software_description.md` as design vocabulary.
- Map each lifecycle rule to canonical TP requirements.
- Reconcile with verification evidence and requirement deltas.
- Keep terminology aligned with the canonical glossary.
- Express final TP design spec contracts for identity, entropy, provenance, split/merge, serialization, observability, and verification.

#### Required TP design-spec content

- purpose and scope
- source document index
- lifecycle contract summary
- TP identity and invariants
- TP state model and lifecycle operations
- entropy behavior and determinism requirements
- split and merge behavior
- provenance and lineage rules
- serialization and artifact contract
- observability and logging contract
- verification and validation contract
- traceability references
- maintenance and change-control rules

### 6.2 Geometry Macro

- Build from manifold/geometry architecture and visualization requirements.
- Define projection contracts, observer-boundary constraints, and deterministic transform expectations.
- Link geometry outputs to observer-only guarantees and non-causality constraints.

### 6.3 Dynamics Macro

- Build from TS state-machine, basin flow, program-flow, and stability requirements.
- Define tick-phase ordering, phase purity boundaries, and deterministic scheduling behavior.
- Separate TP-specific contracts from global dynamics contracts.

### 6.4 Interaction Macro

- Build from interaction model and interface requirements.
- Define command/event boundaries between observer tools and core mechanics.
- Enforce read-only observer and no core-state mutation from UI/observer channels.

### 6.5 Data Structures Macro

- Build from TS data model and data-structure architecture requirements.
- Define canonical structures, compatibility rules, and serialization invariants.
- State allowed schema evolution and backward compatibility expectations.

### 6.6 Error Handling Macro

- Build from error/stability and safety requirements.
- Define failure classes, fail-safe ordering, and recovery/resume boundaries.
- Specify mandatory diagnostics and snapshot behavior on critical faults.

### 6.7 Logging and Observability Macro

- Build from observability, interfaces, and testing requirements.
- Define mandatory log fields, monotonic counter expectations, and snapshot content.
- Specify overhead control, mode behavior, and replayability obligations.

### 6.8 Testing Strategy Macro

- Build from testing/validation requirements and traceability matrix.
- Define levels, determinism tests, regression obligations, and evidence outputs.
- Require requirement-to-test mapping and runtime requirement emission where applicable.

### 6.9 API Contract Macro

- Build from interfaces/IO and non-functional requirements.
- Define API surface stability, versioning, and machine-readable output guarantees.
- Require explicit contract for deterministic-mode behavior and schema versioning.

### 6.10 Core Contract Macro

- Build from core architecture, state-machine, and invariants across requirements.
- Define non-negotiable engine constraints and subsystem boundary rules.
- Provide normative contracts that all other subsystem specs must satisfy.

### 6.11 UI Contract Macro

- Build from interaction and observer-layer requirements.
- Define UI constraints as consumer-only, non-causal, and failure-isolated from core.
- Specify display fidelity, performance envelope, and error-isolation behavior.

### 6.12 Monitoring Basin (MB) Macro

- Build from 20.70 MB requirements, 10.50.39 design requirements, and the approved 40.39 software_description.md (lifecycle narrative) plus 40.39 Phase B executable evidence (prototype + harness + artifact) and 30.39 verification record.
- Define the canonical MBInput/MBOutput schemas (with schema_version, deterministic sorted-key serialization, and forward/backward compatibility per 10.50.39-012).
- Specify non-intrusion invariant, bounded drift history + eviction, visibility-mode sampling control + cost notifications, always-full canonical overflow schema, explicitly flagged non-authoritative what-if actions, and deterministic fallback for malformed inputs.
- Require integration with an external deterministic policy engine for what-if gating (HLR-10.50.39-013) and externally configurable thresholds (HLR-10.50.39-011).
- Define exposure of lifecycle_state and flush_epoch per a 10-series canonical lifecycle model (HLR-10.50.39-015).
- Specify read-only consumption boundaries for GB/IB/OuB without creating supervisory loops (HLR-10.50.39-017).
- Tie verification obligations to the 8 exploration scenarios in 40.39 software_description (stable, high-drift/what-if, overflow, oscillation, visibility, reproducibility, noisy input, lifecycle) plus schema compliance and negative-path malformed-input cases.
- Keep MB strictly advisory/observability-only; numeric policy and full TCU enforcement live in 20.95/50-series numeric areas.
- Update 50.80_logging_and_observability_design.md when MB outputs become inputs to broader event/telemetry contracts.
