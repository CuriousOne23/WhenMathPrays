## Findings 2 Supplemental: Conservative Performance Hypotheses

### Conditional X-Factor Performance Envelope

- Question ID: Q-F2-07
- Section: Findings 2
- Question: Under what conditions could the architecture show materially better control-oriented performance than current mainstream AI systems?
- Conclusion: It may outperform strong LLM-centric and tool-augmented agent baselines on narrowly defined control, replay, and policy-sensitive tasks, but only if the deterministic core, explicit semantics, and supervision boundaries are fully implemented and benchmarked.
- Evidence status: Unverified conjecture
- Baseline/comparator: A fixed comparator set consisting of one strong mainstream chat LLM, one tool-augmented agentic baseline, and one explicit-state deterministic baseline.
- Task family: Deterministic replay tasks, state-continuity tasks, policy-constrained interaction tasks, bounded failure recovery tasks, and long-horizon control tasks with fixed fixtures.
- Metric definition: Each metric must be reported as a ratio or delta against the fixed baseline on the same task family, using identical inputs, versions, and logging rules.
- Mechanism plausibility: Deterministic state transitions, explicit semantics, governed cognition, output-only randomness, and append-only traceability plausibly improve repeatability and reduce hidden-state drift.
- Performance hypothesis: The architecture may plausibly achieve moderate-to-strong gains on control-oriented metrics, but no multiplicative claim should be stated until measured. Provisional placeholders only: stability improvement = to be measured; policy adherence improvement = to be measured; replayability = exact replay under fixed inputs and versions only; long-horizon reliability = to be measured; bounded-failure reduction = to be measured.
- Assumptions: Identical task fixtures; fixed model/version/build hashes; no hidden nondeterministic channels; deterministic serialization; bounded context size; explicit operator interventions logged; comparator systems run under the same evaluation harness.
- Conditions: Claims are valid only for tasks where the architecture’s explicit control mechanisms are actually exercised and where success criteria are defined before execution.
- What would confirm: Repeated benchmark wins with statistically stable improvements on control, replay, and policy-sensitive metrics, plus no regression on comparator sanity checks.
- What would falsify: No measurable advantage over simpler baselines, or improvements disappear when the task family, versioning, or logging conditions are tightened.
- Confidence: Low
- Next de-risking step: Build one deterministic vertical-slice benchmark suite and record per-metric baseline deltas before estimating any numeric ranges.

### Conditional Power, Cost, and Cognitive Throughput Envelope

- Question ID: Q-F2-08
- Section: Findings 2
- Question: Under what conditions could the architecture improve efficiency or throughput relative to current AI systems?
- Conclusion: It may improve cost and power efficiency only if the explicit-state architecture reduces wasted recomputation, supervision overhead, and retry loops enough to offset the extra orchestration cost.
- Evidence status: Unverified conjecture
- Baseline/comparator: The same fixed comparator set used for control benchmarks, measured under matched hardware, token budgets, and runtime limits.
- Task family: Fixed-workload reasoning tasks, multi-step agent tasks, replay-heavy debugging tasks, and policy-constrained interaction tasks where repeated runs are meaningful.
- Metric definition: Power efficiency = task completions or correct benchmark units per joule; cost efficiency = task completions or correct benchmark units per dollar; cognitive throughput = verified benchmark units completed per joule; cost-quality envelope = quality score at a fixed cost ceiling relative to baseline.
- Mechanism plausibility: Output-only randomness, explicit state, and governed transitions may reduce avoidable retries and improve trace efficiency, but the orchestration layer may also add overhead.
- Performance hypothesis: The architecture might achieve modest-to-material gains on efficiency metrics for tasks with substantial replay or supervision overhead, but any larger range should remain a placeholder until measured.
- Assumptions: The benchmark counts only task-relevant work; supervisory overhead is included in the measurement; hardware and runtime are comparable; the task family is stable enough to measure efficiency without gaming the metric.
- Conditions: Claims are valid only when the cost of governance and state management is measured as part of total system cost, not omitted.
- What would confirm: Lower total cost or lower total power for the same validated output quality, with gains persisting across repeated runs and not disappearing after overhead is counted.
- What would falsify: Efficiency gains vanish once supervision, logging, retries, and coordination overhead are included.
- Confidence: Low
- Next de-risking step: Define a single counting rule for "meaningful cognitive step" and validate it on one small benchmark before making any ratio claim.

### Meaningful Cognitive Step Definition

- Question ID: Q-F2-09
- Section: Findings 2
- Question: What is a meaningful cognitive step, and how should it be measured?
- Conclusion: A meaningful cognitive step is a benchmark-scored state transition or decision that advances the task toward a pre-declared success condition and changes the validated trace in a way that is not equivalent to a no-op, formatting change, or repeated artifact emission.
- Evidence status: Specified
- Baseline/comparator: The same benchmark trace counted under the comparator systems, using the same step-counting rule.
- Task family: Multi-step reasoning, controlled planning, and stateful interaction tasks with explicit success criteria.
- Metric definition: Count only steps that satisfy all of the following: they are logged, they are attributable to a specific state transition or decision, they alter the validated task state, and they can be mapped to a predeclared success path or corrective action.
- Mechanism plausibility: Explicit state transitions and append-only traces make this type of counting feasible; without those, the metric becomes ambiguous.
- Performance hypothesis: The architecture may increase the number of counted meaningful steps per joule or per dollar on tasks that require repeated stateful reasoning, but the count must not be treated as inherently beneficial without quality validation.
- Assumptions: The benchmark defines the task state model in advance; the trace format is stable; no step inflation is allowed through trivial micro-steps or logging artifacts.
- Conditions: The metric is valid only when each counted step is independently reviewable and linked to task progress.
- What would confirm: Independent raters or an agreed scoring script count the same steps from the same trace.
- What would falsify: The count varies materially with scorer interpretation or can be gamed by splitting work into artificial micro-steps.
- Confidence: Medium
- Next de-risking step: Publish a step-counting rubric and test it on a small deterministic replay benchmark.

### Appendix Claim Set A — Conditional X-Factor Performance Envelope

The following is a compact appendix copy of the conservative hypothesis set from Findings 2.

- Evidence status: Unverified conjecture
- Baseline/comparator: Fixed comparator set spanning a mainstream chat LLM, a tool-augmented agentic baseline, and an explicit-state deterministic baseline

- Metric definition: Report ratios or deltas against the fixed baseline on the same task family using identical inputs, versions, and logging rules
- Mechanism plausibility: Deterministic state transitions, explicit semantics, governed cognition, output-only randomness, and append-only traceability plausibly improve repeatability and reduce hidden-state drift
- Assumptions: Identical fixtures, fixed hashes, no hidden nondeterministic channels, deterministic serialization, bounded context, logged operator interventions

### Appendix Claim Set B — Conditional Power, Cost, and Cognitive Throughput Envelope

- Evidence status: Unverified conjecture
- Baseline/comparator: Same fixed comparator set, measured under matched hardware, token budgets, and runtime limits
- Task family: Fixed-workload reasoning, multi-step agent tasks, replay-heavy debugging, and policy-constrained interaction tasks
- Metric definition: Power efficiency = task completions or correct benchmark units per joule; cost efficiency = task completions or correct benchmark units per dollar; cognitive throughput = verified benchmark units completed per joule; cost-quality envelope = quality score at a fixed cost ceiling relative to baseline
- Mechanism plausibility: Output-only randomness, explicit state, and governed transitions may reduce avoidable retries and improve trace efficiency, but orchestration overhead may offset gains
- Assumptions: The benchmark counts only task-relevant work; supervisory overhead is included; hardware/runtime are comparable; the task family resists gaming
- Conditions: Claims are valid only when governance and state-management cost are included in total system cost
- What would confirm: Lower total cost or power for the same validated quality, with gains persisting after overhead is counted
- What would falsify: Efficiency gains disappear once supervision, logging, retries, and coordination overhead are included

### Appendix Claim Set C — Meaningful Cognitive Step Definition

- Evidence status: Specified
- Baseline/comparator: The same benchmark trace counted under comparator systems using the same step-counting rule
- Task family: Multi-step reasoning, controlled planning, and stateful interaction tasks with explicit success criteria
- Definition: A meaningful cognitive step is a benchmark-scored state transition or decision that advances the task toward a pre-declared success condition and changes the validated trace in a way that is not equivalent to a no-op, formatting change, or repeated artifact emission
- Metric definition: Count only steps that are logged, attributable to a specific state transition or decision, alter the validated task state, and map to a predeclared success path or corrective action
- Mechanism plausibility: Explicit state transitions and append-only traces make this type of counting feasible; without those, the metric becomes ambiguous
- Assumptions: The benchmark defines the task state model in advance, the trace format is stable, and no step inflation is allowed through trivial micro-steps or logging artifacts
- Conditions: The metric is valid only when each counted step is independently reviewable and linked to task progress
- What would confirm: Independent raters or an agreed scoring script count the same steps from the same trace
- What would falsify: The count varies materially with scorer interpretation or can be gamed by splitting work into artificial micro-steps
