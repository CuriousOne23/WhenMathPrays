# **10.10.30 Interrupts and Preemption Model**

## **1. Purpose and Scope**
This document defines the **interrupt and preemption architecture** of the Thought Simulator (TS).  
It specifies the interrupt levels, service guarantees, preemption rules, supervisory authority, safety boundaries, and deterministic handling of asynchronous events.

This document is **normative**.  
All TS modules must comply with the interrupt semantics defined here.

---

## **2. Architectural Principles**
The interrupt model is governed by the following principles:

- **Deterministic handling:** interrupts must be processed in a predictable, reproducible order.  
- **Safety first:** supervisory and regulatory interrupts override cognitive processing.  
- **Non‑interference:** cognitive modules cannot interrupt each other.  
- **Bounded latency:** each interrupt level has a maximum service time.  
- **Replayability:** all interrupts must be logged and reconstructable.  
- **Isolation:** interrupts cannot mutate module state outside defined boundaries.  
- **Explicitness:** no implicit interrupts; all interrupts must be declared and logged.  

---

## **3. Interrupt Sources**
Only the following components may generate interrupts:

### **3.1 Governor Block (GB)**
- supervisory safety  
- escalation  
- semantic boundary violations  
- inquiry lifecycle violations  

### **3.2 Regulator**
- ΔH% overflow  
- routing fan‑out violations  
- resource exhaustion  
- safety envelope breaches  

### **3.3 Scheduler**
- cycle boundary enforcement  
- timing violations  
- deterministic ordering enforcement  

### **3.4 Safety Layer**
- emergency stop  
- catastrophic fault detection  
- invariant violations  

---

## **4. Components Forbidden from Generating Interrupts**
The following modules **must not** generate interrupts:

- OB  
- TB  
- IB  
- COB  
- any cognitive operator  
- any module performing semantic interpretation  

These modules may **request** supervisory review, but cannot interrupt execution.

---

## **5. Interrupt Levels**
Interrupts are classified into four levels, each with strict semantics and service guarantees.

### **5.1 Level 0 (L0) — Emergency Stop**
**Purpose:** prevent catastrophic failure or unsafe behavior.  
**Examples:** invariant violation, corrupted state, impossible ΔH% transition.  
**Service Guarantee:** immediate; must preempt all activity.  
**Effect:**  
- halt all cognitive processing  
- freeze state  
- escalate to GB  
- enter safe‑mode  

### **5.2 Level 1 (L1) — Safe‑Mode Transition**
**Purpose:** enforce safety boundaries without halting the system.  
**Examples:** repeated overflow, regulator hard limit, GB supervisory escalation.  
**Service Guarantee:** must be serviced before next cycle boundary.  
**Effect:**  
- suspend non‑critical operators  
- restrict routing  
- reduce fan‑out  
- enforce conservative ΔH% limits  

### **5.3 Level 2 (L2) — Slowdown/Dampen**
**Purpose:** reduce system activity to maintain stability.  
**Examples:** soft ΔH% drift, high operator cost, near‑overflow.  
**Service Guarantee:** must be serviced within two cycle steps.  
**Effect:**  
- reduce operator frequency  
- reduce routing throughput  
- apply ΔH% dampening  

### **5.4 Level 3 (L3) — Advisory**
**Purpose:** notify scheduler/GB of non‑critical conditions.  
**Examples:** unusual routing pattern, minor timing drift.  
**Service Guarantee:** best‑effort within the cycle.  
**Effect:**  
- logged  
- may trigger GB review  
- no immediate preemption  

---

## **6. Interrupt Service Ordering**
Interrupts are serviced according to the following deterministic priority:

1. **L0 (Emergency Stop)**  
2. **L1 (Safe‑Mode Transition)**  
3. **L2 (Slowdown/Dampen)**  
4. **L3 (Advisory)**  

Within the same level:

- earlier timestamp wins  
- lower sequence number wins  
- if tied: deterministic module ID ordering  

No nondeterministic arbitration is permitted.

---

## **7. Preemption Rules**
### **7.1 What Can Be Preempted**
- cognitive operators  
- routing  
- TB interpretation  
- IB lifecycle transitions  
- merge operations (except commit phase)  

### **7.2 What Cannot Be Preempted**
- MTP commit  
- safe‑mode entry  
- emergency stop handling  
- regulator hard‑limit enforcement  
- scheduler cycle boundary enforcement  

### **7.3 Preemption Windows**
The scheduler defines explicit interrupt windows:

- **pre‑OB**  
- **post‑TB**  
- **post‑IB**  
- **pre‑merge**  
- **post‑merge**  

Interrupts outside these windows are queued unless L0.

---

## **8. Interrupt Message Structure**
All interrupts must include:

- interrupt_level  
- source  
- timestamp  
- sequence_number  
- reason_code  
- lineage  
- ΔH% (if applicable)  
- payload (immutable)  
- signature  

Malformed interrupts must be rejected.

---

## **9. Interrupt Handling Pipeline**
1. **Interrupt generated**  
2. **Scheduler receives interrupt**  
3. **Scheduler classifies interrupt level**  
4. **Scheduler determines preemption window**  
5. **Scheduler halts or suspends affected modules**  
6. **Regulator evaluates safety envelope**  
7. **GB performs supervisory review**  
8. **Scheduler resumes or transitions to safe‑mode**  
9. **Interrupt logged**  
10. **Cycle continues or halts**  

---

## **10. Denial, Acceptance, and Deferral**
Interrupts must be explicitly acknowledged:

### **10.1 ACCEPT**
- interrupt is valid  
- service begins immediately or at next window  

### **10.2 DENY**
- interrupt malformed  
- invalid source  
- invalid level  
- reason code required  

### **10.3 DEFER**
- interrupt valid but cannot be serviced until next window  
- timestamp and retry window logged  

No implicit acceptance is allowed.

---

## **11. Safety Envelope Enforcement**
The regulator enforces:

- ΔH% hard limits  
- routing fan‑out limits  
- operator cost limits  
- cycle time limits  
- memory bounds  

Violations automatically generate L1 or L0 interrupts.

---

## **12. Logging and Replayability**
All interrupts must be logged with:

- full message contents  
- timestamp  
- sequence number  
- interrupt level  
- source  
- reason code  
- ΔH%  
- lineage  
- scheduler actions  
- regulator actions  
- GB supervisory actions  

Logs must support deterministic replay.
