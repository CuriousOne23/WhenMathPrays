# **10.10.40 Scheduler and Regulator Architecture**

## **1. Purpose and Scope**
This document defines the **scheduler** and **regulator** as first‑class architectural components of the Thought Simulator (TS).  
It specifies their responsibilities, boundaries, timing model, interaction rules, safety envelopes, and the deterministic control‑plane mechanisms that govern all module execution.

This document is **normative**.  
All TS modules must conform to the scheduler and regulator semantics defined here.

---

## **2. Architectural Principles**
The scheduler and regulator operate under the following principles:

- **Deterministic control:** execution order is fixed, reproducible, and cycle‑bounded.  
- **Non‑cognitive:** neither component performs semantic interpretation or inference.  
- **Safety‑first:** supervisory and regulatory constraints override cognitive processing.  
- **Isolation:** scheduler and regulator cannot mutate cognitive state directly.  
- **Boundedness:** all timing, ΔH%, fan‑out, and resource usage are explicitly bounded.  
- **Transparency:** all actions are logged with lineage and reason codes.  
- **Replayability:** all control‑plane decisions must be reconstructable.  

---

# **3. Scheduler Architecture**

## **3.1 Role of the Scheduler**
The scheduler is the **deterministic execution controller** of the TS.  
It is responsible for:

- ordering module execution  
- enforcing cycle boundaries  
- enforcing timing budgets  
- managing interrupt windows  
- coordinating preemption  
- ensuring deterministic sequencing  
- validating module readiness  
- routing supervisory and regulatory events  

The scheduler **does not**:

- perform cognitive inference  
- modify semantic content  
- alter TP or MTP state  
- interpret OB/TB/IB/COB payloads  

---

## **3.2 Execution Ordering**
The scheduler enforces the canonical TS pipeline order:

1. Routing  
2. OB extraction  
3. TB interpretation  
4. IB lifecycle transitions  
5. COB operator execution  
6. Merge  
7. GB supervisory review  
8. Regulation  
9. Commit to MTP  
10. Cycle boundary enforcement  

No module may execute outside its assigned position.

---

## **3.3 Cycle Model**
A TS cycle consists of:

- **pre‑cycle checks**  
- **module execution sequence**  
- **interrupt window**  
- **supervisory review**  
- **regulation**  
- **commit**  
- **cycle boundary enforcement**

The scheduler guarantees:

- no cross‑cycle state leakage  
- deterministic cycle start and end  
- monotonic timestamps  
- strict ordering of events  

---

## **3.4 Timing Model**
Each module has:

- **maximum execution time**  
- **minimum execution time**  
- **expected execution time**  
- **interruptible regions**  
- **non‑interruptible regions**  

If a module exceeds its timing budget:

- regulator is notified  
- scheduler may preempt  
- GB may escalate  

---

## **3.5 Interrupt Windows**
The scheduler defines explicit interrupt windows:

- pre‑OB  
- post‑TB  
- post‑IB  
- pre‑merge  
- post‑merge  
- pre‑commit  

Interrupts outside these windows are queued unless L0.

---

## **3.6 Scheduler Message Handling**
The scheduler receives:

- interrupts  
- supervisory requests  
- regulatory events  
- module readiness signals  
- timing violation alerts  

The scheduler must:

- classify events  
- determine priority  
- enforce ordering  
- route events to GB or regulator  
- log all actions  

---

# **4. Regulator Architecture**

## **4.1 Role of the Regulator**
The regulator enforces **safety envelopes** and **resource constraints**.  
It is responsible for:

- ΔH% enforcement  
- routing fan‑out limits  
- operator cost limits  
- overflow detection  
- memory bounds  
- cycle time bounds  
- safety envelope enforcement  
- generating regulatory interrupts  

The regulator **does not**:

- perform cognitive inference  
- modify semantic content  
- alter TP or MTP state  
- override scheduler ordering  

---

## **4.2 ΔH% Enforcement**
The regulator enforces:

- **ΔH% hard limits**  
- **ΔH% soft limits**  
- **ΔH% monotonicity rules**  
- **ΔH% normalization** (may be offloaded to coprocessor)

Violations generate:

- L1 (safe‑mode)  
- or L0 (emergency stop)  

depending on severity.

---

## **4.3 Routing Fan‑Out Limits**
The regulator enforces:

- maximum number of branches  
- maximum inquiry depth  
- maximum parallel operators  
- maximum TP proliferation  

Violations generate L2 or L1 interrupts.

---

## **4.4 Operator Cost Limits**
Each cognitive operator has:

- cost profile  
- maximum allowed cost  
- cumulative cycle cost  

If operator cost exceeds limits:

- regulator issues L2 slowdown  
- scheduler reduces operator frequency  
- GB may escalate  

---

## **4.5 Memory and Resource Bounds**
The regulator enforces:

- memory usage limits  
- buffer size limits  
- queue depth limits  
- snapshot size limits  

Overflow triggers:

- L1 safe‑mode  
- or L0 emergency stop  

---

## **4.6 Cycle Time Bounds**
The regulator monitors:

- cycle duration  
- module execution time  
- interrupt handling time  
- merge time  
- commit time  

If cycle time exceeds bounds:

- regulator issues L2 slowdown  
- scheduler adjusts timing windows  

---

# **5. Scheduler–Regulator Interaction**

## **5.1 Event Flow**
1. Regulator detects violation  
2. Regulator generates interrupt  
3. Scheduler receives interrupt  
4. Scheduler classifies and routes  
5. GB performs supervisory review (if required)  
6. Scheduler enforces action  
7. Regulator logs outcome  

---

## **5.2 Separation of Concerns**
- Scheduler controls **when** modules run  
- Regulator controls **whether** modules may run  
- GB controls **why** modules may or may not run  

None may perform the responsibilities of the others.

---

## **5.3 Forbidden Interactions**
- Regulator may not reorder modules  
- Scheduler may not modify ΔH%  
- GB may not modify semantic content  
- Cognitive modules may not bypass scheduler or regulator  

---

# **6. Safety Envelopes**

## **6.1 Hard Safety Envelope**
Violations trigger L0:

- corrupted state  
- impossible ΔH% transition  
- invariant violation  
- memory exhaustion  
- catastrophic operator failure  

## **6.2 Soft Safety Envelope**
Violations trigger L1 or L2:

- near‑overflow  
- soft ΔH% drift  
- excessive fan‑out  
- timing drift  

---

# **7. Logging and Replayability**
Both scheduler and regulator must log:

- all interrupts  
- all timing events  
- all regulatory actions  
- all supervisory escalations  
- all cycle boundaries  
- all preemption events  
- all safety envelope violations  

Logs must support deterministic replay.
