# **10.10.20 Interprocess Communication and Channels**

## **1. Purpose and Scope**
This document defines the **interprocess communication (IPC) architecture** of the Thought Simulator (TS).  
It specifies the channel types, message formats, communication rules, ordering guarantees, arbitration, and minimum communication requirements that govern all module‑to‑module interactions.

This document is **normative**.  
All TS modules must communicate exclusively through the channels and protocols defined here.

---

## **2. Architectural Principles for Communication**
The TS IPC model is governed by the following principles:

- **Explicitness:** all communication occurs through declared channels; no hidden backchannels.  
- **Determinism:** message ordering, delivery, and processing are deterministic.  
- **Isolation:** modules cannot mutate each other’s state; all data is passed by value.  
- **Boundedness:** channel width, message size, and queue depth are explicitly bounded.  
- **Replayability:** all messages are serializable and reconstructable.  
- **Portability:** no platform‑specific IPC mechanisms; all channels are logical constructs.  
- **Safety:** supervisory and regulatory messages cannot be bypassed or suppressed.  

---

## **3. Channel Types**
The TS defines three canonical channel types:

### **3.1 Immutable Message Channels**
- Primary communication mechanism.  
- Messages are immutable once created.  
- Sender and receiver share no mutable state.  
- Used for InB→RB, RB→OB, OB→TB, TB→IB, RB→TR routine invocation, TR routine→IB routing metadata handoff, IB→COB‑OPS, COB‑OPS→IB, IB→GB, OuB→GB (supervisory tag path), GB→scheduler, scheduler→modules, CIL→GB, and COP→GB (proposal-only).

### **3.2 Structured State Snapshot Channels**
- Used when a module must pass a structured TP or MTP snapshot.  
- Snapshots are read‑only to the receiver.  
- Snapshots must include lineage and ΔH% metadata.

### **3.3 Deterministic Event Queues**
- Used for asynchronous supervisory or regulatory events.  
- Queue ordering is deterministic and timestamp‑based.  
- Maximum depth is bounded; overflow triggers regulator action.

---

## **4. Forbidden Communication Mechanisms**
The following are strictly prohibited:

- shared mutable memory  
- direct pointer/reference passing  
- implicit cross‑module access  
- global mutable variables  
- side‑effects outside module boundaries  
- bypassing scheduler or regulator channels  
- unlogged communication  

Any violation constitutes an architectural fault.

---

## **5. Channel Width and Message Size**
### **5.1 Channel Width**
Each channel has a defined **maximum width**, representing the maximum number of fields or bytes that may be transmitted in a single message.

- OB→TB: narrow  
- TB→IB: medium  
- IB→COB‑OPS: wide  
- COB‑OPS→IB: medium  
- IB→GB: narrow  
- GB→scheduler: narrow  
- scheduler→modules: narrow  

Additional channels (including InB→RB, RB→OB, OuB→GB, CIL→GB, COP→GB, and GB→CIL/COB supervisory application paths) are bounded by the parameter table referenced in 5.3.

### **5.2 Message Size Limits**
- Maximum message size is defined per channel.  
- Oversized messages must be compressed, summarized, or rejected.  
- Compression must be deterministic and reversible.

### **5.3 Normative vs Tunable Bounds**
This architecture document is normative about **which bounds must exist** and **how bound violations are enforced**.

Concrete numeric values (for example, channel width in bytes/fields, maximum message size, and queue depth) are normative in a separate TS parameter table document.

The parameter table may be updated under controlled change management without renumbering this architecture specification, provided that boundedness, determinism, replayability, and safety guarantees remain satisfied.

---

## **6. Message Structure**
All messages must include the following fields:

- **source** (module ID)  
- **destination** (module ID)  
- **message_type**  
- **timestamp** (monotonic, cycle‑relative)  
- **sequence_number**  
- **lineage** (full provenance chain)  
- **ΔH%** (if applicable)  
- **payload** (immutable content)  
- **signature** (module‑specific provenance tag)  

For routing-affecting messages (including RB/TR gate and TR routine execution events), messages must also include:

- **tp_id**
- **tr_needs_update** (boolean)

Messages lacking any required field must be rejected.

---

## **7. Synchronous vs Asynchronous Communication**
### **7.1 Synchronous Channels**
Used for deterministic pipeline stages:

- InB→RB  
- RB→OB  
- OB→TB  
- TB→IB  
- RB→TR routine invocation (iff TP.tr_needs_update = true)  
- TR routine→IB metadata handoff  
- IB→COB‑OPS  
- COB‑OPS→IB  
- IB→MTP merge  

Characteristics:

- blocking  
- ordered  
- deterministic  
- scheduler‑controlled  

### **7.2 Asynchronous Channels**
Used for supervisory and regulatory events:

- GB→scheduler  
- regulator→scheduler  
- scheduler→modules (interrupt windows)  
- CIL→GB supervisory escalation  
- COP→GB proposal submission (propose-only)  
- GB→CIL/COB supervisory application at safe boundaries  

Characteristics:

- queued  
- timestamp‑ordered  
- bounded depth  
- deterministic dequeue rules  

---

## **8. Ordering Guarantees**
The TS guarantees:

- **FIFO ordering** per channel  
- **total ordering** within a cycle  
- **cycle boundary isolation**  
- **no message reordering**  
- **no speculative execution**  

For conversation decomposition paths, COP proposals are visible only at deterministic safe boundaries and never bypass GB arbitration.

If ordering cannot be guaranteed, the scheduler must halt the cycle.

---

## **9. Arbitration Rules**
If multiple messages contend for the same channel:

1. **Priority:** supervisory > regulatory > cognitive  
2. **Timestamp:** earlier timestamps win  
3. **Sequence number:** lower sequence wins  
4. **Tie:** deterministic module ID ordering  

No nondeterministic arbitration is permitted.

---

## **10. Request/Response Protocol**
All module requests must follow the explicit request/response protocol:

### **10.1 Request Fields**
- request_id  
- caller  
- target  
- reason_code  
- priority  
- payload  

### **10.2 Valid Responses**
- **ACCEPT**  
- **DENY** (with reason code)  
- **DEFER** (with retry window)  

### **10.3 Forbidden Responses**
- implicit acceptance  
- silent failure  
- partial acceptance  
- unlogged denial  

---

## **11. Minimum Communication Requirements**
Every module must:

- log all outgoing messages  
- validate all incoming messages  
- reject malformed messages  
- include lineage in all payloads  
- include ΔH% when applicable  
- include provenance signatures  
- serialize all messages deterministically  
- respect channel width limits  
- respect queue depth limits  
- enforce supervisory mediation for requests affecting global behavior  
- prohibit direct OuB→IB routing and require GB-approved inquiry gating  

RB and TR routine interactions must also satisfy:

- RB routes to TR routine if and only if TP.tr_needs_update = true
- RB must not route to TR routine when TP.tr_needs_update = false
- successful TR routine completion clears TP.tr_needs_update = false
- failed TR routine completion preserves TP.tr_needs_update = true

---

## **12. Error Handling**
### **12.1 Message Rejection**
A message must be rejected if:

- required fields are missing  
- payload exceeds channel width  
- lineage is malformed  
- ΔH% is out of bounds  
- signature is invalid  
- timestamp is non‑monotonic  

### **12.2 Recovery**
Upon rejection:

- scheduler logs the fault  
- regulator evaluates safety envelope  
- GB may escalate to safe‑mode  

---

## **13. Logging and Traceability**
All communication must be logged with:

- full message contents  
- timestamp  
- sequence number  
- channel ID  
- sender/receiver IDs  
- ΔH%  
- lineage  
- supervisory flags  

Logs must be replayable and reconstructable.
