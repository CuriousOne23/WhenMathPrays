# 10.50.120_COP Requirements (Canonical)

## 1. Purpose

This document is the canonical Conversation Coprocessor (COP) requirement anchor for promotion-governed proposal handling, supervisory staging, safe-boundary commit visibility, and deterministic overload control behavior.

## 2. Canonical HLR Set

- `HLR-20.033-002`: COP proposals must include deterministic provenance metadata and input hashing.
- `HLR-20.033-003`: COP proposal effects must become visible only at deterministic safe-boundary commits.
- `HLR-20.033-006`: safety-critical COP proposals must receive deterministic bounded-latency handling guarantees.
- `HLR-20.033-008`: unsupported COP policy states must reject deterministically with fixed audit reason codes.
- `HLR-20.033-011`: COP ordering-critical behavior must derive from deterministic sequence/token state only.
- `HLR-20.033-012`: COP commit visibility must occur only at deterministic safe boundaries.
- `HLR-20.033-013`: COP profile/policy overlaps must resolve by execution-signature-bound profile precedence over environment defaults.

## 3. Canonical Scope

This canonical COP requirement anchor governs:

- deterministic proposal provenance hashing and append-only audit capture
- deterministic bounded queue admission and safety-critical overload handling
- deterministic GB-mediated approval staging and safe-boundary-only commit visibility
- deterministic profile precedence over environment-default fairness and overload policy
- deterministic reject-with-audit behavior for unsupported profile states and ordering violations

## 10.50.120.TCU COP CPU Execution Cycle Requirements

**Anchor authority:**

### 10.50.120.TCU.10 Bounded per-tick cost
- Requirement ID: 10.50.120.TCU.10
- Statement: For any tick with fixed input cardinality N and fixed configuration, the subsystem
  MUST complete its work within a bounded number of CPU cycles C_max(cop) per tick phase,
  as constrained by 20.150. No unbounded or data-dependent worst-case growth is permitted.

### 10.50.120.TCU.20 Deterministic behavior under fixed conditions
- Requirement ID: 10.50.120.TCU.20
- Statement: For fixed seed, fixed input cardinality N, fixed configuration, and fixed hardware/runtime profile,
  the subsystem MUST exhibit deterministic CPU cycle consumption within
  [C_min(cop), C_max(cop)] for the same scenario ID, as defined in 20.150.

### 10.50.120.TCU.30 Provisional vs measured budgets (promotion-controlled)
- Requirement ID: 10.50.120.TCU.30
- Statement: The subsystem MUST maintain two distinct TCU budgets:
  - provisional-budget(cop): design-time estimate used for planning and scheduling.
  - measured-budget(cop): empirically measured values produced by 40_playground harnesses and verified in 30_verification capsules.
  These MUST NOT be conflated in normative documents.
  measured-budget(cop) MAY ONLY be updated through promotion-controlled evidence from 30.

### 10.50.120.TCU.40 Tick budget share
- Requirement ID: 10.50.120.TCU.40
- Statement: The subsystem MUST declare its target percentage of the global tick budget
  (per 20.150) as a provisional-budget(cop) value, and MUST be verifiable against
  measured-budget(cop) from 30_verification capsules.
