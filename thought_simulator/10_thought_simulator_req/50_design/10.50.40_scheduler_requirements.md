# 10.50.40_Scheduler Requirements (Canonical)

## 1. Purpose

This document is the canonical scheduler requirement anchor for promotion-governed tick scheduling behavior.

## 2. Canonical HLR Set

- `HLR-20.440-001`: Scheduler selection order must remain deterministic and replayable for identical inputs and event sequences.
- `HLR-20.440-002`: Scheduler fairness policy must provide bounded progress for active ThoughtPoints and prevent starvation under configured limits.
- `HLR-20.440-003`: Scheduler contract validation must reject malformed inputs that could break deterministic execution (including empty TP IDs, non-monotonic ticks, and unsupported policy values).
- `HLR-20.440-004`: Scheduler shall emit rich, replay-safe observability including tie_break_rationale, cohort_metadata, window/preempt context, budget_status, fairness counters (wait_ticks, total_selected, last_scheduled_tick), and full event history.
- `HLR-20.440-005`: Scheduler shall enforce bounded internal state (history_max) consistent with 10.10.40 safety envelopes and 20.150 TCU constraints.
- `HLR-20.440-006`: Scheduler shall support and deterministically log interrupt windows (pre-OB, post-TB, post-TR, pre-merge, etc.) and preemption in the scheduling contract and observability.
- `HLR-20.440-007`: Scheduler shall support deterministic cohort selection and merge semantics, emitting cohort_metadata (is_cohort, cohort_size, merge_semantics="deterministic_stable_order") when max_active > 1.
- `HLR-20.440-008`: Scheduler shall apply deterministic tie-breaking with explicit tie_break_rationale and provenance (e.g., stable tp_id ordering) when priority signals are equal.

## 3. Canonical Scope

This canonical scheduler requirement anchor governs:

- deterministic per-tick selection behavior
- fairness and starvation-prevention obligations
- scheduler input validation and negative-path enforcement
- replay-safe scheduler observability evidence (rich rationale, cohort metadata, interrupt/preempt context, budget status, fairness counters)
- bounded internal state (history)
- interrupt window and preemption handling in contract and logs
- deterministic cohort selection and merge semantics
- deterministic tie-breaking with provenance

## 6. Canonical Scheduler Contract Elements (Normative at Design Layer)

The scheduler I/O contract (explored in 40.40_scheduler_prototypes and to be detailed in 50.40) SHALL support the following normative elements at the design layer:

- **from_contract payload** (initialization):
  - tick (non-negative int)
  - deterministic_mode (bool, default true)
  - policy ("round_robin" | "weighted_round_robin")
  - max_active (positive int)
  - history_max (positive int, for bounded state per HLR-005)
  - thoughtpoints: list of objects with at minimum tp_id (non-empty string), energy (non-negative float), coherence (non-negative float); optional state: total_selected, wait_ticks, last_scheduled_tick

- **apply_contract event** (for schedule_tick):
  - event_type: "schedule_tick"
  - tick: strictly increasing from prior
  - optional: policy, max_active (updates)
  - optional control-plane context (non-cognitive): window (e.g. "pre_ob", "post_tb", "post_tr", "pre_merge", "none"), budget_tcu (non-negative int), preempt (bool)

- **snapshot / output**:
  - module, contract_version
  - tick, deterministic_mode, policy, max_active, round_robin_cursor, state_counter, history_max
  - last_selection_rationale (string)
  - last_cohort_metadata (object with is_cohort, cohort_size, merge_semantics)
  - last_budget_status (object)
  - last_window
  - thoughtpoints: list with full state (tp_id, energy, coherence, total_selected, wait_ticks, last_scheduled_tick)
  - history: list of events with event_type, tick, state_counter, selected_tp_ids, policy, payload (including tie_break_rationale, cohort_metadata, window, preempt, sim_tcu, budget_status)
  - verification_digest for replay integrity

All serialization SHALL use deterministic sorted-key JSON. The contract SHALL remain stable (additive fields only for backward compatibility).

## 10.50.40.TCU Scheduler CPU Execution Cycle Requirements

**Anchor authority:**
- 20.150_tcu_budgeting_requirements.md
- 10.10.10_system_architecture.md

### 10.50.40.TCU.10 Bounded per-tick cost
- Requirement ID: 10.50.40.TCU.10
- Statement: For any tick with fixed input cardinality N and fixed configuration, the subsystem
  MUST complete its work within a bounded number of CPU cycles C_max(scheduler) per tick phase,
  as constrained by 20.150. No unbounded or data-dependent worst-case growth is permitted.

### 10.50.40.TCU.20 Deterministic behavior under fixed conditions
- Requirement ID: 10.50.40.TCU.20
- Statement: For fixed seed, fixed input cardinality N, fixed configuration, and fixed hardware/runtime profile,
  the subsystem MUST exhibit deterministic CPU cycle consumption within
  [C_min(scheduler), C_max(scheduler)] for the same scenario ID, as defined in 20.150.

### 10.50.40.TCU.30 Provisional vs measured budgets (promotion-controlled)
- Requirement ID: 10.50.40.TCU.30
- Statement: The subsystem MUST maintain two distinct TCU budgets:
  - provisional-budget(scheduler): design-time estimate used for planning and scheduling.
  - measured-budget(scheduler): empirically measured values produced by 40_playground harnesses and verified in 30_verification capsules.
  These MUST NOT be conflated in normative documents.
  measured-budget(scheduler) MAY ONLY be updated through promotion-controlled evidence from 30.

### 10.50.40.TCU.40 Tick budget share
- Requirement ID: 10.50.40.TCU.40
- Statement: The subsystem MUST declare its target percentage of the global tick budget
  (per 20.150) as a provisional-budget(scheduler) value, and MUST be verifiable against
  measured-budget(scheduler) from 30_verification capsules.

## 7. Design Decisions

- The core 3 HLRs (001-003) were established early as the foundational requirements for scheduler determinism, fairness, and validation.
- HLRs 004-008 were added post 40.40 Phase B (approved) and 30.00 promotion to formalize additional behaviors strongly demonstrated in the exploratory prototype (rich observability, bounded state, interrupt/preempt, cohort/merge, tie-break provenance).
- The contract elements in section 6 capture the normative I/O and observability requirements stabilized from the 40.40 JSON-first contract.
- Exploratory policy details (e.g., specific weights in weighted_round_robin, exact default policy) remain non-canonical and are governed by 50-series / 10.50.40 policy engine mechanisms.

## 8. Open Questions

- Canonical default fairness policy (round_robin as baseline vs. weighted_round_robin or variants with aging) and validation of starvation bounds.
- Precise canonical tie-break key ordering and precedence (beyond stable tp_id) once 50.40 defines it.
- Exact integration points with regulator for ΔH% enforcement, fan-out, and overflow handoff.
- Whether additional runtime negative paths (e.g., empty active set mid-cycle) require explicit HLRs.
- Performance/determinism under high load (many active TPs, frequent interrupts) – to be measured via 40 harnesses and test benches.
