# 10.50.30_Basin Requirements (Canonical)

## 1. Purpose

This document is the canonical basin requirement anchor for promoted basin lifecycle behavior.

RB naming in this canonical anchor follows Routing Basin terminology for consistency with the 20-series design-constraint baseline.

## 2. Canonical HLR Set

- `HLR-20.330-001`: Basin state objects must expose a JSON-compatible IO contract that preserves `basin_id`, `tp_id`, and `state_counter` without transformation.
- `HLR-20.330-002`: Basin replay of identical deterministic contracts must produce identical final snapshots and identical verification digests.
- `HLR-20.330-003`: Basin validation must reject empty basin identifiers, duplicate provenance identifiers, and entropy-vector shape mismatches.

## 3. Canonical Scope

This canonical basin requirement anchor governs:

- basin IO contract preservation
- deterministic replay requirements
- validation and negative-path enforcement expectations
- basin-family contract applicability across OB, RB, GB, IB, TB, InB, OuB, and MB canonical variants

## 10.50.30.TCU Basin CPU Execution Cycle Requirements

**Anchor authority:**
- 20.150_tcu_budgeting_requirements.md
- 10.10.10_system_architecture.md

### 10.50.30.TCU.10 Bounded per-tick cost
- Requirement ID: 10.50.30.TCU.10
- Statement: For any tick with fixed input cardinality N and fixed configuration, the subsystem
  MUST complete its work within a bounded number of CPU cycles C_max(basin) per tick phase,
  as constrained by 20.150. No unbounded or data-dependent worst-case growth is permitted.

### 10.50.30.TCU.20 Deterministic behavior under fixed conditions
- Requirement ID: 10.50.30.TCU.20
- Statement: For fixed seed, fixed input cardinality N, fixed configuration, and fixed hardware/runtime profile,
  the subsystem MUST exhibit deterministic CPU cycle consumption within
  [C_min(basin), C_max(basin)] for the same scenario ID, as defined in 20.150.

### 10.50.30.TCU.30 Provisional vs measured budgets (promotion-controlled)
- Requirement ID: 10.50.30.TCU.30
- Statement: The subsystem MUST maintain two distinct TCU budgets:
  - provisional-budget(basin): design-time estimate used for planning and scheduling.
  - measured-budget(basin): empirically measured values produced by 40_playground harnesses and verified in 30_verification capsules.
  These MUST NOT be conflated in normative documents.
  measured-budget(basin) MAY ONLY be updated through promotion-controlled evidence from 30.

### 10.50.30.TCU.40 Tick budget share
- Requirement ID: 10.50.30.TCU.40
- Statement: The subsystem MUST declare its target percentage of the global tick budget
  (per 20.150) as a provisional-budget(basin) value, and MUST be verifiable against
  measured-budget(basin) from 30_verification capsules.
