# 10.50.200_mb_design_requirements.md

**Document ID:** 10.50.1500  
**Version:** 0.2  
**Date:** 2026-06-05  
**Status:** Draft - Incorporating 40.350 Phase B Evidence, 30.200 verification, and CP review feedback (canonical schemas, thresholds, replay, policy engine, lifecycle, malformed input, consumption)

## Role in Development Flow
This document translates exploratory evidence from 40.350_mb_prototypes and verification evidence from 30.200 into concrete **design requirements** for the Monitoring Basin (MB) subsystem. It feeds into the final canonical specification in the 10-series.

## Purpose
Define the design-level requirements for the Monitoring Basin (MB) as a **non-intrusive, deterministic, advisory-only observability and diagnostics subsystem**, based on 20.70 requirements and 40.350 prototype evidence.

**These requirements SHALL be normative and SHALL govern all MB implementations across platforms.**

## Canonical MBInput / MBOutput Schemas (Normative at Design Layer)

All MB implementations SHALL use the following canonical schemas. Implementations MAY extend with additional optional fields only if they are ignored for core contract behavior. Schema evolution SHALL follow the rules in HLR-10.50.1500-012.

### MBInput Schema

- **schema_version**: string, required (e.g. "1.0"). MUST be present for all serialized forms.
- **cycle**: integer, required, non-negative.
- **visibility_mode**: string enum ["low", "medium", "high", "full"], required.
- **basin_telemetry**: object (map<string, any>), required. MAY be empty.
- **lane_identifiers**: array<string>, required. Elements MUST be unique non-empty strings.
- **lineage**: object (map<string, any>), required. MUST contain at minimum "id": string.
- **mtp_snapshot**: object, required, with the following fields:
  - **delta_h_trend**: number (finite float), required.
  - **active_ib_count**: integer >= 0, required.
  - **oscillation_flag**: boolean, required.
  - **contradiction_level**: number in [0.0, 1.0], required.
- **stability_metadata**: object (map<string, any>), optional. Default: empty object.

### MBOutput Schema

- **schema_version**: string, required (must match or be compatible with input version).
- **diagnostics_summary**: object (map<string, any>), required.
- **drift_indicators**: array<object>, required (may be empty).
- **advisory_recommendations**: array<object>, required (may be empty).
- **what_if_flags**: array<object>, required (may be empty). Each entry MUST contain "flagged": true, "non_authoritative": true, "policy_gated", "logged", "rationale", "cycle".
- **execution_diagnostics**: object, required. MUST include "cycle", "deterministic", "visibility_mode", "lifecycle_state", "intervention_count_so_far", "replay_safe".
- **telemetry**: object, required. MUST include "visibility_mode", "sampling_density", "tcu_cost_estimate", "user_notification" (may be null), "drift_history_depth", "flush_epoch".
- **overflow**: object, required. SHALL always contain the full canonical set of fields (see HLR-10.50.1500-014):
  - **overflow_flag**: boolean, required.
  - **overflow_type**: string, required when flag=true (e.g. "high_population", "high_drift", "none").
  - **overflow_source_basin**: string, required.
  - **overflow_cycle**: integer, required.
  - **truncated_fields**: array<string>, required (empty when none).
  - **ΔH%_normalization_applied**: number, required.
  - **tcu_overrun_amount**: number >=0, required.

All objects SHALL be serializable to JSON with deterministic key ordering (sorted keys) for reproducibility.

## Key Design Requirements

**HLR-10.50.1500-001:** MB SHALL operate exclusively as a non-intrusive monitoring layer and SHALL NOT perform direct meaning construction or mutate TP, MTP, OB, RB, or TB core semantic/cognitive state.

**HLR-10.50.1500-002:** MB SHALL accept a deterministic MBInput object (per the Canonical MBInput Schema above) and SHALL emit a deterministic MBOutput object (per the Canonical MBOutput Schema above). The input and output objects SHALL be the sole public contract for MB evaluation.

**HLR-10.50.1500-003:** All MB outputs SHALL be fully deterministic and reproducible: identical effective input + MTP context + seed-bounded state SHALL always produce identical MB outputs (including drift indicators, advisories, and telemetry).

**HLR-10.50.1500-004:** MB SHALL produce deterministic drift indicators over semantically relevant state deltas (e.g., ΔH% trend, oscillation, contradiction) with cycle, source, and lineage references.

**HLR-10.50.1500-005:** Any MB-triggered what-if, probe, or advisory action SHALL be explicitly flagged as non-authoritative, policy-gated, and logged. MB SHALL NEVER silently alter core basin behavior.

**HLR-10.50.1500-006:** MB overflow/degradation telemetry SHALL conform exactly to the canonical overflow field schema (overflow_flag, overflow_type, overflow_source_basin, overflow_cycle, truncated_fields, ΔH%_normalization_applied, tcu_overrun_amount) defined in 20.30 §8.3.

**HLR-10.50.1500-007:** MB SHALL support deterministic telemetry visibility modes (low, medium, high, full) that control only MB sampling density and diagnostics detail. When a mode materially increases estimated TCU cost, MB SHALL emit a deterministic, human-readable notification.

**HLR-10.50.1500-008:** MB SHALL maintain bounded internal drift history with explicit retention/eviction policy and SHALL expose lifecycle/execution diagnostics (lifecycle_state, intervention counts, flush epochs) for audit and replay.

**HLR-10.50.1500-009:** MB SHALL deterministically handle noisy or ill-formed observational signals without probabilistic inference or hallucinated reconstruction.

**HLR-10.50.1500-010:** All MB diagnostic and telemetry outputs SHALL preserve lineage/provenance references and SHALL be structured for deterministic replay, audit, and comparative analysis.

**HLR-10.50.1500-011:** All thresholds governing drift classification (e.g. "elevated"), overflow triggering, what-if activation, visibility cost notifications, and similar decision boundaries SHALL be explicitly defined, versioned, and externally configurable (e.g. via policy or configuration objects). The 10-series SHALL NOT hard-code numeric thresholds in MB implementations; instead, it SHALL define the mechanism by which thresholds are supplied, validated, versioned, and audited. Implementations SHALL support override for different environments while preserving determinism.

**HLR-10.50.1500-012:** MBInput and MBOutput SHALL include a `schema_version` field. All serialized outputs (JSON or equivalent) SHALL be stable under roundtrip serialization with deterministic key ordering (sorted keys). Implementations SHALL support forward/backward compatibility rules: unknown optional fields SHALL be ignored on read; missing required fields SHALL produce deterministic fallback per HLR-10.50.1500-016. Schema changes SHALL be versioned and SHALL NOT break existing replay artifacts without explicit migration.

**HLR-10.50.1500-013:** MB SHALL integrate with a policy engine that deterministically governs what-if, probe, and advisory activation. The policy engine SHALL define: allowed actions, gating rules (including explicit policy sources), logging requirements, and safety boundaries. MB SHALL NOT execute any what-if or probe action without explicit policy authorization. The policy engine itself SHALL be auditable and versioned.

**HLR-10.50.1500-014:** The overflow object SHALL always be present in MBOutput. It SHALL use the full canonical schema (all fields) at all times. When `overflow_flag` is false, non-applicable numeric fields SHALL be 0 and array fields SHALL be empty (no collapse to minimal form). This ensures consistent replay and audit surfaces.

**HLR-10.50.1500-015:** MB SHALL expose `lifecycle_state` and `flush_epoch` according to a canonical lifecycle model defined in the 10-series. The model SHALL enumerate allowed states (e.g. "initializing", "running", "exiting", "degraded"), valid transitions, and the semantics of flush epochs (cycle-based or event-based). `flush_epoch` SHALL be monotonically non-decreasing within a run.

**HLR-10.50.1500-016:** MB SHALL define and implement deterministic fallback behavior for missing, malformed, type-mismatched, out-of-range, or contradictory input fields (e.g. missing delta_h_trend, non-numeric active_ib_count, contradiction_level outside [0,1]). No probabilistic inference, reconstruction, or hallucination is permitted. Fallbacks SHALL be safe, explicit, logged, and reproducible. Defaults SHALL be documented and versioned.

**HLR-10.50.1500-017:** MB outputs SHALL be consumable by GB, IB, and OuB (and user-facing layers) without creating supervisory loops, authority conflicts, or direct mutation of core meaning-construction pathways. The 10-series SHALL define the allowed consumption patterns, read-only boundaries, and integration points. MB SHALL NOT assume or enforce any particular downstream consumer behavior.

## Design Decisions Informed by 40.350 Evidence

- A clean dataclass-style MBInput / MBOutput contract (now formalized in the Canonical Schemas section) is viable and matches the shapes requested in 20.70. The prototype's dict-based implementation is treated as exploratory scaffolding.
- Non-intrusion is straightforward to enforce at the prototype level (read-only evaluate) and is now locked as HLR-10.50.1500-001.
- Drift observation + explicit what-if flagging works cleanly and can be made fully deterministic (HLRs 004, 005, 013).
- Visibility modes + cost notifications can be implemented without side effects on core data (HLR-007).
- Overflow handling using the exact 20.30 canonical fields is practical and verifiable; the design now mandates the full schema always be present (HLR-014).
- Reproducibility (identical inputs → identical outputs on independent instances) is achievable and valuable for verification; this is now strengthened with schema_version + deterministic serialization rules (HLR-012).
- Synthetic snapshots matching the documented MTP fields are sufficient to exercise the contract during exploration; live integration is deferred (see Open Questions).
- Thresholds used in the 40.350 prototype (e.g. delta_h > 0.82 for what-if) are recognized as exploratory only. They are not normative; HLR-011 requires external configuration and versioning.
- Lifecycle observability (lifecycle_state, flush_epoch) was demonstrated; full state machine and semantics are now required by HLR-015.
- Deterministic handling of noisy input was shown; explicit fallback rules for all malformed cases are now mandated by HLR-016.
- Consumption by other basins is acknowledged as an open architectural boundary (HLR-017).

## Open Design Questions (to be resolved in 10-series)

- Exact numeric values and external configuration sources for thresholds and TCU budgets (HLR-10.50.1500-011); these will be supplied by 20.95/50-series numeric policy and must be mirrored here with validation rules.
- Concrete policy engine implementation and authoritative policy sources (HLR-10.50.1500-013) — prototype used simulated gates; 50-series must define the real engine.
- Detailed allowed consumption patterns and read APIs for GB/IB/OuB (HLR-10.50.1500-017) — boundaries are specified at high level; interface contracts belong in 50.30/50.80 or API layers.
- Integration with live (non-snapshot) pipeline objects while preserving the snapshot-based contract for reproducibility.
- Full lifecycle model state machine diagram and transition rules (HLR-10.50.1500-015) to be formalized with diagrams in supporting docs.
